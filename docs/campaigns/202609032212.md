### 4.2 Relational session port and phase protocol

The standard package must expose one canonical session type family. An interactive port is valid only when its exact concrete
function type is structurally equivalent to:

```text
(Option<State>, SessionEvent) -> SessionDecision<State>
```

Every occurrence of `State` is the same closed concrete ordinary type. It may contain supported finite ordinary values, options,
lists, records, and nominal variants, but no stream, capability resource, function, unresolved type parameter, runtime handle,
secret handle, or other live resource. Admission, compilation, strict artifact loading, and deployment preparation independently
reconstruct this relation and reject drift before the listener becomes ready.

`SessionEvent` has exactly these semantic cases:

- `open`: normalized path, query, and bounded ordered headers after a valid transport request but before upgrade;
- `message`: text or binary kind plus one task-scoped `Stream<Bytes>` for the completed message;
- `tick`: a coalesced operational wakeup with no wall-clock promise;
- `peer_close`: validated optional close code and bounded reason; and
- `shutdown`: resident service shutdown.

`SessionDecision<State>` has exactly these semantic cases:

- `accept`: next state and a bounded outbound batch;
- `continue`: next state and a bounded outbound batch;
- `reject`: bounded ordinary HTTP response, valid only for `open`;
- `close`: validated close code/reason and a bounded final outbound batch; and
- `finish`: no state or application output.

Phase validity is mechanical: `open` receives `None` and may return only `accept` or `reject`; `message` and `tick` receive
`Some(State)` and may return only `continue` or `close`; `peer_close` and `shutdown` receive `Some(State)` and may return only
`finish`. `accept` and `continue` install `Some(State)`; all terminal decisions install none. Wrong event/state or
event/decision pairs close or reject with a stable diagnostic and never become the next state.

Only one transition runs per session. Before another event observes it, a successful callback must fully validate its state and
output, commit the complete outbound batch to reserved bounded capacity, and then install the next state. A failed, cancelled,
exhausted, malformed, or protocol-invalid callback installs neither state nor partial output and closes the session. Effects
already performed retain the existing possible-visibility contract and are never replayed.

### 4.3 Structured scope, streams, and bounds

A long-lived connection is not one long-lived VM task. One admitted parent session scope owns one transport reader, one ordered
transition driver, one writer, at most one coalesced tick source, one cancellation lineage, every join/permit, retained state,
stream lease, and mailbox allocation. Children never detach.

Each callback is a finite resident task with its own work/deadline/resource scope. Session lifetime and idle bounds are
separate; the supported descriptor permits at least 24 hours without raising the one-hour callback ceiling. Controlled time may
prove this.

Inbound data frames feed a bounded task-scoped byte stream; graph code sees only a completed application-message event and must
consume or close the stream during that callback. Fragmentation, masking, ping/pong, and close control remain transport
authority. Outbound graph messages are bounded text or bytes. The writer may fragment them without changing message identity.

The descriptor and global policy must independently bound at least active sessions; pending handshakes; message/frame/header
bytes; stream chunk/buffer/total bytes; inbound and outbound mailbox items and aggregate bytes; state nodes and bytes; messages
and bytes per transition; callback work; tick interval; idle and total lifetime; close/cancellation grace; and process-wide
session-buffer bytes. Arithmetic is checked. There is no hidden queue, silent drop, or unaccounted whole-message copy.

Reserve capacity for the configured maximum transition output before invoking a potentially effectful callback, or provide an
observably equivalent guarantee. A slow writer therefore backpressures future callbacks before effects rather than failing after
a graph effect solely because output could not be queued. A tick is present at most once, never overtakes an accepted transport
event, and has no latency guarantee.

Peer close, transport/read/write failure, callback failure, timeout, overload, shutdown, or parent completion stops admission
for that session, cancels siblings, prevents new callbacks, joins every child, closes task streams, drops state and queued
messages, attempts one bounded close handshake where valid, and releases all permits exactly once. Listener overload rejects
before upgrade and does not disturb admitted sessions. Readiness is emitted only after exact artifact, target relation, limits,
grants, and adapter preparation succeed.

### 4.4 RFC 6455 server boundary

The first interactive transport is a plaintext RFC 6455 server over HTTP/1.1 on the existing listener boundary. It validates the
upgrade and `Sec-WebSocket-Accept`, client masking, legal fragmentation, UTF-8 text, control-frame rules, ping/pong, close
codes/reasons, and configured bounds. Malformed continuation, reserved bits/opcodes, invalid text, invalid control frames,
unmasked client data, oversized or truncated input, stalled peers, and abrupt disconnects are contained to the connection with
stable observations.

Graph `reject` returns bounded HTTP without upgrade; `accept` upgrades before application output. Negotiate no extension or
subprotocol. TLS, confidentiality, origin/proxy/browser policy, and authentication are not transport claims; the graph may
enforce path, origin, headers, and credentials. Exclude secrets/full payloads from readiness, diagnostics, and evidence.

### 4.5 Maintained `lkjournal-live-1` consumer

Add one `interactive` target and one maintained deployment descriptor while preserving HTTP `serve`, worker `work`, and their
shared first-party data authority.

The graph-owned protocol is not Nostr. `open` accepts only `/live` with a valid `lkjournal` bearer session. State retains the
actor and a bounded map from connection-local subscription IDs to the last observed resource revisions needed for change
detection.

Text input has two strict JSON-array operations: subscribe or replace a nonempty bounded subscription identifier, and
unsubscribe it. Subscribe emits actor-owned resource summaries in one deterministic graph-owned order followed by an
end-of-snapshot marker. A later coalesced tick scans the existing durable data authority and emits each newly created or
advanced resource once per subscription, then updates ordinary state. Replacing an identifier replaces its prior state;
unsubscribing removes only that identifier. Binary input, unknown operations, unknown fields or arity, malformed JSON, invalid
identifiers, excess subscriptions, and output expansion beyond bounds produce a deterministic application error or
graph-selected close.

Disconnect and restart discard only operational connections and ordinary session state. After reconnect and resubscribe, the
current durable snapshot is reconstructed from data authority; no runtime session state, Rust cache, or second durable cursor is
restored. Existing actor isolation still applies.

Service acceptance runs HTTP, the existing worker coverage where required, and the interactive target against one isolated
initialized data root. Two raw clients authenticated as one actor hold independent subscriptions; HTTP create and update become
server-pushed after ticks; replacing or unsubscribing on one client does not affect the other; a second actor cannot observe the
first actor's resources; one slow client cannot grow memory or stall another; restart drops connections but preserves data and
resubscription results.

No route, token validation, JSON grammar, subscription transition, scan/filter/order rule, message shape, or actor policy may be
authoritative in Rust or verifier fixtures; fixtures may encode only bounded expected transcripts.
