## 2. Fixed outcome and execution contract

**Final state: every eligible pure graph tail call runs without retaining its caller activation in
both production and canonical-reference execution, so the existing graph-owned standard fold and
independently authored recursive programs cross the former call-depth boundary through the copied
public executable while budgets, evaluation order, authority, and task-resource safety remain intact.**

The bottleneck is concrete: standard `list-fold-left<Item, State>` has an ordinary recursive index
helper, used by the maintained stateful HTTP consumer. Retained performance evidence reports
`normalized_call_depth` at 4,096 items. Current `Machine::call_code` pushes every graph call;
`ReferenceState::call_declaration` recursively evaluates every body. Raising limits, optimizing only
production, or replacing the fold with Rust does not close this result.

### Authority and eligible tail positions

The accepted graph alone owns function meaning, call targets, types, effects, and evaluation order.
Tail eligibility is a derivation, never an editable annotation, request flag, package privilege,
stored tail marker, or alternative program. Operational data and grants remain separate authorities.

A pure graph function's body is a tail context. Tail context propagates only into the selected
`if` branch, a `let` body after its ordered bindings, the last sequence item, and the selected
`match` arm after its scrutinee. A direct call or `invoke` in that context is eligible when its
resolved callee is a pure graph function. Include self recursion, same-package mutual recursion,
explicit rank-one instantiation, named indirect invocation, and calls across admitted package
boundaries. Dependency cycles and polymorphic recursion remain rejected by existing rules.

Arguments, invoke-callee evaluation, conditions, binding initializers, preceding sequence items,
scrutinees, constructors, and projections are not tail contexts. Constant/test/port-expression roots
and task bodies do not gain caller-elimination eligibility. Pure functions entered from those
contexts still receive the guarantee internally. Closed externals keep their existing bounded host
call path; no native intrinsic or host callback acquires recursive graph execution authority.

Task and affine frames, including empty-requirement task functions, are not pure frames. Do not infer
purity merely from an empty requirement list. Transactions, requirement bindings, resource handoff,
consume/drop rules, capability calls, and their continuations remain unchanged. In particular, a
pure helper running inside an ancestor's transaction cannot elide or commit that ancestor.

Evaluate the invoke callee first and arguments left-to-right exactly once. Resolve concrete type
arguments in the outgoing scope and satisfy existing target, arity, type, effect, and resource
validation requirements before transfer. Then discard outgoing locals and substitution state, preserve the original return
continuation and caller operand-stack base, and install the callee without an additional activation.
No stale local, type binding, operand, or per-transfer continuation may accumulate. Pending work
must execute normally; an attempted transfer with residual operands, impure authority, or an owned
transaction must fail at its owning validation/runtime boundary, never silently bypass that work.

### Bounds, failure, and visibility

Retain current default admissions: 10,000,000 VM instruction steps, 4,096 live call frames,
1,000,000 operand values, 268,435,456 cumulative allocated bytes, 1,000,000 collection items, and
100,000 capability calls, together with existing narrower input/value/deployment bounds. Non-tail
calls still consume frame admission. Tail transfer neither increments retained depth nor resets
fuel, allocation, collection, cancellation, or capability accounting. Preserve the VM's existing
local-allocation charge for each admitted graph call, including tail transfer, without refunds.
Reference accounting retains its independently defined expression/value units.

Every transfer checks cancellation and consumes execution work. Removed return/jump instructions
are not executed or fictitiously counted; current VM instruction and reference expression counts
need not match each other or predecessor counts. Infinite tail recursion must exhaust fuel or
cancel with the existing failure class, not become unbounded computation. This is a constant
**control-space** guarantee for a tail chain, not constant application heap, unlimited iterations,
termination, a latency promise, or sandboxing.

Pure success and failure never advance HEAD or mutate operational data. Exhaustion/cancellation
releases owned execution state; a fresh invocation can succeed afterward. Existing build output
publication remains create-new and atomic, and an execution failure produces no successful value
receipt. Preserve stable existing diagnostic codes where applicable, including non-tail depth and
fuel errors; identify the failed bound and corrective action without dumping stacks or values.
