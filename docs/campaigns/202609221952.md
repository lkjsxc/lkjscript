## 2. Outcome and rationale

Deliver a maintained ordinary typed-cell library with two explicit entry points: stage an update inside a caller-owned transaction, or own and complete a standalone update. An application must be able to compose independently transported library operations into one same-store atomic transaction without copying their update algorithms or receiving a premature `Committed` result. Calling a participating helper without an active matching transaction must fail before that helper reads data or invokes its callback.

The current limitation is precise. `requirements.producer.structural.lkjc` owns its update inside `transaction-outcome`. Both evaluators reject another transaction on the same canonical requirement. Raw capability calls in ordinary task helpers already use an ancestor's active transaction, and data mutations already reject outside one. This campaign does not claim that multi-key atomicity was previously inexpressible. It supplies a reusable public library boundary and an early, explicit participation check instead of making consumers split or duplicate each transaction-owning algorithm themselves.

The decisive choice is a small DataStore operation plus ordinary graph libraries. Silently flattening nested `transaction-outcome` would misrepresent an inner return as completed publication. A new public affine transaction-handle system would expand lifetime, transport and capture rules without being needed for this synchronous workflow. Preserve the owner/participant distinction and reuse existing canonical transaction routing.

This is preferable now to another authoring-notation increment: complete native units and re-entry have just been delivered, while the composition restriction is visible in the maintained library and both evaluators. `docs/performance.md` also identifies preparation costs in small workloads, but those observations do not identify a current general replacement algorithm or justify a broad optimizer campaign. Native contributor-tool migration should follow a concrete supported workload, not a percentage target.

Non-goals are implicit joining of transaction owners, savepoints, nested partial commits, cross-store atomicity, automatic retry, ambient transaction discovery, transferable transaction handles, broader affine signatures, application-data migration/compaction, a package registry, compiler self-hosting and production deployment.

## 3. Chosen contracts

### A. Exact transaction participation guard

Add a normal exact standard `DataStore` operation, `require-transaction() -> Unit`, declared idempotent with no external visibility. It remains a task capability operation even though it does not mutate data.

- It succeeds only when invocation already routes to a live transaction for the operation's resolved canonical grant. Matching interface names, requirement spelling or physical paths alone cannot select a transaction.
- Outside that scope it produces a classified execution failure with a discoverable diagnostic. It does not open a new snapshot, start/commit/abort a transaction, mutate data or invoke application callbacks. Another independently granted store's active transaction does not satisfy it.
- It returns ordinary Unit, never a token, receipt or authority-bearing value. Descriptors may be created or retained outside a transaction, but their eventual invocation must perform the check again.
- An active transaction whose conditional expectation has already failed still satisfies the guard until its owner exits. Success promises neither eventual commit nor a current-head snapshot; it must not change the existing rule that later body operations may execute after a failed condition.
- Exact operation permission, current activation allowance, deployment grants, cancellation and existing call accounting remain enforced. Charge the ordinary capability call; do not reset counters, introduce a cumulative trusted-execution budget or silently expand operation sets. A requirement-parameter minimum is not a new attenuation mechanism.
- Keep both existing lexical transaction forms unchanged. In particular, invoking the standalone wrapper inside an already active same-canonical transaction still rejects. Only the outer owner finalizes staged work and evaluates its completion outcome.

Use the existing capability-call path and adapter transaction dispatch. No new expression kind, special typed-cell opcode or transaction value type is selected. Standard operation admission must independently validate the complete contract before live adapter opening. Both evaluators must enforce the same authority and routing rules without sharing their evaluator control logic.

### B. Ordinary standard library

Author these public functions directly as native declaration units in `packages/standard`, using existing typed-data operations and task/effect/requirement abstraction:

```text
data-cell-update-in-transaction<T; E; R>(
    space: StaticText, fallback: T,
    transform: TaskFn(T) -> T ! E, key: List<DataKeyPart>
) -> T ! ({R} union E)

data-cell-try-update<T; E; R>(
    space: StaticText, fallback: T,
    transform: TaskFn(T) -> T ! E, key: List<DataKeyPart>
) -> TransactionOutcome<T> ! ({R} union E)
```

These signatures describe contracts, not a new syntax. The participant's R requires exact `get`, `put` and `require-transaction`; the standalone wrapper additionally requires `transaction`. The participant first invokes the guard, then reads the current transaction view, obtains the value using the existing witness's explicit caller-supplied fallback/typed `decode-or` policy, invokes the callback once, encodes the candidate, and conditionally puts against Missing or the exact observed entry revision. Operational failure, cancellation and resource exhaustion never become fallback values. Document that fallback on incompatible typed encoding is an explicit policy choice, not a schema migration or repair.

The participant returns a tentative T. A failed conditional put still marks the parent transaction's failed expectation; it must not be converted into successful publication. Returning a candidate, false or an application variant does not certify commit. Subsequent helpers read earlier staged changes. The wrapper owns `transaction-outcome`, calls this same participant implementation, and returns `Committed(T)` only after actual successful finalization or `Aborted(ConditionFailed | Conflict)` without T.

Call arguments retain ordinary evaluation order: the entry guard precedes the helper's own read/callback/write, not effects already evaluated while constructing its arguments. Callback effects on independent capabilities retain their actual visibility and can survive the parent abort. No callback is replayed automatically.

The core introduces no blanket capture-safe constraint on T. Existing closed-type encoding admission and failure rules apply. Exercise direct calls, named task values and ordinary prefix binding; capture constraints apply where binding actually captures values. Cell keys, spaces, schemas, migration policy and retry decisions remain caller-owned graph meaning. Rust must not implement cell decoding policy, transforms or update composition behind a library-shaped facade.
