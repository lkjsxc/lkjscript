## 2. Selected result and tradeoff

Deliver one native authoring representation that supports both freshly written complete declarations and product-generated editable drafts of existing declarations. An ordinary consumer with the product executable and native inputs must be able to create a substantial library/application, inspect and resume its development without its original generator, review changes, run tests, build, transport dependencies and execute the resulting bundle.

The specific improvement is eliminating the need for a host program to reconstruct parameter IDs, structural-type aliases, member indexes, repeated signatures and name-reference inventories merely to write or resume ordinary code. Existing creation operations already exist; do not market them as newly invented expressiveness. The missing coherent workflow is readable complete declaration authoring plus reliable re-entry from accepted meaning.

Extend the existing change and inspection mechanisms. Do not create a second compiler, a source-file synchronization authority, a parallel build system or a privileged graph writer. Preserve the accepted graph and its intentional guarantees because this is the lower-risk route to the selected outcome, not because graph authority is permanently sacred.

This is preferable now to another storage/performance increment: the current user requirement concerns the development dependency, and Orbloam demonstrates it directly. It is also more valuable than a function-only editor, which leaves initial construction and signature/type scaffolding outside the language. A wholesale compiler/CI rewrite would delay a usable native development loop without proving that the necessary public primitives exist.

Non-goals are complete compiler self-hosting, replacing Cargo/Git/CI, a general process runner, arbitrary compile-time execution, a GUI, hot reload, game redesign, storage optimization and new execution quotas. The native parser may remain Rust. Ordinary program behavior and reusable helpers belong in lkjscript; do not introduce Orbloam-specific compiler cases.

## 3. Chosen contract

### A. Complete native declaration units

Extend native `.lkjc` change input with scoped declaration units, using the existing structural expression notation for bodies. Choose concrete delimiters and field spelling locally and register them through the existing contract owner. These are additions to the public input grammar, not claims about currently accepted syntax.

A unit expresses explicit creation or editing, an owning module or component, declaration names, ordered fields/cases/parameters, types, generic/effect/requirement parameters and constraints, visibility, result/effect contracts, and bodies or test expectations together. Cover the declaration families needed for ordinary libraries and applications: modules, records/variants, functions, constants, tests, interfaces/externals, components, requirements, ports and targets. Existing precise change operations remain available in the same request for deliberate rename, deletion, dependency replacement and other exact edits.

Support compositional inline types and local type aliases rather than requiring separately numbered type records. Named types retain their exact declaration identity; structural aliases are notation only. Function parameters and local bindings use lexical names in bodies. Resolve declared names and exact dependency members inside typed scopes, with explicit qualification for ambiguity. No wildcard search of ambient projects, no overload guessing, no new implicit grant or effect inference, and no silent dependency upgrade.

Collect declarations before resolving legitimate forward references, then lower the entire request to the existing typed authored intent and complete-candidate validation. Preserve declared ordering and lexical shadowing rules. Reject duplicate names in one namespace and scope escapes with located diagnostics. Automatically manage private expression/type labels and child indexes; do not require users to invent them. Retain explicit semantic contracts rather than hiding them behind permissive inference.

Do not stop after supporting only simple function bodies. The fresh and external workflows below must use the native units for new types, declarations, tests and their connections. Low-level records can remain an intentional precise interface, not the hidden mandatory generator target for those workflows.

### B. Revision-bound editable drafts

Introduce a public `change draft` operation; it is not present in the inspected operation registry. Its semantic inputs are explicit typed owner selections, including module selection, and an output destination. Follow existing selector encoding and CLI conventions for the concrete flags. One invocation may select connected declarations for one prospective change.

The operation is read-only with respect to accepted meaning. It emits a complete native edit request containing the observed repository/package/base identity, exact bindings for selected existing owners and contract children, necessary typed reference/type aliases, and editable definitions. External dependencies are references to exact suppliers, not copied definitions. A selected module expands only its actual ownership scope; referenced outside declarations remain references unless explicitly selected.

Reconstruct the draft from accepted canonical meaning, not a historical generator or cached source. Original structural-alias names, comments and formatting may never have been stored: generate readable deterministic aliases and explain this limitation instead of claiming to recover original source. Intern repeated structural types in the draft to avoid mechanically expanding a large signature everywhere.

The emitted output must be complete and deterministically ordered. Output admission, cancellation or unsupported content must fail clearly rather than emit a successful truncated edit. Publish output atomically to an absent destination; do not overwrite an existing file. All draft failures preserve accepted authority. Large projects remain selectable in bounded ownership scopes; no promise of unlimited whole-project export is required.

Untouched draft-to-plan must show no semantic change or owner recreation. Whether an explicit no-op apply records a receipt follows existing publication policy. After a real body edit, preserve declaration and unchanged signature-owner identities; expression/binding replacement follows the existing body-replacement contract, not a new promise that every expression ID survives arbitrary rewriting.

### C. Editing authority and failures

Creation and editing must be distinct. Never perform name-based upsert. A name resolves a locator; only a validated exact binding in the current reviewed change selects an existing identity. Changing a displayed name must not silently turn an edit into creation or select a different declaration.

The request is a patch, not an authoritative replacement snapshot of a project. Unselected owners survive. Within a complete edited signature, omitting an existing contract child is an error unless an explicit supported deletion accounts for it; adding a child is explicit creation. Renames, moves and deletions retain existing review/dependency checks. Do not infer destructive changes from missing text or disappeared files.

A stale base, wrong repository/package, unresolved or private dependency member, altered review input, broken generic scope, or incomplete caller/port repair must reject before accepted publication. Review binds the exact authored candidate and dependency context. Recheck under the existing publication lock. A successful idempotent retry returns the original accepted result. A failed later build/output operation does not roll back accepted meaning.

One reviewed request has one atomic semantic publication boundary. Do not silently split a large unit across accepted commits to evade capacity limits. Resource bounds protect finite preparation/output and use checked admission; they must not become invented cumulative budgets on trusted program execution.

### D. Compatibility and cutover

No graph, artifact or application-data migration is selected. New native inputs are ordinary program authoring, not executable host macros. Generated drafts are disposable proposals; once accepted, future drafts can be reconstructed without them.
