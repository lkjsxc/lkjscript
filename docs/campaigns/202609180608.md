## 1. Outcome and established starting point

**Selected outcome:** an agent using only the product executable can change an existing callable parameter's type without deleting and recreating that parameter, then atomically repair the affected ordinary program. This must work through reviewed public authoring, exact library transport, checking, compilation, and execution. Parameter identity is preserved; compatibility is checked, not inferred from that identity.

Expose the already implemented typed operation `AuthoredChange::SetParameterType` through one public compact record:

```text
set.parameter-type parameter=OWNER type=TYPE
```

This is an input-contract evolution campaign, not a new type system, generalized signature-rewrite engine, or numerical runtime rewrite. It complements existing public result/effect, body, port, and dependency changes. The representative outcome is evolving a numerical library from bare samples to structured readings while retaining its function, parameter, and endpoint identities.

## 3. Chosen public contract

### 3.1 One adapter for an existing typed change

Add the record spelling shown above to the maintained closed compact adapter and its discovery. `parameter` uses the existing owner selector machinery: an exact local parameter identity or a properly typed request alias, including aliases obtained through `reference.owner`. `type` uses the existing authored type reference machinery, including ordinary declared `@` types. There is no new JSON protocol, privileged storage input, or hidden host helper.

The record lowers to the **existing** `AuthoredChange::SetParameterType`. It neither allocates a replacement parameter nor changes which program repository owns it. Support legal local function, task-function, external-function, and interface-operation parameters through the existing common parameter representation and validator. A fixed external implementation's signature is not made arbitrary by exposing the setter: incompatible declarations must still fail existing intrinsic/interface admission.

Use the existing ordered authored-change rules for symbols, operation ordering, repeated mutations, and no-op changes; do not introduce a different parameter-specific interpretation. Legitimate same-request symbols remain usable where the existing typed lowerer admits them. Reject malformed/unknown/duplicate fields according to the closed compact contract. An invalid combination never causes partial publication. Preserve source locations so a rejected new record identifies its actual input location rather than an unrelated operation.

### 3.2 Identity and authority guarantees

Changing the type preserves the selected **ParameterId**, parent, name, positional membership/order, use mode, and any exact requirement binding. It does not grant permission to edit an imported immutable package. Function, component, port, and target identities remain unchanged unless the submitted ordinary request explicitly performs a different supported change. Replacing a body may legitimately create/retire expression owners under existing `replace.body` semantics; do not pretend every expression must retain its identity.

The new type is checked in the parameter's actual defining lexical/generic context, not the context of whichever function was most recently parsed. Foreign type parameters, invalid effect/requirement substitutions, illegal capture/resource types, and mismatched borrow/consume rules continue to reject. A type update cannot turn an existing parameter's unchanged use/requirement fields into new capability authority. Deployment grants remain separate and are never inferred from a signature edit.

Names are locators, not the mutation authority. Bind exact selected owners through the normal reviewed plan; a rename, stale base, or changed resolution must not redirect a previously approved mutation. Report the actual changed owner/type and affected contracts through the existing plan and inspection models. Do not add a parallel signature registry.

### 3.3 Complete candidate validation and failure behavior

An agent may combine the new record with existing body, result/effect, port, and dependency edits in one request. Validate the **complete final candidate** and publish it once. Intermediate invalid signatures must never become accepted meaning, but their presence while constructing a complete valid request is not itself a reason to require multiple accepted revisions.

A changed parameter type does not automatically rewrite direct calls, function values, bound callable types, tests, ports, or other consumers. A candidate leaving a relevant use ill-typed must fail before publication, including unused arguments and unreachable syntax covered by the existing validator. Repair those consumers explicitly through ordinary authored operations in the same candidate. Preserve evaluation order; do not silently insert conversion calls or change argument positions.

Public failure, stale review, invalid input, cancellation, or resource exhaustion leaves accepted HEAD and its meaning unchanged, subject to the existing publication contract. Preserve the established request commitment, plan-token binding, under-lock revalidation, and idempotent accepted-retry behavior. Do not make a failed derived check/build undo an accepted write, and do not relabel a historical acceptance as permission to execute newly invalid current meaning.

### 3.4 Library evolution is explicit and revision-pinned

Edit a library in its own local repository, export the new immutable package revision through existing public operations, and stage that revision in its consumer. A consumer pinned to the old package retains that old contract. Replacing its dependency with the new revision without necessary repairs must reject rather than silently adapting the call. A single complete consumer request may replace the dependency, update its own parameter and port contracts, and repair bodies together.

Parameter identity continuity does **not** mean source/ABI/data compatibility. Old compiled bundles still describe their old accepted closure; no signature edit rewrites an already built artifact, resident process, installed runtime slot, deployment descriptor, or live data. Preserve matching old bundles/descriptors for recovery. A corrected successor request can restore a supported old contract in a new accepted revision; that is not erasing history or rolling back independent external effects.

### 3.5 Encoding and compatibility transition

This operation uses types and owner mutations already represented by the current graph/compiler/artifact formats. Preserve those representations and the existing authored codec's tag 25. **Do not bump the authored codec, graph, compiler, bytecode, artifact, or application-data format merely to expose an existing operation.** At inspection the compact contract was version 22 and the authored codec version 17; reconcile current values, update the compact discovery identity/digest as the maintained compatibility policy requires, and avoid an unrelated public version bump.

Existing compact requests remain supported. Previously issued review tokens and historical retries retain the current project's explicit compatibility/rejection rules; never silently reinterpret an old reviewed request under changed meaning. An older public adapter is expected to reject the new record as unknown, rather than partially applying it. That authoring limitation is distinct from reading an ordinary graph/artifact encoded with already-supported meaning. Prove the narrow predecessor-execution expectation for the selected workload, not an assertion about every historical runtime.

No operational-data migration is selected. Structured command arguments in the witness are a caller protocol change, not a store-format upgrade.
