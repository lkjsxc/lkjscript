## 2. Outcome, selection and revisable trajectory

**Before:** the specification permits ordinary recursive generics only with unchanged ordered type parameters. Current `Call`/`FunctionValue` inference checks signature substitution but has no visible callable-cycle check; the old `semantic.rs::validate_generic_recursion` is not the active normalized owner. `prepared_types::calls` follows exact applications from calls, tail calls and named function values. Expanding type arguments can therefore reach an expensive preparation frontier even when runtime control would immediately return. That last public behavior is a source-derived prediction, not an observed execution.

**After:** programmers may define finite generic recursive libraries that permute, duplicate, drop or reset type arguments, using the same public authoring grammar. Definitions with an expanding parameter cycle fail during reviewed semantic admission, with a useful source-bound diagnostic. Complete transported code and artifacts enforce the same guarantee before live execution. Existing compatible repositories survive a validator-rule update without rewriting their identity/history; an old definition newly rejected by the rule can be repaired through ordinary reviewed edits.

**Thesis:** finite callable instantiation is a property of explicit type-parameter flow, not a same-order convention, a preparation timeout, or a runtime execution-fuel choice. Historical accepted evidence and current validation are separate claims about the same canonical program. Both distinctions are necessary to install the rule honestly.

Why now: the nominal, effect and task-iteration foundations already support rich recursion. Two recent campaigns retained this exact unresolved question. Investigation now identifies its missing enforcement boundary and a related upgrade trap: simply changing the validator digest currently prevents repository opening. Adding another polymorphism mechanism first would compound those problems. This campaign enables a coherent additional domain while removing the known validation gap.

The strongest alternative is explicit operation-bearing requirement parameters for transported libraries. Current effect parameters can forward callbacks, but `CapabilityCall` and `Transaction` require concrete requirements, leaving configuration reads and transaction ownership in consumers. That remains a strong next capability. The finite callable/upgrade boundary is selected first because it already affects trusted admission and will underlie additional applications. A structural authoring-block adapter is another valid future direction: the named-reference transcript removed member-ID plumbing but grew from 447 to 490 records. Numerical support is genuinely missing, but adding F64 alone would not establish useful model-training performance. No numerical, daemon, installer, platform, self-hosting or application-specific feature is selected here.

Short outlook, not authorization for multiple campaigns:

1. Complete finite callable admission, current-validation recovery and combined delivery in this campaign.
2. Reassess requirement-parametric capability libraries. Their decisive dependency is exact operation/interface constraints and authority-preserving substitution, including task descriptors and transactions. Minimum operation requirements must not be advertised as attenuation of a broader supplied requirement.
3. Then choose authoring structure or wider resource composition using an actual public workflow; retain measurements before any throughput/backend redesign.

Overturn conditions are bounded. If current source already implements the complete selected rule and upgrade path, verify them and finish missing proof/delivery instead of adding another analyzer. If the startup probes contradict the missing-boundary prediction, locate the real rejection owner and still replace an enforced same-order restriction with the finite rule where useful. ## 3. Settled semantic rule

The admitted domain remains explicit rank-one ordinary types with the current canonical constructors. Introduce no new expression form, type inference, type-level reduction, recursive runtime descriptor, or second source language.

For each graph function, use its exact declaration/package identity and its ordered ordinary type-parameter identities. For every syntactically present direct `Call` and named `FunctionValue`, inspect every ordered type argument supplied to the exact target. Include private functions, unused type parameters, unused descriptors and branches not executed. Runtime reachability does not erase a type application. Closed externals have checked signatures but no authored body edges. `Bind` and `Invoke` operate on already instantiated monomorphic descriptors and introduce no additional type-application syntax.

Construct a finite directed parameter-flow graph:

- Vertex: exact package, exact function declaration, exact ordinary type-parameter slot.
- For each occurrence of a caller parameter in target argument position j, add an edge from that caller slot to target slot j.
- The edge is **plain** when the entire argument is that caller parameter, and **expanding** when a canonical type constructor encloses the occurrence.
- Closed arguments contribute no source-parameter edge. Scope/arity/kind/constraint checks still apply to all arguments.
- Reject an application closure if any expanding edge has both ends inside one strongly connected component. Allow expanding edges between components.

Traverse every child type, including structural record, list, map, option, result, stream, nominal application, pure-function and task-function parameter/result types. Variance does not cancel syntactic growth; phantom nominal arguments remain part of exact type identity. Do not unfold nominal declarations into callable edges. Record sufficient occurrence provenance for a bounded witness: caller/target, application expression, ordered argument, parameter slots and constructor occurrence path. Shared subterms must retain the plain/expanding fact correctly; do not confuse mere revisitation with admissibility. No defect in the existing nominal walker is asserted by this requirement.

Once an expanding SCC has been established, diagnostic truncation must retain a semantic expansion rejection with an explicit bounded witness/omission marker. Do not turn a known invalid scheme into a resource error merely because the full printed cycle is long. Genuine analysis exhaustion before a decision remains a resource failure, and cancellation remains cancellation. In particular, do not blindly inherit the nominal analyzer's witness-length behavior when sharing its graph machinery.

Representative contract cases, assuming other typing/affinity rules pass:

| Application pattern | Required result |
| --- | --- |
| `f<A,B> -> f<B,A>` | Accept permutation. |
| `f<A,B> -> f<A,A>` | Accept duplication/projection. |
| `f<A,B> -> f<I64,List<A>>` | Accept finite growth followed by reset; expanding edge is acyclic. |
| `f<T> -> g<List<T>>`, `g<U> -> f<I64>` | Accept mutual closed reset. |
| `f<A,B> -> f<B,List<A>>` | Reject expanding cycle. |
| `f<T> -> f<List<T>>` | Reject, including an untaken branch or only a named function value. |
| `f<T> -> f<Phantom<T>>` | Reject even when the nominal parameter has no stored use. |
| `f<T> -> f<Function(T)->I64>` | Reject nested callable-type expansion. |

Substitute simultaneously from each caller's original ordered vector. Do not implement a swap by sequentially overwriting bindings. Distinct declarations' same-spelled parameters are distinct identities. Preserve existing capture-safe constraints at each application, including permutations between differently constrained slots.

The reason this rule suffices is finite syntax plus nonnegative constructor growth. Within a strongly connected slot component only plain forwarding remains; growth can cross only finitely many components. Ground seeds, constructor labels, arities and starting applications are finite, so the resulting exact callable instances are finite. This is an admission rule for the current type language, not a universal theorem about arbitrary future type computation.

Nominal member expansion remains governed by its existing separate finite-flow relation. A finite callable closure supplies finitely many type roots; admitted nominal expansion supplies finitely many member/layout types. Nominal types cannot synthesize named callable applications or feed computed type projections back into call arguments in the current language. Effect rows likewise range over finite exact requirement unions and multiply the closure by a finite set. Preserve simultaneous type/effect substitution and the existing effect permutation/union behavior. Revisit this argument if future language constructs add such feedback.

The current exact package dependency graph is acyclic (`package_source_cycle`), so callable recursion cannot form an SCC spanning packages. Complete per-package body analysis plus independent admission of dependency bodies suffices. Local source checking must not demand foreign private bodies merely to analyze a local SCC from an interface. Conversely, an interface-only check is not proof of a supplier's complete executable closure.

Do not promise every finite admitted program fits runtime preparation limits. Keep work, metadata, structural type depth, cancellation and output bounds distinct. Preparation may reject a very large finite closure with a resource diagnostic. An ordinary expanding cycle must not rely on exhausting these limits for its semantic rejection. This does not prove runtime termination, constant total memory, bounded retained data, or hostile-code isolation.

A standalone symbolic experiment by the architect closed the swap in 2 exact instances, duplication in 2, `f<A,B> -> f<I64,List<A>>` from `(Text,I64)` in 3, and the mutual reset from `f<Text>` in 4. Nested/swap-plus-growth examples continued growing until the experiment's depth cutoff. These are small independent term-model observations only; the cutoff is not a proposed language limit or a substitute for the required product proof.

## 5. Public witness and dependency-ordered implementation

### Designed library witness

Author a fresh transported library through the copied candidate using existing compact records and the accepted named-reference feature. Its principal function alternates two typed values/callbacks by swapping ordinary type arguments on each tail call:

```text
alternate<A,B>(remaining, left:A, right:B,
               on_left:Function(A)->Text,
               on_right:Function(B)->Text, output:Text) -> Text
  if remaining == 0: output
  else: alternate<B,A>(remaining-1, right, left, on_right, on_left,
                        append(output, on_left(left)))
```

This is **semantic pseudocode**, not proposed source syntax or an executed command. Lower it using actual `create.function`, explicit type arguments, existing expression fragments and named references. Supply nonnegative finite test counts; no language-level iteration ceiling follows from this witness. Use callbacks whose outputs depend on supplied values. With integer `7`, text `x`, renderers producing `I7;` and `Tx;`, and count 6, the expected result is **`I7;Tx;I7;Tx;I7;Tx;`**; count 0 returns empty output and calls neither callback. Confirm actual standard helper names through public discovery.

Add a task counterpart with ordered effect parameters `Eleft,Eright`, callback rows respectively `Eleft,Eright`, total allowance their union, and the recursive call swapping both type and effect arguments. Pass it through an ordinary public pure factory or prefix-binding composition and invoke it from an exact consumer command component. This checks named `FunctionValue`, retained descriptor, cross-package body transport, simultaneous substitution and existing task tail behavior. Use existing deterministic Configuration/DataStore fixtures where suitable. Record six ordered callback observations in an owned disposable namespace, with no duplicate effects. Independent reference traces use separate deterministic adapters, never a replay of the actual live invocation.

Exercise a consumer edit/replacement and later invocation after producer paths are removed. Do not add this pedagogical alternator to the maintained standard merely to claim adoption. The actual adoption is the existing offline/tail proof owners accepting the general rule; label the library a designed public composition witness.
