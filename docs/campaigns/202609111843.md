## Assignment

Implement explicit rank-one effect parameters and authority-free task function values. Make it possible for a separately authored, transported library to traverse ordinary values while invoking a consumer's effectful callback, without knowing that consumer's concrete capability requirements or acquiring authority of its own.

Deliver graph-owned standard `task-fold-left` and `task-map`, effect-aware function creation/binding/invocation through the real public executable, strict compiler/runtime enforcement, maintained consumer cutover, independent proof, and the selected release. This is an implementation assignment, not an invitation to write another architecture plan.

Today, public pure `list-map` can transform data, but cannot call a callback that reads configuration or writes application data. Task declarations cannot be generic, their effects are closed requirement lists, and ordinary function types cannot describe task effects. After this campaign, one offline library must serve consumer-defined configuration and storage callbacks through the same generic traversal, including a callback returned by a pure configuration factory.

The thesis is: **abstract over the effects a callback needs, while keeping authority at the invocation and deployment boundary.** An effect argument describes required authority; it neither grants authority nor substitutes a different capability for the callback's original requirement.

### Why this campaign now

Parametric nominal data, finite recursive nominal schemas, capture-safe generics, persistent lists, pure prefix binding, and code-complete offline packages already exist. Their next useful composition is effectful library code. Adding another application-specific adapter would leave this restriction intact.

The strongest rejected language alternative is lexical lambdas and automatic capture. Existing named pure functions and `bind` already express the important pure closure patterns, so that work primarily reduces authoring effort. Effectful higher-order composition enables programs the current public mechanisms cannot express. Further CI optimization is also rejected here: the immediately preceding campaign already removed duplicate expensive public acceptance.

The outcome remains useful with every motivating HTTP, game, and relay example removed. It enables reusable batching, ordered stateful traversal, and interpreters whose application operations remain consumer callbacks. Async scheduling, general capability dictionaries, effect handlers, and resource polymorphism are not prerequisites.

Reverse the selection only if startup demonstrates equivalent complete public capability already present, or a concrete counterexample defeats the authority model below. In the former case, reconcile completion and finish missing proof/cutover; do not reimplement it. In the latter, preserve safe completed work, record the counterexample, and block dependent work. Ordinary implementation corrections do not require another open-ended campaign search.

## Semantic design contract

The notation in this section is explanatory, **not existing source syntax or an already-supported CLI**. Implement discovery and authoring for the meaning through the existing compact/authored change surfaces.

### 1. Explicit effect parameters and rows

Introduce stable function-owned effect-parameter identities, separate from ordinary type-parameter identities. A parameter has an exact owner, ordered position, mutable local name, canonical references, relation/impact participation, and complete inspection.

Pure and task graph functions may declare explicit rank-one effect parameters. Task graph functions may also declare ordinary type parameters under their existing constraint rules. Pure factories need effect parameters so they can configure and return task callbacks without executing them. Effect parameters on external intrinsics or separate nominal declarations are not required: existing nominal type arguments can already carry an instantiated task-callable type.

Represent a row as the canonical set union of exact `RequirementReference` atoms and in-scope effect-parameter atoms:

`E = {r1, r2, ...} union e1 union e2 ...`

Canonical rows have sorted unique atoms by stable identity. Authored unions normalize deterministically; strict encoded inputs with duplicate/noncanonical atoms reject. Equal spellings, equal interfaces, or similar deployment coordinates never merge different exact requirement atoms. There is no wildcard effect, implicit inference, row subtraction, hidden ambient IO, or grant lookup by effect-parameter name.

Direct calls and named function values supply ordered effect arguments exactly matching declared effect parameters, just as they supply explicit type arguments. Effect arguments may be closed rows or rows expressed in the caller's exact scope. Omission is valid only for zero effect arity; omitted/excess/foreign arguments reject even for unused parameters and unreachable expressions.

Substitution traverses all affected parameter/result and callable types, including task callables nested in pure function signatures, aggregates, and nominal applications. Type and effect scopes are distinct. Generic bodies are checked universally: an unknown row can be forwarded, but its concrete operations cannot be guessed.

Canonical row equality and callable type equality use exact identities. For authority containment after substitution, symbolic parameter inclusion requires the same exact parameter; never assume one unrelated parameter is contained in another. A concrete required atom is discharged either by the same atom or by the existing validated requirement-coverage relation: same package/name/exact interface, required operations contained in the available declaration, and compatible declared limits. Runtime discharge additionally proves that the selected references resolve to the same canonical grant. This applies to both direct calls and indirect invocation against the current activation allowance; sharing a grant never widens that allowance. Canonical closed rows have finite requirement universes; union is idempotent. Effect forwarding/permutation/union on recursive calls does not need a new syntactic application-shape whitelist. Bound distinct closed instantiations by existing preparation work/storage admission. Preserve the existing ordinary-type recursive-call contract; this campaign does not admit expanding polymorphic type recursion.

A function explicitly declared task remains task even when its closed row is empty. An empty task effect does not confer purity, pure-command eligibility, or pure tail-transfer eligibility.

### 2. Task callable meaning, construction, binding, and invocation

Keep the current pure `Function` type and add an explicit task-callable form:

`TaskFunction(P0, ..., Pn) -> R ! E`

Do not smuggle tasks into ordinary pure `Function`. Preserve existing pure type encoding bytes/digests where their meaning is unchanged. Give new task-callable meaning its own encoding case/envelope with strict decoding, analogous in purpose to the existing separately owned nominal application envelope.

A task callable is an immutable descriptor containing an exact prepared target, resolved ordered type/effect arguments, and a flat capture-safe prefix. It contains **no adapter, grant object, task scope, transaction, credential, live resource, or mutable frame**. Exact requirement references are descriptive meaning, not held execution authority.

Creating, binding, returning, copying, and composing these descriptors is permitted in pure contexts, because those actions do not execute the target. Their actual evaluation effects still include evaluating the callee and captured expressions. Allow transient ordinary aggregates and returned task values under the same structural storage rules as pure callables; do not introduce a callback-name, argument-position, or non-escape allowlist.

Generalize existing `function-value`, `bind` and `invoke` through their normal owners:
- Named task values require explicit type/effect arguments and an exact accessible target.
- Binding evaluates callee first, then captures once left-to-right. It does not invoke the target. Empty and complete binding and rebinding preserve current prefix semantics.
- Binding preserves the callable's task kind and complete effect row. Bound values obey capture-safe constraints and raw admission.
- Invocation evaluates callee then arguments once left-to-right. Task invocation requires task context even for an empty row, row containment against the current activation's declared resolved allowance, and actual component capability bindings.
- Argument/result types and callable rows must agree exactly. Do not add implicit pure-to-task coercion or effect subtyping to value types. An ordinary graph task wrapper can explicitly adapt pure work when needed.
- Unknown, forged, stale, foreign-preparation, effect-erased, wrong-arity, and mismatched-prefix descriptors reject before body execution.

Pure and task callable signatures are leaves for stored-value capture safety; actual retained prefixes still require complete admission. Callable-containing values remain non-equal and non-durable. Existing JSON/typed-data/session/queue/backup boundaries must reject task callables just as they reject pure callable values. Do not add accidental persistence through an empty collection or inactive nominal case.

Task callbacks may acquire and consume their own lexical resources inside their bodies. Existing resource-bearing function signature restrictions continue to apply: a resource-taking function cannot become an indirect callback, and no captured prefix may contain a live resource. Preserve the maintained direct affine handoff; this campaign does not generalize that protocol.

### 3. Authority, calls, transactions, and failure

Separate three facts:
1. The callable target's declared, substituted exact effect row.
2. The current activation's declared, substituted allowance.
3. The selected component's actual checked bindings to deployment grants.

A descriptor cannot widen any of them. Both evaluators must enforce the invocation row against (2), then resolve against (3). Merely checking every requirement against all globally available component grants is insufficient. Root port entry derives its allowance from the selected component and selected task contract; nested calls receive their own declared resolved allowances.

An imported library with abstract row `E` owns no concrete callback requirement. Instantiating `E` with consumer references leaves the callback's original exact requirement references intact. A body declaring only `E` can invoke an `E`-typed callback; it cannot perform an unnamed operation “on E”.

Keep existing checked component alias mappings for concrete requirements where already valid. Treat mapping as a separate validated derivation, never canonical row equality. Preserve package identity, exact interface, allowed operations, limit restrictions, provenance, and canonical grant identity. No foreign same-name requirement is silently granted. Resolve the observed validation/binding discrepancy on this changed boundary with a counterexample test and consistent admissibility; do not broaden global capability lookup.

Forwarding through a library does not clone adapters, create a new grant budget, reset counters, or start a new transaction. Resolve transaction lookup, resource provenance, and capability accounting through the same canonical bound grant as direct calls. Preserve lexical transaction ownership. A callback called inside a transaction uses the applicable active transaction; nested-transaction prohibition remains effective through indirect and imported calls.

Earlier completed effects retain their actual visibility after a later trap, cancellation, exhaustion, or possible-visibility failure. Only the applicable existing transaction can roll back staged work. Do not convert those failures into ordinary `Result` values or retry/replay callbacks. Conversely, an ordinary returned `Result` is just an element/state value unless graph-authored control flow explicitly branches on it.

Perform cancellation and checked work/storage admission before growth and before result installation. Failure installs no partial callable, local, artifact, accepted graph, or successful traversal result. Cleanup releases owned temporary state and resources exactly once while preserving old immutable aliases.

### 4. Preparation, compilation, and strict loading

Preparation keys include the complete function application: target plus ordered ordinary type arguments and canonical closed effect arguments, with exact source/preparation origin. Closing one instantiation must not certify another callback row or target. Charge row normalization, substitution, worklists, indexes, and metadata under existing checked limits before allocation; do not repeatedly scan a complete dependency closure on every callback invocation.

Production derives executable tables and allowed-effect inventories from strictly admitted compiled inputs. Canonical reference derives its own rows, signatures, and activation allowances from accepted owners. They may share neutral IDs/bytes, not a production effect-checking oracle.

Type traversal for the existing nominal finite-instantiation analysis must visit task-callable signatures and their ordinary type arguments. Stored-value eligibility must separately treat signatures as leaves. This distinction prevents a new callable type from either hiding an expanding nominal scheme or unnecessarily excluding safe descriptors.

Strict transported loading cross-checks effect-parameter ownership/order, concrete references, call arguments, nested callable types, port kinds, and compiled target signatures against canonical owners. Reject structurally valid, rehashed containers with effect-erased or mismatched executable contents. No trusted-local-producer bypass.

### Bounded control space without changing task tail semantics

Task frames currently do not have the pure tail-transfer guarantee. Do not implement linear-depth task recursion and disguise the 4,096-frame ceiling by selecting a tiny witness.

Use a private range helper over the original persistent list:
- empty range returns state;
- singleton range invokes the step exactly once;
- otherwise compute `mid = lo + (hi - lo) / 2` with checked valid indices, fold `[lo, mid)` completely, then feed its result into `[mid, hi)`.

This is sequential left-fold behavior with logarithmic additional range frames, without slicing or materializing list prefixes. For a fixed stateful callback, every completed effect precedes the next callback. Build `task-map` from this fold, a task step with a bound mapper descriptor, and persistent append.

The architect simulated only this neutral range algorithm at lengths 0, 1, 2, 3, 31, 32, 33, 4,097, and 8,192. The 8,192 case visited every index in order with sum 33,550,336 and 14 range frames. This is not an lkjscript test or a runtime performance result. Codex must prove the actual implementation. Its indexed list reads have their existing logarithmic cost; do not claim optimal linear element-access work or task TCO.
