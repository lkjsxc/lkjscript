## 2. Primary objective

Make one copied `lkjscript` release-candidate executable sufficient to create, semantically modify, check, build, and run a new HTTP application outside the repository checkout, using no Cargo, Rust source, checkout-relative asset, prebuilt application artifact, database, container, network registry, or product-side helper executable. An implementation-disjoint test client may send the proving loopback request, but it must not supply program, package, artifact, or deployment input to the product workflow.

The complete public workflow must be:

1. create a fresh Graph 5 HTTP project with `new --template http`;
2. modify its response text through the existing reviewed public `change plan` / `change apply` path;
3. run `check`;
4. build an Artifact 10 bundle to the location named by the generated deployment descriptor;
5. start `serve --deployment ...`;
6. observe readiness and the actual loopback listener;
7. make a real HTTP request and receive the changed response;
8. stop and restart the service cleanly; and
9. prove that serving and restarting did not modify accepted project authority.

This is one vertical public-workflow campaign. It is not a general web framework, a general template language, or a comprehensive authored-change expansion.

## 3. Why this objective is selected now

The preceding campaign `docs/campaigns/202608272159.md` is complete. Artifact 10 now owns the public `serve` and `worker` runtime boundary, and the latest release records that cutover. There is no active incomplete campaign at the audited baseline, and no open issue or pull request was found during the upstream audit.

The current distribution boundary is internally inconsistent:

- `README.md`, `docs/status.md`, `docs/architecture.md`, and `docs/spec/semantic-cli.md` correctly show that a copied binary can create and run a pure command project.
- `src/platform/execution/normalized/http.rs` and the completed service campaign prove that `serve` is a real Artifact 10 HTTP runtime.
- `src/platform/cli.rs::execute_new`, `src/platform/project_creation.rs`, and executable discovery expose only `minimal` and `command` creation recipes.
- `command` creates a `RunnerKind::Command` target; `minimal` creates no target.
- `src/platform/control/change.rs` exposes thirteen authored operations, including `replace.body`, but not component, requirement, port, target, dependency, task-effect, structural-expression, or capability-call construction.
- The underlying typed change engine in `src/platform/change/request.rs` and `src/platform/change/request/creation/` already represents those broader forms, but they are private implementation capability, not a usable distributed-CLI workflow.
- The HTTP runtime requires an HTTP runner target with the exact structural handler type and one exact byte-stream grant.
- The copied-binary release smoke in `.github/workflows/release.yml` currently proves only the command lifecycle.
- The user-supplied field report reproduced the practical consequence: a copied binary could build and run command applications, but could not create an HTTP topology; attempting to serve a command target reached the stable foreign-runner rejection while the checked-in `lkjournal` artifact could serve.

The primary bottleneck is therefore not the absence of an HTTP server implementation. It is the absence of a dependency-closed public authoring path from one distributed executable to an editable HTTP project and its standalone deployment input.

Closing this path now has higher durable value than adding another runtime feature. It converts already-implemented Graph 5, compiler, Artifact 10, deployment, and HTTP work into an ordinary public workflow, adds a no-Docker release boundary, and gives future agents an executable example that does not depend on repository-private material.

### 5.2 Created authority and operational output

`new --template http` atomically publishes one destination containing:

- one valid Graph 5 repository as the sole program authority;
- one strict deployment-contract-1 starter descriptor at `service.deployment.json`;
- one ordinary output directory for the future artifact at `generated/`;
- no prebuilt application artifact;
- no source file, generated graph request, hidden template store, secret, credential, database state, network result, or checkout locator.

The graph contains one exact built-in standard dependency and the smallest coherent HTTP application:

- module `application`;
- a private pure function `response-text` whose result is `StaticText`;
- a private pure function `status-code` returning `I64` value `200`;
- an HTTP handler with the exact current structural request parameter and structural response result;
- a component with one request-body stream requirement and one HTTP port implemented by that handler;
- target `serve` with runner `http`;
- one graph-owned pure test that proves a stable invariant such as `status-code == 200` and does not freeze the editable response text.

The handler returns a bounded whole-byte response with status 200, an empty typed header list, and bytes obtained from `response-text` through exact built-in standard declarations. It may ignore the request in this initial vertical slice. It must not contain route policy, hidden host behavior, or a Rust-only response shortcut.

The handler should be a task function bound to the stream requirement by default. Codex may retain a pure handler only if the validator, compiler, resident runtime, and capability closure all prove that this is the semantically correct current form. Record that evidence as an empirical answer.

### 5.3 Editable through the existing public change path

A fresh project must accept a reviewed change equivalent to:

```text
request base=REVISION
expression.static-text as=$response value="changed through the public CLI"
replace.body function=application/response-text body=$response
```

The actual request must use the exact current compact syntax discovered from the executable. Planning must produce a logical plan and token; applying the same normalized request and token must advance accepted authority exactly once. A stale base, altered request, malformed expression, foreign selector, or mismatched token must publish nothing.

No new special-purpose `set-response`, source-text, JSON graph mutation, direct storage edit, hidden recipe replay, or unchecked project writer is allowed.

### 5.4 Check, build, and live service

Using only the copied candidate and files created by it:

- `check` passes all graph tests through production/reference equality;
- `build --output PROJECT/generated/application.lkja` emits a strict deterministic Artifact 10 bundle without advancing authority;
- `serve --deployment PROJECT/service.deployment.json` loads only the descriptor, artifact, environment, and named host resources, not the project repository;
- readiness reports target `serve`, runner `http`, the exact artifact bundle digest, the actual loopback listener, and one byte-stream adapter;
- a real HTTP/1 GET to the ready listener returns status 200 and the changed response bytes;
- graceful shutdown reports stopped admission, zero remaining tasks, and zero cleanup failures;
- a restart of the same artifact and descriptor returns the same response;
- exact project authority inventory, HEAD, revision, semantic state, and root are unchanged across build, serve, request, shutdown, and restart.

The generated descriptor must default to loopback only. Prefer `127.0.0.1:0` so the operating system selects an unused port, provided the current descriptor validator accepts port zero and readiness reports the bound address. If checkout execution disproves that assumption, select a race-resistant loopback strategy in the acceptance harness and record the deviation; do not silently expose a non-loopback listener.

## 8. Selected design

### 8.1 One closed public recipe

Add `http` as the third executable-owned project recipe. Keep the recipe set closed and registry-owned. Do not create a user-defined recipe loader, macro system, template directory, or plugin protocol.

Refactor string branching into the smallest typed closed representation that prevents template metadata, dispatch, purpose, result fields, and tests from drifting. Do not build a framework beyond the three maintained recipes.

The public template descriptor should report, in ordinary vocabulary:

- template name;
- purpose;
- created runner, using `none`, `command`, or `http`;
- whether a starter deployment is emitted;
- the recommended artifact output path when one exists.

Replace the command-specific `command-target` boolean if it cannot represent the new closed set correctly. This is a direct CLI-11 cutover; do not retain a duplicate legacy field.

### 8.2 One shared owner of HTTP semantic types

The exact structural HTTP request, header, query-map, response, and handler function types must have one implementation owner usable by:

- runtime admission;
- the HTTP recipe;
- focused tests;
- any future compiler or inspection consumer.

Move or factor the current runtime-private construction without changing its semantic digest. Keep this owner in a generation-neutral platform layer; do not make project creation depend on Axum, resident process state, or a dense runtime table. Runtime admission and the recipe must compare against the same constructed type objects.

Retain an implementation-disjoint test that reconstructs or independently describes the normative field set and proves equality, so extracting a helper does not turn one bug into shared false evidence.

### 8.3 Exact built-in standard resolution

Extend the validated `BuiltinStandard` interface with one narrow HTTP-recipe contract resolver. It must discover and signature-check the exact declarations and interface already present in the embedded standard revision, expected to include:

- `StaticText -> Text`;
- `Text -> Bytes`;
- the byte-stream capability interface and the exact operation subset required by the request-body stream grant.

Do not hard-code declaration, operation, or interface IDs in the recipe. Resolve from the exact validated package interface and reject absence, ambiguity, wrong declaration kind, wrong visibility, wrong type, wrong operation set, or foreign implementation.

Prefer stable implementation identity plus exact signature for external declarations. Where an interface has no implementation identity, use its maintained locator only together with a complete exact shape check. Reuse or generalize the current command-text resolver rather than adding parallel ad hoc scans.

The maintained standard package should not change: `core.bytes.from-text` is registered and `lkjournal` already consumes the byte-stream capability. If the active standard interface unexpectedly lacks a required public declaration, do not create a local duplicate external declaration. Record the contradiction, determine whether a dependency-closed standard update is feasible inside this objective, and make the smallest correction only if all standard/`lkjournal` identities, generated assets, and consumers can be cut over and verified in the same campaign.

### 8.4 Typed HTTP graph recipe

Construct the recipe through typed kernel/change builders and full Graph 5 validation. Do not serialize and reparse source or storage records.

The default semantic structure is:

```text
module application

pure function response-text() -> static-text
    returns "hello from lkjscript"

pure function status-code() -> i64
    returns 200

task function handle(request: HttpRequest) -> HttpResponse
    effect requirements: streams
    returns {
        body: bytes-from-text(text-from-static(response-text())),
        headers: [],
        status: status-code()
    }

component application
    requirement streams: exact built-in byte-stream interface
    port http: (HttpRequest) -> HttpResponse implemented by handle

target serve
    component application
    port http
    runner http

test status-is-200
    actual status-code()
    expected 200
```

Names above are selected public locators and should remain exactly as written unless an active normative naming rule rejects one. Stable identities are newly allocated through the current project-creation mechanism; do not derive semantic continuity from names.

The request parameter may be unused. Do not add route matching, body reading, configuration, secrets, or middleware to make the example appear larger. The purpose is to prove an editable HTTP topology and end-to-end runtime, not to claim a framework.

### 8.5 Separate starter deployment

Create `service.deployment.json` as a strict typed serialization of deployment contract 1, inside the same private project stage and before the destination visibility rename. Create `generated/` in that stage. The descriptor names:

- artifact `generated/application.lkja`;
- target `serve`;
- loopback listener, preferably `127.0.0.1:0`;
- one grant for semantic requirement `streams`;
- adapter kind `byte_stream`;
- no configuration entries;
- no secrets;
- no worker configuration;
- current bounded runtime, execution, HTTP, and stream limits.

Use one typed repository-owned default constructor/encoder. Do not maintain a JSON string literal in project creation and another in tests or documentation. The serializer must emit strict accepted JSON plus a final newline. The descriptor is operator-editable after creation and is not hashed into semantic state.
