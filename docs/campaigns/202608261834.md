## 4. Definition of success

1. Capability discovery exposes exactly two deletion policies in deterministic order:
   `reject` and `owned-closure`.
2. Compact records accept `policy=owned-closure`; no direct deletion flag adapter is added.
3. `policy=reject` retains exact leaf-only semantics.
4. `policy=owned-closure` selects the root plus all transitive semantic children from the
   post-mutation, pre-deletion candidate.
5. The selection follows ownership only. It does not follow arbitrary references, package
   dependencies, physical object reachability, map pages, compiler artifacts, or cache entries.
6. Bindings and expressions remain invalid public deletion roots, but are included when owned by an

## 6. Current-state model

### 6.1 Authority and data classes

- **Semantic authority:** the accepted normalized graph revision reached through current HEAD.
- **Continuity authority:** stable owner identities and canonical retirement records inside accepted
  meaning.
- **Required accepted evidence:** canonical ownership, namespace, relation, summary, and test
  witnesses authenticated by the accepted revision. They are not independently editable meaning.
- **Transient intent:** compact records, direct flags, typed `AuthoredChangeSet`, budgets,
  idempotency, and bounded intent text.
- **Derived review evidence:** logical plan token and optional external logical-plan file.
- **Operational evidence:** receipts, work counters, verification receipts, logs, benchmarks, and
  filesystem inventory.
- **Physical implementation:** immutable objects and persistent maps. Their reachability is not
  semantic ownership.
- **Private predecessor paths:** old workspace/compiler/runtime and predecessor project operations
  remain for commands outside this campaign. They are not part of closure deletion.

### 6.2 Existing public behavior

`delete.owner owner=OWNER policy=reject` accepts only one exact non-expression owner with no current
owned child. It rejects a non-leaf with `change_delete_owned_children`. The lowerer then:

- detaches the leaf from a surviving canonical parent where required;
- rejects incoming references from surviving owners;
- writes a retirement bound to the accepted base;
- marks the owner deleted;
- prepares and publishes through the normal normalized change path.

`owned-closure` is currently an invalid policy. A field named `cascade` is an unknown field.
Bindings and expressions are not public roots.

### 6.3 Existing internal capability

Function-body replacement already computes and retires the old expression/binding ownership
closure. The deletion module discovers children from canonical aggregation and external-parent
relationships, uses relation witnesses only as bounded locators, revalidates candidate relations,
rejects surviving incoming references, and records retirements.

The campaign should contract these behaviors into one shared ownership-closure mechanism. It must
not retain one subtly different algorithm for body replacement and another for public deletion.

## 7. Alternatives and selected design

| Design | Correctness and authority clarity | Complexity and locality | Review, cutover, and recovery | Future replaceability and agent operation |
|---|---|---|---|---|
| Client-enumerated owner set | Exact only when the client perfectly reproduces canonical ownership; creates a second practical closure authority. | Small engine change but large requests, duplicate discovery, and stale-set failure. | Review is explicit but burdens weak agents; migration and deletion remain client-specific. | Poor: every client must track owner kinds and closure rules. |
| Implicit cascade/reference repair | Ambiguous because ownership and arbitrary references are conflated; risks deleting more meaning than selected. | Potentially broad graph traversal and unpredictable I/O. | Hidden effects complicate review and uncertain-failure recovery; predecessor terminology survives. | Poor: policy is difficult to constrain or replace safely. |
| Reachability/garbage collection | Incorrect semantic boundary; physical reachability is not ownership or accepted meaning. | Whole-store or whole-graph machinery with unrelated memory and I/O costs. | Does not provide a reviewed semantic cutover and leaves authority/reclamation confused. | Poor: couples language evolution to storage layout. |
| Reviewed transitive semantic ownership | One canonical ownership model computes effects; accepted graph remains sole meaning. | Bounded local traversal using existing multidimensional admissions. | Exact plan, reprepare, atomic publication, predecessor rejection, and complete-oracle recovery. | Strong: small intent surface, exact evidence, and hot traversal representation remains replaceable. |

### 7.1 Rejected: client-enumerated deletion set

Requiring the request to list every owner would make the client repeat canonical ownership
discovery, produce large stale-prone requests, and force weak agents to understand every owner kind
before planning. The reviewed logical plan already provides the correct place to expose the exact
computed set. Do not select this design.

### 7.2 Rejected: implicit cascade

Making ordinary `delete.owner` recursively delete references or accepting `cascade=true` hides the
actual effect before planning, revives predecessor terminology, and encourages accidental
cross-boundary deletion. Do not add a `cascade`, `recursive`, `deep`, `force`, `repair`, or fallback
spelling.

### 7.3 Rejected: reachability or physical garbage collection

Deleting all graph records or objects reachable from a root confuses semantic ownership with value
references and physical storage. Leaving children unreachable for a later collector would permit
incomplete meaning. Physical reclamation is a separate retention/compaction campaign.

### 7.4 Selected: reviewed transitive semantic ownership

The public request names an exact root and the explicit policy `owned-closure`. Plan computes the
semantic closure against the exact candidate and exports every effect. Apply recomputes the same
closure and rejects if either the request or prepared plan differs.

This design gives agents a small intent surface and a complete review surface.

## 9. Target behavior and boundaries

### 9.1 Public request

The accepted compact form is:

```text
request base=REVISION [idempotency=KEY] [intent=TEXT]
delete.owner owner=OWNER policy=owned-closure
```

`OWNER` is one exact typed local owner identity. It is not a name, wildcard, request-local symbol,
package endpoint, query expression, or foreign package owner.

The equivalent leaf form remains:

```text
delete.owner owner=OWNER policy=reject
```

Capability discovery is the sole exhaustive owner of the two values.

### 9.2 Candidate time

Preconditions are evaluated against the exact pinned base. Existing creation and mutation phases
then construct the candidate. Deletion selection observes that post-mutation, pre-deletion
candidate.

This ordering is intentional:

- an explicit earlier mutation may remove a surviving reference;
- an additional selected root may remove a referrer;
- a new child introduced under a selected root makes the request invalid because create-and-delete
  in one request remains forbidden;
- a stale base or changed prepared closure changes the token and cannot publish under an old review.

### 9.3 Ownership closure

For each `owned-closure` root, perform a checked work-list traversal:

1. Require an accepted, live, local owner.
2. Reject a binding or expression as a public root.
3. Insert the root.
4. Discover direct semantic children from the candidate canonical record and exact canonical
   external-parent relationships.
5. Revalidate every witness-located child against canonical meaning.
6. Insert unseen children and continue until the frontier is empty.
7. Charge existing named admissions at the owning boundary.
8. Produce deterministic typed-owner order independent of traversal order, map layout, insertion
   history, or hash iteration.

The closure includes bindings and expressions when reached from an admissible parent. It includes
documentation and annotations attached to any closure member. It does not include an arbitrary
owner merely because the selected owner refers to it or it refers to the selected owner.

### 9.4 Surviving references

Before marking owners deleted, compare accepted incoming relations and relations extracted from the
final candidate:

- a source inside the closure is safe because it is also removed;
- a surviving source is safe only when its final candidate relations no longer target the closure;
- a surviving local source with a remaining relation rejects with
  `change_delete_live_reference`;
- a foreign or package endpoint source rejects; this campaign never opens or modifies another
  package;
- a missing, truncated, foreign, or inconsistent required witness is corruption or resource
  exhaustion, not absence.

Do not choose a replacement owner. Do not erase a relation field silently. The request must say how
a survivor changes.

### 9.5 Parent updates and retirements

For every selected root whose direct parent survives, remove exactly one canonical membership or
external-parent relationship as required by the owner representation. A missing, duplicate, or
kind-incompatible membership is corruption or semantic invalidity under the existing diagnostics.

For every deleted owner, add exactly one retirement using the accepted base facts. The logical plan
must expose the retirement and the accepted semantic diff must bind it.

Do not delete content-addressed type/blob/object bytes merely because this change leaves them
physically unreferenced. Physical retention is outside this campaign.

### 9.6 Review and publication flow

The complete flow remains:

```text
compact input
  -> typed AuthoredChangeSet
  -> request commitment
  -> exact base view
  -> post-mutation candidate
  -> deletion closure
  -> canonical delta and witnesses
  -> impact, validation, and tests
  -> logical plan and prepared commitment
  -> optional external review file
  -> apply reparse and reprepare
  -> publication-lock base check
  -> durable immutable objects
  -> one HEAD visibility change
```

The external plan file may survive an interruption independently of HEAD. It is never trusted or
imported by apply.

### 9.7 Error classes

Preserve current diagnostic ownership:

- malformed policy, field, owner domain, record shape, or token: source/usage;
- nonexistent owner, forbidden root, non-leaf `reject`, create-and-delete, duplicate root, or live
  reference: semantic;
- exceeded owner, retirement, read, relation, validation, test, staging, or output admission:
  resource;
- inconsistent canonical ownership, relation witness, parent membership, retirement base, or plan
  fact: corrupt;
- changed request/prepared plan or base: semantic/stale;
- filesystem or publication failure: infrastructure.

Use existing diagnostic codes where they already describe the failure. Add a code only for a
genuinely new boundary, register it once, and generate its documentation.
