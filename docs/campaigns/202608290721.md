## 3. Objective and campaign selection

### 3.1 Primary objective

Make explicit, named, noncapturing higher-order generic programming a complete distributed
`lkjscript` workflow, then prove its usefulness by adding one Graph-owned generic
`list-fold-left` abstraction to the built-in standard package and replacing the maintained BBS's
manual header traversal with that abstraction.

The dependency-closed final state is:

1. public compact authoring can create type parameters on pure functions, construct a named function
   value with explicit type arguments, and invoke a function-valued expression;
2. the public standard package owns a pure generic left fold expressed in Graph meaning rather than
   a Rust-only intrinsic;
3. the copied-binary stateful HTTP application uses that fold for its real header predicate;
4. every maintained exact-standard consumer selects the one new standard package revision and all
   generated assets agree;
5. production and canonical-reference execution, clean and incremental compilation, and copied-
   binary public behavior agree; and
6. current documents describe the source state without pretending that the already published
   `v0.1.9` binary contains the new behavior.

This strengthens the language itself: reusable behavior becomes ordinary typed semantic meaning,
not another host adapter, application-specific Rust builder, or private graph feature.

### 3.2 Candidate comparison

| Candidate | Decision |

### 5.2 Selected design

#### Public compact vocabulary

Use one canonical public spelling for each concept:

- `add.type-parameter` adds an ordered stable type parameter to an existing function and defines one
  request-local reference usable by the existing parameter type form;
- `expression.function-value` selects one exact named function and receives the existing ordered
  `type.argument` children; and
- `expression.invoke` receives one function-valued expression plus the existing ordered
  `expression.argument` children.

Use `function-value` in public vocabulary and documentation. Do not add `function-ref`,
`function-reference`, `lambda`, `closure`, `apply`, or another alias. Internal enum/tag names may
remain unchanged when they are not public contract.

`add.type-parameter` is public only for functions reachable through the current authored function
surface. Existing validation continues to reject generic task functions. Do not use this campaign
to expose external, component, port, target, or interface creation.

A named function value supplies every declared type argument exactly once and therefore has one
monomorphic `Function` type. `invoke` evaluates the function expression once, then its arguments in
increasing index order, then calls the selected function. Direct `call` remains the normal operation
when the callee is statically named at the call site; do not lower all direct calls through function
values.

#### Standard `list-fold-left`

The public declaration is conceptually and behaviorally exact even though Codex must discover the
local owner symbols and generated IDs:

```text
list-fold-left<Item, State>(
    items: List<Item>,
    initial: State,
    step: Function(State, Item) -> State,
) -> State
```

It is pure. It processes index `0` through `length - 1`. For each item, the result of
`step(previous_state, item)` becomes the next state. Empty input returns `initial` without invoking
`step`. The implementation may use one private generic helper carrying the current index, but that
helper and all recursion are ordinary Graph meaning. Existing instruction, call-stack, expression,
collection, cancellation, and resource admissions remain authoritative; this campaign adds no
arbitrary fold-only item limit.

Tests must include empty, singleton, multi-item, two distinct type instantiations, an order-sensitive
step, and a bounded exhaustion or admission case that proves a typed failure rather than a crash or
host stack overflow.

#### Maintained BBS use

Replace the current manual index traversal used to decide whether request headers contain
`content-type: application/json` with:

- one named pure reducer over `(Bool, Header) -> Bool` or an equivalent exact accumulator that
  preserves current behavior;
- one named function value for that reducer; and
- one call to standard `list-fold-left<Header, Bool>`.

The reducer may contain the current literal policy because it is application meaning. Do not move
HTTP policy into Rust or the standard package. Preserve current accepted behavior for missing,
matching, nonmatching, repeated, and differently ordered headers, subject to the existing HTTP
normalization contract.

## 6. Target authority, failure, and resource boundaries

### 6.1 Authority and dependency direction

Accepted application and standard behavior stays in Graph repositories. The built-in standard
package exports the fold through its exact package interface. Root applications depend on that
exact standard revision; the standard package does not acquire a dependency on an application.
Passing a root-package function value into standard code is a runtime value flow inside the linked
artifact, not a reverse package dependency or hidden source link.

The executable registry owns public compact names and fields. The authored change codec owns the
normalized deterministic request bytes. The Graph validator owns type/effect/capability legality.
The compiler and artifact own derived executable form. The VM and reference interpreter own
independent execution. Generated documents project these owners and do not select behavior.

### 6.2 Type, effect, and value boundaries

- A public type parameter has stable declaration-owned identity and declaration-local name.
- A function value is monomorphic after complete explicit substitution.
- Only pure named functions may become ordinary public function values.
- `invoke` cannot widen the caller's effect set or smuggle a task/capability operation into pure
  code.
- A function value may remain as exact program meaning, including inside an otherwise valid pure
  expression, but it cannot cross equality, ordering, JSON, deployment, capability, or generic
  durable-data boundaries that do not own a function-value encoding.
- A function value remains valid only inside the exact linked package closure that resolved its
  semantic reference; foreign or absent package/function identities reject during validation or
  artifact preparation.

### 6.3 Failure and interruption

Malformed compact records, unknown fields/forms, duplicate child indexes, noncanonical order,
missing or excess type arguments, invalid type-parameter scope, duplicate names, generic task
functions, task function values, nonfunction invocation, arity/type mismatch, foreign references,
fragment cycles, shared owned fragments, unused fragments, stale plans, exhaustion, and
cancellation must return the owning typed diagnostic and leave accepted `HEAD` unchanged.

A failure while regenerating a transport, artifact, or documentation output must not replace a
valid predecessor with a partial file. Use the existing create-new or synchronized owned-stage
publication boundary. An accepted semantic write followed by a derived-cache failure remains an
accepted write and is reported separately; complete the required derived regeneration before
campaign completion.

### 6.4 Resource evidence

Keep authored record/byte counts, normalization and validation work, affected owners/relations,
compiler units, artifact objects/bytes, VM instructions, reference expressions, call frames or
measured depth, collection items, wall time, CPU time, peak RSS, file bytes, service requests, and
retries separate. Do not add one generic `fuel` value or invent a performance SLO. A representative
fold must terminate or return an existing typed limit; it must not panic, abort, recurse through an
unbounded Rust host stack, or silently truncate.
