## 2. Decision and finite outcome

**Before:** a library can abstract over a callback's effect row, but cannot declare a parameter denoting a caller-selected requirement and perform a known operation through it. Useful DataStore/Configuration work consequently remains tied to concrete requirements or consumer callbacks that implement the operation-using body. Current same-name/same-package requirement coverage is not a general cross-package argument mechanism.

**After:** a public ordinary library function can declare ordered requirement parameters constrained by an exact interface and a minimum operation set, receive explicit requirement arguments, perform those operations, and own lexical transactions. It composes with existing ordinary/effect parameters, named function values, prefix binding, direct/indirect calls, recursion and offline packages. A consumer explicitly supplies its own requirements and deployment grants; the library acquires no deployment authority by being imported, instantiated or returned as a callable.

Implement this general mechanism and one useful transported typed-cell attempt-update library. Do not add a native typed-cell operation, compiler recognition of the witness, requirement lookup by mutable name, or contributor-only authoring facility. The mechanism must remain useful after the witness is removed.

The strongest alternative is a structural request-block adapter. Static inspection of the finite consumer found 291 nonempty lines, 107 expression definitions and 71 explicit argument-edge records. Existing contributor builders also assemble these edges. This is real mechanical friction, but it is not a measurement of authoring time, model tokens or billing. The existing executable can express those bodies; it cannot express the selected requirement abstraction. Settle the semantic boundary first, and use the resulting literal library/consumer requests as the likely next authoring workload.

A capability-attenuating effect-view algebra is also deliberately not selected. This campaign's operation constraints are **minimum requirements**, not a promise to narrow the supplied requirement. Exact-match-only operation constraints would needlessly reject ordinary consumers whose requirements allow additional operations. The whole-requirement semantics below resolves that choice without introducing partially erased attenuation types.

The current user's binary-only workflow and explicit trusted-execution preferences remain requirements. Exact authority, evaluation order, atomic publication, affine provenance and current validation are correctness guarantees. Flat notation, concrete-only operation targets and exact wire generations are revisable design/implementation choices. The selected change does not authorize broader grants, new host adapters, a daemon, automatic retries, a scheduler, general resource-transfer signatures or a replacement graph authority.

Reconsider selection only if startup source demonstrates that the complete producer-owned operation/transaction witness already works through a documented ordinary library path. ## 3. Settled language, authority and compatibility contract

### Requirement parameters and applications

1. Pure and task graph functions may own an ordered, stable-identity list of rank-one requirement parameters. Each parameter belongs to exactly one function and has a mutable local name, one exact interface reference and a canonical finite minimum operation set belonging to that interface. Empty sets are legal and still constrain interface identity. There is no interface structural matching, overload search, parameter-name lookup, inferred argument, default or wildcard. Do not extend closed external intrinsics into a new host escape.
2. Requirement parameter identities/scopes are distinct from ordinary type parameters, effect-row parameters and concrete component requirements. A requirement operand is either an exact concrete requirement or an exact in-scope requirement parameter. Use a typed discriminant; never reinterpret an ID string based on a failed lookup.
3. Direct calls and named function-value creation supply one ordered requirement argument per formal, including unused parameters and unreachable expressions. Arguments can be concrete caller requirements or caller requirement parameters. Validate arity, kind, scope, interface, operations and visibility independently of ordinary/effect arguments. Substitution is simultaneous; same-spelled parameters owned by different functions are unrelated.
4. A concrete argument must have the exact required interface and include the formal's minimum operations. Forwarding a symbolic parameter requires its declared interface/minimum set to entail the callee's constraint. A favorable current instantiation does not legalize a generically invalid body. A library body can directly perform only operations justified by the parameter's declared minimum set.
5. Abstract requirement use is allowed in task effect rows, task-callable types, capability-call operands and transaction operands. Existing effect-row parameters remain unknown unions that cannot identify an operation. Requirement substitution traverses all relevant nested types, rows, nominal applications, bodies and callable applications through the existing generic machinery.
6. After closing an application, a parameter `R` supplied with concrete requirement `q` becomes the **whole exact requirement atom `q`**. Operation constraints establish what every valid argument must provide; they do not attenuate `q`. An explicitly supplied callback with effect row containing that same `q` can use additional operations allowed by `q`, even when the generic body cannot name them through its smaller formal constraint. Document and positively test this consequence. A callback requiring an unrelated requirement still requires its own explicit row/allowance and grant.
7. Keep exact row equality, normalized set union and current containment semantics. Do not silently merge requirement identities because names, interfaces or canonical grant targets coincide. Preserve existing concrete narrow-requirement coverage; do not widen an older narrow activation while adding the new argument mechanism. Formal minimum sets introduce no library-local quota or reset: effective invocation limits and canonical counters remain owned by the actual concrete requirements/grants under existing policy.
8. Named callable values retain exact closed requirement arguments as semantic descriptor data, together with current provenance and type/effect arguments. They retain no grant, adapter, credential, live resource, transaction, creator frame or mutable substitution environment. Pure factories can create, bind and return them without invoking operations. Exact prepared/application keys must distinguish different requirement vectors even when parameter/result types happen to match. Bind preserves them; Invoke, direct calls and tail transfer recheck the current activation and concrete grant bindings.
9. Requirement arguments range over a finite set of exact references and in-scope forwarding choices; they introduce no growing type constructors. Extend finite-instantiation reasoning and accounting accordingly, including recursion that permutes requirement arguments simultaneously with existing ordinary/effect arguments. Do not relax ordinary-type expanding-SCC rejection or confuse preparation exhaustion with invalid semantics.
10. Imported functions may operate through explicitly passed caller requirements without importing or mutating the caller's component. Exact package/interface admission still applies. No implicit component search, duplicate library deployment slots, name-based rebinding, ambient authority or grant synthesis is allowed. Requirement selection itself performs no operation.

### Transactions, resources and failures

A library may open a lexical DataStore transaction through a requirement parameter whose constraint admits the exact existing transaction operation. Close it against the actual supplied requirement and existing transaction policy. Calls through the same resolved requirement share that transaction, including through imported helpers and callbacks. Preserve nested-transaction rejection, ordering, commit/rollback ownership, cancellation and possible-visibility behavior. A false conditional expectation sets the existing transaction-wide no-publication state; later operations can return their own local results without clearing it. Normal lexical completion can therefore mean committed or unchanged. A commit-time base conflict retains its existing execution failure. Do not convert a false expectation into a trap, add automatic retries, or silently change transaction semantics to make the witness appear stronger. A second store or external Configuration/HTTP operation is not made atomic by being inside this lexical body. Do not claim distributed rollback.

Support operations through a requirement parameter wherever the existing local affine rules already admit them. A resource acquired through symbolic `R` has provenance `R` and the exact interface; it can be locally matched, borrowed, consumed or dropped under the same operand. `R1` and `R2` remain distinct in generic validation even if one application supplies the same concrete requirement for both. Resolve runtime provenance to the original concrete requirement and canonical grant, preserving task scope and cumulative accounting. A fully rehashed artifact cannot change that binding.

This does not generalize resource-bearing function parameters/results, cross-function affine transfer, capture, aggregates or escape. Preserve the current private concrete consume-helper rule. Do not make a newly generic resource-transfer signature legal merely because local acquisition works. Existing generic task callbacks that acquire and finish resources internally remain useful; no borrowed lifetime is smuggled into a returned descriptor.

All source/package/artifact/raw-input boundaries validate these rules before execution. Malformed applications, missing grants, foreign interface/operation, forged substitutions and unclosed entries must fail before live adapter activation where current preparation guarantees require that ordering. A returned application `Result` is ordinary data. A trap, cancellation, quota failure or output/cleanup failure does not authorize replay. Preserve the actual visibility of earlier effects and complete joined cleanup.
