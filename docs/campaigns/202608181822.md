## 1. Executive directive

The preceding campaigns proved that lkjscript can author immutable semantic revisions, publish reusable
releases, build exact application worlds, operate durable stateful instances, route typed host commands
through immutable grants, recover unknown visibility, and reuse one topology-neutral runtime kernel.

Those are necessary platform achievements. They are not yet a polished end-user application.

The durable controller and immutable-blob publisher are strong infrastructure proofs, but their user
value is primarily verification of lkjscript itself. The next campaign must invert the relationship: a
real product becomes the primary consumer, and platform work is accepted only when it closes that
product.

Build `lkjwork`, a local durable work ledger for humans and coding agents.

The product objective is:

> A user or coding agent can initialize a project, create and evolve tasks, model exact dependencies,
> select the next actionable work, record notes and evidence, attach immutable files, inspect history,
> recover after restart, export the project, and request compact deterministic agent context without
> knowing lkjscript internals or delegating domain policy to a Python or Rust side database.

`lkjwork` must be useful as a standalone local CLI product. It is not a benchmark, a tutorial, a sample
driver, or a thin label over instance commands.

The accepted task model, validation, readiness, dependency rules, lifecycle transitions, filtering,
deterministic ordering, context selection, and attachment workflow must live in lkjscript application
semantics.

The product client may own argument parsing, terminal-safe rendering, strict machine framing,
project-directory discovery, explicit user-selected file reads, and process lifecycle. It may not own
hidden business state or silently repair semantic failures.

The campaign must use the product to expose and resolve the highest-leverage missing capabilities. The
leading gaps are typed application responses, pure read-only instance queries, validated human text,
variable-length homogeneous data, scalable durable history, maintainable large-application authoring,
and a polished product packaging boundary.

Do not begin by independently implementing every proposed language or storage feature. Begin with the
smallest complete `lkjwork` slice, identify the exact blocker, compare serious alternatives, implement
the smallest coherent winner, and immediately return to the product.

At completion, the repository must contain one coherent active architecture and one installed `lkjwork`
product. Losing prototypes, compatibility readers, dormant variants, duplicate schemas, stale examples,
and superseded documentation must be absent.

## 9. Lifecycle semantics

Select and document one coherent transition table. The following is the leading product model and may be
replaced only by a simpler model that preserves the user jobs.

- `planned -> active`: Allowed only when the task is not archived, has no manual hold, and every
  prerequisite is done.
- `planned -> cancelled`: Allowed explicitly and retained in history.
- `active -> done`: Allowed only when every prerequisite remains done and no manual hold is active.
- `active -> planned`: Allowed as an explicit stop or reset operation if retained by the selected
  command vocabulary.
- `active -> cancelled`: Allowed explicitly.
- `done -> planned`: Allowed only through explicit reopen.
- `cancelled -> planned`: Allowed only through explicit reopen.
- `hold add`: Allowed on a nonarchived nondone task; exact duplicate hold returns typed no-change.
- `hold release`: Allowed only when a hold exists; absence returns typed no-change or conflict under the
  selected policy.
- `archive`: Allowed only for done or cancelled tasks unless a stronger user story proves otherwise.
- `unarchive`: Restores visibility without changing phase.

Do not encode lifecycle rules only in CLI command availability. The application must validate every
event independently.

## 11. Mutation decision and publication semantics

The current completed/suspended decision with a byte response is insufficient for this product. Replace
it with one exact typed model that lets the application own product responses and lets pure no-change or
domain rejection avoid meaningless state revisions.

The leading shape is conceptually:

```text
MutationDecision<Response, State, Command> =
    declined  { response: Response }
  | unchanged { response: Response }
  | completed { state: State, response: Response }
  | suspended { state: State, response: Response, command: Command }
```

Names and factoring may differ, but the observable distinctions are mandatory.

- `declined` represents an expected product conflict and publishes no state revision.
- `unchanged` represents an accepted intent that changes no semantic state and publishes no state
  revision.
- `completed` publishes exactly one new state revision.
- `suspended` publishes exactly one new state revision plus one pending command before host work.
- Infrastructure rejection remains outside ordinary application response data.
- A declined or unchanged request evaluated against a stale base still rejects as stale before
  application evaluation.
- If no-publish receipts are retained for response-loss recovery, they must have a separate exact
  bounded owner and must not masquerade as state revisions.
- If no-publish receipts are not retained, document exact retry behavior and prove that no external or
  state visibility occurred.
- Validate-only and commit use the same application evaluation and response validation.

Compare a four-variant decision, a three-variant decision with one product-result sum, and retained
unchanged full-state records. Select the smallest model that gives correct idempotency, audit, and
product UX. Current behavior is not privileged.

## 12. Mandatory pure query contract

Add a first-class pure query path for stateful applications. `list`, `show`, `next`, `summary`,
`context`, and `export` must not be encoded as events.

The leading application-world contract is conceptually:

```text
mutation_entry : (State, Event) -> MutationDecision
resume_entry   : (State, Outcome) -> MutationDecision
query_entry    : (State, Query) -> QueryResult
```

- The stateful application profile names exact `Query` and `QueryResult` types and the exact query
  entry.
- A query selects one exact current instance revision or an explicitly named historical revision if
  supported.
- A query runs pure verified semantics and cannot produce a host command.
- A query publishes no instance record, HEAD, event receipt, attempt, outcome, or identity.
- A query receipt binds contract version, application digest, instance ID, selected revision or HEAD
  digest, exact result, result digest, policy, and bounded observations.
- Query input and output use strict exact typed public values with sequence and text support.
- Query pagination and bounds are validated before materialization.
- Repeated exact query against exact state produces byte-identical canonical machine output.
- Malformed output, excessive output, runtime trap, resource exhaustion, and store corruption remain
  distinct failures.
- One-shot product commands and product sessions call the same runtime-kernel query owner.

Add public platform query commands only where a generic exact consumer exists. The product client may
