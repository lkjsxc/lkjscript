## 2. Decision and finite scope

**Architectural thesis:** binary64 must be an ordinary typed scalar, while numerical algorithms and numerical failure policy belong in ordinary libraries.

Before: the primitive domain has checked I64 but no floating value, literal or arithmetic. Strict JSON admission rejects every fractional number before typed conversion. Decimal measurements require ad hoc fixed-point conventions or computation outside lkjscript.

After: a user authors and imports a statistics library, supplies a pure projection from their own sample type, processes decimal measurements through normal folds and callbacks, and persists/reloads an accumulator through existing typed data. The same scalar composes in generic/nominal values, closures and supported retained state. It remains useful if the statistics witness is removed.

This is a coherent extension of the semantic core, not a new numerical execution subsystem. Keep the accepted graph as authority, existing compilation and independent reference execution, existing effects/grants and existing storage engine. The old prohibition on floating point is a provisional design restriction; it is not a user requirement or a correctness guarantee. Explicit typing, deterministic canonical identity and exact integer behavior are guarantees to preserve.

The strongest capability alternative is broader affine or same-store transaction composition. That would deepen service libraries, but recent campaigns already removed requirement and completion barriers, while transaction joining still needs a distinct ownership contract and consumer. Numerical work opens a different class of substantial programs with a concrete source cause. Storage compaction also remains valuable, but this inspection establishes no new measured growth threshold or retention requirement that outranks the missing numeric domain. A release-only campaign is a credible alternative; the observed launch defect has a bounded existing mitigation, so it can be repaired without turning this into another general proof-system redesign.

Choose the full binary64 value domain with one canonical NaN, rather than a finite-only primitive that traps on every exceptional intermediate. Libraries may enforce finite-only policies using predicates. No user-visible rounding modes, floating exception flags, signaling-NaN payload protocol or fast-math behavior are introduced.

In scope: scalar semantics, both authoring notations, complete admission/transport/compiler/runtime support, general primitive operations, standard exports, JSON and typed-data boundaries, a transported ordinary numerical library, compatibility, the finite shared test-support repair, existing evidence owners and one combined release.

Excluded: F32, decimal/arbitrary-precision types, implicit numeric coercions, numeric type classes, float keys, transcendentals beyond square root, tensors/BLAS/GPU/JIT work, a native statistics primitive, a new storage engine, transaction joining/retry, new application deployments and a new permanent proof framework. These exclusions bound this campaign, not future language design.

The revisable direction is: ordinary numerical libraries first; then use real workload measurements to choose richer mathematics, packed numeric storage or execution improvements. Do not assume F64 makes a useful LLM, a fast tensor system or a production scientific package. Reconsider only if fresh evidence shows this scalar path already complete, a blocking correctness issue, or a fundamentally better mechanism satisfying the same ordinary-library contract.

## 3. Resolved contract

### 3.1 Values, arithmetic and comparison

Introduce the ordinary type **F64**, authored as **f64**. It participates in existing structural and nominal composition, type substitution, immutable lists, generic calls, pure binding, permitted state retention and typed persistence without new authority or capture restrictions.

| Boundary | Required behavior |
|---|---|
| Value domain | IEEE binary64 finite values, subnormals, signed zero, positive/negative infinity and one quiet NaN. Canonical NaN bits are **0x7ff8000000000000**. Other values retain their exact bits. |
| Arithmetic | Add, subtract, multiply, divide, negate, absolute value and square root. Basic arithmetic/square root use round-to-nearest, ties-to-even; preserve authored evaluation order and per-operation rounding. No reassociation, implicit fused multiply-add or flush-to-zero. Normalize every NaN-producing operation to the canonical NaN. |
| Exceptional arithmetic | Nonzero divided by zero yields the sign-appropriate infinity; zero/zero and invalid operations yield canonical NaN; overflow yields infinity; underflow rounds gradually. These are values, not I64-style traps. Existing I64 traps remain unchanged. |
| Numerical equality | Extend existing `core.value.equal` recursively with IEEE F64 leaves: NaN is unequal to every value, including itself; positive and negative zero are numerically equal. Nominal/list equality containing NaN is therefore false even against the same shared object. No pointer/hash fast path may override this. |
| Numerical order | Pure less-than and less-or-equal operations; comparisons involving NaN return false. No implicit total order. Provide `is-finite` and `is-nan`; other comparisons can be ordinary wrappers. |
| Representation/observation equality | Canonical graph bytes and internal representation equality use normalized bits, so NaN is reflexive here and zero signs differ. Evaluator agreement and graph-test expected-value observation use this relation, separately from program equality. Preserve all existing nonfloat observation behavior. |
| Integer conversion | I64-to-F64 is explicit and rounds to nearest, ties-to-even. F64-to-I64 is explicit, fallible, truncates toward zero and succeeds only when the truncated value is representable. Nonfinite/out-of-range inputs are rejected, never saturated. Validate the upper bound with **x < 2^63**, not `x <= (i64::MAX as f64)`; that rounded constant is already outside I64. |

The proposed general primitive family is `core.f64.*` with ordinary standard declarations such as f64-add, f64-subtract, f64-multiply, f64-divide, f64-sqrt and f64-is-finite. Final spellings should follow the existing intrinsic/standard naming convention and be fully discoverable. These are proposed interfaces, not claims of existing commands. Primitive signatures must be independently validated, including legacy signature adapters where still consumed. Library accumulation, merging and policy must execute as graph functions.

Keep an internal canonical-bit wrapper where Rust Eq/serialization contracts require it; do not derive IEEE numerical semantics accidentally from Rust representation equality. VM and canonical evaluator keep separate dispatch and recursive equality paths. They may use the same immutable scalar representation, but their agreement alone cannot prove its arithmetic, canonicalization or encoding correctness.

Rust documents binary64 and correctly rounded square root, but does not promise a stable `f64::NAN` bit pattern; these support an explicit lkjscript canonical representation. See [Rust f64](https://doc.rust-lang.org/std/primitive.f64.html). Do not use unspecified-precision transcendental behavior to broaden the promised primitive set.

### 3.2 Authoring, parsing and formatting

Add an explicit flat floating-literal form and a structural spelling such as `(f64 VALUE)`, both lowering into the same typed intent and canonical expression. Use existing public schema conventions rather than inventing a second parser authority. Preserve reviewed plan/apply bindings, body replacement, scopes and identity continuity. The same literal in both notations must have equivalent reviewed meaning as existing structural authoring requires.

The numeric text grammar is locale-independent: JSON-style decimal numbers, with optional fraction/exponent, plus exactly `nan`, `inf` and `-inf`. No whitespace, leading plus, hexadecimal syntax, underscores or locale decimal separators inside the scalar token. Integer-form tokens are legal inside an explicitly F64 literal. Negative zero spellings preserve the sign. Decimal overflow beyond finite binary64 is a parse failure; explicit infinities use their named tokens. Decimal underflow rounds to a signed subnormal or signed zero. Conversion must be correctly rounded, including halfway cases.

Expose a fallible text parser and formatter. Follow the inspected `i64-parse-result` convention: parsing returns the structural record `{valid: Bool, value: F64}`, with `valid=false` and positive zero in `value` on failure. Fallible F64-to-I64 conversion returns `{valid: Bool, value: I64}`, with false and integer zero on failure. A failure payload is only a deterministic filler, not a parsed result. Do not add an exception system or expand generic Result/Option serialization merely to support these operations.

Formatting must round-trip finite bits, preserve negative zero (emit `-0.0`), and spell special values as `nan`, `inf`, `-inf`. Use a suitable shortest round-trip formatter with its choice documented. Formatting is a presentation boundary; graph identity is derived from canonical bits, not a formatter's decimal choice. Different accepted decimal spellings of the same F64 denote the same numeric meaning, without weakening existing request/idempotency commitments.

### 3.3 JSON and effects

The current shared parser rejects floats globally. Add an explicitly selected **application numeric admission policy**, keeping control/manifests/security integer policies strict. Follow all callers: `src/platform/cli.rs`, `src/platform/deployment.rs`, `execution/normalized/runner.rs` and `codec.rs` are relevant. Do not fix only the inner codec. Typed JSON built-ins and every already-supported application ingress/egress path advertising typed values must agree.

- Typed F64 accepts finite JSON integer/fraction/exponent numerals with defined binary64 rounding. Preserve `-0` and `-0.0` deliberately; an intermediate generic number object must not erase their sign.
- Typed I64 remains exact. Fraction/exponent spellings such as `1.0` and `1e0` remain invalid for I64 under the existing strict contract. Do not route old integers through F64 or relax range checks. Include values above 2^53 in this proof.
- Keep byte/depth/item/string limits, duplicate-field and trailing-input rejection, and exact control schema admission. Reject an out-of-range decimal such as `1e400`; do not convert it silently to infinity.
- Finite F64 JSON output is a JSON number. Nonfinite output fails explicitly; never emit null, strings or invalid JSON in its place. Validate/buffer the complete output before emitting a successful payload, preserving the current bounded output behavior. An F64 type is potentially encodable, so do not reject the whole type during preflight merely because some values are not.
- Rejection of external arguments precedes live effects. Output failure after an effect preserves the actual possible visibility and cleanup classification. Receiving no result is not evidence of rollback. In particular, a completed data transaction remains completed if later JSON encoding rejects its returned infinity.

JSON's finite boundary is a transport contract, not a restriction on internal F64 values; [RFC 8259 section 6](https://www.rfc-editor.org/rfc/rfc8259.html#section-6) excludes NaN and infinity tokens. A library can guard finiteness before returning JSON or represent an exceptional result through an ordinary nominal variant.

### 3.4 Encoding, compatibility and admission

Canonical numeric payloads use eight bytes of binary64 bits in explicit little-endian order with an unambiguous F64 type/expression/value tag. Canonical writers normalize NaN; strict readers reject noncanonical NaN payloads, malformed/truncated encodings and F64 material disguised as a predecessor generation. Signed zero and all supported special values round-trip through typed binary data. No host-endian or JSON encoding may define durable F64 identity.

Keep old primitive/type/layout/data bytes and accepted identities unchanged. The inspected source uses Graph 16, TypeObject 10, compiler-unit 12 and bytecode 8, with genuine older readers. These are observations, not prescribed new numbers. Existing disjoint type envelopes demonstrate how to preserve old bytes. Change only the boundaries that need new representation; enumerate them and each actual consumer before selecting version changes. Do not append a Rust enum variant under an old wire generation and call it compatible.

The new executable must still inspect, check, rebuild and execute currently supported genuine predecessor projects/packages/artifacts. New meaning must be detected by old products and clearly rejected without altering source or application state. Keep authentic old fixtures and old request/allocated identities. Useful owners include `kernel/contract.rs`, `kernel/codec.rs`, `kernel/wire14.rs`, `compiler/wire10.rs` and `tests/fixtures/graph10-unchanged-types-and-data.json`.

No migration of existing integer application data or physical data engine is required. New F64 layout tags describe only new schemas. Mixed old/new programs must work under the current runtime. Floats remain excluded from existing `NormalizedMapKey` and `DataKeyPart` contracts; do not accidentally admit them through Rust Eq/Ord or codec generalization.

Complete semantic/type/effect closure admission still includes unused arguments and unreachable syntax. Producer checking cannot replace independent package/artifact loader checking. Preserve exact substitutions, callable/nominal origins, resource exclusions, cancellation, work accounting and checked-value eligibility; F64 grants no new ability to serialize or capture a secret/resource.

### Ordinary numerical library witness

Author a separate ordinary package implementing:

- A nominal `Stats` accumulator with `count: I64`, `mean: F64`, `m2: F64`.
- Welford update: `n' = n + 1`, `delta = x - mean`, `mean' = mean + delta / F64(n')`, `m2' = m2 + delta * (x - mean')`, in that order.
- Merge: empty accumulators are identities; otherwise `n = a.n + b.n`, `delta = b.mean - a.mean`, `mean = a.mean + delta * (F64(b.n) / F64(n))`, and `m2 = a.m2 + b.m2 + delta*delta * ((F64(a.n)*F64(b.n))/F64(n))`, preserving the stated operation order.
- `summarize<T>` over a list and caller-supplied pure `T -> F64` projection using ordinary fold/binding. Finalization returns an ordinary nominal Empty/Ready result containing count, mean, population variance and standard deviation. Empty has no invented mean. Variance is `m2 / F64(count)`; standard deviation is its square root.

The witness accepts finite projected samples. Use an ordinary application-defined invalid-sample/arithmetic-result case for nonfinite input or accumulator overflow; counts retain checked I64 behavior. This policy is graph code, not a new host primitive. Do not silently clamp numerical errors. Exposed state/policy is a designed witness, not a claim of a production statistical API or adoption.

Remove or make producer authoring paths unavailable before consumer execution. Edit the projection through ordinary reviewed body replacement to add 1.0; mean must increase by 1.0 and variance remain unchanged. No compiler or host change accompanies that edit.

Checkpoint the halfway accumulator through the existing typed binary codec, terminate the process, decode it in a fresh process and continue. A driver may transport opaque emitted checkpoint bytes and supply inputs; it may not implement accumulation or modify internal storage.
