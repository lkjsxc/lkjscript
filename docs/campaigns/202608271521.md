## 2. Primary objective

Establish one public, tag-driven GitHub Release path that makes a verified `lkjscript` binary straightforward to download and use.

The final state must provide:

1. one stable direct URL for the latest supported Linux x86-64 archive;
2. one version-specific release URL for the same immutable bytes;
3. a deterministic archive containing the executable and redistribution notices;
4. a published SHA-256 checksum;
5. exact release metadata binding the asset to source, toolchain, target, executable contract, and verification evidence;
6. an immutable GitHub Release and its GitHub release attestation;
7. a repository-owned release preparation and verification path;
8. a least-privilege GitHub Actions workflow that builds and verifies before obtaining publication authority; and
9. a live first release, expected to be annotated tag `v0.1.0` unless active-checkout evidence requires the next unused patch version.

This campaign changes distribution and release operations. It must not change language meaning, Graph 5 authority, artifact contract 10, CLI contract 10, current public operations, or the service/worker boundary merely to produce a release.

## 3. Why this objective is selected now

The previous campaign closed the ordinary copied-binary command lifecycle. A copied release executable can create a standard-dependent Graph 5 project, inspect and change accepted meaning, run graph-owned tests, build an artifact, and execute target `main` without Cargo, the checkout, the network, or external templates.

Distribution is now the immediate public bottleneck:

- `README.md` instructs users to copy `/path/to/released/lkjscript`, but no public path supplies that file;
- the repository has no `.github/` workflows;
- there are no tags or GitHub Releases;
- GitHub Actions run artifacts would be temporary and less discoverable than a release asset;
- the existing copied-binary acceptance test already provides a strong product oracle that a release pipeline can reuse.

Implementing more semantic operations or normalized service deployment first would increase product capability while leaving every user responsible for cloning and compiling. Publishing an unverified raw build would reduce download friction but create a new integrity, licensing, and support ambiguity. The selected campaign closes the smallest dependency-complete distribution path without reopening the completed semantic architecture.

## 4. Definition of success

The campaign succeeds only when all conditions below are simultaneously true.

### 4.1 Public download

- A non-authenticated client can download `lkjscript-x86_64-unknown-linux-gnu.tar.gz` from both:
  - the exact release URL for the released tag; and
  - `https://github.com/lkjsxc/lkjscript/releases/latest/download/lkjscript-x86_64-unknown-linux-gnu.tar.gz`.
- Both downloads have the same SHA-256 digest as the published `SHA256SUMS` entry and the GitHub asset digest.
- The README presents a direct download link, checksum verification, extraction, optional installation into a user-selected directory, and a first `capabilities` command. Do not use `curl | sh`.
- The README states the exact supported target and the measured dynamic runtime requirement instead of claiming generic Linux portability.

### 4.2 Exact release identity

- The release tag is a strict annotated `vMAJOR.MINOR.PATCH` tag.
- The tag version exactly equals the root `Cargo.toml` package version.
- The tag targets the exact release commit and that commit is reachable from `origin/main`.
- The release title and release identity use the same tag.
- The release is not a prerelease.
- A successful published release and its tag are immutable.
- Existing published tags, releases, or assets are never moved, deleted, overwritten, or uploaded with `--clobber`.

The expected first tag is `v0.1.0` because the audited package version is `0.1.0` and there are no tags or releases. If `v0.1.0` exists by implementation time, inspect it. Reuse it only when it is the exact intended annotated tag and no contradictory release exists. If a source fix is required after that tag was pushed, increment the package to the smallest unused patch version and create a new tag; do not move the old tag.

### 4.3 Supported asset

The canonical release asset is named exactly:

```text
lkjscript-x86_64-unknown-linux-gnu.tar.gz
```

The stable asset name intentionally excludes the release version so GitHub's `releases/latest/download/...` URL remains stable. The archive has one top-level directory named `lkjscript/` and exactly these regular files:

```text
lkjscript/lkjscript
lkjscript/LICENSE
lkjscript/THIRD-PARTY-LICENSES.html
lkjscript/RELEASE-MANIFEST.json
```

Requirements:

- `lkjscript/lkjscript` is executable and is the exact candidate that passed release verification.
- `LICENSE` is byte-equal to the repository root Apache-2.0 license.
- `THIRD-PARTY-LICENSES.html` is generated from the exact locked production dependency closure with a pinned and checksum-verified license tool.
- `RELEASE-MANIFEST.json` is canonical release metadata, not program meaning or an authoring format.
- No source tree, Cargo target directory, local paths, credentials, caches, logs, Graph repositories, artifacts, debug symbols, or workflow metadata outside the selected manifest fields are present.
- The top-level directory mode is `0755`; the executable mode is `0755`; the three metadata/notice files use `0644`.
- Use POSIX ustar-compatible tar metadata, exact listed member order, numeric owner/group `0`, and the tagged commit time for every member. Gzip at the selected fixed level with name/time headers disabled. Record the exact tool versions and arguments.
- A second public asset named `SHA256SUMS` contains exactly one lowercase SHA-256 line in standard two-space form for the archive, terminated by one newline. Do not make it self-referential.

Do not publish a standalone raw executable as a competing canonical asset. An HTTP download does not preserve the executable mode or carry redistribution notices as reliably as the archive.

### 4.4 Release manifest and external release receipt

`RELEASE-MANIFEST.json` must be generated and strictly verified by first-party Rust tooling. Use a versioned operational schema local to the release tool; do not add it to the language contract registry. Keep it reproducible from stable release inputs. It must bind at least:

- schema identity and version;
- package name and package version;
- expected release tag, tagged commit SHA, and commit timestamp;
- annotated tag-object SHA for a real release, with an explicit absent state for a dry run before the tag exists;
- repository identity;
- target triple;
- `rustc` and Cargo versions;
- `Cargo.lock` SHA-256;
- release binary mode, byte length, and SHA-256;
- ELF class, machine, interpreter, required shared libraries, and highest required `GLIBC_X.Y` symbol version derived without executing `ldd`;
- current CLI contract and executable registry digest obtained from the exact candidate;
- root license mode, byte length, and SHA-256;
- third-party notice generator version, downloaded tool SHA-256, notice mode, notice byte length, and notice SHA-256;
- the exact expected archive member names and modes;
- deterministic packaging parameters, command/tool versions, and source timestamp;
- publication mode (`dry-run` or `release`).

Do not put volatile execution evidence in the archive manifest. Runner image identity, workflow run ID/attempt/URL, wall-clock observations, local paths, verification receipt paths/digests, and candidate-test log digests belong in a separate first-party `release-receipt.json` retained in the transient workflow artifact and selected campaign evidence. That receipt must also record the manifest digest, archive digest, `SHA256SUMS` digest, hosted context, and every verification classification.

Do not make the manifest self-referential. It may describe and digest the three payload files other than itself, but it must not contain its own digest, the final archive digest, or the checksum-file digest. The external release receipt, `SHA256SUMS`, GitHub's asset digest, and the immutable release attestation close those outer bindings.

### 4.5 Product verification

Before publication, the exact executable placed in the archive must:

- be a regular non-symlink ELF executable for x86-64;
- pass `capabilities` with CLI contract 10 and the expected registry digest;
- pass the existing copied-binary standard-dependent command lifecycle from a clean temporary directory with a cleared environment and no checkout, Cargo, or network dependency;
- pass a fresh repository `lkjscript-dev check full` for the exact release source content;
- preserve existing service-gate classification. On the GitHub-hosted Ubuntu runner, Docker-dependent service acceptance is expected to be available and must pass. If GitHub changes the runner environment and the gate is genuinely unavailable, do not publish or claim campaign completion until an independent approved hosted environment supplies the required release evidence.

The archive verifier must extract to a new directory, reject symlinks, hard-link surprises, absolute paths, parent traversal, duplicates, noncanonical ordering, extra members, missing members, wrong modes, malformed metadata, checksum mismatch, target mismatch, and candidate mismatch before any public upload.

### 4.6 Workflow security and separation

- The build-and-verify job has read-only repository permissions.
- The publish job receives only the minimum write permission needed to create a GitHub Release. It performs no checkout and executes no repository binary or repository script.
- A separate post-release job has read-only or no repository write permission and verifies anonymous download, checksum, extraction, release attestation, and a public-binary smoke lifecycle.
- Third-party GitHub Actions are pinned to full commit SHAs, not mutable tags.
- Checkout does not persist credentials.
- No long-lived personal access token, cloud credential, package-registry credential, or secret is added.
- Workflow-run artifacts are transient handoff objects between jobs, not the public distribution authority.
- Concurrency is scoped by release tag with `cancel-in-progress: false` so one run cannot cancel another publication midway.
- Every job has an explicit timeout and bounded retained output.

8. Split the workflow into:
   - a read-only build/verify/package job;
   - a publication job with `contents: write`, no checkout, and no execution of repository code;

9. 12. The post-release job anonymously downloads both the exact-tag URL and the latest URL, compares their SHA-256 digests with `SHA256SUMS` and GitHub's asset digest, safely extracts the archive, runs release attestation verification, executes `capabilities`, creates a command project, checks/builds/runs it, and confirms `"hello"` without a checkout or Cargo.

14. Make `v0.1.0` the first release when still unused. Implement, verify, commit, normal-push the release content to `main`, verify `origin/main`, create an annotated tag at that exact commit, push only that tag, and observe the hosted workflow through public completion.

## 7. Target release architecture

```text
annotated SemVer tag on origin/main
              │
              ▼
read-only GitHub Actions build job on ubuntu-24.04
  exact checkout + pinned Rust + Cargo.lock
              │
              ├── fresh lkjscript-dev check full
              ├── exact candidate copied-binary acceptance
              ├── pinned cargo-about notice generation
              └── first-party release prepare + verify
                              │
                              ▼
        transient Actions artifact containing fixed assets
                              │
                              ▼
publish job: no checkout, contents:write only
  immutable-setting check -> draft -> exact asset inspection -> publish
                              │
                              ▼
immutable GitHub Release + release attestation
                              │
              ┌───────────────┴────────────────┐
              ▼                                ▼
exact-tag download URL             stable releases/latest URL
              │                                │
              └───────────────┬────────────────┘
                              ▼
read-only anonymous post-release verification
```

Authority boundaries:

- `Cargo.toml` owns the release version.
- The annotated Git tag binds the version to one commit.
- Source, Graph 5 repositories, and executable contracts remain the product authorities they already are.
- The release archive is a derived distribution of the tagged executable.
- The manifest describes the derivation but does not select semantics.
- `SHA256SUMS`, the GitHub asset digest, and the release attestation are independent integrity evidence.
- The transient Actions artifact is a job handoff, not a public or durable release.
- A published immutable release is durable distribution evidence, not an editable program authority.

Failure boundaries:

- Build, test, notice generation, preparation, archive verification, checksum failure, or tag validation failure occurs before publication authority and creates no release.
- A publication conflict never deletes or overwrites remote state.
- A failed draft remains a draft for exact inspection or safe retry.
- Once published immutable, recovery is a new patch release. Never mutate the published release.
- Post-release transport verification failure does not justify deletion. Diagnose propagation versus content; rerun transport verification when bytes are already exact, or issue a new patch release when content is wrong.
