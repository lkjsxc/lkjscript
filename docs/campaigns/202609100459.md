## 3. Fixed semantic contract

Notation such as pair<A,B> below explains typed meaning; it is not a proposal for a maintained text
language. Public compact records must expose this meaning through their existing typed adapters.

### 3.1 Declarations, application, identity, and public changes

Records and variants retain their existing owner kinds, stable declaration/member identities, and
visibility rules. They may own an ordered list of stable type parameters. Each parameter belongs to
exactly that declaration and carries the existing constraint set: empty or capture-safe. Duplicate
names/identities, foreign ownership, unknown constraints, and out-of-scope references reject.

A positive-arity nominal application consists of an exact nominal declaration reference and exactly
one ordered type argument for each declared parameter. Arguments resolve in the caller's exact scope
and package closure. A generic declaration without its arguments is not a value type. Reject missing,
extra or out-of-scope arguments, non-nominal targets, inaccessible declarations, and unsatisfied bounds
at every application, including unused parameters, dead branches, empty containers and payloadless
variant cases. There is no inferred argument, implicit coercion, subtyping, or type erasure permission.

Zero-arity Named remains the only canonical representation for existing non-generic nominal types.
Reject a separate zero-argument application spelling/encoding that would give the same type a second
canonical identity. Positive-arity identity includes the complete ordered argument vector, including
phantom parameters. Thus pair<I64,Text> and pair<Text,I64>, and marker<I64> and marker<Text> with
identical stored fields, remain different types. Mutable declaration/parameter display names do not
replace stable identities. Exact dependency revision and canonical definition inputs additionally
bind validation, compiled reuse, preparation, and layout proofs; a type digest alone is not that proof.

Extend record/variant creation, the existing add-type-parameter and constraint-edit intent, type
references, constructors, field/case edits, and their public compact representation as one path.
Creation must allow fields/cases to mention parameters allocated in that same complete request.
Adding a parameter to an existing nominal declaration preserves its existing owner/member IDs but
requires every affected reference in the complete candidate to supply a valid application. A partial
edit that strands raw Named references rejects without changing HEAD. Do not solve it with hidden
per-use declaration cloning or implicit defaults.

Inspection and staged-package interfaces must expose parameter order, identities, constraints,
member type expressions and application arguments completely within existing bounded paging/context
rules. Function-definition projection and extraction must preserve applied types on already admitted
function forms; this does not authorize generic-function extraction beyond the current supported
extraction contract. Plans show real type/interface impacts. Stale plans and continuations reject;
renaming alone preserves exact bindings. Update discovery, diagnostics and generated guides through
their executable owners. No separate source syntax, raw-storage authoring, or generic-only CLI exists.

### 3.2 Construction, functions, constraints, and finite type closure

Constructors select one full nominal application, substitute declaration parameters through every
field/case payload, and require exact member ownership and types. Projection returns the substituted
field type. Exhaustive matching uses the selected application's complete case set and exact payload
types, including payloadless cases. Preserve graph-owned expression evaluation order, one evaluation
of each selected child, and existing selected-branch behavior; do not reorder effects by type argument
or field-name sorting. Traps stop later evaluation as before.

Generic pure functions may accept, return, construct, project and match applications containing their
own parameters, including nested lists, existing structural types and other finite nominal
applications. Legal caller-scope arguments may be types owned by the consumer; the producing library
does not acquire a reverse dependency on the consumer merely to instantiate its own template. This
does not waive existing public-interface visibility rules. Concrete task functions and ports may use
closed applications. Generic tasks, generic
interfaces/components, higher-kinded or higher-rank parameters, type aliases, traits, new dictionaries,
automatic lexical capture, and resource polymorphism are not added. Existing generic call-recursion
rules and pure tail-space guarantees remain unchanged.

Declaration bounds are checked while validating templates and again at each use in the appropriate
scope. An in-scope constrained parameter can discharge a matching required constraint; an unrelated
parameter with the same name cannot. Forming batch<T> with unconstrained T is allowed as abstract
ordinary generic data; capturing its stored T requires the appropriate explicit assumption. Do not
make every generic nominal parameter capture-safe by default merely to simplify implementation.

Generic nominal definitions must be nonrecursive in this slice. Reject direct and indirect cycles
involving a generic nominal definition, including expansion through another nominal declaration,
a monomorphic wrapper or a function-type member, and type-growing cycles such as node<List<T>>.
Cycle checks must also prevent a concrete substitution from introducing an applied-nominal layout
cycle through a monomorphic wrapper. A cycle wholly inside an already admitted monomorphic type is
not newly forbidden. Finite values/types such as pair<I64,pair<Text,Bool>> are supported. Diagnose
unsupported recursive generic definitions before unbounded expansion or host-stack overflow. Existing
monomorphic nominal recursion, ordinary value-depth limits, and generic function recursion are
separate matters and must not be conflated.

Build a finite, preparation-local instantiated type/layout closure from all relevant roots: accepted
member/signature types, constructor applications, constants, graph tests, port/target state, dependency
interfaces, and explicit function/call instantiations. A collector that only scans generic function
calls misses a non-generic function constructing a concrete applied record. Memoization includes the
full application and exact preparation inputs, not just the declaration. Charge work, pending nodes,
substitutions, visited state, layout metadata and allocations through the owning existing budgets
before growth. Type-depth/work exhaustion is an explicit failure, never an incomplete successful
layout. No new arbitrary machine minimum or larger default product budget is authorized.

### 3.3 Value properties, retention, and effects

Applied nominal data is not an affine container. A concrete application whose arguments or substituted
stored-member closure contain live capability resources/affine values is inadmissible, including an
absent resource case, an empty list, or a phantom resource argument. Abstract parameters can appear in
validated generic templates; every concrete application and raw execution boundary must recheck the
existing resource-containment rules. Preserve the existing treatment of pure function signatures as
capture-safety leaves: a future signature is not itself a stored resource or capture. Actual callable
origin, pure target and retained environment still require independent admission.

For the new applied types, compute capture safety, equality eligibility, external-encoding/typed-data
eligibility and session retention separately. Require the relevant existing property of all supplied
type arguments, including phantom arguments, and of every substituted stored field and every case
payload. This deliberately conservative all-argument rule prevents phantom parameters becoming an
unproved permission-erasure feature. Do not inspect only the active variant case or existing elements.
A marker<Secret> with an ordinary integer field is not made capture-safe or durable by its phantom use.

A safe concrete batch<I64> may be retained by function-constant/bind. An abstract batch<T> can be
captured with a valid T:capture-safe assumption. A pure callable may be stored transiently where the
existing rules permit it, but callable-containing applications remain unequal/nonserializable and
cannot become retained session state. Secrets, streams, live handles, unresolved parameters and
StaticText retain their existing property-specific restrictions; capture-safe does not mean durable.
Do not broaden raw Option/Result encoding or any other currently unsupported codec form incidentally.

Production values/layout indexes retain exact prepared-program origin and concrete application
identity. A passing result-type declaration is not raw-value admission. Host/decoder/resident ingress
must reject foreign origins, wrong applications and forged eligibility before downstream callbacks
or capabilities. Ordinary internal forwarding/projection/invocation must preserve checked immutable
values without rediscovering descendant eligibility on every use. Retain cumulative accounting,
cancellation and stack-safe disposal. Bounds and classifications cannot be keyed by declaration alone.

Cancellation/exhaustion during validation, preparation, construction or retention installs no partial
accepted graph, callable, successful value or next session state. Old immutable aliases remain valid.
Release owned temporary state and allow a healthy subsequent invocation. An earlier external effect
retains its actual possible visibility; only the enclosing first-party transaction can roll back its
own staged writes. Never execute a live effect twice for production/reference comparison.

### 3.4 Canonical representations, strict loading, and data continuity

Keep all pre-existing base TypeObject bytes/digests, including zero-arity Named and composites of
unchanged types, byte-identical. Introduce one disjoint, explicitly tagged positive-arity application
object encoding carrying the nominal reference and ordered argument digests. Its new form/domain
must be distinguishable from the retained base-type encoding. Select encoding by type form, never
by the history of how a type was loaded. There must be exactly one encoding for each supported type;
reject empty application aliases, unknown tags and mixed/noncanonical envelopes. Private symbols and
wire-tag allocation are implementation decisions, but these identity and rejection guarantees are not.

Advance the affected graph, validation/witness/summary, interface, compiler, artifact and public
request contracts at their actual owners when their representation or admission changes. Do not
renumber every independent contract, globally salt old type identities, or retain obsolete graph
production readers to avoid the cutover. Supporting unchanged base type forms alongside a new
application form is not a compatibility interpreter for an old program graph. Old incompatible
graph/package/artifact inputs reject deterministically without mutation; recovery is retained older
executables/backups or the explicit contributor cutover, not automatic operational migration.

Canonical owners retain templates and explicit type arguments, not generated concrete declarations,
runtime addresses or a mutable instantiation registry. Compiler units retain enough ordered template,
constraint and application meaning for strict loading to cross-check against exact canonical owners.
The loader must detect erased/reordered parameters, forged constraints, wrong constructor applications,
member substitution errors, missing private code/types and nominal-origin mismatches even if outer
hashes are recomputed. Clean/incremental compilation must agree after affected definition, constraint,
argument and dependency changes. A cache from another instantiation cannot certify this one.

Production preparation derives layouts/proofs from admitted compiled inputs; canonical reference
preparation independently substitutes and derives layouts from accepted owners. Neither may select
its answer from the other's tables. Neutral bytes/values may be shared where already appropriate,
but independent expected-layout fixtures and fault tests must cover that shared surface.

For applied ordinary concrete types, extend existing JSON and canonical typed-data codecs rather
than adding another serialization API. JSON keeps its current external representation and expected-type
decoding semantics: an untagged JSON document is not evidence of a prior nominal application identity.
Do not require new nominal identity tags in JSON or claim it rejects indistinguishable phantom types.
Canonical typed-data encoding does bind the application. Its data layout identity includes a new application discriminator,
the nominal identity, every ordered argument (including phantom arguments) and the substituted member
layout under the existing layout rules. Do not include an entire package/source revision merely to
invalidate all stored data after a code-only change. Distinct phantom applications cannot decode
one another's otherwise identical payload. Preserve all existing monomorphic data layout identities
and encoded bytes exactly, as well as data-store, backup, queue and deployment formats. Keep current
codec size/depth/item limits and fallback/error behavior. Malformed or foreign data never yields a
partially decoded successful value; data-decode-or retains its existing explicit fallback semantics.

An ordinary closed application is admissible as structured-session State when its full retention
property passes and all repeated State positions are exactly that application. Mismatched arguments
across State/decision positions, or nested forbidden state, reject before readiness. The existing
session phase, output reservation, cancellation, lifetime and parent-owned resource protocol is
unchanged. No second session representation or application-specific runtime state is introduced.
