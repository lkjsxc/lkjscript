## Observed failure mechanism and selected repair

The healthy repository reader captures its catalog under a shared publication lock.
On a failed catalog observation, `open_store_shared` releases shared ownership,
takes the exclusive publication lock, rechecks, and if necessary reconstructs the
disposable catalog exactly once. The old implementation then converted the owned
exclusive lock back to shared before its caller read HEAD again.

[Linux flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html) does not guarantee
atomic lock conversion. The locked dependency
[fs2 0.4.3 Unix implementation](https://docs.rs/fs2/0.4.3/src/fs2/unix.rs.html)
uses that operation. Another publication may therefore run between the recovered
catalog observation and the caller's later HEAD read. A valid newer HEAD can name
an object absent from the older captured catalog. Strict object admission rejects;
this is a possible inconsistent observation, not evidence of modified accepted
packs, silent acceptance of wrong meaning, or a measured incidence in production.

The selected repair removes the downgrade. Healthy reads keep their existing shared
lock and remain concurrent. Once recovery required exclusive ownership, retain it
until the caller finishes that observation and drops its existing lock handle.
Do not unlock/relock after capturing the store, create a second catalog database,
retry without a finite bound, discard reconstruction observations, or weaken object
validation. The recovery path temporarily excludes other readers as well as writers;
that is the deliberate cost of this small correctness repair. No fairness or
cancellable-lock-wait guarantee is added.

## Maintained regression scope

`src/platform/publication/recovery_lock_tests.rs` owns four checks through the
existing repository and storage operations, using disposable local repositories:

- Healthy observations admit an independent shared lock but reject a writer.
- Recovery retains exclusive ownership through the matching catalog/HEAD read,
  preserves HEAD and reconstruction accounting, and releases ownership afterward.
- An explicitly controlled conversion gap permits a real reviewed publication on
  another thread; the captured old catalog rejects its new HEAD, while both the old
  immutable publication and a newly captured complete observation remain valid.
- An invalid accepted HEAD rejects without replacement and does not leak the lock.

The gap check models an OS-permitted interleaving deterministically. It is not a
probabilistic scheduler stress test or a claim that the kernel produced that timing.
The lock-retention assertion is intended to fail against the old implementation;
the complete outcomes and source acceptance are recorded below when observed.
The tests do not modify user repositories, running services or application data.
