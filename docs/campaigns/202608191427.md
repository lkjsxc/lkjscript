## 1. Executive directive

Convert lkjscript from a semantic platform that can be driven through a large external construction
program into a semantic software-development system whose ordinary public CLI is the primary
authoring, history, build, test, run, inspection, and recovery interface.

The meaning graph must become the center of software development, not merely an intermediate
artifact assembled by Python, Rust, JSON, or another source language. A coding agent must be able to
create and evolve a nontrivial application through bounded exact CLI interactions. Every accepted
semantic change must automatically create an immutable development revision with an exact diff and
reconstructible history. No separate manual commit step is required for semantic development.

Eliminate `applications/lkjwork/build.py` as maintained semantic source. Migrate the complete
`lkjwork` application, its release definition, application profile, immutable cases, exports, host
requirements, and any required bindings into first-class semantic development authority. Rebuild the
checked distribution artifact through public lkjscript commands only.

Treat this as an application-first campaign. The migration is not complete until a coding agent
performs a useful cross-cutting `lkjwork` feature change through the new CLI, observes automatic
semantic history, reviews the exact diff, rebuilds and tests the product, and leaves no custom
semantic builder behind.

The long-term north star is richer software such as a terminal application with an explorer, editor,
structured views, persistent state, and exact host authority. Do not claim that lkjscript can
already deliver such a product if terminal events, incremental rendering, filesystem authority,
long-lived resources, or authoring capabilities remain absent. Use that product shape as a rigorous
readiness probe, not an excuse for speculative platform accumulation.

Use incompatible-change freedom aggressively. One coherent path is better than compatibility
readers, legacy aliases, duplicate command families, generated fallback sources, migration-only
branches, or a new source language retained beside the meaning graph.

## 2. The problem to solve

At the audited baseline, lkjscript has a strong typed semantic graph, immutable workspace revisions,
release projection, application composition, durable instances, pure queries, typed host authority,
and a complete `lkjwork` product. The current weakness is the software-construction path.

- `applications/lkjwork/build.py` is roughly 255 KiB and manually constructs a very large semantic
  transaction in Python.
- The external builder owns declaration creation order, local symbols, export selection, release
  metadata, application profile mapping, immutable cases, initial values, and bindings generation.
- The public CLI validates the transaction, but the repository still treats a custom Python program
  as the practical maintained authoring source for the largest application.
- The existing `agent` interface exposes powerful low-level context and document operations, but
  ordinary development still requires explicit state directories, workspace IDs, revisions, packet
  plumbing, and separate release/application requests.
- Workspace history already exists, but it is not presented as the normal project-level development
  history with discovery, status, log, diff, revert, build targets, and automatic change receipts.
- Build configuration remains outside the semantic graph, so accepted program meaning and the
  instructions that turn it into a release/application can diverge.
- The current decision that a Python recipe was preferable to a new source language was reasonable
  for the prior product campaign, but retaining that recipe is no longer the best long-term
  development model.
- The current fixed root-policy byte ceiling conflicts with the user's explicit permission for a
  larger durable policy; context economy must be evidence-based rather than an arbitrary size
  constant.
- Git is useful outer repository history, but it must not be the only coherent history of semantic
  edits inside an lkjscript project.

The campaign must fix the construction model rather than merely renaming `build.py`, translating it
to Rust, generating it from another file, or hiding the same procedural graph construction behind a
wrapper.

## 8. Stable terminology for this campaign

- **meaning graph**: the accepted typed semantic representation of program and first-class development meaning.
- **semantic project**: one discoverable local development authority containing identity, revisions, graph meaning, targets, and exact project policy.
- **semantic repository**: the durable publication and history mechanism for a semantic project; not necessarily a database or general VCS.
- **development revision**: one immutable accepted project state selected by an exact parent and revision identity.
- **change proposal**: a bounded non-authoritative typed request that may normalize into one candidate revision.
- **change receipt**: the exact result of validation or publication, including base/result identity, diff, omissions, and publication facts.
- **build target**: accepted project meaning that declares how an exact graph closure becomes a release, application, test invocation, or other retained product artifact.
- **derived artifact**: reconstructible release, application, executable, bindings view, cache, or rendering unless a specification promotes it to distribution authority.
- **project locator**: bounded deployment metadata used to discover authority; never semantic identity.
- **selector**: a revision-bound exact or validated lookup expression that resolves to semantic identity.
- **context capsule**: a bounded digest-bound observation for one task and exact revision.
- **session alias**: a nonpersistent revision- and session-bound short handle that reduces repeated bytes.
- **automatic history**: the rule that every accepted semantic mutation publishes one revision without a separate commit step.
- **revert**: a new validated revision that semantically counters an earlier accepted change; never history rewriting or identity resurrection.
- **outer repository**: Git or another host repository that versions Rust implementation, documentation, and checked semantic project files.
- **product runtime state**: durable application instance state, distinct from development revisions.

The final implementation may choose clearer user-facing names. It must preserve these domain
distinctions and update all active documentation consistently. Do not overload `source`,
`workspace`, `project`, `repository`, `revision`, `artifact`, `history`, `runtime`, or `state`
across incompatible authorities.

## 9. Target architecture

Converge on one architecture in which project discovery selects one semantic development authority;
all accepted development meaning lives in one typed graph; every mutation publishes immutable
history; build targets select exact graph closures; and releases/applications remain distinct
derived or distribution domains.

```text
semantic project locator
        |
        v
semantic development repository
        |
        +-- immutable revision 0
        +-- immutable revision 1
        +-- ...
        +-- HEAD --> exact current revision
                         |
                         +-- executable declarations
                         +-- development/build target declarations
                         +-- immutable test declarations
                         +-- exact package/dependency selections
                         +-- task-scoped semantic indexes or derived views
                                      |
                                      | target selection
                                      v
                              exact reusable release
                                      |
                                      | application target
                                      v
                              exact application world
                                      |
                                      | instance creation + grants
                                      v
                              durable product instance

Coding agent:
  orient -> inspect/context -> validate change -> apply -> automatic revision
         -> review diff/log -> build/test/run -> next bounded context
```

- The semantic project is development authority, not application runtime state.
- Build target declarations are part of accepted development meaning but do not implicitly become
  runtime semantics.
- A release remains workspace/project-independent reusable semantic closure.
- An application remains exact runnable composition with declared host requirements and no grants.
- An instance remains durable product-state continuity with exact grants and history.
- A target build always names or resolves one exact development revision before derivation.
- A build never mutates accepted development meaning unless the command explicitly applies a
  validated semantic change.
- Generated views and artifacts never feed back into meaning through rendering and reparsing.
- Project discovery and friendly target names are lookup conveniences, not identity.

## 11. Meaning graph scope

The graph must own every accepted fact whose divergence can change the software that a target
builds. Do not place operational deployment facts, caches, terminal preferences, or local
credentials into graph meaning.

The graph should own:

- packages, modules, nominal declarations, functions, bodies, entries, and exports
- exact reusable dependency selections and import bindings
- release target identity, root package, coordinate metadata, user version if retained, exports,
  imports, and immutable cases
- application target identity, selected root release target, exact application profile, entry
  points, state/event/response/query/command/outcome types, decision mappings, requirements, limits,
  and immutable cases
- product-specific build targets that have exact deterministic semantic output
- stable target dependency edges and deterministic target selection rules
- any binding projection required by a checked native client, unless the client instead validates
  and discovers exact artifact descriptors at build or startup

The graph should not own:

- filesystem location of the project checkout
- temporary output path
- Cargo target directory
- process ID, session handle, lock descriptor, or runtime pointer
- local terminal width and rendering preference
- provider token accounting or private model transcript
- credentials, secrets, grants, or deployment-specific host paths
- derived artifact cache entries
- Git branch, commit, remote, or working-tree status unless explicitly imported as non-authoritative
  evidence

When a build fact is currently represented only in `build.py`, classify it explicitly as semantic
target meaning, distribution authority, deployment configuration, test fixture, or derived view
before migrating it.

## 12. Automatic development history

Make immutable semantic history the default consequence of successful editing, not a separate user
ceremony. The system is VCS-like in observability and recovery, but it is not required to copy Git's
staging, branching, naming, or distributed object model.

- One accepted semantic mutation publishes exactly one development revision.
- One atomic multi-edit proposal still publishes one revision.
- Validate-only publishes nothing.
- Malformed, unknown, excessive, ambiguous, stale, foreign, conflicting, no-change, or semantically
  invalid proposals publish nothing.
- An output write failure after durable publication does not undo the revision; exact idempotency or
  inspection recovers the receipt.
- A possibly visible HEAD publication is reported as unknown and never silently repeated.
- Revision order is exact and contiguous within one project authority unless a different closed
  identity is proved simpler.
- Every revision binds its exact parent, project identity, canonical graph digest, canonical
  semantic diff, publication format, and any retained optional user metadata.
- A user need not provide a commit message, timestamp, author, or branch for ordinary mutation.
- Optional actor, intent, or external-reference metadata is bounded, explicit, nonsecret, and not
  inferred from environment or hidden model state.
- Ambient wall-clock time is not semantic unless the contract deliberately records a host
  observation.
- History is immutable; rollback means publishing a new revision.
- Deleted durable identities are not resurrected by revert.
- A semantic no-change never creates a cosmetic history entry.
- Revision compaction or packing cannot erase accepted history unless a separately specified
  retention policy and portable reconstruction contract justify it.

Expose exact history through bounded public commands. The minimum useful surface includes current
status, revision log, exact revision inspection, adjacent and arbitrary revision diff, and a safe
revert or restore-to-meaning workflow.

### 12.1. Status

- [ ] Report exact project identity and current revision.
- [ ] Report whether the authority is healthy, busy, unknown, tombstoned, or corrupt.
- [ ] Report selected target names and exact identities only when requested or bounded.
- [ ] Report no Git-style uncommitted semantic state when all mutation is transactionally published.
- [ ] If proposal files exist outside authority, label them untrusted unsubmitted files rather than
      semantic changes.
- [ ] Support strict machine output and bounded deterministic human output.

### 12.2. Log

- [ ] Use exact deterministic revision order.
- [ ] Support bounded pages and explicit omissions.
- [ ] Expose parent, graph digest, change digest, change counts, publication facts, and optional
      explicit metadata.
- [ ] Never require decoding every full graph merely to paginate recent log entries unless evidence
      shows it remains acceptable.
- [ ] Reject nonexistent, foreign, pruned, malformed, or future revision selectors distinctly.

### 12.3. Diff

- [ ] Derive semantic change, not textual rendering change.
- [ ] Distinguish durable entity creation/deletion/change from function-local body churn.
- [ ] Expose target-definition changes and their build impact.
- [ ] Bind the result to exact project and before/after revisions.
- [ ] Support compact summary and bounded exact expansion.
- [ ] Never infer continuity from names or structural similarity.

### 12.4. Revert and restoration

- [ ] Publish a new validated revision rather than moving HEAD backward.
- [ ] Preserve tombstones and identity rules.
- [ ] Refuse an automatic inverse when the old identity cannot legally be restored.
- [ ] Offer a deterministic recreation/mapping proposal only when its semantics are exact and
      reviewable.
- [ ] Expose affected targets, tests, and downstream references before publication.
- [ ] Make no claim that semantic revert reverses host effects, product instance state, Git changes,
      or external artifacts.

## 13. Public project-oriented CLI

Design one ordinary public CLI around semantic projects. The exact spelling is a design decision,
but the final system must be coherent, discoverable, scriptable, strict in machine mode, and
economical for coding agents.

The following grammar is a required capability sketch, not a compatibility constraint:

```sh
lkjscript init [PROJECT]
lkjscript orient [--project PROJECT] [--known DIGEST]
lkjscript status [--project PROJECT]
lkjscript inspect SELECTOR [--project PROJECT] [--at REVISION]
lkjscript context --purpose PURPOSE [--target SELECTOR ...] [--at REVISION]
lkjscript change validate [--project PROJECT] [--context FILE] < CHANGE
lkjscript change apply [--project PROJECT] [--context FILE] < CHANGE
lkjscript log [--project PROJECT] [--after REVISION] [--limit N]
lkjscript diff [--project PROJECT] --from REVISION --to REVISION
lkjscript revert [--project PROJECT] REVISION_OR_CHANGE
lkjscript target list [--project PROJECT] [--at REVISION]
lkjscript target show TARGET [--project PROJECT] [--at REVISION]
lkjscript target build TARGET [--project PROJECT] [--at REVISION] --output PATH
lkjscript target test TARGET [--project PROJECT] [--at REVISION]
lkjscript target run TARGET [--project PROJECT] [--at REVISION] --arguments VALUE
lkjscript doctor [--project PROJECT] [--deep]
lkjscript session [--project PROJECT]
```

- Ordinary current-project operations should not require an explicit state directory, workspace ID,
  or current revision.
- Mutations must still bind the exact base revision internally and reject stale requests.
- Exact historical reads must accept explicit revision selection.
- Every command has one strict human surface and one versioned machine surface, or machine-only
  where human syntax would be misleading.
- Machine output contains exactly one framed value and no progress text.
- Human diagnostics are terminal-safe, bounded, deterministic, and actionable.
- Help is generated from or agreement-tested against executable command contracts.
- The CLI never silently falls back from project mode to a global mutable registry.
- Relative paths are resolved under explicit command-local rules and revalidated against symlink
  substitution.
- Public commands use common semantic owners rather than duplicating direct, agent, session,
  release, and application logic.

Reconsider the `agent` prefix. It may disappear if the same exact bounded operations become normal
project commands. Do not retain two equivalent command families merely for compatibility.

## 14. Change proposal and authoring model

Retain the key architectural advantage of the current workbench: editable text or JSON is a bounded
proposal that normalizes into one typed transaction and never becomes authority. Improve the
proposal model until it can maintain a large real application without a custom builder.

- Project-wide atomic creation and modification of declarations, functions, exports, dependencies,
  and targets.
- Function-scoped replacement and hole refinement with exact packet binding.
- Creation-order-independent draft symbols within one proposal.
- Revision-bound selectors and aliases that cannot escape their exact context.
- Exact validate/apply parity.
- A compact semantic preview before publication.
- Stable diagnostics that name exact owners, expected types, legal alternatives, and stale facts.
- Bounded input, nesting, items, output, and diagnostic bytes.

## 15. Build targets as first-class development meaning

Move reproducible build intent out of procedural host code. A target is accepted typed development
meaning that selects exact semantic inputs and a closed derivation contract.

Required initial target kinds include:

- reusable release target
- application target
- pure invocation test target
- stateful application case target
- product distribution target when a checked native client embeds or packages an application
- binding or descriptor projection only if a native consumer cannot directly discover exact
  artifact-owned identities

- Every target has durable semantic identity and a presentation name.
- Target dependencies are exact identity edges, not mutable names or `latest`.
- A release target selects one exact package closure, explicit exact dependencies, exports, imports,
  coordinate metadata, and immutable tests.
- An application target selects exact release targets or exact release artifacts under one closed
  rule, entry/profile mappings, requirements, limits, and immutable cases.
- Target validation checks complete referenced graph meaning at every accepted revision.
- A target may be temporarily invalid only under an explicit incomplete-development contract; build
  then fails with a stable exact blocker.
- Target output is deterministic for the same exact revision, target, dependency bytes, and build
  policy.
- Output path is deployment input and never target identity.
- A target build reads no ambient repository files unless a narrow explicit input contract names and
  validates them.
- Build does not execute arbitrary user shell, Python, Rust, JavaScript, or native hooks.
- A target cannot grant host authority to an application instance.
- Build cases are deterministic semantic executions, not host scripts.
- Target inspection exposes exact inputs, outputs, cases, requirements, limits, and dependency
  closure under bounds.
- Target change appears in semantic diff and automatic history.

## Appendix C. Failure, interruption, and hostile-input matrix

Implement deterministic coverage for each applicable case. A skipped, unavailable, indeterminate, or
unreproduced case does not count as passing evidence.

### C.1. Project marker is absent

**Trigger:** A command requiring project discovery reaches the search boundary without finding a valid marker.

**Required classification:** Project-not-found usage or authority-selection failure, distinct from corruption.

**Authority effect:** No files, locks, revisions, caches, or outputs change.

**Retry or recovery rule:** Specify an explicit project or initialize one; unchanged blind retry is harmless but not useful.

**Proof obligation:** The diagnostic names the bounded search policy without leaking unrelated directories.

- [ ] Run from outside any project.
- [ ] Run with an explicit nonexistent path.
- [ ] Bound parent traversal and output.

### C.2. Project marker is malformed

**Trigger:** The selected marker has invalid version, duplicate fields, bad checksum, invalid UTF-8, or trailing bytes.

**Required classification:** Project-locator corruption.

**Authority effect:** No semantic authority opens and no repair occurs.

**Retry or recovery rule:** Fix or restore the marker from exact authority; do not initialize over it.

**Proof obligation:** The same corruption class reproduces after restart.

- [ ] Cover every field and exact/one-over length.
- [ ] Fuzz structured decoding.
- [ ] Prove no tolerant parser fallback.

### C.3. Project marker is a symlink

**Trigger:** The marker or a required static ancestor is symlinked.

**Required classification:** Path-safety rejection.

**Authority effect:** No target authority is followed or mutated.

**Retry or recovery rule:** Select a real regular project path; never retry by following the link automatically.

**Proof obligation:** Lookup and use are revalidated against substitution.

- [ ] Replace a regular marker between discovery and open.
- [ ] Use relative and absolute spellings.
- [ ] Cover symlinked parent directories.

### C.4. Authority file is nonregular

**Trigger:** HEAD, revision record, graph object, index, or lock path is a directory, FIFO, device, socket, or symlink.

**Required classification:** Repository path corruption or unsafe-file rejection.

**Authority effect:** No read with side effects and no publication.

**Retry or recovery rule:** Operator restores a regular exact file or backup.

**Proof obligation:** Each authority owner validates file kind before trusting contents.

- [ ] Cover every authority class.
- [ ] Use race-oriented replacement fixtures where available.
- [ ] Do not hang on FIFO/device inputs.

### C.5. Permission denies project open

**Trigger:** The OS denies reading marker, HEAD, revision, or required directory.

**Required classification:** Operational authority-open failure, not semantic invalidity.

**Authority effect:** No revision or output publication.

**Retry or recovery rule:** Correct deployment permissions; retry may be legal after the external condition changes.

**Proof obligation:** Diagnostics do not claim absence or corruption when permission is unknown.

- [ ] Test read, traverse, lock, and write denial separately.
- [ ] Restart under corrected permissions.
- [ ] Bound path disclosure.

### C.6. Project mutation authority is busy

**Trigger:** Another live process holds the exact publication lock.

**Required classification:** Authority-busy operational rejection.

**Authority effect:** No candidate publication or identity consumption.

**Retry or recovery rule:** Retry only under an explicit caller policy; never create a second writer namespace.

**Proof obligation:** One project has one publication authority.

- [ ] Compete one-shot, session, doctor, backup, and build operations.
- [ ] Release lock after normal and abnormal exit.
- [ ] Document read-only concurrency.

### C.7. Foreign project identity in marker

**Trigger:** The locator points to repository bytes whose exact project identity differs.

**Required classification:** Foreign-domain rejection.

**Authority effect:** Neither authority is mutated.

**Retry or recovery rule:** Select the correct project or restore a consistent closure.

**Proof obligation:** Path and presentation name cannot override identity mismatch.

- [ ] Swap repositories between markers.
- [ ] Use same friendly name.
- [ ] Bound foreign identity details.

### C.8. HEAD is missing

**Trigger:** A non-genesis initialized repository lacks the current selector.

**Required classification:** Repository corruption or incomplete creation under exact phase facts.

**Authority effect:** No implicit selection of highest numbered revision.

**Retry or recovery rule:** Recover from backup or explicit creation reconciliation.

**Proof obligation:** The implementation never guesses current authority.

- [ ] Remove HEAD after several revisions.
- [ ] Leave staged temporary files.
- [ ] Run status and doctor.

### C.9. HEAD is malformed

**Trigger:** HEAD has invalid magic, version, fields, checksum, canonical encoding, or trailing bytes.

**Required classification:** Current-authority corruption.

**Authority effect:** No revision is selected or repaired.

**Retry or recovery rule:** Restore exact HEAD or backup.

**Proof obligation:** Strict decoder rejects every predecessor and noncanonical form.

- [ ] Exact and one-over sizes.
- [ ] Unknown fields/tags.
- [ ] Fuzz with valid checksum over invalid body.

### C.10. HEAD digest mismatches selected revision

**Trigger:** HEAD names one revision but binds a different graph/record digest.

**Required classification:** Integrity corruption.

**Authority effect:** No current graph is accepted.

**Retry or recovery rule:** Operator repair from independently verified history only.

**Proof obligation:** A digest is equality/integrity evidence, not permission to choose another revision.

- [ ] Swap two valid HEAD bodies.
- [ ] Corrupt graph digest only.
- [ ] Run deep reconstruction.

### C.11. Selected revision is missing

**Trigger:** HEAD points to an absent immutable revision or record.

**Required classification:** History closure corruption.

**Authority effect:** No fallback to an earlier revision.

**Retry or recovery rule:** Restore exact missing object or backup.

**Proof obligation:** Current authority requires the complete named closure.

- [ ] Delete current, middle, and genesis objects.
- [ ] Leave caches that appear to contain state.
- [ ] Prove caches cannot authorize.

### C.12. Revision payload is truncated

**Trigger:** A graph snapshot, journal record, or object ends before declared length.

**Required classification:** Canonical decoding corruption.

**Authority effect:** No partial graph or target set is exposed as accepted.

**Retry or recovery rule:** Restore exact bytes.

**Proof obligation:** Length is checked before allocation and decode.

- [ ] Truncate every boundary.

## Appendix D. Rich TUI editor readiness cards

Complete the matrix even when no code is retained. A missing capability is a precise future gate,
not a reason to add ambient authority or a broad framework.

### D.1. Pure editor-state core

**Current question:** Can current values model buffers, cursors, selections, modes, panes, and deterministic commands without host access?

**Missing or required contract:** Exact application state types, bounded command/event sums, pure transition/query entries, and realistic resource policies.

**Minimum legitimate probe:** A small in-memory editor model with insert/delete/move/undo commands and pure rendered view data.

**Activation gate:** Retain only if it reveals reusable semantic authoring or value blockers and is built through the new CLI.

- [ ] Use multiple buffers and command sequences.
- [ ] Reference-model differential.
- [ ] No terminal or filesystem claims.

### D.2. Buffer identity

**Current question:** Can open buffers have stable continuity distinct from paths, content digests, and pane positions?

**Missing or required contract:** Nominal application-owned buffer IDs, allocation/nonreuse, path association policy, and close/reopen semantics.

**Minimum legitimate probe:** Create, rename association, duplicate content, close, and inspect buffers in a pure model.

**Activation gate:** Activate in a full editor only when multiple open buffers are a frozen workflow.

- [ ] Same content in two buffers.
- [ ] Path change without identity change.
- [ ] Closed ID nonreuse.

### D.3. Large text representation

**Current question:** Do immutable UTF-8 text and nominal sequences avoid unacceptable copying and scans under editor-shaped updates?

**Missing or required contract:** Exact indexing unit, insertion/deletion ranges, canonical encoding, equality, fuel, retained accounting, and no representation identity.

**Minimum legitimate probe:** Benchmark a piece-table, chunk sequence, rope-like value, or application-owned line sequence against current text.

**Activation gate:** Retain a new representation only when a complete editor workload beats the simple safe route materially.

- [ ] ASCII, multibyte UTF-8, combining sequences, long lines.
- [ ] 1000 localized edits.
- [ ] Allocate-new differential.

### D.4. Cursor semantics

**Current question:** What does a cursor index: bytes, Unicode scalars, grapheme clusters, lines/columns, or application-owned positions?

**Missing or required contract:** One deterministic indexing contract, invalidation behavior after edits, bounds, and rendering mapping.

**Minimum legitimate probe:** Pure cursor movement over a bounded text corpus.

**Activation gate:** Do not promise grapheme semantics without a current consumer and Unicode-data contract.

- [ ] Multibyte and combining text.
- [ ] Beginning/end and invalid positions.
- [ ] Edit before/at/after cursor.

### D.5. Selection semantics

**Current question:** Can range direction, anchor/head, rectangular selection, and edit replacement be modeled exactly?

**Missing or required contract:** Closed selection type, normalization rule, indexing domain, and update behavior.

**Minimum legitimate probe:** Single linear selection with insert/delete replacement.

**Activation gate:** Add multiple/rectangular selections only for a frozen workflow.

- [ ] Forward/backward ranges.
- [ ] Empty selection.
- [ ] Selection after text mutation.

### D.6. Undo and redo

**Current question:** How does product-level undo differ from immutable semantic development history and runtime instance history?

**Missing or required contract:** Application-owned reversible command or snapshot policy, bounded retention, identity behavior, and crash persistence.

**Minimum legitimate probe:** Pure editor-state undo/redo for a bounded command list.

**Activation gate:** Retain only if semantics are simpler than storing arbitrary prior opaque state.

- [ ] Undo insert/delete/move.
- [ ] Branch after undo.
- [ ] Never move semantic project HEAD backward.

### D.7. File explorer tree

**Current question:** Can a TUI display a directory tree without ambient filesystem enumeration?

**Missing or required contract:** Narrow list/stat interface, exact root grant, path component encoding, symlink policy, pagination, ordering, errors, and revocation.

**Minimum legitimate probe:** Use a deterministic fake tree interface or a static application-owned tree.

**Activation gate:** Add production filesystem listing only with a complete explorer consumer and threat model.

- [ ] Large directory pagination.
- [ ] Permission and disappearance.
- [ ] Symlink and non-UTF-8 path policy.

### D.8. Explicit file read

**Current question:** How can an editor open a selected file without broad ambient authority?

## Appendix E. Agent-authoring and provider-economy benchmark cards

Run equal tasks against frozen inputs. Prefer semantic success and correction quality over the
smallest raw byte count. Retain optimization mechanisms only when they improve a complete workflow.

### E.1. Fresh project orientation

**Frozen task:** Identify project identity, current revision, active schemas, available target names, and the next legal command.

**Baseline path:** Current explicit state/workspace/revision discovery plus broad help or schema reads.

**Candidate path:** One project-discovered orientation request with known-digest support.

**Required metrics:** Files/source bytes opened, request/response bytes, process count, elapsed time, correctness questions remaining.

**Pass rule:** Candidate must provide all exact facts needed for the next task with no global schema dump.

- [ ] Do not count omitted required facts as savings.
- [ ] Do not infer tokens.
- [ ] Repeat after unchanged and changed revision.

### E.2. Inspect one function

**Required metrics:** Expanded entities, omitted facts, bytes, files, calls, time, and exact comprehension result.

**Pass rule:** Candidate wins only if the agent can produce the correct change without a later global rediscovery.

- [ ] Use a large migrated `lkjwork` function.
- [ ] Verify exact IDs and revision.
- [ ] No hidden builder source read.

### E.3. Replace one function body

- [ ] No source-text authority.

- [ ] Run from a fresh session.
