## 1. Primary objective

Replace the maintained frozen artifact-4 service boundary with strict artifact-10 normalized
deployment for both `lkjscript serve` and `lkjscript worker`, then remove the predecessor artifact,
reader, execution path, adapters, tests, generated contract entry, and current documentation after
every maintained consumer has moved.

This is one dependency-closed replacement. PostgreSQL, object storage, durable queue, HTTP,
configuration, secrets, streams, cancellation, shutdown, deployment preparation, `lkjournal`, the
service harness, and copied-binary acceptance are supporting closure of the same public workflow;
they are not independent feature campaigns here.

## 2. Why this objective is selected now

The latest campaign, `docs/campaigns/202608271521.md`, is complete. It produced and publicly proved
immutable release `v0.1.4`, including fresh hosted full verification and service acceptance. The
normalized command-lifecycle campaign in `docs/campaigns/202608270014.md` is also complete: Graph 5
is the sole editable authority and `check`, `build`, and `run` strictly use artifact 10. The only
maintained public execution split deliberately left behind is `serve` and `worker`, which still load
`applications/lkjournal/frozen-service/lkjournal-artifact-v4.lkja` through the predecessor
`PreparedDeployment` and artifact-4 runtime.

That split is now the primary architectural bottleneck. It keeps two artifact contracts, two value
representations, two prepared-program stacks, two capability bindings, two execution tiers, and a
large frozen implementation surface alive. It also prevents the current Graph 5 `lkjournal`
authority and its checked-in artifact-10 output from being the program that the released service
actually executes. Deferral would make every later service feature, authored operation, adapter,
performance measurement, and release reason across two execution systems.

Success contracts the system: one maintained artifact loader, one executable representation, one
capability binding, one resident execution path, one service harness, and one application authority.
It removes the largest remaining compatibility island before expanding authoring breadth or runtime
optimization.

or distributed runtime was rejected as unrelated scope. The selected design retains one proven host
engine per capability family and replaces only the representation-specific edge.

### 5.2 Selected design

Follow this design unless active-checkout evidence clearly disproves an assumption.

1. Keep one deployment descriptor schema. Decode it strictly and resolve its bounded relative
   artifact path before any listener, worker loop, or application effect.
2. Replace artifact-4 loading with `compiler::load_artifact`, retain the resulting exact artifact
   manifest and bundle identities, and prepare `NormalizedProgram` directly from the standalone
   artifact. Do not route service preparation through `normalized_lifecycle` because that path owns
   project discovery and accepted-authority compilation.
3. Resolve the descriptor target once within the artifact root package. Validate runner kind,
   component, exact signature, and every requirement before constructing a ready application.
4. Resolve descriptor requirement aliases once to exact `RequirementReference`s. Bind adapter kind,
   interface, exact operations, limits, sharing domain, authority revision, and descriptor digest
   through the existing normalized capability model. Runtime dispatch uses dense/exact indexes, not
   repeated name lookup.
5. Preserve the proven host state machines. Refactor database/object/queue modules into a narrow
   representation-neutral core plus artifact-10 normalized codecs/adapters. The core must not
   accept or return predecessor `Value`, `OwnerId`, prepared declarations, or artifact-4 handles.
6. Decode and encode normalized values using artifact-prepared exact type/field/case/operation
   indexes. Validate expected standard interfaces and signatures at preparation. Do not infer
   authority from a mutable alias or from structural shape alone.
7. Reuse the existing normalized configuration, secret-verifier, clock, random, identifier,
   password, byte-stream, HTTP, worker, resource-scope, VM, reference, and resident paths. Promote or
   wrap them at the public deployment boundary; do not create a second production normalized stack.
8. Move genuinely shared execution control, error, run-policy, resident-kernel, HTTP transport,
   stream, and worker mechanics out of artifact-4-only dependencies as necessary. Keep their public
   behavior and bounds; remove only predecessor-specific wrappers.
9. A prepared deployment owns every adapter instance and cleanup action it creates. Preparation is
   all-or-nothing: on failure, release already-created resources and emit no readiness. Shutdown is
   idempotent, stops admission, drains within the configured grace, cancels remaining tasks, closes
   streams/pools/adapters exactly once, and reports cleanup failures without leaking secrets.
10. Preserve the current event envelope where semantically sufficient. Define `artifact_digest` as
    `ArtifactBundleDigest::to_string()` (`artifact_bundle_...`). Add a narrowly named manifest or
    semantic identity field only if an observed maintained consumer requires it; update the owning
    contract and all consumers together if so.
11. Keep deployment contract 1 when its existing schema is sufficient. The contract already
    describes a component artifact and exact grants rather than artifact 4 specifically. Bump a
    contract only for an actual observable schema/semantic incompatibility, not because the
    implementation changed.
12. Migrate deterministic `lkjournal` policy tests to current artifact 10 and normalized scripted
    adapters. Keep the same-handler property: in-memory dispatch and live Axum transport invoke the
    same graph target and response conversion.
13. Update both descriptors and the service harness to the checked-in artifact-10 output. The
    harness verifies byte equality to a fresh public build before staging an isolated deployment.
14. Switch public `serve` and `worker` only after normalized deterministic tests pass. Then delete
    the entire predecessor production closure before final full verification.

### 6.1 Authority and persistence

- Accepted Graph 5 repository state remains durable program authority.
- Artifact-10 bytes are immutable derived executable closure. The deployment observes but never
  advances graph authority.
- The deployment descriptor is durable operational authority for one process invocation.
- Environment secrets, listener handles, pool connections, stream handles, leases, task controls,
  and dense runtime indexes are transient.
- PostgreSQL, object storage, and durable queue remain their own external authorities with the
  semantics already specified. No cross-authority commit or exactly-once guarantee is added.
- Ready output is an observation, not authority. It is emitted only after artifact validation,
  target/grant validation, secret acquisition, adapter construction, and required preflight.

### 6.2 Type and dependency direction

- Artifact preparation owns exact semantic references and dense indexes.
- Adapter codecs depend on exact prepared layouts plus representation-neutral host request/result
  types.
- Host engines do not depend on artifact generations, Graph repositories, mutable names, or VM
  values.
- HTTP/worker transport depends on normalized structural request/response/worker signatures and the
  resident invocation API, not on `lkjournal` routes or database policy.
- The VM depends on capability traits and task resources; concrete host adapters depend outward on
  PostgreSQL/object/queue mechanisms. Concrete adapters never become language semantics.

### 6.3 Failure boundaries

- Descriptor/artifact/path/identity/signature/grant errors are preparation failures.
- Missing or malformed secrets and failed required preflight are preparation failures.
- Admission overflow, deadline, cancellation, capability rejection, stale lease, resource
  exhaustion, and external infrastructure failure are typed runtime failures.
- `possible_visibility` remains a closed external-write outcome requiring application-level
  reconciliation.
- Failed or interrupted deployment never changes Graph `HEAD`.
- A hard process kill may leave effects that the external authority already accepted; restart,
  idempotency, lease, checksum, and reconciliation semantics must remain correct. Do not claim
  rollback beyond the named authority.

### 6.4 Replaceability

Keep the artifact-10 normalized value and dense-index representation behind the VM/adapter boundary.
Do not expose Rust layout or dense indexes in deployment JSON, external storage, queue records, or
public semantic identity. The neutral host cores must remain usable by a future runtime without
preserving artifact-10 memory layout.
