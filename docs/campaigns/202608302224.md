## 6. Verification, evidence, and recovery

Use this ladder: minimum predecessor/source orientation; focused iteration; final fresh full source
proof; exact target/application admission; deterministic local package; hosted dry run; immutable
publication; independent exact/latest anonymous acceptance; evidence-only closure. Do not rerun broad
profiles merely because the mandate listed them, but rerun every boundary whose exact input changed.

Classify every gate as exactly `fresh passed`, `reused passed`, `skipped`, `unavailable`, `failed`, or
`not run`. Final full, exact target admission, local release verification, hosted dry run,
publication preconditions, and both anonymous public boundaries require fresh evidence for exact
inputs. Prior first-party-data and release receipts are orientation unless the current executable
owner explicitly proves exact-input reuse is valid; reused evidence is never reported as fresh.

Required negative and containment cases include: product/tag mismatch; used tag or release; disabled
immutability; unavailable confirmation authority; concurrent release work; stale/foreign receipts or
handoffs; malformed or dynamically linked candidate; target-policy disagreement; archive path/link/
canonicalization/checksum/inventory failure; handoff mutation; publication dependency bypass; asset
clobber; exact/latest identity or behavioral disagreement; predecessor PostgreSQL descriptor or
adapter input; failed application startup without readiness; and cleanup with unchanged semantic
`HEAD`.

Before tag push, fix a bounded release defect, form a new `R`, and rerun all invalidated gates. An
unpushed local tag may be deleted only after proving it never crossed the remote boundary. After tag
push:

- never move or delete the tag;
- one exact-tag recovery dispatch is authorized only for an unchanged tag and a proven transient,
  idempotent orchestration failure that cannot create contradictory state;
- bounded read-only propagation, attestation, and download verification may retry;
- any source, workflow, target, verifier, package, candidate, or public-content defect requires the
  smallest unused additive patch, new `R`, and every affected fresh gate;
- at most one content-changing additive patch is authorized here; a second distinct content defect
  terminates the campaign with exact externally committed state and the next recovery boundary.

Do not claim a minimum kernel, universal Linux portability, reproducible build, code signing,
general provenance, hostile-code sandboxing, encrypted local data, multi-tenant isolation,
replication, consensus, exactly-once queue delivery, cross-capability atomicity, compaction, or
million-key admission.
