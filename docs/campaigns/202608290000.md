## 7. Target architecture and failure boundaries

### 7.1 Version and identity flow

```text
root Cargo package version 0.1.8
            │ owns human release tag
            ▼
annotated v0.1.8 tag -> exact source commit R
            │
            ├─ executable capabilities: independent CLI/registry identities
            ├─ Graph/project/artifact/deployment contracts: independent owners
            └─ target admission: x86_64-unknown-linux-musl candidate bytes
                                      │
                                      ▼
                     release manifest + archive + checksum
```

Compatibility decisions are made by the owning protocol's exact identity and predecessor policy,
not by comparing the product release version. A project with Graph 5 or an artifact with contract 10
does not become “version 0.1.8.” Conversely, a product release may advance while those contracts
remain unchanged.

### 7.2 Static target flow

```text
locked source R + pinned Rust/tool inputs
            -> musl candidate build
            -> independent ELF/runtime-linkage inspection
            -> two pinned userland command probes
            -> exact command/distributed/stateful/service admission
            -> target-admission receipt bound to candidate digest and R
```

The release build must not discover a host target implicitly. Target selection is explicit and
recorded. Native compiler/linker inputs are bounded and reported. Candidate execution receives only
the environment, files, network, PostgreSQL authority, and writable roots required by the owning
oracle.

### 7.3 Release flow

```text
fresh source full receipt + fresh target-admission receipt
            -> deterministic package preparation
            -> strict release verify
            -> transient release + host-verifier handoffs
            -> no-checkout pre-publication distributed/stateful proof
            -> write-isolated publication
            -> anonymous exact/latest static inspection and distributed/stateful proof
```

Release artifacts and receipts are derived evidence. They cannot edit Graph meaning, select a
semantic revision, or become package resolution authority.

### 7.4 Failure and recovery

- A build, static-inspection, userland, application, service, package, or dry-run failure before tag
  push leaves public state unchanged. Correct the exact defect, invalidate affected receipts, and
  rerun only the necessary narrow checks plus final fresh boundaries.
- A required target or hosted prerequisite that is genuinely unavailable blocks publication. It is
  reported as unavailable, never passed.
- A candidate or package mismatch rejects before upload.
- A transferred verifier failure cannot advance publication because the write job depends on both
  application oracles.
- An already-pushed tag is immutable for campaign purposes. Never move or delete it.
- An immutable release whose postcondition is unproved is externally committed but not closed.
  Read-only propagation checks may retry within the existing bounded policy. A content or workflow
  defect requiring changed source recovers through the smallest unused additive patch.
- Failure after Graph publication inside the stateful BBS remains separate derived/runtime evidence;
  it must not falsify or advance semantic authority.
