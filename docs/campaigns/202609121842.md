## 1. Assignment and accepted outcome

Implement and integrate **foreground execution of ordinary command artifacts with exact deployment grants**, then publish the accumulated task-iteration and foreground-command milestone through the existing release owner.

The proposed new public form is:

```text
lkjscript run --deployment PATH [--arguments JSON]
```

This form does not exist at the observed revision; it is an implementation requirement, not a verified command. It selects a command target from an artifact-relative operator descriptor, requires no project checkout, runs its pure or task entry once through production, returns a typed result, and joins owned work and closes adapters before reporting success. An installed executable can run many independent application bundles in separate processes. There is no shared daemon, automatic runtime lookup, embedded application executable, installer, or registry in this campaign.

**Before:** reusable task callbacks, recursive data and constant-control-space task iteration are implemented, but public project `run` executes pure targets through both evaluators. The effectful command runner is test-only. A user cannot take an ordinary effectful command bundle and execute it once using the public CLI without a service/worker harness.

**After:** an author creates and checks a program, builds its dependency-complete bundle, supplies explicit operational grants, removes the authoring checkout, and invokes a foreground command. Imported effect-polymorphic callbacks can iterate from arguments/configuration, persist results, return, and be run again in a fresh process. A pure command whose selected component has no requirements uses the same deployment route without grants. The default foreground policy does not impose cumulative execution fuel; explicit existing execution policy objects retain their bounded behavior.

This is one product-boundary campaign. Its supporting policy work removes an artificial lifetime-work cutoff from the new foreground mode while preserving independently justified admission and operational limits. It is not a scheduler, a new language effect, or a general resource-lifetime redesign.

The user delegates ordinary implementation, integration and this selected repository release. Production deployment, destructive operational-data changes, new spending, credential replacement, permission changes and history rewriting are not authorized. Exercise application effects only in owned disposable fixtures.

## 3. Why this campaign, and the revisable trajectory

The architectural thesis is that **ordinary graph task libraries should cross the same explicit artifact/deployment boundary as services, with a finite process lifecycle of their own**. The runtime already has exact target/port types, typed argument/result codecs, grant preparation, task invocation, cancellation, transactions and adapter cleanup. Exposing these through a coherent public command completes useful composition without adding application-specific host functions.

The strongest alternative is one-command installation and runtime version selection. That is directly useful and remains the next product-access candidate. However, installing the current binary more conveniently would still leave effectful batch applications without a public foreground route. This campaign first creates the application behavior that an installed runtime should execute. Broader affine borrowing/results across packages would unlock more libraries, but its lifetime changes are less bounded and lack as direct a public-path gap here. No new CI campaign is selected: the current public-pair optimization has completed its first hosted acceptance; another infrastructure campaign needs a newly identified bottleneck.

Short outlook, not authorization for subsequent campaigns:

1. Complete foreground artifact commands and publish them together with iteration.
2. Reassess one-command installation, explicit runtime selection and additive upgrades/rollback. A shared installation serving separate processes is the starting hypothesis; a daemon requires measured need. Keep artifact compatibility and recovery visible before automating updates.
3. Use actual foreground applications to choose between broader resource composition and authoring simplification. Promote a new abstraction only when a public workload exposes its missing rule.

Overturn selection only if startup shows the supported executable already supplies equivalent foreground behavior, or a reproduced correctness defect prevents safely establishing this boundary. A small source discrepancy permits a documented implementation correction. An unrelated larger redesign is not a silent substitute. The new trusted profile is a finite transition: foreground deployment execution gains it now; existing project differential execution and resident default policies remain explicitly identified compatibility boundaries. Generalizing those defaults requires a separately selected migration with proof, not indefinite implicit equivalence.

Keep existing `run TARGET [--arguments JSON]` and its project selection semantics. It remains the current pure differential authoring/checking route, with its existing bounded defaults and output contract. Do not route task targets into it or remove its reference evidence incidentally.

Add `run --deployment PATH [--arguments JSON]` as a mutually exclusive artifact execution form. Target selection comes only from the descriptor's exact artifact target. Do not consult cwd parents, Cargo, source assets, an implicit project, environment-based project selection or a package registry.

Accept the public **Command** runner with a closed pure or task function-backed port, including a zero-requirement task. Internal helper support for Batch/Test is not a mandate to expose those private runner contracts. Reject HTTP, interactive, worker, Batch and Test through this new form. A pure callable and an empty-row task remain distinct types. For both, preserve admission of the selected component's entire exact requirement closure; a pure port does not excuse grants required by its component.

Run the selected entry exactly once through the production evaluator. This holds for both pure and task ports in deployment mode. No live reference run, retry, check-time task replay, speculative execution or fallback re-invocation is permitted. `check`, graph tests and deterministic neutral adapters retain their independent reference proof. Report `execution-mode=production` and `verification=not-performed` (or equally explicit registered fields); never report differential equality from this path.

Arguments default to `[]` and use the existing strict bounded JSON-array codec, exact arity and exact closed parameter types. Return the existing typed JSON value encoding in a bounded command response. An encodable application-defined error variant is an ordinary returned value unless the language itself trapped; do not invent shell-exit semantics for particular variant names. ### 4.2 Preflight before effects

1. Parse options and bound descriptor/argument bytes.
2. Strictly decode descriptor and artifact; reconstruct exact root target, command port, closed types and requirement closure.
3. Validate route-specific descriptor shape, grant/interface mapping, argument arity and typed values, and the result type's eligibility for output encoding.
4. Only then read named secrets and construct/preflight adapters.
5. Admit one invocation, execute, encode its result, join owned work, close adapters, and emit success.

Result-type preflight must reject inherently unencodable results before any live adapter is constructed, including an unsupported type in an unselected variant branch. Reuse/factor actual codec rules, not an incomplete parallel predicate. Existing `require_application_encoding` is not by itself proof of every `to_json`/`from_json` case. Distinguish input and output eligibility and terminate over admissible recursive nominal types using their exact finite instantiation domain.

Late size/encoding failure can still occur for a valid result type and is a post-invocation failure. It cannot undo effects. Bound output staging using the existing output owner. Never manufacture a successful value when encoding, cleanup or writing fails.

Keep existing descriptor/artifact path confinement, symlink rejection, strict container admission and secret redaction. A rejected argument, foreign grant, wrong runner or unsupported output type must perform no application work and must not leave a created data root or opened adapter behind. Adapter-preflight failure must close any earlier created adapters under the existing cleanup protocol.

### 4.4 Lifecycle, visibility and cancellation

Use one invocation-owned resource scope and the existing checked deployment/capability machinery. Reuse or factor the common runtime lifecycle; do not copy a second VM driver, adapter factory or shutdown implementation. A foreground wrapper may own one task on the existing runtime without advertising a resident service or opening a listener.

The default foreground control has cancellation but no deadline. Explicit runtime policy supplies its deadline. Scope optional deadline support to this route so resident timeouts remain unchanged. Register supported termination handling before constructing live adapters; propagate cancellation through bounded preparation and clean any partial prepared owner. On the current Linux target, prove Ctrl-C/SIGINT and graceful SIGTERM cancellation. Resolve the invocation-completion/signal race deterministically: if both are already ready when choosing the outcome, prefer completed invocation; once cancellation has been selected, join and report cancellation without later changing to success. Dropping the invocation future alone is insufficient proof: retain the owning lifecycle and await shutdown/join after success, trap, resource failure or cancellation.

Preserve lexical transaction commit/rollback, outgoing effect-row checks, exact prepared origins, resource provenance, final consume semantics and evaluation order. Do not close invocation-owned resources at every tail transfer or refund quotas. Keep ancestor transactions alive across valid terminal calls and keep pending transaction continuations.

Before invocation starts, failures have no application effects. Once a task invocation starts, conservatively report that earlier effects may be visible unless the existing owner proves a narrower outcome. A later trap, cancellation, quota failure, result encoding failure, broken output stream or adapter shutdown failure must not be presented as whole-command rollback or safe automatic retry. A completed inner transaction remains committed if later nontransactional work fails. Never wrap the entire command in an implicit transaction.

Stage the final success response until invocation, encoding and shutdown have all succeeded, with no remaining owned tasks or cleanup failures. Include exact artifact/root/target identity, effective execution profile, typed result and bounded cleanup/production observations using the existing public contract registry. Avoid a misleading repository-cache record or fabricated reference fields. Errors use nonzero process status and the existing structured diagnostic classes, preserving possible visibility and cleanup notes. Preserve the primary execution error when also reporting cleanup failure. An OS-level forced kill is outside graceful cleanup proof.
