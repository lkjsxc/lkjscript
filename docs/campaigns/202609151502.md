## 2. Decision and scope

**Architectural thesis:** the lexical owner of a transaction must be able to observe its completed
publication decision as ordinary typed data, so reusable libraries can expose truthful update APIs
without host-specific logic or hidden transaction state.

Before: an imported typed-cell library returns UpdateAttempt<T>, containing a computed candidate
and its primary write's boolean. An effectful callback may already have failed another expectation;
the primary write can return true even though the whole transaction publishes nothing.

After: an ordinary generic library owns a lexical transaction and returns a typed result after its
finalization. Its caller can match successful completion, a failed condition or a commit-time
conflict, without knowing the library's internal operations. The mechanism also supports read-only
transactions and unrelated application-defined payload types.

This is not a correctness accusation against UpdateAttempt: its existing documentation is honest.
It is a demonstrated expressiveness limit. The source cause is concrete:

- src/platform/data.rs maps both expectation failure and successful no-mutation completion to
  DataCommitOutcome::Unchanged.
- src/platform/execution/normalized/data.rs maps Committed and Unchanged to unit, and converts
  Conflict into a retryable execution error.
- NormalizedCapabilityTransaction::commit returns Result<(), ExecutionError>.
- The VM's commit instruction discards completion information; the independent canonical evaluator
  commits and returns only the body value.

Expose a general semantic result at the lexical boundary. A global last-status getter, a flag on
the primary put, a required callback convention, or recognition of the typed-cell example would
leave the actual abstraction gap in place.

The strongest materially different alternative is first-class floating-point computation, absent
from the current language specification. It would unlock a wider numerical class of programs, but
the present investigation establishes neither its complete numerical contract nor its transition.
Transaction completion has a demonstrated failing composition and a bounded causal repair now.
Do not infer that numerical work is permanently lower priority. Another legitimate alternative is
release-cost reduction: the successful v0.1.36 rehearsal took 1h48m44s and the v0.1.35 publisher
3h00m23s from GitHub timestamps. Those are workflow elapsed times, not token/billing measurements.
Do not redesign or weaken a healthy active publisher during this campaign.

The contingent direction after this outcome is to evaluate useful ordinary libraries or numerical
work from fresh workloads. Retry is an application policy requiring idempotency and effect analysis;
typed Conflict alone does not justify an automatic retry framework. Reconsider this design if the
physical finalization boundary cannot truthfully distinguish definite rejection from uncertain
visibility, or if a simpler ordinary composition already provides the same completed observation.
Resolve that causal boundary first rather than returning a misleading result.

In scope: finalization classification, one additive expression, ordinary nominal outcome types,
complete authoring/checking/transport/compiler/runtime support, one transported generic library
workload, compatibility, maintained consumers/assets/specification, validation and integration.

Out of scope: savepoints, joining an existing transaction, distributed atomicity, automatic retry,
general exceptions, detached commit handles, new storage engines, retention/compaction, floating
point, new platforms, additional permanent demo applications and production deployment.

## 3. Resolved semantic and public contract

### 3.1 Proposed public capability

Implement an additive lexical form, provisionally named **transaction-outcome**, alongside existing
transaction. Provide both the public compact-record form and structural-block spelling through the
same typed intent and graph authority. These names describe **interfaces to implement**, not
commands or syntax claimed to exist today.

Use ordinary standard nominal declarations with this meaning:

    TransactionOutcome<T> = Committed(T) | Aborted(TransactionAbortReason)
    TransactionAbortReason = ConditionFailed | Conflict

The body has type T; the new expression has type TransactionOutcome<T>. Aborted carries no body
value. A successful candidate is therefore not accidentally exposed as an accepted value in the
abort branch. Applications that need candidate diagnostics can design their own separate data flow.

These are ordinary constructible data, not unforgeable receipts, execution permission or proof
tokens. The guarantee attaches to evaluation of this expression. Hand-constructing Committed does
not prove any effect happened.

Use existing parametric nominal types, variants and exhaustive matching. Do not add a universal
Result primitive, an exception subsystem or an application-specific intrinsic. Preserve existing
capture, affine and serialization rules: wrapping T grants no new ability to retain resources,
secrets, streams or intrinsically unencodable values. Do not impose a new capture-safe/durable
constraint on every T merely because it appears in the outcome.

Bind the exact ordinary outcome declaration and case identities in accepted meaning and its
dependency closure; derive and check T using existing substitution. Do not resolve meaning by
the spelling of a type/case, accept a shape-compatible foreign nominal as the recognized result,
or bind semantics to the currently installed standard revision. If explicit declaration references
are needed in authored input, expose them through existing exact named references and retain their
typed inventory. The type/result relation must be independently checkable before executing code.

### 3.2 Finalization table and ordering

Evaluate the body once in normal authored order. Perform no implicit retry. Keep the completed
value private until the exact transaction's finalization decision.

| Condition, in precedence order | New expression | Existing transaction form |
|---|---|---|
| Body trap, failed call, exhausted resource or cancellation before finalization | Propagate existing execution failure; no normal outcome; roll back staged work and perform existing cleanup | Preserve existing failure |
| Any conditional expectation failed in that transaction, including a callback's operation | Aborted(ConditionFailed); no staged change publishes | Preserve normal return of body T and suppressed publication |
| No failed expectation and no mutations | Committed(body); no new revision required | Preserve normal return of body T |
| Mutations exist, no failed expectation, exact base changed before commit | Aborted(Conflict); this transaction publishes nothing | Preserve the existing retryable execution error |
| Mutations are durably accepted through existing store completion | Committed(body) | Preserve normal return of body T |
| Storage/infrastructure failure, including possibly visible publication | Propagate the existing appropriately classified execution failure; never convert to Aborted | Preserve existing failure |

Condition failure wins over no-change and over a possible competing base update, matching the
current early-suppression behavior. Operations after the first false condition may still execute
and return local results; the whole transaction remains uncommittable. Do not add fail-fast body
behavior in this campaign.

A body-returned false, none, or an application-constructed variant remains ordinary data; it does
not itself abort the enclosing transaction. The wrapper reflects the transaction's actual
expectation state and finalization, not the shape or truthiness of T.

Successful no-mutation transactions retain their original snapshot and existing lack of latest-HEAD
revalidation. Committed means successful completion under these rules, not that a new revision was
written or that the snapshot was the latest at return. Update the overbroad data specification
description of unconditional base checking to state this existing distinction.

Conflict is deliberately a normal branch only for the new expression: the physical store already
classifies it as definite non-publication before visibility. This is useful ordinary data, not
catching arbitrary execution exceptions. The legacy form retains its published error behavior.

Pre-admit the outcome type/layout and necessary bounded wrapper capacity before physical
publication. Reuse the already checked body value; avoid a new fallible whole-payload copy or
recursive admission pass after commit. Preserve failure semantics when output or cleanup still
fails later. Receiving no result never proves that publication did not happen.

Keep cancellation checks before the existing bounded publication critical section; do not inject
cancellation between visibility steps. Preserve PossibleVisibility for data_head_visibility_unknown
and data_head_durability_unknown and equivalent current classifications. No infrastructure error
may be mislabeled ConditionFailed or Conflict. A successful result offers the store's actual
durability guarantee, not stronger storage-device or exactly-once claims.

### 3.3 Authority, nesting and composition

A concrete requirement or an in-scope requirement parameter admitting the DataStore transaction
operation may own the new form. Whole-requirement substitution, minimum-operation constraints,
exact grants, task allowance and callback effects retain current semantics. Calls and imported
helpers using the same resolved requirement participate in the owned transaction.

Actual VM/reference guards reject a second active transaction for the **same canonical
requirement**. Some current prose broadly says all nested transactions reject before publication;
that is not what the inspected runtime enforces. Preserve same-canonical rejection, including
aliased symbolic requirements and callback-mediated entry. Do not introduce savepoints, implicit
joining, or a new prohibition on independently granted stores. Reconcile any additional current
frontend restriction with a small source/test check before editing it; correct inaccurate prose.

Another store's transaction or an HTTP/Configuration effect has independent visibility. Aborting
the outer store does not undo an already completed other-store transaction or external effect.
Returning Conflict proves only this transaction's non-publication; it does not certify safe replay
of arbitrary callbacks. Do not enlarge grants or invent distributed rollback.

The transaction binding remains scoped runtime bookkeeping and cannot escape. Preserve ownership,
tail-call continuation, generation checks, cleanup and exact requirement accounting in both
evaluators. A forged or mismatched completion instruction must reject before exposing a fabricated
successful result.

### 3.4 Ordinary library and workflow

Adapt the existing literal typed-cell witness into a normal library with a public try-update-style
function and pure bound-updater factory. Its proposed semantic signature is:

    try-update<T; E; R>(space, default: T,
        transform: TaskFn(T)->T ! E, key)
        -> TransactionOutcome<T> ! ({R} union E)

R retains the existing exact DataStore and get/put/transaction constraints. The core function needs
no capture constraint; the factory retains capture-safe constraints only on actually captured
values. Typed encoding/default behavior, caller-owned schema/key policy and exact grants remain
unchanged. The library computes, encodes and conditionally writes inside transaction-outcome and
returns the finalization result directly. Callers match the ordinary variant.

Use I64 and Text, a callback through the transaction's own requirement, and a callback using a
separate admitted effect. At least one path invokes the imported function directly and another
uses the pure factory plus bound task invocation. Exercise a meaningful supplier body edit and
consumer dependency update. Reuse the current literal requests and public identity inspection;
do not create a second permanent application or new host implementation of cell logic.

Keep a small predecessor witness for old UpdateAttempt/transaction behavior. The original API
and original artifacts keep their meaning; the new public library result is an explicit API
change in the designed witness, not silent reinterpretation of an old nominal record.
