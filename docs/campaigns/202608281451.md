## 5. Decision classification

### 5.1 Mandates

- Graph 5 remains the sole editable program authority. Release and verification evidence is derived.
- The release must close one public HTTP workflow at the actual anonymous-download boundary.
- One first-party implementation owns HTTP acceptance. YAML and shell may orchestrate it but may not
  restate its semantic workflow.
- Executable-generated CLI and registry identities have one canonical owner. Release code, workflow,
  docs, and tests derive them from the source owner, exact candidate, manifest, or receipt.
- The publication job remains write-isolated and cannot execute repository code.
- Exact tag/release/assets are immutable. Recovery after an external commit is additive.
- Current documents cannot claim public state before anonymous postconditions pass.
- Required hosted service and public-boundary evidence cannot be downgraded to unavailable.

### 5.2 Selected design

#### A. Contract-owner contraction

Delete the release-local CLI contract literal. Compare candidate-reported CLI identity with the
canonical executable contract owner exposed by the `lkjscript` crate or its registry snapshot, and
record the candidate identity in the release manifest. Continue deriving the registry digest from
candidate capabilities. Do not introduce another generated file, workflow variable, or handwritten
constant for these values.

The release manifest schema need not change solely for this correction. Change a release schema only
when its serialized contract actually changes, and then update strict decoding, fixtures, and
historical/current documentation without rewriting old evidence.

#### B. Transferable distributed HTTP verifier

Refactor the existing `distributed_http` owner; do not create a second workflow implementation.
The command must support an explicit absolute evidence root suitable for a no-checkout job. In that
mode, absolute candidate and evidence paths are sufficient; no compile-time checkout path may be
resolved. Preserve a convenient checkout-relative default for contributor use only if it has one
clear owner and does not affect transferred mode.

Replace the receipt's campaign-specific identity with a stable schema/workflow identity and advance
that receipt contract when required. Bind at least:

- verifier executable path, byte length, and SHA-256;
- candidate executable path, byte length, mode/executability, and SHA-256;
- platform/process-control/client identity;
- private evidence root and isolated product root;
- every bounded command and resident runner observation;
- package, registry, CLI, project-creation, repository/package/revision/state, compilation, artifact,
  HTTP-response, restart, startup-failure, shutdown, and authority observations;
- result classification and cleanup; and
- the canonical receipt path, byte length, and digest in the one-line machine summary.

The evidence root is operational, not product input. Use create-new private paths, reject symlink or
non-directory surprises, constrain all returned paths to the owned root, and remove the temporary
product workspace after both success and failure. Large stdout/stderr remains in bounded files.

The contributor `distributed_http_application` gate, release precondition, and public release jobs
must call this same owner. Retain the existing command lifecycle test as a separate maintained
regression; it is not the public HTTP release oracle.

#### C. Separate transient verifier handoff

The read-only build job produces two logically separate transient handoffs:

1. the existing release handoff containing exactly the public archive, checksum, and private release
   receipt; and
2. one verifier handoff containing the exact release-built `lkjscript-dev` executable, or a
   one-member wrapper that preserves it without changing its bytes.

Bind the verifier handoff by file inventory, byte length, SHA-256, upload-artifact ID, and
upload-artifact digest. GitHub artifact transport does not preserve executable file mode by default;
package the file to preserve mode or verify its bytes before restoring the expected mode. Do not
assume mode survived transport.

The verifier handoff is a short-retention internal test artifact. It is never a public release asset,
never program authority, and never downloaded by the publication job.

#### D. Pre-publication no-checkout gate

Add a job between build/package and publication. It has read-only minimum permissions, no checkout,
no repository source, no publication token, and no external mutation. It downloads both transient
handoffs, validates their exact identities, runs first-party release verification, obtains a safely
verified extraction without duplicating archive semantics in shell, and runs the transferred HTTP
oracle against the packaged candidate.

Prefer extending the existing first-party release verifier with a create-new verified extraction
output when that avoids a second shell archive validator. Routine shell may check fixed filenames,
invoke first-party commands, compare small typed fields, and manage paths; it must not recreate
archive safety or HTTP product semantics.

The publish job depends on this gate. A dry run executes this job even though publication jobs are
skipped.

#### E. Anonymous exact/latest postcondition

Replace the command-only post-release shell smoke with the same transferred verifier. The read-only
post-release job:

1. anonymously downloads exact-tag and latest archive/checksum pairs with existing bounded
   propagation retries;
2. verifies checksums, release/asset digests, immutable/latest state, and attestations;
3. first-party verifies and safely extracts each archive into a separate private root;
4. runs the HTTP oracle independently against each executable with separate evidence roots;
5. checks each receipt against its own release manifest and expected tag/source identity;
6. compares exact/latest bytes and all deterministic identities; and
7. uploads bounded receipts/logs/manifests as retained verification evidence even when a later
   assertion fails, without exposing secrets.

The verifier step runs with a minimal environment that excludes `GH_TOKEN`, `GITHUB_TOKEN`, and
other credentials. Attestation API steps may use the ephemeral read token separately.

## 6. Target authority and failure boundaries

After completion:

- **Program meaning:** accepted Graph 5 remains the sole authority.
- **Executable contract identity:** the executable registry/source owner is canonical; candidate
  capabilities and generated docs are independently checked consumers.
- **Release source:** one exact tagged commit owns the released binary source.
- **Public distribution:** the immutable GitHub Release owns public asset availability; the archive,
  manifest, checksum, asset digests, and attestations are derived identity/integrity evidence.
- **HTTP acceptance:** the stable first-party distributed HTTP verifier is the sole product oracle
  used in contributor, pre-publication, and post-publication contexts.
- **Workflow orchestration:** YAML owns job order, permissions, artifact transfer, external API
  calls, bounded retries, and evidence retention, not product semantics.
- **Completion evidence:** the post-publication tracked evidence summarizes external identities and
  receipt digests; raw logs and transient artifacts remain derived and bounded.

No workflow artifact, release receipt, public archive, deployment descriptor, or runtime handle may
select or edit semantic meaning.

A failure before tag push cannot publish. A failure after tag push cannot move the tag. A failure
after immutable publication cannot alter that release. Product/verifier failure never advances
Graph authority. Documentation failure never turns an unproved release into current state.

## 9. External action and recovery protocol

### 9.1 Preconditions for tag push

All must hold simultaneously:

- R is clean, pushed, and exactly equals the intended remote source;
- its package version and intended strict patch tag agree;
- the tag and release do not already exist, unless following an exact recovery branch;
- no relevant workflow is queued or in progress;
- local full verification and hosted dry run bind R and are fresh passed;
- the transferred verifier gate passed without checkout or publication authority;
- immutable releases are enabled;
- the authenticated identity can set/read the confirmation variable safely;
- the exact annotated tag-object SHA is bound to that variable; and
- no later source commit or external state invalidates the candidate.

### 9.2 Failure before external tag push

Fix only the diagnosed source/workflow defect, create a new source commit, rerun affected narrow
checks, final full verification, normal push, and hosted dry run. The unused patch identity may
remain unchanged. A local unpushed tag may be deleted and recreated because it has not crossed the
external boundary; record that it was never pushed.

### 9.3 Tag externally exists, release not closed

Never move or delete the tag.

- If the tag selects the exact intended source and failure is limited to workflow orchestration or
  transient infrastructure, use the existing bounded, idempotent recovery path in
  `docs/release.md`. A manual `publish=true` dispatch is allowed only for that exact tag and only
  after proving it cannot clobber or create a contradictory release.
- If source content or the tag-built verifier must change, bump `main` to the smallest unused patch,
  prepare a new release source, and recover additively. Retain the failed tag as history.

### 9.4 Immutable release exists, public acceptance not closed

Classify the state as **externally committed but not closed**. Do not edit, delete, unpublish,
replace, or relabel the release or its assets.

- Bounded read-only retries may recheck propagation, download, digest, attestation, and behavior.
- An evidence-upload or workflow-log failure may be recovered by a read-only re-verification path or
  an exact idempotent workflow retry that performs no new mutation when the release already agrees.
- A content, source-built verifier, or product defect requires the next additive patch release.
- Campaign completion may name the successful additive patch rather than `v0.1.7`, but it must
  record every externally committed predecessor and why it did not satisfy R4-R5.

Do not use an unbounded retry loop. Retain existing bounded propagation policy unless current
GitHub behavior provides concrete evidence for a smaller correction.

### 9.5 Old drafts and releases

The old empty drafts and every published predecessor are historical external state. They are not
cleanup targets for this campaign. Exact-tag lookup and bounded listing must tolerate them without
selection ambiguity. Any unexpected conflicting draft for the intended new tag is an empirical
state to reconcile; do not delete it reflexively.
