## 2. Outcome, thesis and trajectory

**Before:** newly created owners have convenient request-local symbols, and local modules/declarations already have some name selectors. Existing foreign declarations and existing fields, cases, operations, requirements, ports and parameters still require exact identity plumbing in important positions. The public workload builder `foreground_program::consumer` receives separate host `BTreeMap<String, String>` inventories for standard and library identities. Merely saying “add local symbols” would duplicate an existing capability.

**After:** a person or agent can write one readable compact request that selects an exact library once, binds its named declarations/members and existing local owners, reviews their exact resolutions, and applies ordinary typed edits. The product performs resolution, kind checking and commitment. A companion Rust/Python identity-map generator is unnecessary for the accepted workflow. Existing exact references remain useful.

The architectural thesis is that **names are a reviewed addressing layer over exact accepted meaning**. Selection belongs in the existing authored-request/preparation path. Neither request files nor a name index become another editable program authority. This campaign changes authoring access, not expression evaluation, ownership semantics, deployment authority or the meaning graph's representation.

Why now: effects, generic nominal data, task iteration, foreground artifacts and runtime installation already support substantial composition. The inspected acceptance programs still bridge public authoring with bespoke identity maps. Removing that concrete bridge makes those investments accessible without another broad runtime transition. This is a source-observed burden, not measured model-token or elapsed-time savings.

The strongest alternative is requirement-parametric libraries followed by a coherent resource-call protocol. Present affine guards repeat the one-final-consume/private/same-package/acyclic subset across semantic, compiler and runtime boundaries. Removing one guard would not solve concrete requirement ownership. A proper next semantic stage could add explicit operation-bearing requirement parameters distinct from effect rows, then generalize lexical resource transfer. That requires its own complete authority and lifetime contract; it is not folded into this campaign.

A revisable outlook:

1. Complete typed named bindings and observe an actual public author/edit/recovery cycle.
2. If direct capability policy still must be duplicated between packages/components, select explicit requirement parameters with exact interface/operation constraints and a transported public witness. If the remaining dominant burden is expression assembly instead, consider a structural request-block adapter over the same authored intent.
3. Broader resource signatures or numerical computation follow a concrete workload and settled semantics. F64 is genuinely absent but scalar support alone would not establish useful model-training throughput.

This outlook authorizes only the present campaign. No task-specific language primitive, SNS/game/LLM application, new daemon, registry, automatic updater, platform matrix, or compiler self-hosting work is selected.

**Overturn rule:** if startup shows the complete named-binding behavior already works through the public binary, verify it and close the matching obligation instead of adding duplicate syntax. If inspection shows the existing public path already eliminates the claimed identity-map work, reproduce that workflow and document the mistaken premise; do not ship a redundant feature. An isolated missing namespace exposure must be reported precisely, not used to substitute a whole textual language or requirement-polymorphism campaign.

## 3. Settled public surface

Add these **proposed**, currently unimplemented records to the existing compact change grammar. Uppercase metavariables describe grammar, not commands the architect executed.

```text
reference.package as=$ALIAS source=builtin
reference.package as=$ALIAS package=PACKAGE_ID package-revision=EXACT_PACKAGE_REVISION
reference.owner as=$ALIAS package=local|$PACKAGE_ALIAS class=CLASS name=NAME [parent=$OWNER_ALIAS]
reference.owner as=$ALIAS package=$PACKAGE_ALIAS class=declaration owner=DECLARATION_ID
```

The two package forms are mutually exclusive. Unknown/extra fields reject through the existing diagnostic owner. Names obey existing portable-name and compact quoting rules.

The exact declaration-alias form is an explicit escape hatch for ambiguous exported names. It is mutually exclusive with name/parent and still validates the selected dependency interface, visibility and declaration kind. It does not expose a hidden declaration.

Expand the built-in shorthand to the candidate's immutable embedded package/semantic/logical revision identity during normalization, before request commitment, without reading a project. Do not encode an unbound "whatever is builtin later" selector. Repository preparation then checks that exact tuple against the explicitly selected dependency closure.

The package records are addressing declarations, not dependency operations. The explicit form identifies one exact package/logical revision already accepted, or explicitly added/replaced by normal dependency operations in this request after its transport has been staged. The built-in form identifies this candidate executable's exact embedded supplier; it never means “latest.” It must agree with the dependency selected for this request. It does not export, stage, add, upgrade, fetch, execute or grant anything.

`reference.owner` has the following namespace rules:

| CLASS | Required parent | Coverage |
| --- | --- | --- |
| `module` | Absent; local package root | Existing local modules only. |
| `declaration` | Local: module alias. Dependency: absent, exact interface root. | Local declarations or uniquely named exported dependency declarations; use-site validation still checks function/type/interface/component subtype. |
| `type-parameter`, `effect-parameter` | Their declaring owner alias | Exact named parameter; scope and complete application checks remain mandatory. |
| `field`, `case` | Record or variant declaration alias respectively | Exact member; no structural-field/name equivalence is introduced. |
| `operation` | Interface declaration alias | Exact admitted operation identity. |
| `parameter` | Function/external declaration or operation alias | Exact parameter owned by that parent; use-site kind/scope distinguishes operation and function parameters. |
| `requirement`, `port` | Component declaration alias | Exact component member, under existing visibility and reference rules. |
| `target` | Absent; local package root | Existing local target only; no dependency target import or execution. |

For dependencies, only the namespaces/children already exposed and legally referenceable through the current exact package interface are eligible. Do not widen private exports, package visibility or an artifact closure merely to make a name resolve. If a class is not exposed externally, reject that foreign binding with an exact explanation; full local coverage is still required. Expressions, lexical bindings, match payload bindings, HTTP routes, annotations and documentation are outside this named namespace feature. They retain existing structural/exact access. A name is not a lexical-scope inference mechanism.

The inspected `PackageInterfaceSelection::contains` excludes modules, and `PackageInterfaceDeclaration` retains header/name/payload without a module name or ID. Therefore dependency declarations match a unique exported name in that exact interface, not MODULE/NAME. If two exported declarations share a name, reject ambiguity and use the exact declaration-alias form for that parent; its fields/cases/operations can still be bound by names. Do not add module metadata or change the interface format for this campaign.

Reference aliases and creation symbols share the existing `$` namespace for collision detection but carry distinct typed internal values. Bindings may appear before or after uses. Package/parent dependencies form a finite DAG; reject cycles, wrong parent classes, aliases of the wrong kind, duplicate definitions, and collisions with new-owner/expression symbols. Multiple distinct aliases may denote the same existing owner; this must not allocate, duplicate or mutate it.

A parent must belong to the same exact package selection as its child. A same-spelled package alias or owner from another revision cannot supply a parent. Alias-like text inside a string, literal name or documentation remains literal; expansion operates only on typed reference fields.

All declared aliases must be well formed and resolve, including unused declarations. Unused valid bindings are allowed so a small reusable addressing prelude need not be trimmed for every edit. Canonicalize the set of declared typed selectors without alias spelling/order; duplicate equivalent selectors may share one resolution. The normalized request and reviewed resolution inventory must consistently bind that set. Binding-only input does not invent a semantic mutation; preserve the current requirement for an actual authored change.

Names match exactly under the canonical namespace and exact parent. Never use fuzzy matching, global fallback, wildcard import, first-match selection, filesystem search or a mutable global symbol table. Missing/ambiguous/retired/wrong-kind selections fail before publication. Diagnostics identify source location/alias, class/name, parent and exact package revision without dumping unbounded interfaces.

### Use in existing records

A resolved alias is legal everywhere the corresponding existing typed reference or local selector is legal: declarations, type applications, calls/function values, fields/cases, operations, requirements/effect rows, parameters, ports, and eligible existing-owner mutation selectors. Foreign aliases never become local mutation selectors. Selecting another function's parameter cannot make it a valid local read. Existing ownership, visibility, effect, affinity and full-candidate checks remain authoritative.

For example, a library designed for acceptance may contain local module `cells`, public record `cell<T>`, field `value` and function `wrap<T>`. Its consumer binds `cell` and `wrap` directly beneath one exact package interface, then `value` beneath `cell`, constructs/projects `cell<I64>`, and calls `wrap` using the existing ordered type/expression fragments. These are intentionally designed witness names, not claimed names in the current standard. Discover actual standard exported declaration/member names through the candidate's public package interface. Only the producer uses its local `cells` module name.

Keep the existing flat expression and type grammar. Bindings do not solve request-wide expression-symbol collisions, implicit capture, multiline expression syntax or type inference; do not claim otherwise.

## 4. Resolution, identity and failure contract

### One base and one explicitly selected dependency closure

Resolve all existing **local** names against the exact accepted base, before same-request rename/create/delete effects. An alias selecting old name `count` still denotes that original owner when the request renames it. New owners remain referenced through their creation symbols; parent aliases cannot search a hypothetical newly created namespace.

For dependencies, derive the candidate's explicit dependency selection from the base and normal add/replace/delete operations. A package binding must name that exact selected revision. With replacement, resolve against the explicitly selected replacement interface, regardless of record order; never fall back to the old revision because it contains a convenient name. Reject duplicate/inconsistent dependency edits, deleted selections, unstaged closure or revision/interface mismatch through the existing owners. Existing exact dependency IDs/revisions remain the small explicit trust anchors.

Neither alias resolution nor plan generation may create a grant, load secrets, open adapters, run a program, access the network or mutate operational/application data.

### Preserve commitment and allocation ownership

The inspected sequence matters: `decode_compact_change` and `normalize_change_request` compute a request commitment before repository preparation; `lower_authored_changes` later checks the base, encodes authored intent and derives `allocation_seed`. Existing local MODULE/NAME selectors are encoded as selectors rather than magically equivalent exact IDs.

Implement typed binding expansion before creator-symbol collection and normalized intent encoding. Use interned/memoized typed selector paths; do not rewrite user strings or recursively duplicate alias trees. Keep existing creator ordering and stable allocation intact. A selected owner must never enter the new-identity allocation inventory.

Required invariants:

- Renaming only reference aliases, or reordering only reference-binding records, yields identical normalized request intent, request/plan commitments and fresh-owner allocation for the same edits/base/package inputs.
- Aliases lower to typed selectors and a canonical selector inventory independent of alias spelling/order. Do not require a named request and an exact-ID request to mint identical fresh owners: their established intent encodings can differ.
- Old requests without new bindings retain their canonical bytes, request commitment, allocation, logical meaning and accepted-idempotency behavior. Capture baseline golden cases before modifying the codec.
- The prepared logical plan contains the complete exact resolution inventory: selected typed path/class, owner kind/identity, parent or explicit package-root, package, semantic/logical package revision and interface binding where applicable. Bind it through the existing prepared commitment and package-before/after inventory. Human alias labels are presentation, never an independent trusted resolution table.
- Apply reprepares against the same exact base/dependency inputs, validates the plan commitment, and rechecks publication state under the existing lock. It never trusts a cached resolver table or a user's claimed resolved ID.
- A same-name dependency replacement does not establish identity continuity. Report actual preserved/changed IDs and rely on existing complete candidate validation.

Use an additive authored-intent representation for new selectors, preserving the legacy encoding/domain for requests that do not use them. New syntax may evolve the actual public capabilities/selector contract, not every layer's version. Do not bump Graph, artifact, bytecode, package-interface or data encodings for request-only addressing. If existing commitment architecture truly prevents legacy preservation, stop before silently changing retries: document the smallest token/intent boundary requiring a transition, preserve accepted-idempotency records, add explicit rejection and re-plan recovery, and justify the correction in the execution record.

### Built-in supplier changes and retries

A reviewed `source=builtin` selection must be bound to the exact embedded supplier inventory. Applying the same text with a different executable may only proceed when that reviewed supplier and all other inputs still match; otherwise fail with an exact supplier mismatch and explicit re-plan/exact-package recovery. Never silently import the new executable's supplier.

For accepted idempotent retries, use the existing historical-base/accepted-receipt owner. Recover the original exact inputs when that owner genuinely retains them; otherwise issue a classified recoverable mismatch without executing another change. An invalid new request must never inherit a success receipt merely because an idempotency key matches.

### Bounded work and recovery

Charge raw records/input bytes before normalization, then selector nodes, namespace reads and allocation through existing authored/preparation budgets. Canonicalization cannot erase its own admission cost. Repeated aliases/uses of one path share checked resolution within one preparation; do not scan the entire repository per reference. No persistent resolver cache is necessary.

Cancellation, exhaustion, missing/corrupt dependency material, ambiguity and invalid references leave accepted HEAD/owners unchanged. A derived catalog repair retains its existing separate recovery semantics. Owned temporary output must be cleaned up. Failure after an already accepted write follows the current publication/idempotency contract; do not misreport it as rollback or safe retry.
