## 3. Primary objective

Make the distributed `lkjscript` executable sufficient to author and run one persistent,
request-dependent BBS through the supported public boundary.

Starting from `new --template http`, a copied candidate executable outside the checkout must be able
to:

1. discover the exact compact change grammar, current public built-in declarations and capability
   operations, and deployment adapter schema without artifact string scanning or repository source;
2. author task/capability semantics through reviewed compact `change plan` and `change apply`;
3. inspect HTTP method, path, query parameters, headers, and streamed body through generic typed
   expressions rather than HTTP-specific Rust shortcuts;
4. create a graph-owned domain model, request routing, validation, response policy, and persistent
   post operations;
5. check and build a deterministic Artifact 10 bundle;
6. serve the artifact through one `lkjscript` process connected directly to an isolated PostgreSQL
   instance; and
7. pass real HTTP create, read, update, delete, malformed-input, unknown-route, shutdown, and restart
   checks while accepted graph authority remains unchanged during execution.

The final supported data path is:

```text
HTTP client -> lkjscript HTTP adapter -> graph-owned handler and domain policy
            -> exact data capability -> PostgreSQL adapter
```

There must be no second application HTTP server, shell storage protocol, JSON-file database, source
checkout dependency, hidden graph builder, or test-only semantic mutation path.

This campaign uses PostgreSQL as the already implemented data adapter and independent operational
oracle. It must **not** make SQL or PostgreSQL language semantics. Graph meaning must isolate the
BBS domain and HTTP policy from provider-specific statements behind a narrow application-owned
persistence boundary. That seam and the measured workload are deliberate preparation for a later
first-party database and SQL-removal campaign; implementing that database now is out of scope.

### S3 — Request-dependent HTTP behavior

The BBS handler must derive behavior from the canonical request value using generic semantic forms:

- route on exact method and path;
- read query parameters from the canonical typed query map;
- inspect headers when required by request admission;
- consume the request body only through the admitted byte-stream requirement and a declared byte
  bound;
- return the canonical response record with application-selected status, headers, and body.

The proving application must implement at least:

| Request | Required application result |
|---|---|
| `GET /` | `200`, HTML bytes, explicit HTML content type |
| `GET /api/posts` | `200`, canonical JSON list, explicit JSON content type |
| `POST /api/posts` with valid strict JSON | create one post transactionally and return `201` with the created JSON value |
| `PUT /api/posts?id=ID` with valid strict JSON | update the selected post and return `200`, or `404` when absent |
| `DELETE /api/posts?id=ID` | delete the selected post and return `204`, or `404` when absent |
| malformed/trailing/duplicate-field request JSON | `400` without database mutation |
| missing or malformed required query identity | `400` without database mutation |
| known path with unsupported method | `405` |
| unknown path | `404` |

Application status and headers are graph values, not host-side route tables. Transport-owned headers
remain rejected by the existing HTTP boundary. Request-body transport exhaustion remains a
transport response such as `413` according to the current normative contract and is not reimplemented
as application policy.

### S4 — Persistent BBS meaning and replaceable data boundary

The semantic graph, created only through the public reviewed change path, must contain a small but
real application model:

- a nominal post value with stable application identity, author, body, and application-observed
  creation/update time or an equivalently provider-neutral ordering field;
- strict typed request values for create/update operations;
- pure domain validation and response construction that can be graph-tested independently;
- task persistence operations behind one application-owned boundary;
- source-origin `StaticText` migration and parameterized statements confined to the persistence
  implementation;
- a migration identity and checksum owned by graph meaning;
- exact typed conversion between data-adapter rows/values and domain post values;
- deterministic list ordering.

Prefer generic identifier and wall-clock requirements over database-generated identity/time when the
current standard interface supports them without unrelated work. Database schema, statements,
authorization policy, and row conversion remain application meaning. Connection coordinates,
pool size, timeouts, secret bindings, and adapter choice remain deployment authority.

HTTP/domain functions must not expose PostgreSQL connection strings, driver objects, physical table
locations, or Rust adapter types. Keep the provider-specific statement layer narrow enough that a
future native store can replace it without rewriting route, JSON, status, validation, or domain
meaning.

PostgreSQL migration, create, update, and delete work must be transactionally correct. A failed
body or statement rolls back. A possible-visibility commit failure is not blindly retried. The
application maps expected absence/conflict/input outcomes to its public HTTP result; infrastructure
or capability failures remain safe bounded failures without secret leakage.

The active checkout may reveal that one small generic standard declaration is missing. Add one only
when exact built-in interface inspection proves the BBS cannot be expressed with the current
standard package. It must be generic, semantically validated, implemented in production and
reference tiers when pure, documented/discovered, graph-tested, and adopted by maintained
consumers. Do not add BBS-specific intrinsics or Rust route/storage helpers.

## 7. Target boundaries

### 7.1 Semantic and operational authority

After apply, the accepted graph owns:

```text
HTTP/domain types and functions
routing and status/header/body policy
strict request-value interpretation
post identity and validation
persistence operation signatures
migration identity/checksum
parameterized SQL statements and row conversion
component requirement/effect closure
graph-owned pure tests
```

The deployment descriptor separately owns:

```text
artifact path and target
loopback listener
runtime/HTTP/stream limits
requirement aliases and sharing domains
adapter kinds
PostgreSQL connection secret name
pool/wait/statement limits
non-secret configuration and environment secret bindings
```

The PostgreSQL instance owns operational rows and transaction visibility. It is not program meaning.
The artifact, compiler cache, dense runtime indexes, readiness events, receipts, and test evidence are
derived or operational.

### 7.2 Dependency direction

Use this logical direction even if local module names differ:

```text
HTTP handler -> pure route/request/domain helpers -> typed persistence functions
                                                -> explicit capabilities
host adapter  -> normalized capability contract -> PostgreSQL
```

HTTP and domain code must not depend on PostgreSQL driver types or deployment JSON. Persistence code
may depend on exact standard database types and operations, but provider-specific statements must
not leak into the public domain types returned to HTTP code.

### 7.3 Lifetime and failure ownership

- Request streams are owned by the HTTP request/task and close on completion, error, cancellation,
  or shutdown.
- Transaction bindings cannot escape lexical scope. Success commits; task error rolls back;
  possible visibility is preserved as a distinct failure.
- Database connections remain adapter-owned and bounded by pool/deadline policy.
- Response values are completely validated before transport publication.
- Semantic apply publishes one exact accepted revision or none.
- Runtime execution never opens or advances the project repository.
- The acceptance harness owns all temporary processes and storage and must perform bounded cleanup
  even after failure.
