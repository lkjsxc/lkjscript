## 1. Assignment and strategic choice

Execute this mandate. Implement, prove, integrate, and, when its conditions are satisfied, distribute **finite-instantiation recursive nominal data**. A user of one copied lkjscript executable must be able to author a reusable generic tree library, transport its complete source package, instantiate it in an independent consumer, execute graph-owned recursive algorithms, and use eligible concrete recursive values through JSON, typed persistence, pure retained environments, and structured sessions. No language-source checkout or new application-specific host primitive may be required by that user.

The externally meaningful change is from “generic record/variant definition cycles and concrete application cycles reject” to “recursive definitions with a finite admitted instantiation graph work; structurally expanding parameter cycles reject with an actionable witness.” This is not permission to remove cycle guards indiscriminately. Type recursion, finite runtime values, executable recursion, and resource limits remain distinct.

This choice compounds the recently delivered parametric nominal foundation. One generic definition can represent syntax trees, nested documents, expression structures, or hierarchical domain data without per-element-type copies or a convention that reconstructs the shape from lists and integer indexes. These are enabled use cases, not claims of existing adoption. The required new tree library is the executable witness; it is not the user's standalone game or relay, and those projects are not to be imported.

The strongest alternatives were:

* Generic task/effect or wider affine-resource abstraction would remove another genuine restriction, but requires decisions about requirement binding, higher-order effects, transfer, and cleanup beyond this data milestone. It remains a strong subsequent candidate.
* Optional trusted-execution metering would align a real user preference, but is a separate execution-policy contract. It neither supplies recursive data nor justifies an incidental change to today's limits.
* Further compilation or allocation optimization needs a measured limiting workload. Existing persistent lists, checked values, and pure tail execution already supply useful foundations; a fashionable backend is not a bottleneck measurement.
* Another release-only campaign is not selected: the preceding milestone is already publicly accepted. This campaign earns its release by adding a coherent new public capability, not by reopening that delivery.

The cost here is primarily bounded type-closure analysis and the correctness of its composition with existing property, loading, and value boundaries. There is already an explicit nominal-reference representation, disposable instance preparation, and recursive-layout encoding. A second recursive-type syntax, monomorphized program authority, or general heap-cycle facility is unnecessary.

## 3. Fixed semantic contract

### 3.1 Canonical meaning and values

Keep ordered explicit type parameters, exact scope and bounds, nominal declaration/member identities, complete explicit applications, constructor arguments, exhaustive matching, and invariant exact type equality. `tree<I64>` and `tree<Text>` remain distinct even when a selected case contains no payload. Renaming a declaration or parameter does not replace its stable identity. There is no equirecursive structural type equality, implicit fold/unfold operation, subtyping, higher kind, implicit argument inference, or new generic-function recursion rule.

Recursion is a cycle through nominal declaration references and substituted member types. Canonical TypeObjects remain finite structural terms. Derived layouts may form a finite graph. Runtime values are finite immutable values constructed through current operations; this campaign does not introduce cyclic heap objects, lazy infinite values, recursive mutable cells, or user-controlled pointers.

A declaration without a finite inhabitant need not be rejected merely for uninhabitance. For example, an ordinary record containing only another instance of itself has no finite constructor result, but that is not an excuse for the type validator or preparer to loop. Executable nontermination remains subject to its existing execution policy. Existing monomorphic recursive behavior must not be narrowed accidentally.

### 3.2 Finite-instantiation admission

Use a **non-expansive parameter-flow criterion**, not a whitelist of tree shapes and not “try expanding until the budget ends.” Its definition is part of this campaign's public semantic boundary:

1. Resolve the relevant nominal declaration closure against the exact candidate and exact package interfaces, including nested nominal references in fields, cases, structural composites, application arguments, and function signatures. All members and arguments count, including phantom arguments, inactive cases, and empty-container element types. Package dependency rules are unchanged.
2. A parameter slot is the exact pair of nominal declaration identity and its ordered stable type-parameter identity. For every application of declaration B encountered syntactically in a member type of declaration A, inspect each ordered argument of B for occurrences of A's parameters.
3. Add an edge from slot A.i to slot B.j for each such occurrence. Mark it **plain** when that argument is exactly A.i; mark it **expanding** when the occurrence is below any structural type constructor in that argument, including a nominal application. Inspect nested applications as applications in their own right as well. A closed argument contributes no source-parameter edge. Do not treat the outer field/list/case that contains the application as parameter growth: `List<tree<T>>` forwards T plainly to tree's slot.
4. A schema is admissible under this criterion exactly when no strongly connected component of this slot graph contains an expanding edge. Every cycle then forwards/permutates/duplicates parameters without increasing their structural nesting; growth on an acyclic path and replacement by closed arguments are allowed. Scope, arity, constraints, ordinary containment, and other existing checks still apply independently.
5. After admission, derive the actual closed type/layout graph with a worklist keyed by **complete canonical applications**, not declaration alone. Reaching an already admitted exact instance adds an edge rather than unfolding it indefinitely. A finite but large closure can still exhaust a separately identified work/storage limit. Exhaustion is not evidence that a definition has an expanding cycle.

Implement bounded, cancellation-aware graph collection and SCC analysis, retaining an owner/member/argument-path provenance for each edge. An expanding-cycle diagnostic must identify a bounded cycle witness with at least one expanding edge and distinguish it from missing types, bad scope, foreign owners, unsupported effects, and resource exhaustion. Names are helpful presentation, not proof identities. Public diagnostics and generated guides must stop saying that every generic cycle is unsupported.

The justification to document and test is that, in the current first-order finite type terms, a positive edge on a slot cycle can grow a parameter occurrence on every lap. Without such a cycle, positive edges occur only along the finite acyclic condensation graph; zero-growth cycles select among finitely many forwarded terms. This establishes a finite set of instantiated terms for finite roots, subject to ordinary resource limits. It does not promise a small closure or linear total instantiation size: duplication, permutations, and many roots may still be expensive.

Implement an independent small-term reference for this criterion and the resulting closure, rather than making both proofs call one new production SCC helper. The reference can use direct term substitution/enumeration for admitted small schemas and independently checked expanding-cycle certificates for rejected ones. A finite prefix of an enumeration is not proof of divergence. If a genuine counterexample to the proposed analysis appears, correct the analysis and its explanation while preserving the required admitted/rejected cases and bounded finite-instantiation outcome; do not ship a known-unsound rule or quietly revert to rejecting every cycle.

Illustrative type notation below is explanatory, not a new source grammar:

| Definition pattern | Required result |
| --- | --- |
| `tree<T> = leaf(T) or branch(List<tree<T>>)` | Admit; the list contains the recursive value, not a larger next T. |
| `node<T> = { value:T, children:List<node<T>> }` | Admit a directly recursive record. |
| `expr<T> = atom(T) or group(group<T>)`; `group<T> = { items:List<expr<T>> }` | Admit mutual record/variant recursion. |
| `flip<A,B> = stop or next(flip<B,A>)` | Admit its finite permutation of type instances. |
| A forwards `(T,T)` to B, and B returns one unwrapped parameter to A | Admit finite duplication/selection. |
| `A<T>` contains `B<List<T>,I64>`; `B<U,V>` contains `A<V>` | Admit: growth in the dropped U path is not on a slot cycle; the recursive path resets to a closed type. |
| `grow<T> = stop or next(grow<List<T>>)` | Reject with an expanding self-cycle, even if only stop is used. |
| `A<T>` contains `B<T>`; `B<U>` contains `A<List<U>>` | Reject the expanding mutual cycle. |
| Expansion hidden under a function signature, nominal argument, phantom slot, or wrapper | Apply the same analysis; property-specific function-leaf rules cannot hide expansion. |
| A zero-arity wrapper returns to a fixed `A<I64>` | Do not reject merely because a declaration cycle contains a generic declaration; the concrete closure can be finite. |

Admitting a type such as flip does **not** newly authorize polymorphically recursive generic function calls. Existing function-cycle checks remain. Prove the type through concrete instantiations and one-step operations where an existing generic-function restriction would otherwise apply.

The bounded subset excludes expanding recursive type schemes because the implementation prepares a finite instance closure. Reconsider this limit only alongside a concrete lazy/symbolic representation, property decision procedure, and measured workload that need it. Do not copy this campaign-local frontier into root guidance as a permanent definition of the language.

### 3.3 Properties, preparation, and raw admission

Distinguish three different traversals: syntactic dependencies for finite-instantiation analysis; the concrete instance graph; and each property's permitted child relation. The first follows function signatures. Capture-safety and ordinary-value predicates retain their established function-leaf behavior. Confusing these relations can either reject useful types or admit unsafe values.

For ordinary containment, capture safety, equality, JSON, typed-data eligibility, and session retention, compute cycle-safe facts over the relevant exact graph. These are separate predicates, not one “safe type” bit. For conjunction-style safety properties, a worklist propagation of disqualifying leaves or an equivalent greatest-fixed-point calculation is suitable. Marking an active node visited is not permission to omit its other arguments or members. A forbidden leaf elsewhere in its component must invalidate every dependent root. Checks on a parameter's explicit bound must occur in the correct declaration scope before a recurrence assumption can discharge further traversal.

Preserve current distinctions: resources and streams do not become ordinary through recursion; secrets do not become capture-safe or durable; a pure callable-containing application may be transient and capture-safe without being comparable, serializable, or session-retainable. Existing Option/Result codec exclusions and supported map key rules remain. Check phantom arguments, absent variant cases, empty lists, and hidden dependency members. Recursive ordinary data must not become an affine-resource container by accident.

Production and reference preparation must each derive complete finite closures from all relevant roots: concrete signatures, constants, tests, component ports, constructors, explicit calls and named function instantiations, and substituted members. Production may use its compiled units; reference preparation must retain its canonical-owner derivation and not import production instance tables or classification results. Allocate each exact instance once into a private, fully validated preparation and expose it only after its references and properties are resolved. No half-prepared layout escapes after failure or cancellation.

Instance identity includes full arguments and prepared-program provenance. Raw ingress must still validate actual payloads before downstream execution. A cyclic *type* edge does not allow skipping recursively nested *values*. Distinct values using the same type must all receive the required shape, depth, item, allocation, and origin checks. Internally admitted immutable values may retain and share their proof without rewalking complete descendants on every local move or projection.
