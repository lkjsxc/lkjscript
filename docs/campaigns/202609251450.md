## Selected direction

Reduce the concrete setup friction between the native UI witness and a user's
first editable browser application. Add `new --template web` using ordinary
native declarations and the existing atomic project-creation boundary. The
starter should need only create, check, build and serve, with no downloaded
library sources, manual dependency identities, external generator or second
application runtime.

Reuse the maintained literal UI implementation and its tests as editable local
modules in the new project, not a new privileged renderer or hidden framework.
This is explicit vendoring at creation: existing projects do not update silently,
and independently imported exact UI packages retain their own authority. Do not
invent a package registry or pretend a local module is a separately pinned
supplier. The application page and controls are ordinary lkjscript; only the
shared renderer owns HTML/CSS. No browser script is selected.

Generalize only the existing private recipe lowering to accept embedded native
requests through the same decoder, preparation, full validation, logical plan
and publication owners as public changes. All intermediate revisions stay in the
owned private staging repository; expose one complete initial project or nothing.
Keep the existing recipes' semantics and identity-independent projections intact.

Use a small stateless GET application with named input and light/dark choices.
Keep the generated deployment loopback-only and explicit. Query input is not
secret storage, authentication or authorization. Persistence, POST and account
management remain separate application policies, already illustrated elsewhere.
