# v0.1.70: closed generic joined tasks

This successor removes the need for a monomorphic wrapper solely to use a generic
library task as a `parallel` child. Source acceptance, mainline integration and
public binary publication remain separate; [status](../status.md) records them.

Children can use `call` with concrete type arguments or `implementation-call` with
concrete type and implementation arguments. Ordinary generic data and closed Owned
carriers are supported. Exact witness references survive internal forwarding; two
implementations for the same Self type are not interchangeable. Both ordinary and
owned child results keep the existing record or owned-product join shape.

Argument and result custody bind the exact prepared task application, concrete
types and invocation identities. Payload storage is moved without cloning owners.
Closed signature metadata is admitted and charged before allocation. Children
retain one invocation-wide quota and joined cleanup on cancellation or failure.
The independent reference evaluator reconstructs applications from canonical source,
not from the production evaluator's selected instance or inferred result table.

Open caller type and implementation parameters, effect/requirement parameters,
loans, capabilities, secrets and dynamic callables remain outside the child
boundary. This adds no detached tasks, channels, asynchronous borrowing or promised
speedup. Existing monomorphic tasks and concrete wrappers remain valid.

Semantic validator 26 changes admission; compiler 21, bytecode 17 and artifact 28
encode the exact child application. Graph 21 and authored request 25 retain their
representation. Previous derived compiler units are refused before instruction
decoding and require rebuilding from retained accepted meaning. Exact dependencies,
application data, previous releases and running services are not migrated.
All product-version components remain opaque identifiers.

The existing final-archive `native_parallel` harness family includes the new generic
three-package scenario. A source-only test or development-host executable does not
establish acceptance of the distributed executable's final bytes.
