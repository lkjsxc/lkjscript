# v0.1.71: reusable generic parallel groups

Generic task libraries can form joined parallel groups using their own explicitly
transferable type parameters and exact implementation parameters. Callers can
select ordinary data, owned buffers/cells, products and choices without writing a
concrete wrapper for every group. Two implementations with the same Self retain
their exact nominal selection.

Native function parameters add `(constraint transferable)`,
`(constraint capture-safe transferable)` and `(constraint owned transferable)`.
Ownership, capture safety and transfer permission remain separate. Generic bodies
are checked before instantiation; every nominal actual, phantom argument and
inactive case participates in transfer admission. Ordinary metadata in owned
products and choices can contain scoped ordinary transferable parameters.

Both mixed result-pair orientations, owned results and nested groups compose under
the existing sealed custody. Child operands and intermediate pair types become
concrete before execution. Transfers retain owned payload allocations and exact
invocation identities; cancellation, quota refusal and sibling failure join every
started child and release abandoned owners.

Graph 22, authored request 26 for transfer-bearing requests, package interface 13,
compiler 22, artifact 29 and semantic validator 27 carry the new permission.
Bytecode 17 and existing type envelopes retain their layouts. Earlier derived
artifacts require rebuilding from supported accepted meaning. Existing constraint
tags and requests without the new bounds retain their original meaning. Product
version components remain opaque identifiers.

This does not add asynchronous borrowing, capability-bearing children, detached
tasks, channels or implicit implementation search. Installation does not migrate
application data or replace running services. Source acceptance and exact public
distribution state are recorded separately in [current status](../status.md).
