# v0.1.53 — Shared services and recent accepted changes

Development release notes; public availability is recorded in
[status](../status.md), the [history continuation](../campaigns/202609281010.md)
and the [shared-host continuation](../campaigns/202609281356.md).

## Added

### Exact-code shared services

`lkjscript serve --deployment A --deployment B` hosts HTTP and interactive services
in one process. Equal exact artifacts share immutable prepared code; instance
configuration, secrets, grants, adapters, queues and cancellation remain separate.
Different exact versions can coexist. Every input still passes strict admission.
All static admission precedes live preparation, all listeners precede readiness,
and termination joins each started service. Single-descriptor serving is unchanged.

The fixed group accepts up to 64 instances and caps summed declared resident task
capacities at 4096 concurrent and 65536 queued. Redacted ready/stopped events report
exact selection, structural accounting and joined receipts. They do not measure
RSS or establish a process-wide live-memory limit. This is not hot reload,
cross-instance owned messaging, automatic data migration or a hostile-tenant sandbox.
Discover it with `capabilities --section deployment`; the
[shared-runtime contract](../spec/shared-runtime.md) records detailed boundaries.

### Recent accepted changes

`lkjscript --project PROJECT inspect history [--limit N]` shows recent accepted
changes newest-first. Each entry includes exact revision and parent identities,
optional recorded intent, changed-owner/dependency counts and separate selected,
executed and passed test counts.

The reader uses existing immutable revision and receipt objects. It captures one
coherent repository view, then traverses without holding the publication lock.
It defaults to 20 entries, accepts 1 through 100, and shares a cumulative limit of
200 object/catalog reads and 8 MiB of record/receipt payload. A truncated response
identifies a committed but unread next parent. Missing or inconsistent visited
links fail rather than masquerading as the end of history.

Discover the operation with `capabilities --section inspection`.
The [guide](../guides/native-history.md) explains the native editing workflow.

## Corrected

Resident stop cannot overtake accepted work before its queue registration. A short
per-instance registration boundary prevents adapter cleanup from observing false
idle while that work still owns captured resources; execution is not serialized.

Resident failure reporting retains the original structured diagnostic on stderr
when stdout is closed. Reporting failure does not undo already-visible effects.
The immediate closed-stdout contributor witness retains all 24 cases while using
an execution allowance separate from timeout-specific test deadlines.

## Compatibility and limits

No graph, artifact, package or operational-data format changes. Old runtimes do
not gain these commands automatically. The immutable public v0.1.52 is unchanged.
Existing review tokens still bind executable capabilities: re-plan the unchanged
request after an upgrade rather than modifying its base or reusing an incompatible
token.

Recorded acceptance is not current semantic revalidation:
`current-validation=not-run` is explicit. Inspecting history executes no old code,
replays no effect, accesses no application data and performs no rollback.
There is no historical editing, arbitrary revision selector, continuation beyond
100 entries, two-parent projection, project backup/restore or whole-history doctor.
Read counters exclude ordinary repository opening and disposable catalog recovery.

Source tests, candidate acceptance and immutable public delivery remain distinct.
