# v0.1.61 — Owned data across ordinary libraries

This successor combines immutable byte ranges, direct owned storage, constrained
generic functions, exact static implementation witnesses and structural owned
products. The accepted typed meaning graph remains the program authority.
[Status](../status.md) distinguishes integrated source, candidate acceptance and
public availability; these notes do not by themselves establish publication.

## Construct, transfer and decompose owned data

ByteBuffer provides pure creation, consuming octet push/freeze/discard and scoped
synchronous read borrowing. OwnedI64Cell is an independently sealed signed-scalar
allocation, not a byte encoding. Replacement keeps the scalar allocation;
extraction consumes it and returns its exact I64. Immutable Bytes remains
unrestricted data.

An explicit structural owned product groups one or more owned fields with closed
ordinary metadata. Fields can hold ByteBuffer, OwnedI64Cell, a finite nested
product or an in-scope Owned parameter. Metadata may contain closed ordinary
structural and nominal data; a wrapper or phantom argument cannot hide a callable,
capability resource, secret, stream or another unsupported contract.

`pack-owned` evaluates fields in authored order, consuming each owning local
exactly once at its field occurrence. `unpack-owned` consumes the complete product
and binds every field in a fresh body-only scope. Unused owners are released at
lexical exit. An owned
child's storage is transferred, not cloned; the product itself still needs field
and control storage. Ordinary records and collections do not silently become
affine containers.

A generic producer can group a buffer and a scalar with metadata, a second
library can retag or forward the product, and a consumer can decompose and freeze
the result. Native proposals, canonical drafts, literal edits, exact package
transport and source-free artifact execution use the same contracts.
See the [product guide](../guides/native-owned-products.md).

## Symbolic ownership and explicit implementation selection

Rank-one Owned parameters permit direct affine parameters, locals and results.
Bodies are checked symbolically before concrete use. Every actual type, argument
mode and selected implementation is checked again at its application boundary,
including unused arguments and unreachable expressions.

Nominal owned method contracts have exact static implementation operands rather
than implicit search or ordinary runtime dictionaries. Multiple same-signature
implementations remain distinguishable through package transport and preparation.
Concrete ByteBuffer, OwnedI64Cell and closed products can serve as Self.
Pure graph wrappers implement the exact method signatures; an empty-effect task
is not a pure method. Ordinary generic and CaptureSafe constraints do not admit
owned values merely because an argument happens to be unused.

Whole-product read borrowing is opaque and synchronous. A loan cannot be consumed,
unpacked, captured, persisted or returned. This increment does not introduce field
projections through loans, partial moves, owned lists/maps, mutable borrowing,
escaping references, task memory signatures, asynchronous memory transfer,
general trait machinery or region placement.
See the [generic ownership contract](../spec/owned-generics.md).

## Byte views and admitted storage

`bytes-slice` selects a strict half-open view without copying its visible payload
in production. Nested views retain one original backing; empty views retain none.
`bytes-copy` explicitly detaches a small retained view from a larger backing.
Contents, ordering and encoded bytes remain immutable and content-based.

Owned storage reserves its modeled token, synchronization, loan and shared-control
metadata before construction. Capacity growth rechecks cancellation after
reservation and before allocation. Product failures, traps, cancellation, exhausted
quotas and lexical exits release remaining owners and loans, including nested
products and partially completed field evaluation. Cleanup is iterative within
the admitted structural depth and invokes no user-defined destructor.

No proof or execution limit was raised. Allocation accounting is a modeled
cumulative policy, not an allocator-size, live-heap or RSS measurement. Correcting
earlier omitted charges can make a fixed quota refuse previously admitted work.
Neither ownership nor byte views establish universally faster execution, lower
memory use or whole-program zero-copy behavior.

## Compatibility and deployment

Current owned meaning uses graph/owner 19 and semantic validator 19. Frozen
canonical owner generations 14–18 remain readable. Ordinary base type-object 10
identities remain unchanged; owned carriers and products use disjoint envelopes.

Current derived code uses compiler unit 16, bytecode 12 and artifact 23.
Predecessor compiled artifacts require rebuilding from supported accepted meaning;
old proof or code does not silently gain current execution permission.
Current compact change contract is 26, with product-authored request codec 22.
Function-definition projection is 10. Exact package interface generation remains
12. Re-plan the original proposal after an executable upgrade rather than changing
its base to reuse an incompatible review token.

Raw runner/adapter ingress, ordinary result egress and durable storage do not admit
process-owned memory tokens. Freeze or consume into ordinary data before those
boundaries. Existing capability grants and external-effect ordering remain separate
from memory ownership.

Runtime installation does not upgrade accepted applications, exact dependencies,
running services or operational data. No data migration, native-code language
backend, browser/Wasm backend, collector or hostile-code sandbox is provided.
The Rust implementation remains a supported bootstrap boundary, not a claim of
a self-hosted compiler or the final memory-management architecture.
