# v0.1.60 — composable resource contracts and reusable value storage

Development release notes. [Status](../status.md) distinguishes integrated source,
candidate acceptance and public availability. This successor collects the unreleased
v0.1.56–v0.1.60 work after public v0.1.55; the intermediate version numbers do not
represent separate public releases.

## Exact resources across ordinary libraries

Public task helpers can borrow or consume a contiguous final suffix of capability
resources. Every parameter retains its explicit concrete requirement, exact interface
and use mode. Ordinary type parameters, direct and mutual synchronous recursion,
public package boundaries and forwarding packages compose with those contracts.
Repeated shared borrows may refer to one owner, but a repeated owner with any
consuming occurrence rejects in either order. Resource returns, requirement-polymorphic
resource signatures, indirect resource calls and escaping resource captures remain
unsupported.

Resource-free task callbacks may carry explicit effect parameters through these
helpers. Callback effects do not replace a resource's concrete authority, grant
permission to a pure caller, or permit duplication of a consumed resource.
Consumer entry ports declare imported requirements explicitly; their deployment
grants remain separate from callable identity and effect declarations.

Deployment grants can select exact package/requirement identities as an alternative
to an unambiguous name. Two requirements with the same name can therefore keep
independent adapters and data roots. Duplicate name/identity selections and ambiguous
names reject before secret lookup or live preparation. Runtime installation does not
silently upgrade accepted library selections or running applications.

See the [resource guide](../guides/native-resources.md) and
[deployment contract](../spec/deployment-security.md#exact-requirement-selection).

## Avoid unnecessary ordinary-value copies

The production VM transfers an ordinary local value at a proved terminal use.
Bounded control-flow analysis distinguishes exclusive branches, loop-carried values,
redefinitions and dynamic external-call continuations. Exhaustion of this advisory
analysis falls back conservatively; it does not relax semantic admission or turn a
live value into a move. Transaction slot checks remain enforced on both paths.

Text and byte map keys retain immutable payload storage through conversion, cloning
and projection. Byte concatenation additionally reuses a uniquely held vector's
spare capacity and grows it geometrically when required. An empty operand retains
the other payload. Shared prefixes, map keys and retained closures never become
mutable merely because the concatenation implementation can reuse private storage.

New payload capacity is admitted before allocation/copy; copies check cancellation
in bounded chunks. Equality, ordering and encoded bytes depend only on visible
contents, not on capacity or physical addresses. The independent reference evaluator
retains its separate copying implementation.

The byte carrier adds vector metadata and may retain spare capacity. Optional
cumulative-allocation quotas can stop at different boundaries because the selected
storage charges changed. Work counters cover explicit copies and requested capacity
in production concatenation, not allocator internals, process RSS or universal
zero-copy execution. No timing speedup or universally lower memory use is promised.

## Bound proof work independently of program validity

Affine validation now charges metadata reads before work occurs, in addition to
expression visits. Budget exhaustion propagates through owner shape, initial state
and body checking, and whole-snapshot validation no longer discards exhaustion.
Invalid meaning, diagnostic-sink exhaustion and proof-work exhaustion remain distinct.
Counters stop before integer overflow; underlying read errors and cancellation retain
their original behavior.

A fixed proof budget may now exhaust on previously uncounted work. This is not a
new runtime instruction quota or evidence that the program is semantically invalid.
Validator feature 9 invalidates predecessor affine proof reuse.

## Compatibility and scope

Graph, package, artifact and operational-data encodings are unchanged by this
successor. Existing review tokens still bind executable capabilities: re-plan the
unchanged request after an upgrade instead of changing its base or reusing an
incompatible token. Deployment discovery contract 6 admits exact grant selectors.
Raw Rust runtime value representations are implementation details, not a stability
promise.

The shared service host remains a fixed in-process group with per-instance authority
and state. These changes do not introduce general memory references, region ownership,
trait witnesses, a collector, cross-instance owned messaging, a browser backend,
hostile-code isolation or automatic data migration. The Rust implementation remains
a supported bootstrap boundary, not the selected permanent language memory model.

The [byte-storage continuation](../campaigns/20260930-byte-buffer-reuse.md),
[affine-proof correction](../campaigns/20260929-affine-validation-work.md), and linked
language campaigns retain failed attempts and exact-source evidence. A successful
source check is not final-distribution acceptance; any public release must use its
accepted original archive without rebuilding its assets.
