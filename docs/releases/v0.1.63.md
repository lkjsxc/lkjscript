# 0.1.63 — Owned data composition and metadata inspection

This successor consolidates the unpublished 0.1.61 owned-data work, the 0.1.62
product-identity and maintained-input corrections, and ordinary metadata reads.
All components of the product identifier are opaque: none encodes stability,
compatibility, change size or feature availability. These notes select a candidate;
they do not establish final-archive acceptance or a published release.
[Status](../status.md) separates those boundaries.

## Compose owned data across libraries

ByteBuffer provides pure creation, consuming octet push/freeze/discard and
synchronous read borrowing. OwnedI64Cell independently owns signed-scalar storage;
replacement preserves its allocation and extraction consumes it into ordinary I64.
Explicit rank-one Owned parameters admit direct affine parameters, locals and
results. Generic bodies are checked symbolically, not only after concrete use.

Nominal owned method contracts use exact static implementation operands.
Implementations with identical signatures remain distinct across package transport;
there is no implicit witness search or capability grant. ByteBuffer, OwnedI64Cell
and closed structural owned products can serve as Self.

A structural owned product groups one or more owned fields with closed ordinary
metadata. Products can nest. `pack-owned` evaluates fields in authored order and
consumes live owner operands. `unpack-owned` consumes the entire product and binds
every field in one lexical body; unused children are released at exit. Ordinary
records and lists/maps do not silently become affine containers.

Native proposals, canonical drafts, identity-preserving literal edits, exact
package transport and source-free execution retain these contracts. See the
[owned-product guide](../guides/native-owned-products.md) and
[generic ownership specification](../spec/owned-generics.md).

## Inspect metadata without dismantling the owner

An ordinary policy helper can read a product's closed metadata without consuming
and reconstructing the product:

```text
(field (local packet) (name tag))
```

The source is an exact live owning local or borrowed parameter. The operation
briefly borrows the whole product and returns an ordinary immutable value.
Generic helpers and cross-package reborrows preserve the original ownership,
so the caller can subsequently move or completely unpack the product. The
ordinary result may outlive consumption or destruction of its parent.

An owned payload is not a readable ordinary field. Missing fields, consumed
locals, projections from non-local owned temporaries, partial moves and
mutable or escaping loans remain rejected. Bind a temporary explicitly before
inspection. Metadata reads do not implement owned choice/result containers,
general lifetime polymorphism or asynchronous ownership transfer.

## Byte views, storage and maintained inputs

`bytes-slice` selects a strict half-open view without copying its visible payload
in production. Nested views retain one original backing; empty views retain none.
`bytes-copy` explicitly detaches a small retained view from a larger backing.

Owned constructors reserve modeled token, storage, synchronization and loan
metadata before growth. Metadata reads reserve any inline sum/option box spine
before cloning. Cancellation checks bracket reservation and copying. Product
cleanup releases remaining children, including on traps, cancellation and quota
exhaustion. No user-defined destructor is invoked and no independent effect is
rolled back by memory cleanup.

The four maintained native projects include their deterministic first-use packs.
A tracked-source copy checks and rebuilds them without adding missing packs or
changing accepted program revisions. This corrects the failed 0.1.61 candidate's
source-inventory boundary; that run remains failed and is not relabelled.

Allocation charges are a modeled cumulative policy, not allocator size classes,
live heap or RSS. Ownership and immutable backing sharing do not establish a
universal speedup, lower total memory use or whole-program zero-copy execution.

## Compatibility and deployment

Graph/owner 19, package interface 12, authored request 22 and compact change 26
retain their layouts. Ordinary base type-object identities remain unchanged.
Semantic validator 20 and owned-product feature revision 2 invalidate predecessor
proof reuse for the extended read contract.

Derived execution uses compiler unit 17, bytecode 13 and artifact 24. Rebuild old
artifacts from supported accepted source. Re-plan unchanged proposals after an
executable upgrade; do not alter their base or reuse incompatible review tokens.

Raw runner/adapter boundaries and durable storage do not admit process-owned
tokens. Consume or freeze them into ordinary data first. Memory ownership,
declared effects and exact deployment grants remain separate.

Runtime installation does not replace accepted applications, exact dependencies,
running services or operational data. No collector, native-code language backend,
browser/Wasm backend, general traits, asynchronous owned transport or hostile-code
sandbox is supplied. Rust remains the current bootstrap implementation, not the
selected permanent self-hosting boundary.

The [metadata continuation](../campaigns/20261001-owned-product-metadata.md)
records failed attempts, corrected source checks, independent public programs and
the actual candidate/publication state. Public v0.1.60 and earlier immutable assets
are unchanged until a separately accepted candidate is explicitly promoted.
