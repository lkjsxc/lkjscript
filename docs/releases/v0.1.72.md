# v0.1.72: reusable structured execution

Structured parallel tasks reuse lazily created auxiliary workers. A fixed shared
service group owns one executor; standalone commands and graph tests own their
execution lifetime explicitly. Immutable prepared programs are shared through
handles, while each invocation retains its own memory origins, exact task
applications, cancellation, grants and quota ledger.

Idle-worker reservation never waits. The caller executes one child and executes
both when no worker can accept the intact job. Nested groups retain progress under
saturation. Dispatch reservations last through joined completion; caller unwind,
child panic, cancellation and shutdown preserve custody and joined cleanup.
Shutdown closes dispatch, drains invocations and joins every owned worker.

The maintained three-package parallel-work example implements the same byte
transformation and weighted reduction through ByteBuffer and OwnedI64Cell
contracts. It supports serial, parallel and nested command targets and a CPU HTTP
endpoint beside an independent service, using existing native language features.
Full payloads are checked against independent expectations after authoring sources
and transports are removed.

CLI observation 36 replaces `parallel_workers_spawned` with
`parallel_worker_dispatches` and adds `parallel_inline_fallbacks`. Physical thread
starts and joined lifecycle are separate executor observations. Shared-runtime
observation 2 reports a fresh executor receipt at stop; foreground commands also
report `executor-observation`. Consumers must discover these current fields.
Graph 22, validator 27, package interface 13, compiler 22, bytecode 17 and artifact
29 retain their contracts. This runtime change requires no semantic data migration.

The process-wide auxiliary ceiling is available CPU parallelism minus one, with
zero auxiliary workers when CPU discovery is unavailable. It does not bound
blocking-capable resident root execution or establish fairness, preemption, speedup
or hostile-code isolation. Child tasks still require closed empty effect rows;
channels, effectful children and asynchronous borrowing remain separate work.

Product version components remain opaque identifiers. Installation neither changes
application data nor replaces running services. Actual acceptance, measurements and
publication are recorded separately in [current status](../status.md).
