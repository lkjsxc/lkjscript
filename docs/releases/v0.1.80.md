# v0.1.80 — Composable implementations and shared prepared code

Owned implementations declare ordered implementation prerequisites and map
generic functions with explicit witness arguments. Applications retain their exact
declaration, ordered types and complete nested prerequisite identities. Selecting
a witness preserves ownership, callable kind, closed effects and borrowed-result
provenance without granting execution authority.

The [three-package composition witness](../../examples/composable-owned-implementations/README.md)
exports `Maximum<T,W>`, `DelegatingReader<T,W>` and a consuming task adapter before
independently authored cells, buffers and a nested product exist. `Maximum` maps
directly to the existing generic selector. Nested flat/reverse readers distinguish
first ties, source-tied views end before draining and reusing the original owner,
and joined children consume collections through exact task applications.

Mapped witness operands are direct prerequisites from the same implementation or
finite concrete application trees containing no lexical witness parameter.
Eligible symbolic type arguments remain supported. Constructing an application
around a scheme prerequisite inside a method map is unsupported. Before exact
callable exploration, a conservative graph of potential method targets rejects
lexical witness wrapping on recursive construction edges. An unused same-contract
alternative can create such a potential cycle; this rejection does not prove
actual witness growth. Forwarding, permutations, projections, fully concrete
resets and symbolic construction outside those components remain supported.
Capacity exhaustion and independent type-growth rejection retain distinct causes.
Source proofs still retain separate typed prerequisite paths; deeply duplicated
acyclic applications can exhaust proof capacity despite compact witness storage.

Prepared applications with matching exact function, types and closed
effect/requirement context share identical immutable instruction bodies. Each
application keeps its independently admitted witness identities and resolved
call-site bindings for ordinary calls, tail calls, function values and parallel
children. Code sharing establishes no performance claim or reduced admission
obligation. Preparation still materializes each application before deduplicating
its instruction body, and its allocation ledger retains that construction cost.

The affected identities select graph/owner 29, validator 34, package interface 17,
compiler unit 29, bytecode 24, artifact 36, authored change 33, compact change 37,
function definition 19 and CLI 42. Rebuild experimental derived bundles through
supported product operations; no migration promise is added. Original historical
fixtures and immutable publication bytes retain their evidence.
