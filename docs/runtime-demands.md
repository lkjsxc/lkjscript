# Runtime demands at large-program scale

Chromium is a yardstick, not a port or a source dependency. The rows are lkjscript decisions, not claims that its current runtime matches Chromium.
Initial baseline: `6632d1ca`; the table now includes this note's process, foreign-session, admission and graph work. "Needs" identifies a remaining boundary or implementation gap.

| Order / demand | What holds today | Honest form here | Specimen / remaining proof obligation |
| --- | --- | --- | --- |
| 1. Privilege-separated processes and parallel work | Capability/IR implemented: affine Image/Worker/Channel bind authenticated ELF and slot ABI; `Process` remains broad host authority | One Channel entry slot, explicit moved File messages, attached lifetime, deadline and exit/trap values; other capability transfers remain unsupported | Listener/root parent and unprivileged parsers; four-worker ordered pure map; death/restart/kill campaign |
| 1. Typed messages and descriptor transfer | Capability/IR for byte packets and moved File exists; needs compiler semantic message identity and generated codecs | Shared byte codec first; semantic message identity and arbitrary typed codecs remain a compiler handoff; File moves even when send fails | Retained: malformed byte frames and File reuse-after-move refusals; pending: sender/receiver schema mismatch and stale semantic identity |
| 1. Shared payloads | Capability/IR implemented: fully sealed File and ReadRegion with checked shared byte views; structured typed views remain missing | Seal immutable bytes before sharing; owner-tied readonly byte views; no writable mappings, foreign-layout casts or shared allocator state | One MiB round trip by copy versus frozen mapping, write-after-publish refusal |
| 1. Threads, synchronization, scheduling | Existing process capabilities support library parallelism; same-address-space threads need IR transfer/share predicates and a memory model | Processes-only parallelism now; serialized actor owners, bounded channels and readiness/timers. One-address-space threads require separately proved transfer/share predicates and allocator/stack rules | Ordered pool, contended map owner, bounded producer/consumer shutdown; seeded protocol schedules, not a claimed thread race detector |
| 2. Code arriving after start | Expressible by an explicit trusted compiler producer with World; narrow public Admission capability remains missing | Dedicated live producer carries checker/backend, checks an empty authority ceiling and executes a sealed child; authenticated caller-facing admission remains a gap | Runtime-supplied pure IR succeeds; authority growth/mutants refuse; located trap survives at host |
| 3. Long-lived foreign libraries/drivers/codecs | Capability/IR implemented: confined ForeignSession; in-image FFI contradicts the current boundary | Attached worker with read root/null device and byte channel; per-request deadline and library restart; foreign descriptor/shared-region transport remains missing | `git cat-file --batch` worker versus per-request spawn, death/deadline/restart |
| 4. Mutable graphs and nonlexical lifetimes | Library on existing IR: Arena<T,Kind> and generational Handle<Kind> | One owner arena, typed generational handles, lexical lookup borrows; actor owns mutation; stale references are values | Million-node parent/child/sibling/observer graph, random subtree edits and stale-generation checks |
| 5. Runtime dispatch over open type sets | Closed enum dispatch expressible; open in-image callables need IR | Closed enums within an image; independently admitted image/interface identities for open plugins; no fabricated vtable pointers | Pending: two independently built implementations behind one checked request contract |
| 6. Many idle I/O tasks and timers | Existing capabilities and library | Readiness and deadline queue, bounded dispatch, fixed absolute deadlines; no thread per idle peer | Existing HTTP/SSE idle-peer and slow-reader suites |
| 7. Window, input, graphics and sound | Needs capabilities/backend/target work | Explicit device/protocol service handles, typed command streams; foreign driver remains outside checked image | Pending: window/input event loop, submitted frame and audio buffer with scoped device grants |
| 8. Text and cryptography | UTF-8/text, SHA-256/HMAC and entropy expressible; Unicode layout/TLS still missing | Ordinary audited libraries plus explicit entropy/trust-root effects; do not invent assurance for missing algorithms | Pending: Unicode traversal/normalization corpus; authenticated stream with certificate refusal |
| 8. Allocation controlled by program | Existing owned containers, fallible kernel growth and located exhaustion; custom allocator control missing | Ownership-preserving arena/pool libraries first; explicit allocation-domain capability only on measured need | Arena reuse/fragmentation and one maintained heap-refusal case |
| 9. Failure isolation and evidence | Existing capabilities/library: Worker death/status, located traps, private results and durable parent publication | Child fault becomes parent value; bounded library supervision; publish only committed results; no in-image trap recovery claim | Kill every publication phase, retain acknowledged prefix and located worker failure |
| 10. More than one target | Needs backend/runtime: Linux x86-64 only | Target-independent checked contracts with target-specific sealed capability implementations and refusal when unavailable | Pending: same checked cases on a second real target, including failure and authority parity |

The order makes process isolation the prerequisite for both parallelism and failure containment; graphs are independent library work. It does not silently declare same-address-space parallel compilation solved.
A process pool costs separate heaps, IPC and checked unit serialization; compiler adoption is offered through a pending case, never asserted from a toy map benchmark.
The old prose about three pending scoped-concurrency cases is stale: only `borrowed_closure_escape` remains in conformance. No absent test is counted as proof.

Architecture sources (documentation only; no Chromium source checkout): [process separation and failure](https://www.chromium.org/developers/design-documents/multi-process-architecture/), [Mojo messages, platform handles and shared buffers](https://chromium.googlesource.com/chromium/src/mojo/+/refs/heads/main/core/), [threads, sequences and task pools](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/threading_and_tasks.md).
