# Owned byte buffers and synchronous read borrowing

Status: normative for the concrete ByteBuffer slice. CapabilityResource and its authority contracts remain separate.

`ByteBuffer` is a concrete affine type for one mutable sequence of unsigned octets. It carries no requirement, effect row, operation grant or deployment grant. Creation and the closed memory operations are pure. Ordinary immutable `Bytes` remains unrestricted, shareable data; sharing an Arc does not establish language memory ownership.

The closed external inventory is exact:

| Standard operation / implementation | Parameters in evaluation order | Result |
| --- | --- | --- |
| `buffer-empty` / `core.buffer.empty` | none | owned ByteBuffer |
| `buffer-push` / `core.buffer.push` | unrestricted I64, consume ByteBuffer | owned ByteBuffer |
| `buffer-get` / `core.buffer.get` | unrestricted I64, borrow ByteBuffer | I64 |
| `buffer-length` / `core.buffer.length` | borrow ByteBuffer | I64 |
| `buffer-freeze` / `core.buffer.freeze` | consume ByteBuffer | Bytes |
| `buffer-discard` / `core.buffer.discard` | consume ByteBuffer | Unit |

Push accepts only integers in 0 through 255. Get accepts only nonnegative indices below length, including for empty buffers; invalid integers trap without wrapping or clamping. Freeze consumes the owner and adopts its Vec allocation into immutable Bytes. It retains spare capacity and does not guarantee allocator behavior, RSS reduction or zero allocation. No live mutable buffer shares payload storage with Bytes. Discard and implicit lexical drop release owned storage; neither promises secure erasure.

Pure declarations can transfer a direct owned ByteBuffer result and have a final suffix of concrete ByteBuffer parameters marked borrow or consume, with no resource requirement. Preceding data and callback parameters retain ordinary unrestricted semantics. Memory call suffix arguments must be exact live locals. Owned locals require an explicit ByteBuffer binding annotation. Borrowing an owner, or reborrowing a read parameter, creates a read loan scoped to the synchronous call. A borrower cannot push, freeze, discard, return, copy, capture or otherwise escape the loan. A consuming argument moves an owner; combining that owner with any other borrowed/consuming argument in the same call is rejected. Multiple synchronous read loans are permitted.

Ordinary generic data and callback arguments can precede this concrete memory suffix, and generic producers can return a concrete owner. An otherwise legal explicit requirement parameter remains exact signature metadata, including in a pure producer; its presence grants neither effects nor access to operations. Substituting ByteBuffer or a type containing it for an unrestricted parameter is forbidden even when unused, phantom or in untaken syntax. Buffers cannot occur in records, variants, lists, maps, options, results, streams, callable descriptors or other containers. A memory-bearing declaration cannot become a function value or partial application, including when only its result is a buffer. Language equality and map ordering of ByteBuffer are unsupported.

Task bodies may create transient buffers and use pure memory helpers while retaining their existing task permissions. Task declarations with memory parameters or a direct memory result, and signatures mixing capability resources with memory, are unsupported. Capability operations, ports, constants and persistence cannot contain buffers in their declared boundary types. Ordinary-result constant, test and expression-port roots may use transient locals under the same ownership validation as functions. Function extraction does not support capturing a buffer or extracting a direct buffer result in this increment.

Every executable root and the complete relevant type and application closure is admitted before execution, including unreachable expressions and unused generic substitutions. At a branch or match join a preexisting owner remains live only if every branch preserves it. A branch may return one of several owners and discard the others; subsequent access to an owner possibly moved by any branch rejects. Owned temporaries are released after discard, lexical exit, traps, refused allocation/quota reservations, cancellation and failed result transfer. Every nonfinal sequence result is discarded before evaluation of its successor, including sequences used as binding initializers. Allocation work is reserved before growth. Work exhaustion and cancellation remain operational outcomes, distinct from invalid meaning; no proof or execution budget is enlarged for this feature.

Tail transfer may replace a consuming activation after canonical lexical cleanup continuations. A caller owning storage with outstanding read loans remains live until its borrowed callee completes. A reader that only reborrows storage owned by a retained ancestor may tail-transfer without retaining another activation. Pending ordinary non-tail work and existing resource/effect contracts are preserved. Recursion does not establish termination.

Runtime tokens are sealed, checked and scoped to fresh invocation identities. Raw ingress, arbitrary adapter results and retained values cannot manufacture a memory owner or read loan. Rust raw Clone creates an inert identity token: it retains neither readable access nor ownership. Internal raw identity equality ignores token mode so Clone/Eq remains coherent; this is not language equality or payload equality. Debug output is opaque. Owner drop revokes storage even while inert markers or read tokens retain metadata.

ByteBuffer has disjoint version-1 canonical encoding `LKJBUF01`, with domain `lkjscript.kernel.byte-buffer-type-envelope.v1` and its sole tag 1. Base TypeObject 10 and graph/owner 17 remain unchanged. Native authored intent containing the buffer form selects `LKJACR20` and explicit type tag 20; unchanged requests retain their earlier generation. Current compiler unit 14 / bytecode 10 admits memory modes, direct result transfers and canonical Unit/StoreLocal lexical cleanup. Older units cannot contain the buffer digest. Artifact 21 binds exact memory declaration, external, parameter and result metadata and independently compares transported code against canonical lowering for every executable root. It also validates affine meaning across the retained owner inventory: agreeing canonical source, code and checksums cannot certify a double consume, including in an untaken branch or an ordinary-result constant. Exhausted affine proof work is a resource outcome, not evidence of invalid meaning. The source-reference evaluator reconstructs its classifications and tail decisions from canonical owners. Supported earlier exact closures retain their previous encodings; older executables reject this extension.
