# Check native dependency plans independently of their producer

## Decision

Give the native dependency planner a separately authored result checker. Build and
export the checker before authoring the producer, then import its exact package
into checked flat and chunked planner entrypoints. Keep the existing unguarded
planner API and its output encoding unchanged. This is a native tooling boundary,
not a new intrinsic, a production compiler replacement or a general proof system.

The standalone checker artifact contains the existing provisional-graph admission
and reachability implementation and six new checker modules. It contains none of
the component finish-order, component assignment, condensation or readiness-queue
planner modules. Its checking interface takes the original proposal and a claimed
complete valid-plan payload. A claim need not have been generated by our planner.

Typed method signatures establish ownership and type obligations, not algorithmic
laws such as LIFO behavior or correctness of an SCC partition. Rather than adding
an unchecked law annotation, check the particular result against its input. The
checker can reject a false result from an incorrectly implemented producer without
knowing how that producer obtained it. This does not prove the producer correct
for every input, nor make the checker itself a mechanically verified kernel.

## Shared admission, independent result conditions

Ordinary runner admission still checks both complete raw arguments, even when the
proposal is invalid or a claimed field would not be inspected on the selected path.
The checker reuses `provisional-graph::flat` for complete proposal validation and
reported reachability. It inherits the 4,096-node, 4,096-root and 16,384-edge-entry
capacities and their diagnostic precedence. This shared boundary is explicit: the
checker is independent of SCC computation and stage generation, not of all source
validation, standard collections or runtime machinery.

After a valid proposal, admission proceeds in this order:

1. Require nonempty components, exact once-only coverage of all input identities,
   authored member order and authored first-member component order. Only nonnegative
   derived positions use -1 as a missing-position sentinel; signed input identities
   remain ordinary keys. Compare the complete reachable and unreachable lists.
2. Scan the original edges to construct forward/reverse adjacency, self-loop facts
   and the exact first-occurrence list of distinct cross-component dependencies.
   Require the claimed dependency lists and cyclic flags to match these facts.
3. Require every component representative exactly once in nonempty stages, with
   authored component order within each stage. Bind bounded stage indices. A
   dependency-free component must have level zero; every other component must have
   one plus the maximum level of its dependencies.
4. For each nonsingleton component, traverse from its first member in both the
   original and reversed adjacency, restricted to that component. Both traversals
   must visit exactly its member count. Mark at enqueue and read an ordinary list
   queue by increasing offset; this step uses neither finish order nor a LIFO law.

There are at most as many component rows and stage rows as input nodes. Member and
stage scans reject duplicates and unknown identities before extending their maps;
valid insertions cannot exceed the admitted node count. Dependency-list lengths are
compared with reconstructed lists before element comparison. Claimed payloads do
not increase source graph capacities or confer extra execution resources.

## Why these conditions suffice

Exact member coverage establishes a partition of the original vertex set. In a
component with leader r, the two restricted traversals establish r -> v and v -> r
for every member v. Therefore every pair of members is mutually reachable. The
singleton case follows by reflexive reachability; only an actual self-edge marks a
singleton cyclic.

The level equation implies a strict decrease along every cross-component dependency
edge. A cycle between distinct claimed components would require a finite level to
be strictly smaller than itself, which is impossible. Hence no true SCC can have
been split across components. Internal strong connectivity also prevents merging
different true SCCs. Together these conditions establish the complete maximal SCC
partition without running a second SCC algorithm.

The same equations characterize earliest dependency-respecting stages: leaves have
level zero and induction along the acyclic condensation fixes each other level.
Exact stage coverage and peer order then fix the complete presentation, independent
of the producer's readiness queue. The edge scan fixes dependencies and their order;
shared source admission fixes the reported reachability partition.

This is a mathematical argument for the stated predicates. Source tests and public
adversarial executions check their implementation; they are not a mechanized proof
that all supporting software implements those predicates correctly.

## Failure, authority and composition

The standalone `Verification` outcome is `verified(Unit)`, `rejected(Text)`, or the
inherited `invalid(Diagnostic)` / `capacity(Text)` source outcome. Source invalidity
and source capacity precede claim checking. Rejection codes distinguish members,
reachability, dependencies, cyclic flags, stages and internal strong connectivity.
Raw type refusal, interruption and execution-policy exhaustion remain unsuccessful
runtime invocations, never successful partial verification reports.

Checked planner entrypoints invoke the exact imported complete-outcome checker for
every generated valid, invalid or capacity result. Verification success forwards
only the immutable claim actually checked; there is no distinct original-result
argument that could disagree. Rejection becomes the planner's existing
`inconsistent` outcome, never a valid plan or a verified negative diagnosis.
An existing `inconsistent` producer result is preserved as an internal failure,
not certified as a source outcome.

A verification report is ordinary data, not an unforgeable certificate, a program
acceptance token, an execution grant or a publication right. Reusing evidence needs
the same complete proposal, claim, exact checker and applicable execution/trust
bindings. A changed graph, different roots or a report copied from another context
cannot inherit verification merely because a serialized value says `verified`.
Nothing here reads, edits or publishes the compiler's accepted meaning graph.

The checker shares source admission, immutable standard data and the selected
runtime with the producer. Its imported implementation identity must be selected
and independently admitted; a matching function type alone cannot make a malicious
replacement checker trustworthy. Cyclic units still have no implied sequential
member schedule, and a stage still grants no parallel-effect or memory authority.

## Complete outcome checking

The additive `ClaimedDependencyOutcome` interface represents `valid(Plan)`,
`invalid(Diagnostic)` and `capacity(Text)`. `verify-dependency-outcome` independently
runs the complete source validator once, then compares that outcome with the claim.
For a valid source, it passes the admitted partition into the existing plan predicates
without repeating source admission. Wrong outcome kinds reject with `source-outcome`.

An invalid claim must match the first required diagnostic exactly: code text, owner
and target identity. Later but genuine errors are not interchangeable. A mismatch
rejects with `source-diagnostic`. A capacity claim must name the exact first exceeded
dimension under the existing nodes/roots/edges precedence; any mismatch rejects with
`source-capacity`. Text equality is exact, including whitespace, case and null bytes.

The separate two-case `OutcomeVerification` result is `verified(Unit)` or
`rejected(Text)`. Verified negative outcomes do not establish graph validity.
The old successful-plan interface and its source-invalid/capacity precedence remain
unchanged. Complete raw admission still checks the selected claim's entire payload,
even when native source checking would stop before inspecting it. Runtime resource
refusal and interruption remain unsuccessful execution, not claim-verification
outcomes. An `inconsistent` value is not representable as a complete source claim.

Both public interfaces and the checked consumers retain exact separately exported
checker selection. This closes the native wrapper's unchecked-negative-report path;
it does not eliminate shared source-validation trust or adopt the checker in the
production compiler. The [outcome guide](../../examples/dependency-plan/verification/outcomes/README.md)
owns public invocation and the additional diagnostic, capacity and false-negative
matrices. No new source or encoding authority follows from an ordinary report.

## Cost and acceptance

After source admission, graph work scans bounded nodes and edges and visits each
member at most once per connectivity direction. Persistent collections, preparation,
raw admission, export, working storage and result encoding have separate costs.
Additional result checking is real work; there is no speedup, zero-copy, bounded-RSS
or API-cost claim. The checker does not raise a quota to pass its public tests.

The [public guide](../../examples/dependency-plan/verification/README.md) describes
separate authoring and exact dependency selection. Independent expected plans use
pairwise reachability and synchronous level relaxation. The public suite includes
all three-vertex directed graphs with every canonical component partition and
gap-free stage assignment, not only plans generated by the maintained producer.
Targeted malformed claims cover the remaining identity, order and field boundaries.

[Certifying-algorithm research](https://www.dagstuhl.de/25231) motivates separating
answer generation from answer checking. This step implements concrete result
checking, not proof logging, a general theorem prover or the guarantees of that
research's formally verified checkers. Exact accepted source, retained failures,
full-verification receipts and distribution remain owned by [status](../status.md).
