## 0. Executive Directive

Do not automatically continue the current roadmap's “escaping managed value” gate.

Do not add another language type merely because the previous campaign added `bytes`.

Do not optimize the interpreter merely because the runtime now has a managed-value arena.

Do not assume that strict JSON, a complete machine schema, or one-request-per-connection IPC is the best programming interface merely because those mechanisms are correct and already implemented.

The repository has successfully proved a narrow architectural thesis:

> Program meaning can live in one typed, versioned semantic model owned by a local service, with stable identity, immutable revisions, deterministic validation, direct lowering, and safe bounded execution.

That thesis remains the default foundation.

The repository has not yet proved the more important product thesis:

> A coding agent can understand, create, debug, refactor, extend, and maintain a realistic application through a compact semantically local interface, without reading the Rust implementation or reconstructing a text-file project.

The mandatory campaign question is therefore:

> What is the smallest coherent semantic workbench that lets an autonomous coding agent perform long-horizon program maintenance with high success, low correction cost, bounded context, exact reviewability, and no second source of truth?

Treat this as a strategic convergence campaign rather than another isolated feature campaign.

The expected result is not merely a new command.

The expected result is a measured correction of the product boundary.

The current generic JSON CLI is a correct transport projection.

The current `AGENTS.md` is rigorous.

## 14. Phase 5 — The Retained Semantic Workbench

After alternatives are measured, implement one coherent preferred workbench.

The default command family is illustrative:

```text

lkjscript agent context
lkjscript agent view
lkjscript agent validate
lkjscript agent apply
lkjscript agent diff
lkjscript agent run
lkjscript agent explain
```

Choose names that fit the final design.

Do not expose commands that merely mirror every internal request variant.

The workbench should guide the agent through semantic tasks.

The service remains the correctness authority.

### 14.1 Bootstrap behavior

A fresh agent should obtain a compact orientation without reading Rust source.

Bootstrap output should state:

- product model;
- current workspace/revision selection rules;
- available high-level tasks;
- how to request exact context;
- how to validate;
- how to commit;
- how to inspect errors;
- how to run;
- version/digest facts.

Do not dump the complete machine schema by default.

Exact machine expansion must remain available.

### 14.2 Local cache

A local derived cache may store machine-contract and context data keyed by exact digest.

Define:

- location;
- ownership;
- permissions;
- size bounds;
- invalidation;
- corruption behavior;
- concurrent access;
- cleanup;
- whether it is per binary, user, state directory, or workspace;
- whether no-cache mode exists.

A corrupt cache is discarded or rejected as derived state.

It never repairs or overrides authority.

Do not persist model transcripts.

### 14.3 Persistent client connection

Evaluate a persistent daemon connection only after measuring one-connection-per-request overhead.

If retained, define:

- request correlation;
- framing;
- maximum in-flight requests;
- ordering;
- publication boundary;
- shutdown;
- deadlines;
- partial reads/writes;
- cancellation;
- reconnect;
- retry;
- unknown outcomes;
- backpressure;
- output bounds.

The default safe first step is sequential requests on one connection.

Do not add multiplexing or concurrency without measured need.

Never silently replay a mutation after transport uncertainty.

### 14.4 Candidate sessions

Evaluate a multi-turn candidate session only if the maintenance corpus shows that publish-every-step or single-transaction authoring is materially harmful.

A candidate session must clearly state whether it is:

- ephemeral;
- durable;
- authoritative;
- queryable;
- runnable;
- lease-bound;
- resource-bounded.

Default preference:

- keep published revisions authoritative;
- keep candidate state explicitly non-authoritative;
- require exact base revision;
- permit validate/query during the session;
- publish once atomically;
- discard deterministically;
- do not consume persistent IDs on abandonment.

Do not retain this feature if provisional identity mapping, crash behavior, or memory cost is not coherent.

### 14.5 Review and diff

Provide a deterministic semantic review before commit.

The review should distinguish:

- created;
- deleted;
- renamed;
- refined;
- replaced;
- rewired;
- completeness changes;
- entry changes;
- behaviorally relevant signature changes.

Do not infer behavioral equivalence unless proved by exact tests or analysis.

The raw typed diff remains available.

## 17. Conditional Semantic Capability Gate

The maintenance corpus may reveal a language or system capability that is more important than the workbench itself.

Do not ignore that evidence.

Do not implement a capability before the interface and corpus can measure it.

Use the following decision order.

### 17.1 Better query or refactor operation

If the language is expressive enough but maintenance is mechanically expensive, prefer a focused semantic query or identity-safe refactor operation over a new language feature.

Examples:

- replace all exact uses;
- migrate a declaration under explicit mapping;
- move a definition while preserving identity when semantics permit;
- clone a definition with explicit new identity;
- extract a pure helper under exact use rules.

Do not create a generic rewrite language.

### 17.2 Text

If the application needs semantic text distinct from arbitrary bytes, compare:

- a dedicated immutable `text` type with validated Unicode scalar semantics;
- explicit UTF-8 conversion to and from bytes;
- remaining with bytes.

Define normalization policy explicitly.

Do not silently normalize Unicode.

Do not expose host string behavior as language semantics.

### 17.3 Sequence

If repeated homogeneous values are required, compare:

- a dedicated immutable sequence;
- a generic sequence;
- a domain-specific fixed aggregate;
- postponement.

Do not use a bytes representation for arbitrary typed values.

Define order, length, indexing, slicing, equality, allocation, sharing, escape, and runtime accounting.

### 17.4 Generics

If at least two retained consumers need the same abstraction, evaluate generics.

Define declaration identity, substitution, inference, monomorphization or dictionary semantics, recursive constraints, artifacts, queries, and agent context.

Do not add generics solely to avoid duplicating one small declaration.

### 17.5 Packages

If the corpus needs reusable immutable dependencies, evaluate a package model before adding ad hoc imports.

Define package identity, version or content identity, dependency authority, namespace resolution, lock state, offline behavior, artifacts, signatures, and conflict semantics.

Do not let filesystem paths become semantic package identity.

### 17.6 Effects and permissions

If real application behavior requires host access, design one narrow vertical with explicit typed authority and deterministic failure.

Separate permissions from resource ownership.

Do not add ambient I/O.

### 17.7 Branches and merge

If parallel or speculative agent work is materially blocked by one head, evaluate branches.

Start with explicit parented immutable heads and deterministic semantic conflicts.

Do not jump directly to a CRDT.

Use stable identities and edit logs as design inputs.

Represent unresolved conflicts explicitly and typefully if retained.

### 17.8 Incremental indexes

If repeated exact queries dominate measured cost, add the narrowest derived index.

Full recomputation remains the oracle.

### 17.9 Persistence compaction

If artifact growth or rewrite time dominates, compare journal, chunking, checkpointing, and compaction.

Preserve immutable revision semantics and reconstruction.

### 17.10 Runtime acceleration

If pure execution dominates an actual workload, compare interpreter specialization, bytecode, Cranelift, LLVM, or another mature backend.

Keep the safe interpreter oracle.

Do not optimize before the workload exists.

## 31. Decision Tree After Baseline Evidence

After the baseline and corpus are available, choose the next implementation step using this order.

### 31.1 Baseline cannot complete the corpus

If a fresh agent cannot complete the corpus because it cannot discover exact accepted shapes:

- prioritize compact bootstrap and task cards;
- do not add language semantics;
- do not enlarge README;
- compare root projections with packet context;
- retain exact schema expansion as the fallback.

If failure is caused by malformed transport payloads:

- prioritize a compact action grammar or generated client surface;
- preserve semantic validation unchanged;
- classify quoting, field-shape, alias, and schema errors separately.

If failure is caused by missing semantic facts:

- add the smallest deterministic query or packet field;
- do not solve the problem with prose;
- add sufficiency and omission tests.

If failure is caused by a genuinely missing language capability:

- enter the conditional semantic gate;
- name the exact blocked task;
- compare dedicated and reusable designs;
- implement one dependency-closed vertical.

### 31.2 Baseline completes but uses excessive repeated context

Prioritize:

1. digest-keyed local schema cache;
2. task-scoped packets;
3. revision-bound aliases;
4. stable derived review view;
5. fewer repeated help/schema emissions.

Do not change daemon semantics merely to reduce model-visible repetition.

### 31.3 Baseline completes but requires many semantic corrections

Identify whether corrections come from:

- type mismatch;
- scope;
- missing constructor facts;
- stale revision;
- alias ambiguity;
- maintenance operation granularity;
- runtime debugging.

Improve the corresponding deterministic interface.

Do not hide errors through permissive coercions.

### 31.4 Baseline completes but process lifecycle dominates

First use the existing line session correctly.

Then measure a persistent daemon connection.

Do not add concurrent in-flight requests before sequential reuse is measured.

### 31.5 Baseline completes efficiently

Do not force a new authoring syntax.

Retain the baseline.

Keep the derived review view if it independently improves human or agent review.

Use the corpus to select the next semantic or performance gate.

### 31.6 Candidate improves bytes but harms correctness

Reject it.

A smaller interface with more wrong edits is not an improvement.

### 31.7 Candidate improves success but increases context modestly

Retain it when the total task evidence supports the tradeoff.

Record the tradeoff explicitly.

### 31.8 No isolated agent harness is available

Complete deterministic replays and interface-equivalence evidence.

Record that no model-success claim is possible.

Do not substitute self-authored payloads for an isolated trial.

## 45. Closing Directive

Be bold about the product boundary.

Be conservative about semantic authority.

Treat the SPG as a means to reliable agent programming, not as an end in itself.

Do not confuse lack of source authority with lack of useful text.

Do not confuse complete JSON schemas with good agent interfaces.

Do not confuse many passing verticals with a proved development environment.

Do not confuse smaller payloads with lower API cost.

Do not confuse a larger language with a more useful product.

Do not confuse evidence gating with permanent deferral.

Build the smallest coherent semantic workbench that survives a realistic maintenance corpus and controlled agent use.

Delete everything that does not survive.

Leave one active path.

Leave exact evidence.

Leave a repository that the next coding agent can understand with less context and modify with greater confidence than the one you inherited.
