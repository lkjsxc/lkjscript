## 1. Executive Directive

The previous campaign closed the first standalone application lifecycle.

The system can now author a typed semantic program, publish immutable workspace revisions, attach
exact application-local release cases, build one dependency-closed target-neutral application
artifact, delete the source workspace, independently validate the artifact, inspect it, test it,

That decision preserves nominal values after transfer, but it makes the artifact unsuitable as an
importable reusable release.

The repository has no independently published reusable semantic unit.

It has no explicit export surface for independent consumers.

It has no release-local nominal identity.

The central campaign question is:

> What is the smallest coherent architecture that lets independently developed lkjscript
> applications consume exact immutable reusable semantic releases, preserve nominal identity,
> rebuild and run after every producer and consumer workspace is removed, and remain compact enough
> for coding agents and maintainers to reason about—without prematurely creating a conventional
> package ecosystem?

This is not a package-feature accumulation campaign.

This is an authority, identity, composition, distribution, and deletion campaign.

The preferred result is not the largest package manager.

The preferred result is the smallest exact reusable-release model that proves its value in two real
applications and deletes the assumptions that no longer fit.

A smaller duplicated-closure architecture remains a legitimate winner if reusable release
complexity does not pay rent.

Package scaffolding that fails its representative workload must be deleted completely.

A successful campaign leaves one active composition architecture.

A failed experiment leaves no compatibility path, dormant format, unused ID domain, abandoned
resolver, or duplicate specification.

## 10. Architecture Families to Compare

### A. Duplicated application closure

- Core model: Each application embeds its own complete semantic closure and no reusable release layer exists.
- Potential strengths:
  - Minimum new identity surface
  - Simple transfer
  - No resolver
  - No cross-release references
- Primary risks:
  - Semantic duplication
  - No independent updates
  - No shared provenance
  - Repeated agent work
- Required prototype or proof: Use the same shared logic in two applications by deterministic duplication and measure total product and maintenance cost.
- Direct-cutover consequence: Delete every package/release prototype if this wins.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### B. Workspace-lineage releases

- Core model: A release preserves producer workspace identity and selected revision lineage.
- Potential strengths:
  - Straightforward nominal continuity
  - Minimal remapping
  - Easy diagnostics
- Primary risks:
  - Equivalent releases differ by history
  - Producer identity leaks
  - Fork and vendoring ambiguity
  - Poor canonical reuse
- Required prototype or proof: Build equal semantics from distinct workspaces and evaluate whether inequality is product-correct.
- Direct-cutover consequence: Delete release-local remapping if lineage is deliberately selected.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### C. Canonical release-local identity

- Core model: Release bytes remap reachable semantics into a canonical release-local namespace.
- Potential strengths:
  - Independent transfer
  - Workspace deletion
  - Canonical equality
  - Compact graph references
- Primary risks:
  - Canonicalization complexity
  - Recursive ordering
  - Identity churn
  - Diagnostic mapping
- Required prototype or proof: Produce byte-equal releases from distinct workspace histories and preserve nominal separation across releases.
- Direct-cutover consequence: Delete workspace-ID leakage and all old application readers.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### D. Definition-level content addressing

- Core model: Each semantic definition or strongly connected component is identified by domain-separated canonical content.
- Potential strengths:
  - Fine-grained reuse
  - Natural deduplication
  - History independence
- Primary risks:
  - Large identity surface
  - Hash semantics become language semantics
  - Recursive groups
  - Provenance separation
- Required prototype or proof: Model recursion, private changes, nominal types, and diagnostics without conflating content with entity authority.
- Direct-cutover consequence: Delete package-scoped ID machinery if definition hashes win.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### E. Release content digest plus release-local IDs

- Core model: The canonical release digest identifies immutable release bytes while items use release-local IDs.
- Potential strengths:
  - Simple exact dependency key
  - Compact item references
  - Clear transfer unit
- Primary risks:
  - Digest collision contract
  - Potential overloading of digest meaning
  - Whole-release churn
- Required prototype or proof: Keep provenance, coordinate, signature, authorization, and user version separate.
- Direct-cutover consequence: Delete assigned release IDs if the digest is deliberately exact release identity.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### F. Assigned release identity plus content digest

- Core model: Publication assigns a release identity and separately records canonical content digest.
- Potential strengths:
  - Lineage and attribution flexibility
  - Content equality can remain separate
- Primary risks:
  - Allocator authority
  - Equivalent content duplication
  - Publication state
  - Harder offline reconstruction
- Required prototype or proof: Demonstrate why assigned continuity is consumed by a real product operation.
- Direct-cutover consequence: Delete the allocator if no continuity consumer exists.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### G. Deterministic vendoring into consumer workspace

- Core model: Release content is imported and remapped into each consumer workspace before application build.
- Potential strengths:
  - Existing workspace tools may remain primary
  - Consumer can inspect local semantics
- Primary risks:
  - Copy identity
  - Update ambiguity
  - Workspace mutation
  - Loss of exact shared graph
- Required prototype or proof: Define copy, fork, update, conflict, and nominal behavior exactly.
- Direct-cutover consequence: Delete live external-release references if vendoring wins.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### H. External exact release graph

- Core model: Consumer workspaces refer to immutable external releases without importing their declarations.
- Potential strengths:
  - Exact reuse
  - Clear authority boundaries
  - Diamond sharing
- Primary risks:
  - Cross-authority references
  - Context complexity
  - Graph-wide validation
- Required prototype or proof: Author, type-check, inspect, test, compile, and diagnose across release boundaries.
- Direct-cutover consequence: Delete vendoring and copied declarations if this wins.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### I. Application-time graph flattening

- Core model: Reusable releases remain distinct until application build, then canonical flattening creates one run closure.
- Potential strengths:
  - Simple runtime
  - Release graph remains inspectable
  - No runtime resolver
- Primary risks:
  - Flattening may erase nominal boundaries
  - Duplicate versions
  - Origin diagnostics
- Required prototype or proof: Preserve exact semantic identity and diagnostics through private flattening.
- Direct-cutover consequence: Delete distributed flattened identities from semantic authority.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### J. Bundled graph application artifact

- Core model: An application artifact contains a manifest and exact embedded reusable release artifacts.
- Potential strengths:
  - Single-file transfer
  - Independent verification
  - Graph inspection
- Primary risks:
  - Duplicate bytes across applications
  - Nested format complexity
  - Aggregate limits
- Required prototype or proof: Validate each release once, deduplicate exact diamonds, and maintain canonical bundle bytes.
- Direct-cutover consequence: Delete external store dependence for execution if the bundle wins.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

### K. Manifest plus external immutable store

- Core model: Application artifacts name exact releases and execution resolves them from an explicit immutable store.
- Potential strengths:
  - Cross-application deduplication
  - Smaller application manifests
- Primary risks:
  - Multi-file deployment
  - Store availability
  - Hidden mutable state
  - Recovery
- Required prototype or proof: Remove mutable indexes and reconstruct solely from verified content.
- Direct-cutover consequence: Delete bundled duplicate bytes if the store clearly wins.
- Selection rule: judge the complete two-application workload, not an isolated encoding microbenchmark.

The default answer should keep reusable release and application as distinct authority domains.

A reusable release owns exports and exact dependencies.

An application owns entry, invocation profile, execution policy, and application release cases.

A combined artifact is acceptable only if the semantic distinction remains explicit and one field

### 12.1 Closure algorithm requirements

- Start from explicit exports and selected release tests.
- Traverse semantic dependencies through typed references.
- Include nominal declarations required by public signatures.
- Include private implementation required by reachable exported behavior.
- Include dependency release bindings required by cross-release references.
- Reject references outside the allowed release and exact dependency graph.
- Reject reachable holes or incomplete semantics.
- Exclude unrelated packages, modules, declarations, functions, tests, aliases, and history.
- Be iterative for user-scalable graphs.
- Bound nodes, edges, exports, tests, depth, bytes, and aggregate work.
- Produce canonical order independent of map insertion order.
- Share one owner with application closure when semantics are identical.
- Do not duplicate subtly different closure algorithms.
- Provide a differential or reference implementation for complex canonicalization.

## 13. Identity Re-foundation

The reusable-release campaign cannot succeed by reusing workspace identity unchanged.

Application artifact version 1 deliberately retained workspace identity because it represented one
run-only closure from one exact workspace revision. Independently reusable releases have a
different continuity problem:

- two workspaces may independently produce byte-identical release meaning;
- one workspace may produce two incompatible releases under one human coordinate;
- one application may use two releases of the same coordinate simultaneously;
- two dependency paths may converge on one exact release;
- two structurally identical nominal types from different releases must remain distinct;
- copying, vendoring, importing, or rebuilding must not silently change nominal meaning; and
- a workspace allocator's serial history must not leak into transferable release identity.

Design identity from those observations, not from the current `EntityId` encoding.

### 13.2 Canonical release-local identity hypothesis

The default hypothesis is that release items receive canonical release-local identity during
release construction.

This hypothesis separates workspace editing continuity from transferable release meaning.

A serious implementation should perform an explicit projection:

1. select the exact workspace revision;
2. select the reusable unit root;
3. select the explicit export set;
4. select exact dependency bindings;
5. discover the complete release closure;
6. validate closure completeness and visibility;
7. partition local and cross-release references;
8. erase workspace-only history and allocator facts;
9. compute canonical structural descriptors;
10. resolve strongly connected semantic components deterministically;
11. assign compact release-local IDs in canonical order;
12. rewrite all local references to release-local IDs;
13. rewrite cross-release references to exact dependency release plus exported target;
14. validate the projected release model independently;
15. encode canonical bytes;
16. decode from bytes as untrusted input;
17. reconstruct the same validated release model;
18. require exact re-encoding;
19. compute the domain-separated release digest; and
20. expose only the minimum identity facts needed by consumers.

The projection must not depend on map insertion order, allocator history, workspace ID, revision
number, source path, proposal order, field order in input, transient aliases, compiler traversal
order, host endianness, pointer values, runtime handles, or nondeterministic hash iteration.

### 13.4 Nominal identity rules

1. A nominal declaration from release A is not equal to a structurally identical declaration from release B.
2. Two references to the same exact release-local nominal item are equal regardless of dependency path.
3. A diamond graph must not duplicate nominal identity when both paths bind the same exact release.
4. Two exact releases under one coordinate may coexist without accidental unification.
5. A release rebuild that produces identical canonical content should produce the same content digest.
6. Whether identical canonical content also means the same `ReleaseId` must be a deliberate contract.
7. A user-facing version string never establishes nominal equality.
8. A coordinate never establishes nominal equality.
9. A dependency alias never establishes nominal equality.
10. A local immutable store path never establishes nominal equality.
11. An application-local dense remap never changes public nominal equality.
12. Compiler and runtime tags must be derived from exact semantic identity, not assigned globally.
13. A release import into a workspace must not silently turn foreign nominal identity into local nominal identity.
14. A fork must state whether it preserves no release identity, preserves lineage metadata only, or creates a new release.
15. Vendoring must not silently collapse distinct releases.

### 13.5 Content digest versus release identity

Do not leave the relationship between release content and release identity implicit.

Compare at least these contracts:

- `ReleaseId == domain-separated digest of canonical release bytes`;
- assigned opaque `ReleaseId` plus independent content digest;
- coordinate/version plus content digest as a compound exact identity;
- manifest digest as release identity, with semantic payload digests beneath it; and
- graph root digest as exact release identity.

For each candidate, analyze:

- deterministic rebuild across unrelated workspaces;
- deliberate republishing of identical content;
- provenance variation;
- signature variation;
- metadata variation;
- yanking or revocation metadata;
- mirror and cache behavior;
- collision assumptions;
- offline verification;
- human usability;
- nominal identity;
- dependency lock stability;
- and future registry federation.

The default preference is a domain-separated content-derived exact identity if, and only if, the
complete semantic release contract is immutable, canonical, independently validated, and explicit
about which metadata is identity-bearing.

Do not hash unstable workspace identity and then call the result reproducible.

### 13.6 Strongly connected semantic identity

Recursive semantic graphs make naive bottom-up hashing insufficient.

If release-local IDs are assigned canonically, define how mutually recursive functions, nominal
types, and mixed declaration groups are ordered.

Serious candidates include:

- canonical strongly connected component decomposition;
- stable partition refinement over typed labeled edges;
- deterministic graph canonicalization within bounded components;
- explicit declaration-group identity in accepted semantics;
- and rejecting unsupported recursive shapes until a proof exists.

Do not adopt a general graph-isomorphism subsystem without a representative need.

A release canonicalizer may preserve semantically meaningful declaration order when the language
defines such order. It may not preserve arbitrary workspace insertion order merely because that is
easier.

Document worst-case work and bound it before allocation.

### 15.2 Dependency binding requirements

1. Every dependency slot has one canonical local role.
2. Every dependency slot binds one exact immutable release identity.
3. Duplicate slots reject.
4. Duplicate exact releases under different slots are either canonicalized or deliberately preserved with stated semantics.
5. Cross-release references name a dependency slot and an exported target.
6. References cannot escape to transitive dependencies unless explicitly re-exported or directly bound.
7. Dependency order is canonical.
8. The dependency graph is acyclic for the first implementation unless recursive release groups are explicitly proven necessary.
9. Cycles reject before unbounded traversal or allocation.
10. Missing dependencies produce a stable exact error.
11. A dependency with matching coordinate but wrong exact identity rejects.
12. A dependency with matching digest but wrong identity-domain tag rejects.
13. A dependency with valid bytes but invalid semantic closure rejects.
14. A dependency graph with two byte encodings of one logical graph rejects through canonical re-encoding.
15. The graph is bounded in nodes, edges, depth, total bytes, exports, and aggregate semantic items.
16. One exact release reached through a diamond is loaded and validated once per graph operation when safe.
17. Graph deduplication must not merge distinct exact releases.
18. Application build never consults mutable latest state after the exact graph is selected.
19. Offline rebuild consumes only exact immutable releases already provided or bundled.
20. Dependency identity is included in release and application integrity calculations.

9. A dependency graph binds exact releases before execution.
10. Application execution does not consult mutable resolution metadata.
11. No ambient host authority is granted by importing a release.
12. Release code remains pure under the current language.
13. A process boundary remains not a sandbox.
14. Denial-of-service limits are separate from semantic validity.

### 31.3 Signatures and provenance deferral

- trust roots;
- threshold policy;
- replay;
- timestamp semantics;
- revocation;
- yanking;
- transparency or equivocation detection;
- mirror behavior;
- offline verification;
- and failure classes.

Until then, report signatures and publisher authentication as absent.

### 43.12 Documentation language

Prefer precise terms:

- `exact dependency` for a bound immutable release;
- `application closure` for one runnable exact graph;
- `proposal` for editable text or JSON submitted for validation;
- `semantic authority` for the accepted typed model;
- `derived executable` for Core IR, bytecode, or native output;
- and `offline proof` for the explicit no-workspace/no-network lifecycle.

Avoid vague terms such as `source-free`, `package-like`, `portable` without a platform scope,
`secure` without a threat model, `verified` without naming the verifier, and `zero-cost` without a
measurement.

## 46. Final Doctrine

Build one coherent reusable semantic composition architecture.

Do not preserve workspace identity merely because it already exists.

Do not make content addressing universal merely because it appears elegant.

Do not build a registry merely because reusable releases exist.

Do not create a package manager before exact local composition works.

Do not keep duplicated application closure if exact reuse clearly pays for itself.

Do not keep a reuse layer if duplication remains the smaller and more reliable product.

Do not let human coordinates, user versions, aliases, paths, hashes, compiler IDs, or runtime
handles drift into semantic identity without an explicit contract.

Do not add compatibility scaffolding.

Do not retain losing prototypes.

Do not confuse more infrastructure with more capability.

The campaign succeeds when two independently authored applications share one independently
published semantic release through exact bounded interfaces, multiple exact versions and a diamond
remain correct, every source workspace can disappear, the complete workflow works offline from
immutable content, and the resulting repository is simpler to reason about than the alternatives it
rejected.
