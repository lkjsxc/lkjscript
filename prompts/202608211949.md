## 0. Executive mandate

Transform `lkjscript` from a semantic platform whose strongest proof is `lkjedit` into a genuinely
general-purpose language and application platform. The result must make materially different
applications natural to author, package, run, test, deploy, and evolve.

Do not begin from the assumption that the current architecture is excessively editor-shaped.
Investigate that hypothesis. Preserve current mechanisms that are already topology-neutral,
capability-oriented, exact, and efficient. Replace current mechanisms that encode the accidental
shape of `lkjedit`, `lkjwork`, or the sequence of earlier campaigns.

Use the future ability to implement the base capabilities of `kjxlkj` without application-specific
Rust as the principal new forcing function. Do not add `kjxlkj`-specific primitives, routes, tables,
roles, resource kinds, media rules, or UI concepts to the language or runtime.

Translate every discovered blocker into a general language feature, reusable library, component
contract, runtime capability, adapter, deployment mechanism, or tooling improvement that remains
natural for unrelated applications.

The target is not to port all of `kjxlkj` immediately by copying its Rust architecture. The target
is to make a serious, complete service application possible in lkjscript alone above generic native
adapters, and to prove that architecture through an ordinary maintained service vertical.

Existing `lkjedit` and `lkjwork` are secondary regression consumers. Migrate them to the selected
general model when retained, or delete superseded product and adapter paths if their user value no
longer justifies them. Do not let either dictate the universal application model.

## 5. Generalization rule

For each proposed universal feature, identify at least two materially different consumers or one
independently standardized external contract plus one complete consumer. Examples include an
interactive editor, a multi-user HTTP service, a durable queue worker, a batch transformation, and
the semantic development toolchain itself.

- If a capability is useful only for `lkjedit`, keep it in an interactive or editor library.
- If a capability is useful only for the selected service application, keep its policy in that
  application.
- If a capability adapts a broadly standardized external system such as HTTP, PostgreSQL,
  S3-compatible storage, clocks, secure randomness, or terminal I/O, a generic adapter may be
  justified with one complete consumer and independent conformance tests.
- If two consumers need similar behavior but disagree on semantics, do not force them through one
  vague abstraction.
- Genericity is measured by coherent ownership and reuse, not by removing names.

## 6. Minimum no-application-specific-Rust rule

application-specific Rust for routes, domain state, validation, authorization, SQL choice,
transactions, response construction, HTML structure, job state machines, retry policy, or tests.

### 9.1 Development authority and public CLI

- The repository describes `lkjscript` as a meaning-first semantic software platform.
- One discoverable semantic project currently owns one validated typed meaning graph, immutable full
  development snapshots, canonical revision records, and a first-class target graph.
- The public CLI supports project initialization, discovery, orientation, status, semantic queries,
  generated proposals, task context, JSON and document validation/apply, history, diff, restoration,
  targets, doctor, backup, and a caller-owned foreground session.
- Accepted mutations publish exactly one immutable revision and record. Validation, rejection, stale
  input, semantic no-change, and reads publish nothing.
- A semantic document is currently a proposal rather than a second maintained source.
- Raw engine RPC remains a conformance or embedding surface rather than the ordinary project
  workflow.
- Build targets currently lower accepted graph meaning into reusable releases, applications, and
  native products.

These are strong authority and publication properties. Preserve them only in the form that remains
compatible with the selected authored representation and general application model.

### 9.2 Current language

- The closed value set is unit, bool, checked signed i64, immutable bytes, immutable UTF-8 text,
  nominal immutable products, nominal immutable sums, and nominal immutable homogeneous sequences.
- The operation set includes constants, small integer and boolean operations, direct calls, lazy
  conditional, counted loops, nominal construction and matching, bytes, text, sequences, holes,
  return, and yield.
- There is no map, set, iterator, higher-order collection operation, mutable builder, operator
  overloading, implicit coercion, general effect, live resource, time, randomness, filesystem,
  network, process, signal, or concurrency primitive.
- Evaluation is deterministic and pure. Host work is represented outside language evaluation.
- The explicit-frame interpreter is the correctness and only execution route.
- Bytes, text, and sequences use managed immutable representations with independent canonical
  oracles.
- Text uses an unobservable persistent UTF-8 piece treap with byte, scalar, newline, and disposable
  grapheme support.

This small closed language has proven durable and interactive state machines, but it may impose
excessive verbosity, weak reuse, and awkward effect orchestration for large service applications.
Measure rather than assume.

### 9.3 Current application worlds

- Application contract 8 and internal format 9 embed an exact release graph, one entry, one closed
  invocation profile, one run policy, and immutable cases.
- The profile set is typed, bytes stream, stateful, and interactive.
- Stateful applications use mutation, resume, and pure-query functions with a decision that may
  decline, remain unchanged, complete, or suspend with one command.
- Interactive applications use initialize, update, resume, and render roles over ephemeral
  foreground state.
- The interactive action vocabulary currently names semantic-project and selected-filesystem
  operations directly.
- The interactive runner executes at most one host action at a time through one bounded worker.
- The only retained application import interface in the general application artifact is
  `immutable_blob_v1`.
- Artifacts contain requirements but not grants, paths, secrets, live resources, or deployment
  state.

The separation between application meaning and deployment grants is valuable. The closed profile
set, one-command suspension, and interactive action vocabulary are leading candidates for
generalization because they encode current product shapes.

### 9.4 Current runtime kernel

- Runtime contract 2 is explicitly synchronous and topology-neutral only across one-shot, durable
  foreground session, and ephemeral interactive foreground session.
- It admits one active transition, one active host operation, one compilation, one loaded
  application, and one open instance store.
- It has no queue, resident supervisor, general worker pool, request multiplexing, persistent
  compiled cache, bytecode, JIT, or native tier.
- The interactive product has one foreground thread and one capacity-one host worker.
- Runtime observations separate many stages and explicitly report absent acceleration.
- The kernel does not own semantic application meaning or durable instance state.

This design is deliberately simple and exact. A resident concurrent service cannot be treated as a
small flag on this topology; task ownership, admission, cancellation, streams, pools, shutdown, and
grants need a complete contract.

- The only maintained first-party applications are `lkjedit` and `lkjwork`.
- `lkjedit` is a Vim-like terminal editor whose application meaning owns modes, buffers, views,

- `lkjwork` is a durable local work ledger whose application meaning owns task policy and queries.

least privilege, reaches a credible long-term performance path, and reduces repeated agent work.

Do not optimize for preservation of the current graph, preservation of textual source, preservation

maximum immediate feature count. Optimize the complete system.

its product coupling. When the evidence favors replacement, cut over directly and delete the old
path. When evidence remains insufficient, build the smallest bounded prototype that can decide the
question and do not expose a dormant public contract.

run a useful request-driven service and the retained interactive and durable consumers through one
coherent current language and application platform, without application-specific Rust business
