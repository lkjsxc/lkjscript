## 0. Executive mandate

Transform lkjscript into a canonical typed meaning-graph language and application platform whose
public semantic CLI is the normal development environment. The graph owns accepted program meaning.
Text may exist only as deterministic projection, review surface, diagnostic excerpt, new-authority
import, recovery form, or independent oracle. Text must not be a second editable truth or the normal
mutation path.

Do not restore the predecessor graph architecture mechanically. That system proved valuable semantic
publication properties but exposed graph-sized payloads, expensive whole-project operations, large
context bundles, and product-shaped machinery. The new graph must be logically rich and physically
compact, locally loadable, revisioned, indexed, incrementally validated, semantically diffable and
mergeable, and changed through high-level transactions.

Preserve and improve the strongest current results: reusable packages, one component model, typed
capability requirements and grants, prepared bytecode with an independent AST oracle, bounded
resident HTTP and worker runtimes, PostgreSQL, streams, object storage, queues, configuration,
secrets, clocks, randomness, identifiers, password hashing, deterministic test adapters, and the
maintained lkjournal service.

Prove that meaning-graph development is better than text-first development on equal complete tasks.
Superiority means exact selection, safe refactoring, smaller task context, fewer corrections, stable
identity continuity, deterministic transactions, useful impact analysis, strong merge semantics, and
competitive end-to-end latency, storage, build, test, and review behavior. It does not require
winning every microbenchmark.

Long-term performance is a first-class objective. Design graph storage, indexes, incremental
computation, compiler handoff, runtime representations, and query protocols so large packages do not
require architectural replacement. Preserve simple independent oracles so aggressive optimization
remains trustworthy.

Reduce coding-agent API expense where evidence permits. Keep permanent instructions compact, avoid
repeated schema and repository dumps, make successful verification quiet, retain bounded complete
logs outside model context, provide exact task-scoped semantic context, and measure provider usage
when available. Never infer tokens or money from bytes alone.

## 5. Meaning graph definition

The meaning graph is the logical canonical representation of accepted program meaning. It is not
defined by a storage engine, serialization, visual editor, or public graph mechanics. It may be
represented physically by packed tables, immutable segments, arenas, indexes, an embedded database,
memory maps, content-addressed shards, or another measured design.

- Semantic owners and relations represent program meaning rather than lexical trivia by default.
- Stable identity is explicit and independent from physical position and content digest.
- The graph contains enough information to validate, compile, render, diff, merge, export, and
  reconstruct without maintained source.
- Semantically retained documentation and annotations have explicit owners and identity rules.
- Derived types, closures, impacts, IR, bytecode, indexes, and caches are not authority unless
  deliberately selected and justified.
- Every accepted revision has one canonical root and exact graph contract identity.
- Every persisted object has domain-separated integrity protection.
- Deep reconstruction ignores disposable indexes and produces equivalent validated meaning.


## 6. Central architectural correction

The previous campaign selected text because the predecessor graph exposed costly, large, and
difficult authoring payloads. That evidence is real. It does not prove text must own meaning. It
proves a canonical graph needs a better physical model and higher-level semantic CLI.

Separate five questions: what owns accepted meaning; how it is stored; how it is queried and
changed; how it is rendered for review; and how it lowers to executable artifacts. The mandated
answer to the first is the typed semantic graph. Select the other answers by evidence.

A packed binary store and JSON CLI can coexist. A semantic graph and deterministic text projection
can coexist. Stable semantic IDs and Git transport can coexist. Do not make one physical format
carry every architectural responsibility.

## 12. Identity architecture

The graph exists to preserve and manipulate meaning, so identity mistakes are architectural defects.
Do not continue the rule that a declaration is identified only by package, module name, and
declaration name.

- Introduce opaque stable semantic ID domains for owners that need continuity.
- Keep package, module, declaration, field, case, parameter, binding, expression site, port,
  operation, test, and revision domains distinct where lifecycles differ.
- Do not allocate stable IDs for disposable compiler temporaries or cheaply derived relations.
- Keep human names mutable and separately indexed.
- Keep content digests deterministic and separate from stable IDs.
- Keep physical object keys and dense arena indexes private and disposable.
- Specify random, namespaced counter, branch-local, or another allocation and prove offline
  collision behavior.
- Provide deterministic allocation in tests without conflating it with production allocation.
- Never reuse a deleted stable ID.
- Represent rename and move as continuity-preserving transactions.
- Represent clone, copy, extract, and import as explicit identity creation.
- Retain identity provenance sufficient for history without personal data.
- Return full IDs in durable receipts and optional short session handles in bounded interaction.
- Reject cross-domain substitution even if bytes are identical.

## 13. Accepted revisions, drafts, and publication

Accepted revisions must remain exact and independently recoverable. Multi-step agent work needs a
separate draft mechanism rather than invalid accepted graphs.


### 13.1 Accepted revision invariants

- One exact canonical graph root and one exact graph contract.
- Explicit parent relation under the selected history topology.
- All references resolve in the exact package closure.
- All type, effect, capability, component, target, test, and resource invariants validate.
- No unresolved hole or conflict remains.
- The revision can be rendered, compiled, deep-validated, backed up, and restored independently.
- Publication is atomic and crash-consistent.
- Validation, rejection, stale base, no-change, and reads publish nothing.


### 13.2 Draft invariants

- A draft names its accepted base exactly.
- A draft is non-executable and non-deployable.
- Holes, unresolved references, ambiguous choices, and conflicts use closed representations.
- Every draft mutation is bounded, deterministic, and recorded.
- Incremental diagnostics reproduce under full draft validation.
- Draft persistence and sharing require an explicit retention and security policy.
- Draft IDs never masquerade as accepted revisions.
- Publishing validates the whole result against the current exact base or performs explicit rebase
  or merge.
- Discarding a draft cannot affect accepted authority.
- Draft compaction and expiry cannot remove accepted history.


### 13.3 Publication outcome matrix

- `accepted_change`: publish one revision and one compact receipt.
- `semantic_no_change`: publish nothing and report exact equivalence.
- `stale_base`: publish nothing and return bounded rebase or diff handles.
- `invalid_graph`: publish nothing and return bounded diagnostics.
- `unresolved_draft`: publish nothing and identify holes or conflicts.
- `precondition_failed`: publish nothing and identify the exact predicate.
- `ambiguous_selection`: publish nothing and return bounded candidates.
- `foreign_identity`: publish nothing and identify the expected domain.
- `resource_exhausted`: publish nothing and identify the exhausted budget.
- `corrupt_authority`: admit no write and require reconstruction or repair.
- `infrastructure_failure_before_commit`: publish nothing and retain recovery evidence.
- `visibility_indeterminate`: block retry until HEAD and receipt state are reconciled.

## 15. Incremental semantic engine

The canonical graph should make precise incremental work possible. Incremental results are
acceleration; preserve a full semantic oracle.

- Define an exact dependency key for every derived fact.
- Invalidate by stable semantic identity and relation, not source timestamps.
- Separate projection changes from semantic changes.
- Cache parsing only for explicit import inputs, never canonical meaning.
- Incrementally validate names, scopes, types, effects, capabilities, components, targets, tests,
  and package closure.
- Incrementally lower changed reachable owners while preserving deterministic full-build
  equivalence.
- Maintain reverse indexes for references, calls, types, capabilities, exports, tests, and
  artifacts.
- Represent broad invalidation explicitly and measure it.
- Use revision keys to prevent stale facts crossing accepted revisions.
- Make index rebuild and cache miss correct and observable.
- Compare incremental and full validation for every transaction class.
- Fuzz operation sequences and compare with reconstruction from canonical roots.


## 16. Semantic transaction protocol

One public semantic transaction protocol is the sole normal writer of program meaning. It must serve
the CLI, tests, a future workbench, and other tools without embedding Rust internals.

- Request: graph contract, authority identity, exact base revision, optional draft, idempotency key,
  ordered operations, preconditions, budgets, nonsemantic intent metadata, validation profile, and
  requested result projection.
- Result: closed status, observed base and current revision, published revision when accepted,
  semantic diff digest, affected owners, operation results, bounded diagnostics, receipt locator,
  and expansion handles.
- Do not repeat full graphs, schemas, environments, or passing-test lists.
- Transactions are deterministic under exact inputs.
- Stale base, failed precondition, ambiguity, foreign identity, exhaustion, conflict, no-change,
  invalid meaning, corruption, and infrastructure failure remain distinct.

## 17. Semantic query model

Queries must be declarative, revision-pinned, bounded, selective, deterministic, and independently
checkable. A query is not authority and may be cached only under every exact input.

- Select by stable ID, exact name and owner, kind, package, module, annotation, type, capability,
  target, test, or revision.
- Traverse ownership, references, calls, types, constructors, matches, requirements, composition,
  dependencies, tests, and history.
- Project only requested fields and derived facts.
- Order deterministically under an explicit key.
- Require item, byte, depth, fanout, work, and elapsed budgets.
- Return continuation handles bound to revision, query, order, and cursor.
- Represent truncation explicitly rather than silently omitting data.
- Explain why each context item is included when building agent context.
- Keep query syntax closed and versioned; do not embed arbitrary host scripting.
- Provide an independent slow query oracle.
- Return index and work diagnostics only on explicit request or in retained evidence.


### 17.1 Query result stability

- Name the exact observed revision.
- Return stable IDs even when names change.
- Omit empty fields and repeated schema descriptions.
- Expand large bodies, expression trees, docs, and histories explicitly.
- Keep session-local short handles non-authoritative and revision-scoped.
- Sort independently of hash-map or physical storage order.
- Distinguish failure, no match, ambiguity, truncation, stale handle, and corruption.


## 18. Public semantic CLI

The public CLI must be the complete ordinary development surface for Codex CLI, other agents, and
humans. An agent must not emit raw graph storage or know Rust enum layouts.

- One discoverable command grammar and machine-readable help.
- Strict machine mode with one bounded JSON value for ordinary commands and JSONL only for explicit
  streams.
- Optional concise human rendering mechanically derived from the same result.
- Schema digest returned once or on request rather than repeated full schemas.
- Explicit select, limit, byte budget, depth, fanout, and continuation controls.
- Exact revision pinning and stale rejection on mutations.
- No default stack traces, child logs, complete tests, schemas, or graph dumps.
- Stable diagnostic codes, owner IDs, semantic sites, compact messages, and expansion handles.
- Exit classes for success, rejection, stale input, failed verification, unavailable dependency,
  exhaustion, and infrastructure failure.
- Stateless correctness; an optional daemon may accelerate but never own meaning.
- Tested byte and item bounds for every command.

## 27. Migration and direct cutover

source and new graph forms only inside a bounded verification bridge. The completed normal tree has
one graph authority.


### 27.1 Migration sequence

1. Freeze and reproduce the current source baseline and artifacts.
2. Implement graph schema, repository, deep validator, and public read-only semantic CLI.
3. Implement a one-time current-source importer producing canonical graph authority and a migration
   receipt.
4. Import packages/standard and compare semantic model, tests, and artifacts through independent
   paths.
5. Import applications/lkjournal and compare package tests, component contracts, artifacts, and live
   acceptance.
6. Implement public graph mutations and perform real post-import changes through semantic CLI.
7. Switch package build, test, component inspect, target run, service, worker, and deployment
   preparation to graph authority.
8. Switch orientation, query, diagnostics, history, diff, backup, restore, and doctor to graph
   authority.
9. Generate deterministic review projections and update docs.
10. Delete maintained .lkj files and .lkjscript/source-v1 objects.
11. Delete source apply, formatting-only history, source-based identity, workspace source authority,
    and ordinary parse-based build paths.
12. Keep text import only with an independently justified new-authority or disaster-recovery
    consumer.
13. Reject predecessor source and graph formats exactly.

  current plus large-fixture gates pass.

  exceeds its gate.

  transaction robustness.
- Revisit short handles if stale errors or protocol complexity exceed measured token savings.
- Retain a daemon only while stateless correctness is complete and warm latency improves materially.
- Retain pass discovery only while every input is bound and final verification remains fresh.
- Retain text recovery import only while its independent value exceeds grammar and security cost.
- Retain bytecode while it agrees with the oracle and improves complete workloads.
- Revisit specialized interpreter, AOT, or JIT only when execution is at least 30 percent of a
  maintained complete workload or a hard target requires it.
- Revisit graph granularity when context, storage, transaction, or merge evidence shows systemic
  mismatch.
