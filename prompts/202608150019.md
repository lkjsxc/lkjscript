## 3. Audited Baseline

The audited repository already contains one Rust package and one source-free product path:

```text
strict generic JSON projection
    -> private closed binary protocol v2 over a Unix socket
    -> synchronous lkjscriptd
    -> daemon-owned durable workspace
    -> staged typed transaction
    -> immutable Semantic Program Graph snapshot
    -> revision-bound scan query or direct lowering
    -> private verified scalar Core IR
    -> scalar interpreter
    -> typed response
```

The audited Semantic Program Graph contains workspace root, package, module, function,
function parameter, region, block, and operation nodes. A function may own a region. A
region contains exactly one block. A block contains ordered operations and one terminator. A
value is a function parameter or an operation result.

The audited executable language contains only `unit`, `bool`, and `i64`; `const_i64`,
`const_bool`, checked `add_i64`, a typed expression `hole`, and `return`. Entry invocation
accepts no parameters. The private Core IR permits one function and exactly one block.

The audited product already proves important invariants that this campaign must preserve or
deliberately replace with stronger equivalents:

- the daemon is the only live writer of durable graph state;
- snapshots are immutable, revision-labelled, and content-hashed;
- persistent Node IDs are workspace-scoped, monotonic, stable, and never reused;
- rejected and validate-only transactions consume no persistent identities;
- deletion tombstones identity and old snapshots remain queryable;
- a typed hole can be refined without identity churn;
- mutation receipts are compact and explicitly bounded;
- full semantic diffs are revision-bound and paginated;
- queries provide owner chains, body slices, visible values, incoming uses, dependencies,
  legal constructors, and repair contexts;
- strict generic JSON covers the complete public request vocabulary;
- unknown fields, unknown variants, malformed IDs, trailing values, and oversized inputs
  reject;
- canonical artifacts and durable HEAD records are corruption checked;
- durable publication is ordered, preflighted, and failure-injected;
- the compiler consumes the SPG directly and has one private Core IR route;
- the interpreter verifies Core IR before execution;
- user-scalable graph traversals avoid unbounded native recursion;
- the real daemon and real generic CLI are exercised by integration tests;

Do not weaken those properties to make structured-control implementation easier.

## 4. Concrete Problems in the Audited Product

### 4.1 The Language Cannot Express a Useful Structured Program

The current scalar kernel cannot call another function, branch on a runtime value, iterate,
invoke an entry with arguments, or express a reusable computation. A program that returns
`42` proves the storage and execution vertical but does not prove a viable programming
model.

The next semantic additions must form one useful dependency-closed set. Do not add isolated
arithmetic variants while leaving calls and control flow unusable.

### 4.2 Public Construction Mirrors Storage Scaffolding

The current JSON example requires an external agent to create package, module, function,
region, block, operations, terminator, body attachment, and package entry as separate
low-level operations. Structured control would multiply that scaffolding because every
conditional and loop owns nested regions and blocks.

A model should express a structured semantic body, not manually maintain canonical
containment boilerplate. Persistent graph structure remains the canonical authority, but
public creation should use one closed typed draft that deterministically expands into that
structure.

Do not solve this by introducing textual source, an untyped JSON property graph, a generic
macro language, or a second persisted AST.

### 4.3 The README Is an Internal Verification Note

The current README opens with a compressed architecture assertion, immediately presents
build and test commands, and then includes a very large raw JSON transaction for a trivial
program. It does not adequately answer what the project is, why an AI-primary programming
system is useful, how a person would employ it, why source text is not canonical, or how the
daemon, agent, snapshots, and runtime relate.

The README must become a human-first product entry point. Exact protocol catalogues and
giant request payloads belong in generated schema output, protocol documentation, and
runnable examples, not in the opening explanation.

### 4.4 Agent-Cost Evidence Is Still Indirect

The current repository measures bytes, round trips, and elapsed time but has not invoked a
controlled model and therefore makes no token or API-cost claim. Preserve that honesty. This
campaign should reduce observable interaction cost directly and record it. Do not add a
model orchestration subsystem or make speculative token claims.

### 4.5 The Private Core IR Is a Scalar Single-Block Bootstrap

The current Core IR cannot represent calls, multiple functions, branches, block parameters,
or loop backedges. Structured SPG operations must lower through one stronger private IR
rather than being interpreted directly as a second language path.

### 4.6 The Interpreter Relies on a Trivial Execution Shape

The current interpreter executes one block and has no explicit call stack, branch transfer,
block-argument binding, or fuel accounting. Adding recursive calls through native Rust
recursion would violate the repository stack-safety direction. Implement explicit execution
state.

## 5. Campaign Thesis

The smallest coherent next product is a structured pure functional-imperative kernel with
one value result per operation and function, explicit typed graph identity, nested
structured regions, direct calls, and a private CFG-like Core IR.

The canonical semantic language added in this campaign is intentionally narrow:

- `const_unit` completes the existing `unit` value domain;
- `lt_i64` provides one exact dynamic predicate;
- `call` invokes a direct function identity with exact arguments;
- `if` owns two structured regions and yields one typed result;
- `for_i64` owns one structured body region, carries one typed value, and iterates an
  exclusive positive-step i64 range;
- `yield` terminates an operation-owned nested region;
- `return` continues to terminate a function-owned body region;

The private Core IR may use multiple blocks, block parameters, direct function IDs, branch
arguments, conditional branches, and calls. Those are compiler implementation details.
External agents must not author predecessor lists, phi nodes, Core IR block IDs, or compiler
value IDs.

This set is sufficient for a representative multi-function program that validates an input,
calls a helper, iterates over a range, repairs a nested accumulation hole, and returns a
deterministic result.

## 6. Mandatory Representative Program

The campaign must retain and exercise one representative semantic program through the real
generic machine interface. Conceptually, the program is:

```text
range_sum(n: i64) -> i64:
    for_i64 index from 0 to n exclusive, positive step 1, carried accumulator = 0:
        yield accumulator + index

normalize_and_sum(n: i64) -> i64:
    if n < 0:
        yield 0
    else:
        yield range_sum(n)

main() -> i64:
    return normalize_and_sum(101)
```

The initially committed revision must contain a typed `i64` hole in place of `accumulator +
index`. The loop body must yield that hole result. The snapshot is valid and queryable but
the `main` entry dependency closure is incomplete and cannot execute.

The external workflow must then:

1. create the entire package, module, three function declarations, ordered parameters,
   structured bodies, and selected entry in one committed typed transaction;
2. request only the stable bindings that the client actually needs, including the nested
   hole and functions used for direct invocation tests;
3. query one bounded repair context for the nested hole;
4. observe the exact visible loop index and carried accumulator values and the exact
   `add_i64` constructor contract;
5. submit one invalid repair that demonstrates deterministic type or scope rejection and
   publishes nothing;
6. refine the hole to `add_i64(accumulator, index)` while preserving the hole Node ID;
7. query the exact semantic diff page and verify that it reports refinement rather than
   delete/create churn;
8. run `main` and obtain `i64(5050)`;
9. run `normalize_and_sum` directly with `-3` and obtain `i64(0)`;
10. run `normalize_and_sum` directly with `11` and obtain `i64(55)`;
11. restart the daemon and repeat a retained-revision query and run with unchanged Node IDs
    and results;

The example may use different function display names only when a coherent naming convention
or existing test vocabulary strongly justifies it. Preserve the semantic workload and
expected results.

## 11. Language Semantic Contract

Update `docs/spec/language.md` to own the exact accepted semantics introduced below. The
semantic rules in this prompt are requirements. Rust type names and field names may differ
only when the resulting contract is clearer and all public descriptions remain exact.

### 11.1 Existing Types

Retain the closed semantic types `unit`, `bool`, and signed two’s-complement `i64`. There
are no implicit conversions, null values, dynamic values, casts, exceptions, generics, or
nominal data types in this campaign.

Every function has ordered parameters and exactly one result type. A result of `unit` is
still a typed result.

### 11.2 `const_unit`

Add one complete pure `const_unit` operation with no operands and one `unit` result. This
makes the existing unit type constructible through the same value model as bool and i64.

Do not introduce a special zero-operand return path solely for unit. Preserve one
value-oriented return contract.

### 11.3 `lt_i64`

Add one complete pure `lt_i64(lhs, rhs)` operation. Both operands are copied exact `i64`
values. It produces one `bool` result. It has no side effects and cannot trap.

Do not add a general comparison family as collateral. Additional comparison operations
require a later use case.

### 11.4 Direct Pure Calls

Add a complete pure direct `call` operation with one direct function-identity target and an
ordered vector of value operands.

Call validation requires:

- the target exists in the same workspace and is a function;
- argument count exactly matches parameter count;
- each argument type exactly matches the corresponding parameter type;
- each argument obeys lexical visibility, scope, order, and dominance;
- the operation has exactly one result whose type is the target function result;

Function names are never call identity. A rename must not retarget calls.

Calls may cross modules and packages within one workspace. Package dependency policy is not
introduced in this campaign.

Direct and mutual recursion are permitted. Compilation and execution must use iterative
graph traversal and an explicit execution frame stack. Do not recursively compile callees
through the native stack and do not execute calls through Rust recursion.

### 11.5 Structured `if`

Add a complete pure `if` operation with:

- one exact `bool` condition operand;
- one explicit semantic result type;
- one ordered `then` region;
- one ordered `else` region;
- one operation result of the declared result type;

Each arm region contains exactly one block in this campaign. Each arm block has no explicit
semantic block arguments. Each arm terminates with `yield(value)`, and the yielded value
type must exactly equal the `if` result type.

Exactly one arm executes. The unselected arm is not evaluated. Tests must prove laziness by
placing a deterministic trap in the unselected arm and observing successful execution.

Both arm regions may capture values that are lexically visible at the position of the owning
`if` operation. Values created inside one arm do not escape except through the `if` result
and are not visible in the sibling arm.

### 11.6 Structured `for_i64`

Add one structured counted loop operation named `for_i64` or a clearer equivalent stable
machine name. Its accepted semantics are fixed by this section.

The operation has:

- one `i64` start operand, evaluated once before the loop;
- one `i64` end-exclusive operand, evaluated once before the loop;
- one positive nonzero `i64` step literal stored in the operation payload;
- one initial carried-value operand;
- one explicit carried semantic type equal to the initial value type;
- one body region;
- one operation result equal to the carried type;

The step is a literal rather than a runtime value in this campaign. Validation rejects zero
or negative step values. Do not silently normalize them.

The body region contains exactly one block with exactly two ordered block arguments:

- argument zero is the current loop index and has type `i64`;
- argument one is the current carried value and has the declared carried type;

The body block terminates with `yield(next_carried)`, whose type exactly equals the carried
type.

Execution semantics are:

```text
index = start
carried = initial
while index < end_exclusive:
    carried = execute_body(index, carried)
    index = checked_add_i64(index, step)
result = carried
```

If `start >= end_exclusive`, the body executes zero times and the result is the initial
carried value. Index increment overflow is a structured runtime trap attributed to the
`for_i64` operation. The body may capture values visible at the owning operation position.

There is no break, continue, reverse iteration, dynamic step, multi-value carry, or early
return from the loop in this campaign. This operation is a deliberately useful first
structured loop, not a disguised universal control-flow system.

### 11.7 Nested-Region `yield`

Add a `yield` terminator for operation-owned regions. `yield` has one value operand and no
result. It is valid only as the unique terminator of a region whose owning structured
operation expects a yielded value.

A `yield` under an `if` arm must match the `if` result type. A `yield` under a `for_i64`
body must match the carried type. `yield` is invalid in a function-owned body region.

### 11.8 Function `return`

Retain `return(value)` as the unique terminator of a function-owned body region. Its operand
must exactly match the function result type. `return` is invalid in an operation-owned
nested region.

### 11.9 Runtime Values and Entry Arguments

Retain exact runtime values `unit`, `bool`, and `i64`. Extend `Run` so the request carries
an ordered bounded vector of runtime arguments.

Run validation requires the selected entry to be a function, argument count to match
exactly, and each runtime value type to match the corresponding parameter type. A
zero-parameter entry remains a valid empty argument vector.

Run arguments are invocation data, not persisted semantic state.

### 11.10 Arithmetic and Trap Semantics

Retain checked i64 addition. Overflow remains a structured runtime trap attributed to the
semantic origin operation.

Loop index increment is also checked and traps at the loop origin. Comparison, constants,
branch selection, and direct calls do not trap except through execution of their selected
body or callee.

### 11.11 Recursive Calls and Resource Semantics

Recursion is semantically valid. Resource exhaustion is operational policy, not a type or
graph validity rule.

Execution must use explicit bounded fuel. Fuel accounting must be deterministic for the same
verified Core IR and run policy. Decrement fuel at a documented unit such as each
instruction and terminator transfer. Do not let optimizer changes silently alter a public
semantic fuel promise; treat the current fuel model as runtime policy and document it as
such.

Execution must use an explicit heap-backed frame vector or equivalent. A frame limit may
protect the host. Exhaustion returns a structured resource error or trap and must not panic,
overflow the native stack, or corrupt daemon state.

Do not add tail-call optimization in this campaign unless it emerges as a tiny verified
simplification. It is not an acceptance condition.

## 12. Semantic Program Graph Changes

Update `docs/spec/semantic-graph.md`, the code-owned schema, artifact codec, graph
validation, diff logic, queries, and machine schema together. There must be one active
semantic shape.

### 12.1 Block Arguments

Add one closed node kind for a semantic block argument. Prefer the stable public term
`block_argument` unless an existing naming rule makes `block_parameter` materially clearer.

A block argument has:

- one block owner;
- one dense zero-based ordinal;
- one exact semantic type;
- no mutable name requirement unless a presentation name has a demonstrated agent-facing
  use;

Do not reuse function parameter nodes with ambiguous owner semantics. Function parameters
and block arguments are distinct semantic roles and distinct value-reference variants.

### 12.2 Block Shape

Extend a block to own ordered block arguments before ordered regular operations and one
unique terminator. Block arguments are semantic definitions available throughout that block
and descendant nested regions according to lexical visibility rules.

Function-body blocks have no block arguments in this campaign. `if` arm blocks have no block
arguments. `for_i64` body blocks have exactly the two arguments defined above.

### 12.3 Operation-Owned Regions

Extend operation nodes to own an ordered list of nested regions or equivalent explicit
closed region slots. The operation descriptor, not arbitrary graph data, owns the exact
region count, role names, block-argument contracts, and terminator contract.

The schema must distinguish:

- no-region operations such as constants, arithmetic, comparison, call, hole, return, and
  yield;
- the two ordered `then` and `else` regions of `if`;
- the one ordered body region of `for_i64`;

Do not add arbitrary string-labelled region slots or a runtime registry. Closed enums and
static descriptors are sufficient.

### 12.4 Region Ownership

A region may be owned by a function or by a region-owning operation. Every region has
exactly one owner and is reachable through that owner’s explicit semantic slot. A region may
not be shared by two operations or moved between incompatible region roles without a
dedicated identity-continuity rule.

### 12.5 Value References

Extend the closed semantic value reference vocabulary to include:

- a function parameter Node ID;
- a block argument Node ID;
- an operation result identified by operation Node ID and checked output index;

A direct call target is a definition reference, not a value operand. Keep definition
references and value uses distinct in graph queries and dependency facts.

### 12.6 Lexical Visibility and Dominance

Define and validate lexical visibility structurally. At minimum:

- a function parameter is visible throughout that function body and all descendant nested
  regions;
- a block argument is visible throughout its block and descendant nested regions;
- an operation result is visible only after its defining operation in the same block and in
  descendant regions owned by later operations;
- a value visible at a structured operation position may be captured by each owned nested
  region;
- the structured operation’s own result is not visible inside its owned regions;
- a value defined in one nested region is not visible in a sibling region;
- a nested-region local value is not visible after the owning operation except through that
  operation’s result;
- a value from another function is never directly visible; it must be passed as a call
  argument;

Implement validation without unbounded native recursion. An explicit lexical-context stack,
owner-chain walk, or equivalent deterministic worklist is acceptable.

### 12.7 Operation Descriptors

Extend the single code-owned operation descriptor authority rather than scattering new truth
across validators, codecs, queries, compiler lowering, and schema output.

Descriptors or adjacent exact helpers must own, as applicable:

- stable operation code and boundary tag;
- stable machine name;
- fixed or context-derived operand count and type rules;
- operand use modes;
- fixed or context-derived result count and type rules;
- literal fields;
- terminator status;
- completeness status;
- direct definition-reference slots such as a call target;
- nested region count and ordered role names;
- required block-argument contracts per region role;
- required region terminator kind and yield type rule;

A call has dynamic argument and result rules derived from its target function. `if` and
`for_i64` have payload-derived result rules and exact region contracts. Keep those
context-dependent rules explicit and exhaustively tested.

### 12.8 Incompleteness

A typed hole remains a complete structural node with one expected result type and no
executable meaning. It may appear in a function body or any nested region where its result
is in scope.

A selected entry is compilable only when its reachable function and nested-region dependency
closure contains no holes or missing bodies. Unreachable incomplete functions remain valid
and do not block an unrelated complete entry.

### 12.9 Hole Refinement in Nested Regions

The existing one-way identity-preserving refinement rule must work for a hole owned by a
nested-region block. Refinement to a complete no-region expression operation with the same
single result type preserves Node ID, owner, position, and uses.

This campaign does not require a hole to refine directly into an `if` or `for_i64` with
newly created regions. Do not add generic constructor morphing. A later campaign may define
an exact structured-refinement transaction if a real workflow requires it.

Refinement to `call` is permitted when the call has the same result type and exact valid
target and arguments. Refinement to another hole, a terminator, a different result type, or
a region-owning operation without an exact dedicated rule rejects.

### 12.10 History Continuity

Extend adjacent-snapshot validation for new node kinds and owned region slots. Preserve:

- stable function and block argument identity across compatible edits;
- stable owner and ordinal for surviving block arguments;
- stable operation identity for compatible same-constructor operand or literal replacement;
- stable ordered region roles for a surviving structured operation;
- no silent owner transfer of a surviving region;
- no resurrection or persistent ID reuse;
- old snapshot validity after later body edits or refinement;

Do not broaden identity-preserving operation morphing beyond the accepted hole-refinement
rule.

## 13. Agent-Native Structured Authoring

Replace public node-by-node function-body construction with one closed typed structured
draft path. The exact Rust names may adapt, but the public behavior and removal requirements
are mandatory.

### 13.1 Public Construction Shape

The preferred direct replacement is to expand the existing public function creation
operation into a structured function draft. A function draft contains:

- one transaction-local function handle;
- the target module;
- the display name;
- ordered parameter drafts, each with a local handle, display name, and semantic type;
- one result type;
- an optional structured body draft;

A function body draft contains ordered expression-operation drafts and one explicit
return-value reference. It does not require the client to create or attach a region, block,
or return operation explicitly.

An `if` operation draft contains its condition, result type, then-body draft, and else-body
draft. Each arm draft contains ordered expression operations and one yielded value
reference. It does not expose region, block, or yield-node scaffolding.

A `for_i64` operation draft contains start, end-exclusive, positive step literal, initial
carried value, carried type, one local handle for the body index argument, one local handle
for the body carried argument, ordered body operations, and one yielded value reference. It
does not expose region, block, block-argument-node, or yield-node scaffolding.

Every expression operation draft that may be referenced has one local handle. Value drafts
may reference existing semantic values or local parameter, block-argument, and
operation-result handles in the same transaction, subject to final scope validation.

### 13.2 Deterministic Expansion

The transaction layer must recursively inspect the closed draft, reject duplicate or invalid
local handles, stage all required persistent identities in one deterministic order, resolve
forward function references, and create the exact canonical graph nodes.

The following ordering is recommended unless the actual code proves a cleaner equally
deterministic contract:

1. top-level explicit create-operation order;
2. function node;
3. function parameters in declaration order;
4. function body region and block;
5. body operations in semantic order;
6. for each structured operation, its nested regions in descriptor role order;
7. each nested block and block arguments in contract order;
8. nested operations depth-first in semantic order;
9. implicit yield or return terminator last in its block;

The expansion order is a transaction allocation contract and must be tested. Draft-local
handles are transport identities only. Synthetic internal handles, if used, never escape.

### 13.3 Forward and Mutual Function References

All explicitly created function handles in a transaction must be allocated before body
references are resolved, so a body may call a function created later in the same transaction
and mutually recursive bodies may refer to each other.

Do not resolve function calls by name. Use local or existing function identity targets.

### 13.4 Public Low-Level Path Removal

Once the structured function draft supports the current language and the representative
vertical, remove or privatize public machine and protocol exposure of low-level creation
operations whose only role is canonical scaffolding. At minimum reassess and normally remove
public:

- `create_parameter`;
- `create_region`;
- `create_block`;
- `create_operation` for initial body construction;
- `set_function_body`;

The internal transaction implementation may retain small helpers or a private low-level
expansion representation when it remains the one staging path. Do not expose two equally
preferred creation APIs.

Retain public package/module creation and targeted semantic maintenance operations when they
remain useful. Retain targeted rename, compatible operand replacement, hole refinement,
owned-subtree deletion, entry selection, and any exact body-definition operation required
for a previously bodyless function.

If a structured body replacement operation is added, specify identity churn exactly. It must
not silently pretend to preserve identities for replaced owned nodes.

### 13.5 No Second Authority

The draft is decoded, validated as a request shape, expanded, and discarded. It is never
persisted, hashed as program authority, queried as a program, compiled directly, or
round-tripped as a source representation.

The final staged SPG receives the same full validator as any targeted edit. Draft validation
must not become an alternative semantic checker that can disagree with the graph validator.

### 13.6 Authoring Cost Acceptance

Record the exact compact JSON and binary size of the structured creation request for the
representative program. Record the number of explicit public transaction items and explicit
structural objects.

The accepted interface must materially remove canonical scaffolding. Specifically:

- the request must not contain public create-region, create-block, create-terminator, or
  body-attachment operations;
- the complete initial program must be created in one daemon round trip;
- the client must be able to request only the hole and function bindings it needs;
- the structured request must be smaller and contain fewer independent mutation items than
  an equivalent low-level encoding;
- field-name abbreviation or opaque positional encoding must not be used merely to
  manufacture a byte win;

Do not impose an arbitrary byte threshold that encourages unreadable machine contracts.
Report the reduction and explain any residual cost.

## 14. Transaction and Receipt Requirements

Preserve one ordered atomic transaction model. Structured drafts are one or more closed
transaction operations, not a side-channel commit path.

Every mutation still names workspace, exact base revision, commit or validate-only mode,
optional committed-request idempotency key, ordered operations, and a bounded response
projection.

A structured creation transaction must preflight:

- draft shape and local-handle uniqueness;
- all staged identity allocation;
- all references including forward function handles;
- the complete expanded graph;
- semantic diff count and digest;
- canonical artifact bytes;
- durable HEAD bytes;
- the exact compact response bytes;

A rejection at any point publishes nothing and consumes no persistent identities.
Validate-only predicts the same identities, hash, diff facts, and selected bindings without
publication.

The default receipt remains bounded and contains no full diff and no complete allocation
map. Nested draft expansion may create many implicit nodes; report total created count and
only selected bindings.

Idempotency fingerprints must bind the exact structured request semantics and response
projection. Exact retry returns the retained compact receipt. A different draft or
projection under the same key rejects.

## 15. Protocol and Machine Projection

The public request vocabulary and semantic graph encoding will change incompatibly. Use one
direct version transition. Do not retain a compatibility reader.

### 15.1 Protocol Version

Bump the private binary protocol and generic JSON envelope to a new explicit version when
the active public variants or wire layout change. Version 3 is the expected next value if no
newer checkout version exists.

Delete protocol-v2 decoding and tests that exist only to preserve v2 success. Retain
explicit tests that old version bytes reject cleanly.

### 15.2 Strict JSON

The generic CLI continues to read exactly one bounded typed request and emit exactly one
typed response. Unknown fields and variants, duplicate fields, malformed IDs, invalid
numbers, excessive nesting, and trailing JSON reject.

Machine stdout remains one JSON value. Diagnostics remain on stderr. Typed daemon rejection
remains a successful transport response with the established exit-code distinction or a
deliberately replaced, fully documented equivalent.

### 15.3 Runtime-Generated Schema

Extend the executable schema description to expose:

- new semantic types and operation contracts;
- call target and dynamic signature rules;
- structured operation region roles;
- block argument contracts;
- structured draft forms and local-reference forms;
- new run argument shape and runtime policy limits;
- all active request, response, transaction, query, error, and boundary variants;

Do not hand-maintain a second exhaustive JSON schema file. A small runtime descriptor
derived from closed code-owned contracts remains preferred.

### 15.4 Boundary Limits

Retain centralized bounds for frames, JSON input, JSON output, batch count, page count,
response bindings, nesting, and draft traversal. Add a draft nesting or item bound only as
an operational decoder/request boundary, never as a semantic maximum on program structure.

Large semantically valid programs must be creatable through multiple bounded transactions.
Do not define the language by one request frame size.

## 16. Query and Repair Requirements

Extend existing exact scan-based queries rather than introducing a generic query engine.
Full recomputation remains the oracle unless representative measurements justify a narrow
index.

### 16.1 Owner Chains

Owner-chain results must represent nested operation ownership without ambiguity: operation
-> block -> region -> owning operation -> enclosing block, continuing to the function,
module, package, and workspace root.

### 16.2 Body Slices

A body slice must distinguish function-body, if-arm, and for-body contexts. Operation
summaries for structured operations should expose compact region-role summaries without
recursively dumping every nested body by default.

Block arguments must appear as exact typed definitions in the block summary or a dedicated
bounded field. Do not expose private Core IR block parameters as semantic block arguments.

### 16.3 Visible Values

Visible-value queries must implement the lexical rules for nested regions. For the loop-hole
target, the result must include the exact current loop index block argument, current carried
block argument, visible function parameter when applicable, and valid captured prior values.
It must exclude sibling-arm locals, future values, the owning structured operation result,
and values from other functions.

### 16.4 Incoming Uses and Definition References

Incoming value uses must identify source operation, target semantic value, operand index,
output index, and owning function/block context. Direct call references must be queryable as
definition references and must not be collapsed into value uses.

### 16.5 Dependencies and Reachability

Outgoing dependency queries must include direct call targets and values captured by nested
regions. Entry dependency closure used for compilation must follow calls and nested regions
deterministically.

### 16.6 Legal Constructors

Legal-constructor queries remain deterministic schema facts, not language-model suggestions.
For a target hole, return exact constructors whose result contract matches and whose
required region shape is supported.

At minimum, legal constructor data must cover new constants, comparison, direct calls whose
callee result matches, and structured operations at the descriptor level. A no-region hole
refinement query must distinguish constructors that can be used by the existing direct
refinement operation from structured constructors that require a different authoring action.

### 16.7 Repair Context

The nested loop-hole repair context is a mandatory acceptance surface. It must be sufficient
for a simple external agent to construct the correct `add_i64` refinement without a
workspace dump or manual owner traversal.

Include bounded typed facts for:

- target Node ID and exact expected result type;
- owner chain with structured region roles;
- function signature;
- block arguments and their semantic roles;
- bounded surrounding body operations;
- visible values with types and origins;
- incoming uses of the hole result;
- legal direct refinement constructors;
- relevant completeness blockers;

Do not include arbitrary natural-language advice in the canonical response. Presentation
layers may summarize typed facts later.

### 16.8 Pagination and Determinism

All collection results remain explicitly bounded and deterministically ordered. Cursors bind
the exact workspace, revision, query purpose, target, and next position. Cross-revision and
cross-target cursor reuse rejects.

## 17. Compiler and Reachable Program Closure

Replace the scalar one-function lowering with a deterministic multi-function compiler while
retaining one production route.

### 17.1 Compiler Input

The compiler accepts one immutable snapshot, one exact entry function, target-independent
bootstrap policy, run arguments separately at execution, and explicit runtime policy as
applicable.

### 17.2 Reachability

Collect the exact function closure reachable from the entry through direct call references.
Use an explicit worklist. Recursive cycles are valid and must not recurse through the native
stack.

Use deterministic dense function ordering. A suitable rule is ascending persistent Node ID
with the entry mapped explicitly, or deterministic discovery with an explicit documented
tie-break. Do not rely on hash-map iteration.

Only reachable functions must be complete and compilable. Unreachable incomplete functions
remain valid semantic state.

### 17.3 Compile Diagnostics

Compile rejection must identify the entry, incomplete or invalid reachable target, and
related Node IDs. A call to a bodyless or hole-containing reachable function is a
compile-incomplete error, not a daemon panic or missing-map failure.

### 17.4 One Core IR Route

Every executable semantic operation introduced in this campaign lowers through the same
private Core IR and verifier. Do not interpret SPG calls, ifs, or loops directly as a
fallback path.

## 18. Private Core IR Replacement

Replace the single-function single-block Core IR with the smallest closed IR that can
faithfully represent this campaign.

### 18.1 Required Core Entities

- a dense private function ID;
- a dense private block ID scoped unambiguously to a function;
- dense typed values;
- multiple Core functions in one program;
- ordered function parameters;
- multiple blocks per function;
- ordered block parameters;
- instructions for unit, bool, and i64 constants, checked i64 add, i64 less-than, and direct
  call;
- terminators for return, unconditional branch with arguments, and conditional branch with
  arguments;
- semantic origin Node IDs for diagnostics and traps;

Core IDs are derived dense implementation details and never become public semantic identity
or persisted artifact state.

### 18.2 Block-Local Value Discipline

Prefer a Core IR in which an instruction may use current block parameters and earlier
instruction results in the same block. Values crossing a control-flow edge are passed
explicitly as branch arguments to destination block parameters.

When an SPG nested region captures an outer value, the lowerer should deterministically
materialize the capture as a private Core block parameter and branch argument. Captures are
compiler-derived and do not become additional semantic nodes.

Use a deterministic capture order, such as first semantic use with a stable tie-break or
ascending semantic value identity. Document and test the selected rule.

### 18.3 Call Instruction

A Core call names a dense target function, carries ordered value arguments, and defines one
result. The verifier checks target range, argument count and types, result type, and local
operand availability.

### 18.4 Branch Terminators

An unconditional branch names one destination and ordered arguments. A conditional branch
consumes one bool and names then and else destinations with ordered arguments. The verifier
checks every destination, count, and type.

### 18.5 Return Terminator

A return consumes one value matching the owning function result. It has no successor.

### 18.6 No Serialized Core IR

Core IR remains same-build derived state. Do not include it in `.lkjscript` artifacts,
durable HEAD, semantic hashes, or public machine identity.

## 19. Structured Lowering

Lower structured semantic regions into private Core blocks deterministically. Preserve one
semantic route and exact origin mapping.

### 19.1 Straight-Line Operations

Lower constants, add, less-than, holes, and direct calls in semantic block order. A hole in
the reachable closure rejects before executable lowering.

### 19.2 `if` Lowering

Lower one semantic `if` into at least:

- a conditional branch from the current continuation to then and else Core blocks;
- one lowered Core subgraph for each arm;
- one join block with a parameter for the yielded result;
- branches from each arm yield to the join with the yielded value;

After the join, the join parameter is the Core value corresponding to the semantic `if`
operation result. Captured values required by each arm are passed explicitly as private
block arguments.

### 19.3 `for_i64` Lowering

Lower one semantic `for_i64` into a deterministic private loop shape. A suitable shape is:

- branch from the current block to a loop header with start and initial carried values;
- header block parameters for current index and carried value;
- an i64 less-than comparison of index and end-exclusive;
- a conditional branch to body or exit;
- body block parameters for semantic index, carried value, and any private captures;
- lowered body operations;
- checked index increment by the positive literal step;
- branch back to the header with next index and yielded carried value;
- exit block parameter representing the final carried result;

The exact block factorization may differ when it produces a simpler verifier and
interpreter, but it must preserve zero-iteration behavior, lazy body execution, checked
increment, result identity, and deterministic block ordering.

### 19.4 Nested Structured Operations

Structured operations may nest. Lowering must use an explicit compiler work structure or
carefully bounded implementation that cannot overflow the native stack on user-controlled
nesting. A 10,000-deep semantically valid nested fixture need not compile quickly, but it
must reject due to an explicit operational boundary or process iteratively without stack
overflow. Do not define arbitrary semantic nesting invalid merely for implementation
convenience.

### 19.5 Recursive Functions

Lower recursive call edges to dense function references after or during a deterministic
two-phase function allocation. Do not require callees to be fully lowered before a call
target can be represented.

## 20. Core IR Verification

The verifier is an independent trust boundary. It must reject malformed private IR before
execution even though the compiler is expected to produce valid IR.

Verify at least:

- entry function exists;
- function and block IDs are in range;
- each function has a valid entry block;
- parameter value IDs and types are dense and valid;
- block parameter IDs and types are dense and valid;
- instruction result definitions are unique and ordered according to the chosen
  representation;
- every instruction operand is available in the current block;
- instruction result and operand types match the instruction contract;
- call targets, argument counts, argument types, and result types match;
- branch targets exist;
- branch argument counts and types match destination block parameters;
- conditional branch conditions are bool;
- return values match function results;
- no block falls through without a terminator;
- no private index conversion overflows host indexes;

Add direct malformed-Core-IR tests for every new verifier rule. Do not test only
compiler-produced IR.

## 21. Interpreter Replacement

Replace the single-block evaluator with an explicit deterministic interpreter for the
verified multi-function Core IR.

### 21.1 Execution State

Use an explicit execution state that contains at least:

- remaining fuel;
- an explicit vector of call frames;
- current function and block per frame;
- current instruction position;
- current block-local values or a compact equivalent;
- a continuation describing where a callee result is written in the caller;

Do not use Rust recursion for calls. Do not use Rust recursion for control-flow transfer.

### 21.2 Function Entry

Bind exact runtime arguments to the entry function parameter values. Reject mismatch before
execution. A call frame binds Core argument values to callee parameter values using the same
exact type model.

### 21.3 Calls and Returns

A call pushes one frame and records the caller continuation. A return pops one frame and
writes the returned value to the caller result slot or completes the run when the entry
frame returns.

Mutual recursion must work until fuel or frame policy is exhausted. Exhaustion is structured
and leaves daemon state unchanged.

### 21.4 Branches

A branch selects the destination block, evaluates or copies branch arguments from the
current block state, initializes destination block parameters, clears or replaces
block-local instruction state, and resumes at instruction zero.

### 21.5 Fuel

Choose one simple deterministic accounting unit and document it in status or architecture as
runtime policy. Tests must demonstrate finite recursion exhaustion and finite loop
exhaustion without hangs.

Fuel must be bounded at the request boundary. A caller may request less than or equal to the
daemon maximum if useful. Do not allow an unbounded integer to allocate proportionally
before execution.

### 21.6 Runtime Traps

Retain structured origin-aware traps for checked add and loop-index overflow. Add exact
resource-exhaustion and frame-exhaustion errors or traps. The daemon must remain usable
after a run trap.

## 22. Artifact and Persistence Transition

New node kinds, operation payloads, block arguments, owned region slots, and value
references change canonical semantic encoding. Replace the artifact format unambiguously.

### 22.1 Artifact Version

Use a new artifact magic, format version, semantic schema identity, or a coherent
combination sufficient to make old and new bytes unambiguous. Artifact format version 2 is
the expected next value if no newer checkout state exists.

Delete the old success reader. Add explicit tests that old artifact bytes reject rather than
being heuristically interpreted or migrated.

### 22.2 Canonical Ordering

Preserve deterministic ordering for nodes, block arguments, operation regions, operations,
direct references, tombstones, and all new variable-length payloads. Encode checked counts
and lengths with fixed endianness and strict trailing-byte rejection.

### 22.3 Durability

Preserve exact commit ordering: preflight bytes, write and flush a temporary revision,
rename and sync it, write and flush temporary HEAD, atomically replace and sync HEAD,
publish in memory, then acknowledge.

If HEAD layout or retained idempotency receipt encoding changes, replace its magic/version
directly. If it does not change, prove that retaining the current HEAD version remains
unambiguous. Do not bump versions cosmetically and do not preserve old success readers.

### 22.4 Restart Validation

Restart must decode every retained new-format artifact, validate semantic graph and adjacent
history, validate HEAD and compact replay receipts, reconstruct the workspace, and reject
corrupt or ambiguous state.

The representative incomplete revision and repaired revision must both survive restart and
remain individually queryable. Running the incomplete revision must still reject after
restart; running the repaired revision must succeed.

## 23. Security and Trust Boundaries

Treat all external and persisted representations as untrusted: JSON, binary frames,
structured drafts, nested local handles, pagination cursors, artifacts, HEAD, runtime
arguments, Core IR, and future host data.

A malformed or adversarial structured draft may reject. It must not:

- panic;
- consume unbounded native stack;
- allocate without a checked boundary;
- hang;
- publish a partial graph;
- consume persistent identities on rejection;
- write a revision that cannot be acknowledged;
- cause a later valid daemon request to fail because transient state leaked;

Do not claim process sandboxing. The current local filesystem and socket permissions remain
the bootstrap access boundary unless this campaign explicitly implements and tests more.

- persistent ID assignment;
- selected handle bindings;
- graph validation result;

- query ordering and pagination;
- visible-value ordering;
- legal-constructor ordering;

- interpreter result and trap origin;

Use ordered collections or explicit sorting at observable boundaries. Add insertion-order
perturbation tests where practical.

```rust
    return_value: ValueDraft,
}

struct ExpressionDraft {
    handle: LocalHandle,
    operation: ExpressionKindDraft,
}

enum ExpressionKindDraft {
    ConstUnit,
    ConstBool(bool),
    ConstI64(i64),
    AddI64 { lhs: ValueDraft, rhs: ValueDraft },
    LtI64 { lhs: ValueDraft, rhs: ValueDraft },
    Call { function: NodeTarget, arguments: Vec<ValueDraft> },
    Hole { expected: SemanticType },
    If {
        condition: ValueDraft,
        result: SemanticType,
        then_body: YieldingBodyDraft,
        else_body: YieldingBodyDraft,
    },
    ForI64 {
        start: ValueDraft,
        end_exclusive: ValueDraft,
        step: i64,
        initial: ValueDraft,
        carried: SemanticType,
        index_handle: LocalHandle,
        carried_handle: LocalHandle,
        body: YieldingBodyDraft,
    },
}

struct YieldingBodyDraft {
    operations: Vec<ExpressionDraft>,
    yield_value: ValueDraft,
}

enum ValueDraft {
    ExistingFunctionParameter(NodeId),
    ExistingBlockArgument(NodeId),
    ExistingOperationResult { operation: NodeId, output: u8 },
    LocalFunctionParameter(LocalHandle),
    LocalBlockArgument(LocalHandle),
    LocalOperationResult { operation: LocalHandle, output: u8 },
}
```

A smaller unified local-value reference form is acceptable when it remains unambiguous and
exact. Do not require external clients to distinguish synthetic region and block handles
when those objects are structurally implied and never referenced.

The draft must still permit the caller to request persistent bindings for semantically
important local handles such as functions, parameters, block arguments, operations, and
holes. Region and block identities can normally be discovered through owner queries rather
than being transport handles.

A bodyless function remains representable for valid incomplete state. If the public
transaction supports attaching a structured body later, use a closed operation that creates
the complete owned body subtree atomically and refuses to overwrite an existing body unless
a separately specified replacement operation is used.

### 42.1 Candidate Initial Transaction

A representative initial transaction may contain create-package, create-module, three
structured create-function operations, and set-entry-function. The function bodies may refer
to later function handles because allocation is staged before application.

Do not force the client to issue one request per function. Do not require a query between
declaration and body creation solely to learn persistent function IDs.

### 42.2 Candidate Implicit Canonical Nodes

For each structured body, expansion creates a canonical region, block, regular operation
nodes, any nested regions and blocks, block argument nodes, and canonical yield or return
operation nodes. These are real persisted nodes with stable IDs even when the transport
draft did not assign them explicit handles.

Implicit creation must not mean hidden semantic state. Exact node views, owner chains, body
slices, diffs, artifacts, and restart all observe the resulting canonical nodes.

### 42.3 Candidate Reference Resolution Phases

- Scan every top-level operation and recursively scan structured drafts for explicit
  local-handle declarations.
- Reject duplicate handles, zero handles, invalid output indexes, and boundary overflow.
- Allocate explicit and implicit persistent IDs in the documented deterministic order
  without publishing the frontier.
- Resolve module, function, parameter, block-argument, and operation-result references
  against existing IDs and staged bindings.
- Materialize canonical nodes and containment in staged state.
- Run the complete final graph validator once over the candidate snapshot.
- Derive receipt, diff, artifact, HEAD, and response bytes before publication.

## 43. Error and Diagnostic Contract

Keep errors stable, typed, compact, and useful to an external agent. Reuse an existing error
code when its semantic category remains exact. Add a narrow new code only when callers need
to distinguish a new recovery action.

Potential distinct categories include:

- invalid structured draft shape or duplicate local handle;
- invalid region contract;
- invalid block argument contract;
- lexical value not visible at use;
- call signature mismatch;
- invalid loop step;
- compile-incomplete reachable function;
- run argument mismatch;
- execution fuel exhausted;
- execution frame policy exhausted;

Do not create a separate error code for every prose message. A code should identify recovery
semantics. Attach exact target Node ID, operation index, expected and actual kind or type,
related IDs, revision, and retryability where relevant.

Draft expansion errors should identify a deterministic path or local handle without
persisting that transport path as semantic identity. Keep error paths bounded so an
adversarial nested request cannot create an oversized response.

A compile error caused by a nested hole should identify the entry and hole. A scope error
should identify the use and referenced value. A call mismatch should identify the call and
target function. Fuel exhaustion should identify runtime policy and the semantic origin when
one is available.

Do not expose private Core function IDs, Core block IDs, or dense value IDs in public
semantic errors unless explicitly labelled as internal diagnostic presentation and never
accepted back as identity.

## 44. Risk Register and Required Mitigations

### 44.1 Risk: Structured Draft Becomes Source Code

A nested typed draft resembles an AST. The distinction is authority and lifecycle. Mitigate
by never persisting, hashing, querying, compiling, or round-tripping the draft; discard it
after deterministic transaction expansion. State this clearly in protocol and architecture
documentation.

### 44.2 Risk: Two Public Creation Paths

Keeping low-level create-region/create-block/create-operation beside structured creation
forces agents and maintainers to choose between equivalent paths and doubles testing.
Mitigate by removing or privatizing displaced scaffolding once coverage is complete.

### 44.3 Risk: Descriptor Abstraction Becomes a Framework

Dynamic call signatures and region contracts may tempt a general constraint engine. Mitigate
with closed enums, static descriptors, and a few exhaustive context-dependent helpers. Do
not build a registry or solver for seven operations.

### 44.4 Risk: Lexical Scope Validation Becomes Recursive and Fragile

Nested regions add ancestor visibility. Mitigate with an explicit scope stack or
deterministic owner-chain context, focused sibling/future/owner-result rejection tests, and
a large nesting stack-safety test.

### 44.5 Risk: Semantic Regions and Core Blocks Become Coequal

The SPG is structured and the Core IR is CFG-like. Mitigate by keeping Core blocks private
and derived, never persisting them, and ensuring compiler lowering is the only bridge.
External queries return semantic regions and blocks, not Core CFG bookkeeping.

### 44.6 Risk: Captures Produce Nondeterministic Core IR

Nested regions may capture several outer values. Mitigate by selecting one deterministic
capture ordering, documenting it as a private build contract, and perturbing semantic
insertion order in tests.

### 44.7 Risk: Recursive Calls Overflow the Host Stack

Mitigate with iterative reachable-function collection, two-phase dense function allocation,
explicit interpreter frames, deterministic fuel, frame policy, and deep recursion tests. Do
not hide native recursion behind helper functions.

### 44.8 Risk: Loop Semantics Expand Uncontrollably

Mitigate by keeping one exclusive positive-literal-step loop with one carried value and no
break, continue, or multiple results. Reject attempts to generalize during this campaign
unless the representative program proves impossible without it.

### 44.9 Risk: Protocol and Artifact Cutover Leaves Mixed State

Mitigate with direct version replacement, old-byte rejection tests, one coherent commit
boundary, restart tests, and final searches for old tags, magic, version constants, and
docs. Do not end a turn with readers and writers on different formats.

### 44.10 Risk: README Becomes Aspirational

Mitigate by writing or finalizing README after the real vertical passes, checking every
capability and limitation against status and tests, and linking detailed owners rather than
duplicating speculative plans.

### 44.11 Risk: Agent-Cost Work Optimizes Bytes Instead of Semantics

Mitigate by removing scaffolding and round trips while preserving readable stable names and
exact validation. Record bytes as evidence, but reject opaque positional formats or
compressed field names whose only purpose is a cosmetic result.

### 44.12 Risk: Campaign Scope Prevents Completion

Use the milestone sequence and non-goals to maintain a coherent boundary. Calls, if,
for_i64, structured authoring, Core IR, interpreter, persistence, queries, README, and the
representative vertical are jointly mandatory because each validates the others. Everything
beyond them is postponable.

## 45. Final Directive

Implement the campaign. Do not stop at analysis, a proposed architecture, an AGENTS.md
replacement, or a README rewrite. Produce a coherent active product path with code, tests,
documentation, real generic-machine evidence, and measured costs.

Use the freedom to break compatibility to remove accidental complexity. Use architectural
restraint to avoid replacing accidental complexity with speculative machinery.

The final product should let an AI coding agent express structured program meaning directly,
let deterministic machinery decide whether that meaning is valid, let a human understand why
the system exists, and keep one canonical graph from durable edit through verified
execution.
