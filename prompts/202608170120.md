## 4. Campaign Thesis

The accepted language should preserve simple immutable value semantics for ordinary data.
The runtime should not pay invocation-wide retention or repeated deep-copy cost when exact control flow proves that storage is dead or unique.
Ownership is the preferred default for managing cycle-free values.
Borrowing is the preferred default for non-owning access.
Precise reference counting is the preferred fallback for dynamic sharing.
Regions are preferred when one exact lifetime dominates all contained values.
Tracing is reserved for real cycles.
Affine semantic ownership is reserved for values whose duplication and cleanup are observable.
The coding agent should author program meaning, not memory choreography.
The compiler and verifier should exploit the SPG use graph and Core IR control flow.
The safe arena interpreter should remain available as an oracle until the ownership route has enough evidence to replace it.

- allocate-new concat can copy quadratically

## 7. Meaning of Ownership-First

Use `ownership` precisely.
Semantic ownership answers whether duplication or transfer changes observable behavior.
Physical ownership answers which runtime claim is responsible for keeping storage alive.
Borrowing grants access without taking the cleanup obligation.
Sharing creates more than one live ownership claim to the same physical storage.
Uniqueness means exactly one live ownership claim under the relevant contract.
Last use is a control-flow fact, not a source-position guess.
Drop discharges one ownership obligation.
Reclamation releases physical storage after the final obligation ends.
Reuse repurposes unique storage while preserving immutable observable semantics.
Region lifetime bounds a set of values with one proven destruction boundary.
Reference counting represents dynamic ownership multiplicity for cycle-free values.
Tracing discovers reachability for value classes that admit cycles.
Affine ownership is a semantic restriction that forbids implicit duplication.

For ordinary immutable bytes, the default is:

- semantically duplicable
- physically unique when one claim remains
- physically shared when multiple claims remain
- borrowable for reads
- reclaimable at the final drop
- reusable under verified uniqueness
- never address-observable

For future files, sockets, locks, processes, transactions, and foreign allocations, the default is different:

- semantic ownership is explicit
- duplication is forbidden or separately defined
- consuming operations are explicit
- cleanup is deterministic
- unknown outcomes are explicit
- garbage-collector finalization is insufficient

Do not conflate these classes.

## 8. Default Architecture Hypothesis

The default architecture has seven layers.

### 8.1 Observable semantic layer

`bytes_concat` is pure.
It reads two immutable values and returns their exact concatenation.
It exposes no mutation, move, address, ownership count, or allocation identity.

### 8.2 Core IR layer

Core IR retains ordinary typed values and explicit control flow.
It gains only the minimum instruction or operation needed for byte concat.
It does not embed allocator implementation details.

### 8.3 Ownership analysis layer

Analysis computes liveness, last use, transfer opportunities, borrow opportunities, sharing, escape, and cleanup.
Analysis understands managed references inside aggregate layouts.
Analysis produces a closed derived plan.

### 8.4 Ownership verifier layer

The verifier recomputes control-flow and type facts.
It checks every owned claim, borrow lifetime, transfer, duplicate, drop, and cleanup edge.
It rejects a malformed plan before execution.

### 8.5 Managed object layer

A managed store owns byte backing and view objects.
Handles are typed and generation-safe if slots are reused.
Objects carry exact ownership metadata only inside the runtime.

### 8.6 Execution layer

The interpreter executes one verified plan.
Reads borrow where possible.
Transfers avoid increments.
Multiple owners use precise counts.
Final drops reclaim objects.
Unique concat may reuse capacity.

### 8.7 Oracle and evidence layer

A simple safe path computes the same semantic result without ownership optimization.
Differential tests compare all results and failures.
Benchmarks compare peak and cumulative memory plus execution work.

Do not retain all seven as separate abstractions if direct code can preserve the same contracts more clearly.
Do retain independent verification boundaries.

## 11. `bytes_concat` Semantic Contract

`bytes_concat(lhs, rhs)` reads two exact `bytes` operands.
It produces one exact `bytes` result.
The result contains every visible octet of `lhs` followed by every visible octet of `rhs`.
The result has no observable storage identity.
Empty-left and empty-right behavior is exact.
Length addition uses checked arithmetic.
A result exceeding the accepted byte-value limit fails at a specified deterministic boundary.
The operation is complete, regionless, non-terminating, and single-result.
It is eligible for anonymous inline authoring.
It is eligible for typed-hole refinement when the existing refinement contract otherwise permits it.
It has an exact stable operation tag under the new direct-cutover format.
Its semantic operand use is `Read` unless a stronger general semantic vocabulary is justified.
Physical transfer, borrow, sharing, allocation, and reuse are derived implementation facts.
Its logical fuel does not depend on reference-count traffic or whether unique reuse succeeds.
Its logical fuel includes an exact per-octet construction charge or another documented deterministic semantic work model.
Its memory preflight occurs before destructive reuse.
A failed preflight leaves every input valid under the oracle semantics.
It supports bytes nested in records and variants without special semantic cases.

Do not add `bytes_push`, `bytes_builder`, `bytes_reserve`, `bytes_mutate`, or a generic sequence solely because concat exists.
Add a second byte-construction operation only when the retained application proves concat alone is semantically or asymptotically inadequate and the alternative remains smaller overall.

## 16. Ownership Analysis Requirements

Compute control-flow liveness iteratively.
Handle loops to a fixed point with explicit bounds or monotone convergence.
Handle recursion at call-convention boundaries rather than recursively traversing user depth.
Treat block parameters as explicit transfers.
Treat generated edge arguments as explicit uses.
Distinguish semantic read from physical ownership action.
Recognize last use only when all successor paths agree.
Insert or derive cleanup on every edge where a managed owner dies.
Do not drop a value on one branch when another branch still owns it.
At joins, reconcile ownership conventions deterministically.
At loop backedges, prove the loop-carried owner transfers exactly once per iteration.
At calls, define whether each parameter borrows or receives ownership.
At returns, transfer the result and drop nonescaping live owners.
For aggregates, inspect nested managed-reference maps.
For variants, act only on the active payload.
For projections, avoid retaining unrelated fields when a transfer can isolate the projected claim safely.
For immutable views, distinguish the view object from its backing owner.
For public output, transfer or materialize ownership before runtime teardown.
For traps, drop all owners created before the failing semantic boundary.
For cancellation, define a complete cleanup root set.
Do not make analysis correctness depend on map iteration order.
Do not consume unbounded native stack.

### 24.1 Asymptotic Fuel Decision

Repeated immutable concatenation creates a fundamental contract choice.

If concat fuel charges `lhs_length + rhs_length`, a loop that appends one octet at a time has quadratic logical work even when unique storage is physically reused.

That model safely upper-bounds the allocate-new oracle.

It may make large canonicalization intentionally fail under the current fuel ceiling.

If concat fuel charges only the appended octets, a shared or non-reusable fallback may perform quadratic physical copying under linear logical fuel.

That model can permit resource amplification unless another exact bound closes the gap.

Do not let the ownership optimizer silently select a cheaper fuel charge.

A compiler-version-dependent ownership proof must not change observable fuel exhaustion.

Choose one coherent contract:

1. Charge full logical result construction and accept that repeated immutable concat is not the scalable construction abstraction.
2. Retain concat for modest workloads and introduce a separately justified affine builder or bulk construction operation for linear construction.
3. Use a representation whose accepted worst-case construction work remains bounded by the cheaper charge even when values are shared.
4. Define another exact representation-independent work model and prove that all production fallbacks respect it.

Do not claim linear construction merely because one unique benchmark reuses capacity.

Measure both unique and shared paths.

Make the retained application's payload sizes consistent with the selected fuel contract.

Record the first accepted and rejected dense-construction sizes.

Keep fuel, copied bytes, allocation bytes, and elapsed time as separate evidence.
