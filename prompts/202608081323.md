# Coding-Agent Task: Remove the Measured Scale Pathology Before Expanding lkjscript

## Mandate

Work directly in `lkjsxc/lkjscript`.

The user authorizes you to make autonomous technical decisions, delete large amounts of code, break every form of backward compatibility, change syntax and internal formats, merge or remove crates, replace representations, and revise documentation. Do not preserve a mechanism because it is old, expensive, tested, documented, or associated with an earlier user preference.

The only overriding goal is to make `lkjscript` converge, over multiple coherent turns, toward the strongest simple long-term design: AI-primary, statically typed, memory-safe, understandable, and eventually extremely fast.

The companion `AGENTS.md` supplied with this task is the intended complete replacement for the repository root `AGENTS.md`. Replace the existing file; do not append the old policy to it. The replacement deliberately keeps procedure in `AGENTS.md` and leaves semantics, architecture, status, performance evidence, and ordering to their owning documents.

Do not ask the user to choose implementation details that repository evidence or experiments can decide. Do not stop after producing a plan. Complete at least one root-cause correction end to end, leave one active architecture, verify it, commit it, and push it without force when credentials permit.

Backward compatibility is not a requirement.

The name or existence of `lkjscript-sys` is not a requirement. Treat it like any other component. Preserve, merge, split, rename, or delete it only when present evidence supports that action. Do not divert this task into a speculative syscall or platform rewrite.

## Multi-turn discipline

This is a long-term project, but this task is intentionally narrower than “finish the language.”

Do not decide every future language, runtime, persistence, collaboration, GUI, web, game, scheduler, or deployment question now. Each turn should finish the highest-leverage dependency-closed vertical and use the resulting evidence to choose the next one.

For this turn, the priority is measured compiler scale and memory behavior. Do not expand the language surface or semantic workspace merely because those features are attractive. A fast, simple, trustworthy foundation is more valuable than another broad layer.

If the repository has advanced beyond the commit described below, re-audit the current checkout and follow the same intent rather than mechanically recreating stale changes.

## The measured problem

The retained ignored release stress test:

```text
crates/lkjscript-app/tests/source_scale.rs
sixteen_thousand_three_hundred_eighty_five_calls_and_borrow_scopes_execute_in_vm
```

generates 16,385 calls that repeatedly borrow one string. The program compiles, validates, and returns `42`, so the former arbitrary limit is gone. However, the recorded run is unacceptable:

```text
total test-body time:       333.24 s
approximate process-tree RSS: 30.4 GiB
HIR memory planning:          0.14 s
bytecode validation:         59.44 s
preparation:                261.05 s
```

This is now the highest-value known local blocker. It is a performance and architecture defect, not a reason to restore a quota.

The current roadmap already places this work first. Honor that evidence.

## Primary objective

Redesign the affected validation and preparation paths so that large straight-line programs do not create instruction-count multiplied by whole-function-state work or memory, and so that compilation does not construct, verify, hash, and discard a native-specialized whole program merely to bind a generic in-process program identity.

The result must preserve:

- language semantics;
- bytecode and native safety;
- the complete VM route for supported valid programs;
- pre-entry native decline and no VM retry after native entry;
- failure atomicity;
- deterministic behavior;
- unrestricted trusted local validity; and
- malformed-input rejection at genuine untrusted boundaries.

Do not claim success from a small constant-factor tweak. Remove the asymptotic or duplicate-work cause.

## Important hypotheses to verify, not blindly assume

### 1. Bytecode validator state explosion

Inspect:

```text
crates/lkjscript-core/src/validation/entry.rs
crates/lkjscript-core/src/validation/control/
crates/lkjscript-core/src/validation/model/state.rs
crates/lkjscript-core/src/validation/model/merge.rs
crates/lkjscript-core/src/validation/failure_cleanup/
```

At the audited commit, `validate_control_flow`:

- allocates one `Option<State>` per decoded instruction;
- clones a complete `State` when processing an instruction;
- retains states for all instruction positions;
- clones another complete state for a newly reached successor; and
- scans complete stack, local, global, and unique-place vectors at joins.

`State` contains dense vectors for stack, locals, globals, and every unique place, plus structural destination state.

The failure-cleanup check is invoked at every processed instruction. At the audited commit it:

- linearly searches `failure_cleanup_ranges` for a covering range;
- scans all unique places to ask whether any owner is active;
- scans locals for borrowed state; and
- performs this work even though full plan validation matters primarily at range starts and coverage transitions.

For a large straight-line function with many borrow scopes, these choices can produce quadratic work and enormous retained memory.

Confirm with profiling and scaling data.

### 2. Preparation performs discarded native specialization

Inspect:

```text
crates/lkjscript-compiler/src/pipeline/common.rs
crates/lkjscript-compiler/src/package/program/
crates/lkjscript-contracts/src/prepared/
crates/lkjscript-ir/src/specialize/
crates/lkjscript-ir/src/identity/
crates/lkjscript-core/src/validation/model/identity/
```

At the audited commit, `package::program::bind`:

1. hashes the complete verified semantic SSA;
2. calls `specialize_native_transport(&ssa)`;
3. hashes the resulting specialized verified SSA;
4. discards that specialized program;
5. hashes complete validated bytecode;
6. constructs a `PreparedProgramDescriptor`;
7. hashes the descriptor; and
8. writes the resulting identity into the original SSA and bytecode.

At the audited commit, `specialize_native_transport` can clone the whole SSA program, clone and rewrite functions, and invoke full SSA verification. Search results showed the optional `native_specialization_ssa` identity used by the prepared descriptor and its tests, but no product consumer of the discarded specialized program.

This is a strong explanation for the preparation phase, but prove the complete producer/consumer graph before deleting it.

The expected default is:

- do not create a native-specialized program until an actual native attempt needs one;
- do not include an identity for a nonexistent discarded artifact in a generic prepared-program key;
- if a native artifact needs an identity or cache key, compute it from the actual selected/lowered artifact at the native boundary; and
- delete the field, transform, contract surface, and tests when they have no remaining consumer.

Do not replace one redundant identity hierarchy with a more elaborate identity framework.

### 3. Other repeated full-program work may remain

Measure and inspect:

- repeated validation of already typed in-process values;
- repeated canonical hashing;
- whole-program clones;
- duplicate witness and memory-plan serialization;
- unconditional construction of bytecode and native metadata;
- retained decoded instructions or indexes with avoidable duplication; and
- repeated scans during cleanup, ownership, or preparation.

Only address additional work when it is on the measured path and can be removed in a coherent vertical. Do not turn the task into an unlimited rewrite.

### Phase 2: Redesign bytecode control-flow validation

The target property is:

> Validation memory and work should scale with executable facts and control-flow joins, not with the number of instructions multiplied by the full width of function state.

A likely simple design is:

1. Decode instructions once.
2. Identify basic-block boundaries and successor edges.
3. Store incoming abstract state at block entries, not at every instruction.
4. Clone or materialize state once when beginning a block.
5. Mutate one working state through the straight-line body.
6. Merge only at successor block entries.
7. Reprocess a block only when its incoming state changes.
8. Pre-index failure-cleanup ranges and transitions.
9. Validate cleanup plans at the semantically relevant boundaries.
10. Track whether cleanup is required without rescanning every dense state vector at every instruction.

This is guidance, not a mandate. A better measured design is allowed.

Important constraints:

- loops and backedges must converge correctly;
- incompatible joins must remain rejected;
- stack categories, locals, globals, ownership, unique places, structural destinations, active variants, and borrow use must retain exact meaning;
- malformed jumps and non-instruction boundaries must remain rejected;
- failure-cleanup coverage and plans must remain fail-closed;
- error messages must stay deterministic enough for tests;
- the validator must remain stack-safe;
- no arbitrary block, state, iteration, or program-size quota may be introduced; and
- allocation or host failure must remain distinct from semantic invalidity.

Prefer a block-level algorithm before introducing persistent maps, sparse snapshots, custom arenas, dataflow frameworks, or parallel validation.

If block-level state still has a measured width problem at joins, consider the smallest adequate improvement, such as:

- separating immutable function shape from mutable flow facts;
- dense state plus compact incremental summaries;
- sparse deltas for rarely changed ownership facts;
- copy-on-write state at actual branch points;
- interned immutable state only when repeated equality/clone cost is measured; or
- more precise liveness so dead state is not carried.

Do not implement all of these preemptively.

Failure-cleanup validation should not linearly search every range or rescan every unique place for every instruction. Build a validated range index or sweep schedule once. Maintain or cheaply derive a truthful “cleanup required” summary as state changes. Ensure the summary participates correctly in clone, merge, and mutation.

Do not solve the problem by skipping bytecode safety validation. A trusted typed-construction path may eventually bypass redundant untrusted decoding only if it is demonstrably simpler and preserves an independently usable validator at real external boundaries. That is not the default first move.

Add focused tests for:

- a long straight-line function;
- one branch and join;
- nested branches;
- loops and backedges;
- incompatible stack or local state at a join;
- unique-owner movement across a join;
- borrowed views;
- structural destinations;
- cleanup range start, interior, end, gaps, and malformed overlap;
- cleanup plans for entered and unentered failure;
- malformed jump targets;
- deterministic diagnostics;
- allocation failure where the codebase has a test mechanism; and
- scaling beyond former boundaries.

Default tests should use affordable geometry. Retain the large ignored release stress test.

### Phase 3: Delete unconsumed preparation and identity work

Build a complete producer/consumer inventory for:

- `PreparedProgram`;
- `PreparedProgramDescriptor`;
- `PreparedProgramIdentity`;
- `semantic_ssa`;
- `native_specialization_ssa`;
- `validated_bytecode`;
- contract digests;
- `verified_program_identity`;
- `validated_bytecode_identity`;
- `specialize_native_transport`;
- JIT eligibility and lowering;
- executable installation; and
- any compilation cache.

Classify each value:

- required for current correctness;
- required at a real trust or transfer boundary;
- used as a cache key by a current consumer;
- diagnostic/telemetry only;
- redundant derivation; or
- dead ceremony.

Then perform the simplest direct cutover.

At minimum, unless a real consumer disproves the audit:

- remove unconditional `specialize_native_transport` from generic compiler preparation;
- stop verifying and hashing a specialized program that is immediately discarded;
- remove `native_specialization_ssa` from the generic prepared descriptor;
- delete tests and documentation that preserve that dead field;
- compute native-specific facts only inside an actual eligible native attempt;
- keep native decline before entry;
- keep the generic VM path independent of native specialization; and
- ensure preparation no longer hides a second whole-program verification pass.

Challenge the rest of the prepared-identity design rather than assuming every existing digest is necessary.

The current product is in-process. If a descriptor field exists only to authenticate a value that never crosses a trust, persistence, process, or cache boundary, consider deleting it. A typed verified value may already be sufficient authority.

However:

- do not weaken executable installation, relocation, W^X, generated entry, FFI, or externally loaded artifact checks;
- do not make cache collisions or stale artifact reuse possible;
- do not mix target-neutral semantic identity with target-specific machine artifact identity;
- do not compute a native artifact identity from an artifact that was never actually selected and built; and
- do not invent a new universal key hierarchy.

If semantic SSA and validated bytecode identities still have current consumers, compute each at most once per compilation and pass the result forward. Fuse traversal with an existing producer only when that makes ownership and validation clearer; do not contaminate unrelated phases to save an unmeasured pass.

Add tests that prove:

- compiling a VM-only program performs no native specialization;
- native-ineligible programs remain valid;
- native-eligible programs still attempt the selected baseline path;
- pre-entry decline still executes the unchanged VM program;
- entered native execution never retries in the VM;
- stale or mismatched identities at real boundaries are rejected;
- preparation failure does not partially bind or publish state; and
- program results remain equivalent.

Prefer observable counters in tests over timing assertions.
