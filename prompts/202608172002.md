## 2. Product North Star

`lkjscript` is not primarily a syntax experiment, graph database, compiler benchmark, daemon protocol, or memory-management demonstration.

It is a programming system intended to let autonomous coding agents produce and maintain real software with deterministic machine-checked meaning.

The strongest long-term product boundary is expected to have three layers.

1. Human intent, governance, security policy, review, and product ownership.

2. Agent-facing semantic observation and proposal surfaces optimized for reliable low-cost work.

3. A compact authoritative semantic substrate that validates, versions, packages, compiles, and executes accepted programs.

No current implementation mechanism is allowed to dominate all three layers by accident.

The system should eventually support:

- weak and strong coding models without requiring repository implementation knowledge

- deterministic creation, repair, refactoring, migration, testing, debugging, and review

- multiple modules and packages

- publishable immutable package artifacts

- parallel agents and explicit branches or change sets when justified

- capability-secure host effects

- resource-owning values with deterministic cleanup

- portable deterministic builds

- a simple interpreter oracle

- a compact bytecode or equivalent execution substrate

- profile-guided optimization only after representative workloads

- native acceleration without changing language meaning

- human-readable review and standard version-control workflows

- bounded local operation without a public network service

- cross-platform clients and eventually cross-platform execution

- semantic caching keyed by exact accepted revisions

- machine-verifiable test and contract artifacts

- safe package distribution and dependency resolution

This campaign does not need to implement the entire destination.

It must ensure that the next accepted substrate makes that destination easier rather than harder.

### 2.1 Primary optimization objective

Optimize the total lifecycle cost of correct software, not one serialization size or one interpreter microbenchmark.

- probability that an agent completes an exact task

- probability that a weaker model can complete the same task

- number and severity of unintended corrections

- provider input, cached-input, output, and reasoning tokens

- number of semantic requests and shell commands

- amount of unchanged context repeated

- human ability to review semantic change

- semantic diff stability under unrelated edits

- workspace and package storage growth

- restart and reconstruction cost

- compiler and runtime performance

- implementation source and verification surface

- trusted computing base

- cost of adding the next language or effect feature

- cost of branching, merging, and package reuse

- cost of maintaining the repository with coding agents

### 2.2 Primary design stance

Prefer semantic structure over incidental text structure.

Prefer compact editable text over verbose machine DTOs when editable text preserves exact semantic validation and wins controlled tasks.

Prefer durable identity over positional identity when continuity has a consumer.

Prefer structural or revision-local identity over durable identity when continuity has no consumer.

Prefer immutable content and explicit publication over hidden mutable client state.

Prefer simple correct execution over premature optimization.

Prefer generated exact contract projections over copied schema prose.

Prefer deletion over compatibility.

### 2.3 Human role

Humans must be able to understand what changed without reading private compiler indexes or a model transcript.

A human reviewer should see stable declaration identity, changed contracts, changed behavior, permissions, package effects, tests, and migration facts.

Human review does not require hand-authoring the authoritative representation.

Human review does require deterministic comprehensible projections.

## 5. Candidate Architecture Matrix

Do not compare only one favored design with the status quo.

At minimum, evaluate the following dependency-closed candidates.

### Candidate A: Current identity model plus focused migration operation

Keep persistent identity for every current node, full snapshots, the daemon, and the current workbench; add one exact mapped declaration migration operation.

This is the lowest immediate implementation risk and the current roadmap default.

Its burden is that it may treat symptoms while preserving scaffold identity, tombstones, broad schemas, full rewrites, and node-level edit choreography.

### Candidate B: Identity-stratified semantic bodies over current persistence

Keep the current workspace publication model temporarily, but replace persistent body scaffolding with immutable function-body structures and revision-local term references.

Add durable IDs only for declarations, members, parameters where justified, tests, and explicit repair/debug anchors.

This isolates the identity question from the storage question and provides a strong measured intermediate candidate.

### Candidate C: Identity stratification plus canonical editable semantic documents

Use Candidate B's semantic model and add a deterministic bounded text document that renders and replaces one exact semantic scope.

The document is a proposal bound to a base revision, schema digest, scope, and continuity map.

This directly tests whether model-native text can outperform the current plan grammar without becoming authority.

### Candidate D: Identity stratification plus incremental immutable storage

Store semantic entities and body objects as canonical immutable chunks referenced by revision commits.

Use content digests as storage keys only and preserve separate semantic entity identities.

This targets full snapshot cloning, artifact growth, restart, branching, package reuse, and cacheability.

### Candidate E: Canonical textual program authority

Make a canonical typed textual form the direct program authority and rebuild semantic structures from it.

This is the strongest challenge to the current thesis and must be evaluated honestly.

Reject it if authority, identity, exact semantic merge, partial context, or validation becomes weaker; select it only if it is materially simpler and still satisfies every enduring invariant.

### Candidate F: Mature transactional store behind the current or identity-tiered model

Use a mature embedded transactional store rather than custom full snapshots or a custom object database.

Evaluate crash guarantees, native and unsafe surface, portability, canonical export, corruption handling, package artifacts, compile cost, and dependency risk.

Do not select a database because databases sound scalable.

### Candidate G: Direct embedded engine rather than mandatory daemon

Run transaction, query, compile, and execution through one library engine opened by the CLI under exact workspace locking.

Use a bounded session or batch to amortize startup.

Select it if lifecycle simplicity and agent reliability beat daemon caching and concurrency.

### Candidate H: Transparent service with persistent client connection

Retain one service authority but remove explicit lifecycle and one-connection-per-request overhead.

Define startup, discovery, correlation, cancellation, reconnect, unknown outcomes, and shutdown exactly.

Do not retain both direct and service paths as equal production semantics.

### 5.1 Comparison protocol

- Use the same accepted semantic tasks and independent oracles.

- Measure current workbench behavior before changing semantic or storage contracts.

- Keep provider trials sealed from implementation source, tests, examples, prompts, and prior payloads.

- Use deterministic replay for most candidate elimination.

- Do not pay for a fresh model baseline when an exact sealed baseline remains valid.

- Prototype candidates in isolated modules or scratch branches that can be deleted cleanly.

- Do not let a prototype write current workspace artifacts that a losing implementation cannot read.

- Compare human review output and identity continuity.

## 6. Default Target: Identity-Stratified Typed Semantic Model

Unless evidence selects a materially better architecture, replace the universal persistent node model with explicit identity strata.

### 6.1 Proposed identity domains

#### Workspace identity

Durable random or otherwise collision-safe authority-domain identity. It names a workspace namespace, not content.

#### Package identity

Durable when a package or published library has continuity independent of one revision or name.

#### Entity identity

Durable identity for externally referenceable declarations and other semantic entities with independent continuity.

#### Member identity

Durable identity for record fields, variants, public parameters, test cases, permissions, resources, or similar members when rename, migration, or external reference requires continuity.

#### Anchor identity

Durable identity for an explicitly repairable placeholder, breakpoint, obligation, or body location whose continuity is a product feature.

#### Revision or commit identity

Exact immutable accepted program state, preferably content-verifiable and distinct from display sequence numbers.

#### Body object identity

Immutable storage identity or digest for a typed body object; not automatically semantic identity.

#### Term reference

Revision-local or body-local reference to an operation result, binder, region, branch, or terminator.

#### Structural path

Deterministic location inside one exact immutable body, valid only with that body or revision digest.

#### Proposal symbol

Transaction-local label discarded after normalization.

#### Context alias

Packet- or document-local compact alias bound to exact scope and digest.

#### Compiler identity

Dense private type, function, block, value, or instruction ID derived for one compilation.

#### Runtime handle

Private validated storage handle valid only within one runtime domain.

#### Storage key

Digest or database key for canonical bytes, not semantic continuity.

### 6.2 Durable identity admission test

No new durable identity class is accepted until every question below has an exact answer.

- What user, agent, package, history, or runtime contract targets this object across revisions?

- Can the object be anonymous without losing repair, sharing, review, or external reference?

- What observable behavior depends on preserving identity?

- Which edits preserve continuity?

- Which edits require replacement identity?

- Can order, scope, or structural path supply sufficient local identity?

- How is identity represented at public boundaries?

- How is the domain validated?

- How does validate-only predict new identities?

- How do rejected proposals avoid consuming identities?

- How do branches or parallel proposals avoid collision?

- How are deleted identities prevented from resurrection or ambiguous reuse?

- How do semantic diffs distinguish continuity, replacement, and structural movement?

- How does package export preserve or intentionally rebind identity?

- What storage representation proves the contract without making storage keys semantic?

### 6.3 Default durable entities

The default durable set should be small and justified.

A reasonable starting hypothesis is:

- workspace

- package

- module only if module continuity is externally meaningful

- named record declaration

- variant declaration

- function

- record field

- variant alternative

- public or independently targeted parameter when signature continuity needs it

- first-class test or specification declaration when introduced

- explicit effect authority or resource declaration when introduced

- explicit repairable body anchor

Do not retain durable identity for package/module scaffolding merely because the current schema has nodes for them.

Either give them real semantic and package behavior or simplify them.

### 6.4 Default revision-local structures

- ordinary expression terms

- ordinary operation results

- implied returns and yields

- single-block region scaffolding

- branch-local regions

- compiler-generated blocks

- loop-local binders

- match payload binders

- anonymous constants

- anonymous calls

- anonymous aggregate construction and projection

- temporary query rows

- rendering groups

These structures may have compact local IDs inside one immutable body object.

Local IDs exist to express sharing, ordering, dominance, and diagnostics.

They do not enter workspace-wide allocation, tombstone history, package identity, or cross-revision continuity unless explicitly promoted to an anchor.

### 6.5 Body model requirements

- A function body is one immutable typed semantic object or a small dependency-closed immutable object set.

- The body owns explicit local binders and local terms.

- Term order is canonical where order is semantically observable or needed for deterministic encoding.

- Shared values use exact local references rather than repeated syntax.

- Structured control remains typed and explicit.

- User-depth traversal remains iterative or otherwise stack-bounded.

- Body validation has no dependency on parser syntax.

- Body-local IDs are canonical or explicitly allocated within the body domain.

- Body-local IDs never collide with durable entity IDs.

- A body replacement can preserve the function entity identity.

- A body edit does not create workspace tombstones for every changed anonymous term.

- A body hash or object digest may accelerate equality and diff but does not become function identity.

- Compiler diagnostics name exact revision, function entity, and body-local origin.

- Historical diagnostics remain resolvable while the referenced revision is retained.

- A repairable hole is represented by an explicit durable anchor or another exact continuity-bearing construct.

- The model can represent incomplete bodies without accepting ambiguous partial syntax.

- Cross-function calls target durable function entities.

- Nominal types target durable declaration entities.

- Local value references cannot escape their body domain.

- Artifact decoding validates every local reference, binder, type, branch, use, and terminator.

### 6.6 Continuity and structural editing

Do not attempt to infer durable continuity from arbitrary structural similarity.

Automatic structural matching may produce a review aid.

It cannot silently decide semantic identity.

- A surviving durable entity keeps its exact ID only when the proposal explicitly targets it or an exact scoped replacement contract preserves it.

- A renamed entity preserves ID when all other identity-defining contracts remain valid.

- A body replacement preserves the owning function ID but not anonymous term identity.

- An anchored hole replacement preserves the anchor ID only under its exact type and scope contract.

- A declaration migration creates a new declaration ID unless the accepted declaration contract explicitly supports the changed shape.

- Member continuity across declaration replacement requires an explicit old-member to new-member map.

- A continuity map is injective within each identity class unless the semantic operation explicitly supports merging.

- Unmapped surviving external references reject before publication.

- Ambiguous mapping rejects.

- Mapping to a wrong owner, kind, type, or package domain rejects.

- A mapping may be used to rewrite exact uses, public values, tests, or package exports only under a named migration contract.

- Semantic diff reports preserved entity, replaced body, mapped member, removed entity, and new entity separately.

### 6.7 Allocation alternatives

Compare at least the following durable entity allocation strategies.

- Current workspace-wide monotonic serial allocation.

- Workspace-qualified 128-bit random entity IDs generated by the authority.

- Branch-qualified counters with explicit merge remapping.

- Domain-separated IDs derived from canonical normalized proposal identity plus local allocation ordinal.

- A hybrid: stable random workspace plus monotonic entity counter while body terms remain local.

- Evaluate validate-only predictability.

- Evaluate idempotent retry.

- Evaluate rejected-proposal non-consumption.

- Evaluate parallel branch creation.

- Evaluate merge behavior.

- Evaluate canonical encoding size.

- Evaluate human and agent reference compactness.

- Evaluate collision argument.

- Evaluate deterministic tests.

- Evaluate package import and copy semantics.

- Evaluate recovery after crash.

Do not replace the current monotonic allocator merely to appear distributed.

Identity stratification may remove enough pressure that the current entity allocator remains the best bootstrap choice.

### 6.8 History conversion

Backward compatibility is not required.

If the identity model changes, perform a direct semantic epoch cutover.

- Choose an unambiguous new semantic schema identity.

- Choose a new artifact, object, commit, and HEAD magic or version as applicable.

- Delete old readers and writers.

- Reject old bytes directly.

- Regenerate every retained example from the public path.

- Retain no converter in production.

- A one-off disposable migration experiment may be used to compare equal semantics, then deleted.

- Tests prove old formats reject and new canonical forms round-trip.

- Update every protocol, schema, context, alias, idempotency, cache, and package digest domain affected by the semantic change.

## 7. Canonical Editable Semantic Documents

The current one-way review view was a prudent first step.

It should no longer be treated as a permanent restriction.

Coding models are trained to understand and edit structured text.

A canonical editable semantic document may be the highest-leverage way to reduce action and observation cost while preserving semantic authority.

### 7.1 Product contract

- A document observes one exact accepted revision or immutable candidate commit.

- A document declares one exact editable scope.

- A document declares its semantic schema or contract digest.

- A document declares its workspace or package domain.

- A document declares whether omitted content is read-only context or absent from the scope.

- A document contains durable entity anchors only where continuity is required.

- A document uses compact local binders and term references for body structure.

- A document is deterministic for the same revision, scope, options, and schema.

- A document parser is strict, bounded, iterative where user depth scales, and location-aware.

- Parsing produces a closed typed proposal.

- The proposal enters the same semantic normalization and validator as every other edit path.

- Parser syntax and formatting are discarded after normalization.

- A render-parse no-op produces no semantic change.

- A render-edit-parse operation cannot mutate content outside declared editable scope.

- Stale base, stale schema, foreign anchors, unknown aliases, duplicate fields, ambiguous continuity, and malformed structure reject.

- The document is never required to reconstruct accepted authority after publication.

### 7.2 Required document scopes

#### Function document

Signature, bounded dependency signatures, exact body, local terms, anchors, tests or callers when requested.

#### Declaration document

One type declaration, members, exact uses or migration surface, and optional replacement continuity map.

#### Module document

A bounded set of declarations and functions with explicit editable membership.

#### Task document

The smallest dependency-closed editable scope for a create, repair, refactor, debug, migrate, or delete task.

#### Review document

Read-only deterministic projection of one revision or semantic change set.

#### Package document

Public declarations, dependencies, permissions, tests, and release metadata when package work begins.

### 7.3 Syntax evaluation

Do not select syntax by taste.

Prototype at least three candidate spellings over identical semantic tasks.

- A concise block-structured source-like form with named fields and exact anchors.

- A canonical S-expression or bracketed form with low parser ambiguity.

- A line-oriented tagged document optimized for diff stability and streaming.

- The current compact plan grammar as the control.

- Strict packet-scoped JSON as an additional control when useful.

- Measure render bytes.

- Measure edited proposal bytes.

- Measure tokenization under the actual provider when telemetry is available.

- Measure model correction count.

- Measure parser implementation size.

- Measure error location quality.

- Measure diff stability.

- Measure human reviewability.

- Measure ability to express shared local values.

- Measure ability to express nested control.

- Measure ability to express declaration continuity.

- Measure ability to omit read-only context safely.

- Measure ability to generate help from the semantic contract.

Do not retain multiple editable syntaxes.

Select one or retain the current plan if every document candidate loses.

### 7.4 Non-normative shape sketch

The following sketch illustrates required domains.

It is not a preselected grammar.

```text
semantic_document 1
workspace w:...
base revision:...

context type @Job Job
context type @Decision Decision

function @score (job: @Job) -> i64 {
    let cpu = project @Job.cpu job
    let trusted = project @Job.trusted job

        add_i64 cpu 2
```

A winning grammar may be more compact.

It must remain exact about identity, scope, types, shared values, and omitted content.

### 7.5 Round-trip and equivalence

- Test that render then parse without edits is a semantic no-op.

- Test that render then reformat in allowed insignificant ways normalizes identically.

- Test that explicit local term form and nested shorthand normalize identically when promised.

- Test that document and typed DTO proposal produce the same accepted semantic body.

- Test that document spelling does not change durable entity allocation.

- Test that local binder spelling does not change body meaning.

- Test that unknown or duplicate anchor rejects.

- Test that foreign workspace or package anchor rejects.

- Test that stale base rejects.

- Test that wrong schema digest rejects.

- Test that read-only context modification rejects.

- Test that omitted content is never deleted implicitly.

- Test that body-local reference outside scope rejects.

- Test that continuity map type or owner mismatch rejects.

- Test that deep or oversized documents reject before unbounded allocation.

- Test that error spans remain bounded and deterministic.

### 7.6 Public edit operations

The document should normalize to a small semantic edit vocabulary.

A likely high-level vocabulary is:

- create package or module scope

- create declaration set

- replace declaration set within an exact scope

- create function

- replace function signature under explicit identity rules

- replace function body

- insert or remove a named entity

- rename a durable entity

- set package entry

- create anchored placeholder

- refine anchored placeholder

- map old declaration members to replacement members

- delete an exact durable entity after complete use preflight

- attach or update bounded documentation metadata if accepted

- create or update first-class tests if accepted

Retain a fine-grained internal transaction or builder as a differential oracle if it materially helps verification.

Do not require external agents to author representation scaffolding.

### 7.7 Migration decision

Use the existing `Limits` to `DeploymentLimits` replacement as one control task.

Add a second independently shaped declaration migration authored through the public path.

- If the editable document plus explicit continuity map performs both migrations compactly and locally, do not add a specialized mapped migration endpoint.

- If two independent migrations still require repeated error-prone semantic choreography, implement the smallest exact migration operation.

- A specialized migration operation must not become a generic rewrite language.

- It must preflight every affected use, type, public value, test, package export, and deletion.

- It must remain differential against the fine-grained or document-normalized oracle.

- Delete it if it is not reused by the second migration or if verification becomes less local than explicit replacement.

### 8.3 Content-addressed candidate requirements

- Content digests are storage identities, not semantic entity identities.

- Every object encoding is canonical, versioned, domain-separated, and independently bounded.

- Every object declares or implies its object kind.

- References name exact expected object kind and digest.

- Decoding verifies digest, kind, canonical form, domain, counts, and all semantic references.

- Revision commits name exact parent or parents, root object, semantic schema, package map, and publication metadata required for replay.

- Nondeterministic timestamps, host paths, and process IDs do not enter semantic commit identity.

- Durable entity IDs remain explicit object contents.

- Write missing objects before writing the commit object.

- Flush and sync according to a documented crash contract.

- Publish one compact head reference last.

- Never acknowledge a commit whose head durability is unknown without an explicit unknown-outcome error and authority shutdown.

- Concurrent duplicate object writes are idempotent or serialized safely.

- Existing object bytes are never silently overwritten.

- A digest collision or mismatched existing object causes hard rejection.

- Symlinks, nonregular files, path traversal, and noncanonical names reject.

- Object counts and transitive traversal are bounded.

- Restart can validate head and reachable closure without decoding all unreachable history unless policy requires it.

- A full reconstruction and semantic validation oracle remains available.

- Garbage collection has an explicit root set, lease or pin model, interruption behavior, and mark/sweep or equivalent correctness argument.

- Compaction never changes semantic commit identity.

- Package caches and workspace stores have explicit trust and retention domains.

### 8.4 Delta-log candidate requirements

- The log stores normalized semantic changes, not untrusted proposal syntax.

- Every record has exact length, version, checksum or digest, parent state identity, and resulting state identity.

- Partial tail records are distinguishable and safely ignored or rejected under one documented rule.

- Replay is deterministic and bounded.

- Periodic checkpoints are canonical and validated.

- Compaction produces a state equivalent to full replay.

- History queries do not depend on retaining transient parser or workbench forms.

- Identity non-reuse and deletion history remain provable.

- A corrupt middle record rejects rather than being skipped.

### 8.5 Package artifact separation

- Define the workspace store as development authority and history.

- Define a publishable package artifact as a closed immutable semantic package plus exact dependency manifest.

- Define an executable artifact as derived from an exact package graph, target, compiler version or digest, backend, and policy.

### 8.6 Storage cutover gate

- Do not implement an object store solely because it is architecturally attractive.

One process keeps the engine or service connection alive for multiple commands with exact correlation and no hidden semantic state.

#### Transparent local service

The current user-managed service remains primary.

## 19. Protocol, Schema, Artifact, and Cache Epoch Rules

Backward compatibility is absent.

Version discipline remains exact.

- Change the semantic schema identity when accepted program meaning or authoritative representation changes.

- Change artifact or object format identity when durable bytes change incompatibly.

- Change protocol version only when accepted boundary bytes or semantics change.

- Change editable document version when its accepted grammar or normalization contract changes.

- Change context capsule version when its canonical fields, digest, scope, or alias semantics change.

- Change idempotency fingerprint domain when normalized request meaning or replay bytes change.

- Change cache domains when their canonical inputs or omissions change.

- Do not bump unrelated versions for documentation or internal refactors.

- Do not leave old readers.

- Do not reuse old magic for new meaning.

- Do not accept unknown fields for hypothetical future compatibility.

- Reject old forms before expensive semantic work.

- Update manifest, help, status, tests, and examples in the same milestone.

### 19.1 Canonical encoding requirements

- fixed unambiguous tag domains

- checked lengths before allocation

- checked integer conversion and arithmetic

- canonical field and collection order

- canonical UTF-8 policy

- no host-endian or pointer-width dependence

- strict trailing-byte rejection

- duplicate rejection

- foreign-domain reference rejection

- hash or checksum validation

- encode-decode-encode byte identity

- independent limits for individual objects and aggregate traversal

### 19.2 Cache requirements

- Caches are disposable derived data.

- Cache keys bind every semantic input, schema, options, target, and omission policy.

- Cache values have independent byte and item limits.

- Cache corruption causes miss or explicit rejection, never semantic acceptance.

- Cache eviction cannot change behavior.

- A client never assumes current HEAD from a cache entry.

- Cross-workspace, cross-package, cross-revision, and cross-purpose reuse rejects.

- Do not cache private provider prompts or transcripts in the repository.

- Keep `unsafe_code = "forbid"` package-wide unless an active task explicitly authorizes a narrow isolated exception.

- Do not claim transitive dependencies contain no unsafe code.

- Validate every index, length, range, handle, tag, layout, and conversion.

### 20.5 Effects and retry

- Pure transaction validation may be repeated.

- Durable publication may not be silently repeated after unknown outcome.

- Future external effects require explicit idempotency and partial-action semantics.

- Client reconnect never implies mutation retry.

- A command batch states whether later commands run after semantic rejection or transport failure.

- Required resource cleanup is deterministic and not delegated to finalization.

- Domain-separate every digest use.

- State which properties of BLAKE3 or any replacement are relied upon.

- Verify bytes against digest on load.

- Do not use truncated display digests as authority.

- Do not use content digest as semantic entity identity.

- Treat a conflicting existing object under the same digest as corruption.

- Do not add signatures, encryption, or authentication without a current threat model and key lifecycle.
