## 12. Normative deletion semantics for this vertical

Update `docs/spec/workspace.md` so the following semantics are explicit. The code and tests must
implement the specification, not an accidental ordering in the current edit loop.

### 12.1 Deletable declarations

- A user-defined product declaration is directly deletable by its stable workspace `EntityId`.
- A user-defined enum declaration is directly deletable by its stable workspace `EntityId`.
- An ordinary user function and `main` retain their current deletion semantics.
- Compiler-owned builtin operations, prelude enums, and core traits are not deletable.
- Trait declaration deletion is not part of this vertical.
- Independent implementation declaration deletion is not part of the public surface unless the
  implementation audit proves it is required for sound product deletion.

### 12.2 Owned containment cascade

- Deleting a product deletes every product-field entity owned by that product.
- Deleting an enum deletes every variant entity owned by that enum.
- Deleting an enum also deletes every field entity owned by every deleted variant.
- Owned member deletion is atomic with the container deletion.
- Owned member identities are tombstoned in the new revision.
- Owned members are reported as deleted semantic entities.
- No surviving containment edge may point into a deleted container.
- No direct member deletion operation is exposed in this vertical.
- Reject direct member deletion rather than trying to infer a new product or enum shape.

### 12.3 Independent dependencies

Do not silently delete arbitrary functions, main, other products, other enums, or unrelated
declarations merely because they depend on a deleted nominal declaration.

- A surviving callable body reference blocks deletion unless an existing structural edit removes
  that reference in the same transaction.
- A surviving callable signature type reference blocks deletion.
- A surviving product field type reference blocks deletion.
- A surviving enum field type reference blocks deletion.
- A surviving match pattern or match plan reference blocks deletion.
- A surviving generic substitution or witness type reference blocks deletion.
- A surviving explicit implementation witness referring to a removed implementation blocks deletion
  unless it is remapped to the same surviving semantic implementation.
- A surviving declaration dependency inside the deletion set does not block deletion.
- A dependency owned entirely by a deleted callable or deleted nominal declaration does not block
  deletion.
- The blocker selection and message must be deterministic.
- The blocker must identify the requested deletion and at least one surviving dependent using stable
  public identity and kind information.

### 12.4 Product-targeted implementation policy

The verified baseline represents explicit marker-trait implementations as top-level entities whose
meaning names one trait and one product. They have no independent body and cannot survive deletion
of their target product.

Use this default policy unless the current checkout proves it semantically wrong: deleting a product
automatically deletes every explicit implementation whose target is that product. Treat this as one
narrow product-owned lifecycle rule, not as general transitive deletion of arbitrary dependents.

- Report each cascaded implementation entity as deleted.
- Tombstone each cascaded implementation identity.
- Remove each cascaded implementation from the staged semantic program.
- Compact surviving `ImplId` values.
- Remap every surviving explicit implementation witness.
- Preserve surviving implementation public identities through private address relocation.
- Do not delete a trait merely because an implementation or target product is deleted.
- Do not delete functions or other nominal declarations automatically.
- If current semantics establish that implementations are independent declarations, support their
  explicit same-batch deletion instead and document that policy.
- Whichever policy is selected must permit deletion of an imported product that has explicit marker
  implementations without leaving an orphan or retaining stale dense IDs.

### 12.5 Final-state transaction semantics

- Collect and validate all delete intents before applying order-sensitive mutation.
- Duplicate deletion of the same stable entity in one transaction is invalid.
- Deleting a container and directly deleting one of its owned members in the same transaction is
  invalid redundant intent.
- Deleting an entity and renaming the same entity in one transaction is invalid.
- Deleting a callable root and structurally editing one of its nodes or holes in the same
  transaction is invalid.
- Deleting a nominal declaration and structurally editing a surviving callable to remove its use is
  valid when the final staged program has no dependency.
- Deleting a nominal declaration and deleting every dependent callable or nominal declaration in the
  same transaction is valid.
- The validity of a dependency-closed batch does not depend on whether the deletion edits appear
  before or after each other.
- The final staged graph, not the base graph alone, decides whether a dependency survives.
- The final staged graph, not edit-list order, decides whether a removed body reference still blocks
  deletion.
- A transaction that cannot produce a valid final semantic state publishes nothing.

### 12.6 Delete and recreate

Do not treat deletion and same-name creation as implicit replacement in this vertical.

- Reject deleting a product and creating a product with the same name in one transaction.
- Reject deleting an enum and creating an enum with the same name in one transaction.
- Reject any same-transaction form that would let a name-based product type accidentally rebind from
  the deleted declaration to a new declaration.
- A later transaction may recreate the same name after deletion succeeds.
- The recreated declaration receives a fresh stable public identity generation.
- The recreated declaration receives fresh owned member identities.
- The recreated declaration does not inherit old references, implementations, holes, nodes, or
  semantic meaning.
- A future explicit declaration-replacement operation may define identity-preserving replacement,
  but this task must not invent it implicitly.

### 12.7 Old snapshots and stale identities

- Existing immutable snapshots remain valid values after publication of a later deletion revision.
- An old snapshot continues to resolve the old declaration and compile according to its own state.
- The new snapshot rejects the deleted declaration identity as stale.
- The new snapshot rejects every deleted member and cascaded implementation identity as stale.
- A reused slot must have a strictly newer generation.
- A foreign namespace must fail before slot or generation lookup.
- A stale identity must never resolve to a surviving or recreated object.
- A failed transaction must not advance generations or consume free-list slots.

### 12.8 Completeness

- Deleting `main` continues to produce an honest missing-entry-point blocker.
- Deleting a nominal declaration does not by itself make a dependency-free program incomplete.
- A transaction with an unresolved surviving nominal dependency is invalid rather than published as
  an executable placeholder.
- Typed holes continue to carry exact expected types and stable visible entities.
- A hole or blocker owned by a deleted declaration is removed with that declaration.
- A surviving hole whose expected type references a deleted nominal declaration blocks deletion
  unless its owning declaration is also deleted or the hole is replaced appropriately.
- A complete resulting snapshot must pass complete HIR, ownership, match-plan, and workspace
  validation.
- An incomplete resulting snapshot must not enter complete compiler phases.

### 12.9 Diff meaning

- Emit `EntityDeleted` for the requested product or enum.
- Emit `EntityDeleted` for every owned product field, enum variant, and enum field removed by the
  cascade.
- Emit `EntityDeleted` for every implementation removed by the selected narrow product lifecycle
  policy.
- Do not emit `EntityCreated` for a surviving declaration merely because its private dense address
  changed.
- Do not emit `EntityDeleted` for a surviving declaration merely because its private dense address
  changed.
- Do not emit expression replacement for a surviving node whose public semantic node survives and
  only an internal dense product or implementation ID changed.
- Continue to emit genuine reference and call rewires caused by structural edits.
- Keep diff ordering deterministic across hash-table state and edit ordering.
- Set invalidated domains truthfully; do not claim a fine-grained incremental result that the
  implementation does not provide.

## 13. Product identity asymmetry decision gate

The current product representation deserves a focused audit because it combines three notions: dense
`ProductId`, a 256-bit declaration identity, and name-based `Type::Product`. Enums already use
stable IDs in types and expressions. Do not redesign products merely to make the two representations
look symmetric.

Before changing `Type::Product`, prove or disprove each proposition below in the current checkout.
Record the result in tests or owning documentation only when it is durable and useful; do not create
a decision record for a routine local conclusion.

- Global product names are unique within every valid complete semantic program.
- No valid same-transaction deletion path can cause a surviving `Type::Product(name)` to bind to a
  newly created declaration of the same name.
- Every product expression and product pattern carries a dense `ProductId` that is independently
  validated against the name-based type.
- Every product declaration carries a stable 256-bit identity that survives private dense
  compaction.
- Every product field carries a stable 256-bit identity that survives parent relocation.
- Public workspace type views use stable `EntityId` and therefore do not expose the name-based HIR
  identity choice.
- Old and new immutable snapshots do not share mutable HIR identity tables.
- A later recreation with the same name cannot make a stale workspace `EntityId` resolve in the new
  snapshot.
- Direct product rename remains unsupported, so name-based type identity does not currently need to
  survive rename.
- Compilation derives product metadata after semantic compaction and does not retain cross-revision
  dense product IDs.

If all propositions hold and tests demonstrate sound deletion, keep the existing product type
representation for this vertical. Add only the explicit dense `ProductId` remap that is required. Do
not spend this turn replacing product type identity for conceptual symmetry.

If any proposition is false in a way that makes deletion or survivor identity unsound, perform one
direct product nominal-identity cutover. Prefer reusing the existing stable declaration identity if
its semantic contract is correct. Do not add a fourth product identity. Update every producer,
consumer, validator, equality/hash operation, type view, analyzer path, HIR expression, pattern,
memory derivation, bytecode derivation, test, and document in one cutover. Delete the old name-only
identity path and all compatibility code.

Whether the representation changes or not, product names remain human- and AI-visible declaration
attributes. A private dense ID remains a compiler placement identity. A public workspace `EntityId`
remains the editing identity. Do not conflate these roles.

## 14. Required private compaction model

Extend the current single staged compaction boundary. Do not add an independent product-deletion
pipeline that bypasses binding and match-plan compaction.

The implementation may rename or reshape the current compaction result. Prefer one explicit result
value whose fields correspond only to identity spaces actually remapped by this vertical.

- old-to-new `BindingId` mapping;
- old-to-new `ProductId` mapping;
- old-to-new `ImplId` mapping when implementations are removed;
- old-to-new `MatchPlanId` mapping;
- per-root old binding to new local slot mapping;
- per-root old binding to new local place mapping;
- old product-vector index to new product-vector index for public entity-address relocation;
- old enum-vector index to new enum-vector index for public entity-address relocation;
- old implementation-vector index to new implementation-vector index for public entity-address
  relocation;
- enough explicit deletion facts to omit removed declarations and members from survivor relocation.

Do not add a generic `RemappableId` trait, reflection registry, variant-erased ID table, rewrite
bytecode, graph rewrite language, or plugin mechanism. Concrete maps and explicit matching are
preferable while the set is small and semantically distinct.

Do not compact stable public workspace identities. Do not compact stable enum, variant, enum-field,
runtime-layout, product declaration, or product-field semantic identities. Compact only private
dense placement identities that current validators require to be dense.

### 14.1 Product compaction

- Determine the set of deleted product declarations before rebuilding the product vector.
- Retain every surviving product exactly once and in deterministic retained order.
- Assign each survivor the dense `ProductId` corresponding to its new vector position.
- Preserve each survivor's stable declaration identity unchanged.
- Preserve each survivor's name unchanged.
- Preserve each survivor's field order unchanged.
- Preserve every surviving product-field stable identity unchanged.
- Preserve every surviving field source-order ordinal unchanged.
- Build one old-to-new `ProductId` map.
- Reject any surviving reference whose old `ProductId` is absent from the map.
- Do not retain dead product entries, tombstone placeholders, sparse vector holes, or compatibility
  aliases.

### 14.2 Enum vector compaction

- Determine the set of deleted user enum declarations by stable public identity and current private
  address.
- Retain compiler-owned prelude enums unchanged.
- Retain every surviving user enum exactly once in deterministic retained order.
- Preserve stable `EnumId` values unchanged.
- Preserve stable `VariantId` values unchanged.
- Preserve stable `VariantFieldId` values unchanged.
- Preserve stable `RuntimeLayoutId` values unchanged.
- Preserve variant and field order unchanged.
- Build an old enum-vector index to new enum-vector index map for entity relocation and private
  indexing.
- Do not rewrite stable enum IDs merely because vector positions changed.
- Do not regenerate enum layouts for surviving declarations.
- Do not retain dead enum, variant, or field metadata.

### 14.3 Implementation compaction

- Remove every implementation selected by the explicit product lifecycle policy.
- Retain every surviving implementation exactly once in deterministic retained order.
- Assign each survivor the dense `ImplId` corresponding to its new vector position.
- Remap each survivor's target `ProductId` through the product map.
- Preserve each survivor's `TraitId` because trait deletion and trait compaction are outside this
  vertical.
- Preserve source provenance for surviving imported implementations.
- Build one old-to-new `ImplId` map.
- Remap every explicit trait witness in every surviving generic call instantiation.
- Reject a surviving explicit witness whose old implementation was deleted.
- Preserve surviving implementation public `EntityId` values through private address relocation.
- Do not retain dead implementation entries or sparse `ImplId` values.

### 14.4 Existing binding and match-plan compaction

- Preserve the current binding lifecycle semantics.
- Preserve dense binding validation.
- Preserve retained-order match-plan compaction.
- Preserve per-root local-slot and place compaction.
- Preserve source-free and imported match behavior.
- Do not regress the 20,000-local and 20,000-match small-stack fixtures.
- Integrate nominal deletion before the final complete-HIR derivation.
- Keep one compaction cutover rather than running independent remap passes that repeatedly clone
  full expression trees.

## 16. Dependency analysis requirements

The final deletion decision must account for semantic dependencies, not merely explicit expression
reference edges. Use existing indexes when they are complete. Use one local staged traversal when
they are not. Do not build a second persistent dependency authority.

### 16.1 Dependency categories

- containment ownership from product to fields;
- containment ownership from enum to variants and fields;
- the narrow selected product-to-implementation lifecycle relation;
- binding signature type dependencies;
- `main` signature type dependencies;
- product field type dependencies;
- enum field type dependencies;
- expression product construction, projection, update, and pattern dependencies;
- expression enum construction, inspection, unwrap, and match dependencies;
- callable body references to nominal members or declarations;
- match-plan pattern and projection dependencies;
- generic substitution type dependencies;
- trait witness type and explicit implementation dependencies;
- hole expected-type dependencies;
- declaration dependencies exposed by workspace indexes;
- any ownership or layout fact retained inside `SemanticProgram` that names a nominal declaration.

### 16.2 Final-state deletion set

Represent requested top-level deletion intent explicitly. Expand only the owned containment and
narrow implementation cascade required by the selected policy. Do not recursively delete arbitrary
dependents.

- The set must be independent of edit ordering.
- The set must identify deleted product vector positions.
- The set must identify deleted enum vector positions.
- The set must identify deleted implementation positions.
- The set must identify every public entity that will be tombstoned.
- The set must identify callable roots already handled by the current lifecycle.
- The set must allow dependencies whose dependent is also inside the final deletion set.
- The set must reject dependencies whose dependent survives.
- The set must be validated against namespace, generation, kind, and current address before
  mutation.

### 16.3 Deterministic blockers

- Choose a stable ordering for candidate blockers, preferably stable public entity identity and then
  dependency identity.
- Report the deleted declaration's stable identity, kind, and current name.
- Report the surviving dependent's stable identity, kind, and current name.
- Report the dependency category when it is known.
- Do not expose private dense IDs as the only actionable information.
- Do not depend on hash-map iteration order.
- Do not return a random dependent when multiple blockers exist.
- Do not construct a general diagnostic graph or explanation engine.
- A small structured error variant is acceptable if it materially improves deterministic machine
  handling.
- A deterministic `InvalidTransaction` message is acceptable if no current consumer justifies a
  broader public error model.

### 16.4 Product-name lookup

The current product type representation may require name-to-product resolution during dependency
analysis and index construction. Avoid scanning the complete product vector once per encountered
product type when one local map can serve the traversal.

- Build the map once per staged validation or index build when needed.
- Validate duplicate names before relying on the map.
- Use the map only as derived lookup, not as a second mutable authority.
- Discard or rebuild it with the snapshot indexes.
- Add deterministic structural counters if they are the clearest proof that lookup work tracks type
  work rather than products times type references.
- Do not create a repository-wide symbol database.

## 17. Recommended staged transaction algorithm

The exact function names may differ, but the transaction should have one understandable atomic flow.
Avoid interleaving deletion with sequential edits in a way that makes the final result order
dependent.

1. Validate the base revision and namespace.
2. Clone the semantic program, allocator, and existing hole records into staged state.
3. Collect all `DeleteEntity` edits without mutating the program.
4. Reject duplicate, foreign, stale, wrong-kind, redundant member, delete-plus-rename, and
   deleted-root structural edit combinations.
5. Classify requested callable, product, and enum deletions.
6. Expand owned product fields, enum variants, enum fields, and the selected narrow product
   implementation cascade.
7. Precompute deleted callable roots and private binding identities using the current binding
   lifecycle.
8. Process supported creation, rename, structural replacement, hole introduction, refinement, and
   filling edits into the staged program.
9. Do not let a `DeleteEntity` edit mutate sequentially inside this loop.
10. Prune holes under structurally replaced subtrees using the existing stack-safe path.
11. Evaluate final staged dependencies against the complete deletion set.
12. Reject any surviving semantic location that references a deleted product, enum, member,
    implementation, or callable.
13. Remove deleted main and function definitions using the current lifecycle.
14. Remove deleted product and enum definitions.
15. Remove cascaded or explicitly deleted implementations.
16. Remove new holes and other staged facts owned by deleted declarations.
17. Run one explicit dense compaction and survivor rewrite across bindings, products,
    implementations, match plans, local slots, and places.
18. Preserve stable enum and nominal identities that are not dense placement identities.
19. Remap staged new-entity and new-hole private addresses.
20. Install explicit old-address to new-address relocation for every surviving public entity kind
    affected by compaction.
21. Reserve public identities only for genuinely new semantic entities.
22. Infer effects on the staged semantic program.
23. If complete, derive complete HIR and run ownership, match-plan, and complete-HIR validation.
24. If incomplete, validate the partial semantic representation without entering complete compiler
    phases.
25. Build fresh canonical workspace indexes from the staged semantic program.
26. Compute forced surviving node identities from stable owners and structural keys.
27. Reconcile public entity and node identities.
28. Tombstone every deleted public identity exactly once.
29. Refresh hole state, expected types, visible entities, blockers, and diagnostics.
30. Construct the deterministic semantic diff from stable public observations.
31. Construct truthful invalidated-domain information.
32. Publish one new immutable snapshot and increment revision only after every prior step succeeds.

## 18. Survivor entity relocation

The current callable lifecycle remaps `EntityAddress::Binding` through the binding map. Generalize
survivor relocation explicitly for nominal deletion.

- Surviving `Main` remains at `EntityAddress::Main`.
- Surviving binding-backed entities relocate through the binding map.
- Surviving products relocate from old product vector index to new product vector index.
- Surviving product fields relocate with their parent product and unchanged field ordinal.
- Surviving enums relocate from old enum vector index to new enum vector index.
- Surviving enum variants relocate with their parent enum and unchanged variant ordinal.
- Surviving enum fields relocate with their parent enum, unchanged variant ordinal, and unchanged
  field ordinal.
- Surviving traits keep their current addresses because trait deletion and compaction are outside
  this vertical.
- Surviving implementations relocate from old implementation vector index to new implementation
  vector index.
- Deleted entities have no relocation entry.
- New entities receive freshly reserved stable identities.
- No two old stable identities may relocate to one new private address.
- No one old stable identity may relocate to two new private addresses.
- A relocated entity kind must equal its old public kind.
- A relocated owned member must retain the same stable owner identity after reconciliation.

Prefer a direct old-address to new-address map or a small explicit relocation result. Do not infer
survival by names after deletion. Names are not public identity.

## 19. Node identity preservation

Nominal dense-ID compaction may rewrite private contents inside a surviving expression node without
changing its semantic node identity. Preserve the existing public node identity law.

- A node survives when its stable semantic owner survives, its structural position survives, and no
  structural edit targets its subtree.
- Changing an internal dense `ProductId` from old placement to new placement does not by itself
  create a new public node.
- Changing an explicit dense `ImplId` witness from old placement to new placement does not by itself
  create a new public node.
- Deleting an unrelated earlier product or enum must not churn public node identities.
- Deleting a callable removes all nodes owned by that callable.
- Replacing a subtree removes the targeted node and descendants according to current structural edit
  semantics.
- Node reconciliation must remain iterative and deterministic.
- Do not compare rendered source or private dense IDs to decide node survival.

## 20. Hole and incomplete-state handling

- Remove every hole owned by a deleted callable.
- Remove every hole whose context node is structurally removed.
- Nominal declarations currently own no expression body holes; do not invent nominal member holes.
- A surviving hole expected to produce a deleted product or enum blocks deletion.
- A surviving hole whose visible entity set contained the deleted declaration must refresh that set
  after deletion.
- A surviving hole must retain its stable `HoleId` when its backing node survives.
- A deleted hole identity must be stale in the new snapshot.
- No hidden valid expression may be retained beneath a hole to make deletion easier.
- Completeness blockers and diagnostics must be regenerated from staged semantic truth.
- An incomplete snapshot remains compilationally blocked before memory, SSA, and bytecode phases.

## 21. Query, projection, and pagination behavior

- Entity pages omit deleted declarations and members.
- Entity pages preserve surviving stable IDs and deterministic ordering.
- Entity type facts resolve surviving product and enum types to surviving stable nominal entities.
- A type fact never resolves a deleted nominal name to a different declaration.
- Constructor queries omit constructors for deleted products and enums.
- Constructor queries continue to describe surviving declarations after private compaction.
- Match views omit deleted plans and remain valid for surviving plans.
- Containment queries omit deleted members and preserve surviving owner relationships.
- Dependency queries contain no edge to or from a deleted public entity in the new snapshot.
- Reference and call queries contain no stale target.
- Projection slices omit deleted nodes and entities.
- Projection roots using a deleted identity fail as stale.
- Projection roots using a surviving identity continue to work after private relocation.
- Continuation tokens remain revision-scoped and fail deterministically against a different
  revision.
- Pagination never silently truncates results.
- Ordering must not depend on hash-map state.
- Old snapshots retain their own query and projection behavior.

## 23. Complexity and performance contract

This vertical may continue to clone the staged semantic program and rebuild indexes. That is the
current simple architecture. Do not add incremental recomputation before representative edit
workloads demonstrate repeated equivalent work and a worthwhile invalidation boundary.

Within the current full-recomputation architecture, nominal deletion must not introduce avoidable
quadratic or deletion-count-multiplied work.

- Collect requested deletions once.
- Expand owned member and implementation deletion once.
- Build each old-to-new dense-ID map once.
- Traverse each surviving expression tree at most a constant number of explicit times required by
  the existing transaction pipeline.
- Traverse each surviving match pattern at most a constant number of explicit times.
- Traverse each stored type tree at most a constant number of explicit times per owning validation
  or rewrite phase.
- Do not scan all products for every dense product reference.
- Do not scan all products for every product type when one local name map is available.
- Do not scan all implementations for every witness.
- Do not rescan the whole semantic program once per deleted declaration.
- Do not repeatedly reconstruct address maps inside inner loops.
- Do not render or parse source.
- Do not derive memory, SSA, or bytecode for incomplete snapshots.
- Do not retain dead product, enum, implementation, binding, plan, slot, or place entries.
- Use checked capacity calculations and fallible reserve paths where surrounding code treats
  allocation failure explicitly.
- Keep user-controlled expression, pattern, and type traversals iterative.

The intended structural complexity is expected linear work in declarations, stored type nodes,
expression nodes, pattern nodes, implementation and witness records, holes, and rebuilt index
records, modulo normal hash-map behavior.

## 24. Anti-patterns that fail this task

- Allowing a same-name creation to capture a surviving name-based product type.
- Validating dependencies only against the base snapshot.
- Making validity depend on the order of delete edits.
- Applying delete edits sequentially before structural edits can remove references.
- Relying on final HIR validation as the only user-facing deletion blocker.
- Using hash-map iteration order to select diagnostics or diff entries.
- Adding a generic graph database to compute one staged dependency closure.
- Adding a generic visitor framework merely to avoid writing explicit matches.
- Adding a product/enum deletion cache.
- Adding persistence or serialization because deletion introduces tombstones.
- Adding source regeneration to simplify remapping.
- Keeping both old and new product type identities behind conversion adapters.
- Adding an edition or feature flag for the corrected behavior.
- Adding numeric limits to make scale tests pass.
- Using recursive product, type, expression, or pattern traversal on user-controlled depth.
- Weakening existing lifecycle, convergence, ownership, or cleanup tests.

- Committing the prompt, temporary audit, raw output, or copied context.
