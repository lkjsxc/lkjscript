## 0. Executive Directive

The previous campaign completed a high-value semantic convergence. It replaced universal durable
identity for anonymous function-body structure with revision-local identity, made the direct
Engine the primary topology, retained one exact editable semantic document, isolated the
machine-contract catalogue, and converted historical campaign material into current
specifications and evidence.

Do not repeat that campaign. Do not restore the architecture it deleted. Do not treat its
successful decisions as permanent merely because they are recent.

The repository is now unusually rigorous for a language that still cannot close the lifecycle of
a normal distributable application. It can author and execute pure programs from a workspace,
but it has no independently runnable application artifact, no first-class program tests, no
package distribution contract, no useful host invocation profile beyond direct typed Run, and no
evidence that its largest runtime and schema-maintenance mechanisms pay for themselves on
representative applications.

> What is the smallest coherent architecture that lets a coding agent create, test, seal,
> inspect, distribute, and run a useful lkjscript application through compact exact
> interactions, while deleting semantic, runtime, schema, topology, and repository complexity
> that does not earn its permanent cost?

This is an application-closure campaign, not a feature-accumulation campaign.

Application closure means that one representative program can be authored through the supported
agent surface, reviewed deterministically, tested through an immutable oracle, sealed or built
from an exact accepted revision, moved away from its development workspace, inspected without
implementation source, run through a public invocation boundary, reproduced after restart, and
rejected safely when corrupt or incompatible.

The campaign must treat deletion and simplification as first-class outcomes.

The campaign must also treat current absences as hypotheses rather than doctrine. A package
graph, a test entity, text, a collection, a host adapter, a bytecode image, or a service may be
justified. None is justified merely because mature languages usually have one.

The preferred final result is one smaller, more application-capable system. A larger system with
more names but no closed application lifecycle is a failure.

### 0.1 Mandatory strategic questions

1. Can a sealed, target-neutral application artifact close the first useful lifecycle without
   prematurely implementing a reusable package ecosystem?
2. Should the artifact contain validated semantic closure, verified Core IR, or both as
   explicitly distinct layers?
3. Can a pure byte-stream or exact typed invocation profile produce useful command-line
   applications before a general host-effect system exists?
4. What is the smallest first-class test contract that travels with an application and improves
   coding-agent work without creating a second assertion language?
5. Do the current `Package` and `Module` entities have enough observable semantics to justify
   durable identity and permanent hierarchy, or should they be collapsed, redesigned, or made
   real?
6. Does the 153,226-byte manually assembled contract catalogue have a current consumer worth its
   duplication, or should it be derived, narrowed, or deleted?
7. Does the ownership-plan plus managed-handle runtime provide enough absolute end-to-end
   benefit to justify its implementation and verification surface on representative byte
   workloads?
8. Does the current bracketed editable document remain the best authoring projection after
   identity stratification, or can a more source-like exact document reduce proposal and
   correction cost without becoming authority?
9. Should the optional daemon remain after the direct Engine and session became primary, or is
   its diagnostic value below its permanent source and binary cost?
10. What evidence would actually justify changing full snapshots, full scans, one-writer
    publication, Core IR, or the explicit-frame interpreter during this campaign?

### 0.2 Default strategic hypothesis

1. Retain one authoritative typed semantic program model, immutable accepted revisions, strict
   rejection, deterministic transactions, identity stratification, exact-base mutation, and one
   simple executable oracle.
2. Create an immutable application artifact that contains one exact runnable semantic dependency
   closure and one explicit invocation contract, but does not contain workspace history,
   idempotency records, caches, aliases, or unrelated declarations.
3. Make the first application artifact target-neutral and independently validated. Treat a
   native image, bytecode cache, or Core IR image as a separate derived executable artifact
   unless evidence proves a combined format is simpler and equally clear.
4. Provide at least one useful pure invocation profile. The strongest bootstrap candidate is a
   deterministic `bytes -> bytes` stream profile that maps standard input to the entry argument
   and the successful result to standard output while mapping traps to explicit process failure.
5. Add the smallest first-class test representation that can be selected, carried with an
   application, run without publishing workspace state, and reported deterministically. Prefer
   exact entry invocation plus expected value or expected trap over a general assertion
   language.
6. Make package and module hierarchy earn its semantics. If the campaign cannot identify a real
   export, dependency, visibility, provenance, or distribution consumer, collapse or redesign
   premature structure rather than preserving names.
7. Replace copied contract facts with one reviewable executable owner, or delete introspection
   surfaces whose only consumer is historical. Do not automatically choose a proc macro, build
   script, IDL, or generic JSON Schema library.
8. Rebenchmark the current ownership planner against simple safe owned values, `Arc` or `Rc`,
   and an invocation arena on representative applications. Delete the planner and managed-handle
   machinery if absolute savings are marginal relative to code, tests, Miri cost, and
   maintenance risk.
9. Retain full canonical workspace snapshots, full-scan queries, direct Engine topology, one
   writer, and the interpreter unless an application-derived measurement crosses a documented
   reversal threshold.
10. Evaluate the current editable document and at least one materially different exact authoring
    projection on equal tasks. Keep one active proposal grammar and delete losing paths.
11. Measure agent cost using actual provider telemetry only when exposed. Otherwise report exact
    command, byte, process, file-open, correction, and elapsed proxies without relabelling them
    as tokens or money.
12. After direct cutover, retain one current root policy, one current campaign prompt while it
    has a consumer, concise current documentation, and Git history as the archive.

This hypothesis is not pre-approved implementation. Reproduce the baseline, test serious
alternatives, and reverse any item that loses on the complete evidence.

## 4. Claims, Evidence, and Decision Rules

Classify every material statement before using it to retain architecture.

- `enduring invariant`: independent of current implementation.
- `accepted contract`: normative observable behavior owned by a specification and executable
  contract.
- `verified baseline`: reproduced behavior of the exact checkout.
- `controlled observation`: a bounded comparison whose environment and limitations are recorded.
- `benchmark distribution`: repeated measurements with sample count and appropriate statistics.
- `experimental hypothesis`: a proposed explanation or direction awaiting evidence.
- `historical fact`: useful context that does not govern the active tree.

Do not promote a controlled observation to a universal benchmark. Do not promote a bootstrap
absence to a permanent semantic prohibition. Do not promote a storage digest, compiler index, or
process exit convention to semantic identity without an explicit contract.

### 4.1 Evidence ladder

1. Compile-time type and lint rejection.
2. Focused deterministic unit or property tests.
3. Independent verifier or reconstruction oracle.
4. Public-path integration test.
5. Failure injection across each lifecycle edge.
6. Deterministic malformed-input or mutation corpus with recorded seed.
7. Miri, sanitizer, fuzzing, or model checking when applicable.
8. Representative application replay.
9. Equal-task agent comparison.
10. Repeated performance distribution.

Use the lowest-cost evidence that can falsify the decision. Do not run expensive provider trials
before deterministic architecture candidates pass their oracles.

### 4.2 Complexity budget

- Count production source, verification source, generated source, dependencies, build scripts,
  proc macros, binaries, protocols, artifact versions, and public commands.
- Measure clean and incremental build time when architecture changes compilation.
- Measure focused-test selection and full-suite cost.
- Measure source files and source bytes needed for representative maintenance tasks.
- Measure runtime allocations, copies, peak retained bytes, result bytes, fuel, and wall time
  separately.
- Measure application artifact bytes and workspace retained bytes separately.
- Measure command count, process count, input bytes, output bytes, corrections, and provider
  telemetry separately.
- Assign a deletion target to every winning replacement.

### 5.3 Program tests

- External Rust or Python fixtures only.

### 5.4 Package and module semantics

## 7. Execution Plan

The phase order is evidence-oriented, not bureaucratic. Combine phases when one dependency-
closed implementation naturally owns them. Do not skip an exit gate merely because later work
appears more interesting.

If a candidate fails its gate, remove it before continuing. Do not carry losing alternatives
behind feature flags.

The campaign may finish with fewer new subsystems than the default hypothesis when deletion or a
narrower artifact closes the application lifecycle more coherently.

### 7.1 Phase 0 — Checkout safety and instruction convergence

Goal: Establish the exact active state and prevent stale campaign assumptions from governing
work.

- Run `git status --short`, `git branch --show-current`, and `git rev-parse HEAD`.
- Identify untracked, modified, staged, or user-owned work and preserve it.
- Read the replacement root `AGENTS.md` completely.
- Confirm that this file is the explicitly selected campaign prompt.
- Read `docs/status.md` before architecture decisions.
- Read only the owning specifications and source needed for the first hypothesis.
- Inventory files under `prompts/` and mark the prior prompt for deletion after this prompt is
  active.
- Record the exact toolchain, OS, architecture, CPU, memory, filesystem, and lockfile digest.
- Record unavailable tools without installing broad dependencies automatically.
- Do not create a branch, commit, push, or pull request unless the active invocation authorizes
  it.

Exit gate: A concise starting record names commit, worktree, active instructions, environment,
and unrelated work.

Rollback rule: No repository behavior or remote state has changed.

### 7.2 Phase 1 — Reproduce the complete verified baseline

Goal: Ensure later regressions and improvements are measured against the actual checkout.

- Run formatting check.
- Run all-target/all-feature Clippy with warnings denied.
- Run all-target/all-feature tests.
- Run the release build.
- Run every retained public example through its production script.
- Run focused identity-stratification, document, transaction, persistence, compile, runtime, and
  old-version rejection controls.
- Measure warm and cold command boundaries separately where practical.
- Record current CLI and daemon release binary sizes.
- Record current source and test bytes and lines by owner.
- Record current machine-contract manifest and full-description bytes.
- Record current maintenance process, stdin, stdout, and context bytes using the retained
  deterministic corpus.
- Record current ownership and allocate-new metrics on all existing byte controls.
- Hash retained evidence inputs and outputs.
- Do not update expected files merely because a baseline differs from an old prompt.

Exit gate: The unchanged checkout passes or every pre-existing failure is isolated and reported
before edits.

Rollback rule: If the baseline is not trustworthy, stop architecture work and repair or
accurately bound the baseline first.

### 7.3 Phase 2 — Build a current fact and complexity map

Goal: Locate the real cost centers and avoid solving remembered architecture.

- Map semantic type and operation ownership.
- Map transaction normalization, allocation, validation, diff, publication, and receipt
  ownership.
- Map context, document, help, view, diff, test, build, compile, and run flows.
- Map machine-contract DTO, descriptor, codec, sample, help, and agreement facts.
- Map runtime value, ownership plan, verifier, managed store, interpreter, policy, and result
  materialization facts.
- Map workspace artifact, HEAD, lock, restart, idempotency, and failure-injection facts.
- Map every current use of `Package` and `Module` entities.
- Map every current unique consumer of the daemon and socket transport.
- Map every source file opened by one representative semantic addition.
- Map every full-scan query used by application closure.
- Identify copied facts and generated facts separately.
- Identify dormant code, old terminology, stale tests, and prompt-derived comments.
- Create no permanent architecture inventory document unless it has a future owner.

Exit gate: The campaign has a disposable or handoff-local dependency map sufficient to choose
prototypes.

Rollback rule: Delete exploratory inventory files before final cutover unless a current document
owns the retained facts.

### 7.4 Phase 3 — Select representative applications and independent oracles

Goal: Anchor architecture in real complete workflows.

- Evaluate `binary-canonicalizer` as the primary pure byte-stream application.

- Define exact accepted inputs and outputs for each selected application.
- Define deterministic invalid-input behavior and runtime traps.
- Define exact resource policies.
- Define an independent oracle outside the candidate artifact implementation.
- Define the sequence of authoring revisions needed to build, repair, refactor, test, and

- Define a corruption and wrong-version matrix.

## 8. Application Artifact Contract Requirements

The following requirements apply if the campaign selects an application artifact. They
intentionally constrain authority, identity, corruption, and standalone execution while leaving
physical layout open to evidence.

### 8.1 Required logical facts

- Artifact kind and unambiguous format version.
- Accepted semantic schema identity.
- Canonical content digest under an application-specific hash domain.
- The exact selected semantic closure.
- The exact application entry or explicit bounded export set.
- The invocation profile and its exact signature obligations.
- The exact first-class test set or test-set binding.
- All nominal declarations and members required by entry, public values, and tests.
- All called functions and reachable body structure required by entry and tests.
- Explicit bounds needed to decode, validate, compile, test, and run.
- Optional non-authoritative display metadata only when it has a current consumer.
- A deterministic manifest projection derived from validated facts.

### 8.2 Forbidden logical facts

- Mutable current HEAD.
- Workspace lock state.
- Prior workspace revisions.
- Idempotency receipt history.
- Context packet aliases or digests used only for editing.
- Proposal syntax or formatting.
- Absolute filesystem paths.
- Temporary build paths.
- Unrelated workspace declarations.
- Compiler-private dense IDs as semantic identity.
- Runtime handles or allocator state.
- Provider, transcript, or coding-agent metadata.
- Timestamps or randomness inside canonical content unless accepted semantics require them.
- A cache payload presented as semantic authority.

### 8.3 Identity questions that must be answered

1. Does the artifact retain workspace-qualified entity IDs, translate them to an artifact
   namespace, or embed an explicit mapping?
2. What equality and continuity meaning do nominal IDs retain after transfer?
3. Can two artifacts contain equal semantic content under different entity identities?
4. Can an artifact be rebuilt deterministically after names change but identities remain?
5. Can an artifact be imported, copied, or forked, or is it explicitly run-only?
6. Does artifact-local identity survive application rebuilds, and who consumes that continuity?
7. How do test expected nominal values bind to artifact-local declarations and members?
8. How does a diagnostic identify a local function-body term after transfer?
9. What domain separates semantic content digest, artifact file digest, executable digest, and
   receipt digest?

### 8.4 Decoder obligations

- Reject unknown magic, kind, version, schema, section, tag, field, and enum value.
- Reject noncanonical integers, lengths, ordering, IDs, names, and encodings.
- Reject duplicate sections, entities, tests, exports, fields, and mappings.
- Reject zero, excessive, overflowing, or inconsistent lengths and counts as applicable.
- Reject truncated, trailing, hash-mismatched, wrong-domain, and foreign-identity data.
- Reject dangling ownership, type, call, nominal, operand, control, test, entry, and profile
  references.
- Reject incomplete reachable functions, holes, invalid terminators, and invalid local domains.
- Reject invalid public test values before flattening or execution.
- Reject resource policies outside accepted bounds.
- Perform size and count checks before large allocation.
- Use iterative traversal for attacker-scalable depth.
- Re-run the full independent semantic or executable verifier before acceptance.

### 8.5 Build-state machine

1. Open the exact workspace authority or immutable source artifact.
2. Resolve exact workspace and revision; never use implicit current state in a machine contract.
3. Select exact entry and test set.
4. Compute complete dependency closure.
5. Reject incomplete or invalid closure.
6. Validate invocation profile compatibility.
7. Run declared release tests under exact policies when the selected contract requires them.
8. Construct the candidate logical artifact.
9. Validate the candidate independently from builder assumptions.
10. Encode canonical bytes.

## 9. First-Class Test Contract Requirements

Use these requirements if tests become part of semantic or application content. Do not confuse
them with Rust implementation tests.

### 9.1 Minimum test case

- Exact owner or application binding.
- Stable name only if name-based selection is useful.
- Identity only as strong as continuity consumers require.
- Exact target function or export.
- Exact typed argument list.
- Exactly one expected outcome: success value or typed runtime trap.
- Exact Run policy or an explicitly versioned policy profile.
- Canonical order.
- Optional bounded explanatory text only with a real consumer.

### 9.2 Test acceptance

- Validate target and signature before publication.
- Validate all argument and expected values against exact types and identity domains.
- Validate expected trap against the stable observable trap contract.
- Reject unreachable or incomplete test closure.
- Reject duplicate identity, owner, or selection keys.
- Reject a test that depends on implicit HEAD, environment, host time, random state, or
  repository path.
- Do not let test execution publish workspace revisions.
- Do not let a trap poison a reusable Engine or session.
- Charge exact per-case and aggregate resources.
- Bound result and diagnostic materialization.

### 9.3 Test result model

- `passed`: observed outcome exactly matches expected outcome.
- `unexpected_value`: successful value differs under exact typed equality.
- `unexpected_trap`: execution trapped when success was expected.
- `missing_trap`: execution succeeded when a trap was expected.
- `wrong_trap`: trap code or accepted stable target differs.
- `invalid_case`: the test contract itself is malformed or stale.
- `incomplete`: dependency closure cannot compile.
- `resource_failure`: test or suite policy is exhausted.
- `engine_failure`: trusted operation could not complete and no semantic verdict is claimed.

Do not collapse these into one text string. Do not claim `passed` after skipping, resource
exhaustion, unsupported version, unavailable entry, or output truncation.

### 9.4 Test review and agent context

- Show exact owner, target, argument and expected-outcome types, and current pass status when
  known.
- Summarize large values with exact digest and bounded expansion rather than silently
  truncating.
- Include failing tests and blockers in repair, debug, build, and review packets.
- Make test edits explicit; omission never deletes a test.
- Show whether a test is included in the application artifact and release gate.
- Bind aliases to the exact packet and test identity domain.
- Report stale tests after declaration replacement or entry changes.

## 10. Pure Process Invocation Profile

The campaign should prefer a narrow pure process profile when it can demonstrate useful
applications without a general effect system.

### 10.1 Candidate byte-stream profile

- The selected entry accepts exactly one `bytes` value and returns exactly one `bytes` value, or
  another equally explicit signature selected with evidence.
- Standard input is read under an exact maximum decoded byte policy.
- No newline, UTF-8, locale, terminal, or text interpretation is implicit.
- Successful result bytes are written exactly to standard output.
- Human diagnostics are terminal-safe and do not corrupt machine output.

  semantic output or trap.

- Retain exact public-value invocation for applications whose entry is not stream-compatible.
- Bind arguments to artifact-local exact types and nominal identities.

- Use strict bounded machine input and output.

- The representative applications can receive all required input as exact values or bytes.

all lifecycle contracts instead of extending the stream adapter informally.
