## Executive objective

The required semantic surface is ordered sequencing, explicit mutable-local introduction, assignment to a mutable local, and `while`.

## Why this task is selected

- The normative language already supports ordered blocks, explicit mutation, `while`, loops, `break`, `continue`, and early return.
- The HIR already contains sequence, mutable-local, assignment, `while`, loop, and control-transfer forms.
- The source resolver already implements mutable-local initialization, lexical scope, exact assignment typing, and `while`.
- The compiler, ownership analysis, memory planning, SSA, bytecode, and VM already consume these HIR forms.
- The semantic workspace already indexes and projects imported mutable-local and `while` nodes.
- The source-free `ExpressionDraft` currently lacks sequence, mutable-local, assignment, and `while` forms.
- The source-free operation surface currently supports addition but not the comparison needed by a natural counted loop.
- The repository retains scalar-loop examples and fixtures that demonstrate a real current program shape.
- Therefore the missing work is a source-import/source-free convergence gap rather than a request for a new language subsystem.
- Closing this gap enables a representative nontrivial program and exercises scope, mutation, effects, identity, lifecycle, compilation, and execution together.
- General public movement would be architecturally tidy but does not presently demonstrate an equally concrete program it unlocks.
- This task is intentionally chosen to resist speculative platform work and API taxonomy completion for its own sake.

## Semantic contract

- Ordered sequencing evaluates children from first to last.
- An empty ordered sequence has type `unit` unless the accepted language specification states otherwise.
- A non-empty ordered sequence has the type of its final reachable child.
- A sequence rejects an expression after a child whose type is `never`.
- Effects are the ordered union of child effects.
- Sequence construction must not fabricate source provenance.
- Mutable-local introduction explicitly declares mutation intent.
- The initializer is resolved and evaluated before the new binding enters scope.
- The body is resolved with the new binding in scope.
- The mutable-local expression has the type of its body.
- The declared storage type is semantically explicit.
- The initializer type must exactly satisfy the declared storage type under the existing type rules.
- A divergent initializer cannot initialize storage.
- The existing storage restrictions for `never`, lexical references, resource-bearing aggregates, products, and type parameters remain authoritative.
- Do not duplicate those restrictions in a second hand-maintained rule set.
- Assignment targets only a visible mutable local owned by the same callable scope.
- Assignment cannot target a parameter, immutable local, static-bytes local, match temporary, function, or builtin.
- The assigned value must exactly satisfy the target storage type.
- A divergent assigned value cannot fill the storage slot.
- Assignment has type `unit`.
- Assignment carries the established local-mutation effect plus value effects.
- A mutable local may be loaded only when the existing ownership rules permit a copy.
- An affine mutable value must not be copied through `Load`.
- Move and borrow behavior must use the existing ownership semantics.
- `while` evaluates its condition before each iteration.
