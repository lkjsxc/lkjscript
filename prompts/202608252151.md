## 2. Primary objective

Close the current public semantic-change interface as a self-describing, transport-neutral workflow.

After completion:

1. every one of the 13 already-public compact semantic operations has complete executable field metadata;
2. that metadata is the sole authority for each operation's accepted field set and required/optional classification;
3. executable discovery provides enough typed form information for an agent to construct those operations without reading Rust source;
4. one common operation, `rename.owner`, is available through direct CLI flags as a vertical proof that compact records are a transport adapter rather than semantic authority; and
5. direct and record forms converge before planning, produce the same normalized typed request and reviewed plan, and use the same preparation, validation, response, publication, and failure paths.

Do not expose additional private authored operations in this campaign. Do not cut over another command family.

## 3. Why this objective is selected now

The active checkout already exposes 13 compact operations through `COMPACT_CHANGE_OPERATIONS`, but `COMPACT_CHANGE_OPERATION_FIELDS` describes only `delete.owner`. The decoder therefore carries twelve independent inline field lists that executable discovery cannot report. An agent can discover operation names, type forms, expression forms, deletion policy, and semantic preconditions, but must still inspect source or guess most operation grammars.

The current campaign ledger names complete operation-field discovery plus one common direct edit as the exact next action. The control-representation decision also requires direct common flags to lower through the same typed path. Completing those two coupled obligations removes a present agent bottleneck without changing semantic authority, storage, compiler, runtime, or maintained application data.

## 4. Definition of success

5. The current compact record grammar and semantics remain available; raw JSON and predecessor change flags remain rejected.
6. The following direct forms are public and discoverable:

   ```text
   lkjscript [--project PATH] change plan rename.owner \
     --base REVISION --owner OWNER --name NAME \
     [--idempotency KEY] [--intent TEXT]

   lkjscript [--project PATH] change apply rename.owner \
     --base REVISION --owner OWNER --name NAME \
     [--idempotency KEY] [--intent TEXT] --plan PLAN
   ```

7. Direct `--owner` accepts one exact typed `OwnerKey`, not a request-local symbol or name lookup. Direct `--base` is mandatory. Direct apply requires the exact reviewed plan.

   ```text
   rename.owner owner=OWNER name=NAME
   ```

9. Plan mismatch is rejected before repository discovery or repository access. Stale base, malformed input, semantic rejection, resource exhaustion, corruption, and infrastructure failure never advance accepted authority.
10. Direct apply uses `GraphRepository::prepare_authored_change` and the existing publication boundary. There is no direct writer, alternate receipt, alternate allocation, or alternate validation path.
11. The CLI public contract version is advanced from 5 to 6 for the new accepted direct grammar. The compact record contract remains `lkjscript-change-records-3`, and the plan digest domain remains `lkjscript.change-plan.v4`.
12. Generated contract documentation matches executable output exactly.
13. Normative documentation, current status, the control-representation decision, examples, and campaign ledgers describe the final public behavior without claiming broader normalized cutover.
14. Focused checks pass during iteration and the final `lkjscript-dev check full` result is fresh for the final content. Any environment-dependent unavailable check is reported as unavailable, never as passed.

## 6. Decision classification

### 6.1 Mandates

Codex must not change these conditions.

- The accepted typed semantic graph remains the sole program authority.
- Compact records and direct flags are non-authoritative request transports.
- The executable registry owns the finite public vocabulary.
- Every accepted write names one exact base and has one publication visibility point.
- Plan and apply use the same typed normalization and preparation path.
- Failed work cannot advance HEAD.
- Direct apply requires the exact plan returned for the exact normalized request.
- Record input remains available for batched, connected, and preconditioned changes.
- Raw JSON, predecessor request flags, compatibility aliases, and fallback readers remain rejected.
- The current 13-operation semantic subset is not expanded.
- No source text, macro language, storage-record authoring path, session, daemon, cache, JIT, allocator, `unsafe`, or new dependency is introduced for this campaign.
- `lkjscript-change-records-3` and `lkjscript.change-plan.v4` remain unchanged.
- The CLI contract version becomes 6 because the accepted public command grammar expands.
- Generated files are regenerated from the executable, never hand-edited.
- Unrelated user work and historical prompts are preserved.

### 6.2 Selected design

Follow this design unless active-checkout evidence clearly disproves an assumption.

#### One operation grammar authority

Replace the independent operation-name list, incomplete flat field table, and twelve inline decoder whitelists with one compile-time descriptor inventory, or derive every one of those views from one inventory.

Represent the public subset with one closed `CompactChangeOperation` enum or an equivalently exhaustive typed key. Each descriptor must own:

- the typed operation key and public name;
- ordered field descriptors;
- field name;
- required/optional status;
- typed form token; and
- whether the operation has a direct CLI form.

Parse the record operation once into that typed key. `Decoder::decode_change` must match the typed key exhaustively rather than matching an independently maintained string list. Operation lookup, field validation, registry projection, registry self-validation, generated documentation, and direct-operation discovery must consume the same descriptors.

Delete `COMPACT_CHANGE_OPERATIONS` and `COMPACT_CHANGE_OPERATION_FIELDS` as independent authorities. They may remain only as derived views when a real consumer requires their exact type.

Registry validation must prove at startup or test time:

- operation names are unique and nonempty;
- every descriptor has at least one field;
- field names are unique within each operation;
- no field descriptor refers to an unknown operation;
- every field form is advertised;
- only `add.case.payload` is optional in the current grammar;
- the direct-operation marker refers only to `rename.owner`; and
- the descriptor inventory and semantic decoder have equal operation coverage.

Do not use a hand-maintained count as the sole coverage proof. The exact 13/49 counts are black-box acceptance observations.

#### Direct `rename.owner` adapter

Extend `change plan` and `change apply` with the exact `rename.owner` positional operation shown in the success definition.

The direct adapter must:

1. parse `--base` as `RevisionId`;
2. parse `--owner` as exact `OwnerKey`;
3. parse `--name` with `Name::new`;
4. validate optional idempotency and intent with the same functions and bounds as the record request;
5. construct:

   ```rust
   AuthoredChangeSet {
       base,
       preconditions: Vec::new(),
       changes: vec![AuthoredChange::RenameOwner {
           owner: OwnerSelector::Exact { owner },
           name,
       }],
       budget: Default::default(),
   }
   ```

6. construct the same `PublicationOptions` as the equivalent request record;
7. compute the plan only from the typed request and options;
8. enter the same common plan/apply execution function as decoded records; and
9. use the same compact response renderer and exit classification.

Do not synthesize compact text and reparse it. Direct flags and compact records are sibling adapters to the typed request. Rename the current private transport wrapper if needed so its name does not imply that compact records own the normalized request.

Keep action order as `change plan rename.owner ...` and `change apply rename.owner ...`. Do not add `rename`, `edit`, `set-name`, or another alias.

For apply, parse and normalize all arguments, compute the exact expected plan, and reject a mismatched `--plan` before project discovery or repository access. Only after that comparison may the command open the normalized repository and prepare the change.

#### Discovery

`capabilities --section change` must expose:

- all 13 operations;
- all 49 operation fields;
- every current precondition and precondition field;
- current selector/reference syntax;
- current visibility values;
- current function-effect values;
- current deletion policies; and
- the fact that only `rename.owner` has a direct CLI form, including its exact usage.

Use existing registry vocabulary where possible. A small `change.direct-operation` record is acceptable. Do not duplicate a full operation schema for the direct form.

#### Versioning

- Set `CLI_CONTRACT_VERSION` to 6 and update its consumers and tests.
- Let the executable registry and section digests change from their content.
- Do not bump the registry contract merely because its current section content expands.
- Do not bump the compact change record contract or plan digest domain.
- Do not alter allocation seeds, normalized intent bytes, revision identity, or receipt identity for an equivalent record/direct rename.

## 7. Target architecture and behavior

### 7.1 Authority and data flow

The completed path must be:

```text
compact records ── parse/decode ──┐
                                  ├─> typed public change request
direct rename flags ── typed parse┘
                                           │
                                           ├─> canonical authored intent
                                           ├─> publication options
                                           └─> reviewed plan digest
                                                    │
                                   plan: prepare and report, no publication
                                                    │
                           apply: compare exact plan before repository access
                                                    │
                                      open normalized GraphRepository
                                                    │
                                      prepare_authored_change
                                                    │
                                      existing response/publication path
                                                    │
                                          one atomic accepted HEAD
```

The typed semantic request is the convergence boundary. Neither transport becomes program meaning.

### 7.2 Error boundaries

- argv grammar, missing/duplicate/unknown options, and malformed typed values: source/usage rejection;
- invalid names, identities, or idempotency: typed source rejection;
- plan mismatch: semantic rejection before repository access;
- stale base: stale outcome with process exit 7;
- invalid candidate or failed precondition: semantic rejection without publication;
- configured bound exhaustion: resource rejection;
- inconsistent canonical authority: corruption;
- filesystem/process failures: infrastructure.

Compact failure output remains deterministic and bounded. Do not write stack traces, large schemas, or child logs to stdout.

### 7.3 Persistence and resource ownership

This campaign changes no persistence format. Direct planning owns only bounded argv strings, one typed request, one plan digest, and the existing preparation objects. The repository remains owner of canonical reads, publication staging, durability, and HEAD advancement.

Do not add a resident process or cache. Do not use one scalar as a substitute for the existing multidimensional change budget.
