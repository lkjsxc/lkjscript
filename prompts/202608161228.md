## 0. Executive Directive

Preserve the daemon-owned typed program model and the Semantic Program Graph as the one authoritative semantic representation.

Do not restore the deleted source-oriented compiler.

Do not add a broad language feature merely because the current pure language is small.

Do not start with collections, effects, packages, concurrency, a database, a JIT, or self-hosting.

The next unresolved product question is more basic:

> Can an actual coding agent, using only the public machine interface and deterministic feedback, author and repair a nontrivial current-semantics program efficiently and reliably?

The repository currently has deterministic Python drivers.

Those drivers prove the public path.

They do not prove that a model can discover and use that path.

The current evidence also exposes a probable architectural mismatch.

The machine-facing control plane is much more complicated than the current product needs.

The current path performs strict JSON decoding in the CLI, converts the same closed request to a second private binary encoding, opens one Unix connection, decodes the second encoding in the service, and maintains a very large generated-description surface for both.

That design may have been a reasonable bootstrap experiment.

It is not an enduring requirement.

The active evidence makes it a prime candidate for deletion.

The campaign must begin with a controlled black-box agent task.

The campaign must then make the smallest dependency-closed interface correction supported by that evidence.

The default architectural hypothesis is:

> Use one strict, versioned, bounded, inspectable control-plane representation end to end; keep the binary `.lkjscript` artifact separate; remove the private custom binary RPC codec unless measured evidence proves that its benefits exceed its duplicated code, schema, tests, and agent search cost.

The default agent-authoring hypothesis is:

> Initial program creation should use one closed semantic proposal with draft-local symbolic references and deterministic expansion, while fine-grained Node-ID edits remain the maintenance path.

The default contract-discovery hypothesis is:

> An agent should request exact contract roots and receive their complete transitive definition closure, rather than downloading broad sections containing many unrelated variants.

These are hypotheses, not slogans.

Prove or reject them through the required baseline.

If the evidence defeats one hypothesis, retain the current mechanism and record the exact reason.

If the evidence supports it, perform a direct incompatible cutover.

Do not retain a compatibility path.

Do not leave two preferred interfaces.

Do not weaken memory safety, identity, atomicity, durability, deterministic validation, or explicit authority in pursuit of convenience.

Do not claim token or cost savings from byte counts alone.

Use provider-reported telemetry only when genuinely available.

The desired campaign outcome is not merely a smaller protocol.

The desired outcome is an end-to-end programming interface that an autonomous coding agent can discover, use, repair, and verify with less ambiguity and less repeated context.

### 7.5 Required scoring oracle

Use a deterministic loop with `start = 0`, `end_exclusive = rollout_steps`, `step = 1`, and initial carried value `0`.

The loop body adds the current loop index to the carried value.

For `rollout_steps = 4`, the resulting rollout weight is `6`.

Use channel bonuses:

- stable: `1`;
- beta: `2`;
- nightly: `3`.

A successful decision returns `Decision.serve(rollout_weight + channel_bonus)`.

### 7.6 Required decision semantics

1. If `version.major < policy.minimum_major`, return `Decision.block(BlockReason.major_too_old)`.
2. Otherwise, if `version.minor < policy.minimum_minor`, return `Decision.block(BlockReason.minor_too_old)`.
3. Otherwise, handle every `Transport` alternative.
4. For `Transport.unsupported`, return `Decision.block(BlockReason.unsupported_transport)`.
5. For supported transports, handle every `Channel` alternative.
6. For `Channel.nightly`, require `trusted = true`.
7. For untrusted nightly clients, return `Decision.block(BlockReason.nightly_requires_trust)`.
8. For accepted clients, return the exact deterministic score.

## 10. Control-Plane Simplification

### 10.1 Default direction

The default direction is a direct protocol version replacement that carries the strict JSON envelope over the private Unix socket.

The durable artifact remains binary.

The control plane does not need to be binary merely because the artifact is binary.

Use existing closed Rust request and response types as the sole logical DTO vocabulary.

Use one encoder and one decoder for the public control plane.

Keep framing independent of JSON parsing.

### 10.2 Candidate direct framing

- A fixed little-endian length prefix is acceptable.
- The framed body is one canonical compact JSON envelope.
- The envelope contains the protocol version, nonzero request ID, and closed request variant.
- The response repeats the request ID.
- The request and response use the same canonical JSON shapes exposed to agents.
- Unknown fields and variants reject.
- Duplicate fields reject.
- Wrong numeric domains reject.
- Malformed canonical IDs reject.
- Trailing JSON values reject.
- Connection-level trailing bytes reject.
- Oversized frames reject before allocation.
- Output is preflighted against its exact bound.
- Semantic rejection remains a typed response, not a boundary parse error.
- A clean close before a frame remains ignorable.
- Request-side EOF is proved before dispatch if the one-request-per-connection model remains.
- Response-side EOF is proved before client acceptance.
- Timeout and shutdown behavior remain explicit.

### 10.3 Direct cutover rules

- Use a new protocol version.
- Use a new machine-schema identity.
- Use a new JSON envelope version when the public JSON shape changes.
- Do not retain protocol-v4 success decoding.
- Do not retain binary request writers.
- Do not retain binary response writers.
- Delete binary protocol tags that have no artifact consumer.
- Delete binary protocol size measurements from active acceptance where they no longer describe a product path.
- Retain historical measurements as clearly historical evidence when useful.
- Update every client, service, integration test, example, and specification in the same milestone.

### 10.4 What may remain binary

- Immutable `.lkjscript` artifact bytes.
- Durable HEAD metadata.
- Hashes and digests represented canonically at the JSON boundary.
- A future runtime data plane if a measured workload justifies it.
- Do not reuse artifact codecs for control messages.

### 10.5 Retention burden if binary RPC survives

If the custom binary RPC is retained, the completion report must include concrete evidence for all of the following.

Absence of this evidence is a reason to delete it.

- Measured equal-work latency benefit.
- Measured throughput benefit.
- Measured peak-memory benefit.
- A workload for which JSON control traffic is material.
- Why a standard serialization dependency is worse than the existing custom code.
- Why duplicate JSON and binary contract testing is justified.
- Why the code and schema search cost is acceptable for coding agents.
- A deletion condition.

## 11. Machine-Contract Discovery Redesign

### 11.1 Goal

An agent should obtain exactly the contract needed for the next semantic action, including every transitively required type definition and limit.

The response must be self-contained.

The agent must not guess omitted dependencies.

The service must not maintain a second hand-written schema.

### 11.2 Root-based projection

- Expose a compact manifest of discoverable contract roots.
- Give every root a stable lowercase identity.
- Allow exact roots for requests, responses, transaction operations, expression drafts, query families, runtime values, errors, ID formats, and limits.
- Allow a bounded unique set of roots in one request.
- Return the complete transitive closure of named definitions referenced by those roots.
- Return definitions in canonical deterministic order.
- Return each definition exactly once.
- Include the relevant scalar and ID formats.
- Include relevant limits.
- Include relevant stable error codes or error payload shape.
- Reject unknown roots.
- Reject duplicate roots.
- Reject empty root sets when a non-manifest projection is requested.
- Keep explicit full projection.
- Keep a canonical digest over the complete executable contract.
- Keep known-digest unchanged.

### 11.3 Closure integrity

- Every named type reference in a projected result must resolve inside that result or to a documented primitive.
- No projected definition may depend on a hidden broad section.
- The closure algorithm must be deterministic.
- The closure algorithm must be bounded.
- The closure algorithm must not recurse through the native stack according to descriptor depth.
- The digest must bind root identities and complete definitions.
- Projection must not alter semantics.
- Projection may be recomputed rather than cached until measured.

### 11.4 Standard schema formats

A standard schema representation may be used only if it materially reduces custom code and faithfully represents every accepted strict shape.

Do not add a dependency merely to emit a familiar label.

If JSON Schema is considered, verify all of the following.

- Tagged enum shape is exact.
- Unknown-field rejection is represented.
- Canonical IDs and numeric domains are represented.
- Required versus nullable fields are represented.
- Recursive definitions are handled.
- Generic list, page, tuple, and optional shapes are exact.
- Machine contract digest remains deterministic.
- Generated output agrees with actual serde behavior.
- Dependency and build cost are justified.
- The result is smaller or easier for the controlled agent.

A small project-owned closed descriptor can remain preferable.

Do not build a general-purpose schema compiler.

### 11.5 Acceptance evidence

- Measure the exact roots requested by the baseline task.
- Measure manifest bytes.
- Measure task-contract bytes.
- Measure full bytes.
- Measure unchanged bytes.
- Measure number of definitions returned.
- Measure repeated discovery.
- Measure lookup failures.
- Run strict agreement tests against real JSON decoding.
- Do not claim success merely because the new response is syntactically smaller.

## 12. Semantic Proposal Ergonomics

### 12.1 Principle

The service may accept a compact semantic proposal for initial construction.

That proposal is not the authoritative program.

It is not a source file.

It is not persisted.

It does not allocate persistent identities.

The service deterministically expands it into the same canonical semantic nodes and validates the final graph.

### 12.2 Evidence gate

Change structured authoring only when the baseline shows material friction from explicit handles, repeated scaffolding, or local-reference errors.

Do not redesign it merely because the JSON looks verbose.

Compare the current and candidate proposal on the same task.

- JSON request bytes.
- Explicit identifier count.
- Required returned-binding count.
- Round trips.
- Rejected proposals.
- Error precision.
- Implementation bytes.
- Tests.
- Canonical graph equality.
- Future editability.

### 12.3 Candidate draft-local symbols

- Use a distinct `DraftSymbol` domain.
- A draft symbol is transaction-local.
- A draft symbol is not a display name.
- A draft symbol is not persistent identity.
- A draft symbol may be a bounded UTF-8 identifier or another compact closed representation.
- Symbols must be unique in their declared draft scope.
- Errors must name the offending symbol and exact path.
- The service resolves symbols before persistent allocation.
- Rejected and validate-only proposals consume no persistent identities.
- Response selection may request exact draft symbols.
- Persistent receipts return Node IDs only for explicitly selected symbols.

### 12.4 Optional expression binding

- Do not require a symbol for an expression result that is never referenced later or returned to the caller.
- Allow inline single-use expressions only if the closed proposal remains easy to validate and bound.
- Require a symbol for shared or forward-referenced values.
- Do not introduce implicit dynamic name lookup.
- Do not make object-key order semantic.
- Use ordered arrays where order is semantic.
- Document deterministic expansion order.

### 12.5 Declaration references

- Permit references to existing semantic Node IDs.
- Permit references to draft-local declaration symbols.
- Do not permit persistent lookup by mutable display name as the correctness mechanism.
- A display name may be copied into a declaration but must not resolve identity.
- Forward and mutual function references must remain deterministic.
- Forward nominal type references must remain deterministic.
- Field and variant references must resolve to exact owners.

### 12.6 Canonical equivalence

- The candidate proposal must expand to the same accepted semantic graph as the equivalent existing structured transaction.
- Compare snapshot hashes when canonical allocation order is intentionally identical.
- If allocation order changes, document the semantic reason and update the accepted contract directly.
- Do not claim equivalence based only on successful execution.
- Test success, rejection, allocation rollback, validate-only, restart, diff, and selected bindings.

### 12.7 One preferred authoring path

- Initial multi-declaration construction should have one preferred aggregate path.
- Fine-grained Node-ID edits remain the maintenance path.
- Do not leave both old handle-heavy and new symbolic initial-creation paths as equally preferred public APIs.
- Delete the displaced initial-creation surface if the new path strictly subsumes it.

## 23. Long-Horizon Policy Revalidation

The campaign must review the following architecture dimensions.

Most are not implementation work for this campaign.

The purpose is to avoid turning current bootstrap choices into permanent dogma.

Update the existing fact owner only where a current document incorrectly presents a baseline as an invariant.

Do not create a new strategy document.

Use `docs/roadmap.md` for ordered gates and `docs/architecture.md` for current mechanisms.

### 23.1 Product Audience and Human Governance

Current baseline: Coding agents are the primary authors of the authoritative program model; humans supply intent, governance, review, operation, and product ownership.

Enduring requirements:

- Do not confuse agent-primary authoring with removal of human control.
- Every externally meaningful change must remain explainable and reviewable.
- Permissions, deployment, release, and destructive operations remain governed decisions.

Potentially better long-term direction:

- Treat human-readable source, diagrams, summaries, and semantic diffs as projections over exact revisions.
- Invest in review surfaces only after the authoritative mutation and identity contracts are stable.
- Evaluate whether intent-level approval receipts should be derived from transactions rather than stored as semantic state.

Decision for this campaign: Keep the current audience split. Improve the machine path first. Do not build a human IDE in this campaign.

Evidence required before entry:

- A real human review task cannot be completed from existing semantic diff and query output.
- A representative deployment workflow needs explicit approval evidence.

Stop or reversal condition: Reject any review layer that becomes a second mutable program or obscures exact Node IDs and revisions.

### 23.2 One Semantic Authority and Multiple Views

Current baseline: The SPG is the only mutable program authority. JSON, diagrams, drafts, debug views, and possible future source text are proposals or projections.

Enduring requirements:

- One accepted semantic meaning exists for each workspace revision.
- Views cannot bypass validation or allocate persistent identities.
- Round-tripping a view must never be required for normal editing.

Potentially better long-term direction:

- Allow multiple generated views when they reduce model or human reconstruction cost.
- Give every view an exact revision and projection identity.
- Prefer lossless semantic links over source-position identity.

Decision for this campaign: Retain the one-authority rule. Remove language that sounds hostile to text or visual interfaces.

Evidence required before entry:

- Controlled tasks show that a generated textual projection materially improves comprehension or review.
- The projection has a deterministic derivation and exact mapping back to semantic targets.

Stop or reversal condition: Delete a view if it begins accumulating independent mutable facts or requires parse-render cycles for correctness.

### 23.3 Single Head, Branches, and Semantic Merge

Current baseline: Each workspace has one published head and immutable linear revision history.

Enduring requirements:

- Published revisions remain immutable.
- Identity non-reuse and exact ancestry remain unambiguous.
- A merge cannot guess through conflicting semantic edits.

Potentially better long-term direction:

- Multiple agents will eventually benefit from revision branches, isolated proposals, and semantic three-way merge.
- A revision DAG may be more natural than one global mutable head once concurrent authoring is real.
- Conflicts should be expressed in semantic identities, ownership slots, and accepted continuity rules.

Decision for this campaign: Do not add branches in this campaign. Explicitly classify linear history as a current baseline, not an eternal product law.

Evidence required before entry:

- Two authorized agents need long-lived independent changes in one workspace.
- Serializing them through one head creates measured retries or coordination cost.
- A deterministic merge oracle and exact conflict vocabulary are specified first.

Stop or reversal condition: Do not introduce Git-like text merge, last-writer-wins semantics, or branch metadata as hidden program authority.

### 23.4 One Logical Writer and Process Topology

Current baseline: One logical service authority is the only live writer of durable workspace state; the current implementation is one synchronous process.

Enduring requirements:

- Exactly one authority decides publication order for a workspace.
- No worker independently writes authoritative artifacts or allocator state.
- Publication ambiguity stops the writer.

Potentially better long-term direction:

- The authority may later supervise compiler, runtime, effect, or native workers in separate processes.
- Workspace sharding may allow independent authorities for independent workspaces.
- A replicated service would require a real consensus and durability contract, not shared-file optimism.

Decision for this campaign: Keep one process and one writer. State clearly that logical authority does not require one address space forever.

Evidence required before entry:

- A real isolation, privilege, crash-containment, target, or measured concurrency need appears.
- The process protocol is smaller and safer than in-process trust.

Stop or reversal condition: Remove a worker split if it merely moves code without improving isolation, throughput, or trusted-computing-base boundaries.

### 23.5 Source-Independent Authority and Optional Text

Current baseline: No source parser exists, and source text is not required authority.

Enduring requirements:

- Programs can be constructed, inspected, revised, compiled, executed, and debugged without retained source.
- Formatting and source positions are not semantic identity.
- A source frontend submits validated semantic proposals.

Potentially better long-term direction:

- A generated or importable textual form may be an efficient interchange and review surface.
- A future parser can target the same proposal model rather than recreate a competing compiler frontend.
- Stable semantic anchors can make generated source more robust than hand-maintained offsets.

Decision for this campaign: Do not add syntax now. Replace absolute anti-source language with the positive one-authority invariant.

Evidence required before entry:

- Controlled model or human tasks show that text materially reduces authoring or review cost.
- The frontend can be deleted without losing the authoritative program.

Stop or reversal condition: Reject any frontend that persists an AST as coequal authority or makes reparsing necessary for ordinary edits.

### 23.6 SPG Semantics and Physical Storage

Current baseline: The SPG specifies typed entities, identity, ownership, order, and references; maps, vectors, and full artifacts implement it.

Enduring requirements:

- The accepted semantic schema remains closed and typed.
- Physical traversal order is not observable unless specified.
- Derived indexes and caches cannot become mutable semantic truth.

Potentially better long-term direction:

- Dense tables, columnar layouts, content-addressed chunks, a database, or another store may eventually outperform full snapshot maps.
- Physical representation should follow workload evidence rather than the word graph.
- The correctness oracle should remain a direct complete interpretation of semantic state.

Decision for this campaign: Keep current maps and vectors. Do not describe a graph database as required or forbidden.

Evidence required before entry:

- Artifact rewrite, clone, query, or memory measurements exceed a named workload budget.
- A replacement preserves canonical semantics, atomic publication, and strict recovery.

Stop or reversal condition: Delete a storage abstraction if it adds migration and synchronization states before a real scaling threshold exists.

### 23.7 Stable Identity Granularity

Current baseline: Persistent Node IDs identify declarations, members, parameters, blocks, operations, and other semantic entities.

Enduring requirements:

- Identity is independent of names, positions, hashes, indexes, offsets, and addresses.
- Persistent identities are never reused.
- Continuity is explicit, not inferred from shape similarity.

Potentially better long-term direction:

- Re-evaluate whether every current node kind needs externally durable identity.
- Some private scaffolding may remain derivable while user-repairable or referencable entities retain identity.
- Identity granularity should minimize churn and API burden without hiding meaningful continuity.

Decision for this campaign: Do not change semantic identity granularity during the control-plane campaign unless the baseline proves one specific implied identity is public friction.

Evidence required before entry:

- Agents repeatedly manipulate or receive identities that have no independent semantic use.
- A smaller identity surface preserves history and repair behavior with less protocol state.

Stop or reversal condition: Do not collapse identities needed for references, diagnostics, repair, history, or semantic merge merely to shorten payloads.

### 23.8 Names, Paths, and Lookup

Current baseline: Names are presentation and sibling lookup metadata; Node IDs are authority.

Enduring requirements:

- Rename preserves identity where the semantic contract says so.
- Persistent references do not silently retarget after rename.
- Ambiguous or missing lookup rejects.

Potentially better long-term direction:

- Draft-local symbolic labels can improve proposal readability without becoming persistent lookup.
- Human-facing qualified paths can be derived over one revision.
- Import and package systems may later need explicit namespace and dependency identities.

Decision for this campaign: Use symbolic labels only inside one bounded proposal if selected. Resolve them before allocation and discard them.

Evidence required before entry:

- Controlled tasks show numeric local handles are a material source of errors or bytes.
- A closed label grammar and deterministic duplicate policy are specified.

Stop or reversal condition: Reject global string references, implicit nearest-name lookup, or persistent label identity.

### 23.9 Incomplete Programs, Placeholders, and Repair

Current baseline: Missing bodies and typed holes are accepted incomplete states; `RefineHole` is one exact identity-preserving transition.

Enduring requirements:

- Incomplete state remains structurally valid and queryable.
- Only reachable incompleteness blocks selected execution.
- A repair is accepted only by deterministic final validation.

Potentially better long-term direction:

- Future repair plans may expose expected contracts, candidates, blockers, and multi-target dependencies more directly.
- A typed unresolved reference may be preferable to forcing a hole in some future authoring cases.
- Repair can become a first-class agent workflow without making a model authoritative.

Decision for this campaign: Retain current holes and repair context. Measure whether the baseline needs avoidable follow-up queries.

Evidence required before entry:

- A real task requires a missing semantic relation that cannot be represented by current incomplete forms.
- A new incomplete form has exact completion, identity, and execution-blocking semantics.

Stop or reversal condition: Do not add generic morphing, heuristic repair, or prose-only correctness decisions.

### 23.10 Structured Proposals and Draft-Local References

Current baseline: Structured function and expression drafts use explicit numeric LocalHandles and deterministic expansion into canonical nodes.

Enduring requirements:

- The proposal is closed, typed, bounded, and discarded after expansion.
- Persistent identity allocation remains service-owned and deterministic.
- Final SPG validation remains authoritative.

Potentially better long-term direction:

- One semantic proposal can omit canonical scaffolding and use symbolic draft-local references.
- References can target explicit proposal labels, existing Node IDs, parameters, expression results, and structured arguments through closed variants.
- The proposal can make intent visible without becoming source syntax.

Decision for this campaign: Use the controlled baseline to decide. The default is a direct replacement of initial-construction drafts if handle burden is material.

Evidence required before entry:

- Handle count, malformed local references, or repeated scaffolding materially affects the task.
- The replacement has deterministic expansion, bounded complexity, and equivalent final validation.

Stop or reversal condition: Do not create two equally preferred initial authoring APIs or a general macro/template language.

### 23.11 Machine Contract Discovery

Current baseline: A manifest, seven broad sections, full description, and digest-based unchanged response are generated from executable definitions.

Enduring requirements:

- One executable authority owns accepted request and response shapes.
- A projection is complete for the definitions it returns.
- Digest identity binds the complete active contract.

Potentially better long-term direction:

- Exact root selection with deterministic transitive dependency closure can avoid unrelated sections.
- The manifest can advertise root names, compact summaries, dependency counts, and digest.
- Clients should not need a second schema language to understand projection.

Decision for this campaign: Default to root-and-closure replacement if the black-box task proves broad over-fetch or discovery repetition.

Evidence required before entry:

- A selected task needs a strict subset of the full graph.
- Closure can be derived automatically from the same executable type description.

Stop or reversal condition: Retain broad sections if exact closure adds more public vocabulary or unresolved-definition risk than it removes.

### 23.12 Control-Plane Serialization

Current baseline: The CLI strictly decodes JSON, translates to a custom binary request, and the daemon decodes the custom frame.

Enduring requirements:

- The control plane is versioned, bounded, strict, deterministic, correlated, and trailing-data rejecting.
- Committed responses are preflightable before durable publication.
- Malformed input cannot corrupt state or violate memory safety.

Potentially better long-term direction:

- One canonical strict JSON representation can travel from CLI to local service inside a simple length frame.
- This can delete duplicated codecs, stable binary tags, schema translation, and many agreement tests.
- Binary remains appropriate for durable artifacts and future runtime data only when evidence supports it.

Decision for this campaign: The default is a direct JSON control-plane cutover after baseline evidence. Do not add JSON-RPC ceremony unless it solves a measured need.

Evidence required before entry:

- Equal-task end-to-end cost and code deletion outweigh increased local wire bytes.
- Exact response preflight and EOF behavior remain preserved.

Stop or reversal condition: Keep or restore a compact binary control plane only with measured throughput, latency, or memory pressure under a real high-rate workload.

### 23.13 CLI Sessions and Connection Lifetime

Current baseline: Each CLI RPC launch opens one connection, sends one request, receives one response, and exits.

Enduring requirements:

- Each response is correlated and bound to an exact request.
- A dropped client does not make committed authority ambiguous.
- Independent mutations remain revision-checked.

Potentially better long-term direction:

- A streaming CLI session, persistent client process, or request batch may remove process and discovery overhead.
- Read-only commands may share one revision-bound session.
- Mutation batches should remain explicit rather than relying on implicit connection state.

Decision for this campaign: Measure launch and connection cost in the controlled task. Prefer a small session mode only if it removes material round trips without hidden mutable client state.

Evidence required before entry:

- CLI startup or handshake cost is material relative to service work.
- A persistent mode has explicit framing, cancellation, backpressure, and failure semantics.

Stop or reversal condition: Reject session state that owns a shadow workspace, implicit base revision, or unbounded response stream.

### 23.14 Local Service versus Public Network API

Current baseline: The service listens on a private Unix socket protected by local filesystem permissions.

Enduring requirements:

- Do not claim a sandbox or remote security boundary that does not exist.
- Authentication and authorization must be explicit before network exposure.
- Untrusted network input receives stricter resource and abuse controls.

Potentially better long-term direction:

- A remote or multi-user service may eventually be useful for shared infrastructure.
- A gateway could translate an authenticated network protocol to the same typed service operations.
- Remote collaboration may pair naturally with revision branches rather than shared mutable sessions.

Decision for this campaign: Remain local-only. Do not make the control-plane replacement network-oriented.

Evidence required before entry:

- A named remote consumer exists.
- Identity, authentication, authorization, quotas, confidentiality, audit, replay, and denial-of-service contracts are specified.

Stop or reversal condition: Remove public exposure if it broadens the trusted boundary before isolation and authorization are credible.

### 23.15 Pure Core and Effect Boundary

Current baseline: Current operations are pure and have no host access.

Enduring requirements:

- Pure computation remains deterministic and replayable under explicit runtime policy.
- Host authority is never ambient.
- Effectful execution cannot be silently replayed after partial action.

Potentially better long-term direction:

- A small explicit effect model can later support real applications.
- Operations should declare effect class, required permission, result, failure, cancellation, accounting, and replay behavior.
- Effect interpretation may belong in supervised workers rather than the program-model service.

Decision for this campaign: Do not add effects in this campaign. Treat pure-core success as a platform for a later explicit effect gate, not as a permanent no-I/O law.

Evidence required before entry:

- A representative application needs one concrete host operation.
- Permission values, resource ownership, cancellation, and failure atomicity are designed together.

Stop or reversal condition: Reject ambient filesystem, network, process, environment, clock, entropy, terminal, or device access.

### 23.16 Strings, Bytes, and Text Data

Current baseline: The language has unit, bool, i64, and acyclic named immutable values; names are metadata, not runtime strings.

Enduring requirements:

- Text and bytes have explicit encoding, size, equality, slicing, and allocation semantics.
- Untrusted sizes are checked before allocation.
- External text decoding is strict and distinguishable from arbitrary bytes.

Potentially better long-term direction:

- Immutable UTF-8 strings and immutable byte sequences are likely the next foundational value classes for real applications.
- Small inline values, shared backing storage, or handles should be compared under real workloads.
- Agent-facing APIs need semantic constructors rather than offset arithmetic.

Decision for this campaign: Do not add them here. Place them near the front of later language gates, before broad frameworks.

Evidence required before entry:

- A retained application cannot be honestly represented with current values.
- The large-value memory strategy is evaluated together with runtime and artifact implications.

Stop or reversal condition: Do not conflate strings with names, assume null termination, or expose unchecked indexing.

### 23.17 Collections and Iteration

Current baseline: No general sequence, map, set, iterator, or collection operation exists.

Enduring requirements:

- Collection order is explicit.
- Bounds, allocation, equality, mutation, sharing, and iteration cost are specified.
- User-controlled traversal does not recurse through the native stack.

Potentially better long-term direction:

- One immutable sequence is likely more valuable than many specialized containers.
- Persistent, flat, chunked, or copy-on-write representations should be measured.
- Higher-order iteration should not be added before closures and effect semantics are clear.

Decision for this campaign: Do not add collections as collateral. Use application evidence to choose the first minimal collection.

Evidence required before entry:

- At least two representative tasks need homogeneous variable-length data.
- The value, memory, runtime, and serialization contracts are dependency-closed.

Stop or reversal condition: Delete a generic collection hierarchy if one concrete sequence covers the actual workloads more clearly.

### 23.18 Generics and Polymorphism

Current baseline: Types are closed primitives and exact nominal declarations; no generics or implicit conversions exist.

Enduring requirements:

- Instantiation and type equality are deterministic.
- Runtime representation and monomorphization or erasure rules are explicit.
- Diagnostics identify exact type arguments and constraints.

Potentially better long-term direction:

- Generics may reduce duplication once collections, results, permissions, or resources create real repeated shapes.
- A small parametric system may be preferable to nominal duplication.

Decision for this campaign: Do not add generics before multiple concrete consumers exist.

### 23.19 Resource-Owning Values and Linear Use

Current baseline: Current values are pure, immutable, and copyable; no external resource ownership exists.

Enduring requirements:

- Exclusive resources cannot be duplicated, used after move, or closed twice.
- Deterministic cleanup is separate from memory reclamation.
- Cancellation and exceptional exits define cleanup behavior.

Potentially better long-term direction:

- Affine or move-only handles are likely appropriate for files, sockets, processes, transactions, devices, and foreign objects.
- Borrowing may be inferred or restricted to narrow regions rather than exposed as pervasive source burden.
- Capabilities and resource ownership should be distinct but composable types.

Decision for this campaign: Do not impose ownership rules on ordinary immutable values. Reserve the design for the first actual resource class.

Evidence required before entry:

- An effectful application needs an exclusive external resource.
- Move, drop, scope, cancellation, error, and inter-process transfer semantics are specified.

Stop or reversal condition: Do not rely on nondeterministic finalizers for exclusive resource release.

### 23.20 Heap and Memory-Management Strategy

Current baseline: Current runtime uses bounded flat cells and copying for acyclic immutable values.

Enduring requirements:

- Accepted programs remain memory-safe.
- Aliasing, lifetime, mutation, cycles, and cleanup are explicit for each data class.
- Resource exhaustion is reported separately from memory unsafety.

Potentially better long-term direction:

- The eventual runtime may combine inline values, arenas, stable handles, reference counting, tracing collection, copy-on-write, and affine resources.
- A hybrid by data class may be simpler than one universal ideology.
- The compiler should derive lifetime facts when possible rather than burden agents with proofs that provide no value.

Decision for this campaign: Retain flat cells. Keep GC, RC, regions, handles, and ownership evidence-gated.

Evidence required before entry:

- Strings, collections, sharing, cycles, mutation, large objects, or foreign resources create a real heap workload.
- Compare throughput, tail latency, peak memory, fragmentation, complexity, diagnostics, and agent burden.

Stop or reversal condition: Reject a universal collector or universal borrow discipline chosen before representative data exists.

### 23.21 Concurrency and Parallelism

Current baseline: Requests and program execution are synchronous; the language has no concurrency semantics.

Enduring requirements:

- Data races and invalid aliasing are impossible in accepted programs.

- Cancellation and resource accounting are explicit.

Potentially better long-term direction:

- Independent read queries, compilation, and pure executions may safely run concurrently over immutable revisions.
- Workspace mutations can remain serialized while expensive derived work is parallel.
- Language-level structured concurrency should be considered only after effects and resources.

Decision for this campaign: Do not add async or threads here. Measure whether control-plane latency is actually serialization-bound.

Evidence required before entry:

- Concurrent current workloads produce measured queueing or underutilization.
- The immutable-revision and publication boundaries permit a small safe parallel design.

Stop or reversal condition: Remove concurrency if synchronization cost, nondeterminism, or test-state explosion exceeds measured benefit.

### 23.23 Persistence, Journaling, and Compaction

Current baseline: Every revision is a full immutable artifact; all history and tombstones are retained; HEAD identifies the authoritative revision.

### 23.24 Queries, Indexes, and Caches

## 24. Ordered Gates After This Campaign

Do not treat the following order as a promise.

It is a default dependency order derived from the current semantic gaps.

The controlled agent evidence may move one gate earlier when it proves a different bottleneck.

Do not start a later gate merely because it is more technically impressive.

### 24.1 Gate A: Agent-facing control plane is proven

- Complete the current campaign first.
- One actual coding agent can discover, author, reject, repair, run, restart, and verify through the public path.
- The active machine contract is self-contained and bounded.
- The control plane has one preferred serialization and one preferred initial-authoring path.
- Provider and byte evidence is honestly recorded.

Do not proceed to broad language growth while a model still requires implementation knowledge to use the current language.

### 24.2 Gate B: Foundational immutable data

- Evaluate immutable UTF-8 strings and immutable bytes together.
- Evaluate one homogeneous immutable sequence after or with a real string/bytes consumer.
- Choose a large-value representation from measurements rather than extending flat copying blindly.
- Specify equality, ordering, length, bounds, slicing, encoding, allocation, serialization, and runtime fuel.
- Preserve a memory-safe direct interpreter oracle.

Prefer a small set of orthogonal value classes over a generic collection framework.

### 24.3 Gate C: Explicit effects and permissions

- Select one real host operation from a retained application.
- Design explicit permission values.
- Design failure, cancellation, accounting, and replay semantics.
- Design resource-owning handles when the operation opens an exclusive resource.
- Decide whether the effect executes in-process or in a supervised worker.

Do not add ambient I/O or hide exclusive cleanup behind garbage collection.

### 24.4 Gate D: Packages and composition

- Compose two independently maintained semantic packages.
- Use immutable dependency identities and an exact lock graph.
- Separate package acquisition trust from runtime permission.
- Measure contract discovery and compile closure across package boundaries.
- Retain deterministic reproducibility.

Do not build a registry before local immutable package composition works.

### 24.5 Gate E: Scale and collaboration

- Measure large workspaces and revision rates.
- Select narrow indexes, caches, journaling, compaction, or branches only for proven pressure.
- Consider revision DAGs and semantic merge when multiple agents actually collide.
- Parallelize pure reads and derived work before parallel mutation.
- Preserve one publication authority per workspace.

Do not combine database, concurrency, branching, and distributed service work into one speculative rewrite.

### 24.6 Gate F: Runtime acceleration

- Build representative CPU-bound programs using the mature language surface.
- Profile interpreter, lowering, verifier, and value movement separately.
- Compare a specialized interpreter, mature backend, AOT, and baseline JIT.
- Keep the interpreter as differential oracle.
- Isolate unsafe or native code and expand the trusted-computing-base record.

Do not write a custom JIT because the project aspires to speed.

### 24.7 Gate G: Additional platforms and human projections

- Port the service boundary to a second real platform.
- Generate a textual or visual view only for a measured human or agent workflow.
- Bind every view to exact revision and semantic identities.
- Keep views deletable and non-authoritative.
- Expand CI and durability evidence per platform.

Do not let portability or presentation redefine the language core.
