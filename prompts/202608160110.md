## 4. Concrete Problems in the Current Product

### 4.1 `source-free` Is a Negative and Ambiguous Product Label

A new reader cannot infer from `source-free` whether the project:

- has no source text at all;
- stores source but does not expose it;
- uses generated bytecode;
- uses a graph database;
- is a visual language;
- is a binary-only language;
- forbids human-readable views;
- has abandoned source control;
- or merely does not treat text as authoritative.

The term emphasizes what is absent.

It does not explain what exists.

It also invites an accidental policy conclusion that all textual frontends must remain forbidden.

The enduring invariant is narrower and stronger:

- program meaning has one authoritative typed model;
- source text is not required;
- text cannot become a second authority.

State that directly.

### 4.2 Formal Compiler Terms Lead Before Product Meaning

Terms such as:

- Semantic Program Graph;
- canonical authority;
- nominal product;
- closed sum;
- exhaustive match;
- identity-preserving refinement;
- retained revision;
- projection;
- dependency closure;
- ambient authority;
- ownership-bearing value;
- vertical;
- schema digest;

are valid in precise contexts.

They are poor opening vocabulary when used without explanation.

The problem is not that technical terms exist.

The problem is audience ordering.

Plain meaning must come first.

Formal terminology should follow where it adds precision.

### 4.3 The Current Policy Mixes Invariants and Bootstrap Choices

Some policies are true product laws.

Examples:

- one authoritative program model;
- stable identity;
- failure-atomic publication;
- memory safety;
- strict decoding;
- explicit host authority.

Other policies describe current implementation.

Examples:

- one Rust package;
- synchronous IPC;
- full scans;
- full snapshot cloning;
- flat cells;
- no heap;
- no parser;
- no native tier.

Other policies are future design choices.

Examples:

- tracing collection versus ownership;
- database versus artifact store;
- async versus synchronous service;
- graph tables versus relational indexes;
- source frontend versus no frontend.

Treating all three groups as equally permanent makes the project rigid in the wrong places and vague in the important places.

### 4.4 Memory Safety Is Under-Specified as a Product Contract

The package currently forbids local unsafe Rust.

That is a strong implementation property.

It is not the complete memory-safety story.

Dependencies may contain unsafe code.

The compiler, standard library, operating system, and future generated native code are trusted.

Resource exhaustion is not memory unsafety.

Stack overflow from user depth is a safety and availability problem even in safe Rust.

Future resources need ownership and cleanup semantics.

Future shared mutable objects need aliasing and concurrency rules.

The project needs a precise layered statement rather than an anti-GC slogan.

### 4.5 The Existing Examples Are Narrow Product Oracles

The current named-data example is valuable.

It proves one record, one variant type, complete matching, repair, and restart.

It does not prove that the current language and agent interface can express a broader policy application with several interacting data types, nested decisions, multiple domain outcomes, a loop, and a stable edit history.

The next application should be broad enough to expose friction but narrow enough to avoid platform work.

### 4.6 Agent Cost Is Measured Indirectly

The repository measures bytes, round trips, CLI launches, and elapsed time.

That is useful direct evidence.

It has not measured a controlled model successfully performing the task.

Do not claim token savings or model reliability.

The next campaign should improve the direct evidence and capture provider telemetry only when it is already available.

### 4.7 Machine-Contract Discovery May Be Too Coarse

The current digest and unchanged path are good.

The current manifest is compact.

The current task-relevant section bundle can still exceed 86 KiB.

That cost dominates the example response volume.

A more task-scoped projection may be justified.

It may also be more complex than the cost it removes.

Measure and decide.

### 4.8 Repository Instructions Are a Product Cost

A coding agent must read the root policy before work.

A repetitive policy consumes context every session.

The replacement policy should be clearer, less duplicative, and more explicit about fact ownership.

Do not optimize only runtime bytes while ignoring repository instruction cost.

### 4.9 “Graph” Risks Becoming a Physical-Storage Dogma

The semantic model is graph-shaped because entities have ownership and references.

That does not require generic graph storage.

Long-term performance may favor dense tables, stable-ID maps, compact indexes, columns, persistent data structures, or a database.

Preserve semantic meaning.

Do not freeze one physical representation through terminology.

### 4.10 “No Arbitrary Limits” Needs a More Honest Form

Every implementation has finite IDs, address space, file sizes, frame sizes, and time.

The correct policy is not to pretend that implementation is infinite.

The correct policy is:

- do not impose small arbitrary semantic ceilings;
- expose representational and operational limits;
- justify them at the boundary they protect;
- use pagination, streaming, staging, and resource policy where possible;
- do not confuse policy limits with language meaning.

### 4.11 Full History and Tombstone Representation Are Current Mechanisms

Identity non-reuse is an enduring rule.

Saving every revision forever in one active workspace is not necessarily an enduring storage requirement.

A future retention or compaction policy may summarize deleted identity and prune unneeded artifacts if it preserves explicit guarantees.

Do not implement pruning now.

Do stop describing the current physical retention mechanism as the only conceivable safe design.

### 4.12 Architecture Restraint Must Not Forbid Safety Abstractions

“Wait for multiple consumers” is a useful defense against frameworks.

It is not absolute.

A single dangerous FFI or native-code boundary may justify a focused isolation abstraction because it centralizes one critical invariant.

Use current consumer, state-space reduction, and safety value as the test.

Do not use consumer count as the only test.

## 9. Terms That Must Be Used More Carefully

### Canonical

Use `canonical` for:

- byte representation;
- normalized order;
- one accepted encoding;
- deterministic identity input;
- one authoritative normalized form.

Do not use it as a synonym for “important.”

### Semantic

Use `semantic` when distinguishing program meaning from representation, transport, cache, or physical layout.

Do not prefix every subsystem with `semantic`.

### Exact

Use `exact` when the contract is exact.

Examples:

- exact Node ID;
- exact field set;
- exact type;
- exact byte count;
- exact revision;
- exact ordering.

Do not write “exact” merely to make a sentence sound strict.

### Closed

Name what is closed.

Examples:

- closed protocol vocabulary;
- fixed variant set;
- closed semantic schema;
- non-extensible request enum.

Do not assume readers know whether “closed” refers to inheritance, extension, world assumptions, or network access.

### Ownership

Distinguish:

- semantic containment;
- Rust memory ownership;
- resource ownership;
- exclusive capability possession;
- process responsibility;
- document fact ownership.

Never use one sense as evidence for another.

### Safe

State the property.

Examples:

- memory-safe;
- corruption-safe;
- crash-consistent;
- race-free;
- capability-safe;
- bounded against resource exhaustion.

Do not claim “safe” without a named threat or invariant.

## 16. Memory-Safety Contract

The final active documentation must make the following distinctions explicit.

### Language-level memory safety

A valid current lkjscript program cannot express:

- raw pointers;
- arbitrary addresses;
- unchecked loads or stores;
- pointer arithmetic;
- unchecked casts;
- arbitrary byte reinterpretation;
- direct foreign-memory access;
- data races;
- explicit deallocation;
- use-after-free;
- double free.

The current pure runtime values are primitives and acyclic named immutable aggregates.

They are represented by verified layouts and bounded flat cells.

This is current implementation evidence.

### Implementation-level memory safety

The repository package forbids unsafe Rust.

Preserve the existing Cargo lint.

Do not add `unsafe`, `allow(unsafe_code)`, an unsafe build script, generated unsafe code, or a native dependency as collateral.

The code must continue to:

- check lengths before allocation;
- check integer conversions;
- check index domains;
- reject malformed tags;
- reject trailing data;
- use explicit work structures for user-scalable depth;
- preflight runtime cells and scratch;
- stop on ambiguous durable authority;
- preserve service usability after ordinary structured rejection or runtime trap.

### Trusted computing base

Document that memory safety still trusts:

- the Rust compiler;
- the Rust standard library;
- the operating system;
- the filesystem and socket implementation;
- all linked dependencies;
- build tooling;
- any CPU-specific implementation inside dependencies;
- future FFI;
- future generated machine code;
- future native runtime workers.

Inspect current normal dependencies.

Record whether each has:

- a current consumer;
- build scripts;
- native code;
- known unsafe implementation surface where discoverable;
- platform-specific behavior.

Do not add a new dependency solely to produce this inventory.

A concise architecture section is sufficient.

### Resource safety

A request rejected for:

- JSON depth;
- artifact size;

- runtime items;
- runtime cells;
- fuel;
- frames;
- response bytes;

Keep error categories distinct.

### Stack safety

Safe Rust does not prevent process stack exhaustion from recursive algorithms.

- validate;
- history traversal;
- type-cycle analysis;
