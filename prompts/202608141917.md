## 2. Audited Baseline

The audited repository is already a direct replacement product.

It contains one Rust package.

It builds two binaries:

- `lkjscript`;
- `lkjscriptd`.

The current canonical path is:

```text
client
    -> framed private Unix IPC
    -> synchronous daemon
    -> daemon-owned durable workspace
    -> staged typed transaction
    -> immutable Semantic Program Graph snapshot
    -> canonical `.lkjscript` revision artifact
    -> direct Semantic Program Graph lowering
    -> private verified Core IR
    -> interpreter
    -> typed response
```

The current semantic types are:

- `unit`;
- `bool`;
- `i64`.

The current operation constructors are:

- `const_i64`;
- `const_bool`;
- `add_i64`;
- typed expression `hole`;
- `return`.

The current graph schema includes:

- workspace root;
- package;
- module;
- function;
- parameter;
- region;
- block;
- operation.

The current implementation already proves important properties:

- one daemon owns durable writes;
- snapshots are immutable and revision-labelled;
- persistent Node IDs are stable and never reused;
- failed and dry-run transactions do not consume IDs;
- deletions tombstone identity;
- old snapshots remain queryable and executable;
- artifacts are canonical and corruption-checked;
- IPC is closed, framed, bounded, and correlated;
- durable publication is ordered and failure-injected;
- direct lowering reaches one verified Core IR;
- the interpreter returns typed values;
- user-controlled large deletion uses an explicit work stack;
- restart restores the same IDs and retained history;
- invalid typed mutation leaves durable and in-memory state unchanged.

Preserve these strengths.

Do not weaken them to accelerate interface work.

## 3. Audited Gaps

The current implementation is a successful scalar kernel.

It is not yet an effective external agent programming interface.

The following gaps are concrete.

### 3.1 Hole Filling Churns or Fails Identity

A `Hole` is a valid incomplete operation with a stable Node ID.

Current history validation requires a surviving operation to retain the same stable
operation tag.

Current `ReplaceOperation` also requires the same operation tag.

Therefore a hole cannot become `ConstI64`, `ConstBool`, or `AddI64` while preserving
its Node ID.

This defeats the most valuable editing property of an explicit semantic hole.

A coding agent should be able to fill a hole while all existing uses continue to
reference the same semantic result identity.

### 3.2 Mutation Responses Contain Unbounded Detail

The current `TransactionResult` contains:

- every local-handle allocation;
- the complete semantic diff.

The durability layer correctly preflights the encoded response before commit.

This prevents a committed-but-unreportable result.

However, it also means an otherwise valid large transaction can be rejected because
the default response shape is too large.

Mutation semantic validity should not depend on returning every optional detail in
one frame.

### 3.3 Durable HEAD Retains the Full Result

The current idempotency record stores the complete `TransactionResult` in HEAD.

That couples bounded commit metadata to allocation-list and diff size.

It also rewrites and revalidates more metadata than exact replay requires.

HEAD should retain a compact replayable receipt.

Full diff detail is derived from retained snapshots.

### 3.4 Queries Are Too Primitive for Repair

The current public query vocabulary provides:

- workspace summary;
- one node summary or exact record;
- workspace blockers.

It does not provide:

- incoming value uses;
- incoming definition references;
- outgoing dependencies with exact slots;
- bounded body slices;
- semantic diff queries;
- pagination;
- legal constructors;
- visible values;
- owner chains;
- repair contexts;
- read batching.

An external agent must reconstruct context through repeated low-level requests or a
whole graph dump that does not exist.

### 3.5 The CLI Is a Demonstration Client

The current CLI contains bespoke commands such as:

- `bootstrap-42`;
- `rename-and-set-i64`;
- individual summary and node commands.

It does not expose the complete typed public request vocabulary.

An external coding agent cannot submit arbitrary typed transactions and query batches
without writing a Rust client or modifying the repository.

A generic strict machine projection is required.

### 3.6 Boundary Coverage Is Incomplete

The current repository has strong focused tests.

It does not yet have:

- generated transaction-sequence testing;
- deterministic malformed-byte mutation smoke;
- a generic JSON boundary;
- machine schema output;
- end-to-end agent-repair cost evidence.

### 3.7 Closed Contracts Allocate and Drift

The current operation contract constructs vectors on lookup.

Operand enumeration also allocates vectors.

Stable tags and variant handling are repeated in several codec matches.

The vocabulary is small enough to keep explicit.

It is also important enough to give one authoritative code-owned descriptor.

Do not solve this with a generic IR framework.

## 4. Campaign Thesis

The next product milestone is not "more syntax."

The next product milestone is semantic editability.

A language designed for autonomous agents needs an interface that exposes the facts
required to make a correct edit.

Typed holes are useful only when the system can answer:

- what is expected here;
- what values are visible here;
- what constructors can produce the expected type;
- who currently uses this value;
- what exact transaction can preserve continuity;
- what changed after publication.

The daemon already owns the authoritative graph and validators.

Use that authority to provide deterministic context.

Do not make the model rediscover semantic facts from a textual dump.

Do not place an LLM inside the daemon.

The daemon derives facts.

The external agent proposes a typed edit.

Deterministic validation accepts or rejects it.

## 5. Research-Informed Motivation

Typed-structure editing research demonstrates that incomplete programs can remain
statically meaningful rather than becoming malformed text.

Hazelnut and Hazel are relevant conceptual evidence.

The 2016 Hazelnut work formalizes typed structure edits over incomplete terms.

The 2018 Hazel live-programming work treats holes as meaningful incomplete program
states.

The 2024 work "Statically Contextualizing Large Language Models with Typed Holes"
argues that type and binding context can make model assistance more reliable and
token-efficient.

Use these ideas as motivation, not as a request to import their calculi or runtime
semantics.

This campaign does not implement evaluation through holes.

This campaign does not implement gradual typing.

This campaign does not implement a proof assistant.

This campaign implements the narrow product consequence that `lkjscript` currently
needs:

- explicit typed incompleteness;
- exact semantic context;
- identity-preserving refinement;
- deterministic validated edits.

## 6. Mandatory End State

At campaign completion, the repository must prove the following real workflow.

### 6.1 Construct an Incomplete Program

Through the generic machine CLI and real daemon, create a workspace containing:

- package `app`;
- module `root`;
- zero-parameter function `main` returning `i64`;
- one function region;
- one block;
- `const_i64 40`;
- `const_i64 2`;
- `const_bool true`;
- one `hole` expecting `i64`;
- `return` of the hole result;
- package entry set to `main`.

Request stable IDs only for the nodes the client needs after commit.

Do not require the response to include every created handle.

### 6.2 Discover and Inspect the Hole

Through one revision-bound query batch or one repair-context query:

- identify the hole;
- report its expected `i64` type;
- report its owner function and block;
- report its ordinal;
- report a bounded body window;
- report visible values, including the two `i64` constants and the `bool` constant;
- report exact value types;
- report legal constructors that can satisfy `i64`;
- report current incoming uses, including the `return` operand;
- do not return the entire workspace.

### 6.3 Reject an Invalid Refinement

Attempt to refine the hole to `add_i64` using one `i64` operand and the visible
`bool` operand.

The transaction must reject with structured expected and actual type facts.

The rejection must preserve:

- revision;
- HEAD bytes;
- revision-file set;
- allocation frontier;
- tombstones;
- hole identity;
- future allocation result.

### 6.4 Refine the Hole Correctly

Submit one typed transaction that refines the hole to `add_i64(40, 2)`.

The refinement must preserve:

- the hole Node ID;
- its owner block;
- its operation position;
- the existing `return` use;
- all unrelated node IDs.

The new revision must be complete.

The old revision must still contain the typed hole.

The transaction response must be compact and bounded.

### 6.5 Query the Exact Diff

Query the semantic diff from the incomplete revision to the refined revision.

The result must be deterministic and paginated.

It must identify the explicit hole-refinement transition.

It must identify the completeness transition.

The transaction receipt and queried diff must agree by change count and digest.

### 6.6 Execute the Result

Run `main` through:

```text
snapshot
    -> completeness validation
    -> Core IR lowering
    -> Core IR verification
    -> interpreter
```

The typed result must be `i64 42`.

### 6.7 Restart and Recheck

Restart the daemon from the same state directory.

Verify:

- the refined revision still runs as `42`;
- the old revision still exposes the hole;
- the hole/refined operation has the same Node ID across the transition;
- the paginated diff remains identical;
- an exact idempotent retry returns the same compact receipt;
- no custom Rust client is required.

### 6.8 Repair an Existing Operand

Attempt to replace one `add_i64` operand with the visible `bool` value.

Verify exact type rejection and no publication.

Request an operand repair context.

The context must report:

- expected `i64`;
- current operand value;
- visible `i64` candidates;
- visible incompatible `bool` candidate with its type;
- the operation and operand index;
- a bounded body window.

Apply a valid operand replacement in one transaction.

Verify the new revision executes the expected result.

Verify earlier revisions retain their earlier results.

## 7. Closed Architectural Decisions

The following decisions are made for this campaign.

### 7.1 Keep the Semantic Graph Baseline

### 7.2 Use a Direct Protocol Replacement

Introduce one protocol version for the new request and response vocabulary.

Delete the old request/response decoder and encoder when the replacement is complete.

Do not maintain dual protocol readers.

### 7.3 Replace HEAD Metadata Directly

When the idempotency payload changes, use an unambiguous new HEAD magic or format

Reject the old HEAD layout.

Do not add a migration path.

Tests use fresh temporary state.

### 7.4 Preserve Artifact Version Unless Artifact Bytes Change

Hole refinement changes valid history continuity.

It does not necessarily require a different snapshot byte encoding.

Do not bump the `.lkjscript` artifact format merely because the protocol changes.

If canonical artifact bytes or semantic snapshot schema change, replace the artifact
format or schema identity directly and document the reason.

### 7.5 Add One-Way Stable Hole Refinement

Use an explicit transaction operation for hole refinement.

Do not broaden `ReplaceOperation` into unrestricted constructor morphing.

### 7.6 Use Compact Transaction Receipts

The transaction response contains bounded receipt facts.

It does not contain the complete diff.

It does not contain all allocation bindings unless the client explicitly requests a
bounded selected set.

### 7.7 Derive Full Diffs from Snapshots

Serve the complete diff through a revision-bound paginated query.

Do not persist the complete diff in HEAD.

### 7.8 Keep Full Recalculation as the Oracle

Implement incoming uses, dependency facts, blockers, legal constructors, and repair
contexts by deterministic scanning and local derivation first.

Do not add a reverse-reference index, query DAG, Salsa integration, or cache during
this campaign.

### 7.9 Add a Generic Strict JSON CLI Projection

The CLI must expose the public typed request vocabulary to an external process.

JSON is a transport projection.

It is not `lkjscript` source code.

It is not persisted in semantic artifacts.

Use closed types and strict unknown-field rejection.

### 7.10 Permit Only Justified Serialization Dependencies

`serde` and `serde_json` are permitted when used for the generic machine projection.

Measure and report their build and dependency cost.

Do not add `schemars`, a parser generator, a CLI framework, an async runtime, a
database, or a property-testing framework unless a concrete blocker proves a small
local implementation insufficient.

### 7.11 Do Not Expand the Language

Do not add subtraction, multiplication, calls, parameters at invocation, branches,
loops, aggregates, sums, generics, effects, capabilities, ownership-bearing values,
packages, native code, or runtime cells in this campaign.

The campaign closes the agent repair interface first.

## 10. Milestone 1: Code-Owned Contract Cleanup

Prepare the closed vocabulary for protocol and query expansion without building a

### 10.1 Introduce Stable Operation Codes

Separate operation constructor identity from payload when useful.

A shape similar to this is acceptable:

```rust
pub enum OperationCode {
    ConstI64,
    ConstBool,
    AddI64,
    Hole,
    Return,
}
```

The exact type name may differ.

The semantics may not.

Each operation value must expose its code without allocating.

### 10.2 Introduce Static Operation Descriptors

A descriptor should provide code-owned facts such as:

- stable machine name;
- stable binary tag;
- operand schema;
- result schema;
- use mode;
- terminator status;
- completeness status;
- literal fields.

Use static slices, small fixed structures, or equivalent borrowed data.

Do not allocate vectors for a static contract lookup.

### 10.3 Keep Context-Dependent Contracts Explicit

`Hole` result type depends on its payload.

`Return` operand type depends on the owning function result.

Do not force context-dependent rules into an inaccurate static table.

The descriptor can distinguish:

- fixed type;
- payload-provided type;
- owner-provided type;
- no result.

### 10.4 Centralize Stable Tags

Stable tags should be owned by the corresponding domain.

Examples:

- semantic type tags in the semantic type definition;
- node kind tags in the node kind definition;
- operation tags in the operation code definition;
- error tags in the error-code definition;
- transaction-operation tags near transaction operations;
- query tags near query definitions.

Protocol code should call these owners.

Do not repeat raw numbers in unrelated match expressions.

### 10.5 Avoid Graph-Wide Temporary Allocations

Replace allocation-heavy helpers used in full scans where a narrow direct API is
clearer.

Examples include:

- operation operand access by index;
- borrowed operand iteration;
- direct-reference visitation;
- owned-child visitation.

Do not build a general visitor framework.

### 10.6 Add Descriptor Invariant Tests

## 11. Milestone 2: Protocol Replacement Skeleton

Replace the public request and response vocabulary coherently.

Do not leave protocol version 1 and version 2 active together.

### 11.1 Separate Mutation Semantics from Response Projection

Use a request shape equivalent to:

```rust
pub struct ApplyTransactionRequest {
    pub transaction: Transaction,
    pub response: TransactionResponseSpec,
}
```

Equivalent naming is permitted.

The distinction is mandatory.

The transaction states semantic mutation intent.

The response specification states bounded transport detail.

### 11.2 Transaction Mode

Represent commit versus validate-only explicitly.

A boolean may work internally.

A closed enum is clearer at the public boundary.

For example:

```rust
pub enum TransactionMode {
    Commit,
    ValidateOnly,
}
```

Do not describe validate-only as a weaker validator.

It uses the same semantic preparation path.

### 11.3 Bounded Response Specification

The initial response projection should contain only the selected local handles whose
persistent IDs the client needs.

A shape such as this is sufficient:

```rust
pub struct TransactionResponseSpec {
    pub return_handles: Vec<LocalHandle>,
}
```

Require the selected handles to be unique.

Prefer a deterministic canonical order.

A strictly increasing order is simple.

Set a boundary policy maximum.

The maximum is an IPC response policy, not a language limit.

### 11.4 Public Request Vocabulary

The replacement protocol should have closed requests equivalent to:

- create workspace;
- apply transaction;
- revision-bound query batch;
- run an entry;
- describe machine schema or protocol contract;
- shutdown.

A separate health request is optional only if a current consumer needs it.

Do not preserve demo-specific mutation requests.

### 11.5 Public Response Vocabulary

The replacement protocol should have closed responses equivalent to:

- workspace created;
- transaction receipt;
- query batch result;
- run result;
- schema description;
- acknowledged;
- structured error.

### 11.6 Query Correlation

Each query in a batch needs deterministic correlation.

Use either:

- a client-provided compact query ID;
- exact ordered result position.

Client-provided IDs are preferable when JSON is used.

Reject duplicate query IDs inside a batch.

### 11.7 Error Boundaries

A malformed frame rejects the whole request.

A missing workspace or revision may reject the whole revision-bound batch.

A target-specific read error may be returned as that query item's structured
outcome.

Read-only partial outcomes are permitted.

Mutation partial outcomes are forbidden.

### 11.8 Response Encoding Preflight

## 12. Milestone 3: Compact Transaction Receipt

Replace `TransactionResult` with a bounded receipt.

### 12.1 Required Receipt Facts

The receipt must contain:

- workspace ID;
- base revision;
- resulting or predicted revision;
- resulting or predicted snapshot hash;
- publication status;
- total created-node count;
- selected local-handle bindings requested by the client;
- total semantic-change count;
- deterministic semantic-change digest;
- useful bounded completeness summary.

A suggested shape is:

```rust
pub struct TransactionReceipt {
    pub workspace: WorkspaceId,
    pub base_revision: Revision,
    pub revision: Revision,
    pub hash: SnapshotHash,
    pub published: bool,
    pub created_count: u64,
    pub returned_bindings: Vec<(LocalHandle, NodeId)>,
    pub change_count: u64,
    pub change_digest: ChangeDigest,
    pub complete_before: bool,
    pub complete_after: bool,
    pub blocker_count_before: u64,
    pub blocker_count_after: u64,
}
```

Equivalent names and a smaller completeness summary are acceptable.

Do not omit change count or digest.

Do not include the complete change vector.

### 12.2 Selected Binding Semantics

The transaction may create many nodes.

The client selects only the local handles it needs after commit.

For each selected handle:

- the handle must be declared exactly once by a create operation;
- the returned Node ID must match staged allocation;
- the output order must be deterministic;
- an unknown handle rejects before publication;
- duplicate selected handles reject before publication.

Do not require dense local handles.

Do not expose an undocumented allocation formula merely to compress the response.

### 12.3 Created Count

`created_count` is the total number of persistent nodes allocated by the prepared
transaction.

It is independent of selected bindings.

A validate-only receipt predicts the same created count and selected bindings that an
unchanged subsequent commit would produce.

### 12.4 Change Digest

Define a canonical change digest.

Use the existing BLAKE3 dependency.

Use a domain-separated canonical encoding.

The digest input should include:

- a stable domain label;
- workspace ID;
- from revision;
- to revision;
- total change count;
- every canonical change item in deterministic order.

Do not use Rust debug strings.

Do not use map iteration order.

Do not use the digest as semantic identity.

### 12.5 Completeness Summary

The receipt should let the client know whether the transaction moved the workspace
or relevant target toward completeness without returning every blocker.

At minimum, report complete-before and complete-after.

Blocker counts are useful if cheap under the current full-recomputation baseline.

The full blocker list remains a query.

### 12.6 Validate-Only Semantics

Validate-only returns:

- predicted next revision;
- predicted hash;
- predicted selected bindings;
- predicted change count and digest;
- `published = false`.

It does not write a revision file.

It does not write HEAD.

It does not update in-memory head.

It does not retain idempotency state.

Choose and document whether an idempotency key is forbidden in validate-only mode.

The preferred behavior is structured rejection because replay protection has no
publication to protect.

### 12.7 No-Change Semantics

A transaction with no canonical semantic change still rejects as `NoChange`.

A response projection alone is not a semantic change.

### 12.8 Receipt Encoding Bound

Prove that the maximum selected-binding policy produces a response under the frame
limit.

Use exact encoded-size tests.

Do not rely on intuition.

### 12.9 Receipt Determinism

For the same base snapshot and exact request, the receipt is byte-identical.

Validate-only and commit receipts differ only in publication status and any field
whose contract explicitly differs.

The predicted revision, hash, selected bindings, change count, and change digest must
agree.

Do not broaden this campaign into a general idempotency database.

## 14. Milestone 5: Stable Hole Refinement

Add explicit semantic refinement.

### 14.1 Public Transaction Operation

Add a transaction operation equivalent to:

```rust
RefineHole {
    hole: NodeTarget,
    replacement: OperationDraft,
}
```

The exact name may differ.

The semantics may not.

### 14.2 Target Requirements

The target must:

- resolve in the transaction workspace;
- exist in the staged graph;
- be an operation node;
- currently contain `Hole`;
- occupy a regular non-terminator operation slot;
- remain owned by the same block.

### 14.3 Replacement Requirements

The replacement must:

- be a complete operation;
- be a non-terminator;
- not be another hole;
- produce exactly the same result count as the hole contract;
- produce the same result types as the hole contract;
- satisfy all operand scope and order rules in the final staged graph;
- use no ambient or inferred conversion.

In the current scalar schema, a typed expression hole has one result.

Keep the validation expressed in contract terms so future multi-result design does not
silently inherit a one-result assumption.

### 14.4 Identity Continuity

A successful refinement preserves:

- Node ID;
- owner;
- body ordinal;
- direct uses that target the hole result;
- tombstone state;
- allocation history.

The operation code changes from `hole` to the replacement code.

This code change is permitted only because the explicit refinement operation defines
semantic continuity.

### 14.5 History Validation

Update retained-history validation.

Permit exactly:

```text
old = Hole(expected)
new = complete non-terminator operation
new.result_contract == expected
owner unchanged
node kind unchanged
```

Continue permitting same-code payload edits already accepted by explicit operations.

Reject:

- concrete operation to different concrete operation code;
- concrete operation to hole;
- hole to hole through refinement;
- hole to terminator;
- hole to different result contract;
- owner change;
- node-kind change;
- resurrection.

### 14.6 Diff Semantics

Represent refinement explicitly in the semantic diff.

Do not report it only as an anonymous scalar change.

A change kind equivalent to this is appropriate:

```rust
OperationRefined {
    before: OperationCode,
    after: OperationCode,
}
```

The `before` code is currently `Hole`.

Keep the shape extensible enough to describe the exact transition without authorizing
other transitions.

### 14.7 ReplaceOperation Scope

Keep or rename the existing same-constructor update operation for edits such as:

- `const_i64 2` to `const_i64 3`;
- `const_bool false` to `const_bool true`.

It must not become a second hole-refinement path.

Its history rule remains same operation code and compatible identity contract.

### 14.8 Same-Transaction Supporting Nodes

Support this useful atomic pattern:

1. create supporting values before the hole in its block;
2. refine the hole to an operation using those local values;
3. preserve all existing uses of the hole result;
4. validate the final graph once;
5. publish one revision.

All local handles may be allocated before operation application as they are now.

Final scope and order validation decides correctness.

### 14.9 Rejection Precision

A refinement rejection should report structured facts.

Use existing fields where sufficient.

Add a narrow error code only when clients need to distinguish refinement-contract
failure from a generic operand failure.

Useful facts include:

- target;
- operation index;
- expected type;
- actual type;
- related operand producer;
- expected operation role;
- actual operation code where represented.

Natural language remains secondary.

## 15. Milestone 6: Query Page Model

Introduce one small page model before implementing graph-wide queries.

### 15.1 Typed Page Requests

Use typed cursors per query family.

Do not create a generic opaque cursor service.

A generic container is acceptable:

```rust
pub struct PageRequest<C> {
    pub after: Option<C>,
    pub limit: u32,
}
```

Reject zero limit.

Reject a limit above the query policy.

### 15.2 Typed Page Responses

A page should contain:

- ordered items;
- exact next cursor when more items remain;
- optional total count when it is already computed or cheap;
- no ambiguous `truncated` state without a continuation.

A shape such as this is acceptable:

```rust
pub struct Page<T, C> {
    pub items: Vec<T>,
    pub next: Option<C>,
    pub total: Option<u64>,
}
```

### 15.3 Revision Binding

Every cursor is interpreted only under the exact workspace, revision, query kind,
and target supplied by the request.

A cursor from another target or revision rejects.

The cursor is transport state.

It is not stored in snapshots.

### 15.4 Cursor Simplicity

Because revisions are immutable, an ordinal cursor is acceptable for an ordered body
slice.

A stable last-key cursor is preferable for BTree-ordered uses and diffs.

Do not expose private memory offsets or Core IR indexes.

### 15.5 Boundary Proof

Set central policy maxima for:

- page items;
- batch queries;
- aggregate batch items;
- compact name preview bytes if names appear.

Add tests proving the maximum legal compact response fits the IPC frame or is safely
preflighted before any mutation.

Read-only query failure may return a policy error.

Mutation publication may not occur before response preflight.

## 16. Milestone 7: Semantic Reference Facts

Replace bare reference counting with exact typed reference facts.

### 16.1 Distinguish Containment

Containment is ownership.

Semantic reference is dependency or use.

Do not report containment as an operand use.

### 16.2 Value Uses

A value-use target is:

- a function parameter value;
- a specific operation result identified by operation Node ID and output index.

Do not collapse a multi-result-capable value to only its producer Node ID.

### 16.3 Use Site Shape

A compact use site should contain:

- source operation Node ID;
- operand index;
- target semantic value;
- owner block;
- owner function when cheaply derived;
- expected operand type;
- operand use mode.

Do not include full source node records by default.

### 16.4 Definition References

A definition-reference site should identify:

- source node;
- reference slot;
- target definition.

The current package entry reference is one example.

Keep value uses and definition references distinct.

### 16.5 Outgoing Dependencies

An outgoing-dependency query reports exact direct reference slots from one node.

It does not recursively dump the entire dependency closure by default.

A future closure query may be added when a consumer needs it.

### 16.6 Incoming Use Implementation

The initial incoming-use query scans the immutable snapshot.

Use allocation-free or low-allocation reference iteration.

Sort results canonically.

Do not add a reverse index in this campaign.

### 16.7 Reference Count Terminology

Rename ambiguous summary fields.

For example:

- `reference_count` becomes `outgoing_reference_count`;
- `diagnostic_count` becomes `blocker_count` when it counts only blockers.

No compatibility shim is required.

## 17. Milestone 8: Body Slice Queries

Add compact revision-bound body inspection.

### 17.1 Query Target

Prefer a block Node ID as the unambiguous body-slice target.

A function convenience query may resolve its current entry block when useful.

Do not assume one block in the public shape if a block-specific query is already
simple.

### 17.2 Body Item Shape

A compact body item should include:

- operation Node ID;
- semantic ordinal;
- operation code;
- result types;
- operands;
- completeness;
- whether it is the terminator;
- small literal payload when essential, such as an `i64` or `bool` constant.

Do not include full owner chains in every item.

### 17.3 Terminator Representation

The block terminator is semantically separate from regular operations.

The query may:

- include it as a final item marked terminator;
- return it in a separate bounded field.

Choose one deterministic representation.

### 17.4 Ordinal Cursor

Use the immutable semantic order.

A cursor may contain the next ordinal and whether the regular-operation sequence has
reached the terminator.

Reject a cursor outside the body shape.

### 17.5 Context Window Helper

Implement a pure helper that returns a bounded window around a target operation.

It should support repair-context composition.

Do not persist the window.

Do not create a generic text-editor range abstraction.

## 18. Milestone 9: Semantic Diff Query

Move full change detail out of mutation responses.

### 18.1 Query Inputs

A diff query names:

- workspace;
- from revision;
- to revision;
- page request.

Reject revisions from another workspace or unavailable history.

### 18.2 Canonical Item Order

Use one deterministic sort key.

A suitable key is:

```text
(node ID, change-kind stable tag, canonical detail)
```

### 18.3 Diff Page Result

Return:

- from revision;
- to revision;
- total change count;
- change digest;
- ordered page;
- next cursor.

Every page for the same revision pair reports the same count and digest.

### 18.4 Receipt Agreement

For a committed transaction from revision N to N+1:

- receipt change count equals diff total;
- receipt change digest equals diff digest;
- selected binding facts agree with created nodes in the diff;
- completeness summary agrees with blockers at both revisions.

### 18.5 Arbitrary Revision Pairs

Supporting arbitrary retained `from <= to` pairs is useful and feasible with retained
snapshots.

If the first implementation only supports adjacent revisions, document that exact
limit as a query capability, not a language limit.

Prefer arbitrary pairs if it does not complicate correctness.

Do not add a stored delta chain solely for this query.

## 19. Milestone 10: Legal Constructor Queries

Expose the closed operation schema to agents.

### 19.1 Query Targets

Initial legal-constructor targets are:

- an expression hole;
- an operation operand slot.

### 19.2 Constructor Filtering

For a hole:

- filter complete non-terminator constructors by result contract.

For an operand:

- report values and constructors that can produce the expected operand type;
- do not claim a constructor insertion is directly legal without considering body
  placement.

### 19.3 Constructor Descriptor

A constructor descriptor should contain:

- stable machine code;
- result contract;
- ordered operand contracts;
- operand use modes;
- required literal fields;
- completeness;
- terminator status;
- nested region requirements when introduced;
- capability requirements when introduced.

The current scalar descriptors are small.

Return them directly.

### 19.4 Current Expected Results

For expected `i64`, legal complete expression constructors include:

- `const_i64`;
- `add_i64`.

For expected `bool`, legal complete expression constructors include:

- `const_bool`.

`hole` is not a completion constructor.

`return` is not an expression-hole replacement.

For `unit`, return an empty constructor set until a complete unit-producing operation
exists.

Do not invent a unit constant merely to make the query non-empty.

### 19.5 Visible Values

Visible values are not constructors.

Return them in a separate ordered collection.

Each visible value should include:

- exact semantic value reference;
- semantic type;
- producer or parameter identity;
- producer code when applicable;
- owner function;
- body ordinal when applicable;
- compact display name for parameters when useful.

### 19.6 Visibility Rules

In the current one-block language, visible values include:

- parameters of the owning function;
- results of complete or incomplete value-producing operations earlier in the same
  block, subject to the current type rules.

A hole result itself is not a candidate for filling that same hole.

A later operation result is not visible.

A value from another function is not visible.

A value from another workspace is not visible.

Use current validators as the semantic oracle.

Do not duplicate a second approximate scope algorithm.

## 20. Milestone 11: Repair Context Queries

Build one deterministic composite query over the primitives.

### 20.1 Repair Targets

Use a closed target enum equivalent to:

```rust
pub enum RepairTarget {
    Hole(NodeId),
    Operand {
        operation: NodeId,
        index: u32,
    },

```

### 20.2 Explicit Context Budget

The request provides bounded counts such as:

- body operations before target;
- body operations after target;
- visible values;
- incoming uses.

Use central maximums.

Reject values above policy.

Do not accept an arbitrary token budget whose meaning depends on a model tokenizer.

### 20.3 Hole Context Fields

A hole context should return:

- workspace and revision;
- hole Node ID;
- expected result type;
- owner block;
- owner function;
- semantic ordinal;
- function signature;
- compact owner chain;
- body window;
- visible values page or bounded prefix plus continuation;
- incoming uses page or bounded prefix plus continuation;
- legal constructors;
- relevant completeness blocker;
- exact refinement operation code expected from the client.

### 20.4 Operand Context Fields

An operand context should return:

- operation Node ID;
- operation code;
- operand index;
- expected operand type;
- operand use mode;
- current semantic value;
- current actual type;
- owner block;
- owner function;
- semantic ordinal;
- body window;
- visible compatible values;
- optionally visible incompatible nearby values with explicit types when the bounded
  context requests them;
- incoming uses of the operation result when useful;
- legal value-producing constructors.

### 20.5 Deterministic Selection

The context is selected by:

- containment;
- semantic order;
- scope;
- type;
- exact reference facts;
- explicit request limits.

Do not rank with embeddings.

Do not call an LLM.

Do not use file proximity because files are not semantic program structure.

### 20.6 Context Sufficiency Test

The principal fixture must be repairable from one context result.

The test should not access private graph maps or manually assumed Node serials after

The test may use selected returned handle bindings.

## 21. Milestone 12: Query Batching

Add one revision-bound read batch.

### 21.1 Batch Shape

A shape equivalent to this is acceptable:

```rust
pub struct QueryBatchRequest {
    pub workspace: WorkspaceId,
    pub revision: Revision,
    pub queries: Vec<QueryItem>,
}

pub struct QueryItem {
    pub id: QueryId,
    pub query: Query,
}
```

### 21.2 Outcome Shape

Each item returns:

- the same query ID;
- one typed query result;
- or one structured query error.

Preserve input order even when IDs are present.

### 21.3 Batch Atomicity

A query batch is read-only.

It does not need mutation-style all-or-nothing semantics for target-specific errors.

All successful items observe the same immutable snapshot.

### 21.4 Batch Policy

Bound:

- query count;
- aggregate requested page items;
- aggregate response bytes.

Prefer compact item limits that make ordinary legal batches fit by construction.

Retain exact final response encoding preflight.

### 21.5 No Query Language

Do not implement:

- arbitrary graph patterns;
- user-provided predicates;
- SQL;
- GraphQL;
- Datalog;
- a general query planner;
- a dynamic property projection language.

Use a closed `Query` enum.

## 22. Milestone 13: Generic Strict JSON CLI

Make the daemon usable by an external coding agent without a custom Rust program.

### 22.1 Command Shape

Provide a command equivalent to:

```bash
lkjscript --state DIRECTORY rpc
```

It reads exactly one JSON request from stdin.

It writes exactly one compact JSON response to stdout.

A `--pretty` flag may opt into presentation formatting.

A file-input option is optional.

Stdin is sufficient.

### 22.2 Scope

The generic command must support the complete public request vocabulary:

- workspace creation;
- transactions;
- query batches;
- run;
- schema description;
- shutdown.

Do not require one bespoke CLI command per transaction operation.

### 22.3 JSON Envelope

Use an explicit versioned envelope.

A shape similar to this is appropriate:

```json
{
  "version": 2,
  "request_id": 1,
  "request": {
    "kind": "query",
    "workspace": "0123456789abcdef0123456789abcdef",
    "revision": 1,
    "queries": []
  }
}
```

Use stable lowercase snake-case machine names.

Do not expose Rust `Debug` spelling as a contract.

### 22.4 Enum Representation

Use an explicit tagged representation.

Internally tagged or adjacently tagged enums are both acceptable when every current
variant is represented clearly and strictly.

Avoid untagged enums whose shape becomes ambiguous.

### 22.5 Strictness

Reject:

- unknown fields;
- unknown variants;
- missing required fields;
- duplicate fields;
- invalid IDs;
- zero Node serials;
- out-of-range integers;
- invalid page limits;
- trailing JSON values;
- input beyond the configured byte policy.

Do not silently ignore misspelled fields.

### 22.6 Canonical ID Representation

Use one canonical JSON form.

Recommended forms are:

- workspace ID as lowercase 32-digit hexadecimal string;
- Node ID as `WORKSPACE:SERIAL` string;
- snapshot hash and change digest as lowercase hexadecimal strings;
- revision and request IDs as JSON integers within exact range;
- local handle as JSON integer.

Reject noncanonical alternatives if accepting them adds ambiguity.

### 22.7 Output Semantics

Machine stdout contains one response object and one trailing newline.

No progress text appears on stdout.

Transport or CLI parse failure produces a structured machine error when possible.

Daemon semantic errors remain typed response variants.

Choose and document exit status semantics.

A practical contract is:

- exit 0 when a syntactically valid daemon response was emitted, including a typed
  semantic rejection;
- nonzero when the CLI could not parse input, connect, exchange a frame, or emit a
  valid response.

If another contract is chosen, test it exhaustively.

### 22.8 Compact Defaults

Default JSON output is compact.

Do not pretty-print by default.

Do not emit null fields that carry no information unless the stable schema requires
them.

Do not shorten stable field names into unreadable one-letter keys merely to win a toy
byte benchmark.

### 22.9 Serialization Authority

The JSON layer maps exhaustively to the same closed public request and response
vocabulary used by binary IPC.

It may use boundary DTOs.

Boundary DTOs are transport types, not semantic authority.

Every conversion is total or returns a structured boundary error.

Do not pass arbitrary `serde_json::Value` into semantic validation.

### 22.10 Dependency Decision

Using `serde` and `serde_json` is expected to be the simplest robust implementation.

Configure only required features.

Record:

- direct dependency additions;
- transitive dependency additions;
- fresh release build delta;
- incremental build observation;
- release binary-size delta.

Do not add a CLI parsing framework solely for the two or three top-level flags.

### 22.11 Delete Demo-Only Surface

After generic RPC examples and tests exist, remove obsolete demo-only commands unless
a concise human convenience command has a current documented consumer.

At minimum, do not retain `bootstrap-42` and `rename-and-set-i64` as privileged
product paths.

The integration fixture should use the generic request path.

## 29. Detailed Semantic Requirements

The following sections define edge behavior that must not be left implicit.

## 29.1 Hole Identity Means Semantic Continuity

The hole Node ID identifies the semantic expression position and result continuity.

Refinement changes the constructor occupying that identity.

This is not content-addressed identity.

The snapshot hash must change.

The Node ID must not change.

Consumers already referencing the hole result continue to reference the same Node ID
and output index.

Old snapshots interpret the ID as a hole.

New snapshots interpret the same ID as the refined operation.

This historical type of the node remains `Operation` in both snapshots.

## 29.2 Refinement Is One-Way

An explicit hole refinement may occur once for the surviving identity.

A later same-code payload edit may occur through the normal operation-update path.

A later constructor change is not silently accepted.

To replace a concrete expression with a different constructor in the future, define a
separate explicit continuity or replacement operation with exact use-rewrite
semantics.

Do not anticipate it now.

## 29.3 Refinement Does Not Bypass Order

If a replacement references an operation result after the hole position, reject.

If supporting operations are created in the same transaction before the hole, allow
them when final order is valid.

If supporting operations are appended after the hole and referenced by it, reject.

Transaction operation order and body semantic order are distinct.

Validate final body order.

## 29.4 Refinement Does Not Bypass Type Checking

The hole expected type constrains the replacement result.

The replacement's operands are checked independently.

A replacement that returns `i64` but contains a `bool` operand where `i64` is required
rejects.

Report the operand type mismatch rather than only a generic refinement failure when
that is the deepest deterministic cause.

## 29.5 Refinement Does Not Bypass Completeness

The replacement must be complete.

Do not allow a hole to become another hole with a different expected type.

Do not allow a complete operation containing inaccessible incomplete nested regions
when nested regions are introduced later.

The current schema has no such complete nested operation.

## 29.6 Refinement and Deletion

A refined operation may later be deleted through normal subtree deletion when no
surviving direct reference blocks it.

Its ID becomes tombstoned.

It is never reused.

Old snapshots retain both its hole and refined historical forms at their revisions.

## 29.7 Diff Detail

The canonical refinement change should include enough information for an agent to
understand that identity was preserved.

At minimum include:

- node ID;
- before operation code `hole`;
- after operation code;
- expected/result type when not derivable cheaply by querying either revision.

Avoid copying complete old and new node records into every diff item.

## 29.8 Selected Bindings and Deletion in One Transaction

A transaction may create a node and delete its owned subtree before final publication.

Current identity staging may tombstone the allocated ID in the candidate.

Define selected-binding behavior explicitly.

The preferred behavior is:

- a selected created handle may return its allocated Node ID even if the final
  candidate tombstones it;
- receipt created count still includes the allocation;
- diff reflects no live creation when canonical before/after state has only the new
  tombstone or reflects the exact tombstone semantics according to the accepted diff
  model;
- persisted replay validation accepts the binding only when the resulting snapshot
  contains the ID live or tombstoned.

If the implementation instead rejects create-then-delete as canonical no-change or
forbids returning a tombstoned created handle, specify and test that narrower rule.

Do not leave it accidental.

## 29.9 Response Projection Is Not Semantic State

Changing selected return handles changes the exact request replay contract.

It does not change the snapshot hash.

It does not change semantic diff.

It does not publish a revision by itself.

## 29.10 Query Results Are Derived

A query response may change representation in an incompatible protocol replacement.

It may not change the meaning of the queried snapshot.

No query creates semantic nodes.

No query consumes persistent IDs.

No query updates HEAD.

No query writes a cache during this campaign.

## 29.11 Cursor Forgery

Clients may send arbitrary cursor values.

A cursor is not trusted.

Validate:

- target domain;
- revision availability;
- ordinal or last-key range;
- relation kind;
- output index;
- query compatibility.

Invalid cursors return structured query errors.

They do not panic.

## 29.12 Large Names

Canonical semantic names may be larger than compact query presentation allows.

Do not return a megabyte name in every body item.

Use either:

- no names in compact body items;
- a bounded name preview with explicit truncation;
- exact name only in node summary or exact record query.

Do not truncate canonical stored names silently.

## 29.13 Query Totals

A total count is useful when the query already scans all results.

Incoming uses and semantic diff initially scan all candidates, so exact total is
available.

Body slice total is available from the block vector.

Do not add a second scan solely to populate a decorative total when it becomes
expensive in future implementations.

## 29.14 Query Errors and Batch Continuation

One query item error does not invalidate another read item.

The response preserves exact item order.

A query item error has no page continuation.

A successful empty page at the end has no next cursor.

A cursor exactly at the last item returns an empty terminal page or rejects according
to one documented rule.

Prefer an empty terminal page only when it simplifies idempotent pagination.

Test the chosen rule.

## 29.15 Run Remains Revision-Bound

A run request names the exact workspace, revision, and entry Node ID.

It does not implicitly run HEAD unless a separate convenience request is explicitly
added.

Do not add implicit latest behavior in the machine protocol.

## 29.16 Schema Description Is Build-Bound

The machine schema description describes the current binary build.

It is not persisted in workspaces.

It does not promise compatibility with future versions.

The version field prevents ambiguity.

## 29.17 JSON Does Not Replace Binary IPC

The CLI may parse JSON and convert to typed Rust values.

It then sends the existing compact typed binary request to the daemon.

Do not make the daemon accept public TCP JSON in this campaign.

Do not add HTTP.

Do not add WebSockets.

Do not add remote authentication.

## 29.18 Binary and JSON Agreement

For every public request representable in JSON:

```text
JSON decode
    -> typed request
    -> binary encode
    -> binary decode
    -> same typed request
```

For every public response:

```text
typed response
    -> binary round trip
    -> JSON encode
    -> JSON decode where supported
    -> equivalent typed response
```

Test representative and exhaustive closed variants.

## 39. Stop Conditions

Stop the current line of implementation and narrow it if any of the following occurs.

### 39.1 Semantic Authority Split

Stop if a JSON document, schema file, source projection, diff record, or query cache
becomes coequal mutable program authority.

### 39.2 Identity Ambiguity

Stop if a generic operation morph permits constructor changes without explicit
continuity semantics.

### 39.3 Unbounded Receipt

Stop if the default transaction result again contains all created bindings or all
diff items.

### 39.4 Protocol Duplication

Stop if both protocol versions remain active merely for compatibility.

### 39.5 Persistence Expansion

Stop if the campaign begins adding a database, journal, or chunk store without
measured full-rewrite pressure.

### 39.6 Query Framework Expansion

Stop if closed queries are being replaced by a dynamic query language, planner, or
generic graph engine.

### 39.7 Premature Indexing

Stop if a reverse-reference index or incremental query graph is added before scan
measurements.

### 39.8 Language Scope Expansion

Stop if calls, control, aggregates, effects, ownership, or native code enter the diff
without the agent-repair gate already complete and a new active task.

### 39.9 Dependency Expansion

Stop if a schema framework, CLI framework, async runtime, property framework, or
fuzzer runtime is added only for convenience when a small local solution suffices.

### 39.10 Test Evasion

Stop if behavior is made less strict merely to make generated or mutation tests pass.

Fix the defect or narrow the input policy honestly.
