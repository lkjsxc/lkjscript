- Wrong Boolean expected type identifies Boolean pattern/type mismatch.
- Wrong I64 expected type identifies I64 pattern/type mismatch.
- Wrong product entity kind identifies the required product declaration kind.
- Wrong field entity kind identifies the required product-field kind.
- Wrong field owner identifies that the field does not belong to the selected product.
- Duplicate field identifies duplicate product-field use.
- Missing field identifies incomplete exact product coverage.
- Foreign identity uses the canonical namespace rejection.
- Stale identity uses the canonical stale-identity rejection.
- Wrong expected product identifies exact nominal mismatch.
- Malformed graph uses existing invalid-draft errors.
- Usefulness and exhaustiveness errors remain canonical analyzer errors.
- Host allocation or overflow failures remain host-class failures.

## Design decision rules

Use these rules when the implementation presents alternatives.
1. **Separate product and enum metadata vectors versus one private enum.** Choose the smaller and clearer local representation. A private enum is justified only when it removes duplicated state transitions without spreading beyond pattern lowering.

2. **Existing helper versus new helper.** Reuse a helper when its contract is already exact. Extract a helper when two present call sites have identical semantics. Do not extract for possible future use.

3. **Hash map versus declaration-sized vector.** Prefer declaration-indexed vectors when private field addresses already provide exact indices. Use a local hash map only when stable identity mapping otherwise becomes repeated scanning.

4. **Test module split.** Split only when navigation and ownership improve materially. Do not split for symmetry.

5. **Error variant versus message.** Follow existing workspace error taxonomy. Add a variant only when callers require structured distinction and current conventions support it.

6. **Public convenience constructor.** Do not add one unless multiple current callers become substantially clearer and no semantic ambiguity is introduced.

7. **Performance measurement.** Use deterministic work counts for local complexity. Use wall-clock measurement only when a real latency hypothesis and decision threshold exist.

8. **Broader refactor.** Perform it only when required for correctness or when it deletes more code and cognitive load than the direct extension. Keep it dependency-closed.

10. **New dependency.** Reject it unless it removes substantial correct machinery. This task should require none.
