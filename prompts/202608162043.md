## 4. Strategic Decision

The official roadmap's next gate remains directionally correct:

> Retain a concrete bounded binary application, then compare a dedicated immutable bytes value with a generic sequence and postponement.

This campaign strengthens that gate.

It does not merely append bytes to every enum.

It establishes the first explicit managed-value architecture.

The default retained architecture is:

### 4.1 Semantic class

`bytes` is an immutable value type.

Equality depends only on visible byte content.

It has no observable allocation identity.

It has no observable address.

It is semantically duplicable.

A semantic duplicate may share physical backing.

A slice or view is semantically another immutable byte value.

### 4.2 Runtime class

A byte value occupies one fixed runtime handle cell.

Its payload is stored in an invocation-scoped arena.

A handle is a checked domain-specific integer newtype, not a pointer.

The arena owns immutable backing buffers and bounded view descriptors.

Handles are monotonic and not reused during an invocation.

The arena is destroyed after result materialization.

### 4.3 Reclamation class

The mandatory implementation uses invocation-region reclamation.

No per-object reference count is required because no managed handle may outlive the invocation.

No tracing collector is required because there are no managed cycles.

No surface ownership syntax is required because the lifetime boundary is the `Run`.

### 4.4 Future path

The compiler and runtime should not prevent later:

- nested lexical regions;
- caller-region result placement;
- precise reference counting for escaping cycle-free values;
- inferred borrows;
- uniqueness;
- drop-guided reuse;
- affine resources;
- isolated tracing regions.

Do not implement those mechanisms unless the current campaign gains a real consumer and dependency closure.

### 4.5 Public boundary

Runtime byte values use one exact canonical JSON encoding.

The default candidate is canonical unpadded URL-safe base64 with no whitespace and strict rejection of noncanonical trailing bits.

Compare it against lowercase hexadecimal and integer arrays.

Select one.

Do not support multiple encodings.

Artifact bytes store raw length-delimited payloads.

JSON encoding is transport only.

### 4.6 Operation set

The default minimal operation set is:

Retain an operation only when the representative application or a named exact boundary needs it.

`bytes_at` returns exact `i64` in `0..=255`.

## 5. Research Inputs

Research informs alternatives.

The repository contract and reproduced evidence decide implementation.

### 5.1 Region-based memory management

Tofte and Talpin's region-based memory-management work demonstrates that allocation and deallocation regions can be inferred from types and effects.

Use this as evidence that region placement need not become manual surface choreography.

Do not assume classic lexical region inference solves future effects, tail calls, concurrency, or escaping values automatically.

### 5.2 Counting Immutable Beans

Ullrich and de Moura describe reference counting optimized for eager purely functional programs, including borrowed references and reclaiming nonshared values.

Use this as evidence that semantic immutability does not require repeated physical deep copies.

Do not add reference counting to the first invocation-scoped bytes implementation merely because it may be useful later.

Reference: arXiv:1908.05647.

### 5.3 Perceus

Perceus derives precise reference-count operations from explicit control flow and enables uniqueness-guided reuse in cycle-free functional programs.

Use this as evidence that the SPG use graph and Core IR CFG could support compiler-inserted memory operations later.

Do not claim Perceus's garbage-free result for programs with cycles or for an implementation that has not reproduced its premises.

Do not implement a ceremonial retain/release IR with no current consumer.

### 5.4 Frame-limited reuse

Drop-guided reuse research shows that reuse strategy must consider peak-memory behavior and robustness under program transformations.

Use this as a warning that “in-place” is not automatically lower-memory.

Any future reuse optimization needs a peak-memory reversal condition.

### 5.5 Modal memory management

The OCaml modal-memory work separates affinity, uniqueness, and locality and shows that modes can support stack allocation and in-place update while remaining inferable.

Use this as evidence for separating independent axes.

Do not copy mode syntax into an agent-facing language before inference fails on a real program.

Reference: DOI 10.1145/3674642.

### 5.6 Reference capabilities and isolated regions

The Verona reference-capability work organizes objects into isolated regions with local memory-management strategies.

Use this as evidence that one runtime may legitimately use multiple memory strategies by isolated value class or region.

Do not build region capabilities before mutable or concurrent region consumers exist.

Reference: arXiv:2309.02983.

### 5.7 Yarrow

Yarrow studies region-based memory management in the presence of one-shot and multi-shot effect handlers.

Use this 2026 work as evidence that future effects complicate stack-discipline assumptions.

Do not design the current pure bytes arena around hypothetical multi-shot handlers.

Reference: arXiv:2607.15876.

### 5.8 MMTk

MMTk provides a modular GC toolkit and a safe Rust-facing core API, while VM bindings still own object-model, root, barrier, thread, and unsafe integration obligations.

Use this as evidence that adopting a mature collector is a major VM boundary, not a small crate addition.

Do not adopt MMTk for the cycle-free bounded invocation arena.

Reconsider it only when real tracing workloads exist.

### 5.9 Swift ownership

Swift's `borrowing`, `consuming`, noncopyable, nonescaping, and ownership-aware container work demonstrates practical separation between ordinary copyable values and resources or containers that need explicit ownership control.

Use this as evidence that resource semantics should be conditional by type class.

Do not make every ordinary immutable value noncopyable.

### 5.10 Fully in-place functional programming

Recent functional in-place work demonstrates that immutable programs can sometimes execute with safe storage reuse under uniqueness or precise reference counting.

Use this as a long-horizon optimization direction.

Do not make in-place execution observable.

## 12. Semantic Bytes Design

### 12.1 Type

Add one dedicated primitive semantic type.

Do not model bytes as `nominal(hidden_node)`.

Do not model bytes as `list<i64>`.

Do not model bytes as external host state.

### 12.2 Equality

Two byte values are equal exactly when they have equal length and equal visible octets in order.

Allocation, backing, view range, handle, and sharing are unobservable.

### 12.3 Duplication

Bytes are semantically duplicable.

A duplicated value remains independently usable.

The runtime may share immutable backing.

The language does not promise a deep physical copy.

### 12.4 Slices

A slice denotes exactly the selected contiguous subsequence.

A slice may share backing.

A nested slice should canonicalize to the original backing and checked absolute range where practical.

A zero-length slice is valid at every start in `0..=length`.

A nonzero slice requires the complete range within length.

### 12.5 Indexing

Indexes are signed `i64` at the language boundary.

Negative indexes trap.

Indexes not representable as host indexes trap before access.

Index equal to length traps.

A valid byte returns exact `i64` in `0..=255`.

### 12.6 Length

Length returns exact nonnegative `i64`.

The runtime policy must guarantee every accepted byte length fits `i64`.

### 12.7 Constants

A byte literal is immutable semantic payload.

Set a separate maximum literal size.

Do not allow one transaction to bypass the aggregate request and artifact policies through many literals.

Literal bytes enter artifact identity.

### 12.8 Fuel

Define deterministic logical charges.

A recommended starting model is:

- one base unit for every instruction;
- `bytes_len`: no additional per-byte charge;
- `bytes_at`: no additional per-byte charge;
- `bytes_slice`: one additional logical handle/view charge, not per visible byte;
- `bytes_equal`: one charge per compared octet, with exact early mismatch behavior if short-circuiting is retained;
- public input materialization and output materialization: separately accounted policy work, not silent unmetered unbounded work.

Do not let physical sharing change logical fuel.

### 12.9 Traps

Use stable typed runtime failure categories.

Do not collapse bounds, fuel, memory policy, malformed public value, and invalid Core IR into one error.

Do not mutate durable state on any runtime failure.

### 12.10 Products and variants

A product field may have type bytes.

A variant payload may have type bytes.

A product or variant containing bytes remains semantically immutable and duplicable.

Its fixed runtime cell layout contains handles rather than inline payload.

Its logical retained size remains dynamic.

### 12.11 Holes

A hole may expect bytes.

A byte-producing complete regionless operation may refine a byte hole if it satisfies the existing continuity rule.

Do not permit anonymous holes.

### 12.12 Inline authoring

Byte constants and regionless byte operations should be inline-eligible when their descriptors meet the existing rule.

Do not hard-code a second eligibility list if descriptors can derive it.

Bound literal and nested payload items exactly.

### 12.13 Queries

Legal constructors for bytes should expose exact operations and requirements.

Repair context should identify bytes as an exact expected type.

Machine descriptions should not expose arena handles.

### 12.14 Public runtime values

The Rust value representation may own decoded bytes.

The JSON representation must be canonical.

Do not serialize bytes as an unrestricted integer list unless the decision proves it superior.

Do not serialize private views or handles.

Output serializes visible content only.

## 14. Managed Arena Design

### 14.1 Scope

The arena belongs to one `Run`.

It does not belong to the daemon.

It does not belong to a workspace.

It is not persisted.

It is not shared across requests.

It is dropped after the run result is materialized or the run fails.

### 14.2 Handle

Use a dedicated newtype.

Prefer a nonzero checked integer domain.

Zero may be invalid.

Do not expose `usize` as semantic identity.

Do not expose an address.

Do not serialize the handle.

### 14.3 Tables

A simple candidate uses:

- a backing table;
- a byte-value/view table.

A backing owns immutable bytes.

A view stores:

- backing handle;
- start;
- length.

A byte-value handle indexes the view table.

Do not require each slice to copy backing.

Do not allow nested view chains to become unbounded.

### 14.4 No reuse

Do not reuse a handle index within one invocation.

This avoids generation complexity for the first arena.

Check table growth.

Fail before overflow.

### 14.5 Validation

Every handle access checks:

- nonzero;
- host conversion;
- table bounds;
- expected kind;
- backing bounds;
- view range.

Invalid internal handles are verifier or runtime errors.

They are not memory accesses.

### 14.6 Allocation preflight

Before allocating backing or view:

- check length arithmetic;
- check object count;
- check visible logical bytes;
- check distinct retained backing bytes;
- check view-retained bytes;
- check encoded result implications when applicable;
- check host capacity;
- check reserve failure behavior where expressible.

Do not partially update accounting before a fallible allocation without rollback.

### 14.7 Cleanup

Safe Rust drop is the implementation mechanism.

The semantic contract is deterministic invocation cleanup.

Test cleanup with instrumentation rather than relying on process RSS.

### 14.8 Views and retention

A one-byte view over a one-megabyte backing visibly contains one byte.

It physically retains the backing while the view lives.

Account both facts.

Repeated views over the same backing do not multiply distinct backing bytes.

They do increase view-object count and descriptor memory.

### 14.9 Equality

Equality reads exact visible ranges.

It must not depend on backing identity.

Two equal values with distinct backings compare equal.

Two unequal views into one backing compare by content.

### 14.10 Materialization

Public result conversion copies visible bytes into the public runtime value.

Preflight exact output limits first where possible.

Drop the arena only after the owned public value exists.

### 14.11 Current limitation

Invocation arenas cannot hold values across separate runs.

Do not hide that limitation.

A future persistent runtime state, closure, effect, resource, or long-lived cache will need another lifetime mechanism.

## 18. Interpreter Design

### 18.1 Cell

Add an explicit managed-handle cell representation.

Do not encode handles in `i64`.

Do not permit arithmetic on handles.

Do not permit public construction of handles.

### 18.2 Frame storage

Frames continue to own fixed cell arenas.

Managed payload lives in the invocation arena.

A frame cell may reference invocation-owned immutable data.

Frame destruction does not free backing.

Invocation destruction does.

### 18.3 Initialization

Inactive or invalid aggregate cells remain uninitialized or canonical according to the existing verifier/runtime contract.

Do not treat a zeroed inactive handle cell as a valid empty byte value.

### 18.4 Calls

Passing bytes to a call copies or transfers a handle cell according to semantic read behavior.

It does not clone payload.

Current semantic behavior remains that both caller-visible and callee-visible uses are valid when the value is used multiple times.

### 18.5 Branches

Branch arguments copy handle cells.

Unselected branches allocate nothing and consume no byte-operation fuel.

### 18.6 Products

Constructing a product containing bytes copies handle cells.

Projecting a byte field copies a handle cell.

No payload deep copy occurs.

### 18.7 Variants

Constructing a byte-payload variant stores a handle cell.

Selected match payload edges carry the handle.

Unselected variants allocate nothing.

### 18.8 Public input

Strictly decode public bytes before or during invocation preparation.

Check aggregate input encoded-byte policy.

Check decoded logical bytes.

Intern each accepted public byte value into the invocation arena.

### 18.9 Public output

Read exact visible bytes from the arena.

Check output policy.

Create an owned public byte value.

Only then destroy the arena.

### 18.10 Trap cleanup

Ensure every early return drops:

- frames;
- flat arguments;
- invocation arena;
- temporary public conversion buffers.

Test with a counted test arena or drop witness.

## 27. Memory-Management Alternative Matrix

The implementation decision must compare all of the following.

### 27.1 Deep copy on every semantic copy

Strengths:

- simple mental model;
- no shared backing;
- no lifetime metadata.

Weaknesses:

- poor large-value performance;
- repeated call, branch, aggregate, and projection copies;
- higher peak memory;
- conflicts with value-semantics optimization goals.

Default disposition: reject as the primary runtime representation.

Retain only as a small differential oracle if useful.

### 27.2 Safe shared backing through `Arc<[u8]>`

Strengths:

- simple safe Rust;
- immutable sharing;
- easy cloning;
- deterministic drop when counts reach zero.

Weaknesses:

- per-copy atomic count traffic;
- representation leaks into every copy path;
- does not use known invocation lifetime;
- can obscure logical versus physical accounting;
- nested views need careful retention.

Default disposition: useful prototype or oracle, not preferred mandatory runtime.

### 27.3 Invocation arena with checked handles

Strengths:

- matches exact run lifetime;
- no per-copy count updates;
- safe handle copies;
- deterministic bulk reclamation;
- simple no-cycle reasoning;
- compatible with explicit frames.

Weaknesses:

- retains dead values until run end;
- cannot escape;
- requires exact retained-byte policy;
- may raise peak memory for long runs;
- needs bounded tables and output materialization.

Default disposition: preferred first implementation.

### 27.4 Precise reference counting

Strengths:

- prompt reclamation;
- cycle-free fit;
- future uniqueness and reuse;
- derived from control flow in principle.

Weaknesses:

- substantial compiler/runtime/verifier work;
- loops and CFG joins;
- count traffic;
- cycle limitation;
- premature for invocation-scoped bytes.

Default disposition: future gate or disposable analysis only.

### 27.5 Tracing collection

Strengths:

- cycles;
- general shared graphs;
- simple surface semantics.

Weaknesses:

- root and object model;
- barriers;
- pauses or concurrency;
- larger trusted surface;
- unnecessary for first bytes.

Default disposition: reject for this campaign.

### 27.6 Lexical region inference

Strengths:

- prompt bulk reclamation;
- no per-object metadata;
- strong static bounds.

Weaknesses:

- escape constraints;
- tail calls;
- future effects;
- interprocedural inference;
- surface diagnostics.

Default disposition: study as future refinement after invocation arena.

### 27.7 Hybrid per value class

Strengths:

- mechanism matches semantics;
- avoids universal compromise;
- supports future resources and cycles.

Weaknesses:

- more compiler classifications;
- more verification;
- interactions need discipline.

Default disposition: long-horizon architecture, implemented now only for immediate/fixed/managed-invocation classes.

## 36. Mandatory Stop and Reversal Conditions

Stop, delete, or redesign when any applicable condition is met.

### 36.1 No real consumer

- Trigger: The manifest task remains an echo or can be expressed naturally with current values.
- Required action: Do not implement bytes; redesign the consumer or record postponement.

### 36.2 No closed encoding

- Trigger: Two public byte spellings remain accepted.
- Required action: Choose one direct encoding and delete aliases.

### 36.3 Unbounded decode

- Trigger: The decoder allocates from attacker-declared decoded size before checked preflight.
- Required action: Stop and repair the boundary.

### 36.4 Raw pointer

- Trigger: A runtime cell, diagnostic, artifact, or public value contains an address.
- Required action: Stop and replace it with a validated handle.

### 36.5 Handle escape

- Trigger: A managed handle survives beyond invocation-owned storage.
- Required action: Stop and redesign lifetime or materialize the value.

### 36.6 No kind check

- Trigger: A handle can index the wrong object table.
- Required action: Stop and add exact validation.

### 36.7 Handle reuse ambiguity

- Trigger: An index is reused while stale copies may remain.
- Required action: Stop; keep no reuse or add a proven generation scheme.

### 36.8 Hidden deep copy

- Trigger: Calls or aggregates clone byte payload unintentionally.
- Required action: Stop and fix semantic/physical separation.

### 36.9 Hidden retention

- Trigger: Views count visible bytes but not pinned backing.
- Required action: Stop and correct accounting.

### 36.10 Unmetered linear work

- Trigger: Equality or conversion scans arbitrary bytes without fuel or policy work.
- Required action: Stop and define exact charge.

### 36.11 Static preflight unsoundness

- Trigger: A dynamic result can exceed output bounds without checked rejection.
- Required action: Stop and repair result policy.

### 36.12 Overconservative preflight

- Trigger: Every useful byte-returning function is rejected from componentwise maxima.
- Required action: Stop and adopt a sound dynamic check.

### 36.13 Artifact ambiguity

- Trigger: Old and new bytes can parse under the same unambiguous header without exact schema distinction.
- Required action: Stop and cut over the format.

### 36.14 Dual protocol

- Trigger: Both v6 and new success paths remain active.
- Required action: Delete the old path.

### 36.15 Second schema

- Trigger: A hand-maintained bytes schema differs from executable DTOs.
- Required action: Delete it and derive from facts.

### 36.16 Second expression AST

- Trigger: Inline byte expressions use a separate validator or persistence form.
- Required action: Stop and normalize through the current path.

### 36.17 Daemon heap

- Trigger: Managed byte payload is retained globally without a lifetime consumer.
- Required action: Stop and return to invocation scope.

### 36.18 Premature RC

- Trigger: Reference counts exist but no object can outlive the arena.
- Required action: Delete them unless measured evidence justifies them.

### 36.19 Premature GC

- Trigger: A tracing collector appears for cycle-free bytes.
- Required action: Delete it.

### 36.20 Surface lifetime syntax

- Trigger: Agents must author regions or lifetimes for the classifier.
- Required action: Stop and infer or simplify.

### 36.21 Generic sequence scope

- Trigger: The campaign adds polymorphic collection machinery.
- Required action: Stop and return to dedicated bytes.

### 36.22 Effect scope

- Trigger: The classifier reads files or network.
- Required action: Stop and pass bytes as explicit input.

### 36.23 Unsafe code

- Trigger: Package unsafe prohibition is weakened.
- Required action: Stop unless separately authorized by the active user.

### 36.24 Dependency surprise

- Trigger: A codec adds build scripts, native code, or large unsafe transitively without review.
- Required action: Stop and compare alternatives.

### 36.25 Contrived operation

- Trigger: A retained byte operation has no application or exact boundary consumer.
- Required action: Delete it.

### 36.26 Contrived example

- Trigger: The release-manifest script does not exercise repair, restart, and decisions.
- Required action: Redesign or do not retain it.

### 36.27 Unreproducible measurement

- Trigger: Performance numbers lack commands, environment, or exact workload.
- Required action: Do not publish the claim.

### 36.28 Token overclaim

- Trigger: Byte reductions are described as token or monetary savings without telemetry.
- Required action: Correct the claim.

### 36.29 Agent contamination

- Trigger: Fresh trial reads implementation or prior payloads.
- Required action: Label it contaminated and do not use as isolated evidence.

### 36.30 Blocked harness

## 38. Final Instruction

Work autonomously.

Use the active checkout rather than historical momentum.

Prefer one strong dependency-closed vertical over broad scaffolding.

Be willing to replace current assumptions when evidence supports a better architecture.

Be equally willing to stop an attractive advanced design when the consumer does not justify it.

The desired result is a programming system in which coding agents manipulate exact program meaning, while the compiler and runtime infer as much safe memory behavior as the semantic graph and control flow permit.

Do not make agents micromanage memory merely because the implementation needs a policy.

Do not hide memory behind vague “copy” language when physical sharing is required.

Do not hide resource ownership behind garbage collection.

Do not adopt a collector before cycles exist.

Do not adopt a borrow checker before a value class needs noncopyability.

Do not preserve invocation arenas after values escape their invocation.

Converge on one coherent active system.

Verify every boundary.

Report only what was proved.
