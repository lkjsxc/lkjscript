## 1. Central objective

Turn the currently split system into one public, dependency-closed semantic-graph platform. The
normalized semantic kernel, publication path, compiler, artifact, runtime, deployment adapters,
service runner, and worker runner must become the maintained public path. The predecessor graph,
artifact, runtime, CLI request model, and duplicate adapter boundary must then be deleted rather
than kept beside the new system.

At the same time, replace the repository's JSON-heavy authoring and machine-output assumptions
with a compact, typed, agent-oriented CLI control plane; replace all maintained Python
repository tools with Rust; separate semantic revision identity from validation and operational
evidence; minimize durable identity; preserve multidimensional resource accounting; and make
every reported receipt atomically durable.

### 1.1 Definition of success

- A copied release executable can create an application in an absent or empty safe directory
  without Cargo, Python, repository source, a network registry, or an external bootstrap
  artifact.

- The created application is accepted semantic-graph authority, not generated source text.

- A fresh coding agent can discover the command model, find semantic owners, retrieve focused
  context, author connected changes, dry-run them, commit them, inspect the semantic diff, test,
  build, and run without reading Rust source.

- Ordinary authoring does not require embedding a recursive JSON object in a shell command or
  producing a large JSON request file.

- Default successful output is compact, deterministic, bounded, and directly useful to the next
  agent action.

- Large graphs, schemas, logs, artifacts, and review material are written to explicit files and
  represented on stdout by paths, digests, identities, and concise summaries.

- JSON remains available only where a real application or external integration benefits from it;
  it is not semantic authority, canonical storage, an artifact container, or the required
  control-plane representation.

- Every maintained first-party verification, scale, and service-acceptance tool is Rust; the
  three current Python tools and Python shebangs are removed.

- Public `new`, inspect/query, change, draft or equivalent work-in-progress flow,
  history/diff/merge, check, build, run, serve, worker, package, backup, restore, and doctor
  operations use one current semantic and runtime architecture.

- Maintained standard-package and `lkjournal` workflows use the same public path available to
  external application authors.

- The old graph, old change engine, old artifact, old runtime, old deployment decoder, old
  generated protocol, and compatibility residue no longer compile or appear in public
  documentation.

- Semantic revision identity does not change merely because validation implementation, witness
  layout, cache layout, or operational receipt format changes.

- Publication cannot make HEAD visible without its required semantic objects and acceptance
  evidence being durably and atomically retained.

- Durable identity is justified by continuity consumers instead of assigned indiscriminately to
  every representational node.

- Incremental claims are supported by complete-workflow observations and independent full-oracle
  agreement.

- The final system retains a plausible route to high runtime and compiler performance without
  embedding storage accidents or current runtime indexes in semantic meaning.

- The root `AGENTS.md` remains concise and below the ordinary Codex project-instruction budget;
  detailed campaign design is not copied back into it.

## 2. Why this campaign is necessary

The audited checkout contains two substantial architectures. Public exports, the release binary,
the documented operation registry, maintained application descriptors, and much current
documentation still describe the predecessor graph and JSON CLI. In parallel, the normalized
semantic kernel and its compiler, artifact, reference interpreter, dense runtime, exact
capabilities, deployment preparation, resource scopes, byte streams, resident execution, HTTP
adapter, live server, and structured worker have advanced through many private checkpoints.

This is no longer a harmless prototype boundary. Continued horizontal development on the private
path increases duplicate code, duplicate policy, duplicate tests, stale documentation, and the
cost of every later change. The campaign must force vertical closure: complete the smallest
dependency-closed public path, cut over maintained consumers, and delete the predecessor.

| Area | Audited condition |
|---|---|
| Public CLI | The generated operation table exposes `change (--request JSON \| --request-file PATH)`, JSON `run` arguments, and JSON deployment descriptors. |
| Release process boundary | `src/bin/lkjscript.rs` serializes finite responses and runtime readiness events with `serde_json` and explicitly requires `<descriptor.json>` for service and worker startup. |
| Private authored protocol | `src/platform/publication/authored_protocol.rs` defines a strict private Graph 5 JSON request, JSON response, and generated JSON Schema. |
| Private change model | `src/platform/change/request.rs` already contains a broad typed authored-change enum and bincode derives, but its public representation is still JSON-shaped and expression creation remains recursively nested. |
| Dual module graph | `src/platform/mod.rs` publicly exports predecessor modules while normalized kernel, compiler, publication, package, storage, and witness modules are private behind `dead_code` allowances. |
| Runtime duplication | `src/platform/execution/` contains predecessor compiler, VM, reference interpreter, and capability code beside a large `execution/normalized/` implementation. |
| Tooling | `tools/check`, `tools/semantic-scale`, and `tools/service-acceptance` are maintained Python programs containing verification, caching, process control, JSON parsing, benchmark, PostgreSQL, Docker, and service orchestration logic. |
| Instruction size | The audited root `AGENTS.md` is approximately 70 KiB and mixes durable work rules with detailed architecture. Codex ordinarily stops loading combined project instructions at 32 KiB unless configured otherwise. |
| Documentation drift | `README.md`, `docs/status.md`, `docs/roadmap.md`, and generated public protocol material primarily describe Graph 4 while the campaign ledger records later private normalized checkpoints. |

## 3. Decisions that this campaign makes now

### 3.1 One public architecture, followed by deletion

- Freeze unrelated expansion of the private normalized path until its public dependency closure
  is mapped.

- Do not add another adapter, owner kind, language feature, storage format, or protocol
  generation unless it is required by the maintained public cutover or removes a blocker.

- Select the normalized semantic kernel as the presumptive survivor because it already has the
  broadest current dependency-closed implementation, but verify that its semantics and physical
  model satisfy the audits in this prompt.

- Correct the normalized design before cutover when a defect would otherwise become the new
  public contract.

- Do not expose the normalized path under a `graph5`, `new`, `next`, `experimental`, or edition
  flag.

- At the cutover commit, the normalized path becomes simply the current semantic graph,
  compiler, artifact, runtime, and deployment implementation.

- After all maintained consumers pass, delete predecessor modules in the same campaign.

- Remove `dead_code` allowances whose only reason was a private cutover boundary.

- Remove versioned names from ordinary user vocabulary; retain opaque contract identities only
  at actual decoding and integrity boundaries.

- Do not retain predecessor tests as negative snapshots unless they prove current rejection at a
  public boundary.

### 3.2 JSON is not required for semantic development

JSON is useful as an interchange format, but it is not intrinsically suited to graph authoring,
canonical storage, high-volume repeated agent interaction, shell composition, localized repair,
or compact context. This campaign therefore removes JSON from required semantic-development
control paths without attempting to remove JSON as application data.

| Boundary | Decision | Required interpretation |
|---|---|---|
| Accepted semantic graph | No JSON | Use explicit canonical binary records and typed digests. |
| Repository objects and persistent roots | No JSON | Strict bounded binary codecs own canonical bytes. |
| Package and artifact transport | No JSON | Use deterministic segmented binary representation. |
| Ordinary change authoring | No JSON by default | Use direct CLI operations and a compact typed change notation. |
| Default finite CLI response | No JSON by default | Use compact deterministic records intended for an agent and a shell. |
| Optional machine projection | JSON allowed | Expose only when a real integration needs it; derive it from typed results. |
| Capabilities and schema discovery | No giant JSON dump by default | Provide focused sections, digests, compact help, and file export. |
| Deployment and host grants | No required JSON descriptor | Use typed CLI/grant notation or another selected compact transport. |
| Resident protocol | No JSONL default | Adopt only after measurement; share the typed request model. |
| Application HTTP payloads | JSON retained | It is ordinary application data selected by graph meaning. |
| Review and diagnostics | JSON optional | Compact text is normal; exact full material may be exported. |
| Evidence files | Format chosen by consumer | They are not semantic authority; binary, compact text, or JSON may be appropriate. |

- Do not globally remove `serde_json` while maintained HTTP or explicit export consumers need
  it.

- Do remove `serde_json` and `schemars` from control-plane modules that no longer have a JSON
  consumer.

- Do not keep generated JSON Schema merely because it already exists.

- Do not introduce YAML as a replacement; indentation, implicit typing, aliases, and parser
  variation are worse for this boundary.

- Do not introduce TOML for recursive semantic changes; its data model does not match the task.

- Do not require agents to emit CBOR, MessagePack, protobuf, bincode, or another binary format
  directly from shell commands.

- Keep the typed operation model independent from the selected compact textual representation.

- Make optional JSON a projection of the typed model, never the owner of fields, defaults, tags,
  or validation.

- Delete public `--request JSON` once the compact authoring path covers every maintained
  workflow.

- Reject predecessor JSON change and deployment requests after cutover instead of silently
  translating them.

### 3.3 Replace Python with one Rust development harness

The current Python footprint is small enough to remove decisively but important enough that
literal transliteration would preserve duplication. Build one Rust development harness with
shared process, receipt, logging, hashing, cache, benchmark, and service orchestration
primitives. Migrate behavior vertically, prove parity, then delete all three Python tools.

- Create a non-shipped Rust package or binary with an ordinary name such as `lkjscript-dev`; do
  not overload the released application-development CLI with contributor-only commands.

- Use a workspace layout that keeps the main library dependency direction acyclic.

- Provide one stable contributor entry point, for example `cargo run --locked -p lkjscript-dev
  -- ...` and optionally a concise Cargo alias.

- Implement `check`, `scale`, and `service` command groups in the same binary.

- Share bounded child-process execution, timeout, signal, log, digest, atomic-file, environment
  identity, and receipt code.

- Retain the existing verification DAG and cache semantics only after auditing their
  correctness; do not preserve incidental Python structure.

- Port the checker's self-tests before deleting the Python checker.

- Port semantic-scale generation through public CLI calls; do not reach into private graph
  builders merely because the harness is Rust.

- Port service acceptance with exact PostgreSQL container lifecycle, redacted environment
  handling, live service and worker readiness, shutdown, backup, restore, and retained evidence.

- Use typed receipt structures and explicit canonical encoding; a readable optional JSON
  projection is acceptable for external CI consumers.

- Make successful terminal output compact and retain detailed child logs under bounded artifact
  directories.

- Ensure interruption and child failure leave an inspectable failure receipt instead of an
  absent aggregate record.

- Delete Python shebangs, imports, source files, instructions, and CI assumptions after parity.

- Add a repository gate that rejects new first-party Python files or Python shebangs unless the
  active user explicitly authorizes a narrowly justified external fixture.

- Do not require Python in contributor setup after migration.

### 3.4 Semantic revisions and evidence are separate domains

A revision identifies accepted meaning and history. Validation evidence proves that a particular
validator and policy accepted that meaning. A verification receipt records an operational
observation. These facts may be atomically linked, but they must not collapse into one identity
domain.

- Inventory every byte currently hashed into semantic revision, semantic root, revision record,
  witness manifest, validation certificate, transaction receipt, artifact manifest, and HEAD.

- Classify each field as semantic meaning, history structure, publication metadata, validation
  evidence, derived acceleration, compiler input, runtime input, or operation observation.

- Remove validation implementation identity, witness layout identity, query-index identity,
  cache generation, wall-clock observation, host identity, and verification receipt from
  semantic meaning hashes unless a normative semantic reason exists.

- Make semantic revision identity stable across rebuilding or upgrading validation evidence for
  unchanged meaning and unchanged semantic parents.

- Keep parent relationships in revision semantics only to the extent required by the selected
  history model; do not confuse content identity with commit identity without stating the
  distinction.

- Use separate typed digests for semantic revision, validation evidence, transaction or
  publication receipt, verification receipt, and benchmark observation.

- Do not permit implicit conversion between digest domains.

- Bind publication evidence to the exact repository, package, semantic revision, semantic root,
  dependency bindings, validator contract, policy, and relevant resource observations.

- Make acceptance visibility conditional on durable semantic objects and durable evidence
  binding.

- Make HEAD refer to the exact semantic revision and the durable publication record needed to
  prove acceptance.

- Allow later revalidation to append or replace current evidence policy without mutating
  accepted meaning.

- Preserve old evidence needed to justify historical acceptance according to the retention
  policy.

- Do not make disposable query or summary indexes part of the semantic revision merely to detect
  cache corruption.

- Use independent rebuild-and-compare logic for derived data.

- Crash-test every transition between object write, synchronization, evidence write, directory
  synchronization, and HEAD visibility.

### 3.5 Durable identity must be minimized

Stable identity is one of the semantic graph's strongest advantages, but indiscriminate identity
assignment creates larger requests, more storage, more indexes, more tombstones, more merge
conflicts, more allocation rules, and more vocabulary. Audit each identity domain from first
principles.

| Current concept | Presumption | Reason to test |
|---|---|---|
| Repository | Retain | Required to reject foreign authority and bind history. |
| Package | Retain | Required for dependency and exact cross-package references. |
| Module | Likely retain | Rename, move, namespace, query, and package organization need continuity. |
| Top-level declaration | Retain | Exact references, rename, move, history, merge, and compilation need continuity. |
| Field, case, operation, requirement, port | Evidence-gated retain | Exact use sites and reorder-safe edits may justify continuity. |
| Function or operation parameter | Audit scope | External selection and reorder may need scoped identity; repository-global identity may not. |
| Type parameter | Audit scope | Substitution and reorder need continuity, but declaration-scoped identity may suffice. |
| Lexical binding | Prefer scoped | External durable reference is uncommon; body-scoped identity may be enough. |
| Expression | Prefer scoped | Precise replacement needs continuity, but global owner identity for every node may be excessive. |
| Documentation and annotation | Audit | Some need exact attachment/history; content-addressed or owner-scoped records may suffice. |
| Request-local symbol | Ephemeral | It must never become a durable identity domain. |
| Type object | Content identity | Immutable canonical structure should normally use a digest, not allocated stable identity. |
| Compiler unit | Content identity | It is derived from semantic inputs. |
| Runtime function/value/resource | Dense or scoped | Hot and task-local representations must not leak into graph identity. |

- For every current ID type, identify all persisted references, public selectors, merge
  consumers, diff consumers, cache keys, runtime consumers, and tests.

- Delete an ID type when no continuity consumer survives.

- Use a pair such as declaration identity plus local node identity when cross-body global
  identity is unnecessary.

- Keep scoped identities unambiguous in diagnostics and change requests.

- Do not replace stable identity with positional paths that break on insert, reorder, or sibling
  edits.

- Do not use names as hidden identity.

- Do not use content digests for mutable semantic entities whose continuity across changes
  matters.

- Do not allocate durable IDs in a separate round trip.

- Bind deterministic allocation to exact base, normalized request, identity domain, and ordinal
  or use another collision-safe scheme with equivalent replay properties.

- Test concurrent branch creation, deterministic replay, idempotency replay, branch merge,
  deletion, recreation with the same name, rename, move, reorder, and collision rejection.

- Measure storage and request-size changes from identity contraction on large expression bodies
  and wide records/interfaces.

- Update query, diff, merge, tombstone, backup, and compiler consumers in the same cutover.

### 3.6 A resident session is not an invariant

- Keep stateless CLI correctness complete before considering a session.

- Construct equal workflows that perform orientation, focused queries, change preparation,
  commit, check, and diff through repeated process invocations.

- Measure process startup, repository open, registry discovery, index load, semantic reads,
  output bytes, elapsed time, CPU, and peak memory.

- Prototype a session only when repeated startup or repeated context materially dominates the
  workflow.

- Compare stdio framing, a local client/server split, and no session only if the baseline
  warrants the complexity.

- Do not default to JSON Lines.

- If retained, use the same typed request and response model as stateless commands.

- Bind every session handle to repository, exact revision, schema digest, policy, and expiration
  or explicit lifetime.

- Invalidate stale handles deterministically.

- Preserve cancellation, bounded queues, output bounds, crash recovery, and clean shutdown.

- Never let session memory become semantic authority or the only place a prepared write exists.

- Retain a measured reversal condition and delete the session if benefits cease to be material.

### 3.7 Resource accounting stays multidimensional

| Boundary | Independent dimensions to preserve or observe |
|---|---|
| Input decoding | bytes, records, fields, nesting depth, collection items, string bytes |
| Semantic reads | owners, relation edges, dependency edges, type objects, exact lookups |
| Persistent storage | map pages, pack index probes, objects, bytes read, bytes written, fsync or equivalent operations |
| Change lowering | operations, preconditions, allocated identities, rewritten owners, retired identities |
| Impact analysis | frontier owners, reverse edges, packages, targets, tests, fanout |
| Validation | owners, relations, type unifications or substitutions, effect checks, cycle checks, diagnostics |
| Compilation | units considered, units reused, units rebuilt, semantic bytes, instructions, constants, layouts |
| Artifact assembly | segments, bytes read and written, copied bytes, peak buffered bytes |
| Runtime | instruction steps, call depth, value stack, language allocations, allocation bytes, collection items, capability calls |
| Resident operation | admitted tasks, queue depth, worker permits, deadlines, cancellation work, live resources |
| External adapters | calls, input bytes, output bytes, records, transactions, retries where policy permits |
| CLI response | records, bytes, exported file bytes, continuation work |
| Operational observation | elapsed time, CPU time, peak RSS, page faults, filesystem operations when available |
| Provider economy | exact prompt tokens, cached tokens, output tokens, retries, monetary charge only when telemetry exists |

- Use typed units.

- Do not add unrelated dimensions together merely to produce one fuel number.

- A deterministic admission budget may contain multiple independent maxima.

- Operational measurements such as wall time and RSS are observations, not deterministic
  semantic budgets.

- Graph-authored resource limits are application policy inputs, not automatically host grants.

- Deployment grants must not exceed graph requirements and must preserve units.

- Report consumption at the boundary that owns it.

- Avoid double counting shared work across nested layers.

- Tests must force each deterministic budget independently and verify the owning diagnostic.

- Defaults may be tuned from evidence; they are not language principles.

### 3.8 Evidence must be atomically retained

- Define one reusable Rust primitive for writing a complete receipt to a private sibling,
  flushing it, synchronizing it when required, and making it visible with one atomic rename.

- Write or synchronize referenced logs and output files before publishing a receipt that claims
  them.

- Bind receipt digests to exact referenced file digests, command identities, inputs, toolchain,
  platform, environment names, and result status.

- Retain aggregate failure receipts even when a child exits, times out, is signaled, emits
  excessive output, or the verifier itself encounters an infrastructure error.

- Do not print a success receipt path before the final receipt is durable.

- Do not print a failure as an unstructured Python or Rust traceback.

- Use a stable compact terminal failure plus the durable evidence path.

- Test interruption after every material write and rename boundary.

- Test short writes, synchronization errors, rename failure, full disk behavior, permission
  failure, stale cache records, and corrupted referenced logs where injection is practical.

- Keep evidence retention separate from accepted semantic publication while applying the same
  atomicity discipline.

## 13. Phase 8 — Prove locality, scale, and long-term performance

### 13.1 Locality definitions

- Semantic locality means the exact changed and affected semantic frontier is bounded by actual
  dependencies rather than project size.

- Storage locality means physical reads and writes follow the changed semantic frontier plus
  bounded index paths.

- Validation locality means unchanged independent owners are not decoded or revalidated.

- Compilation locality means unchanged units with equal semantic inputs are reused.

- Artifact locality means unchanged segments are reused or copied without rebuilding unrelated
  code and data.

- Query locality means exact or narrow queries do not construct the complete graph.

- Runtime locality means startup and invocation load only the selected target closure or a
  justified bounded resident set.

- Backup locality is not assumed; exact retained closure may be intentionally broad, but memory
  use and transfer must remain bounded.

- A unit test over an in-memory map is not end-to-end locality evidence.
