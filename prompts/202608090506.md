## 6. Semantic and representation requirements

### 6.3 Identity domains must not be conflated

Keep these domains distinct:

- stable workspace `EntityId` and `NodeId`;
- transaction-local draft node and draft binding handles;
- compiler-local dense HIR identities and physical slots;
- nominal semantic declaration identity;
- runtime/layout identity or fingerprint;
- source provenance;
- display name and source order.

A public editing API must not require callers to construct or persist `BindingId`, `PlaceId`, `LoanId`, product/enum dense indexes, VM slots, source IDs, source order, or source-derived hashes.

Names are presentation and lookup aids, not universal identity. A nominal reference in a transaction or structured semantic query must resolve through a stable workspace entity identity or an equally strong opaque semantic handle. Display names may accompany it.

Compiler-local dense identities may remain private derived implementation details. They must be allocated deterministically with checked conversions and must not leak into long-lived agent-facing state.

### 6.4 Minimal source-independent type input

- lowering resolves once into the internal compiler type;
- it is not another mutable type authority;
- display strings are never the only machine-readable nominal identity; and
- unsupported generic or recursive forms fail explicitly rather than being silently misrepresented.

Do not copy the entire compiler type system merely for symmetry. Support the dependency-closed forms required by this vertical and leave unsupported forms honest.

Using separate transactions to create a declaration and then use its returned `EntityId` is acceptable. Do not create a general transaction-wide symbol graph merely to save one round trip. - deep/small-stack behavior;

- documentation examples; and
- Miri, sanitizer, fuzz, or property checks only where the changed unsafe/trust boundary makes them relevant.

Do not silently substitute a weaker command. If the environment prevents a command, report the exact command, failure category, and remaining successful evidence.

## 21. Git discipline

Preserve unrelated work.

Commit only cohesive changes from this task. A small sequence of dependency-ordered commits is acceptable when each commit is coherent and buildable; a single coherent commit is also acceptable. Do not create temporary checkpoint commits that leave a second active architecture.

Push the current branch without force when credentials and the upstream permit it. Verify the branch and upstream state before claiming success. Never rewrite unrelated history.

## 22. Final report

The final report must state, with no inflated claims:

1. the inspected starting revision and final revision;
2. the implemented source-free capabilities;
3. any semantic or representation changes;
4. source-bound assumptions removed;
5. important obsolete paths deleted;
6. the exact ownership behavior proven;
7. transaction atomicity and identity behavior;
8. direct compile/VM results;
9. imported/source-free convergence evidence;
10. structural work counters or performance measurements and their protocol;
11. exact verification commands and outcomes;
12. untested or environment-blocked paths;
13. commit and push state;
14. remaining risks and deliberately deferred work; and
15. the single next highest-leverage problem.

Distinguish implementation from plan, semantic identity from layout identity, current behavior from target behavior, and measurement from hypothesis.
