# Task: Remove the remaining borrow-call scale pathologies without creating another architecture

Use the accompanying replacement `AGENTS.md` as the repository-wide engineering policy for this task. Replace the root `AGENTS.md` with it before or as part of the first cohesive commit, unless the checkout already contains identical or stronger instructions. This task prompt is an external instruction, not product documentation; do not commit a copy of this prompt merely to preserve an agent handoff.

## 1. Intent

Continue the current architectural reset by removing the next **measured, dependency-closed causes of superlinear work** in the existing local product path.

The immediate product path is:

```text
text/package import
    -> typed HIR analysis and ownership checking
    -> semantic WorkspaceSnapshot
    -> memory planning
    -> SSA construction, verification, and normalization
    -> bytecode lowering and validation
    -> one baseline-native attempt or generic VM execution
```

The current borrow-call scaling fixture has already exposed and helped remove two major pathologies: instruction-indexed full validator state and unconsumed generic preparation/identity work. Do not rebuild either mechanism in a different form.

At the repository head inspected while this task was written (`0705fdf8d233e0be3f8eb0370c9d4d9454ba2038`), the retained measurements for 1,024 through 16,385 repeated borrowed calls show approximately quadratic growth in three remaining phases:

- HIR analysis: about `7.8 ms -> 29.9 -> 116.3 -> 479.3 -> 1,876.9 ms`;
- bytecode lowering: about `1.2 ms -> 4.0 -> 15.1 -> 56.2 -> 233.2 ms`;
- VM execution: about `2.5 ms -> 8.7 -> 28.1 -> 106.0 -> 573.8 ms`.

The checkout may have advanced. Treat these numbers and the concrete leads below as orientation, not as authority. Inspect the actual branch, current diff, recent commits, current documents, and current measurements before changing code.

The goal of this turn is to make this product path scale according to the amount of real work, while preserving language semantics, memory safety, failure cleanup, cancellation/resource behavior, determinism, and the unrestricted validity of trusted programs.

This is not a request to expand the language, semantic workspace, daemon story, optimizer, backend matrix, or platform scope. It is a request to remove demonstrated waste from the one active path.

## 4. Concrete code leads that must be verified

The following are direct observations from the inspected checkout. They are strong hypotheses, not permission to skip profiling or semantic analysis.

### 4.1 HIR ownership analysis repeatedly reconstructs future-use information

Relevant files include:

- `crates/lkjscript-compiler/src/ownership/checking/arguments.rs`;
- `crates/lkjscript-compiler/src/ownership/checking/expressions.rs`;
- `crates/lkjscript-compiler/src/ownership/uses.rs`;
- related control/scope/loan logic under `crates/lkjscript-compiler/src/ownership/`.

In the inspected implementation:

- `check_sequence` clones the outer future set for every expression and traverses every later expression to rebuild the suffix-use set;
- `check_arguments` performs the same suffix reconstruction for arguments;
- `check_expr` traverses the complete current subtree again through `uses(expression)` before expiring loans;
- `uses`, `uses_bindings`, branch handling, and related helpers allocate and union ordered sets repeatedly.

For a flat sequence, this makes the ownership pass revisit a linearly shrinking suffix at every step. The repeated-borrow fixture is almost an ideal quadratic trigger.

Replace this with a simple, explicit liveness/future-use design whose total work is proportional to the HIR and the relevant binding-use facts, not to all suffixes multiplied by sequence length.

Possible shapes include a reverse prepass with per-binding remaining-use counts, a compact expression-use summary consumed by a forward checker, or another equally direct design. Do not blindly materialize a complete suffix set for every node; that can exchange time quadraticity for quadratic retained memory. Prefer dense checked storage when HIR identities make that natural. Preserve deterministic diagnostics and evaluation order; map iteration must not choose which error is reported.

The new design must preserve at least:

- temporary borrow lifetime through an exact call;
- references that remain live because of later uses;
- early loan expiration when no future use exists;
- left-to-right argument and sequence semantics;
- branch/conditional future-use joins;
- let and mutable-local scope behavior;
- move, resource, and structural ownership behavior;
- loops and the currently explicit unsupported loop-carried ownership cases;
- typed allocation failure and checked identity/index conversion; and
- deep-input stack safety at least as strong as the current path.

Delete obsolete recursive suffix collectors or narrow them to genuine consumers after the cutover. Do not keep both old and new liveness authorities.

### 4.2 Bytecode local classification rescans the whole SSA function for every value

Relevant files include:

- `crates/lkjscript-compiler/src/codegen/locals.rs`;
- `crates/lkjscript-compiler/src/codegen/locals/coloring.rs`;
- `crates/lkjscript-compiler/src/codegen/locals/storage.rs`;
- `crates/lkjscript-compiler/src/codegen/interference.rs`;
- cleanup-value traversal used by local allocation.

In the inspected implementation, `local_storage_class(function, chunk, value)` repeatedly scans all blocks, parameters, instructions, entry parameters, and sometimes places to rediscover a value's type, producer, parameter role, and structural-place facts. `color_locals` invokes it for each value. This alone is sufficient to explain a quadratic lowering component in a large single function.

Build the necessary value metadata once while the existing local-allocation pass is already walking the function, or compute the storage class directly in that pass. Keep the representation local to this mechanism. Do not introduce a repository-wide metadata registry or a second SSA authority.

Audit adjacent lowering work after fixing this obvious scan:

- cleanup-chain traversal frequency;
- liveness fixed-point cloning;
- interference construction and graph density;
- color selection complexity;
- repeated structural-representation lookup;
- repeated function/block/value lookup during emission; and
- constant/global/metadata interning.

Fix additional causes only when profiling or a complexity audit demonstrates material repeated work on the selected product path. A sparse straight-line program should not pay for a dense general interference graph if the existing semantics permit a simpler allocation strategy, but do not replace the allocator merely on aesthetic grounds. Measure and preserve all storage-class distinctions, failure-cleanup operands, parameter slots, and generated bytecode behavior.

### 4.3 VM safe-boundary checks linearly search cleanup ranges per instruction

Relevant files include:

- `crates/lkjscript-vm/src/run/failure_cleanup.rs`;
- `crates/lkjscript-vm/src/run/state/execution.rs`;
- VM frame/call/control state;
- validated bytecode cleanup-range definitions and validation.

In the inspected implementation, `run_loop` calls `is_failure_boundary` before and after ordinary stepping. `is_failure_boundary` linearly searches the current function's sorted, non-overlapping `failure_cleanup_ranges`. A successful program therefore scans an increasingly large range table approximately twice per instruction. Failure unwind also performs a linear range lookup per frame.

Replace repeated full scans with the simplest correct indexed lookup. A shared binary-search helper over validated sorted ranges may be sufficient and is a reasonable first correction. If measurements show that even logarithmic lookup materially dominates, use a small frame-local cursor/index or another direct mechanism that handles sequential execution cheaply and repositions correctly on jumps, calls, returns, and exceptional paths. Do not build a general interval framework.

Preserve exactly:

- whether deadline, fuel, and runtime-resource checks occur at a safe failure boundary;
- start-inclusive/end-exclusive cleanup-range semantics;
- gaps and empty range collections;
- variable-width bytecode offsets;
- jumps and loop backedges;
- main and prototype frames;
- call entry, return, and tail-call behavior;
- pre-step versus post-step failure sites;
- unentered-call cleanup versus ordinary cleanup;
- failure unwind order across frames; and
- cleanup continuation even when diagnostic retention is exhausted.

A small test-only linear reference lookup is acceptable as an independent oracle. It must not remain in the production hot path.

## 6. Measurement and acceptance criteria

Do not use unstable wall-clock thresholds as ordinary CI correctness gates. For this development task, however, the before/after release matrix must demonstrate the algorithmic correction.

A successful result should satisfy all of the following:

1. The generated program remains semantically unchanged and returns `42` through the validated product path.
2. Trusted compilation and VM execution retain no count-based admission quota.
3. The identified full suffix/function/range rescans are absent from the production hot path.
4. HIR analysis, bytecode lowering, and VM execution no longer exhibit the prior near-`4x` cost for each `2x` increase on the borrow-call matrix. Aim for a doubling ratio close to linear; a median ratio below roughly `2.5x` over the larger sizes is a useful development selection criterion, not a permanent platform promise.
5. Peak memory remains bounded by actual retained program/analysis state rather than quadratic intermediate state.
6. Small workloads do not regress materially without a documented reason. Report absolute times as well as ratios; do not celebrate a percentage on a sub-millisecond phase while harming the product path.
7. Results are reproducible from a retained command/harness and identify commit, worktree, machine, toolchain, profile, sample count, and cache state.
8. Correctness is supported by semantic tests, not by timing alone.

If one phase remains superlinear after the concrete cause is removed, profile again. Fix a second cause only when it is in the same dependency-closed path and can be completed coherently. If the remaining cause requires a distinct architectural project, record the evidence and leave it as the next task instead of scaffolding that project now.

## 7. Tests required by the changed boundaries

At minimum, retain or add focused coverage for:

### Ownership/liveness

- repeated temporary shared borrows of one owner;
- a reference used later versus a reference dead after the current expression;
- multiple bindings with interleaved last uses;
- argument order and suffix liveness;
- `do`, `let`, mutable local, conditional, return, break, trap, and exit paths;
- branch state merge and cleanup equivalence;
- current loop restrictions;
- move-after-borrow and borrow-after-move rejection;
- resource/structural ownership cases already supported; and
- large flat and deep generated shapes without a semantic quota or native-stack failure.

### Local allocation/lowering

- every existing `LocalStorageClass` category;
- entry and non-entry parameters;
- plain, unique, resource, structural owner, structural view, structural destination, and dynamic owner values where supported;
- moved structural places;
- cleanup-only liveness;
- calls with unentered cleanup;
- branch/join interference; and
- bytecode execution equivalence on the reference VM.

### VM range lookup and unwind

- offset exactly at range start;
- offset inside a range;
- offset exactly at range end;
- before the first range, after the last range, and in a gap;
- empty and one-range functions;
- sequential stepping and non-sequential jumps;
- loop backedges;
- nested prototype frames and main;
- successful calls, entered call failures, and unentered cleanup;
- deadline, cancellation, fuel, allocation, stack/value, and other relevant runtime-policy failures; and
- ordinary and structural cleanup order.

Use differential/property testing where an independent reference is cheap. Do not keep a complete duplicate production engine merely to obtain an oracle.
