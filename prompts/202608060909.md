### Observed source representation

The current source format uses one marker or atom per physical line, paired `name/` and
`/name` markers, strict lowercase naming, and deeply expanded signatures and imports. A tiny

The current Semantic Source service has useful ideas—stable node access, typed holes,

### Observed execution architecture

The audited architecture described this broad flow:

```text
canonical text tree
    -> resolved typed HIR
    -> verified typed SSA
    -> normalized SSA
    -> validated bytecode
    -> SSA evaluator / VM / baseline native / proof native
```

Exact memory, representation, ownership, witness, and prepared-program facts are repeatedly
carried, reconstructed, authenticated, or compared across layers. Some repetition protects
real serialized or executable boundaries; some appears to exist inside one trusted process
because the architecture requires every tier to prove its own copy of the same fact.

Retained baseline-native evidence showed that generated code can materially outperform the
VM on a narrow scalar workload. That is a reason to preserve and measure native execution,
not a reason to preserve every current native abstraction. The proof-oriented optimizing
path has a mixed record: a forced workload was adopted in one historical run, another run
was rejected for a scalar regression, a later post-cutover run was rejected again, and
automatic promotion remained disabled and unmeasured. OSR, deoptimization, and speculation
were absent.

The leading simplification hypothesis is therefore a universal generic execution path plus
one measured baseline native accelerator as a single tiered product path, with a small
reference executor used only when it provides high-value semantic testing. The separate
proof-oriented product tier should be frozen and treated as a deletion candidate unless
representative evidence justifies its ongoing cross-product cost. Test this hypothesis;
do not preserve or reject it by ideology.

## Core diagnosis

Use the audit to test the following diagnosis.

### 1. A constraint lattice replaced scalable engineering

Small prototype limits were promoted into language rules, compiler budgets, resource
profiles, documentation, tests, repository topology, graph authority, and acceptance gates.
Every later mechanism then had to preserve and explain the limits. This made the limits
harder to remove than the algorithms they originally protected.

The correct response is not another migration framework. Remove the semantic restrictions,
make algorithms scale safely, and retain only coarse operational resource policy where a
host genuinely needs it.

### 2. The feature cost is multiplied by execution tiers

A language feature frequently crosses source schema, parser, HIR, ownership, SSA, SSA
verification, evaluator, bytecode, bytecode validation, VM, native planning, baseline
lowering, optimizing lowering, proof checking, process rehydration, package facts,
documentation facts, and evidence gates.

This cross-product can make a narrow feature look rigorous while preventing the language
from becoming broad, usable, or easy to change. End the policy that every experiment is a
mandatory implementation surface.

### 3. Internal facts are treated like hostile serialized input

Independent reconstruction and digest authentication are valuable across untrusted or
persistent boundaries. They are often redundant between typed structures created and
consumed synchronously inside one process.

Identify real trust boundaries. Use typed construction internally. Verify once at the
boundary. Delete repeated authentication that does not defend a distinct attacker, stale
cache, process, disk artifact, or unsafe mechanism.

### 4. Documentation machinery has become a second product

Public-fact shards, markers, status closure, graph context, platform revisions, capsule
manifests, handoff records, evidence pages, and exact-data comments impose a broad update
cost. Their incompleteness means the cost is not buying trustworthy authority.

Replace the system with a small active documentation set and executable references.

### 5. The current syntax amplifies token and context cost

One marker per line and repeated open/close names make small programs physically large.
Tiny file and token limits then force more imports and fragmentation. This is especially
poor for agents with bounded context and for incremental editing.

Do not spend major effort polishing the current notation. Keep only the minimum bootstrap
adapter required while the semantic model is established.

### 6. The Semantic Source schema is bound to the wrong layer

Typed holes and transactions are useful, but the schema mirrors physical syntax and trivia.
A permanent semantic model must represent declarations, expressions, references, types,
effects, ownership, capabilities, holes, conflicts, and dependencies independent of any
one textual projection.

### 7. Resource safety and language meaning are conflated

The same category system contains source counts, compiler work, protocol bytes, semantic
session fuel, scheduler events, task records, and output limits. A low fixed maximum can
therefore reject an otherwise valid trusted local program.

Language meaning, representation boundaries, host policy, and implementation tuning must
be separated.

### 8. Repository structure policy creates artificial modules

Hard line, byte, width, depth, and fan-out constraints encourage numbered shards, façade
layers, one-child directory ladders, and tiny files whose relationships are harder for an
agent to retrieve than a cohesive larger module would be.

Remove numeric topology validity. Recombine artificial fragments, then split only on
semantic ownership and measured navigation or compilation value.

### 9. Custom infrastructure is not automatically a performance advantage

The repository has implemented substantial custom scheduling, graph, protocol, storage,
verification, and JIT infrastructure while maintaining very few third-party dependencies.
Owned infrastructure is justified for a small hot mechanism or a unique semantic need. It
is not a goal in itself.

Evaluate mature dependencies when they can delete code, reduce risk, or accelerate the
roadmap. Measure hot paths and compile costs before deciding.

### 10. Toy workload completion displaced product foundations

The accepted next sequence prioritized native borrow transfer and full Brainfuck completion
before documentation repair, general generics, broad source authoring, and practical
workloads. This ordering is no longer valid.

Remove Brainfuck from all required gates and roadmap authority.

## North-star architecture

The desired conceptual system is:

```text
agent or human operation
    -> semantic program transaction
    -> immutable semantic snapshot
    -> incremental name/type/effect/ownership queries
    -> canonical typed core IR
    -> verified executable IR
    -> one coherent production runtime path
```

Text import, text rendering, structured interchange, IDE views, and semantic diffs are
projections around the semantic snapshot. They do not compete as canonical program
authorities.

The exact data structures and engine choice remain empirical engineering decisions, but the
following properties are required.

### One semantic authority

- The compiler consumes semantic program data directly.
- Text parsing constructs or updates semantic data through the same validation rules as
  agent operations.
- Names, formatting, file positions, and comments are not the identity of mutable entities.
- Derived types, bindings, effects, ownership, layouts, and dependencies are query results,
  not duplicated source authority.
- Immutable snapshots can be hashed for caches and artifact identity without making every
  mutable edit content-addressed.

### One production path

- Every valid ordinary program has a generic production execution path.
- Native compilation and specialization are internal accelerators, not separate language
  subsets.
- An optimization failure does not make a valid program invalid.
- A reference evaluator, if retained, is a test oracle with deliberately small scope and
  low maintenance cost.
- Public forced-engine modes should be diagnostic tools, not product semantics.
- Feature work is implemented once at the semantic and executable-IR levels and reused by
  the production runtime.

### Real trust boundaries

Keep fail-closed validation where data crosses:

- an untrusted edit or source-input boundary;
- a serialized snapshot, cache, package, or executable-artifact boundary;
- a daemon or process boundary;
- a capability, filesystem, network, database, or host-provider boundary;
- an unsafe FFI or executable-memory boundary.

Inside one synchronous trusted pipeline, use private constructors, typed IDs, and opaque
verified wrappers instead of repeated content digests and independent fact registries.

### Collector-free source abstraction

Continue the product direction in which ordinary source does not expose memory engine
selection, lifetime names, retain/release, general `free`, or raw pointers.

Use a small measured combination of static data, unique ownership, lexical or invocation
regions, arenas, and coarse immutable sharing. The implementation may change radically,
but do not add a tracing fallback as an architectural shortcut.

### Daemon-first without daemon-first complexity

A persistent runtime and compiler service can eventually amortize compilation, code caches,
program snapshots, and application resources. That remains a useful product direction.

Do not make the daemon, scheduler, database, or process-cell system a prerequisite for
proving the local semantic model and compiler. Build local deterministic foundations first,
then integrate them into the daemon through narrow interfaces.

## Replace the current limit system

### Required classification

Every remaining bound must be classified as one of only four concepts.

#### 1. Semantic law

A semantic law determines program meaning or safety. Examples include type compatibility,
ownership legality, capability authority, pattern exhaustiveness, valid control flow, and
artifact well-formedness.

A semantic law is never “no more than N declarations” or “no more than N expressions.”

#### 2. Unavoidable representation boundary

A representation boundary follows from a real integer width, OS API, executable format,
address space, or wire protocol. Prefer widening, segmentation, streaming, paging, or a
format redesign before exposing the boundary to ordinary programs.

Document the actual external reason. Do not choose a smaller project number merely for
convenience.

#### 3. Host or request resource policy

An untrusted or multi-tenant host may configure coarse policy such as:

- accepted input bytes;
- available memory;
- output bytes;
- elapsed time or cancellation deadline;
- parallelism;
- open handles or provider resources when the host has a real finite allocation.

Policy is selected by the host or request context. It does not change source validity,
types, ownership, or semantics. The same program can exhaust a low policy and succeed under
a higher or unrestricted trusted-local policy.

Prefer a small explicit policy structure over dozens of semantic counters. A possible
shape, to be adapted rather than copied blindly, is:

```rust
pub struct RequestPolicy {
    pub input_bytes: Option<u64>,
    pub memory_bytes: Option<u64>,
    pub output_bytes: Option<u64>,
    pub deadline: Option<std::time::Instant>,
    pub parallelism: Option<std::num::NonZeroUsize>,
    pub cancellation: CancellationToken,
}
```

Do not use this example to create a new normative schema before the operational needs are
understood. In ordinary trusted local mode, count quotas should normally be absent.

#### 4. Internal tuning or test geometry

Growth factors, initial capacities, cache thresholds, JIT hotness, worker batch size, and
test fixture dimensions are internal. They are not serialized language contracts or
permanent documentation facts.

### Required operational behavior

- Exhaustion is typed and identifies the responsible operation and coarse resource.
- Cancellation and allocation failure leave no partial semantic snapshot, verified IR,
  installed code object, or published output.
- Query and diagnostic views paginate or stream; they do not truncate hidden authority.
- Large input is processed incrementally or in bounded chunks where possible.
- User-controlled depth is handled iteratively or with another demonstrated stack-safe
  design.
- Arithmetic is checked before allocation, indexing, encoding, or multiplication.
- Published maxima are not preallocated.
- Resource policy is not embedded into content identities unless it actually changes the
  generated artifact.
- Optimization must not erase required deterministic semantic effects, but physical
  resource accounting must not become source semantics.

### Disallowed interpretations of “remove the limits”

Do not:

- change 8 to 64;
- change 384 to 65,536;
- change 16,384 to 1,048,576;
- move a parser limit into a profile;
- move a HIR limit into an SSA verifier;
- call the same project-selected count an implementation safety maximum;
- keep a low fixed `trusted-local` ceiling;
- silently stop collecting diagnostics or graph nodes;
- reject a program because a specialization cache is full;
- reject a program because a narrow optimized representation cannot encode it when a
  scalable generic representation is possible;
- preserve the repository width rules as CI errors under a different command.

### Source and package shape

Remove all semantic restrictions on:

- lexical or structural nesting;
- parser marker depth;
- children and arguments;
- tokens per file;
- declarations or top-level forms;
- fields and variants;
- parameters, type variables, bounds, imports, patterns, and match arms;
- files and immediate directory entries;
- source-directory depth and package width.

Repair parsers and validators to use iterative stacks and fallible growth. A source directory
with many entries may be inconvenient, but it is not an invalid program for that reason.

Keep path containment, symlink policy where security requires it, import-cycle detection,
file-type validation, UTF-8 or encoding rules, and deterministic enumeration where those
serve real correctness or security.

### Source foundation bytes and units

Review fixed per-file, source-closure, source-unit, and tree-entry maxima. Replace trusted
local count ceilings with streaming reads, incremental parsing, checked total byte
accounting, host cancellation, and explicit untrusted input policy.

A real address-space or allocator failure may still occur. Do not disguise it as a language
rule.

### HIR and ownership

Remove the 16,384-expression boundary end to end:

- the ownership precheck;
- any HIR accounting reserve coupled to it;
- profile entries for ownership and HIR expressions;
- tests that require rejection;
- docs and error messages;
- downstream assumptions that counts fit a narrow type.

Convert recursive user-controlled expression, type, pattern, and ownership traversals to
explicit worklists. Measure memory growth on large generated programs. Prefer per-function
or incremental analysis state over one dense whole-program state when it improves scale.

Do not replace the expression limit with a fixed ownership-state count. If ownership
analysis has pathological complexity, improve the algorithm, report cancellation or host
resource exhaustion, and create adversarial performance tests.

### Type, trait, pattern, and effect analysis

Inventory fixed type depth, trait work, recursion work, usefulness matrix, pattern count,
hole candidate, legal action, and fixed-point iteration limits.

A malformed cyclic type or nonconverging solver condition is a semantic or algorithmic
failure. A large finite valid type is not invalid merely because it crosses a small count.
Use cycle detection, memoization, canonicalization, work sharing, cancellation, and
incremental queries.

When a search is intentionally incomplete—such as suggestions or optional hole candidates—
return an explicitly paged or best-effort view. Do not confuse an incomplete suggestion
view with incomplete type checking.

### SSA and executable IR

Remove arbitrary fixed counts on:

- blocks per function;
- values, edges, frame states, and instructions;
- ownership retained-state cells;
- CFG and dominator work;
- verification traversal depth;
- proof or optimization edit counts when they reject otherwise valid generic execution.

Replace dense algorithms that scale quadratically or allocate by maximum ID. Use sparse,
chunked, incremental, or algorithmically better representations. If an executable format
uses narrow indexes, widen or section it, or split functions and tables transparently
without changing source validity.

### Specialization and optimization

Any fixed cap on monomorphization, generic witnesses, specialization work, native groups,
proof edits, or code objects must not reject a semantically valid program.

Provide a guaranteed generic representation and execution path. Specialize according to
measured heuristics and cache capacity. On pressure, skip, evict, or defer optimization.
Do not fail compilation solely because an optimization budget was reached.

### Structural values and memory images

Review fixed semantic-node publication quotas, implementation maxima, live domain/root
counts, narrow node IDs, field-cell counts, and release-work limits.

The user specifically wants strange structural ceilings removed. A scalable design may use:

- 64-bit logical IDs;
- segmented arenas;
- chunked flat images;
- multiple linked immutable segments;
- checked sparse tables;
- streaming serialization;
- coarse regions that can grow fallibly.

Select through benchmark and implementation simplicity. Keep generation safety, exact
release, failure atomicity, iterative traversal, and pathologically deep value tests.

Do not raise the current default and maximum node counts and call the work complete.

### Bytecode, native code, and artifacts

Search every field width and table index in bytecode, constant pools, function tables,
metadata, relocations, stack maps, cleanup records, witness tables, and serialized outcomes.

Distinguish actual format addressability from policy. Redesign version-unstable artifacts
freely. Backward decoding is not required. Prefer sectioned or variable-width encoding when
it meaningfully removes global ceilings without harming hot-path decoding.

Keep validation for untrusted or persisted artifacts.

### Runtime operations

Review fixed equality steps, byte storage size, bulk I/O size, stack values, frame depth,
call depth, handles, roots, domains, task counts, provider response sizes, database rows,
stream records, process messages, and daemon request limits.

Use streaming and chunking for bytes and I/O. Runtime cancellation or host fuel can stop a
long operation; the operation must not have a hidden language-semantic cutoff such as “two
otherwise equal lists become an error after a fixed number of nodes.”

A finite external provider may impose a real quota. Report the provider policy explicitly
and keep it separate from language validity.

### Repository, documentation, and agent tooling

Remove hard repository validity based on:

- 200 lines;
- 32 KiB authored files;
- 120-scalar lines;
- 16 directory entries;
- fixed directory depth;
- fixed module or capsule fan-out;
- top-level item counts;
- graph node and edge counts;
- public-fact shard and member counts;
- fixed context graph completion.

Delete tests and CI rules that enforce these counts. Recombine artificially fragmented
files and directories. Keep ordinary formatter, linter, compiler, dependency-cycle,
security, generated-file provenance, and test checks where they still serve real value.

Repository queries should operate directly or incrementally over the checkout and paginate
large views. A complete global graph must not be constructed for every local task.

### Identify genuine boundaries

For every crate or major subsystem, answer:

1. Is this a real trust boundary?
2. Is it independently reusable?
3. Does it target a materially different platform or build environment?
4. Does it provide useful compile-time isolation?
5. Does it own a coherent concept with low coupling?
6. Would merging it delete contracts, digests, re-exports, adapters, or duplicate types?
7. Would splitting it improve hot-path compilation or safety?

Do not set a target crate count. Reduce boundaries until every remaining boundary has a
plain explanation.

### Leading consolidation candidates

These are hypotheses to inspect, not commands to merge blindly:

- fold internal contract registries into the types or protocol that actually own them;
- consolidate `native`, executable-memory mechanism, and JIT adapter layers where their
  split mainly transfers internal plans and metadata;
- consolidate host, residual system wrappers, and Linux host observation behind clear
  platform modules when separate crates do not defend distinct trust boundaries;
- fold general resource scheduling into runtime unless it remains independently useful;
- isolate or defer database support until the core language path needs it;
- reduce `xtask` to transparent build, test, code-generation, and release tasks;
- remove repository graph, public-fact, agent-state, and capsule subsystems rather than
  merging them into a new governance crate;
- merge numbered or mechanically sharded implementation files by semantic responsibility.

Preserve narrow executable-memory and unsafe host boundaries if they provide a real review
and safety benefit. Consolidation does not mean spreading unsafe code.

### Reduce the engine matrix

Perform a focused architectural comparison using representative workloads and maintenance
surface.

Measure at least:

- VM-only generic execution;
- baseline-native execution and compilation cost;
- the current tiered automatic path;
- any retained optimizing path only if its code is still a serious candidate;
- binary size and compile time of each configuration;
- feature implementation surface and duplicate code;
- allocation, memory, and startup;
- behavior on aggregates, bytes, calls, recursion, errors, and host operations, not only a
  scalar loop.

The leading hypothesis is:

```text
validated generic VM or executable interpreter
    + internal baseline native acceleration
    = one production runtime path

small SSA or core-IR evaluator
    = test-only reference where useful

separate proof-oriented optimizing product tier
    = frozen or deleted unless representative value is demonstrated
```

A different result is acceptable if measured evidence and total complexity support it.
The decision must include deletion. Do not keep every candidate “for later.”

### Use one verifier per boundary

Aim for:

- semantic model invariants enforced by constructors and transactions;
- one semantic/type/ownership validation authority;
- one executable-IR verifier;
- one artifact verifier on deserialization;
- one executable-memory installer boundary;
- one process-protocol validator.

Do not independently reconstruct identical facts in HIR, SSA, bytecode, every engine, the
package lock, the docs, and the process codec unless those are genuinely independent
untrusted boundaries.

### Dependencies are allowed

Review mature libraries for incremental computation, parsing, serialization, arenas,
small-vector storage, bitsets, graph algorithms, testing, and code generation where they
can materially simplify the repository.

For each serious dependency candidate, record:

- code and custom mechanism it replaces;
- maintenance and security posture;
- compile-time and binary-size cost;
- runtime benchmark on relevant paths;
- portability;
- exit cost if abandoned.

Do not add a dependency for prestige. Do not reject it to preserve a zero-dependency metric.

## AI-native semantic program model

### Design objective

Build a local, deterministic, typed program substrate that an agent can manipulate through
semantic operations without rewriting text files. It must also produce reviewable
projections for humans and ordinary tools.

Do not begin by designing a network protocol or database schema. Begin with the in-process
model and operations.

### The model is not the current AST

Do not mirror every current parser marker, trivia attachment, span, and textual container in
the permanent schema.

Represent semantic concepts such as:

- package and module;
- declaration and visibility;
- function, parameter, type parameter, and result;
- nominal type, product, enum, variant, and field;
- expression and control flow;
- binding and reference;
- pattern and match;
- type and trait requirement;
- effect and capability requirement;
- ownership and value category where semantically relevant;
- hole, unresolved reference, ambiguity, conflict, and error node;
- documentation attachment and projection metadata as separate concerns.

The schema should be extensible without accepting unknown untyped objects in core semantic
positions. Use typed variants and explicit migration while the project is unstable; no
compatibility promise is required.

### Stable logical identity

Use stable IDs for mutable entities and nodes. Consider generation-bearing arena IDs,
random or monotonic workspace IDs, or another compact design. Requirements:

- rename does not change identity;
- moving an entity does not change identity;
- formatting does not change identity;
- a small edit does not cascade through unrelated IDs;
- stale references are detected;
- snapshots can compare identity and semantic content separately;
- serialized snapshots can validate uniqueness and references.

Use content hashes for immutable snapshot identity, immutable definition identity where it
is useful, compiled artifacts, cache entries, and transfer integrity. Names remain separate
metadata. Do not make every editable node's identity equal to its content hash.

### Partial and erroneous programs

An agent must be able to construct a program incrementally. The model should support:

- typed holes with expected type and contextual facts when known;
- untyped holes when not enough context exists;
- unresolved and ambiguous references with candidate information;
- missing fields or branches;
- parse-import error nodes that preserve recoverable structure;
- merge conflicts as explicit nodes;
- declarations whose bodies are incomplete;
- diagnostics attached to stable semantic entities.

Transactions may commit an incomplete workspace snapshot. Release compilation requires the
necessary completeness and semantic checks.

### Transaction model

Define an in-process transaction API with operations such as:

```text
create_entity
remove_entity
move_entity
rename_entity
insert_node
replace_node
set_field
set_reference
rewire_call
introduce_hole
refine_hole
fill_hole
resolve_conflict
apply_refactoring
```

Every transaction must:

- name a base revision or equivalent precondition;
- validate IDs and operation shape before publication;
- apply atomically;
- return a new revision;
- return a semantic diff;
- return diagnostics and invalidated query families;
- preserve the prior snapshot on failure;
- support cancellation before publication;
- avoid serializing and reparsing the entire program for an ordinary local edit.

Do not make textual patch application the foundational transaction.

### Semantic diff

A semantic diff should report entities and relationships changed, not only lines changed.
It should support review of:

- declaration creation, deletion, and movement;
- binding rename;
- type or signature change;
- reference rewiring;
- control-flow replacement;
- effect or capability change;
- hole introduction or resolution;
- inferred impact on callers and dependents.

Text diffs remain useful projections but are not sufficient for agent correctness.

### Query model

Provide deterministic queries for:

- entity by stable ID;
- declaration by qualified name;
- definition and references;
- callers and callees;
- type and expected type;
- effects and capabilities;
- ownership or move state where relevant;
- diagnostics;
- hole context and legal actions;
- dependency and impact slices;
- small semantically selected context bundles;
- compilation and cache status.

Results must identify the snapshot revision. Large results must paginate or return a stable
continuation. Local queries must not require construction of a complete repository graph.

### Compiler integration

The first model vertical is not complete until a program can compile from the semantic
model without rendering and reparsing text.

A practical first slice can cover a small but real subset:

- one module;
- main and ordinary functions;
- primitive types and literals;
- calls, local bindings, conditionals, and one incomplete-expression hole;
- stable IDs;
- a rename and a replace/fill transaction;
- type and reference queries;
- direct lowering to the existing typed core or a simplified replacement;
- deterministic text import and text rendering for review.

Choose the exact subset after inspecting current seams. It must exercise identity,
transactions, partial state, query invalidation, and direct compilation together. Do not
build a broad schema with no executable vertical.

### Text projection

Treat the current `.lkjscript` syntax as a bootstrap adapter:

```text
current text -> importer -> semantic transaction/snapshot
semantic snapshot -> renderer -> review/debug text
```

Round-trip preservation of comments and formatting is optional during the unstable reset.
Preserve semantic meaning. A future concise textual projection may replace the current one
without changing semantic identity.

Do not make exact current trivia bytes part of the permanent semantic snapshot unless a
separate document projection explicitly owns them.

### Persistence

Start with:

- an in-memory store;
- immutable snapshots or copy-on-write revisions;
- deterministic snapshot serialization for tests and interchange;
- a small transaction journal only if needed for crash recovery experiments.

Measure snapshot creation, edit latency, retained memory, and invalidation breadth.

Adopt an embedded database only when it improves measured scale, persistence, concurrent
readers, or crash recovery. Do not build distributed consensus, a remote codebase service,
or a custom database before the local model is strong.

### Incremental computation

The model should drive memoized queries with explicit dependencies. Evaluate:

- a mature incremental query framework;
- a compact custom dependency graph;
- hybrid per-module and per-function caches.

Select using:

- invalidation precision;
- deterministic behavior;
- cycle handling;
- cancellation;
- parallel-read behavior;
- memory retention;
- serialization needs;
- compile-time cost;
- implementation and debugging complexity;
- measured full and incremental latency.

Do not prematurely create dozens of query kinds or cache identities. Begin with name
resolution, typing, and direct lowering for the first vertical.

### Agent protocol comes after the in-process semantics

Once the in-process model is sound, expose it through a local protocol suitable for agents.
The transport may be stdio, a local socket, or an existing agent-tool protocol. The
transport must not define semantics.

Avoid JSON in hot internal storage merely because it is convenient at a boundary. Use typed
Rust structures internally and a bounded, versioned, debuggable boundary encoding.

### Agent evaluation

Build repeatable tasks for both strong and weaker agents. Measure:

- successful semantic edits;
- invalid operation rate;
- number of repair cycles;
- tokens and bytes transferred;
- tool calls;
- time to first valid change;
- context retrieved;
- stale-revision conflicts;
- incremental compiler latency;
- semantic regressions;
- human review clarity.

Compare direct semantic operations with text patching on the same tasks. Use results to
shape query granularity and transaction ergonomics.

### External systems to study, not copy

Inspect these primary references for ideas. Do not adopt their full architecture or add
them as runtime dependencies merely because they are listed here.

- Hazel: typed holes and meaningful incomplete programs — <https://hazel.org/>
- JetBrains MPS Projectional Agent Toolkit: agents operating on live structured models
  instead of serialization files —
  <https://www.jetbrains.com/help/mps/mps-projectional-agent-toolkit.html>
- Unison: a codebase stored and queried by semantic identity, with content-addressed
  immutable definitions and names as separate metadata —
  <https://www.unison-lang.org/docs/the-big-idea/>
- Salsa: query-based incremental computation and dependency-driven invalidation —
  <https://salsa-rs.github.io/salsa/overview.html>

Extract principles, test them in a small vertical, and keep only what improves lkjscript.

## Memory-system simplification

The collector-free direction should survive the reset, but its current implementation
complexity is not sacred.

### Preserve these outcomes

- memory-safe ordinary programs;
- no source-level retain/release or manual free;
- no tracing fallback hidden behind unsupported paths;
- exact cleanup for affine resources and unique storage;
- failure-atomic publication and transfer;
- generation-safe resource handles;
- iterative release for deep structures;
- no per-node reference counting by default;
- portable boundary values without leaking process-local keys;
- clear ownership across process and daemon boundaries.

### Reconsider these mechanisms

Audit and reduce:

- repeated memory witness identities at every IR layer;
- independently reconstructed placement facts inside one trusted pipeline;
- separate representation routes for many narrow value families;
- physical copies inserted to satisfy tier-specific ABIs;
- cleanup plans duplicated in evaluator, bytecode, VM, and native metadata;
- per-engine owner tables;
- package and prepared-program digests used only to prove in-process consistency;
- sealed-value special cases that do not serve representative applications;
- memory policy coupled to Brainfuck completion.

### Target shape

Prefer one compiler-owned memory and ownership plan attached to canonical typed IR, verified
once before executable lowering. Each production backend consumes the same plan through one
well-defined ABI.

Use a small number of runtime storage classes. Candidate classes include:

- immediate or static values;
- unique values;
- region or arena values;
- coarse immutable shared values;
- host resources.

Do not predeclare a large closed matrix. Add a storage class only when it has distinct
semantics and measured value.

Representation selection may be optimized, but a generic representation must exist for
ordinary valid values. Failure to select a specialized sealed or flat representation must
not reject the program.

### Measure memory behavior

Use application-shaped cases with:

- nested and wide products and enums;
- large and small lists;
- strings, paths, bytes, and buffers;
- repeated calls and returns;
- recursive and iterative algorithms;
- error and early-exit cleanup;
- process transfer and rehydration;
- warm daemon retention;
- mixed long- and short-lived values.

Measure peak RSS, retained bytes, allocations, copies, metadata bytes, cleanup latency, and
cache locality. Do not choose architecture from a single synthetic structural tree.

## Performance program

### Establish a reset baseline

Before broad deletion, record a compact baseline under `target/reset-baseline/` for the
actual `HEAD`:

- debug and release build wall time;
- release binary sizes;
- workspace test wall time;
- compiler cold and warm timing for representative examples;
- runtime timing for scalar, aggregate, byte, recursive, error, and host cases;
- peak RSS where practical;
- existing native compilation and execution metrics;
- current source and documentation file counts;
- current agent operation latency if the Semantic Source service works.

Do not block architectural work on an extremely long inherited benchmark. Use a compact
reproducible baseline and retain raw output outside the authored tree.

### Replace the benchmark portfolio

Build a small representative suite containing:

1. A generated program just beyond each former source and IR boundary.
2. A much larger scale program that exercises iterative traversal and fallible growth.
3. Many declarations, imports, fields, variants, parameters, and match arms.
4. Deep types and nested expressions without stack recursion.
5. Name, type, effect, ownership, and pattern-analysis stress.
6. A numeric loop and call-heavy kernel.
7. Aggregate construction, traversal, equality, and cleanup.
8. Byte-buffer and streaming I/O work.
9. Error, cancellation, and early-exit cleanup.
10. Full compilation followed by one-node incremental edits.
11. Warm daemon or compiler-session reuse.
12. Multiple applications or modules sharing immutable compiled state where appropriate.
13. One service-like workload using capabilities and host providers.

Brainfuck must not be required for correctness or performance acceptance. Delete its
benchmark infrastructure if it consumes meaningful maintenance effort.

### Metrics

Record where relevant:

- cold and warm compilation wall time;
- phase time;
- incremental p50, p95, and p99 latency;
- peak and retained RSS;
- allocation count and bytes;
- bytes copied and serialized;
- generated code and metadata size;
- startup and time to first useful execution;
- runtime throughput and tail latency;
- cache entries, hit rate, and invalidation breadth;
- native compile and install cost;
- break-even call count;
- agent tokens, tool calls, invalid operations, and repair cycles.

### Protocol discipline

- Verify exact outcomes before timing.
- Compare same-commit alternatives.
- Record the host and toolchain.
- Use warmups and enough samples for noisy measurements.
- Retain every measured sample in CI artifacts or `target/`.
- Do not tune thresholds after observing a result.
- Keep unfavorable size and memory results visible.
- Profile before changing data layout or unsafe code.
- Revisit old sentinels when the workload or architecture is no longer semantically
  comparable; do not preserve an obsolete benchmark forever.

### Performance gates

A gate must protect a demonstrated product property. It must not require retaining a
specific engine, witness system, file topology, or toy workload.

During early reset phases, prefer reporting regressions and decisions over hard gates that
make deletion impossible. Reintroduce narrow hard gates after the architecture stabilizes
and the metric is representative.

## Security and correctness boundaries to preserve

Decomplexification must not weaken real boundaries. Preserve or improve:

- path containment and symlink safety;
- explicit capabilities and provider grants;
- generation-safe handles;
- checked arithmetic and fallible allocation;
- validation of untrusted serialized IR, snapshots, and process messages;
- W^X executable-memory installation;
- relocation and code-object validation;
- safe wrappers around unsafe FFI and native entry;
- deterministic cleanup of owned host resources;
- transaction and artifact failure atomicity;
- stale revision and stale generation rejection;
- clear process and tenant isolation;
- no silent native fallback when a diagnostic mode promises generated execution.

The product runtime may use a generic fallback by design. The fallback must be explicit in
metrics and semantics, not hidden behind a claim that a specialized tier executed.

## Acceptance criteria for the reset program

The long-term reset is successful when all of the following are true.

### Language and scale

- No arbitrary count determines semantic validity.
- The former nesting, token, child, top-level, field, directory, HIR, and SSA boundaries are
  absent from implementation, tests, profiles, and docs.
- User-controlled deep traversals are stack-safe.
- Large programs fail only for semantic errors, cancellation, real host exhaustion, or real
  representation boundaries.
- Large views paginate or stream rather than truncating authority.

### Architecture

- One semantic program authority exists.
- The compiler consumes it directly.
- Text is an adapter and projection.
- One coherent production runtime path handles ordinary valid programs.
- Experimental optimization does not multiply every feature implementation.
- Crates and verifiers correspond to real boundaries.
- Internal fact and witness duplication is materially reduced.
- No compatibility architecture remains.

### AI-native editing

- Stable identity survives rename, movement, and formatting.
- Partial programs and holes are first-class workspace states.
- Atomic semantic transactions produce semantic diffs and diagnostics.
- Queries are revisioned, deterministic, and pageable.
- An agent can edit and compile without text patching.
- Strong and weaker agent tasks show measurable improvement over text-only editing.

### Documentation

- Active documentation is small enough to inspect directly.
- Code, tests, schemas, Cargo metadata, and examples own exhaustive facts.
- No public-fact shards, digest markers, platform revision synchronization, capsule
  manifests, or status closure remain.
- Current, architecture, language, source-model, and roadmap documents agree with the
  checkout.
- Examples execute in CI.
- Historical material lives primarily in Git history.

### Performance

- Representative full and incremental compile measurements exist.
- Runtime measurements include scalar, aggregate, byte, allocation, cleanup, and host work.
- Memory and code size are visible.
- Native acceleration earns its complexity on representative cases.
- Optimization and specialization fall back to generic execution rather than rejecting
  valid programs.
- Warm daemon reuse is measured before it becomes a default complexity source.

### Correctness and security

- Typed semantic, artifact, process, capability, path, and executable-memory boundaries
  remain fail closed.
- Resource exhaustion and cancellation are failure-atomic.
- Unsafe code remains narrow and tested.
- Memory cleanup and process transfer remain correct without source-level memory mechanics.
- No silent fallback, truncation, or partial authority publication is introduced.

## How to make decisions when evidence is incomplete

Use the following hierarchy:

1. Preserve semantics and real security boundaries.
2. Remove self-imposed compatibility and governance constraints.
3. Prefer the architecture with fewer independent mechanisms.
4. Prefer a universal generic path over a matrix of special cases.
5. Prefer an iterative or incremental algorithm over a small fixed maximum.
6. Prefer measured application behavior over toy benchmark behavior.
7. Prefer mature infrastructure over custom infrastructure when it deletes substantial
   code and does not harm the critical path.
