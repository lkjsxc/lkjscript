## Why this is the next problem

The semantic workspace has reached a real editing boundary rather than a missing constructor.

At the observed checkout:

- `SemanticProgram` stores compiler-HIR-shaped dense vectors such as `Vec<Binding>`.
- HIR `BindingId` is the binding-vector index.
- public workspace identity is reconciled through private addresses such as `EntityAddress::Binding(raw)` and vector-index-based product, enum, variant, and field addresses;
- `identity::reconcile` preserves identity primarily by private address and can force newly reserved identities, but it is not yet a general survivor-relocation mechanism;
- published lexical locals and match payload bindings therefore remain coupled to program-wide dense binding storage;
- `ReplaceExpression` and `IntroduceHole` explicitly reject a subtree for which `subtree_defines_local` is true;
- whole structural edits that would remove published local or pattern-binding entities reject rather than compact and remap the underlying dense program;
- the roadmap correctly identifies declaration deletion, movement/identity survival, and local-binding removal/compaction as the current blocker.

Adding more expression or pattern constructors before fixing this lifecycle would deepen the coupling and multiply later migration work. The next turn must remove the root obstruction.

## Design decision gate

Prefer the smallest architecture that makes the lifecycle correct.

The likely economical design is a private, iterative, linear-time remap/compaction step over the staged `SemanticProgram`, combined with explicit survivor relocation during workspace identity reconciliation. That design is preferable when it can:

- remove deleted bindings rather than retain dead semantic objects forever;
- rewrite every dense private reference exactly once;
- recompute or rewrite local places and counts coherently;
- preserve public stable identities independently of new private addresses; and
- leave one mutable semantic authority and one derived complete HIR path.

Do not blindly implement that suggestion. Prove it against the actual affected identity domains.

Introduce a distinct edit-stable private semantic key layer only when a local remap cannot remain smaller and more coherent. If such a cutover is necessary:

- make it the sole mutable semantic authority;
- derive compiler-dense HIR in one direction;
- delete the displaced HIR-shaped mutable authority in the same change;
- do not keep old and new semantic programs in parity;
- do not add a universal graph, registry, descriptor hierarchy, or general transformation framework; and
- do not expose compiler-dense IDs publicly.

Do not solve the problem by:

- retaining unbounded dead bindings or declarations in executable semantic state;
- making public IDs equal vector positions;
- preserving identity by name, path, source span, source hash, or incidental order;
- treating fingerprint coincidence as sufficient proof that a moved semantic object is the same object;
- serializing, rendering, hashing, or reparsing the program;
- adding a database, journal, daemon, wire protocol, CRDT, persistence layer, cache framework, or collaboration model;
- adding arbitrary limits;
- weakening ownership, type, effect, match, or consistency validation; or
- adding compatibility adapters around the old restriction.

## Required semantics

### 1. Callable deletion

Add one typed semantic edit operation for deleting an entity. `DeleteEntity { entity }` is a reasonable shape, but choose the cleanest public API for the current workspace.

For this turn, deletion must support:

- `main`; and
- ordinary non-builtin functions, including imported and source-free functions.

Deletion of `main` must:

- remove the entry entity and its body, nodes, holes, parameters if any, locals, and hidden compiler-owned descendants;
- tombstone all removed public IDs;
- produce a valid incomplete snapshot with the canonical `MissingEntryPoint` blocker and diagnostic;
- preserve all unrelated identities;
- allow a later `CreateMain` to allocate according to normal tombstone/generation rules; and
- never retain a hidden executable entry point.

Deletion of a function must:

- remove the function declaration, contained parameters, local and payload-binding entities, body nodes, holes, and function-layout participation;
- reject when a surviving staged declaration, call, type fact, match plan, or other semantic dependency still requires it;
- succeed in one transaction when every dependency is removed or rewired by other edits in that same transaction;
- preserve all unaffected public IDs even when binding and function vectors compact;
- leave deterministic dependency, call, reference, query, projection, and diagnostic results; and
- compile and execute when the staged final snapshot is complete.

Direct deletion of a parameter, local, payload binding, field, variant, or other contained member should reject unless the repository already has a coherent operation that owns the containing semantic rewrite. Do not expose an operation that can manufacture an orphan.

Deletion of builtin operations or fixed compiler context must reject explicitly.

### 2. Removal of local-defining subtrees

Remove the current product limitation, not merely its error message.

After this change:

- `ReplaceExpression` may replace a `let`, mutable-local, match, or other subtree that defines published local entities when the final expression is valid;
- `IntroduceHole` may replace such a subtree with one real typed hole;
- replacing or holing a semantic match may remove payload bindings and match-owned nodes cleanly;
- all entities and nodes owned only by the removed subtree become stale and tombstoned;
- semantically surviving ancestors, sibling subtrees, declarations, and unrelated nodes retain identity;
- a retained target root keeps identity where the operation contract already promises root preservation;
- no removed expression remains hidden behind a hole;
- no dead binding remains visible through queries or projection; and
- complete staged snapshots still pass canonical type, match, ownership, memory, and consistency validation before publication.

Imported mutable locals and other existing HIR forms must not be silently corrupted. Either support their removal through the same lifecycle or reject only the unsupported operation with a precise reason before publication. Do not regress source-free or imported behavior.

### 3. Stable identity across private compaction

Public identity must describe semantic continuity, not dense storage continuity.

Deleting an earlier function or local must not renumber surviving public identities. Test at least:

- a later function whose dense binding index changes;
- its parameters;
- an unaffected lexical local;
- callers, callees, references, and dependencies targeting it;
- an unaffected node whose private preorder or root address changes only because surrounding storage compacted; and
- hole identity where the hole itself survives.

A deleted ID must fail as stale in the new snapshot. If its slot is later reused, the generation must differ. An old snapshot must remain fully queryable and internally consistent.

Extend identity reconciliation deliberately. A forced survivor relocation must be explicit, one-to-one, namespace-correct, generation-correct, and checked for duplication, omission, wrong kind, and collision. Do not rely on an old private address accidentally remaining available.

### 4. Batch semantics

A transaction describes one atomic final state.

A dependency-closed batch such as “replace the only call to `f`, then delete `f`” must not require two published revisions merely because the current implementation loops over edits in input order. Validate the staged final state whenever that is the truthful semantic rule.

Define deterministic behavior for conflicts including:

- deleting an entity twice;
- renaming and deleting the same entity;
- editing a node contained by a declaration deleted in the same transaction;
- deleting a callee while retaining a call;
- overlapping structural edits;
- stale, foreign, or wrong-kind identities;
- deleting then attempting to refer to the deleted entity from a newly lowered draft; and
- deleting a declaration that owns an active hole.

Reject contradictory batches before publication with a precise error. Do not make semantics depend accidentally on vector iteration or hash-map order.

### 5. Failure atomicity

Every failed transaction must preserve:

- the exact published `Arc<WorkspaceSnapshot>`;
- revision;
- namespace;
- allocator generations, live bits, tombstones, and free lists;
- deterministic future IDs;
- program state;
- holes and blockers;
- diagnostics;
- query and projection output; and
- source/provenance attachments according to current policy.

Do not reserve, tombstone, or consume a stable ID in the live workspace before all fallible staging and validation succeeds.

Where the test infrastructure can inject allocation failure, cover the new staging/remap boundaries. Otherwise make fallible allocation explicit and cover representative failure paths.

### 6. Semantic diff, invalidation, queries, and projection

Extend `SemanticDiffEntry` only with entries that represent real semantic change. Expected additions include an entity-deleted entry and, only if an explicit move operation is implemented, a movement entry. Keep ordering deterministic.

A successful deletion diff must make it possible to identify:

- the deleted declaration;
- deleted contained entities and nodes where the existing diff model reports descendants;
- holes removed by deletion;
- reference and call rewiring caused by the batch; and
- the new revision.

Do not emit duplicate or contradictory deletion records.

Queries and projections must immediately exclude deleted objects and show the correct blocker/diagnostic state. Continuations from the previous revision must remain stale by the existing revision rules. Pagination and deterministic ordering must remain valid after compaction.

Dependency checks must use semantic dependencies, not only names or textual occurrence. If a structured dependency explanation can be added without creating a new error framework, include the blocking dependent identities in the rejection.

### 7. Direct compiler and runtime behavior

A complete edited snapshot must still follow:

```text
semantic snapshot
    -> completeness and consistency gate
    -> one source-optional complete HIR
    -> ownership and memory planning
    -> SSA and bytecode
    -> baseline-native attempt or generic VM
```

No source rendering, source loading, parsing, or source-hash reconstruction may be introduced into semantic deletion or compaction.

Preserve:

- exact ownership and borrow laws;
- match usefulness/exhaustiveness and payload binding semantics;
- cleanup on normal, trap, error, cancellation, and early-exit paths;
- exactly-once effects and no VM retry after native entry;
- the complete generic VM route;
- source-free semantic origins without dummy `SourceId`;
- imported origin/provenance truth;
- checked conversions; and
- stack-safe traversal for user-controlled depth.

### 8. Movement scope

Do not invent a public movement operation merely to satisfy a roadmap noun.

For this turn, movement necessarily includes semantic identity surviving private relocation caused by deletion and compaction. That is mandatory.

Implement an explicit public entity or node move only if the current semantic model has a clear present use case and a small operation with unambiguous ownership, scope, type, effect, identity, and failure semantics. Source order and file placement are not automatically semantic. A generic coordinate system, tree editor, path language, or insertion framework is out of scope.

If explicit move remains deferred, update `docs/roadmap.md` to distinguish:

- completed identity-preserving private relocation and callable/local removal; from
- the next concrete, user-visible movement vertical.

Do not claim public movement support when only private compaction exists.

## Performance and complexity requirements

- no “for every binding, rescan the whole program” pattern;
- no recursion on user-controlled expression or pattern depth;
- no repeated serialization, hashing, rendering, parsing, or reconstruction;
- no retained dead semantic data proportional to edit history; and
- checked arithmetic and checked host-index conversion.
