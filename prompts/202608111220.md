## Observed current architecture to verify

At prompt-authoring time, the measured transaction path appeared to be concentrated in
`crates/lkjscript-compiler/src/workspace/transaction.rs`. Verify the current code rather
than assuming this map remains exact.

- `Workspace::apply` checks the base revision, clones allocator state, stages a
  transaction, allocates a diagnostics copy, and publishes the new snapshot and
  allocator only after success.
- `stage` clones the semantic program, preflights deletions and structural edits, lowers
  drafts, applies replacements, refreshes match facts when needed, validates surviving
  deletion dependencies, compacts private dense structures, infers effects, validates
  complete programs, rebuilds semantic indexes, reconciles stable identities, refreshes
  holes, builds diffs, and publishes a snapshot.
- `try_clone_program` currently performs an explicit fallible clone of program vectors,
  functions, main, and expression trees.
- `compaction::compact` is invoked from the transaction path and may own more than
  explicit deletion behavior because local-defining subtree replacement can remove
  bindings and plans.
- `effects::infer_partial` currently receives the complete set of functions and optional
  main body.
- A complete staged program derives complete HIR and runs ownership, match-plan, and
  semantic validation before publication.
- `index::build` rebuilds canonical snapshot indexes.
- `identity::reconcile` preserves stable public identities across private relocation.
- Semantic and call-instantiation diff construction may perform additional
  whole-snapshot work.
- Queries and projection consume immutable snapshot indexes and semantic state.
- `compile_snapshot` is the sole complete-snapshot compiler boundary.

This list is an audit hypothesis, not an instruction to optimize every named step.
Instrument and measure before deciding which, if any, step is problematic.

## Decision gates

### Gate 1 — is the measurement trustworthy?

- Workload semantics are exact and verified.
- Setup is separated from the measured operation.
- Sample state is equivalent across repetitions.
- Machine output decodes successfully.
- Failures are not hidden.
- Instrumentation overhead is understood.
- Noise is small enough to distinguish material differences.
- Scale geometry is recorded.

### Gate 2 — is full recomputation actually a problem?

- Look for superlinear growth inconsistent with intended traversal shape.
- Look for a medium-workload latency that materially impairs the measured authoring
  loop.
- Look for one phase that dominates end-to-end cost across relevant scale points.
- Look for repeated traversal or copying that has no correctness or boundary purpose.
- Distinguish unavoidable whole-program validation from accidental duplicate work.
- Distinguish synthetic stress cost from representative local-edit cost.
- Do not infer a problem merely because a pass touches the whole program.

### Gate 3 — is a local correction sufficient?

- Prefer skipping work that is provably unnecessary for a transaction shape.
- Prefer reusing a derived fact already computed in the same staging operation.
- Prefer one local index over repeated scans inside a pass.
- Prefer sharing immutable data only when ownership and failure atomicity remain
  obvious.
- Prefer changing traversal order or data layout over adding cache invalidation.
- Prefer deleting duplicate validation at a trusted internal boundary only when one
  canonical validator remains.
- Do not implement incremental dependency graphs until local corrections are exhausted
  and measured need remains.

### Gate 4 — is the correction worth retaining?

- Require a material end-to-end improvement in the representative medium workload, not
  only a micro-phase.
- Use a predeclared noise-aware threshold. A reasonable default is at least ten percent
  end to end or twenty percent in a clearly dominant phase, but adjust before comparison
  when pilot noise or workload meaning requires it.
- Require no material regression in tiny, ownership, nominal/match, generic, lifecycle,
  or large workloads.
- Require code and test complexity proportional to the saved work.
- Require a focused structural or regression test preventing recurrence.
- Require updated compact evidence and a clear reversal condition.

## Candidate investigation order

Investigate in this order only when measurements point to the area. Do not implement
every item.

- Unnecessary repeated full-program discovery inside one transaction.
- Unconditional work whose semantic preconditions show it cannot affect the transaction
  shape.
- A scan repeated once per node, binding, deletion, reference, or query instead of once
  per root or snapshot.
- Duplicate construction of the same local map or canonical fact inside one staging
  operation.
- Deep cloning of data that can safely remain immutable and shared without creating
  stale authority.
- Compaction work on transaction shapes that provably cannot remove or relocate owned
  semantic facts.
- Whole-program match refresh when no match plan or affected root requires it.
- Whole-program effect inference when an existing sound boundary can cheaply identify
  unaffected roots, but only if the local mechanism remains simpler than full
  recomputation.
- Repeated complete-HIR derivation or validation inside one operation.
- Index construction work duplicated by identity reconciliation or diff production.
- Semantic diff scans that rediscover facts already available from old and new indexes.
- Projection traversal that emits facts not requested by the selected slice.
- Compiler work repeated between transaction publication and immediate check without a
  current authoritative reuse boundary.

## Special caution: semantic-program cloning

The explicit fallible semantic-program clone is an obvious potential cost, but it also
makes failure atomicity and immutable old snapshots straightforward. Do not replace it
with a broad persistent data structure merely because cloning appears inelegant.

- Measure cloned nodes and clone time.
- Compare clone cost with validation, indexing, reconciliation, diff, and compile cost.
- Determine whether clone cost is material at the representative medium scale.
- Consider narrow immutable sharing only for data untouched by the selected transaction
  and only when mutation ownership remains simple.
- Do not introduce copy-on-write layers throughout the semantic model without a measured
  threshold and a complete failure-atomic design.
- Do not trade predictable linear cloning for hidden reference-count churn, fragmented
  allocation, or complex invalidation without equivalent evidence.
- If cloning is acceptable, document that decision and stop investigating it.

## Special caution: compaction

- Understand all current reasons compaction runs, including removed local-defining
  subtrees and match plans, not only explicit declaration deletion.
- Do not add a fast path that leaves dead bindings, stale plans, wrong places, wrong
  slots, or unstable survivor identity.
- Measure common non-deletion edits separately from lifecycle edits.
- A no-op compaction fast path is acceptable only when its precondition is complete and
  mechanically enforced.
- Do not retain sparse dead history merely to avoid one measured pass.
- Do not add a general rewrite engine for current dense remapping.

## Special caution: validation

- Do not remove canonical ownership, match, type, effect, or consistency validation
  merely because it is expensive.
- Determine whether validation is duplicated within the same trusted staged pipeline.
- Keep fail-closed validation at real untrusted boundaries.
- Use typed wrappers and Rust ownership to avoid redundant reconstruction only when the
  producer-consumer trust boundary is explicit.
- If a partial validation path is considered, prove that it is equivalent for every
  affected semantic dependency and simpler than full validation.
- Do not create an unsound incremental validator in this turn.

## Special caution: indexes and identity reconciliation

- Indexes are derived, not semantic authority.
- Stable public identity must survive private dense relocation exactly where meaning
  survives.
- Do not expose dense addresses to avoid reconciliation.
- Do not use content fingerprints to infer semantic continuity.
- Measure index build and reconciliation separately before combining or changing them.
- Reuse a map within one pass when the same relation is currently rediscovered.
- Do not cache indexes across revisions without a measured invalidation design.
- Verify stale, foreign, wrong-kind, duplicate, missing, and colliding relocation
  failures remain atomic.

## Special caution: invalidation reporting

The current transaction outcome reportedly returns coarse invalidated domains. This task
measures actual recomputation; it does not require pretending the system is incremental.

- Do not refine invalidation merely to make output look sophisticated.
- Report current coarse invalidation truthfully.
- A measured work summary may distinguish phases without changing public invalidation
  semantics.
- Do not add dependency tracking unless a present consumer needs finer invalidation and
  measurements justify it.

## Special caution: post-edit compilation

- Measure transaction and compilation separately and together.
- Do not attribute compiler cost to workspace recomputation.
- Do not cache `ExecutableProgram` across revisions without a current reuse boundary and
  invalidation proof.
- Do not render or parse source between snapshot and compiler.
- Confirm incomplete revisions stop before downstream compiler phases.
- If compile dominates the agent loop, record that fact; do not force a workspace

## Special caution: query cost

- Do not add memoization for an O(1) or short indexed query.

- Do not return enormous result sets merely because the harness can count them.

- What is the median and tail latency of edit plus compact inspection plus compile?
- How does the same edit scale as unrelated declarations and nodes increase?
- How much of transaction time is fixed overhead?
- How much is proportional to total program size?
- How much is proportional to edited subtree size?
- How much differs between common replacement and lifecycle deletion?
- Does a hole-only edit avoid downstream compile phases as intended?
- Are direct queries negligible relative to staging?
- Is selected projection output small enough for an agent review loop?
- Which phase dominates at medium scale?
- Does the dominant phase remain dominant at large scale?
- Is any phase unexpectedly repeated per entity, node, binding, deletion, or edge?
- Does the fallible program clone dominate allocations or latency?
- Does compaction do material work for a simple edit?
- Does effect inference revisit unrelated roots in a way that matters?
- Does complete-HIR derivation duplicate work already required by immediate compilation?
- Do ownership and match validations dominate, and are they canonical rather than
  duplicated?
- Does index construction perform one pass over expected facts?
- Does identity reconciliation perform work proportional to survivors?
- Does diff construction materially duplicate index or reconciliation work?
- Does diagnostic copying matter at representative diagnostic counts?
- Does retained old-snapshot ownership materially increase memory?
- Are allocation and memory results reliable enough to report?
- Are measurement-command stdout and stderr compact and deterministic?
- Would a local correction remove measured work without an invalidation system?
- Would full recomputation remain easier to reason about than the expected gain from
  incrementality?
- What exact observation would justify revisiting incrementality later?

## Candidate-correction acceptance checklist

- The baseline identifies one material root cause.
- The correction does not require a general cache or incremental dependency graph.
- The correction has one clear owner and lifetime.
- The correction cannot return stale semantic facts.
- The correction preserves one atomic publication boundary.
- The correction preserves old immutable snapshots.
- The correction preserves stable identity and tombstones.
- The correction preserves deletion and replacement semantics.
- The correction preserves complete and incomplete validation boundaries.
- The correction preserves source-free zero-load and zero-parse behavior.
- The correction remains stack safe.
- The correction has checked allocation and index conversions.
- The correction has a focused deterministic regression test.
- Equivalent end-to-end measurements meet the declared materiality threshold.
- No representative workload materially regresses.
- The added code and tests are smaller than the eliminated problem.
- The displaced path is deleted.
- The documentation states the retained architecture truthfully.

## Full-recomputation retention checklist

- Representative medium edit latency is recorded.
- Combined edit-inspect-check latency is recorded.
- Scaling shape is recorded.
- Common replacement and lifecycle deletion are distinguished.
- No hidden superlinear work is observed.
- No repeated scan materially dominates.
- Queries are acceptably indexed.
- Projection output is acceptably compact.
- Memory or allocation limitations are stated honestly.
- A future reconsideration trigger is explicit.
- No placeholder incremental hooks are added.
- The roadmap advances only after the evidence is committed.

## Final handoff checklist

- The prompt file itself is not committed.
- Raw samples are outside Git.
- The harness and exact command are retained.
- The compact result is in the owning performance document.
- Current status matches code.
- Architecture matches retained flow.
- Roadmap `Now` is complete.
- The next item is named but untouched.
- All required tests and builds are reported exactly.
- A local commit exists when permitted.
- No remote publication occurred without instruction.
- The final report is concise enough for the next agent to orient without reading raw
  logs.

## Closing directive

Begin with repository evidence, not with a preferred architecture. Make full
recomputation earn retention through representative measurements, and make every
proposed optimization earn its complexity through equivalent end-to-end results.
Complete one coherent vertical, leave one active architecture, update the owning facts,
and stop before the next roadmap problem.
