## Governing principles

### One product path

`check` must reuse the same required-package validation and production compiler path as `run`.

It must not be a weaker parser-only check.
It must not be a separate validator.
It must not compile a different source closure.
It must not use a test-only evaluator.

It must not use a special reduced type system.
It must not use a different ownership checker.
It must not use different package capability rules.
It must not use different bytecode validation.
A program accepted by `check` should be accepted by the compile portion of `run` under equivalent checkout state, target, package, lock, and options.

A program rejected by the compile portion of `run` should not be silently accepted by `check`.
Factor a shared compile entry only if that removes real duplication.
Do not wrap one public convenience around another if doing so repeats package verification or source import.

### No program effects

`check` must not:
- construct a host execution environment;
- invoke the VM;
- invoke native code;
- install executable memory;
- enter a generated ABI;
- perform program-declared stdio;
- perform program-declared filesystem operations;
- perform program-declared network operations;
- perform program-declared terminal operations;
- perform program-declared entropy operations;
- perform program-declared clock operations;
- perform program-declared SQLite operations;
- invoke cleanup associated with entered program execution; or
- otherwise evaluate the user program.

Package and source loading needed to compile are compiler host I/O.
They are not program effects.
Keep that distinction explicit in tests and documentation.

### Quiet success

The default human `check` success path must emit zero bytes to stdout.
The default human `check` success path must emit zero bytes to stderr.
Exit status is the success signal.

Do not print:
- `ok`;
- `checked`;
- a path;
- a duration;
- a phase list;
- a package name;
- a compiler version;
- a native eligibility result;
- a warning that nothing ran;
- progress bars; or
- decorative output.
A requested verbose or machine-readable mode may produce bounded output.
Do not add a verbose mode unless it answers a current consumer question.

### Actionable failure

The default human failure must be concise.

It must preserve the most useful facts already known by the failing producer.
It must not require parsing debug output.
It must not dump internal Rust values.
It must not dump the semantic program.
It must not dump HIR.

It must not dump SSA.
It must not dump bytecode.
It must not dump machine code.
It must not dump a backtrace by default.

It must not repeat the same message through multiple wrapper layers.
A source failure should preserve, where actually available:
- logical path;
- line;
- column;
- stable diagnostic code;
- severity;
- message; and
- related source locations.
A package failure should preserve the package fact actually known.
A workspace-incomplete failure should preserve the structured blocker actually known.

A compiler failure without richer structured facts should remain an honest typed category plus message.
Do not fabricate a span or code for a boundary that does not have one.
Do not parse a rendered source diagnostic string to recover its path, line, code, or message.
Carry the facts through a narrow typed boundary.

### Compact machine result

Provide a deterministic machine-readable result for the current check consumer.

Prefer the CLI's existing `--json` convention unless inspection demonstrates a better smaller convention.
Keep the document deliberately narrow.
A reasonable upper bound for the schema is:
- schema identity;
- success or failure state;
- one current failure or a current bounded diagnostic collection;
- exact structured source facts when available;
- honest failure phase or class;
- optional related locations;
- explicit completeness metadata only if partial output can actually occur.
Do not serialize:

- `ExecutableProgram`;
- `WorkspaceSnapshot`;
- private parser nodes;
- private HIR;
- private SSA;
- private bytecode internals;
- internal identity allocators;
- dense IDs;
- every package object;
- every compiler metric; or
- the Rust error enum by derivation.
Do not add a schema version solely to preserve compatibility.
A schema name is useful.
Backward compatibility is not required.

A machine success result should be one compact JSON value.
A machine failure result should be one compact JSON value.
Do not mix progress text with JSON.
Use stdout for the requested machine document.
Keep stderr empty for an ordinary represented check result.

CLI usage failure, inability to emit the requested document, or an equivalent command-boundary failure may use stderr.
Decode JSON in tests.
Do not test JSON with substring matching when exact decoding is practical.

### Honest cardinality

Inspect how many diagnostics the current compiler can actually return.
Do not design pagination for a compiler that returns exactly one current failure.

Do not claim to return every possible program error if compilation stops at the first failure.
If a current producer can return multiple facts, preserve deterministic order.
If output can become large, use one of:
- an explicit bound with an omitted count;
- an explicit partial marker;
- pagination;
- streaming; or
- a hard host-output error.

Never silently truncate.
Do not create a generalized pagination framework for one bounded command.

### Simple exit behavior

Preserve a simple exit contract.
Success must be zero.
An invalid program, package, or compile result must be non-zero.
Command misuse must be non-zero.

Do not create a large exit-code taxonomy.
Use the current one-code failure convention unless a directly useful distinction has a current consumer and focused tests.

Update tests to the intended current contract.

## Detailed design constraints

### Compiler API boundary

Prefer a compiler-owned compile/check result over an app-owned reimplementation of compiler phases.
The app should orchestrate.
The compiler should own compile facts.

The source layer should own source diagnostic facts.
The package layer should own package facts.
The workspace should own semantic diagnostic and completeness facts.
The app may own:
- CLI argument validation;
- selection of human versus machine rendering;
- stdout and stderr routing;
- process exit status; and
- the narrow public check document.

Do not make the app parse compiler display strings.
Do not make the compiler know about terminal decoration.
Do not make the source parser know about JSON.
Do not make the core error type absorb every domain solely for this command if a narrower compile boundary is cleaner.

Changing an existing public compiler return type is permitted.
There is no backward-compatibility requirement.
Choose the design with fewer active paths.

### Structured source facts

If `SourceDiagnostic` remains private, expose a narrow immutable view.
If it becomes public, expose only facts with current consumers.
A source range should distinguish start and end when the producer knows both.

Do not reduce a range to one point merely because human output currently shows one point.
Use logical source paths.
Do not expose canonical host containment paths unless a current diagnostic consumer needs them.
Keep byte offsets only if they answer a current machine editing question.

Line and column are sufficient for the current check loop if byte offsets add no current value.
Do not create UTF-16 positions without an LSP consumer.
Do not create zero-based and one-based duplicate coordinates.
Document the chosen convention.

Test it.

### Error codes

Preserve existing stable source diagnostic codes.
For other boundaries, prefer a small closed kind or phase over invented fine-grained codes.
Examples of honest broad kinds may include:
- source;
- package;
- incomplete;
- compiler;
- host; and
- internal contract.
Use the actual current boundaries.

Do not expose `ErrorClass` names merely because they exist if they are not meaningful to the consumer.
Do not claim stability beyond the current schema.

### Human rendering

Human output should lead with the actionable location and message.
One concise shape is:

```text
path:line:column: error[CODE]: message
  related other-path:line:column: label
```

Use the existing renderer when it is already correct.
Do not add ANSI color unless the repository already has a color policy and tests.

Do not add source snippets or carets unless they materially improve the current workflow and can be implemented without a source-rendering subsystem.
The default should fit in a small context.

### JSON rendering

Use a real serializer already present in the dependency graph when it makes the implementation safer and smaller.
Do not manually concatenate JSON if a typed serializer is already available and avoids escaping defects.
Do not add a dependency when existing `serde` and `serde_json` suffice.
Do not derive serialization for large internal types.

Create one narrow response type.
Keep field ordering deterministic.
JSON object key order is presentation, not semantic meaning, but byte-for-byte deterministic tests are useful for this command.
Do not include null fields for facts that do not exist unless a consistent nullable field materially simplifies the consumer.

Omitting absent optional facts is usually more compact and more honest.
Do not repeat the same message in `summary`, `detail`, and `diagnostics`.

### Program path semantics

Use the same path acceptance and containment rules as `run`.
Do not introduce a current-directory source scan.
Do not add globbing.
Do not accept stdin unless a current workflow and package identity model justify it.

Do not accept directories if `run` requires an entry file, unless the current package API already resolves directories coherently.
Do not canonicalize a display path differently from the compiler's logical source origin.

### Package semantics

A check of the product command should require the same package/lock boundary as `run`.
Do not silently fall back to development compilation when a required package is absent.
If a separate development compiler convenience remains useful internally, keep it distinct.

Do not make the product CLI guess.
Do not verify the package twice.
Do not load source twice.
Do not parse twice.
Do not analyze twice.

Use counters or focused tests where existing instrumentation can prove this without production telemetry.

### Metrics

Do not emit runtime metrics from check.
Compile timing may remain internal.
Do not add default timing output.
If an existing metrics environment variable automatically captures compile metrics, decide deliberately whether check supports it.

Support it only with a current consumer and a compact documented schema.
Otherwise reject or ignore it consistently.
Do not expand this task into a metrics redesign.

### Native path

Check should validate the generic production compiler artifact.
It does not need to prove native eligibility.
Native lowering is an optional execution specialization.

Do not run it merely to say the program checks.
Do not report a native decline as a program error.
Do not make check target-dependent beyond the existing production compiler and package target contract.

### Determinism

Equivalent invocations in the same checkout must produce equivalent:
- status;
- human diagnostic selection;
- machine document;
- diagnostic ordering; and
- path spelling under the same invocation path.

Do not include:
- timestamps;
- durations;
- process IDs;
- temporary paths;
- allocation addresses;
- hash-map iteration order;
- random IDs;
- cache hits;
- thread scheduling; or
- absolute checkout paths
in default check output.

### Output safety

The compiler must not allocate an unbounded duplicate rendering merely to print an error.
Reuse existing strings or bounded construction where practical.
Do not impose a language-validity limit on diagnostic size.

A host output policy may fail explicitly.
Do not silently cut a diagnostic message.
If a related list can be large, use an explicit current bound and omitted count only when evidence shows the list can become large.
Do not add policy machinery preemptively.

### Repository output safety

A quiet verification mechanism must not discard complete logs before success is known.

A full log path must be outside tracked source.
Use `target/` when appropriate.
Do not place logs in the repository root.
Do not use a stable filename that concurrent agents can overwrite.
Include process identity or a safe temporary directory.

Do not expose secrets from the environment in a failure summary.
Do not echo the full environment.

### Cross-platform shell behavior

The currently tested host is Linux x86-64.
A verification script may target the supported development host.
Use `bash` only if the repository already relies on Bash and the script declares it.

Do not pretend POSIX portability if Bash features are used.
Do not add PowerShell and Windows variants in this task.
Do not add a script abstraction layer for hypothetical hosts.
