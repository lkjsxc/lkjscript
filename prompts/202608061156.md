## Product mandate

Build toward an AI-primary, statically typed, memory-safe, high-performance language and runtime whose authoritative program representation is semantic rather than textual.

The long-term product should let an AI agent:

- inspect program meaning without reconstructing it from files and token streams;
- query types, expected types, bindings, references, effects, capabilities, ownership, call relationships, dependencies, diagnostics, and legal edits;
- work on incomplete but semantically meaningful programs;
- apply typed, atomic, revision-checked edits;
- receive compact semantic diffs and precisely scoped context;
- compile a complete semantic snapshot directly, without rendering and reparsing text;
- use deterministic local machinery for every correctness decision;
- review and export concise human-readable projections when needed.

Text remains useful as an import, export, review, debugging, and interoperability projection. It must not permanently own semantic identity or constrain the authoritative schema.

Final performance matters. Optimize the whole product rather than one benchmark: agent interaction cost, edit latency, cold and warm compilation, startup, execution latency and throughput, memory footprint, allocation and copying, code size, cache behavior, and failure-path cost. Choose architecture through measurement rather than through preservation of existing mechanisms.

## Non-negotiable outcomes

The following are defects, not language rules:

- token-count limits;
- source nesting limits;
- type nesting limits;
- parser child-count limits;
- top-level declaration or form limits;
- product-field, enum-field, variant, parameter, argument, pattern, and match-arm limits;
- file, import, module, directory-entry, directory-width, directory-depth, and source-unit count limits;
- HIR expression, function, entry, use, loan, call, obligation, type-node, witness, destination, scope, and verifier-work limits;
- ownership-analysis expression or retained-state limits;
- SSA function, block, edge, value, operand, frame-state, type-work, trait-work, and verification-work limits;
- specialization-count limits that turn a valid program into an error;
- structural metadata, structural value, witness, dependency, layout, and representation count limits;
- task-graph count ceilings used as compiler semantic admission checks;
- repository topology rules based on file length, line width, directory width, directory depth, or arbitrary fan-out;
- limits hidden behind resource profiles, digest identities, “foundation maxima,” implementation maxima, or supposedly deterministic profiles.

Remove these restrictions dependency-closed. Do not satisfy this assignment by increasing values, changing powers of two, moving constants, renaming errors, selecting a more permissive profile, or applying the same quota at a later phase.

A semantically valid program must remain semantically valid independently of these counts. Trusted local compilation must continue until it succeeds, is explicitly cancelled, encounters allocation or operating-system failure, or reaches a genuine unavoidable external representation boundary. Ordinary program size must not be rejected by a project-selected count quota.

Operational resource control is still necessary at untrusted, daemon, and multi-tenant boundaries. Implement it as explicit coarse host policy over resources such as input bytes, resident or allocated memory, output bytes, elapsed time or deadline, cancellation, and concurrency. Such a policy controls an execution request; it does not redefine the language. The same program must be able to fail under a low policy and succeed unchanged under a higher or unrestricted policy.

### Narrow bytecode and identifier encodings

Removing parser and HIR checks is insufficient. The inspected bytecode path encoded or stored ordinary user-scale quantities with narrow integers:

- function arity and local counts as `u8`;
- owner and unique-place indexes as `u8`;
- constants, globals, jumps, and several type indexes as `u16`;
- other source-order and metadata positions as narrow integers;
- some insertion paths used unchecked `as u16` casts from vector lengths.

The compiler consequently rejected more than 255 locals or parameters and exposed other narrow representation boundaries. Search all crates for unchecked or fallible narrowing, including `as u8`, `as u16`, `as u32`, `u8::try_from`, `u16::try_from`, and error strings that describe an integer width as a language limit.

Break and redesign the bytecode or executable representation. Use scalable in-memory identifiers and a checked, extensible encoded form. Variable-width operands, wide fixed-width operands, segmented tables, multiple instruction forms, or another measured design are all acceptable. Silent truncation is never acceptable. A compact fast path is acceptable only when a scalable path exists and ordinary language validity does not depend on the compact range.

### Phase 1 — Eradicate arbitrary validity-changing limits end to end

This is the highest-priority implementation phase.

#### 1.1 Separate semantic validity from resource policy

Replace the broad semantic-count profile/ledger system.

For trusted local compilation:

- do not instantiate a finite named profile;
- do not reject by token, node, expression, declaration, field, function, block, edge, witness, or work-unit count;
- retain telemetry only when it is cheap and useful;
- make telemetry observational rather than authoritative.

For untrusted operations:

- introduce one small explicit host policy at the boundary;
- use coarse resources: accepted input bytes, memory or allocation budget where enforceable, output bytes, deadline or elapsed time, cancellation, and concurrency;
- make unrestricted policy explicit;
- propagate cancellation and allocation failure without partial publication;
- ensure low policy failure does not poison caches or mutate the prior snapshot;
- ensure the identical program succeeds under a higher or unrestricted policy.

Do not encode dozens of compiler internals into a public profile digest.

#### 1.2 Remove source-shape limits

Remove count-based validity checks from source loading, tokenization, parsing, import resolution, source trees, declarations, fields, variants, parameters, arguments, patterns, and nesting.

Keep semantic and security checks such as:

- path containment;
- exact import resolution;
- symlink policy;
- cycle detection;
- UTF-8 and syntax correctness;
- duplicate and unresolved-name errors;
- capability boundaries.

Make user-controlled depth stack-safe. Replace recursive parsing, traversal, formatting, identity computation, analysis, rendering, and destruction where their depth follows program input. An explicit stack is usually preferable.

Avoid reading or copying the entire repository when only a dependency closure is required. Stream or incrementally read where practical.

#### 1.3 Remove HIR, ownership, memory-plan, SSA, structural, and specialization quotas

Delete fixed count admission checks throughout:

- HIR construction and analysis;
- ownership and effect analysis;
- memory-plan production and verification;
- type and trait resolution;
- SSA construction and verification;
- structural representation and witness construction;
- optimization input admission;
- native specialization.

Repair algorithms that depended on rejection:

- replace recursive walks with explicit worklists;
- replace global repeated scans with indexed or graph algorithms;
- avoid accidental quadratic behavior on ordinary large programs;
- use checked arithmetic for sizes and offsets;
- use fallible reservation and growth;
- release temporary memory promptly;
- use generic lowering when specialization is unavailable or not profitable;
- paginate or stream large diagnostic and query results rather than truncating them.

A timeout or cancellation at an untrusted boundary is not permission to publish an arbitrary semantic count limit.

#### 1.4 Redesign narrow representations

Audit every user-scale identifier and encoded operand.

At minimum, remove ordinary dependence on:

- `u8` arity and local counts;
- `u8` owner/place counts;
- `u16` constant and global counts;
- `u16` jump or code offsets;
- narrow source-order fields;
- unchecked casts from collection lengths;
- a single function or chunk layout that cannot scale beyond old boundaries.

Choose a coherent replacement based on measured decode cost, code size, implementation complexity, and future evolution. Possible designs include wide fixed-width operands, compact and wide opcodes, LEB128-like variable integers, segmented constant/function tables, or a block-oriented executable IR. No compatibility with the current bytecode is required.

Requirements:

- every narrowing conversion is checked;
- constructors cannot silently wrap;
- decoder validation proves bounds before indexing;
- malformed serialized data fails closed;
- in-memory IDs are not public positional indexes;
- compact IDs may be snapshot-local but must map from stable semantic identities;
- representation overflow is distinct from semantic invalidity;
- practical scale tests cross `255`, `4,096`, `16,384`, and `65,535` boundaries where those boundaries previously mattered.

#### 1.5 Replace rejection tests with scalable positive tests

Remove tests whose purpose is to canonize an arbitrary maximum.

For each former boundary, add:

1. a just-beyond-old-boundary positive regression;
2. a substantially larger representative case;
3. a failure test only for genuine semantic invalidity, malformed input, explicit low resource policy, cancellation, allocation simulation, or unavoidable external failure.

Generated test programs are preferable to enormous checked-in fixtures.

Required coverage includes, where semantically supported:

- more than 384 tokens;
- nesting well beyond 8 and type depth beyond former limits;
- more than 16 children and arguments;
- more than 8 top-level declarations;
- more than 15 fields and variants;
- more than 255 locals or parameters;
- more than 4,096 relevant nodes or blocks in targeted verifier tests;
- more than 16,384 HIR expressions through complete compilation;
- more than 65,535 constants, globals, offsets, or table entries in a focused executable-format test when applicable;
- a wide directory and large dependency closure;
- unchanged program success under unrestricted policy after low-policy exhaustion;
- compile and execution, not parsing alone, for representative scale cases.

Keep CI geometry reasonable by separating quick boundary regressions from opt-in stress and benchmark campaigns. Do not reduce coverage by testing only a helper that bypasses the production path.

After scale is no longer blocked by arbitrary ceilings, reduce the architecture to the mechanisms the product needs.

#### 2.1 Reconstruct the production dependency graph

Use `cargo metadata`, `cargo tree`, call-site searches, tests, and release binary inspection. Identify:

- the minimal semantic compiler;
- the selected generic execution route before final runtime selection;
- true host and unsafe boundaries;
- optional daemon and persistence consumers;
- test-only and benchmark-only code;
- subsystems with no production consumer.

Do not use crate count as a goal. Use cohesion, boundary ownership, build isolation, and measured coupling.

#### 2.2 Delete residual topology damage

Remove:

- numbered `impl_XX`, `helpers_XX`, and similar mechanical shards;
- one-child directory ladders;
- facade modules that only re-export internal fragments;
- files split solely to satisfy former line or directory limits;
- duplicate model types across crates;
- contract crates whose main role is to hash internal Rust facts;
- adapters that convert between nearly identical internal representations;
- inactive benchmark and Brainfuck remnants;
- obsolete docs and test helpers.

Recombine code first, then split on natural semantic boundaries.

#### 2.3 Reduce internal authority machinery

For every digest, descriptor, witness, certificate, verifier, revision, registry, and reconstruction pass, ask:

1. What attacker or stale producer is on the other side?
2. Is data serialized, persisted, or crossing a process, capability, FFI, or executable-memory boundary?
3. Would ordinary typed construction and ownership prevent the invalid state?
4. Is the mechanism catching a demonstrated bug class?
5. What compile time, memory, code size, and maintenance cost does it impose?

Keep only mechanisms with a concrete answer.

Inside one trusted process:

- own each semantic fact once;
- derive compact backend facts when needed;
- avoid serializing and hashing transient compiler state;
- avoid “independent” reconstruction that duplicates the producer without an adversarial boundary;
- avoid opaque authority wrappers whose only purpose is to satisfy another internal wrapper.

At actual boundaries:

- keep explicit schema/versioning local to that boundary;
- validate once on entry;
- use typed data internally;
- validate executable installation and unsafe calls rigorously.

#### 2.4 Defer speculative platform foundations

The daemon, process cells, database, scheduler, hardware-topology, retained-runtime, remote execution, GUI, web, and distributed work may remain only when they have a current tested consumer and do not multiply the language/runtime implementation surface.

Otherwise, remove them, merge the reusable mechanism into a smaller owner, or move them out of the default workspace until the compiler and semantic source foundations are credible. Do not maintain speculative infrastructure merely because it may be useful later.

#### Phase 2 gate

Record before/after build time, release size, and dependency graph changes. Do not set arbitrary line-count or crate-count targets.

### Phase 4 — Measure and select one production runtime path

Do not assume that the current VM, baseline JIT, optimizing JIT, or custom native backend is the correct survivor.

#### 4.1 Build a representative workload matrix

Cover at least:

- cold one-shot command execution;
- warm repeated calls;
- many small functions;
- one large function and large CFG;
- scalar integer and floating-point arithmetic;
- branches and loops;
- direct calls and higher-order or generic calls where implemented;
- products, enums, matching, and field access;
- bytes, byte vectors, strings, and lists;
- allocation, movement, borrowing, region/arena behavior, and cleanup;
- error, trap, cancellation, and early-return paths;
- host-call boundaries;
- compilation of large generated programs;
- code with optimization opportunities and code with none.

Use target applications as they become possible. Brainfuck is not required.

#### 4.2 Measure end to end

For release builds, with repeatable machine metadata and repeated runs, measure:

- parse/import or semantic-load time;
- analysis time by major query or phase;
- executable lowering time;
- time to first result;
- time to first native entry if applicable;
- steady-state latency and throughput;
- peak resident memory;
- allocated bytes and allocation count where practical;
- generated code size;
- release binary size;
- cache hit rate and retained cache memory;
- failure-path latency;
- incremental edit latency later;
- agent query bytes, response bytes, and round trips later.

Use medians and tail distributions rather than one run. Keep raw data out of permanent authority.

#### 4.3 Compare alternatives

Compare the current paths without requiring feature parity as a precondition. Also implement bounded spikes sufficient to evaluate:

- Cranelift as a mature Rust-native JIT/AOT backend;
- LLVM/ORC only if maximum optimized throughput plausibly justifies integration and build complexity;
- direct AOT or cached native artifacts where startup and repeated deployment matter;
- a simpler VM or threaded interpreter if it remains a useful generic path.

Do not adopt a backend because it is fashionable, and do not retain custom code because it is custom. Compare compile latency, runtime quality, memory, portability, safety, maintenance burden, and integration cost.

#### 4.4 Make and execute the decision

Before measurement, state selection criteria and reversal conditions. After measurement:

- choose one production execution architecture;
- make implementation tiers internal policy rather than public language semantics;
- retain at most one small reference executor for differential semantics;
- delete public flags, test matrices, contracts, and adapters for losing paths;
- stop constructing unused representations on every compile;
- remove feature-parity obligations across discarded engines;
- simplify metrics around the selected path;
- retain a generic fallback for valid programs when optimization or specialization is unavailable.

If the optimizing tier does not show material representative benefit, delete or freeze it. If a mature backend dominates a custom backend, migrate. If the custom path wins on the product’s actual constraints, retain it with documented evidence.

#### Phase 4 gate

The default runtime must have one explainable production path, one semantic definition, representative measurements, and no unnecessary cross-product of execution engines.

### Phase 5 — Make the semantic workspace authoritative

Implement this as an integrated replacement, not a parallel `v2`.

#### 5.1 Minimal semantic model

Begin with the smallest executable vertical that proves the architecture:

- one workspace and module;
- `main` and ordinary functions;
- primitive types and literals;
- parameters, local bindings, references, and calls;
- conditionals;
- one explicit incomplete-expression hole;
- enough effects/capabilities to demonstrate the boundary without mirroring the entire current language.

It is acceptable to reduce the provisional language surface during the reset. Do not preserve a feature solely for compatibility. Preserve or reintroduce features when they belong to the target semantics.

Use a model with:

- stable logical `WorkspaceId`, `RevisionId`, `EntityId`, `NodeId`, `BindingId`, or equivalent concepts;
- generation or namespace checks that reject stale IDs;
- an ownership/containment structure for syntax-independent semantic nodes;
- explicit graph edges for references and dependencies;
- names and projection locations as attributes rather than identity;
- snapshot-local dense indexes only as private acceleration structures;
- content hashes only for immutable snapshots, artifacts, caches, and transfer verification.

Do not content-address every mutable node. Do not make source order an identity.

#### 5.2 Meaningful incomplete states

Workspace snapshots must be able to represent:

- typed holes with expected type and local context;
- untyped holes while inference is incomplete;
- unresolved references;
- ambiguous references or choices;
- type and effect mismatches;
- missing branches, fields, parameters, or declarations;
- explicit conflict and import-error nodes.

These are valid editing states. A release/execution gate rejects incomplete reachable states with precise diagnostics. The workspace itself remains queryable and editable.

#### 5.3 Typed transactions

Provide an in-process typed API before optimizing a wire protocol.

Operations should include a coherent subset of:

- create and delete entity;
- insert, move, and replace semantic node;
- rename declaration or binding;
- set a typed field, type, effect, capability, or reference;
- rewire a call;
- introduce, refine, and fill a hole;
- apply a legal refactoring;
- resolve a conflict;
- commit and abort.

Every transaction must:

- name a base revision or equivalent precondition;
- validate IDs and operation shape before publication;
- apply atomically;
- preserve the old snapshot on failure or cancellation;
- produce a new revision only on success;
- return a semantic diff, diagnostics, and invalidated query families;
- support batching so an agent does not need one round trip per node.

A text patch may be imported into a transaction. It is not the foundational operation.

#### 5.4 Agent-oriented semantic queries

Implement deterministic, revision-labelled queries for a useful subset of:

- entity lookup and summaries;
- definition and references;
- callers and callees;
- actual and expected type;
- typing context;
- effects and capabilities;
- ownership and move/borrow state;
- diagnostics;
- hole context;
- legal constructors and edits at a hole;
- dependency and impact slices;
- search by name, type shape, operation, or capability;
- concise rendering of a selected semantic slice.

Large results require stable order, filtering, pagination, and continuation. Never silently truncate.

Provide compact response modes that return semantic headers and IDs first, with selective expansion. Optimize for context precision and low round-trip count rather than dumping the repository or compressing it into an opaque blob.

The model may propose operations. Deterministic compiler and workspace code validates them. No model call belongs in a correctness gate.

#### 5.5 Projections and direct compilation

The current line-oriented text parser becomes an importer into the semantic workspace. A renderer produces a human-readable projection. Both are replaceable adapters.

A complete semantic snapshot must lower directly into the canonical typed core without rendering text and reparsing it.

Tests must prove:

- direct semantic compilation does not call the text parser;
- formatting-only changes do not change semantic identity;
- rename and movement preserve entity identity;
- stable IDs survive unrelated edits;
- stale revisions and stale IDs fail before publication;
- failed transactions leave the prior snapshot byte-for-byte or semantically unchanged;
- semantic diffs identify meaningful changes;
- importer and renderer are deterministic;
- snapshot serialization, if present, round-trips;
- text import followed by semantic compile matches the intended semantics;
- incomplete snapshots remain queryable but cannot be released.

Delete the old syntax-shaped JSON authority and text-publication path after the integrated replacement covers the selected vertical.

#### 5.6 Persistence discipline

Start in memory. Use immutable snapshots, persistent/COW data structures, or another simple measured design. Do not begin with a distributed database, CRDT, event-sourced platform, or universal content-addressed graph.

Add a transaction log, binary snapshot, embedded database, collaboration algorithm, or remote protocol only after measurements establish a need for crash recovery, retained scale, concurrent writers, or distribution.

#### Phase 5 gate

The semantic model is authoritative when an agent can create or import a small program, query and edit it through typed operations, preserve meaningful incomplete states, obtain semantic diagnostics and diffs, and compile a complete snapshot directly without a text round trip.

### Phase 6 — Add measured incrementality and performance specialization

After Phase 5 works from scratch:

1. Instrument dependency and invalidation behavior.
2. Establish from-scratch baselines for small, medium, and generated large workspaces.
3. Measure edit cases: local literal, rename, signature change, effect change, dependency change, module move, and hole fill.
4. Compare a small explicit query cache with a mature incremental framework such as Salsa.
5. Evaluate finer-grained techniques, including direct binding/reference pointers and order-maintenance approaches, only where profiles show value.
6. Select based on correctness, cancellation, cycle handling, invalidation precision, retained memory, compile time, debugging cost, and edit latency.
7. Add cache eviction and memory accounting before long-lived daemon integration.
8. Keep caches derivable; corruption or eviction must not alter semantics.
9. Add reproducible performance regression checks with noise-aware thresholds.
10. Profile before introducing tiering, OSR, deoptimization, speculative compilation, custom scheduling, or NUMA placement.

Do not build a custom scheduler to solve a bottleneck that has not been measured.

#### Phase 6 gate

Incremental recomputation must be observably correct relative to from-scratch analysis and materially improve representative edits without uncontrolled retained memory or a new authority system.

### Phase 7 — Resume broader platform work only after the foundations pass

Only after the preceding gates may the project expand service, package, database, GUI, web, game, distributed, remote-execution, or sophisticated runtime-scheduling features.

Every new platform feature must use:

- the authoritative semantic workspace;
- the selected production runtime;
- explicit capabilities;
- genuine boundary validation;
- measured resource policy;
- the active documentation authority.

Do not recreate an alternate source or runtime path for a framework.

## Required technical standards

### Failure atomicity

Compilation, semantic transactions, artifact installation, cache publication, and runtime registration must not leave partially published state after:

- validation failure;
- cancellation;
- timeout;
- allocation failure;
- I/O failure;
- backend failure;
- relocation or executable-memory failure;
- stale-revision rejection.

Use staged construction and a single publication point.

### Determinism

Given the same semantic snapshot, explicit options, target, and capabilities:

- analysis and diagnostics must use stable ordering;
- semantic diffs must be deterministic;
- serialization and artifact identity must be deterministic where claimed;
- parallel discovery must not change meaning;
- caches and scheduling must not change observable program semantics.

Operational timing limits may change whether a request completes, not what a completed request means.

### Security and capability boundaries

Do not weaken:

- path containment and symlink checks;
- explicit host capabilities;
- artifact and protocol validation at untrusted boundaries;
- W^X executable-memory discipline;
- relocation and generated-entry validation;
- FFI and operating-system error handling;
- SQLite or persistence transaction safety;
- daemon framing and authorization where retained.

Simplification means moving validation to the correct boundary, not removing the boundary.

### Memory safety direction

The current product hypothesis is collector-free ordinary execution. Do not introduce a tracing collector merely to avoid simplifying ownership and representation machinery unless the user explicitly changes direction.

Source code should not require:

- explicit lifetime names;
- retain/release;
- a general `free`;
- raw pointers;
- runtime memory-engine selection.

Prefer a small, coherent combination of:

- static and immediate values;
- unique or affine ownership;
- lexical or invocation regions;
- arenas for phase-local data;
- coarse immutable sharing;
- compiler-inserted cleanup with one authority.

Measure per-value metadata, witness tables, cleanup plans, copies, allocations, and locality. Redesign internal memory representation aggressively when the current witness system costs more than it protects.

### Dependency policy

Third-party dependencies are allowed.

Use a mature dependency when it removes substantial custom complexity, security risk, or maintenance. Keep a custom mechanism when it is small, performance-critical, and measurably better for the product.

For each major dependency decision, consider:

- correctness and security posture;
- maintenance and release cadence;
- supported targets;
- compile time;
- binary size;
- runtime performance;
- API stability;
- integration complexity;
- exit cost.

A zero-dependency claim is not a goal.

### Unsafe code

Keep unsafe code in narrow, named mechanism crates or modules with safe caller contracts and focused tests. Do not spread unsafe code into the semantic model, compiler policy, or general runtime.

Performance-critical unsafe code needs a benchmark against the safe alternative and a written invariant.

## Verification

Run focused tests during development, then the complete transparent suite:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo build --workspace --release --locked
```

Run retained Docker verification when available:

```sh
docker compose -f meta/docker-compose.yml --profile verify run --build --rm verify
```

Also run, when relevant:

- generated scale tests;
- differential tests between reference and selected production execution;
- malformed-bytecode and malformed-protocol tests;
- cancellation and allocation-failure tests;
- sanitizer, Miri, fuzz, or property tests at unsafe or decoding boundaries;
- benchmark harnesses in release mode;
- documentation link and example tests.

Do not weaken or delete a test merely because the new architecture fails it. Determine whether the test owns a valid target semantic law, a genuine boundary invariant, an obsolete compatibility promise, or an arbitrary limit. Preserve the first two, replace the last two.

## Commit and publication discipline

- Keep the worktree understandable at phase boundaries.
- Make cohesive commits that explain architectural intent and deleted mechanisms.
- Do not mix unrelated user changes into your commits.
- Do not manufacture platform revisions or compatibility migrations.
- Push the current branch when credentials and task context permit.
- Do not open a pull request unless explicitly requested by the surrounding task.
- Never claim a command passed unless you ran it after the relevant final change.
- Report retries and environment failures exactly.

## Final report

At the end of the work, provide a precise report containing:

1. the starting commit and final commit;
2. the architectural decision made;
3. the code and crates deleted, merged, or replaced;
4. every arbitrary limit removed, grouped by source, HIR, ownership, memory, SSA, executable representation, runtime, protocol, and repository;
5. every remaining bound, classified as semantic law, unavoidable external representation boundary, untrusted host policy, or private tuning;
6. evidence that trusted local compilation is not count-quota limited;
7. scale tests and former boundaries crossed;
8. runtime and compiler measurements, with workload and environment;
9. the selected production execution path and discarded alternatives;
10. semantic workspace operations and queries implemented;
11. documentation authority changes;
12. verification commands actually run and exact results;
13. known risks, untested boundaries, and the next highest-priority dependency-closed slice.

Do not describe planned work as completed. Do not hide unsupported cases behind “experimental” labels without explaining the exact implementation boundary.

## Research basis: use as input, not doctrine

The following work contains useful ideas. Study the primary sources where relevant, but do not copy an architecture without testing it against lkjscript.

- Cyrus Omar et al., **“Hazelnut: A Bidirectionally Typed Structure Editor Calculus”** (2017): statically meaningful incomplete terms and typed structure-edit actions.
- Andrew Blinn et al., **“Statically Contextualizing Large Language Models with Typed Holes”** (OOPSLA 2024): expected types, typing contexts, semantic retrieval, iterative language-server feedback, and token-efficient AI context.
- Michael D. Adams et al., **“Grove: A Bidirectionally Typed Collaborative Structure Editor Calculus”** (POPL 2025): stable identities and structured edit actions for collaboration; collaboration is a later concern, not a reason to begin with a CRDT.
- Thomas J. Porter et al., **“Incremental Bidirectional Typing via Order Maintenance”** (OOPSLA 2025): fine-grained incremental typing, direct binding pointers, and measured order-maintenance techniques.
- Unison’s official design documentation: content-addressed immutable definitions and names as metadata. Adopt hashes selectively for immutable definitions, snapshots, artifacts, and caches; do not use content hashes as mutable editor-node identity by default.
- Salsa’s official documentation: deterministic query-based incremental recomputation. Evaluate it against a small direct design after the semantic vertical works.
- MLIR’s rationale: progressive lowering and explicit representation levels. Use the principle of clear abstraction levels without importing a multi-level framework merely to preserve current IR layers.
- Cranelift’s official documentation and LLVM ORCv2 documentation: mature backend options to benchmark against the custom native/JIT implementation.

The goal is not to make lkjscript resemble any one of these systems. The goal is to use the strongest relevant ideas while keeping one coherent, measurable, AI-primary language architecture.
