## 7. Leading architecture hypothesis

The leading hypothesis is a deterministic application-instance kernel.

It separates four domains.

### 7.1 Semantic application

An exact application artifact owns program meaning, release graph, entry contracts, policies, and
tests.

It does not own mutable instance state.

### 7.2 Durable instance

A durable instance binds:

- one exact application identity;
- one instance identity;
- one exact state type;
- one canonical initial state;
- one monotonic state revision;
- one retained transition history or independently reconstructible state authority;
- one explicit resource policy;
- and zero or more exact capability grants.

An instance is not a workspace, release, application, deployment path, process, or cache.

### 7.3 Deterministic transition

A semantic transition consumes exact typed inputs such as:

- current state;
- event;
- prior command outcome when resuming;
- exact policy;
- and explicit deterministic observations.

It returns exact typed data such as:

- next state;
- response;
- completion status;
- and zero or more ordered commands or one suspended command.

The transition itself performs no ambient host action.

### 7.4 Host executor

A host executor:

- validates the requested command;
- validates the exact capability grant;
- performs or simulates the external action;
- records known success, known failure, or unknown outcome;
- returns a typed command result;
- never changes semantic authority directly;
- and never silently retries a command after possible visibility.

This model is only a hypothesis.

Compare it with serious alternatives before committing.

## 8. Serious architecture candidates

Implement the smallest prototypes needed to decide among serious candidates.

Do not retain all candidates.

### Candidate A: pure state-transition kernel

Shape:

```text
(state, event) -> (next_state, response)
```

Advantages:

- smallest semantic surface;
- deterministic;
- no external action ambiguity;
- easy replay;
- state persistence can close useful local applications.

Risks:

- may externalize too much orchestration;
- cannot model multi-step operational workflows coherently;
- may force host logic to duplicate application intent.

Retain only if a useful application closes without semantic command requests.

### Candidate B: transition plus ordered commands as data

Shape:

```text
(state, event) -> (next_state, response, commands)
```

Advantages:

- pure semantic kernel;
- explicit intent;
- deterministic ordering;
- host authority remains external;
- easy fake-host testing.

Risks:

- next-state publication before command completion may encode the wrong lifecycle;
- batching may complicate partial action;
- command collections may require new language data forms.

Retain only with an exact suspended/completed and recovery contract.

### Candidate C: one-command suspension and resume

Shape:

```text
(state, event_or_result) -> done(next_state, response)
                         | request(next_state, command, continuation)
```

Advantages:

- makes sequencing and partial outcomes explicit;
- avoids an arbitrary command list;
- models retry and reconciliation as semantic states;
- can remain pure and deterministic.

Risks:

- continuation identity may become a second program representation;
- persisted continuation data may leak compiler/runtime state;
- repeated invocation may increase operational and agent surface.

Retain only if continuation state is ordinary validated semantic data rather than opaque control
state.

### Candidate D: typed algebraic effects or handlers

Shape:

```text
function : input -> output ! {effect_set}
```

Advantages:

- compositional effect signatures;
- familiar language-level abstraction;
- may scale to future effects.

Risks:

- large type-system, lowering, handler, continuation, artifact, and runtime surface;
- easy to confuse capability declaration with authority grant;
- replay and unknown-outcome semantics remain unsolved;
- no current application proves the generality pays rent.

Retain only if a bounded implementation materially simplifies the complete representative workload
against candidates B and C.

### Candidate E: direct capability values and host calls

Shape:

```text
function(capability, input) -> output
```

Advantages:

- explicit authority in signatures;
- direct programming model.

Risks:

- semantic execution becomes host-dependent;
- deterministic tests need substitution;
- resource lifetimes and partial actions enter the interpreter;
- replay and crash behavior become difficult;
- capability serialization may be invalid.

Retain only if command-as-data cannot close the workload and the exact resource lifecycle is
independently verified.

### Candidate F: external orchestration only

Keep lkjscript pure.

Make a Rust host application store state and interpret pure decisions.

Advantages:

- no language or artifact change;
- fast experiment;
- preserves current semantic core.

Risks:

- host becomes the real application language;
- coding agents must maintain split authority;
- application artifacts no longer close behavior;
- exact review and transfer weaken.

Use as an oracle or losing prototype unless the split is demonstrably simpler and still keeps
application meaning reviewable.

### Candidate G: embedded database or general workflow engine

Advantages:

- mature persistence or durability behavior.

Risks:

- imports a large trust and operational surface;
- may define semantics instead of merely storing them;
- may obscure exact canonical authority;
- dependency and binary costs may dominate the small system.

Do not retain without a measured need that a narrow journal or snapshot owner cannot meet.

## 12. Exact external-outcome model

- known success with evidence;
- outcome unknown after possible visibility;
- reconciliation confirmed absent;
- reconciliation confirmed present;
