## 2. Exact Product Operation

An agent must be able to submit one atomic `Edit::CreateEnum` whose field `DeclarationType` values
refer to the enum created by that same edit.

- The reference identifies exactly the current enum declaration; it is not name lookup.
- For a non-generic enum, the self reference carries zero type arguments.
- For a generic enum, the self reference carries one explicit argument for every declared binder.
- Arguments may contain declaration-local type-parameter handles at arbitrary depth.
- Arguments may contain already published semantic types admitted by the existing enum field rules.
- The self reference may occur at arbitrary type depth wherever the source language already permits
  the equivalent recursive enum type.
- Successful staging resolves the marker to the newly reserved stable enum identity and canonical
  private `EnumId`.
- The published snapshot contains only ordinary stable `SemanticType::Enum` facts and ordinary
  canonical HIR types.
- The creation-only marker never enters a snapshot, query, projection, diagnostic identity, semantic
  diff, HIR, SSA, bytecode, runtime value, package, or persistent format.
- The resulting enum receives correct recursive runtime layout facts rather than the current
  unconditional non-recursive value.
- All ordinary enum field, generic argument, ownership, reference, arity, and `never` restrictions
  remain canonical and exact.
- Failure publishes nothing and consumes no identity in future observable allocation.

## 8. Preferred Representation Decision

The preferred public creation-time representation is a context-bound variant equivalent to:

```rust
pub enum DeclarationType {
    // existing variants
    CurrentEnum {
        arguments: Vec<DeclarationType>,
    },
}
```

The exact spelling may change if repository naming conventions strongly favor another name. The
semantics may not change.

- `CurrentEnum` is a marker, not an identity.
- It is meaningful only while staging one `Edit::CreateEnum`.
- It identifies exactly the enum owned by that edit.
- It carries explicit invariant type arguments.
- It has no name field.
- It has no user-selected stable identity.
- It has no draft nominal ID.
- It may be nested at arbitrary depth.
- It is invalid in `CreateFunction` and every other declaration context.
- It is eliminated before publication.
Because one `CreateEnum` edit creates exactly one enum, a separate `DraftEnumId` would add an
identity domain without disambiguating anything. Do not add it.

## 9. Rejected Representation Families

### Name-based `self` or enum-name strings

Names are presentation and lookup. Name resolution would create ambiguity, rename coupling, and a
second declaration-time resolution law.

### Caller-supplied future `EntityId`

The allocator owns stable identity. Exposing a future identity would break failure atomicity and let
callers fabricate continuity.

### General `DraftNominalId`

Only one current enum must be referenced. A generalized nominal handle anticipates mutual recursion
and unrelated declaration batching.

### Temporary source rendering

Rendering and reparsing would violate semantic authority and zero-parser guarantees.

### Partially published placeholder enum

A published incomplete nominal would create a second lifecycle and observable identity state not
required by the operation.

### Global staged-type registry

One private staged enum fact is sufficient. A registry would manufacture framework and search cost.

### Implicit generic self arguments

Exact arguments are already the semantic-edit convention. Implicit identity substitution would add
inference and hide arity errors.

### Always-recursive layout

Only actual recursive definitions are recursive. Forcing the bit would change non-recursive runtime
facts and imported/source-free equivalence.

### Treat every enum-containing field as self-recursive

Field indirection and definition self-recursion are related but distinct facts. Match the canonical
imported law exactly.
