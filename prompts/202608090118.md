## 1. Mission for this turn

Make it possible for a `lkjscript` program to originate, remain incomplete while being edited, become
complete, compile, and execute entirely through the in-process semantic workspace API without ever
parsing or rendering source text.

This is the next dependency-closed AI-primary vertical. It is not a request to redesign the
`.lkjscript` file encoding, build a database, revive a semantic wire service, introduce a daemon, or
implement a general incremental compiler.

The only fixed source-format decision is the `.lkjscript` extension. The current line-oriented bytes,
grammar, textuality, formatting, and compatibility are all provisional. Do not spend this turn
polishing or replacing them unless direct repository evidence proves that doing so is unavoidable for
the source-free semantic vertical.

Backward compatibility is irrelevant. Prefer a direct representation correction and delete displaced
APIs or mechanisms rather than preserving them behind adapters.

## 2. Why this is the highest-leverage current problem

Recent work correctly removed speculative runtime/platform layers, selected one production execution
policy, made `WorkspaceSnapshot` the direct compiler input, deleted the semantic stdio service, added
stable workspace identities and atomic expression edits, removed several scale pathologies, and made
owned structural values stack-safe and near-linear.

However, the current checkout still contains an architectural contradiction that prevents the
semantic workspace from being the actual program authority at program genesis:

- The public ways to obtain a `WorkspaceSnapshot` are text/path import conveniences.
- `Workspace::new` requires an already existing snapshot rather than creating a program.
- `WorkspaceSnapshot::new` requires a complete, resolved, typed `hir::Program`.
- `hir::Program` requires a concrete `main` and at least one source origin.
- `Main`, `Function`, ordinary bindings, and every HIR expression are tied to `SourceId`-based origin
  facts.
- workspace consistency validation rejects a program with no source origins;
- current transactions clone and mutate a complete HIR program;
- current incompleteness is a typed-hole overlay over an otherwise valid HIR expression, so the
  hidden executable body remains present;
- the current incomplete-compilation error can describe holes only; it cannot describe a missing
  entry point, missing declaration body, unresolved reference, or another non-hole blocker; and
- the only programmatic direct-compilation test first imports text and then privately clones the HIR.

Verify every one of these observations against the actual HEAD. They describe the inspected baseline,
not immutable assumptions.

The result is that text is no longer the documented semantic authority but remains the only practical
bootstrap authority. It also prevents the target workspace contract from representing genuinely
empty, declaration-incomplete, unresolved, or otherwise recoverable semantic states.

Do not paper over this contradiction with a public HIR builder, synthetic source file, fake path,
dummy `main`, unit-valued placeholder body, hidden valid body beneath a hole, or render-and-reparse
round trip. Correct the owning representation and boundary.

## 3. Core hypothesis

A small, source-independent, first-class semantic construction vertical can replace the current
complete-HIR-plus-overlay bootstrap assumption while preserving one authoritative workspace model and
the existing direct compiler path.

The hypothesis succeeds when all of the following are true:

1. a public API creates an empty source-free workspace;
2. valid intermediate revisions can contain a missing entry point and real incomplete bodies without
   fabricated executable content;
3. semantic transactions can create the minimum declarations and expression structure needed for a
   nontrivial program;
4. queries and deterministic projections remain useful at each incomplete revision;
5. completion blockers are structured and revision-labelled;
6. filling the remaining incomplete structure produces a complete snapshot;
7. `compile_snapshot` consumes that complete snapshot directly;
8. the parser invocation count remains zero for creation, editing, querying, projection, compilation,
   and execution; and
9. text import and source-free construction converge on the same semantic authority rather than
   creating two product architectures.

If evidence shows that the current HIR can be cleanly evolved to satisfy these requirements, do that.
If evidence shows that HIR must remain a complete compiler IR, introduce the smallest authoritative
semantic representation from which HIR is derived, and cut all workspace paths over to it. A third
solution is acceptable if it is demonstrably smaller and more coherent.

The objective owns the task; the mechanism above is not predetermined.

## 4. Representation decision gate

Before implementation, trace at least these paths:

- text/path import through source validation and analysis into `WorkspaceSnapshot`;
- `WorkspaceSnapshot` storage, indexes, provenance, attachments, and consistency checks;
- `Workspace::apply`, identity allocation, staging, reconciliation, diagnostics, semantic diffing,
  and publication;
- the complete-HIR and hole-overlay relationship;
- source and origin requirements in HIR, analysis, effects, ownership, memory planning, SSA, and
  diagnostics;
- `compile_snapshot` completeness checks and direct compilation;
- current query, projection, legal-constructor, and continuation behavior; and
- existing tests that deliberately prove no render/reparse path.

Evaluate candidate designs against these questions:

- What object owns mutable semantic meaning?
- Can it represent an empty program, a missing entry point, an incomplete declaration, and a typed
  expression hole without hidden valid content?
- Are source paths and spans optional attachments rather than mandatory semantic data?
- Does text import produce the same authoritative object?
- Is complete HIR authoritative state or a derived compiler representation?
- If HIR is derived, what invalidates it, and can it be omitted from incomplete snapshots?
- If HIR is evolved, can compiler-only invariants remain explicit and enforceable at the completeness
  boundary?
- Where are names resolved, types checked, effects inferred, ownership checked, and completeness
  decided?
- Which semantic facts are stored once, and which are derived?
- Can existing stable IDs survive unrelated semantic changes without depending on preorder addresses?
- Can failure preserve the published snapshot and identity allocator exactly?
- Does the design reduce or increase the number of representations and conversions?
- Is the minimum vertical implementable without scaffolding for generics, persistence, collaboration,
  or distributed execution?

Reject any design whose main purpose is to preserve the current API or internal layout. Reject any
adapter that lets source-free calls construct a private complete HIR through fake source facts. Reject
a second mutable semantic AST kept in parity with HIR.

A derived complete compiler IR is not a second authority when its ownership, construction,
invalidation, and lifetime are explicit. A second independently mutable semantic model is.

Document the selected current architecture in the existing owning documents. Do not create a large
planning hierarchy. Add a decision record only if the representation choice is durable, non-obvious,
expensive to rediscover, and cannot be explained adequately in the workspace specification and
architecture document.

## 5. Required semantic invariants

The implementation produced by this task must satisfy the following invariants.

### 5.1 One source-independent authority

There is exactly one authoritative semantic state for both imported and programmatically constructed
programs.

A semantic program can exist with no source file, path, span, parser tree, formatting attachment, or
source digest. Imported source metadata may be attached without changing semantic identity.

Do not use strings such as `<workspace>`, `<generated>`, or `memory.lkjscript` as fake semantic source
origins. A diagnostic or compiler stage that has no source attachment must operate on semantic
identity and optional presentation data honestly.

### 5.2 Honest incomplete states

An empty program and a program with missing declarations or bodies are valid workspace states.

Do not retain an executable expression behind a hole. A hole or missing body is the semantic state,
not an overlay that cosmetically hides another value.

An incomplete snapshot is queryable and projectable but not executable. `compile_snapshot` must
return a structured incomplete result before compiler-only lowering. The result must not be limited to
a vector of hole IDs; it must be able to represent at least:

- a missing entry point;
- an incomplete declaration or entry-point body; and
- a typed expression hole.

Design the completeness-blocker representation so the first vertical is honest and later unresolved
references, missing match arms, conflicts, and other target states can be added without inventing a
second error system. Do not pre-build every future blocker variant when no current producer exists.

### 5.3 Stable identity and revisions

Use opaque workspace namespace, slot, generation, and revision defenses or a demonstrably better
replacement.

Creating, filling, or changing one body must not renumber unrelated entities or nodes. A stable
identity may change only when the semantic object is actually deleted and replaced or when the
operation contract explicitly says so.

A failed transaction must not advance the revision, mutate the published snapshot, consume identity
slots or generations, change provenance, or alter future deterministic allocation results.

### 5.4 Atomic semantic edits

All construction occurs through the same atomic transaction mechanism used for later edits. Do not
add a one-shot builder that bypasses revision checks, identity allocation, validation, semantic diff,
diagnostics, or publication.

The public API shape is not prescribed, but it must support the minimum acceptance scenario below.
Operation preconditions and failures must be typed and actionable.

### 5.5 Deterministic local correctness

Model inference is never part of validity. Given the same base snapshot and transaction, validation,
diagnostics, semantic diff, and completed meaning are deterministic.

Do not add a protocol, network service, or model callback. Keep the vertical entirely in-process.

### 5.6 Direct compilation

A complete snapshot compiles without source rendering, parsing, source analysis, or a text-specific
identity reconstruction step.

If the authoritative workspace state is no longer complete HIR, derive the compiler representation at
an explicit boundary. Do not retain a stale mutable HIR copy inside every incomplete revision merely
for convenience.

Full recomputation is acceptable for this correctness vertical when its work is bounded by actual
program size and documented truthfully. Do not implement a general incremental engine in this task.

### 5.7 Source-format freedom

Keep the `.lkjscript` extension. No other source-format compatibility is required.

Do not introduce a new textual grammar, binary container, database, content-addressed code store,
formatter, or migration reader in this task unless it is a necessary consequence of the selected
semantic cutover. Updating repository fixtures after an incompatible API or semantic correction is
allowed; preserving old bytes is not a goal.

## 6. Minimum dependency-closed vertical

Implement a public source-free workflow that demonstrates actual program authorship rather than only
constructing a private test object.

The exact Rust API and operation names are yours to choose. The following behavior is required.

### 6.1 Empty workspace

Create a new workspace without importing source.

The initial snapshot must:

- have a fresh namespace and a valid initial revision;
- have no presentation attachments;
- contain no fake sources, declarations, entry point, or body;
- report `Incomplete` through the existing state concept or a cleaner replacement;
- expose a deterministic diagnostic or completeness blocker for the missing entry point;
- support entity, diagnostic, and projection queries without panic or parser activity; and
- fail direct compilation with a structured incomplete result.

An empty transaction should remain invalid unless there is a compelling semantic reason to change
that rule.

### 6.2 Declaration construction

Through one or more atomic semantic transactions, create:

- one non-generic function named `identity` with one `i64` parameter named `value`, return type `i64`,
  and an honestly incomplete body; and
- one `main` entry point with no parameters, return type `i64`, and an honestly incomplete body.

The order of creation should not require fake declarations. It is acceptable for references to be
created only after their target declaration exists in this first vertical. General unresolved
references remain a later target unless the selected representation makes a small honest version
natural.

The resulting incomplete snapshot must expose stable entity IDs for the function, parameter, and
entry point, plus stable identities for body holes or equivalent incomplete semantic nodes.

Queries must expose expected types and visible entities. The `identity` body context must make the
parameter available as an `i64` load. The `main` body context must make `identity` available as a
callable `(i64) -> i64` function.

If introducing both a function and `main` would force an otherwise bad abstraction, establish the
correct representation with `main` first, then add the function in the same turn once the root is
sound. Do not lower the acceptance result to a source-free wrapper around a scalar HIR constructor.
The final committed vertical should exercise at least one created declaration identity and one
created reference or call edge.

### 6.3 Body completion

Fill the `identity` body with a semantic load of `value`.

Fill the `main` body with a call to `identity(42)`.

Use the existing flat, child-before-parent draft concept if it remains the simplest correct proposal
format. Replace it if the representation change makes another compact non-recursive operation clearly
better. Do not expose recursive Rust values that make user-controlled depth consume the native stack.

Remove public placeholder-only draft variants such as reserved unsupported shapes when they have no
implemented producer/consumer after the cutover. Public operation types should describe implemented
behavior, not advertise future scaffolding.

After both bodies are filled:

- the snapshot is complete;
- diagnostics contain no executable blockers;
- references and call edges identify the created function correctly;
- projection is deterministic without source attachments;
- `compile_snapshot` invokes no parser or source analyzer; and
- executing the selected production bytecode/VM path returns `42`.

### 6.4 Imported-program convergence

Retain at least one existing text-imported program and prove that it enters the same semantic
workspace representation and direct compilation boundary as the source-free program.

Do not require imported and source-free workspaces to share namespace-specific IDs or unstable binary
artifacts. Compare stable semantic observations: declaration kinds and signatures, expression
meaning, references/calls, complete diagnostics, compiler result, and execution outcome as
appropriate.

If the representation cutover changes private source parser or analysis APIs, delete displaced
workspace-specific adapters. The parser may remain as importer machinery; it is not the product
authoring authority.

## 7. Failure and adversarial behavior

Add focused tests for at least the following cases.

### 7.1 Revision and identity failures

- a transaction against a stale revision is rejected before publication;
- an entity, node, hole, or continuation from another namespace is rejected;
- a deleted or replaced generation is rejected as stale; and
- duplicate creation of `main` or a colliding declaration is rejected deterministically.

### 7.2 Type and scope failures

- an `i64` body hole rejects a Boolean, `unit`, or otherwise incompatible draft;
- the function parameter cannot be loaded from `main`;
- an invisible or stale callee cannot be called;
- call arity and argument types are checked before publication; and
- malformed or cyclic flat drafts fail without recursion, panic, or partial identity allocation.

### 7.3 Atomicity

For representative failed transactions, prove that:

- the current `Arc<WorkspaceSnapshot>` or equivalent published state remains unchanged;
- the revision remains unchanged;
- entity/node/hole sets remain unchanged;
- diagnostics and projections remain unchanged;
- parser invocation count remains zero; and
- retrying the corresponding valid transaction from the same base receives the same deterministic
  next IDs that it would have received without the failed attempt.

### 7.4 Incomplete compilation

- an empty workspace reports a missing-entry blocker;
- a declaration with an incomplete body reports a stable blocker tied to the declaration or semantic
  node;
- a typed expression hole reports its expected type and context;
- compilation does not enter memory planning, SSA, bytecode lowering, or runtime for an incomplete
  snapshot; and
- filling all blockers transitions exactly once to a complete compilable revision.

### 7.5 Depth and scale

Retain iterative construction, clone, traversal, identity reconciliation, projection, and destruction
for user-controlled semantic depth.

Add a normal fast test that exercises the algorithm on a modest generated depth and an ignored locked
release stress fixture on a small worker stack at a much larger depth, using the repository's existing
scale-testing conventions. Do not add a semantic depth limit.

Close a remaining `stack::grow` use only if it lies on this new construction/compilation path and the
focused deep fixture demonstrates it as the actual next root cause. Do not turn the task into a global
recursion rewrite.

## 8. Performance and complexity evidence

This task is primarily an architecture and correctness cutover, not a claim that semantic editing is
already incremental.

Before changing the implementation, characterize the current source-imported scalar/function path and
current transaction path sufficiently to detect accidental pathological work. At minimum record or
assert the relevant work shape:

- number of parser invocations;
- number of complete-program clones or reconstructions per transaction;
- major analysis passes rerun;
- semantic node/entity counts; and
- whether any path is quadratic in expression depth or declaration count.

After the cutover, measure or structurally demonstrate:

- zero parser invocations for the complete source-free workflow;
- no source bytes rendered, hashed, or parsed for that workflow;
- no fabricated source objects;
- no more than the necessary full semantic/analysis rebuilds for the selected non-incremental design;
- bounded or linear work across a generated size series for the changed traversal; and
- compile and execution behavior equivalent to the selected imported fixture.

A small repeatable development harness is appropriate if timings or allocations support a decision.
Do not add a global metrics framework. Do not gate CI on noisy wall-clock values. Store raw samples
outside Git and commit only compact evidence and reversal conditions in `docs/performance.md` when a
performance claim is made.

Do not optimize whole-program cloning, incremental invalidation, or caching unless the baseline shows
that one of them blocks this vertical or introduces unacceptable asymptotic behavior. Record honest
remaining costs in status/roadmap rather than preemptively building a framework.
