## 2. Primary objective

Complete one ordinary copied-binary command-application lifecycle on normalized Graph 5 authority.

The final released `lkjscript` executable must be able to:

1. create a useful command project with `new --template command`;
2. inspect and change its accepted typed semantic graph through the already normalized public paths;
3. check graph-owned tests through normalized compilation and implementation-disjoint execution;
4. build a deterministic normalized artifact;
5. run a pure command target through normalized production and reference execution;
6. perform the same lifecycle for the maintained standard package and the maintained `lkjournal` application;
7. advertise the contracts and operations it actually implements; and
8. reject predecessor editable repositories instead of selecting a second authority path.

Achieve this as one direct cutover. Do not add marker-selected dual dispatch, legacy modes, fallback readers, dual writes, graph editions, or a permanent migration command.

The primary objective includes only work required to close that lifecycle: maintained-consumer migration, normalized built-in standard-package material, shared compiler/runtime preparation, exact-current and incremental derived-cache handling, executable-registry correction, and deletion or isolation of predecessor lifecycle paths.

## 3. Why this objective is selected now

The audited checkout has completed normalized project creation, publication, status, inspect, query, and authored change. It also contains a substantial private normalized compiler, linker, artifact loader, dense VM, canonical reference interpreter, command runner, test runner, and deployment machinery.

The public lifecycle is nevertheless split:

- normalized `new --template minimal` creates Graph 5 authority;
- `new --template command` is deliberately rejected as a predecessor contract;
- released `check`, `build`, and `run` still open predecessor `SemanticWorkspace` authority;
- the maintained standard package and `lkjournal` remain stored as predecessor repositories;
- `src/platform/kernel/contract.rs` and `src/platform/publication/contract.rs` own Graph 5-era contracts while `src/platform/contract/registry.rs` and generated discovery still present Graph 4-era current truth;
- a copied executable cannot create and execute a useful normalized application without crossing into predecessor authority.

This is the current primary bottleneck. Adding more query breadth or authored edits would deepen an authoring surface that still cannot complete a normal application lifecycle. A registry-only correction would merely document the split. A migration-only campaign would leave a temporary second authority without a public payoff. A full service/worker adapter cutover would bundle PostgreSQL, queue, object-storage, and deployment work that the normalized adapter layer does not yet close.

Success removes the most consequential authority seam, makes subsequent package and adapter campaigns operate on one current graph/artifact stack, and converts the private normalized compiler/runtime into a maintained public path.

## 5. Definition of success

The campaign succeeds only when all of the following are simultaneously true.

### 5.1 One current editable authority

- `packages/standard/` and `applications/lkjournal/` contain current Graph 5 repositories and no predecessor `.lkjscript` or manifest authority.
- New command projects contain Graph 5 authority only.
- Released graph-authoring and command-lifecycle operations never open Graph 4 repositories.
- Predecessor repository markers are rejected with one stable diagnostic before mutation or derived-cache work.
- No migration reader, compatibility switch, graph-edition selector, or dual-write path remains in production.

### 5.2 Complete copied-binary command workflow

A copied release binary, executed outside the checkout with a minimal ordinary environment and no Cargo, network, repository-root, or source-file dependency, can:

1. discover its executable contract;
2. create a command project atomically;
3. report status;
4. inspect and query it;
5. apply one reviewed authored change;
6. check its graph-owned tests;
7. build a deterministic artifact to an explicit new output path; and
8. run target `main` and produce the typed result expected by the command recipe.

The command recipe must exercise an exact dependency on the built-in standard package rather than succeeding as a dependency-free toy.

### 5.3 Maintained consumers moved

- The standard package and `lkjournal` open through `GraphRepository`.
- Both compile through the normalized compiler and link through artifact contract 10.
- Their graph-owned tests pass through normalized production/reference equality, or any effectful test is converted to a deterministic replayable test boundary without weakening its assertion.
- Their exact package, target, test, dependency, and public-interface inventories are covered by migration evidence.
- Current normalized artifacts are reproducible from current graph authority.
- The built-in standard material embedded or otherwise owned by the executable is byte-for-byte generated from the maintained standard package and verified by the product profile.

### 5.4 Truthful public contracts

- The executable registry advertises Graph 5-era current contracts and the actual current operation surface.
- `check`, `build`, and `run` use compact bounded responses and normalized request/response models.
- Predecessor-only graph commands are not advertised as current operations.
- Generated contract and operation documentation is regenerated and byte-verified by its executable owner.
- Handwritten current documentation no longer presents Graph 4 as current semantic authority.

### 5.5 Direct cutover and deletion

- Predecessor command bootstrap, public `SemanticWorkspace` lifecycle routing, predecessor lifecycle readers/writers, migrated maintained stores, test-only predecessor project factories, obsolete generated descriptors, and stale current documentation are deleted.
- Private predecessor code remains only when an exact retained consumer or an implementation-disjoint oracle still requires it. Its boundary must be named, non-public where possible, and excluded from current semantic-authority claims.
- `serve` and `worker` may remain only as explicit artifact-runtime operations over a separately named frozen predecessor artifact and deployment descriptors. They must not read a predecessor repository, regenerate that artifact from current authority, or be described as normalized service completion.

### 5.6 Verification and evidence

- Clean, exact-current-cache, and post-publication incremental compilation produce equal normalized artifacts for the same accepted semantic revision.
- Pure command bytecode and canonical reference execution agree.
- Check/build/run do not advance accepted authority.
- Failed, stale, cancelled, exhausted, corrupt, interrupted, or output-conflicting work does not advance authority or publish a partial artifact/cache head.
- Final product and full verification are fresh for the final content, except for explicitly classified environment-unavailable gates.
- The working tree is clean except for clearly identified pre-existing user work.

## 9. Target architecture and behavior

### 9.1 Authority and persistence

A current project root is a Graph 5 repository discovered by `project_discovery`. Accepted meaning consists only of the exact current revision and its immutable object closure exposed through atomic `HEAD`.

The compiler cache remains derived state under its existing repository-owned derived directory. It binds repository ID, exact revision, compiler contract, optimization policy, and manifest digest. It may be deleted and rebuilt. It must never make a corrupt or stale semantic revision appear valid.

Artifacts are immutable external or embedded derived outputs. Their manifest binds the exact repository, root package, semantic revision, semantic state, dependency package revisions, compiler contract, bytecode contract, and artifact closure.

### 9.2 Built-in standard package

Create one typed owner for built-in standard material. It must:

- strictly decode and validate both the package transport and artifact before use;
- expose exact package, semantic revision, package revision, interface, and artifact identities;
- reject internal disagreement at build/test time and at runtime initialization;
- provide no path-based lookup into the checkout;
- be regenerated from `packages/standard/` by first-party Rust tooling or an executable-owned generation command;
- be compared byte-for-byte in product verification;
- support `package builtin inspect` and `package builtin export` without exposing storage internals as authoring input.

Do not introduce a general package registry. The built-in package is one exact first-party dependency.

### 9.3 Command project recipe

The command recipe is executable-owned typed construction, not source text and not a general template language.

It must create:

- a new repository and package identity;
- one application module;
- one private pure command implementation;
- one component and one exact port;
- one root command target named `main`;
- at least one graph-owned test;
- one exact dependency on the built-in standard package;
- an implementation body that calls a public standard declaration and returns a deterministic typed value such as `"hello"`.

The exact declaration names may follow the maintained standard package, but the recipe must bind exact identities after validating the built-in interface. It must not retain name-only runtime references.

Project creation must retain the current safe boundary:

- reject an existing destination, non-directory parent surprise, symlink component, and invalid name before publication;
- build in a private sibling;
- synchronize durable data before the atomic visibility rename;
- remove only its own incomplete private stage after a proved failure;
- never traverse or mutate an unrelated path.

### 9.4 Shared normalized lifecycle preparation

Implement one internal typed path with roughly this dependency direction:

```text
CLI adapter
  -> current project discovery
  -> GraphRepository / exact RepositoryView
  -> exact dependency closure resolution
  -> exact-current cache or clean normalized compilation
  -> strict dependency artifact loading
  -> normalized artifact linking
  -> strict artifact-10 loading
  -> dense NormalizedProgram preparation
  -> check, build publication, or run
```

Do not create separate compiler/linker logic for each command.

The result must expose enough typed observations for compact responses and evidence: repository/package/revision/state, cache profile, compiled/reused/removed units, package count, artifact digest/bytes, object/page work when available, test counts, and execution observations.

### 9.5 Check

`check` must:

- open only current Graph 5 authority;
- validate exact dependency closure;
- compile/link/load through the shared path;
- run all graph-owned tests through normalized VM and canonical reference execution;
- use only deterministic replayable capabilities when a maintained test genuinely requires them;
- return bounded compact records identifying the observed revision and test/differential result;
- leave accepted authority unchanged;
- classify malformed authority, corrupt cache/artifact, missing dependency, capability need, exhaustion, and cancellation distinctly.

### 9.6 Build

`build` must:

- use the same preparation and exact dependency closure as check/run;
- reuse only an exact validated current cache;
- clean-build when no exact cache is available;
- produce artifact contract 10 only;
- publish an explicit output through an owned create-new staged writer;
- reject an existing output, symlink/non-regular-file surprise, invalid parent, interruption, and insufficient resource bound without a partial visible artifact;
- return a compact receipt including exact authority and artifact identities;
- produce identical bytes for equal authority, dependency artifacts, compiler contracts, and options.

Do not make an artifact file or cache head part of semantic revision identity.

### 9.7 Run

`run` must:

- use the same exact prepared program as check/build;
- select an exact root target by the current public name;
- accept the existing strict bounded JSON array argument adapter;
- reject non-command runner kinds;
- reject effectful components with an exact grants-required or unsupported-in-command diagnostic;
- execute a pure command once in the normalized VM and once in the canonical reference interpreter;
- reject any disagreement;
- emit the typed result plus bounded production/reference observations;
- leave accepted authority unchanged.

### 9.8 Incremental derived cache

When `change apply` accepts a revision:

1. complete authority publication first;
2. if an exact base compilation cache was loaded before publication, retain the prepared publication in-process;
3. attempt `build_incremental` against the newly current repository;
4. compare incremental output with clean output in tests and selected evidence;
5. publish the new cache head only through its existing atomic derived-state boundary;
6. on cache failure, remove or ignore incomplete derived state and report semantic acceptance separately from cache status.

Do not fail or roll back an accepted semantic change because derived compilation failed. Do not report a failed change when authority actually advanced. Do not add a persistent compiler-impact log.

### 9.9 Public operation contraction

At cutover, one dispatcher and one executable registry own the current operation set.

Remove predecessor-only operations from discovery and dispatch. Unknown removed names must receive the ordinary stable unknown-operation or usage diagnostic; do not add aliases explaining every historical spelling.

`serve` and `worker` remain separate asynchronous runtime operations. Their descriptors must identify the frozen artifact contract they accept. The registry must not present that retained artifact as the current build artifact or semantic authority.

### 9.10 Resource and error ownership

- `GraphRepository` owns accepted repository opening, locking, immutable-object durability, and atomic `HEAD` visibility.
- The compiler-cache layer owns derived cache staging, exact-revision validation, invalidation, and atomic cache-head publication.
- The shared lifecycle preparation layer owns exact dependency closure, compiler/linker coordination, artifact validation, and preparation observations; it does not own semantic publication.
- The CLI adapter owns argument decoding, compact output metering, exit mapping, explicit external output paths, and cancellation propagation.
- The owned file writer owns private staging, synchronization, create-new publication, and cleanup of only its own stage.
- `NormalizedProgram` and the runner own dense runtime indexes and pure execution; canonical `RepositoryView` remains the independent semantic reader.
- `PreparedDeployment` and host adapters own live runtime resources for `serve`/`worker`; those resources never enter graph identity.

Each boundary must return the repository's typed `Diagnostic` classes and stable codes. Source errors identify invalid user-controlled input, semantic errors identify well-formed but invalid meaning, capability errors identify missing grants, resource/cancelled errors identify bounded termination, corruption identifies inconsistent durable or derived bytes, and infrastructure errors identify host failures. Do not collapse these classes into command-specific strings.

### 9.11 Service artifact isolation

If the empirical audit confirms artifact-only operation:

- retain one exact predecessor service artifact only for the existing `lkjournal` service/worker acceptance workflow;
- move or rename it so it cannot be confused with the current normalized `lkjournal` artifact;

## 10. Migration and direct-cutover design

### 10.1 Temporary migration pipeline

Implement the converter in first-party Rust. It may live under contributor tooling or a narrowly scoped internal module while in use. It must not become a released user migration command.

For each maintained repository:

1. strictly open and validate the predecessor authority;
2. enumerate the complete accepted semantic closure;
3. map identities, types, declarations, members, expressions, components, ports, targets, tests, dependencies, documentation, annotations, and retirements into Graph 5 records;
4. preserve stable predecessor identities when the concept already had exact continuity;
5. allocate identities deterministically only for concepts that had no predecessor identity;
6. replace module-bearing, name-bearing, or alias-bearing semantic references with exact Graph 5 references;
7. build and validate the complete Graph 5 snapshot and witness;
8. publish it through the ordinary Graph 5 repository creation/publication boundary;
9. reopen it from disk;
10. emit an independent migration manifest and compare it with the predecessor manifest.

Do not silently omit or approximate an unsupported construct. Add the smallest normalized representation/compiler correction required by maintained semantics, or classify the assumption as disproved under the scope-control rules.

### 10.2 Migration manifest

Use established vocabulary. A “migration manifest” is a temporary, deterministic, sorted verification projection, not authority.

It must cover at least:

- repository and package continuity mapping;
- module inventory;
- declaration/member kind, visibility, effect, signature, and stable identity;
- canonical type structure;
- expression and binding ownership;
- exact semantic relation inventory;
- component requirements, ports, and targets;
- graph-owned tests and comparison policy;
- exact dependency package/revision/interface bindings;
- public package interface;
- documentation/annotation ownership where present;
- retirement inventory;
- counts and a digest of the canonical projection.

The projection must normalize away generation-specific physical layout and the intentional removal of module locators from exact references. It must not normalize away semantically meaningful differences.

Retain concise final manifests or a structured summary under `docs/evidence/`; keep full raw projections under `.artifacts/campaign/202608270014/`.

### 10.3 Behavioral oracles

Before deleting predecessor stores, compare:

- predecessor and normalized package/interface inventories;
- predecessor and normalized target inventories and runner kinds;
- predecessor graph tests and normalized graph tests;
- old and new pure target results where both tiers can execute the target;
- normalized clean and incremental artifacts;
- normalized VM and canonical reference results;
- the existing service acceptance result against the frozen predecessor service artifact.

A frozen predecessor service artifact proves only retained service behavior. It does not prove the normalized `lkjournal` artifact can serve.

### 10.4 Cutover sequence

1. Capture baseline identities, manifests, test results, artifacts, and service evidence.
2. Complete migration and behavior proof in temporary locations.
3. Complete normalized command-template and lifecycle implementation behind focused tests.
4. Replace maintained standard and `lkjournal` roots with Graph 5 repositories.

6. Isolate the frozen service artifact and update its harness/descriptors.
7. Switch public dispatch and executable registry once.
8. Delete predecessor stores, bootstrap/lifecycle adapters, fixtures, and current documentation.
9. Run predecessor-rejection and no-dual-dispatch searches/tests.
10. Regenerate docs, update evidence, and run final verification.

There must be no committed checkpoint where two maintained editable repositories both claim current authority. Use coherent commits whose intermediate state is testable, but keep migration materialization and authority cutover in one dependency-closed commit if necessary.

### 10.5 Required deletion audit
