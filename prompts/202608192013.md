demanding interactive product is built through that boundary.

## 3. Why the next campaign is necessary

The completed semantic-development campaign solved the largest authority defect: maintained
application meaning no longer lives in a graph-construction script.

It did not prove that the current semantic CLI is sufficient as a daily development environment for
a much larger and more interactive product.

- The successful dogfood feature was small enough to fit three carefully prepared change bundles
- The targeted context was still tens of kilobytes
- The session retains only one context capsule and invalidates aliases after revision change
- Apply returns a complete semantic diff but no exact continuation context
- Local operation references are exact-base-bound but authoring ergonomics and response economy have
  not been measured on long repeated edits
- All project operations conservatively hold one exclusive engine lock, including reads
- Every accepted target is prepared eagerly, which is simple and correct but may become expensive
  for an interactive development loop
- Current text operations are insufficient for a practical editor core without repeated whole-text
  reconstruction
- Current sequences do not provide insertion, removal, slicing, or concatenation
- A durable instance publication for every key event is likely too expensive and semantically
  inappropriate, but no interactive foreground profile exists
- Terminal events, rendering, lifecycle, cancellation, selected filesystem authority, file conflict
  handling, and external modification are absent
- A native product client still needs hand-written boundary code; the reusable shape of an
  interactive product runner is unproven

The next campaign must test these boundaries with one demanding product rather than accumulating
speculative features.

## 8. Terminology

- **meaning graph**: the validated typed graph that owns accepted project meaning.
- **semantic project**: the discoverable project authority containing exact revisions, records,
  targets, and one selected HEAD.
- **proposal document**: editable text that normalizes into a typed semantic change and is never
  authority.
- **semantic explorer**: a bounded exact revision-bound view of meaning-graph structure and history.
- **editor buffer**: application identity for editable content, distinct from file path and semantic
  entity identity.
- **file origin**: an observed deployment locator and exact base facts associated with a buffer.
- **interactive session**: a caller-owned foreground interaction state with explicitly stated
  durability.
- **terminal runner**: native adapter that owns terminal mechanics and invokes application-defined
  update/render semantics.
- **host action**: closed typed request to an authority outside pure application semantics.
- **continuation context**: bounded exact post-operation facts that let a caller continue without
  rediscovering unchanged context.
- **local edit address**: exact-base-bound selector for a function-local item or structural fact,
  not durable identity.
- **unknown visibility**: an outcome where external publication may have occurred and automatic
  retry is unsafe.
- **reconciliation**: independent observation that classifies a prior unknown action.

## 10. Primary architecture hypotheses

These are starting hypotheses, not commands to preserve a losing design.

H1. The meaning graph should remain the sole editable authority, with generated proposal documents
as bounded views.
H2. The current project/session/transaction owners should evolve rather than be wrapped by a
duplicate project layer.
H3. A closed semantic graph query plan with projections and continuations can reduce context better
than a global schema or general query language.
H4. Exact post-apply continuation data can reduce rediscovery enough to justify a new protocol
generation.
H5. Existing exact-base local operation IDs and local edit operations may be sufficient if context
and continuation improve; durable local IDs are probably unnecessary.
H6. Whole-function replacement should remain the correctness oracle.
H7. A pure or hybrid foreground interactive application session is more suitable for key-rate UI
state than publishing a durable instance revision for every event.
H8. A generic native terminal runner can own terminal mechanics while application policy remains in
lkjscript.
H9. A closed frame model is safer than raw ANSI.
H10. A narrow selected-filesystem interface can support a useful explorer and editor without broad
ambient authority.
H11. A semantic-project host interface can reuse the existing public project owner rather than
reimplementing validation.
H12. The first retained product should use one action at a time unless a complete workflow proves
bounded parallel actions are necessary.
H13. UTF-8 text should remain semantically exact bytes, while editor cursor operations may choose
Unicode scalar indices and rendering may use terminal-cell widths.
H14. Persistent text representation should remain unobservable and be selected by complete editor
workloads.
H15. A foreground session and explicit recovery journal may outperform a daemon while preserving
ownership.
H16. A product target may need to grow from application selection into deterministic native runner
packaging, but only if the complete product exposes that gap.

## 12. Frozen complete workflows

Freeze these workflows before redesign so before/after comparisons remain meaningful.

- **A. Small semantic edit**: Rename one private declaration used by one function and inspect exact
  history.
- **B. Local function change**: Change one condition or constant inside an existing `lkjwork`
  function without replacing unrelated body meaning.
- **C. Cross-cutting feature**: Add one new `lkjwork` query or mutation requiring types, functions,
  exports, profile mapping, target cases, native artifact discovery, and product rendering.
- **D. Repeated local maintenance**: Apply 100 deterministic local edits to a large maintained
  application in one foreground session.
- **E. New application bootstrap**: Create the first complete editor-core vertical in a fresh
  semantic project through public CLI operations.
- **F. Interactive event replay**: Initialize the workbench, process 10,000 deterministic input and
  resize events, render frames, and exit.
- **G. Semantic navigation**: Navigate a large project from orientation to one function, callers,
  target impact, history, and diff without a global dump.
- **H. Proposal edit**: Generate a function proposal view, edit, validate, show diagnostics or diff,
  apply, and continue on the new revision.
- **I. Stale draft**: Advance project HEAD externally, attempt the old draft, preserve it, and
  display exact stale facts.
- **J. File workflow**: Select a root, list, open UTF-8 content, edit, save with expected base,
  detect an external change, and resolve deliberately.
- **K. Unknown save**: Inject possible visibility during atomic save and reconcile without duplicate
  publication.
- **L. Target loop**: Apply a semantic change, test affected targets, build product artifact, and
  run one headless scenario.
- **M. Self-hosting change**: Use the resulting development surface to make one real change to the
  workbench application itself.

## 60. Stop and reversal rules

- Stop a context feature if equal tasks do not reduce total calls, total observation bytes,
  correction depth, or elapsed time.
- Stop a local-transform feature if whole-function replacement is simpler and equally successful.
- Stop a source-like view if it becomes a second authority or cannot represent the selected scope
  exactly.
- Stop a persistent context index if ordinary queries meet goals without it.
- Stop concurrent project reads if snapshot lifetime or path substitution cannot be proved.
- Stop selective target validation if it disagrees with the full oracle or saves less than 20
  percent on the complete loop.
- Stop durable-per-key interaction if it misses responsiveness or creates excessive history.
- Stop a foreground-only topology if required external-action recovery cannot be made safe.
- Stop a hybrid checkpoint design if it adds more authority than it recovers.
- Stop a text representation if it does not materially beat flat canonical text on the complete
  editor workload.
- Stop patch rendering if full frames meet goals or patch correctness is fragile.
- Stop background work if sequential operation meets responsiveness.
- Stop a filesystem operation class without a current product action.
- Stop a terminal event variant without a current keymap or interaction consumer.
- Stop a dependency whose complete-workflow benefit does not repay its costs.
- Reopen project storage only at existing or newly measured size/service gates.
- Reopen bytecode or native execution only when interpretation dominates the complete interactive
  workload and a faster tier improves at least 30 percent.
- Reopen a daemon only when a complete multi-client or unattended workflow cannot use foreground
  sessions.
