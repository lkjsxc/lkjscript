# Later Milestone A: Minimal local agent development loop

The following section defines the next intended product vertical. It is not part of the current implementation turn. Its purpose is to prevent vague future
planning and speculative platform work.

## A.1 Product question

A coding agent should be able to answer, with a small number of deterministic local tool calls:

1. What language and package forms are currently supported?
2. How do I create a minimal valid project?
3. How do I check a program without executing effects?
4. What exact diagnostics and semantic blockers prevent compilation?
5. How do I inspect relevant declarations, types, calls, capabilities, and effects?
6. How do I run the program intentionally?
7. How do I verify the observed result?
8. Which limitations are current and explicit?
9. Which output is stable only within one invocation?
10. Which command should I call next after a failure?
The first agent product should answer those questions. It should not attempt to solve collaborative semantic editing.

## A.2 Smallest likely boundary

Begin with the existing local CLI. Prefer one-shot commands. Likely useful commands are:

```text
lkjscript check <entry-or-package>
lkjscript inspect <entry-or-package> ...
lkjscript run <entry-or-package> [--] [program-arguments...]
lkjscript describe --json

```

These names are not pre-decided. Inspect the active CLI and choose a coherent command family. A compile-only command is the highest-priority missing operation.
It must compile or validate without executing program effects. A machine-readable mode must expose structured facts. Do not merely place an opaque compiler
error string inside a JSON field. A human mode may present concise diagnostics. A machine mode should expose exact categories, locations or semantic subjects
where available, blockers, capabilities, and suggested next query or action where deterministic.

## A.3 No false identity persistence

A fresh source import currently creates a fresh workspace namespace. Stable semantic IDs are stable within the snapshot lineage. They are not automatically
stable across separate CLI invocations that independently reimport text. Do not expose one-shot IDs as if they were persistent project identities. Machine
output must label their scope. Possible honest choices include:

- invocation-local identities;
- a single command that performs import and all requested queries;
- a one-shot batch document with local cross-references; or
- a later long-lived process once measured need justifies it.
Do not add persistence merely to make IDs look stable.

## A.4 Check command

A future `check` command should:

- accept the active file or package input;
- verify package state where required;
- import source exactly once;
- run completeness and compilation validation;
- never execute program effects;
- report success deterministically;
- report failure with a stable exit policy;
- keep stdout and stderr roles explicit;
- support machine-readable output;
- preserve exact host and resource failure distinction;
- avoid native execution;
- avoid hidden writes except those explicitly required by package verification; and
- be covered by end-to-end CLI tests.
Do not implement this command by running the program and suppressing output. Do not use `run` as check. Do not invoke a host effect.

## A.5 Inspect command

A future inspection surface should be driven by concrete agent questions. Start with a small useful set, such as:

- summary;
- declarations;
- one declaration;
- signature;
- references;
- callers;
- callees;
- diagnostics;
- blockers;
- hole context;
- node type;
- call instantiation;
- required capabilities; and
- concise deterministic projection.
Do not expose every internal Rust field. Do not serialize private dense IDs. Do not build a general query language. Do not build GraphQL. Do not build SQL over
semantic state. Do not build a plugin query registry. Use existing workspace queries. Add a new public query only when a concrete agent question cannot be
answered.

## A.6 Machine output

Machine output should use a real structured model. Use an established serializer if the boundary justifies it. Do not hand-build JSON with incomplete escaping.
Do not add `serde` to every compiler type. Define a narrow CLI result model. The result should distinguish:

- success;
- incomplete semantic state;
- invalid source;
- invalid package;
- compiler semantic failure;
- host failure;
- resource exhaustion;
- cancellation where applicable; and
- CLI usage failure.
Use deterministic ordering. Use explicit null or absence semantics. Do not use measured zero for missing metrics. Do not include nondeterministic paths or
timings by default. Make timings opt-in. Do not promise schema compatibility yet. Backward compatibility is not required. Still keep one current schema rather
than ad hoc command-specific prose.

## A.8 Agent acceptance workload

Define a representative local coding-agent workload without embedding model inference in tests. For example:

1. initialize or copy a minimal example;
2. make a small semantic change;
3. run `check`;
4. inspect one diagnostic;
5. correct the program;
6. run `check` successfully;
7. run the program;
8. assert its output;
9. inspect required capabilities; and
10. rerun from a clean process.
The test harness should act like a consumer. It should parse machine output. Do not validate JSON by substring matching. Measure tool-call count manually or
structurally. Do not call a remote model from CI.

## A.9 Evidence gate for a long-lived process

- parsing;
- semantic import;
- query latency;
- check latency;
- retained memory;
- repeated edit count;
- expected workspace lifetime;
- cancellation behavior; and
- process crash behavior.

- one present consumer;

- malformed-request handling;
- failure atomicity;
- namespace and snapshot lifetime;
- capability isolation;
- shutdown behavior;
- version posture; and
- deletion condition.
Do not call it a daemon merely because stdin remains open. Do not add network listening by default.
