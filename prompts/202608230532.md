## Graph 5 root

Use a small fixed root manifest.

The preferred logical shape is:

```rust
pub struct SemanticRoot {
    pub graph_contract_version: u32,
    pub repository_id: RepositoryId,
    pub package_id: PackageId,
    pub package_name: Name,
    pub owners: MapRoot,
    pub dependencies: MapRoot,
    pub retirements: MapRoot,
}
```

This is conceptual.

Add a root field only when it is canonical meaning or required to reach canonical meaning.

Do not add derived name, relation, summary, test, query, or compiler roots to the semantic root.

Those belong to validation witness or disposable derived manifests.

Targets, documentation, annotations, modules, declarations, members, bindings, and expressions
should be stable-ID owner records in the owner map.

A root with a small number of generic maps is preferable to a root with one map per Rust enum
variant.

Measure key locality before finalizing key encoding.

## Owner map

Use a tagged typed owner key.

A conceptual key is:

```text
owner-domain-tag || stable-id-bytes
```

The key must sort deterministically.

The map value should be a compact content digest and minimal closed metadata only if the metadata is
needed to decode the object safely.

Prefer:

```rust
pub struct OwnerBinding {
    pub kind: OwnerKind,
    pub object: OwnerObjectDigest,
}
```

Do not duplicate mutable name, parent, and payload in both the map value and owner object.

An owner object includes its stable ID and kind for independent integrity validation.

Changing one owner creates one new owner object and path-copies the owner map.

Large owner payloads reference chunked objects.

Do not depend on a shell protocol.

Do not use terminal control sequences.

## Framing

Use one canonical JSON object per UTF-8 line.

Reject:

- invalid UTF-8;
- blank frames unless explicitly allowed as keepalive;
- trailing bytes after one JSON object;
- duplicate keys;
- unknown fields;
- frames above the advertised byte maximum;
- request IDs outside the closed request-ID grammar.

Never write logs, progress bars, or diagnostics to stdout outside protocol frames.

Stderr may contain bounded host diagnostics only when protocol startup fails before a valid session
exists.

After session establishment, every recoverable result belongs to a stdout response frame.

## Handshake

The client sends a `hello` request containing:

- protocol contract version;
- client identity string;
- optional known registry digest;
- optional known schema digests;
- requested optional features;
- requested maximum response bytes;
- requested maximum retained session bytes;
- requested heartbeat policy.

The server returns:

- protocol version;
- executable version and build identity;
- graph contract;
- change contract;
- query contract;
- artifact contract;
- registry digest;
- missing schema handles;
- supported optional features;
- negotiated response bound;
- negotiated session-memory bound;
- process identity;
- platform claims that are actually verified;
- explicit nonclaims.

Do not send all schemas when the client already knows their digest.

A known registry digest should produce a compact unchanged result.

A partial schema miss should return only requested or unknown schema entries.

## Request envelope

Every request after handshake contains:

- `request_id`;
- `operation`;
- `arguments`;
- optional `repository_handle`;
- optional `revision`;
- optional `deadline_milliseconds`;
- optional `budget`;
- optional `projection`;
- optional `idempotency_key`.

The registry owns the exact schema for each operation.

Unknown operations reject without changing session state.

Unknown fields reject.

A duplicate live `request_id` rejects.

A completed request ID may be reused only after an explicit release or after a contract-defined
bounded retention period.

## Response envelope

Every response contains:

- `request_id`;
- `status`;
- `operation`;
- `result` or `diagnostics`;
- consumed work;
- output bytes;
- exact revision observed when applicable;
- optional result handle;
- optional expansion operations;
- optional session resource summary.

Distinguish:

- success;
- no_change;
- stale_revision;
- precondition_failed;
- ambiguous;
- conflicted;
- invalid_meaning;
- resource_exhausted;
- cancelled;
- deadline_exceeded;
- corrupt_authority;
- infrastructure_failure;
- protocol_error.

Do not collapse these into one generic failure.

## Repository handles

`repository.open` accepts an explicit path.

It returns a short opaque session-local handle.

The handle binds:

- canonicalized path;
- repository identity;
- exact HEAD observed at open;
- store contract;
- relevant filesystem identity;
- open generation.

The handle does not pin HEAD automatically.

The server must recheck current HEAD before every operation whose semantics depend on HEAD.

A handle may cache immutable metadata and disposable indexes.

A repository move, replacement, identity change, or store replacement invalidates the handle.

`repository.close` releases the handle and all dependent ephemeral handles unless independently
retained by contract.

The protocol must cap simultaneously open repositories.

## Revision pins

A read request either names an exact revision or explicitly requests current HEAD.

The response always reports the exact revision observed.

A change preparation names an exact base.

A commit names the prepared handle and exact expected current base.

The protocol must never silently advance a prepared change to a newer revision.

An explicit rebase operation may recompute against a newer base and returns a new prepared handle.

## Short semantic handles

The session may map verbose stable IDs to short handles such as `o1`, `o2`, and `e7`.

A short handle binds:

- exact repository;
- exact revision;
- stable identity domain;
- stable identity;
- projection generation.

Short handles are never serialized into accepted meaning.

They cannot be used across sessions.

A response that introduces a short handle also returns the full stable ID at least once unless the
client has already acknowledged the mapping.

A handle must reject after its bound revision or repository is no longer the request context.

Do not let the same textual handle refer to different owners concurrently.

## Schema handles

Registry and nested schema documents may receive content-addressed handles.

A client can request:

- schema summary;
- exact schema by handle;
- schema diff from a known digest;
- examples for one operation;
- enum values for one field.

This should avoid transferring a complete schema catalog to every model turn.

Schema handles are executable-derived, not repository authority.

## Context handles

`context.create` accepts:

- exact revision;
- exact seed owners or query selectors;
- context profile;
- item, byte, depth, and fanout budgets;
- projection;
- optional exclusion handles.

It returns:

- context handle;
- digest;
- owner summaries;
- inclusion reasons;
- omitted-count summary;
- work consumed;
- exact expansion operations.

`context.expand` requests bodies or relation details for selected items.

`context.diff` compares two handles and returns only added, removed, and changed items.

When a local edit changes a small slice, a client should be able to request a context delta rather
than retransmitting the entire previous context.

A context handle cannot be used as a write base.

## Prepared change handles

`change.prepare` performs:

- strict decoding;
- selector resolution;
- deterministic ID allocation;
- precondition evaluation;
- overlay construction;
- canonical delta derivation;
- relation and witness delta derivation;
- impact planning;
- incremental validation;
- affected-test selection;
- optional selected test execution;
- incremental compilation planning;
- exact result-root prediction.

It returns a prepared handle plus compact evidence.

The prepared handle binds every semantic and operational input needed for publication.

At minimum it binds:

- repository identity;
- exact base revision;
- exact base root;
- normalized change digest;
- canonical delta digest;
- result root;
- validator contract;
- witness roots;
- selected tests and outcomes;
- compiler-plan digest;
- resource consumption;
- expiration generation.

The handle may refer to in-memory prepared data or a private temporary stage.

It is not accepted authority.

## Commit protocol

`change.commit` takes one prepared handle and optional idempotency identity.

Under the publication lock it must:

1. reread exact HEAD;
2. reject a stale base;
3. verify the prepared handle integrity and generation;
4. verify staged immutable object digests;
5. make required immutable data durable;
6. write revision and receipt;
7. publish HEAD once;
8. return exact accepted identities.

Do not repeat semantic validation merely because commit is a separate request.

Do recheck all authority and integrity facts that protect against stale or tampered preparation.

A client disconnect during commit must not cancel after the non-cancellable visibility boundary
begins.

The next session must reconcile uncertain completion through HEAD and receipt lookup.

## Publication reconciliation

Provide `change.reconcile`.

It accepts:

- repository;
- transaction digest or idempotency key;
- expected base;
- optional predicted result revision.

It returns:

- not_started;
- accepted;
- semantic_no_change;
- stale;
- conflicting_idempotency;
- indeterminate_corruption.

This is the safe recovery path after transport loss.

Do not advise blind retry.

## Cancellation

Support an explicit `cancel` operation naming a live request ID.

Cancellation is cooperative.

Every long derived traversal must have bounded cancellation checkpoints.

Cancellation before publication visibility returns cancelled and publishes nothing.

Cancellation cannot interrupt the atomic visibility sequence in a way that leaves ambiguous partial
authority.

A commit that has entered its non-cancellable phase reports that cancellation was deferred and
finishes reconciliation.

## Deadlines

A deadline is a request policy, not part of program meaning.

Reject impossible or negative deadlines.

Check deadlines before expensive allocation and at traversal checkpoints.

Return consumed work and the safest narrower retry.

Do not use a deadline to skip required validation and still publish.

## Backpressure

Process a bounded number of concurrent requests.

The first implementation may process one request at a time except explicit cancellation.

If concurrency is introduced, define:

- maximum live requests;
- fair scheduling;
- per-request memory;
- total session memory;
- publication serialization;
- response ordering;
- cancellation ownership.

Never spawn an unbounded task per input line.

Never buffer unbounded input while a request runs.

Use bounded channels or direct read scheduling.

## Session memory accounting

Account at least:

- open repository metadata;
- decoded registry and schemas;
- query indexes;
- owner records;
- relation pages;
- context handles;
- prepared changes;
- compiler units;
- output buffers;
- temporary stages.

Expose current and peak retained bytes when measurable.

Evict only disposable entries.

Never evict a prepared publication stage without returning an explicit expired-handle outcome.

Use deterministic or documented eviction order.

## Handle lifetime

Each handle class defines:

- owner;
- maximum count;
- maximum bytes;
- expiration;
- explicit release;
- cascade behavior;
- stale behavior;
- diagnostics.

Provide `handle.release`.

Provide `session.status` with counts and bytes by handle class.

Provide `session.compact` to release unused disposable caches without affecting authority.

Do not rely solely on process memory pressure from the host.

## Progress

Do not stream noisy progress by default.

A request may opt into bounded progress frames.

Progress frames contain:

- request ID;
- phase identifier from the registry;
- monotonic completed work;
- current bound if known;
- elapsed time;
- no secret data.

Progress is not evidence of success.

A dropped progress frame must not affect operation semantics.

## Event ordering

For one request ID, frames are strictly ordered.

A final response is emitted exactly once.

For different request IDs, either serialize all responses or include an explicit sequence field.

Document the policy in the registry.

Do not make clients infer completion from connection closure.

## Session shutdown

`session.shutdown` stops admission, cancels cancellable requests, finishes non-cancellable
publication, releases handles, removes private temporary stages that are proven unreferenced, and
returns one final receipt.

EOF should perform the same safe shutdown without requiring a final command.

A crash may leave private stages.

Startup repair must classify and safely remove or recover owned stages based on integrity and
publication evidence.

## Stateless equivalence

For every stateful operation, retain an equivalent stateless public command or a composition of
stateless commands.

Compare equal workflows:

- create;
- orient;
- query;
- edit;
- validate;
- commit;
- check;
- build;
- run;
- backup.

Stateful and stateless paths must produce equal accepted revisions and equal deterministic
artifacts.

Session-only handles may differ.

## Agent-protocol acceptance

Create a black-box harness that starts a copied release executable in an empty temporary directory.

The harness must:

1. negotiate a schema digest;
2. create a command project;
3. open it;
4. request compact orientation;
5. resolve the entry function;
6. prepare and commit a body edit;
7. receive a context delta;
8. rename the function;
9. move it to a new module without changing its stable declaration ID;
10. add a test;
11. run selected tests;
12. build;
13. close and reopen the process;
14. inspect the same accepted revision;
15. reconcile the last transaction;
16. back up and restore;
17. run the restored target.

Assert bounded frame size and no nonprotocol stdout.

## Agent-economy evidence

Measure one equal end-to-end development workflow in:

- standalone process-per-command mode;
- one resident session;
- resident session with known registry digest;
- resident session with context-handle deltas.

Record:

- process starts;
- request frames;
- input bytes;
- output bytes;
- elapsed time;
- peak RSS;
- repeated schema bytes;
- repeated context bytes;
- correction count;
- provider token and monetary data only when the external harness exposes it.

Do not infer token savings from byte savings.

Retain the session only if the complete workflow materially improves and its correctness cost is
acceptable.

# Phase 7: Drafts, diff, merge, and persistent typed conflicts

## Draft contract cutover

Replace the predecessor draft contract together with Graph Contract 5.

Do not teach the current draft format to read Graph Contract 5.

A draft is one explicit non-executable overlay authority.

It is not a miniature accepted repository.

It is not a source branch encoded as text.

It is not a bag of transaction JSON with ambiguous cumulative meaning.

## Draft record

The current draft record should bind:

- draft ID;
- repository identity;
- exact base revision;
- draft generation;
- normalized pending change sequence;
- current canonical overlay delta;
- allocated request-local identities;
- holes;
- typed conflicts;
- diagnostics;
- bounded nonsemantic intent;
- created and updated operational metadata where useful;
- contract digests.

Do not copy the complete base graph into the draft.

Do not copy unchanged owner records.

A draft should be reconstructible from exact base plus normalized changes or an equivalent exact
overlay object.

## Draft operations

Support:

- create;
- inspect;
- append change;
- replace pending change;
- remove pending change;
- validate;
- query overlay;
- context overlay;
- rebase;
- list conflicts;
- inspect conflict;
- resolve conflict;
- publish;
- drop.

Every draft mutation increments an exact generation.

Every request names the expected generation.

Stale draft generation rejects.

Draft mutation publishes no accepted revision.

## Draft overlay reads

Queries against a draft observe:

- exact base revision;
- exact draft generation;
- overlay result;
- holes and conflicts;
- whether the requested projection is executable.

A draft query should use the same overlay map and relation derivation engine as change preparation.

Do not materialize a second query implementation.

Return owner origin:

- unchanged base;
- modified;
- created;
- retired;
- conflicted;
- hole-dependent.

## Holes

A hole is typed.

It identifies:

- hole ID;
- owning semantic record;
- expected semantic category;
- expected type when applicable;
- scope;
- constraints;
- creation reason;
- candidate query operation.

Do not represent holes as null values in canonical record fields.

Do not allow holes into accepted Graph Contract 5 authority.

A hole may exist in a draft expression, type, reference, target, capability binding, or other
authoring form only through an explicit draft-only representation.

## Conflict model

A conflict is a stable draft-owned identity.

It contains:

- conflict ID;
- conflict kind;
- base semantic state or digest;
- left semantic state or digest;
- right semantic state or digest;
- affected stable owner IDs;
- dependency paths;
- automatic-resolution candidates;
- resolution schema;
- status.

Keep conflict payload bounded.

Large alternative bodies live in referenced draft objects or expandable handles.

Do not embed unstructured source markers.

Do not encode the complete conflict only in prose.

## Conflict kinds

At minimum distinguish:

- create/create identity collision;
- create/create namespace collision;
- retire/modify;
- move/move;
- move/retire;
- rename/rename;
- signature/signature;
- body/body;
- member/member;
- ordered-child conflict;
- reference/rebind;
- dependency/dependency;
- target/target;
- documentation/documentation;
- semantic invalidation introduced by otherwise disjoint edits;
- foreign or missing base owner.

Do not force unrelated kinds into one generic owner conflict when the resolution grammar differs.

## Semantic diff

Define diff over stable owner records and derived semantic relations.

A diff reports semantic state changes, not storage-page changes.

For each owner distinguish:

- created;
- retired;
- moved;
- renamed;
- signature changed;
- implementation changed;
- metadata changed;
- child order changed;
- relation set changed;
- unchanged.

A declaration move must appear as move, not delete plus create.

An expression subtree replacement should report the selected semantic region and new descendants
without dumping all nodes by default.

## Diff identity

A semantic diff digest binds:

- exact before revision or root;
- exact after revision or root;
- diff contract;
- normalized change facts.

Do not hash a human rendering as the authoritative diff identity.

The diff implementation may use Merkle subtree equality to skip unchanged maps.

Report skipped subtrees and visited records.

## Diff pagination

Default diff output is compact.

Return counts by class and the highest-value owners.

Provide continuation and field projection.

Allow explicit expansion of one owner or change path.

Do not inline every new expression node for a large body replacement.

## Three-way merge basis

Merge exact base, left, and right accepted revisions or exact draft states.

Use persistent-map three-way comparison to skip equal subtrees.

For one key:

- unchanged/unchanged keeps base;
- changed/unchanged keeps changed;
- unchanged/changed keeps changed;
- equal changes keep the equal result;
- disjoint fields may combine if the record merge contract proves independence;
- incompatible changes create a typed conflict.

Do not use name matching to infer identity.

Do not use content similarity to silently pair distinct created stable IDs.

## Record-specific merge

Define field-level merge rules for each owner-record kind.

Examples:

Module record:

- namespace-parent change is move;
- name change is rename;
- two equal renames merge;
- different renames conflict;
- documentation changes may merge separately.

Function record:

- type parameters;
- parameters;
- result type;
- effect;
- body root;
- attributes.

A body-only change may merge with a disjoint documentation change.

Two body-root changes conflict unless an expression-level merge succeeds.

Record declaration:

- field child sets merge by stable field ID;
- independent field additions merge;
- add and rename of another field merge;
- two additions with same display name but distinct IDs create a namespace/member-name conflict;
- incompatible order changes create an ordered-child conflict.

Variant declaration follows analogous case rules.

Interface declaration follows operation rules.

Component declaration follows requirement and port rules.

## Expression-level merge

Expression merge is optional only if owner-level conflict persistence remains complete.

Implement expression-level merge when stable expression IDs make it exact.

Rules should include:

- unchanged child versus changed child;
- changes to different child slots;
- independent binding additions when order semantics allow;
- equal replacement;
- retirement versus modification;
- operation-kind replacement.

Never merge child lists merely by numeric position after both sides reordered them.

Use stable child IDs and explicit order facts.

If exact expression merge is not safe, create one body conflict.

## Namespace merge

Namespace conflicts are derived from the merged candidate.

Two unrelated stable owners may independently choose the same `(namespace, kind, name)`.

That is a typed namespace conflict even when their owner records merge independently.

Do not resolve by arbitrary suffixing.

Offer candidate operations such as:

- rename left;
- rename right;
- move left;
- move right;
- retire one;
- keep both after explicit namespace redesign.

## Relation and validation conflicts

After record-level merge, derive relation and validation deltas.

A graph may be structurally merged but semantically invalid.

Convert merge-introduced issues into typed conflicts or diagnostics bound to exact owners.

Examples:

- a retained caller points to a retired declaration;
- a type argument no longer satisfies an explicit arity;
- a target points to a retired port;
- a capability invocation points to a removed operation;
- a record construction omits a newly required field;
- an exhaustive match misses a new case.

Do not publish an invalid merged graph.

## Merge result

A conflict-free valid merge may publish directly with two exact parents.

A conflicted result creates or updates a draft.

The result reports:

- merge base;
- left and right revisions;
- merged clean owner count;
- conflict counts by kind;
- validation diagnostics;
- draft ID and generation;
- bounded next operations.

Accepted HEAD remains unchanged until explicit conflict-free publication.

## Conflict resolution operations

Resolution is a normalized semantic change.

Support:

- choose base;
- choose left;
- choose right;
- choose exact owner state;
- apply a typed replacement;
- rename;
- move;
- rebind;
- retire;
- preserve both with explicit new identity where semantically valid;
- manually compose an expression or type through normal change forms.

A resolution names exact conflict ID and expected draft generation.

A resolution may create new conflicts; return the new exact set.

Resolved conflicts are retained in draft history only as bounded audit evidence, not accepted
meaning.

## Rebase

Rebase one draft from old base to new accepted HEAD.

Compute:

1. semantic diff from old base to draft overlay;
2. semantic diff from old base to new base;
3. three-way merge;
4. normalized new overlay;
5. new conflicts;
6. new draft generation.

Do not replay name-based commands blindly.

Stable IDs and normalized changes must drive rebase.

If a referenced owner was retired in the new base, produce a typed conflict.

## Publish

Draft publication requires:

- exact repository;
- exact current base;
- exact draft generation;
- no holes;
- no unresolved conflicts;
- valid overlay;
- selected tests passed under current contracts;
- result witness;
- explicit commit.

Publication reuses the generic prepared-change path.

Do not implement a separate draft publisher with different validation rules.

## Diff and merge oracles

Keep a straightforward full-map diff oracle for tests.

Keep a straightforward record-level three-way merge oracle.

Compare optimized Merkle-skipping implementations against them over randomized histories.

Generate branches containing:

- rename;
- move;
- body replacement;
- signature change;
- member addition;
- member removal;
- rebind;
- dependency change;
- target change;
- documentation change;
- retire and restore.

Shrink mismatches to a minimal branch history.

## Draft and merge black-box acceptance

Using only the public CLI and copied binary:

1. create a project;
2. create a draft;
3. append a valid body edit;
4. inspect overlay execution status;
5. create an accepted competing rename;
6. rebase the draft;
7. inspect a clean rename/body merge;
8. create competing body edits;
9. merge them;
10. observe a persistent typed body conflict;
11. close and reopen the process;
12. inspect the same conflict;
13. resolve with an exact replacement;
14. validate;
15. publish;
16. verify two-parent or rebased history as applicable;
17. build and run.

Assert that no conflict enters accepted HEAD.

## Deletion

After Graph Contract 5 draft cutover, delete:

- predecessor draft decoder;
- predecessor transaction-list draft representation;
- source-shaped conflict renderers;
- compatibility conflict kinds;
- duplicate merge-only graph builders;
- tests that depend on Graph Contract 4 record shape.

Retain historical evidence only as labeled historical data.

# Phase 8: Incremental compiler units, artifacts, and runtime adaptation

## Compiler boundary

The compiler consumes validated Graph Contract 5 records and exact validation witnesses.

It must not reconstruct the predecessor recursive module AST as its normal input.

A temporary compatibility-shaped in-memory view is allowed only during the direct migration and
must be deleted before campaign completion.

The compiler input API should request exact semantic owners and derived facts through a narrow
read-only interface.

## Compilation unit

Make one declaration the default compilation unit.

A compilation-unit key binds:

- compiler contract;
- graph contract;
- exact declaration stable ID;
- declaration semantic digest;
- relevant type-object digests;
- relevant expression-object digests;
- direct semantic dependency summary digests;
- effect and capability contract;
- optimization policy;
- target-independent or target-specific policy as applicable.

Do not key solely by accepted revision.

An unchanged declaration with unchanged semantic dependencies should reuse across revisions.

Do not reuse when a relevant dependency summary changes even if the declaration bytes do not.

## Unit classes

Distinguish at least:

- pure function;
- task function;
- constant initializer;
- test;
- component/port adapter;
- type layout metadata;
- interface/capability metadata;
- target entry.

Do not force nonexecutable declarations into fake function bytecode.

## Dense lowering

After validation, lower stable graph IDs to compact dense indexes for hot execution.

The dense layout may include:

- function index;
- type index;
- field offset;
- case tag;
- operation index;
- local slot;
- constant index;
- string-pool index.

Stable IDs remain in debug or observation maps only where needed.

Do not carry 128-bit textual identities through each hot instruction.

Do not use mutable display names for runtime dispatch.

## Bytecode contract

Define a new bytecode contract together with Graph Contract 5.

Use typed numeric references.

Examples:

- `LoadLocal(LocalIndex)`;
- `Call(FunctionIndex, Arity)`;
- `ConstructRecord(TypeIndex, LayoutIndex)`;
- `ReadField(FieldOffset)`;
- `ConstructVariant(TypeIndex, CaseTag)`;
- `SwitchVariant(JumpTableIndex)`;
- `Perform(RequirementIndex, OperationIndex, Arity)`;
- `BeginTransaction(RequirementIndex, BindingSlot)`.

Names may remain in bounded debug tables.

Do not encode field names, variant-case strings, capability aliases, or operation names in the hot
instruction stream.

## Bytecode representation prototype

Measure at least:

- enum-based Rust instruction vector;
- compact fixed-header bytecode with side tables;
- variable-length encoded instruction stream.

Compare:

- compile time;
- decode time;
- dispatch time;
- memory;
- artifact bytes;
- corruption handling;
- implementation complexity.

Select based on complete maintained workloads.

Do not optimize instruction density before eliminating string dispatch and full recompilation.

## Compiler output

A compiled unit contains:

- exact unit key;
- typed bytecode or prepared metadata;
- constant pool;
- dense-reference relocation table;
- capability requirements;
- debug semantic map;
- verifier result;
- checksum.

It is derived and rebuildable.

Reject malformed unit bytes before allocation.

## Unit store

Store compiled units through the generic derived object store.

Use content addressing.

A revision-bound compilation manifest maps exact semantic unit IDs to unit digests and target
metadata.

Delta-update the manifest for affected units.

A missing or corrupt unit rebuilds.

A rebuilt unit that differs from deterministic clean compilation is a compiler defect.

## Compilation planner

The same impact engine that selects validation work selects compilation invalidation.

Classify changes:

- no compiler effect;
- implementation only;
- signature;
- layout;
- effect/capability;
- target/deployment metadata;
- compiler-contract change.

Examples:

- documentation-only change should not recompile;
- function-body change recompiles that function and any specialization depending on body semantics;
- public signature change recompiles direct callers and dependent type checks;
- record layout change recompiles constructors and field users;
- variant case change recompiles constructors and matches;
- component requirement change recompiles component preparation and affected targets.

Do not maintain a second hand-coded dependency graph.

## Incremental build

`build` should:

1. open exact revision;
2. load or rebuild validation witness;
3. compute required executable closure from targets;
4. load reusable units by exact keys;
5. compile missing or invalid units;
6. link deterministic package artifact;
7. compare or optionally audit against clean compilation;
8. atomically publish external output.

Return:

- revision;
- target closure;
- units reused;
- units compiled;
- semantic records read;
- bytes read and written;
- artifact digest;
- deterministic publication status;
- expansion handle.

## Clean build oracle

Retain a clean compiler path that ignores compiled-unit caches.

For deterministic test fixtures, incremental and clean artifacts must be byte-identical.

Do not accept semantic equivalence alone if artifact determinism is part of the contract.

Run clean comparison probabilistically during development and always in authoritative focused
campaign evidence for affected compiler work.

## Artifact redesign

Replace package artifacts that embed one complete logical `GraphRoot` plus `Vec<MeaningModule>`.

The Graph Contract 5 artifact should contain a deterministic executable closure.

A package artifact may bind:

- package identity;
- accepted revision;
- semantic root;
- semantic certificate;
- exact dependency artifact digests;
- selected targets;
- compiled-unit objects;
- type/layout tables;
- constants and string pools;
- requirement metadata;
- bounded debug semantic map;
- receipt.

Do not include unrelated repository history.

Do not include drafts.

Do not include deployment grants, secrets, live resources, query indexes, or compiler cache metadata
not needed for execution.

## Artifact object graph

Use independently integrity-checked immutable objects.

The bundle manifest names exact object digests.

Support streaming or segmented transport so one package closure is not constrained by one
monolithic in-memory buffer.

Keep a strict hostile decoder.

Reject:

- duplicate objects;
- unreachable objects;
- missing objects;
- digest mismatch;
- cyclic object references where forbidden;
- contract mismatch;
- trailing data;
- excessive object counts or bytes before bounded allocation.

## Artifact determinism

Artifact identity must not depend on:

- filesystem enumeration order;
- hash-map order;
- process ID;
- time;
- absolute paths;
- cache hit order;
- pack physical offsets;
- session handles;
- display formatting.

Canonicalize manifest and object ordering.

Test equal artifact bytes across:

- clean build;
- incremental build;
- process restart;
- repository copy;
- pack compaction;
- query-index loss;
- different allowed worker counts.

## Dependency artifacts

Accepted dependency bindings remain exact.

The compiler loads exact semantic/executable metadata from the bound dependency artifact.

Do not resolve by mutable name or ambient path.

Do not force every local query to load complete dependency executable bytes.

Separate inspectable semantic interface data from heavy executable implementation objects where
measurement justifies it.

## Specialization

Do not implement unconstrained specialization during the Graph Contract 5 storage cutover.

First create exact generic unit keys and clean/incremental equivalence.

# Phase 10: Backup, restore, retention, packing, compaction, and garbage collection

## Storage problem to solve

The retained 10,000-module checkpoint shows that canonical logical work is increasingly local while
backup remains dominated by per-object filesystem operations.

Treat this as a physical-layout defect until measurements disprove it.

Do not optimize backup by weakening integrity or omitting reachable authority.

## Reachability model

Define one canonical reachability engine used by:

- backup;
- deep doctor;
- retention preview;
- compaction;
- garbage collection;
- restore verification;
- artifact closure enumeration where applicable.

The engine begins from explicit roots.

Canonical repository roots include:

- current HEAD;
- retained revision pins;
- live draft bases and draft objects;
- active reader leases;
- registered backup roots;
- explicitly retained historical revisions;
- publication-recovery stages proven live.

Derived caches are not canonical roots.

Do not let each maintenance feature invent a different reachability policy.

## Streaming reachability

The reachability engine must not retain one in-memory set proportional to all objects by default.

Prototype bounded approaches:

- external sorted runs;
- partitioned digest sets;
- disk-backed exact set;
- mark bitmap over a verified pack catalog;
- Merkle range traversal with deduplication;
- hybrid in-memory frontier plus spill.

The algorithm must remain exact.

A probabilistic filter may reduce disk lookups but may not authorize deletion or omission.

## Reachability receipt

Return:

- root set digest;
- object counts by class;
- logical bytes;
- physical bytes;
- duplicate references skipped;
- maximum frontier;
- spill bytes;
- elapsed time;
- corruption diagnostics;
- exact policy contract.

This receipt is evidence, not program authority.

## Backup contract

Design a new segmented backup contract for Graph Contract 5.

A backup manifest binds:

- backup contract;
- repository identity;
- exact selected revision;
- root-set policy;
- exact canonical root objects;
- ordered segment descriptors;
- per-segment digest;
- total entries and bytes;
- draft inclusion policy;
- dependency artifact policy;
- required store contracts.

Backup segments contain bounded canonical entries.

No segment should require allocating its declared total before bounds validation.

## Backup write path

The backup pipeline should:

1. acquire an exact source snapshot or reader lease;
2. enumerate exact reachability;
3. stream entries in canonical order;
4. read object bytes through the generic store;
5. verify each digest;
6. write bounded segments;
7. make each segment durable;
8. write the final manifest last;
9. atomically publish the backup destination;
10. release the lease.

A partially written backup without final manifest is not valid.

Do not hold the repository publication lock during the complete payload copy.

Use exact revision pinning or leases instead.

## Backup output forms

Support a directory bundle first if it simplifies bounded segments and atomic manifest publication.

Support a single-file container only if it preserves streaming and corruption isolation.

Do not force all backup bytes through one `Vec<u8>`.

The public output path must be explicit.

Do not overwrite an existing backup silently.

## Pack-aware backup

When canonical objects already live in packs, backup may copy complete immutable pack ranges only if
the manifest proves every included object and no omitted required object.

Otherwise stream logical objects.

Measure:

- object-by-object read;
- pack-range copy;
- repacked backup segments.

Select by complete backup and restore performance.

Do not make physical pack identity part of semantic backup identity unless the contract explicitly
chooses physical preservation.

## Restore

Restore into a private destination stage.

It must:

1. strictly decode manifest and segment descriptors;
2. verify segment digests;
3. stream entries with bounded allocation;
4. reject duplicates and foreign contracts;
5. write immutable objects through the target store;
6. reconstruct exact root and revision bindings;
7. verify complete reachability;
8. rebuild validation witness independently;
9. compare semantic certificate;
10. run deep structural doctor;
11. optionally run selected maintained acceptance;
12. publish destination atomically.

Do not make a destination visible before verification.

Restore must not trust derived indexes from backup.

Prefer excluding them.

## Restore equality

An exact backup/restore must preserve:

- repository ID;
- selected accepted revision;
- revision record;
- semantic root;
- transaction and receipt identities;
- exact canonical owner bytes;
- exact dependency bindings;
- exact draft authority included by policy.

Pack layout may differ.

Query indexes, validation-witness pages, and compiler units may rebuild unless committed as required
witness inputs.

The rebuilt semantic certificate must equal the accepted revision certificate.

## Revision pins

A pin contains:

- pin ID;
- repository;
- exact revision;
- purpose;
- creation metadata;
- optional expiry policy;
- owner;
- integrity record.

## Reader leases

A lease binds:

- lease ID;
- exact revision or object-root set;
- process/session owner;
- created generation;
- heartbeat or bounded expiry;
- recovery rule.

- retain draft bases;

# Risk register

## Risk: Graph Contract 5 becomes a verbose database schema

Mitigation:

- keep owner records semantic;
- keep physical records private;
- expose high-level change grammar;

## Risk: Over-normalization destroys locality

- logical owner normalization does not require one file per owner;
- use packed objects;
- benchmark owner, declaration, and body chunk granularity;
- preserve content-addressed structural sharing;
- co-locate small records physically without merging identity.

Failure signal:

- local edit touches hundreds of physical reads for a tiny body;
- backup regresses;
- pack catalog dominates storage.

## Risk: Stable expression IDs create excessive tombstones

Mitigation:

- allocate identity only for selected/referenced expression regions where continuity has a consumer;
- allow content-addressed anonymous substructure only if exact edits and merge do not need identity;
- measure identity density;
- define subtree replacement retirement compaction.

Do not blindly assign durable identity to every literal if no consumer exists.

The initial design may still use expression IDs broadly for simplicity, but revisit with evidence.

## Risk: Committed witness creates duplicate authority

Mitigation:

- define logical derivation exactly;
- commit only witness roots needed for incremental proof;
- full rebuild must equal;
- witness pages remain reconstructible;
- no independent witness writer;
- publication rejects mismatch.

Failure signal:

- two different witness roots are accepted for one semantic root and validator contract;
- deleting witness bytes makes accepted meaning unknowable;
- witness contains policy not derivable from graph and declared contracts.

## Risk: One generic change engine becomes an untyped catch-all

Mitigation:

- normalized closed change enum;
- record-kind-specific validation;
- typed selectors;
- typed preconditions;
- one generic overlay infrastructure, not one generic JSON patch;
- generated per-operation schemas.

Failure signal:

- operation handlers cast arbitrary JSON;
- invalid combinations are discovered only after storage mutation;
- compiler and validator receive partially typed records.

## Risk: Full validator is accidentally reused as incremental validator

Mitigation:

- separate entry points and work counters;
- architecture tests;
- fail local-work bound if full scan occurs;
- independent full oracle.

## Risk: Session protocol hides stale state

Mitigation:

- every handle binds exact repository/revision/generation;
- every write rechecks base;
- no implicit current base;
- close/reopen equivalence;
- stale-handle tests.

## Risk: Schema generation becomes macro complexity

Mitigation:

- start with a plain typed registry;
- generate only duplicated facts;
- prefer compile-time Rust structures plus JSON Schema derivation;
- measure build time and code size;
- avoid a bespoke DSL unless it removes more complexity than it adds.

## Risk: Pack storage complicates crash safety

Mitigation:

- immutable packs;
- append or stage fully before catalog publication;
- old catalog and packs retained until new visibility durable;
- rebuildable catalog;
- deterministic failpoints;
- no in-place mutation.

## Risk: Compiler cache affects deterministic artifacts

Mitigation:

- unit keys bind all semantic inputs;
- clean build oracle;
- exact byte comparison;
- cache loss/corruption tests;
- linker canonical order independent of completion order.

## Risk: Campaign scope is too large for one safe cutover

Mitigation:

- dependency-closed vertical slices;
- private intermediate implementation;
- continuous focused gates;
- maintain old public system until new complete path passes;
- direct final switch;
- do not lower final invariants.

Do not respond by shipping permanent dual contracts.

## Risk: Auxiliary agents increase cost and inconsistency

Mitigation:

- task-scoped prompts;
- independent audits, not duplicate broad redesign;
- concise returned conclusions;
- primary integration;
- exact verification;
- use cheaper models only for bounded mechanical tasks.

## Risk: Documentation outruns implementation

Mitigation:

- generated current contracts;
- status updated last from receipts;
- normative specs changed with cutover;
- drift gate;
- proposed design stays in campaign ledger until implemented.
