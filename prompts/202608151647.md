## 4. Concrete Problems in the Audited Product

### 4.1 Ordinary Domain Data Is Not Expressible

The scalar language can express control and reuse.

It cannot express one named immutable application value with several fields.

It cannot express one closed choice among domain cases.

It cannot inspect a named field.

It cannot dispatch exhaustively over a closed set of variants.

Application logic must encode domain meaning through unrelated scalar parameters and booleans.

That is not a viable long-term semantic interface for autonomous agents.

### 4.2 Type Identity Does Not Exist

`SemanticType` is currently a closed scalar enum.

There is no semantic declaration identity for a domain type.

There is no stable field identity.

There is no stable variant identity.

Adding a string type name would make rename and ambiguity unsafe.

Adding only an ordinal would make edits and repair fragile.

The next gate must use persistent declaration and member identities.

### 4.3 Match Requires Dynamic Closed Contracts

The existing operation descriptor handles fixed regions for `if` and one region for `for_i64`.

A closed-sum match has one arm per current variant.

The arm count is dynamic but still closed by the sum declaration.

Do not solve this with an open pattern registry.

Do not solve this with arbitrary region labels.

Use one exact context-dependent match contract.

### 4.4 Aggregate Runtime Values Challenge Current Accounting

The current interpreter stores one `RuntimeValue` per Core value slot.

The current live-slot policy counts Core value slots.

A product containing many scalar cells must not consume the same budget as one bool.

A sum payload must not disappear from accounting.

The next runtime must account for materialized aggregate footprint.

It must remain explicit and deterministic.

### 4.5 Recursive Host Data Structures Can Violate Stack Safety

A direct recursive Rust enum for arbitrary nested products and sums is tempting.

Deep acyclic nominal types can still create deep values.

Recursive decode, validation, clone, formatting, or drop can consume native stack.

Use bounded transport shape and iterative internal processing.

Do not let nominal values weaken the repository stack-safety law.

### 4.6 Monolithic Schema Discovery Is Measurably Expensive

The current full schema is authoritative and useful.

It is also the largest response in the retained agent workflow.

Most tasks do not need every request, query, error, envelope, and payload shape on every session.

The next protocol may replace monolithic-only discovery with:

- a compact manifest;
- one canonical digest;
- exact named sections;
- multi-section projection;
- a compact unchanged response.

Do not create a second schema authority.

Do not infer token savings.

Measure bytes and round trips.

### 4.7 Shape Evolution Can Break Retained Meaning

If a product field is inserted under the same declaration ID, retained construction and projection meaning changes.

If a sum variant is inserted under the same declaration ID, retained matches become non-exhaustive.

If a field or payload type changes in place, retained values are reinterpreted.

The bootstrap must make nominal shape immutable under one declaration identity.

Shape change creates new identity.

Git history and retained graph revisions preserve old meaning.

## 10. By-Value Type Dependency Graph

## 11. Derived Layout Contract

Derive one deterministic bootstrap layout for every reachable nominal type.

Layout remains private derived state.

Do not persist it in the semantic artifact.

Do not expose dense layout indexes as semantic identity.

### 11.1 Primitive Layout

Use an exact bootstrap layout contract.

The preferred initial contract is:

- `unit`: size 0, alignment 1, zero runtime cells;
- `bool`: size 1, alignment 1, one runtime cell;
- `i64`: size 8, alignment 8, one runtime cell.

If the implementation selects a different exact contract, document why and preserve deterministic tests.

Do not use Rust `size_of` as the language contract.

### 11.2 Product Layout

Lay out fields in declaration order.

For each field:

1. align the current byte offset to the field alignment;
2. record the field byte offset;
3. add the field size with checked arithmetic.

Product alignment is the maximum field alignment, or 1 for an empty product.

Round final product size up to product alignment.

Flattened runtime-cell count is the checked sum of field cell counts.

Record exact field offsets as derived facts.

- cannot recurse;
