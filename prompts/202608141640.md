## Mission

Build lkjscript as an AI-native semantic programming system in which an agent creates, inspects,
changes, validates, compiles, executes, profiles, and debugs software by issuing typed graph
operations to one daemon.

The permanent conceptual path is:

```text
agent intent
    -> typed semantic query
    -> revision-checked semantic transaction
    -> immutable Semantic Program Graph snapshot
    -> deterministic derived semantic facts
    -> compact verified Core IR
    -> interpreter and native execution tiers
    -> daemon-supervised runtime result
```

The canonical path does not contain source parsing.

Textual rendering, structured export, graph visualization, debugging views, human-readable
diagnostics, and package files are projections from or serialized forms of the semantic authority.
They do not become authoring authorities.

The daemon owns the live mutable head of each workspace. Published snapshots are immutable. Compiler
IR, executable code, profiles, indexes, diagnostics, and caches are derived and disposable.

The system must become easier for an AI agent as programs grow. The agent must not need to reread an
entire program, reproduce boilerplate, remember private numeric indexes, infer types from error
strings, manually maintain imports, render and reparse code, or choose an execution tier.

## Canonical terminology

Use these terms consistently.

### Semantic Program Graph

The `Semantic Program Graph`, abbreviated `SPG`, is the sole canonical representation of program
meaning.

The SPG is not:

- a syntax tree;
- a parse tree;
- a generic property graph;
- a bag of JSON objects;
- a compiler IR;
- a runtime heap;
- a documentation graph;
- a repository graph;
- a source map;
- an arbitrary user-extensible dialect host.

The SPG is a closed, versioned, strongly typed schema of semantic node kinds and semantic relation
kinds.

### Workspace

A `Workspace` is a daemon-owned durable history of SPG snapshots plus workspace metadata that does
not alter program meaning.

A workspace has exactly one current head revision under one daemon writer.

### Snapshot

A `Snapshot` is an immutable, internally consistent SPG revision.

A snapshot may be incomplete.

A complete snapshot may be compiled.

An old snapshot remains readable while retained.

### Node ID

A `NodeId` is an opaque stable identity for one semantic entity or semantic node within one
workspace.

A NodeId is not a name, source coordinate, vector index, hash, address, compiler ID, runtime ID, or
artifact offset.

### Local handle

A `LocalHandle` identifies a not-yet-published node inside one transaction.

It never appears in a published snapshot.

It may be used to create cycles or mutually recursive declarations inside one transaction.

### Revision

A `Revision` monotonically identifies a successfully published workspace snapshot.

Failed transactions do not create revisions.

### Snapshot hash

A `SnapshotHash` is a deterministic content hash of canonical snapshot meaning used for artifact
identity and cache keys.

It is not the public identity of nodes.

### Derived fact

A `DerivedFact` is deterministic information computed from a snapshot, such as a resolved type,
effect set, ownership state, dependency edge, layout, diagnostic, or executable eligibility result.

Derived facts are disposable and must never become a second mutable program authority.

### Core IR

`CoreIR` is the compact verified compiler representation derived from a complete SPG snapshot.

It is private compiler data.

### Daemon

`lkjscriptd` is the one logical host service that owns writable workspaces and coordinates
compilation and execution.

### Runtime cell

A `RuntimeCell` is an optional isolated execution worker supervised by the daemon.

It is not a second workspace authority.

- carries no compiler-assigned register;
- carries no runtime address;

## Node identity

Begin with one simple workspace-scoped NodeId domain.

Recommended bootstrap representation:

```text
NodeId {
    workspace: WorkspaceId,
    serial: nonzero u128 or checked nonzero u64
}
```

A different width may be chosen after a concrete capacity and encoding analysis.

The important properties are:

- allocation is monotonic;
- IDs are never reused;
- deletion tombstones the ID;
- failed transactions do not consume IDs;
- old snapshots preserve old nodes;
- compaction does not change IDs;
- serialization preserves IDs;
- restart preserves the allocator high-water mark;
- names and content do not affect identity;
- one ID cannot be interpreted as a different node kind;
- ownership and kind checks occur at transaction boundaries.

Avoid slot/generation reuse unless retained storage measurements prove monotonic IDs unacceptable.

Do not use content hashes as mutable node identities.

Use content hashes for immutable snapshot and cache identity.

## Snapshots

Snapshots are immutable.

The daemon publishes one new snapshot per successful transaction.

A snapshot contains canonical semantic data and the minimum indexes required to support its
invariants.

Derived indexes may be cached separately if they can be reconstructed.

A snapshot must not contain:

- compiler IR;
- machine code;
- execution counters;
- mutable diagnostics;
- source text as authority;
- stale type results;
- stale effect results;
- stale ownership results;
- private allocator addresses;
- session aliases;
- client handles.

A snapshot may contain presentation metadata when it is clearly non-semantic and excluded from
semantic hashing where appropriate.

Decide explicitly whether a metadata field affects package identity.

## Transactions

All semantic mutation occurs through typed transactions.

A transaction has:

- workspace identity;
- base revision;
- optional client request identity for idempotency;
- ordered typed operations;
- local handles for newly created nodes;
- explicit preconditions where useful;
- optional dry-run mode;
- optional requested response projection.

A transaction is validated in a staged candidate state.

A transaction either publishes exactly one new snapshot or publishes nothing.

Failure preserves:

- current head revision;
- durable snapshot bytes;
- allocator high-water mark;
- tombstones;
- indexes;
- diagnostics cache;
- compile cache;
- session aliases;
- deterministic future allocation;
- runtime state unrelated to the transaction.

Do not allocate public NodeIds directly while decoding the request.

Resolve and validate local handles first.

Reserve IDs in staged state.

Publish allocator and snapshot atomically.

A no-op transaction should reject by default or return an explicit no-change result without
publishing a revision. Pick one rule and test it.

## Capabilities

A capability is an explicit typed value granted by the daemon or passed through program semantics.

Do not infer authorization from package identity, ambient process state, file path, source import,
or a global registry.

A host operation must require the corresponding capability.

The daemon must validate grants before execution.

Do not add broad `all_access` capability shortcuts to tests.

- hash-map order;
- private index rebuilding;
- allocator addresses;
- compiler IR changes;
- code-cache movement;
- session aliases;
- artifact offsets;
- formatting changes unless presentation metadata is explicitly requested.

Diff ordering is deterministic.

A transaction response should include a compact diff summary and optionally expanded changes.

Diffs are a major mechanism for reducing agent context and API cost.

## Persistence

The daemon must eventually own durable workspaces.

Persistence begins in the daemon phase, not as a separate speculative platform.

The initial durable design should favor obvious correctness:

- one canonical snapshot artifact per committed head;
- write to a new temporary file;
- flush file contents;
- atomically replace the durable head pointer or file;
- flush the containing directory where required;
- publish the in-memory head only after durable success;
- recover by loading the last fully committed snapshot;
- ignore or remove incomplete temporary files.

Do not acknowledge a successful transaction before durability when the workspace is configured as
durable.

Do not build a custom database, WAL, LSM tree, or distributed log before measurements demonstrate
that full-snapshot replacement is insufficient.

When a journal or embedded database becomes justified, preserve the same transaction semantics and
artifact authority.

## `.lkjscript` artifact

- explicit magic bytes;
- explicit artifact-format version;
- explicit semantic-schema identity;
- canonical endianness;
- canonical integer encoding;
- explicit section lengths;
- checked total lengths;
- canonical table ordering;
- explicit stable tags;
- NodeId encoding;
- root identity;
- allocator high-water mark;
- semantic node tables;
- presentation metadata sections, if retained;
- snapshot hash;
- corruption detection;
- strict trailing-byte policy;
- deterministic re-encoding;
- bounded decoder resource policy;
- no Rust memory layout;
- no pointer values;
- no compiler-dense IDs;
- no machine code;
- no derived compiler IR;
- no session aliases.

Artifact-format versioning is not language editions.

A format version exists because persistent bytes need an exact decoder contract.

Backward decoding is not required during this reset.

The current decoder may reject every older format.

## Hashing

Canonical snapshot hashing should cover semantic meaning.

Presentation metadata should be included or excluded by explicit field policy.

The hash should support:

- cache keys;
- artifact identity;
- deterministic test assertions;
- corruption detection when combined with exact encoding.

The hash must not become NodeId.

Do not hash mutable in-memory map iteration order.

Do not create per-node Merkle identities before measured incremental persistence or distribution needs
justify them.

## Daemon target

Build one logical per-user host daemon named `lkjscriptd`.

The command-line client is named `lkjscript`.

- deadlines;
- metrics;

The initial daemon may be synchronous internally.

Do not adopt an async runtime until concurrent workloads require it.

Do not make the daemon globally network-accessible.

Use local IPC with operating-system peer authentication or filesystem permissions.

## One logical daemon

“One daemon” means one authority and one coordination plane per user or configured host scope.

It does not forbid:

- compiler workers;
- sandboxed runtime cells;
- native-code installation helpers;
- crash-isolated host-operation brokers;
- platform-specific workers;
- future remote executors.

Helpers may never mutate workspace authority independently.

## IPC protocol

Choose based on implementation clarity and exact decoding, not fashion.

The protocol is not the SPG artifact.

Do not reuse persistent artifact bytes as an interactive transaction protocol unless a real analysis
proves it superior.

## Idempotency

A client may retry after connection loss.

A mutating request should support an idempotency key scoped to a workspace and client domain.

The daemon must return the prior committed result for an exact duplicate.

A conflicting reuse of the same key with different content must reject.

Idempotency records may have a bounded retention policy.

Do not make transaction semantics depend on the client guessing whether a previous request committed.

## Sessions and aliases

The protocol may assign short session-local aliases for long stable IDs to reduce bytes and tokens.

Aliases:

- are compression only;
- are revision-aware where necessary;
- never enter snapshots;
- never enter artifacts;
- never become public identity;
- fail deterministically when stale;
- can be reconstructed.

Do not implement aliases before request size measurements justify them.

The typed API should remain correct with full IDs.

## Compiler path

The compiler consumes the SPG directly.

The permanent conceptual path is:

```text
complete SPG snapshot
    -> semantic validation and derived facts
    -> compact dense CoreIR
    -> CoreIR verification
    -> interpreter preparation
    -> optional native compilation
```

There is no source AST in this path.

There is no requirement to preserve HIR, old SSA, old bytecode, old VM instructions, old native
image contracts, old executable wrappers, or old proof tiers.

The reset should delete those types rather than adapt them.

## CoreIR

CoreIR should be one compact typed control-flow and value IR shared by the interpreter and native
lowering.

CoreIR is not agent-authored.

CoreIR may use dense private indexes because it is derived from one snapshot.

CoreIR should define:

- functions;
- signatures;
- blocks;
- block parameters;
- instructions;
- typed values;
- terminators;
- direct call targets;
- constant pool references;
- effect/capability metadata needed for execution;
- source-independent semantic origin IDs for diagnostics and profiling;
- verified dominance and control-flow rules;
- checked index conversion;
- canonical deterministic lowering.

Do not preserve a separate HIR and separate bytecode merely for layering.

Add an intermediate form only when it removes repeated work or enables a measured transformation.

## CoreIR verifier

The verifier must reject malformed compiler-produced or deserialized CoreIR.

If CoreIR never crosses a persistent or untrusted boundary, use typed constructors and focused debug
verification rather than an elaborate authenticated artifact.

Verify at least:

- index bounds;
- block termination;
- operand definition;
- dominance;
- type agreement;
- call signature agreement;
- result arity;
- effect/capability consistency;
- control-flow target validity;
- ownership state when implemented.

Compiler bugs should fail deterministically rather than execute unchecked malformed state.

## Interpreter

Build a complete generic interpreter for every currently accepted CoreIR instruction.

The interpreter is the bootstrap execution route and semantic differential oracle.

It should be simple, deterministic, and instrumentable.

It need not preserve the old VM instruction format.

Prefer direct-threaded or compact dispatch only after a baseline exists.

Do not add a second evaluator of the SPG.

Interpret CoreIR.

Do not require every optimization to be mirrored in the interpreter.

## Native execution

Native execution is an accelerator inside one product path.

A valid program remains valid when native compilation declines or fails before entry.

Tier selection is not public language meaning.

The initial native backend should be selected by measured implementation and runtime tradeoffs.

Cranelift is a strong first candidate because it can provide a production-quality baseline without
requiring lkjscript to own a machine-code backend immediately.

LLVM ORC or another backend may be evaluated for a later optimizing tier.

A custom backend is permitted only after profiling proves an external backend blocks a material
world-leading target.

Do not begin with a custom assembler.

Do not begin with speculative optimization, deoptimization, OSR, or profile-guided specialization.

## Tiering direction

A plausible long-term tier path is:

```text
Tier 0: CoreIR interpreter
Tier 1: fast baseline native compilation
Tier 2: optimizing native compilation for hot stable code
Tier 3: profile-specialized or domain-specific code where evidence justifies it
```

This is a hypothesis, not an obligation.

Keep only tiers whose end-to-end benefit exceeds their implementation and maintenance cost.

All tiers share one semantic validator and CoreIR contract.

A tier failure before entry may fall back.

A failure after native entry must not rerun effects in another tier.

## Code cache

The daemon is the natural owner of compiled-code reuse.

Do not implement a generalized code cache before repeated compilation is measured.

When added, a cache key should include:

- semantic snapshot or function hash;
- compiler configuration;
- target triple;
- target feature set;
- backend version;
- relevant runtime ABI identity;
- optimization tier;
- capability ABI where relevant.

A cache hit may not bypass validation required at the trust boundary.

Cache eviction never changes program meaning.

## Profiles

Profiles are derived runtime evidence.

They are keyed to exact semantic and executable identities.

Do not write execution counters into snapshots.

Profile use must be deterministic enough to debug.

Profile-guided optimization may change performance, not semantic results.

Retain representative profile summaries, not unbounded raw events.

## Runtime ABI

The ABI must cover:

- values;
- calls;
- returns;
- traps;
- capability invocation;
- allocation;
- cleanup;
- cancellation polling;
- deadline polling;
- stack or frame management;
- runtime-cell interaction;
- profiling hooks.

Do not expose Rust ABI as a persistent contract.

Keep unsafe code localized.

Use W^X for generated executable memory.

Validate relocations and entry signatures.

## Runtime values

Prefer unboxed scalar values and compact layouts.

Derive layouts from semantic types.

Do not preserve boxed uniform values merely because they simplify a prototype interpreter.

Do not prematurely specialize every value representation before types exist.

Measure:

- interpreter dispatch;
- allocation;
- call overhead;
- representation conversions;
- host-call overhead;
- cache locality;
- code size;
- compilation latency.

## Runtime cells

A cell may provide:

- crash isolation;
- memory limits;
- CPU limits;
- capability isolation;
- target separation;
- cancellation;
- cleanup;
- native-code containment.

The daemon remains the authority.

A cell consumes immutable executable input and explicit grants.

A cell returns a structured result and measurements.

A cell cannot mutate SPG state directly.

Do not build a broad cell scheduler before one isolated execution vertical works.

## Concurrency

Do not add language concurrency in the reset milestone.

The daemon may later coordinate many workspaces and invocations concurrently.

Internal daemon concurrency must preserve deterministic transaction serialization per workspace.

Do not use nondeterministic hash iteration in observable results.

Do not let race timing change semantic diffs, diagnostics, or compile results.

## Security boundaries

Classify each boundary.

### Trusted same-build in-process values

Use Rust types and constructors.

Do not add serialization, digests, registries, or version tokens without an independent consumer.

### Persistent `.lkjscript` bytes

Decode defensively.

### IPC bytes

Authenticate the local peer or rely on explicit local filesystem access policy.

### Native code

### Runtime cells

Treat the child process as failure-prone.

Validate every result.

Do not trust child-provided resource claims without host observation where security matters.

### Host capabilities

Validate grants and arguments at dispatch.

Do not confuse language type checking with operating-system authorization.

- content-addressed immutable artifacts;
- database transaction and crash-recovery principles.

For every borrowed idea, translate it into lkjscript's actual invariants and current scale.

Do not import another project's terminology, abstraction count, compatibility burden, or extension
model without need.

## Anti-overengineering rules

Do not create:

- a generic graph database;
- a generic query language;
- a generic schema compiler;
- a generic transaction planner;
- a generic distributed daemon framework;
- a generic actor runtime;
- a generic plugin system;
- a generic incremental engine;
- a generic artifact registry;
- a generic capability registry;
- a generic compiler pass manager;
- a generic benchmark service;
- a generic evidence ledger;
- a generic documentation authority;
- a generic model-context service;
- a generic prompt optimizer.

Build the narrow product mechanism.

Generalize only after at least two real consumers expose the same stable abstraction.

## Deletion bias

When replacing a concept:

1. identify every producer;
2. identify every consumer;
3. cut over all active consumers;
4. delete the old representation;
5. delete adapters;
6. delete stale tests;
7. delete stale documentation;
8. delete dependencies that became unused;
9. verify repository search finds no accidental authority;
10. record only the new state.

A deprecated unused path is worse than deleted code in this reset.

## Compatibility prohibition

Do not add:

- `legacy`;
- `compat`;
- `v1`;
- `v2`;
- `old`;
- `new`;
- `next`;
- `edition`;
- migration readers;
- migration writers;
- aliases for deleted commands;
- feature flags preserving the old product;
- conversion from old HIR or bytecode;
- import from old `.lkjscript` text;
- adapters around old semantic workspace APIs.

An explicit artifact-format number is allowed and required.

It is not a language edition.

## Stop-the-line conditions

Stop and correct the design immediately if work introduces:

- two writable semantic authorities;
- source text in the compiler path;
- names as references;
- arbitrary graph properties;
- untyped mutation;
- public compiler indexes;
- NodeId reuse;
- partial durable publication;
- acknowledged transactions before durability;
- fake hole values;
- execution of incomplete snapshots;
- nondeterministic error precedence;
- daemon helpers that mutate workspaces;
- a second compiler IR without measured purpose;
- a native tier that narrows valid language behavior;
- effect retry after native entry;
- ambient capability grants;
- user-depth native recursion;
- arbitrary semantic quotas;
- an old-format compatibility path;
- a consumerless protocol;
- a consumerless persistent field;
- a broad framework before the first vertical;
- documentation growth that exceeds product clarity;
- skipped final verification disguised as API-cost savings.

## Required implementation posture

Be bold about deletion.

Be conservative about new abstractions.

Prefer one simple exact mechanism over a comprehensive framework.

Prefer immutable data over synchronization complexity.

Prefer stable semantic identities over positional APIs.

Prefer direct typed operations over text.

Prefer explicit contracts over inference.

Prefer one complete path over several partial tiers.

Prefer measured backend reuse over custom code generation.

Prefer daemon reuse over repeated process setup.

Prefer deterministic compact queries over whole-program dumps.

Prefer a small active tree over historical context.

## Ordered implementation campaign

The phase order below is the default dependency order.
Advance only when the previous phase acceptance boundary is real.
A later phase may be pulled earlier only when a concrete blocker proves the dependency assumption wrong.

### Phase 0: Authority cutover and empty-tree reset

Objective: Replace repository governance and remove the existing product without leaving a second implementation.

Entry condition: The actual checkout and worktree are inspected; unrelated work is preserved; replacement `AGENTS.md` is ready.

Deliverables:

- Install the replacement `AGENTS.md`.
- Create the active reset prompt under `prompts/`.
- Record the exact deletion inventory.
- Delete legacy product code, tests, fixtures, package artifacts, obsolete docs, obsolete CI, and obsolete verification machinery.
- Create one minimal Rust package with compiling client and daemon entry points.
- Create a small README and current architecture/roadmap skeleton.
- Make the new active tree build and test.

Acceptance:

- No old parser, HIR, SSA, bytecode, VM, JIT, native, semantic-workspace, or package product path remains.
- No compatibility reader or adapter remains.
- `cargo metadata` reports the intended minimal package set.
- Repository searches for old authority names are empty or every residue is explained.
- Full active-tree verification passes.

Explicitly deferred:

- Semantic execution.
- Durable workspace format beyond the smallest skeleton.
- Native code.
- Broad schema.

Deletion obligation: Every obsolete active-tree mechanism; Git history remains the only archive.

Performance evidence: Record clean build and test time only; do not optimize.

Agent-cost evidence: Measure final active-tree file count and navigation fan-out as the reset baseline.

Handoff rule:

- Name the exact completed invariants.
- Name the exact retained tests and commands.
- Name every known gap without creating scaffolding for it.
- Identify the next phase's first evidence gate.
- Keep the active tree green.

### Phase 1: Semantic kernel

Objective: Establish the closed SPG schema, stable identities, immutable snapshots, and failure-atomic in-memory transactions.

Entry condition: Phase 0 is green and no legacy authority remains.

Deliverables:

- Implement WorkspaceId, Revision, NodeId, LocalHandle, and SnapshotHash domains.
- Implement the minimal closed node schema.
- Implement immutable snapshots.
- Implement staged transaction batches.
- Implement deterministic allocation and rollback.
- Implement graph validation and deterministic semantic diffs.
- Implement incomplete state and blockers for the bootstrap schema.
- Add property tests for operation sequences.

Acceptance:

- Create package, module, function, region, block, scalar operations, and return through typed operations.
- Rename preserves identity.
- Invalid ownership, kind, workspace, or type targets reject.
- Failed transactions leave revision and future IDs unchanged.
- Old snapshots remain readable.
- Hashing and diff ordering are deterministic.
- Deep graph traversal is stack-safe.

Explicitly deferred:

- Filesystem persistence.
- IPC.
- Compilation.
- Native execution.

Deletion obligation: Any temporary alternate graph builder or mutable candidate representation after the staged transaction path works.

Performance evidence: Measure transaction latency at representative node counts without adding caches.

Agent-cost evidence: Measure bytes and operation count required to construct the bootstrap function.

Handoff rule:

- Name the exact completed invariants.
- Name the exact retained tests and commands.
- Name every known gap without creating scaffolding for it.
- Identify the next phase's first evidence gate.
- Keep the active tree green.

### Phase 2: Canonical artifact and durable workspace

Objective: Make `.lkjscript` deterministic semantic bytes and make durable publication crash-safe.

Entry condition: The in-memory semantic kernel and transaction atomicity are complete.

Deliverables:

- Specify artifact magic, format, schema identity, tags, sections, IDs, and canonical ordering.
- Implement bounded encode and decode.
- Implement deterministic snapshot hashing.
- Implement atomic temporary-write, flush, replace, and directory-flush publication.
- Persist allocator state with the snapshot.
- Implement workspace open and recovery.
- Add corruption and crash-point tests.

Acceptance:

- Encode-decode-encode is byte-identical.
- Restart preserves revision, IDs, graph, allocator, and hash.
- Truncated, corrupt, unknown-tag, overflow, duplicate-ID, wrong-kind, and trailing-byte cases reject.
- Injected failure before durable replacement leaves the old head intact.
- Acknowledged success always survives restart in durable mode.

Explicitly deferred:

## Bootstrap schema v0

The following is the preferred concrete bootstrap schema for Phases 1 through 4.

It is deliberately small.

If implementation evidence requires a small change, update this section and the code together before
broadening the schema.

### Scalar identity types

Define distinct Rust newtypes for:

- `WorkspaceId`;
- `Revision`;
- `NodeId`;
- `RequestId`;
- `IdempotencyKey`;
- `SnapshotHash`;
- `ArtifactVersion`;
- `SchemaId`.

Do not accept raw integers interchangeably.

Use explicit checked encoding at persistent and protocol boundaries.

### Node storage

A bootstrap snapshot may use a deterministic ordered map from NodeId to NodeRecord.

A full-map clone per transaction is acceptable initially if retained measurements show it is not yet
a bottleneck.

Do not build a persistent HAMT, copy-on-write graph engine, graph database, or arena-compaction
framework before measuring the simple baseline.

The snapshot should maintain only indexes required for correctness or first queries.

Derived reverse-use indexes may be rebuilt or cached as measurements justify.

### Node kinds

Bootstrap `NodeKind` should contain no more than:

- `WorkspaceRoot`;
- `Package`;
- `Module`;
- `Function`;
- `Parameter`;
- `Region`;
- `Block`;
- `Operation`;
- `Hole`, only if a hole cannot be represented honestly as an operation kind;
- `UnresolvedReference`, only if source-free staged construction requires a published unresolved
  entity.

Prefer `OperationKind::Hole` over a second hole representation when the hole occupies an expression
position.

Do not add an `Unknown` node kind.

### Value identity

Do not allocate a public node for every operation output unless a concrete editing or lifecycle need
proves it necessary.

Prefer this bootstrap value address:

```text
ValueRef =
    FunctionParameter(NodeId)
    | BlockParameter(NodeId)
    | OperationResult {
          operation: NodeId,
          output: checked small unsigned index
      }
```

The producing operation NodeId is stable.

The output index is part of the closed operation contract.

A replacement that changes output identity must create a new operation or follow an explicit
identity-preserving replacement rule.

Do not represent values by dense compiler indexes in the SPG.

### Built-in types

Bootstrap semantic type values:

```text
SemanticType =
    Unit
    | Bool
    | I64
```

Do not add `Never` until structured control needs it.

Do not add generic `Any`, `Unknown`, `Dynamic`, or `Error` types.

Holes carry expectations without weakening type equality.

### WorkspaceRoot record

Required fields:

- its own NodeId;
- ordered or canonically sorted package NodeIds;
- optional presentation metadata under explicit policy.

Validation:

- exactly one root per snapshot;
- root belongs to the workspace;
- every listed package exists and has kind Package;
- every package is owned by the root;
- no duplicate package;
- no unowned reachable semantic node;
- no multiply owned contained node.

### Package record

Required fields:

- NodeId;
- owner WorkspaceRoot NodeId;
- display name metadata;
- contained Module NodeIds.

Bootstrap semantics:

- one package is sufficient;
- package order is non-semantic unless later initialization semantics require order;
- names do not define identity;
- exports are deferred unless needed by the first call vertical.

Validation:

- owner exists and has the correct kind;
- modules exist and are owned by the package;
- display-name constraints are minimal and deterministic;
- duplicate display names may reject for lookup ergonomics without making names identity.

### Module record

Required fields:

- NodeId;
- owner Package NodeId;
- display name metadata;
- contained Definition NodeIds.

Bootstrap definition kind:

- Function only.

Validation:

- owner exists and has kind Package;
- definitions exist and are owned by the module;
- duplicate lookup names follow one exact rule;
- definition order is presentation unless later semantics define initialization order.

### Function record

Required fields:

- NodeId;
- owner Module NodeId;
- display name metadata;
- ordered Parameter NodeIds;
- declared result SemanticType;
- optional body Region NodeId;
- entry-point marker or package entry relation under one exact rule.

Bootstrap restrictions:

- no generics;
- no effects;
- no capabilities;
- no variadics;
- no overloading;
- one result;
- body may be absent while incomplete;
- exactly one selected entry function named or identified semantically.

Prefer an explicit package entry reference over deriving entry identity from the spelling `main`.

The CLI may display the conventional name `main`.

### Parameter record

Required fields:

- NodeId;
- owner Function NodeId;
- ordinal;
- display name metadata;
- SemanticType.

Validation:

- ordinals are dense and unique;
- owner lists parameters in the same semantic order;
- no parameter belongs to two functions;
- rename preserves NodeId;
- parameter value references use the parameter NodeId.

### Region record

Required fields:

- NodeId;
- owner Function or owning structured Operation NodeId;
- ordered Block NodeIds.

Bootstrap restrictions:

- function body region contains exactly one block until structured control is added;
- nested regions are absent until `if` is implemented;
- empty region is incomplete or invalid according to its owner contract.

Validation:

- every block exists and is owned by the region;
- block order follows the owning structured-operation contract;
- a region cannot be shared by two owners.

### Block record

Required fields:

- NodeId;
- owner Region NodeId;
- ordered BlockParameter NodeIds when that node kind is introduced;
- ordered non-terminator Operation NodeIds;
- exactly one terminator Operation NodeId.

Bootstrap restrictions:

- no block parameters are needed for the first straight-line vertical;
- no arbitrary successor edges are exposed;
- the terminator must be `return`.

Validation:

- all operations exist and are owned by the block;
- no operation occurs twice;
- terminator kind is permitted;
- non-terminators cannot be terminators;
- lexical value use order is valid for the bootstrap straight-line block;
- later CoreIR dominance is independently verified.

### Operation record

Required fields:

- NodeId;
- owner Block NodeId;
- closed `OperationKind`;
- ordered ValueRef operands;
- kind-specific typed attributes;
- direct definition references where applicable;
- nested Region NodeIds where applicable;
- presentation metadata only when justified.

Do not store result types redundantly in the bootstrap SPG.

### Bootstrap transaction operations

Prefer a closed transaction enum containing only implemented operations.

Potential initial variants:

```text
CreatePackage
CreateModule
CreateFunction
CreateParameter
CreateRegion
CreateBlock
CreateOperation
SetFunctionBody
SetEntryFunction
RenameNode
ReplaceOperation
DeleteOwnedSubtree
```

The exact split may be simplified.

Each create operation returns a LocalHandle inside the batch and a NodeId mapping on success.

`CreateOperation` contains a closed operation draft, not an arbitrary property map.

`ReplaceOperation` must define whether the existing operation NodeId survives.

Bootstrap recommendation:

- preserve the NodeId only when owner, operation kind, output arity, output types, and semantic role
  remain compatible;
- otherwise create a new operation and require explicit rewiring;
- reject ambiguous identity preservation.

A constant-value change from `ConstI64(2)` to `ConstI64(3)` should preserve the operation NodeId.

This makes the old/new revision diff precise and permits downstream identity continuity.

### Bootstrap completeness

A snapshot is executable only when:

- one entry function is selected;
- the entry function exists and is complete;
- every contained node satisfies schema invariants;
- every function body exists;
- every block has a valid terminator;
- every operand resolves;
- every direct reference resolves;
- no hole is reachable from the entry dependency closure;
- every operation type-checks;
- every call target is complete;
- CoreIR lowering and verification succeed.

Decide whether unreachable incomplete definitions block package compilation.

Bootstrap recommendation:

- workspace and package may contain incomplete unused definitions;
- compile one entry dependency closure;
- execution requires that closure to be complete;
- queries report package-wide blockers separately from entry-closure blockers.

Document and test the distinction.

- node created;
- node deleted;
- node renamed;
- scalar attribute changed;
- containment changed;
- operand changed;
- direct reference changed;
- entry function changed;
- completeness status changed.

Use stable NodeIds.

Do not expose map positions or serialized offsets.
