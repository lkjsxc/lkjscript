## 1. Executive objective

The next repository-level decision is not whether lkjscript should have an incremental compiler.
The next decision is whether the current full-recomputation semantic-workspace path is already
adequate for representative AI-authored edits and queries, and, if not, which measured local
operation is the first real bottleneck. Establish that evidence boundary with a reproducible
harness, truthful phase accounting, representative source-free workloads, compact recorded
results, and one explicit keep/change/defer decision.

- Primary result: a reproducible baseline for transaction latency, query latency, projection
  cost, post-edit compilation, process memory orientation, deterministic work, and agent-visible
  output.
- Valid result A: the baseline shows that full recomputation is acceptable for the selected
  representative scales. Record the evidence, retain the architecture, and stop without
  production optimization.
- Valid result B: the baseline exposes one local repeated, avoidable, disproportionate, or
  superlinear operation. Correct only that root cause, remeasure equivalently, keep the
  correction only if the complete tradeoff is favorable, and stop.
- Valid result C: instrumentation or scale work exposes a correctness, atomicity, identity,
  cleanup, or determinism defect. Complete that correctness vertical before performance work,
  add regression coverage, and report that the original performance decision remains open if
  necessary.
- Invalid result: introducing a general incremental dependency graph, cache hierarchy, dirty-bit
  framework, daemon, journal, database, event bus, wire protocol, or persistent semantic store
  without first proving that the present local path needs it.
- Invalid result: selecting a favorite mechanism first and constructing a benchmark that merely
  justifies it.
- Invalid result: optimizing only a synthetic maximum-depth fixture while ordinary edit/query
  behavior remains unmeasured.
- Invalid result: reporting a single developer-machine timing as a product guarantee.

## 8. Falsifiable working hypothesis

Start with the neutral hypothesis that full semantic-program cloning and recomputation may be a
reasonable implementation for the current local product, but one or more phases may perform
avoidable work disproportionate to the edit or query. The experiment must be capable of
confirming that the current path is adequate. It must not assume that incrementality is
required.

- Null hypothesis: representative edits, queries, projections, and post-edit compiles have
  predictable scale, bounded output, acceptable memory orientation, and no local repeated-work
  pathology that justifies added production complexity.
- Alternative hypothesis: one named phase performs demonstrably disproportionate work, dominates
  equivalent end-to-end samples beyond noise, or repeats semantic work already available at the
  same trusted boundary.
- Correctness hypothesis: current results preserve publication atomicity, stable survivor
  identity, old snapshot validity, exact query semantics, deterministic ordering, completeness
  gating, ownership cleanup, and source-free direct compilation at every measured scale.
- Reversal condition for instrumentation: measurement changes production semantics, materially
  distorts the measured path, adds a general framework, or cannot be cleanly isolated from
  product behavior.
- Reversal condition for an optimization: semantic or cleanup divergence, identity instability,
  greater retained memory without justified latency benefit, worse representative end-to-end
  work, or maintenance complexity larger than the removed problem.
- Stop condition: the evidence supports one explicit keep/change/defer decision and the selected
  vertical is documented, tested, and verified.

### W0. measurement control

- **Purpose:** Separate Cargo build and test-process startup from semantic workspace work.
- **Construction:** Use an already-built locked-release test binary and a tiny complete

- **Mutation:** Perform no measured semantic mutation in the timed control interval.
- **Queries:** Issue one constant-size direct identity query only when a timer calibration point
  is needed.
- **Correctness:** Require the exact scalar result, zero source loading, zero parsing, and no
  retained owner or loan.
- **Measurement:** Record process startup separately and never subtract an unstable single
  control sample blindly.
- **Selection:** Always include enough control evidence to state what the reported phase timers
  exclude.

### W1. incomplete metadata-only hole refinement

- **Purpose:** Reveal work performed by a transaction that changes a hole goal but no executable

## 11. Phase map to instrument before optimizing

Do not time only `Workspace::apply` and call the result understood. Identify enough internal

### P00. fixture and draft construction

- **Why it matters:** Input generation outside the product path can dominate small samples.
- **Record when relevant:** Generated declarations, draft nodes, pattern nodes, bytes, and setup
  allocations.
- **Decision rule:** Exclude it from product latency or report it separately; do not conceal it
  in transaction time.

### P01. revision and transaction-shape validation

- **Why it matters:** Fast rejection and base-revision checks define the atomic boundary.
- **Record when relevant:** Edits examined, identities checked, and rejection point.
- **Decision rule:** Keep explicit; no optimization is justified unless repeated validation is
  measured.

### P02. identity allocator staging clone

- **Why it matters:** The current workspace stages allocator state before publication.
- **Record when relevant:** Live slots, tombstones, free-list entries, and clone invocations.
- **Decision rule:** Measure retained and copied state before proposing structural sharing.

### P03. semantic program clone

- **Why it matters:** Current successful transactions deep-clone declarations and function
  bodies.
- **Record when relevant:** Functions, bindings, products, enums, implementations, match plans,
  and expression nodes cloned.
- **Decision rule:** This is a central hypothesis, not proof that persistent data structures are
  needed.

### P04. deletion preflight

- **Why it matters:** Every transaction may inspect deletion intent and target kinds.
- **Record when relevant:** Edits scanned, deletion requests, dependency roots, and maps
  allocated.
- **Decision rule:** A local empty-deletion fast path is eligible only if measured and
  semantically exact.

### P05. structural-edit preflight

- **Why it matters:** Overlap, ownership, target, and final-state rules protect atomic
  replacement.
- **Record when relevant:** Structural edits, target ancestors, overlap comparisons, and
  identity lookups.
- **Decision rule:** Do not weaken preflight or make edit order semantically observable.

### P06. draft scope and lowering

- **Why it matters:** Source-free authoring must remain stack-safe and proportional to the
  submitted draft.
- **Record when relevant:** Draft nodes, scope visits, stable-binding lookups, pattern nodes,
  calls, and type arguments.
- **Decision rule:** Reuse existing test counters and add only missing counters needed for the
  selected workload.

### P07. structural replacement and match refresh

- **Why it matters:** Targeted edits rebuild roots and may refresh match facts.
- **Record when relevant:** Roots rebuilt, nodes copied, ancestors recomputed, match plans
  inspected, and plans refreshed.
- **Decision rule:** Separate legitimate affected-root work from unrelated full-program scans.

### P08. final-state dependency validation

- **Why it matters:** Deletion and type/reference validity are checked against the staged graph.
- **Record when relevant:** Stored types, expressions, patterns, holes, witnesses, and
  dependents visited.
- **Decision rule:** Preserve order independence and deterministic surviving-dependent
  diagnostics.

### P09. dense compaction and remapping

- **Why it matters:** Current staging compacts products, enums, implementations, bindings,
  plans, places, and slots.
- **Record when relevant:** Items taken, retained, removed, mapped, cloned, remapped, and root
  traversals.
- **Decision rule:** Compare no-deletion, local-removal, and declaration-deletion workloads
  before changing it.

### P10. survivor relocation and new identity reservation

- **Why it matters:** Stable public identities must survive private relocation exactly.
- **Record when relevant:** Forced entity/node mappings, survivor lookups, reserved IDs,
  tombstones, and collisions checked.
- **Decision rule:** Do not trade identity correctness for lower work.

### P11. partial effect inference

- **Why it matters:** Every staged program currently refreshes effects before publication.
- **Record when relevant:** Functions, roots, and expression nodes visited; fixed-point
  iterations if any.
- **Decision rule:** Do not invent incremental effect state until repeated unaffected work is
  demonstrated.

### P12. complete-HIR derivation during transaction validation

- **Why it matters:** Complete revisions must prove executable semantic consistency before
  publication.
- **Record when relevant:** Derivations, semantic nodes converted, core facts installed, and
  validation visits.
- **Decision rule:** Measure separately from post-publication compile derivation; do not retain
  a second authority casually.

### P13. ownership and match validation before publication

- **Why it matters:** Move, borrow, cleanup, usefulness, and exhaustiveness are correctness
  gates.
- **Record when relevant:** HIR nodes, places, uses, loans, plans, patterns, and checks.
- **Decision rule:** Never skip these gates merely because the following compile also validates
  related facts.

### P14. semantic index construction

- **Why it matters:** The snapshot rebuilds entities, nodes, edges, type facts, and private
  maps.
- **Record when relevant:** Entities, nodes, containment edges, references, calls, dependencies,
  sorts, deduplications, and map inserts.
- **Decision rule:** Measure index cost and query benefit together before adding more indexes.

### P15. identity reconciliation

- **Why it matters:** Canonical dense indexes are reconciled with stable public identity and
  generations.
- **Record when relevant:** Old/new entities and nodes compared, forced matches, tombstones,
  allocator operations, and map rebuilds.
- **Decision rule:** Finer reconciliation is high-risk incrementality; require decisive
  evidence.

### P16. hole address and diagnostic refresh

- **Why it matters:** Incomplete-state facts must remain exact after compaction and edits.
- **Record when relevant:** Holes scanned, addresses refreshed, blockers built, diagnostics
  allocated, and messages cloned.
- **Decision rule:** A metadata-only fast path must still preserve all blockers and diagnostics.

### P17. semantic and graph diff construction

- **Why it matters:** The agent-facing result must explain semantic change, not private
  relocation.
- **Record when relevant:** Entries compared, references/calls inspected, call instantiations
  converted, entries sorted, and bytes retained.
- **Decision rule:** Do not make diffs incomplete or unordered to reduce time.

### P18. snapshot publication and outcome copy

- **Why it matters:** Publication swaps one `Arc` and returns diagnostics and invalidation
  facts.
- **Record when relevant:** Arc operations, diagnostics cloned, invalidation entries, and
  allocator copy ownership.
- **Decision rule:** Treat tiny copies as noise unless measurements show otherwise.

### P19. entity/search page materialization

- **Why it matters:** Current pages may clone and sort complete candidate vectors.
- **Record when relevant:** Total entities scanned, items cloned, comparisons, requested limit,
  returned items, and continuation offset.
- **Decision rule:** Optimize only a measured common query; do not build a general query
  planner.

### P20. reference/call/dependency query filtering

- **Why it matters:** Reverse-edge queries may scan globally sorted edge vectors.
- **Record when relevant:** Edges scanned, matches returned, sorts, pages, and target density.
- **Decision rule:** Any reverse index must justify retained memory and index-build cost on the
  complete loop.

### P21. type and signature view conversion

- **Why it matters:** Structured public types protect semantic identity but may allocate or
  scan.
- **Record when relevant:** Entities scanned, binders ordered, type nodes converted, bounds
  visited, witnesses converted, and output items.
- **Decision rule:** Do not expose compiler-dense types as a speed shortcut.

### P22. match, hole, and legal-constructor queries

- **Why it matters:** These queries preserve scope, partial state, and truthful candidate
  status.
- **Record when relevant:** Nodes/plans/bindings inspected, candidates considered,
  ownership-deferred results, and response size.
- **Decision rule:** Do not claim branch-sensitive ownership legality from a cheap filter.

### P23. selected projection

- **Why it matters:** Projection should visit and emit the selected semantic slice, not
  unrelated state when avoidable.
- **Record when relevant:** Snapshot nodes scanned, selected nodes emitted, depth bookkeeping,
  type conversions, bytes, and lines.
- **Decision rule:** A local traversal improvement is eligible only with exact deterministic
  output.

### P24. post-edit completeness gate and HIR derivation

- **Why it matters:** Compilation must reject incomplete snapshots before compiler phases.
- **Record when relevant:** Blockers copied, complete-HIR derivations, and semantic nodes
  converted.
- **Decision rule:** Preserve zero memory/SSA/bytecode work for incomplete snapshots.

### P25. memory planning

- **Why it matters:** The compiler verifies ownership-aware memory obligations.
- **Record when relevant:** HIR nodes, obligations, layouts, and duration from existing compile
  metrics.
- **Decision rule:** Do not optimize this turn unless it is the measured local root cause and
  transaction work is already understood.

### P26. SSA construction and verification

- **Why it matters:** Typed SSA remains a verified in-process authority.
- **Record when relevant:** Construction, verification, normalization durations and relevant
  deterministic counts.
- **Decision rule:** Do not add a second IR or cache for this task.

### P27. bytecode lowering and validation

- **Why it matters:** The generic production route depends on validated bytecode.
- **Record when relevant:** Instructions emitted, locals, cleanup ranges, links, lowering
  duration, and validation duration.
- **Decision rule:** Preserve unrestricted trusted validation and malformed-bytecode rejection.

### P28. optional VM execution and cleanup

- **Why it matters:** The complete local loop may include one intentional execution.
- **Record when relevant:** VM steps, frames, allocations, owners, loans, cleanup, output, and
  duration where existing metrics permit.
- **Decision rule:** Do not use execution to validate `check`; check remains effect-free.

### P29. process wall, RSS, and agent-visible output

- **Why it matters:** End-to-end cost can be dominated by startup, retained memory, or
  irrelevant output.
- **Record when relevant:** Process wall, approximate process-tree RSS, stdout/stderr bytes and
  lines, JSON bytes, commands, and round trips.
- **Decision rule:** Report measurement limitations and avoid provider-token claims without
  provider/tokenizer evidence.

## 12. Instrumentation constraints

- Use existing production APIs and test fixtures wherever possible.
- Prefer `#[cfg(test)]` counters, a focused measured helper, or a narrow internal metrics struct
  over a public metrics framework.
- Do not change public semantic APIs solely to expose private benchmark timing.
- Do not add global mutable production state for measurements.
- Thread-local test counters are acceptable when the measured test runs single-threaded and
  resets them explicitly.
- A metrics struct may carry durations and exact work counts only for phases with a current
  measured consumer.
- Do not expose private dense IDs, addresses, slots, or compiler objects through public metrics.
- Do not serialize and parse internal values merely to measure them.
- Do not hash entire representations merely to prove benchmark equivalence; assert semantic
  outcomes and selected exact facts.
- Do not instrument every function in the compiler. Instrument the smallest set of boundaries
  needed to explain the selected end-to-end workload.
- Keep timer calls outside tight inner loops unless the timer itself is part of the measured
  API.
- For very small query operations, execute a calibrated repeated batch and divide only after
  checking that the batch result and iteration count are exact.
- Prevent dead-code elimination by consuming structured results and asserting them, not by
  printing giant values.
- Keep raw metrics deterministic where possible; distinguish saturating observation from exact
  work.
- Use checked counters and report overflow as a host measurement failure rather than wrapping.
- Do not make measurement code alter ordering, allocation strategy, or snapshot retention in the
  production path under test.
- If allocation counts require a new dependency or unsafe allocator wrapper, first prove that
  RSS and deterministic work are insufficient for the decision.
- It is acceptable to record allocation counts and bytes as Unknown with an explanation.
- Keep raw output under `target/` or another ignored path.
- Ensure the measurement harness records the exact commit and dirty worktree digest.

## 14. Timing protocol

- Use locked release artifacts for product-path measurements.
- Build the relevant test binary before starting sample timing.
- Record build time separately when build footprint is part of the question; otherwise exclude
  it.
- Use a fresh test process per end-to-end sample when process wall and RSS are recorded.
- State whether Cargo dependency and release artifacts are warm or cold.
- Use `Instant` or the repository's existing monotonic timing mechanism.
- Collect enough samples to report a median and a meaningful tail orientation; five samples is a
  reasonable default when cost permits, not a universal rule.
- For three samples, label nearest-rank p95 as orientation rather than a stable percentile.
- Randomize or alternate before/after sample order when thermal or cache drift could bias a
  close comparison.
- Pin or record relevant thread-count settings; do not silently compare different parallelism.
- Record CPU, logical CPUs, memory, kernel/OS, architecture, Rust, Cargo, build profile, and
  host name.
- Record exact workload geometry and semantic result in every sample.
- Report phase duration and process wall separately.
- Do not subtract independently noisy medians to manufacture a phase time.
- Use deterministic work to interpret timing when samples are near timer or scheduler noise.
- Do not create a hard CI timing gate from developer-machine samples.
- A measured regression smaller than noise is Unknown, not a win or loss.
- Preserve complete failure output; native quiet flags may suppress successful progress only.
- A sample that fails semantic assertions is invalid and must not enter the summary
  distribution.
- A sample that runs under unexpected memory pressure, swapping, or unrelated load must be
  marked or discarded by a stated rule.

## 15. Memory and allocation protocol

- Prefer the existing Linux `/proc` process-tree RSS sampling convention when process-level
  memory orientation can answer the decision.
- State that summed process-tree RSS is approximate and not unique physical memory.
- Use a sampling interval appropriate to the operation; record the interval.
- Distinguish peak process RSS from retained snapshot memory.
- When retaining old snapshots, record exactly how many revisions and which roots remain live.
- Measure after a controlled warm-up and at named synchronization points.
- Release old snapshots explicitly before the post-release observation.
- Do not claim reclaimed heap bytes merely because RSS does not fall.
- Do not build a generic deep-size estimator for one snapshot experiment.
- A local exact capacity/count estimate is acceptable only when it follows the owned
  representation without duplicating semantic traversal machinery.
- Do not count source fixture strings or raw JSON as retained workspace state unless the product
  retains them.
- Separate benchmark fixture memory from production snapshot memory when possible.
- Record allocator counts and bytes only when the method is low-distortion and already available
  or small enough to justify.
- If allocation evidence is unavailable, state that explicitly in `docs/performance.md`.
- Never reinterpret allocation failure as semantic invalidity.

## 16. Agent-output and API-cost protocol

- Measure output bytes and lines for successful high-frequency operations.
- Measure stdout and stderr separately.
- Measure machine JSON bytes when a machine document is emitted.
- Measure selected semantic projection bytes and lines.
- Record the number of commands and process round trips required for the representative loop.
- Record duplicate diagnostics or repeated facts when they materially increase context.
- Report whether a response gives the next needed identity or requires another broad query.
- Do not equate bytes with provider tokens or billing.
- Do not claim API-credit savings without provider-specific tokenization and billing evidence.
- It is valid to claim fewer bytes, lines, commands, repeated facts, or round trips.
- Do not make output cryptic merely to reduce bytes.
- Keep stable codes, kinds, identities, types, ranges, effects, blockers, and recovery facts
  needed for the next deterministic action.
- Successful human `check` remains quiet.
- Machine commands emit one deterministic document or documented stream without progress
  chatter.
- Do not create a daemon, output broker, or logging framework to save command output.
- Do not print raw phase traces in ordinary tests.
- Store detailed raw results outside Git and commit only a compact reproducible summary.
- Search and open focused ranges during the implementation turn; avoid repeatedly loading
  complete large files into model context.

## 17. Harness architecture

Use the repository's established scale-harness pattern rather than inventing a benchmark
platform. A good shape is one ignored locked-release test or focused internal sampler that emits
one machine-readable marker, plus one small Python driver that builds once, runs the selected
matrix in fresh processes, polls RSS when needed, records metadata, and writes raw JSON under
`target/`.

- Reuse `meta/scripts/compiler-scale.py` conventions for worktree hashing, host metadata, fresh
  process samples, marker parsing, RSS polling, and ignored raw output.
- Copy small local code when it is clearer than generalizing the existing script into a
  framework.
- Generalize shared harness code only when two retained current consumers benefit and the
  resulting code is smaller than the duplication.
- Give the script a narrow name tied to semantic workspace recomputation.
- Give the test a narrow name tied to the selected workload and result schema.
- Use environment variables or explicit test arguments for measurement geometry.
- Validate every geometry as positive and checked before constructing it.
- Build the release test binary once with `--no-run` before collecting samples.
- Run sample tests with `--exact`, `--ignored`, `--nocapture`, and one test thread where
  thread-local counters or deterministic output require it.
- Capture stdout and stderr completely for each sample.
- Fail the harness when the test exits nonzero, emits no marker, emits multiple conflicting
  markers, or returns malformed JSON.
- Include semantic result and correctness counters in the marker so timing cannot be separated
  from valid execution.
- Keep progress messages in the driver, not in the machine sample document.
- Write sorted, indented JSON with a stable top-level schema.
- Record the exact command template and environment variables.
- Record HEAD, dirty Boolean, status lines, tracked diff hash, untracked file hashes, and a
  combined worktree digest using the existing exclusion rules.
- Exclude `target/`, temporary subagent directories, bytecode caches, and generated scratch from
  the worktree digest exactly and explicitly.
- Record cache state in prose, not as an implied universal category.
- Keep raw sample logs or JSON in ignored storage.
- Make the summary reproducible from committed code and documented commands.
- Do not make ordinary `cargo test` run the expensive sample matrix.
- Keep a small non-ignored correctness test for the same measurement path when practical.
- Do not add a benchmark dependency when `Instant`, deterministic counters, and the existing
  Python driver are sufficient.

## 18. Raw result document

- `schema`: A stable local schema name and version only when a version is genuinely consumed.
- `label`: The operator-selected before or after label.
- `commit`: The exact Git commit.
- `worktree`: Dirty state, status, hashes, and combined digest.
- `machine`: Host, OS, architecture, CPU, logical CPUs, memory, Rust, and Cargo.
- `build`: Exact build command, profile, features, target, and cache state.
- `sample_command`: The exact test or binary command template.
- `workload`: Workload ID, semantic description, and correctness result.
- `geometry`: Total declarations, total nodes, affected-root nodes, draft nodes, edge density,
  page size, and retained revisions as relevant.
- `samples`: Per-sample phase durations, deterministic counters, process wall, RSS, output
  bytes, and semantic assertions.
- `selection`: Sample inclusion and exclusion rules.
- `summary`: Median, tail orientation, scaling ratios, and deterministic-work interpretation.
- `decision`: Keep full recomputation, apply one local correction, fix correctness first, or
  defer due to insufficient evidence.
- `limitations`: Unavailable allocation data, timer noise, process-RSS limitations, unsupported
  hosts, and unmeasured paths.

## 19. Before-baseline procedure

1. Finish reconnaissance and state the selected hypothesis, workloads, geometry, metrics,
   selection criterion, reversal condition, and stop condition in temporary working state.
2. Add only the minimal measurement instrumentation and harness needed to observe the unchanged
   path.
3. Add correctness assertions before collecting timing samples.
4. Run the small correctness version of the measurement path.
5. Build the locked-release measurement binary once.
6. Record the exact pre-change commit and complete worktree digest.
7. Collect the selected matrix without production optimization.
8. Inspect raw samples for failed assertions, malformed output, swapping, thermal drift,
   outliers, and unexpected phase omissions.
9. Summarize deterministic work first.
10. Summarize timings and RSS second.
11. Summarize output bytes, lines, commands, and round trips third.
12. Identify the smallest phase that explains the end-to-end shape.
13. Do not modify production code until the baseline and decision evidence are saved outside
    Git.
14. If instrumentation itself materially changes the path, redesign the instrumentation and
    recollect.
15. If the baseline is adequate, proceed directly to documentation and verification.

## 20. Analysis questions

- Does transaction work scale with submitted edit size, affected-root size, total workspace
  size, or some combination?
- Which scaling relationship is semantically necessary?
- Which relationship is caused by implementation convenience?
- Does W1 perform complete-program compaction, effect inference, indexing, or identity
  reconciliation despite changing only a hole goal?
- Does W2 spend more time validating correct ownership than cloning or indexing?
- Does W3 repeat complete-HIR derivation or ownership work during immediate compile?
- Does W4 show linear total-workspace work for a constant-size affected root?
- Is that whole-workspace work acceptable at representative scale?
- Does any phase grow faster than its exact semantic input count?
- Does a phase revisit the same node, edge, type, or binding multiple times without a
  correctness reason?
- Are sorts operating on vectors already in canonical order?
- Do paginated queries materialize and sort complete result sets for a small page?
- Does a continuation page repeat all first-page filtering or sorting?
- Do sparse reverse-edge queries scan every reference or call?
- Would an index that speeds a query increase every transaction's build time or snapshot memory
  more than it saves in the measured loop?
- Does body projection inspect unrelated roots?
- Does projection allocate a full-snapshot work map for one selected body?
- Does public type conversion rescan all entities for one function signature?
- Does call or match projection repeat signature or type conversion work already performed by
  the same query?
- Does `TransactionOutcome` duplicate diagnostic or invalidation data that is material at scale?
- Does retaining a snapshot duplicate allocator state enough to affect representative memory?
- Does the current `Arc` ownership already share the largest immutable components?
- Would structural sharing reduce cloning but substantially complicate identity, failure
  atomicity, or stack-safe destruction?
- Is a local early return or reuse of existing ordering sufficient?
- Can a local correction delete more code than it adds?
- Does the candidate correction benefit the complete agent loop rather than one microphase only?
- Does the candidate worsen index build, retained memory, compile time, or output?
- Can the candidate be reversed cleanly if broader workloads disagree?
- Are source loading and parser invocation still exactly zero on source-free paths?
- Are successful check and query operations still quiet or compact?
- Is the observed cost dominated by process startup, making a daemon tempting but unjustified
  without repeated in-process measurements?
- Would a one-shot in-process use already solve the measured cost without a service boundary?
- Does the current local product have a real consumer for retained warm state?
- Is the measurement geometry representative of code a coding agent can construct today?
- Are known unsupported language features accidentally shaping the benchmark more than current
  ordinary features?
- Is a correctness defect masquerading as a performance issue?
- Is a performance improvement merely moving work into snapshot construction or retained memory?
- Is a lower byte count omitting facts needed for the next deterministic action?
- Can the final decision be stated without speculative future architecture?

## 21. Decision gate

After the before baseline, choose one branch. Do not mix branches to justify broader work. The
decision must cite exact workload geometry, deterministic work, equivalent semantics, timing
distribution, memory orientation where available, complexity cost, and reversal condition.

- Choose **Branch A — retain full recomputation** when work is proportional to a defensible
  semantic boundary, timings are stable enough for current representative use, output is
  bounded, and no small local simplification has a clear benefit.
- Choose **Branch B — correct one local pathology** when deterministic work is disproportionate
  or repeated, equivalent samples show a material end-to-end effect beyond noise, and a local
  change can remove the problem without introducing a second authority or general framework.
- Choose **Branch C — correctness first** when scale or instrumentation reveals invalid
  publication, identity drift, cleanup divergence, nondeterminism, incomplete-state execution,
  stack failure, malformed query output, or another correctness defect.
- Choose **Branch D — evidence insufficient** only after improving the experiment within
  reasonable scope. Record exactly what remains unknown and why no architecture decision is
  justified.
- Do not choose Branch B solely because one phase is measurable.
- Do not choose Branch A solely because the smallest sample is fast.
- Do not choose a general incremental architecture in this turn even when evidence suggests
  future incrementality. Record the exact affected facts and required invariants as a later
  decision gate.
- A measurement-only commit is a complete successful result when Branch A is supported.
- A documentation-only final state is acceptable when the reusable harness already exists and no
  code change is necessary.

### Branch A — retain full recomputation

- Keep the current transaction and query architecture.
- Retain only measurement code that has a clear future regression or decision consumer.
- Delete exploratory instrumentation with no retained consumer.
- Record the representative baseline and limitations in `docs/performance.md`.
- Update `docs/status.md` to state what is measured and what remains unmeasured.
- Move the roadmap beyond the completed measurement item without creating an incrementality
  project.
- Do not phrase full recomputation as permanently optimal.
- State the scale and workload at which it is currently adequate.
- State the reversal condition that would reopen the decision.
- Stop.

### Branch B — correct one local pathology

- Name the exact root cause in one sentence before editing production code.
- Name the exact producer, consumer, authority, lifetime, failure behavior, and affected
  workload.
- Prefer deletion, reuse of existing order, a local early exit, a local precomputed range, or a
  single-purpose index over a framework.
- Implement the smallest dependency-closed correction.
- Update every active producer and consumer of the changed fact.
- Delete displaced code and obsolete tests.
- Do not retain a compatibility path.
- Add a focused regression test that fails on the original root cause.
- Add semantic-equivalence and failure-atomicity tests.
- Collect equivalent after samples using the same harness, host, build state, geometry, and
  selection rules.
- Compare deterministic work before timings.
- Compare end-to-end agent-loop cost, not only the optimized phase.
- Compare retained memory and index-build cost when a new retained fact is added.
- Keep the correction only if benefit justifies code, tests, memory, compile cost, and
  maintenance.
- Revert or redesign when equivalent evidence does not support the change.
- Stop after this one correction.

### Branch C — correctness first

- Reduce the defect to the smallest semantic reproducer.
- Classify the violated authority: language semantics, workspace contract, identity,
  transaction, query, compiler, ownership, runtime, or documentation.
- Fix the dependency-closed root cause.
- Do not weaken the measurement or test to avoid the defect.
- Add a focused regression test and an independent oracle where cheap.
- Verify old snapshot validity and allocator atomicity when staging is involved.
- Verify cleanup and exactly-once effects when control or ownership is involved.
- Update the owning specification only when intended semantics change.
- Record that the original recomputation decision remains open when the corrected baseline was
  not completed.
- Stop after the correctness vertical.

## 22. Candidate local hypotheses, not preselected solutions

The following candidates are reasons to inspect and measure, not instructions to implement.
Reject any candidate whose benefit is not demonstrated on the selected complete loop.

### metadata-only transaction classification

- **Hypothesis:** A `RefineHole`-only transaction may not require cloning or compacting
  executable program state.
- **Required proof:** Prove that the edit cannot affect identities, types, effects, ownership,
  indexes, or diagnostics beyond its exact hole record before introducing a narrow path.
- **Guardrail:** Do not create a general transaction planner.

### no-deletion compaction bypass

- **Hypothesis:** Compaction may traverse and remap every dense space even when no declaration,
  binding, local, or plan can disappear or move.
- **Required proof:** Define exact preconditions from current edit semantics and compare against
  W8 deletion behavior.
- **Guardrail:** Do not maintain parallel compacted and uncompacted representations.

### reuse of canonical index ordering

- **Hypothesis:** Entity, reference, call, or dependency vectors may already have stable order
  before query-time sorting.
- **Required proof:** Prove the order after identity reconciliation and every producer.
- **Guardrail:** Do not depend on accidental vector order without a tested contract.

### page-without-full-materialization

- **Hypothesis:** A small page may currently clone and sort every candidate.
- **Required proof:** Preserve stable continuation semantics, completeness, filtering, and
  deterministic order.
- **Guardrail:** Do not add a general iterator or query DSL when one bounded scan suffices.

### targeted reverse-edge range

- **Hypothesis:** References or calls to one target may scan all edges.
- **Required proof:** Measure target density, query frequency, index-build time, and retained
  memory.
- **Guardrail:** Do not add every conceivable reverse index.

### owner-local body traversal

- **Hypothesis:** Projection of one body may inspect every snapshot node and allocate a
  full-snapshot depth map.
- **Required proof:** Use existing containment or child indexes only when they preserve semantic
  order and complete body coverage.
- **Guardrail:** Do not create a second tree authority.

### signature binder lookup reuse

- **Hypothesis:** Function signature queries may scan all entities to recover owned type
  parameters.
- **Required proof:** Reuse an existing stable owner relation or narrow index if measured.
- **Guardrail:** Do not expose binder strings or dense ordinals as public identity.

### avoid repeated type-view conversion within one response

- **Hypothesis:** Projection may request a query and then repeat related type conversion.
- **Required proof:** Share one response-local derived fact only within the call.
- **Guardrail:** Do not retain a global type-view cache.

### diagnostic outcome borrowing or sharing

- **Hypothesis:** A transaction outcome may clone all diagnostics already retained by the
  snapshot.
- **Required proof:** Measure diagnostic volume and API ownership requirements.
- **Guardrail:** Do not complicate the public API for an unmeasured tiny copy.

### complete-HIR derivation handoff

- **Hypothesis:** A complete transaction may derive and validate HIR, then an immediate compile
  derives it again.
- **Required proof:** Measure duplicate work and define a one-shot ownership/lifetime boundary
  if correction is justified.
- **Guardrail:** Do not make HIR a coequal snapshot authority or add a general compilation
  cache.

### skip redundant match refresh

- **Hypothesis:** Structural edits in programs with matches may inspect plans unrelated to the
  affected root.
- **Required proof:** Measure exact plans and roots touched.
- **Guardrail:** Do not weaken canonical usefulness, exhaustiveness, or result-type refresh.

### narrow effect recomputation

- **Hypothesis:** A small edit may infer effects across every function.
- **Required proof:** Prove effect dependencies and changed roots before considering local
  recomputation.
- **Guardrail:** Do not build a generic invalidation graph in this turn.

### preallocation from exact known counts

- **Hypothesis:** Repeated vector growth may be visible in deterministic allocations or RSS.
- **Required proof:** Use exact local counts already available.
- **Guardrail:** Do not add a global allocator or capacity prediction system.

### remove duplicate map rebuild

- **Hypothesis:** Index construction and identity reconciliation may rebuild overlapping maps.
- **Required proof:** Trace authority and consumers before combining work.
- **Guardrail:** Do not let reconciliation accept unvalidated canonical indexes.

### special-case direct queries

- **Hypothesis:** Direct identity queries should be map lookups rather than scans.
- **Required proof:** Verify current behavior and type-view costs.
- **Guardrail:** Do not add redundant maps for already constant-time cases.

### reduce projection bookkeeping

- **Hypothesis:** Depth or selection bookkeeping may be larger than emitted output.
- **Required proof:** Measure nodes inspected versus emitted.
- **Guardrail:** Preserve stack safety and selected semantic ordering.

### reuse compact diff facts

- **Hypothesis:** Transaction staging may already know created, deleted, or rewired facts later
  rediscovered globally.
- **Required proof:** Prove completeness for every edit kind before reusing them.
- **Guardrail:** Do not make a partial edit log the semantic authority.

### avoid work on incomplete compiler path

- **Hypothesis:** Incomplete snapshots must stop before complete HIR, ownership, memory, SSA,
  and bytecode phases.
- **Required proof:** Use counters to verify zero work.
- **Guardrail:** Do not optimize by fabricating executable placeholders.

### reduce outcome output

- **Hypothesis:** Agent-visible results may duplicate unchanged diagnostics or broad
  projections.
- **Required proof:** Measure next-decision usefulness and bytes.
- **Guardrail:** Do not omit structured facts needed for exact action.

### merge unjustified representation boundary

- **Hypothesis:** A crate or intermediate model may exist only to convert internal descriptors.
- **Required proof:** Use profiles and current consumers before restructuring.
- **Guardrail:** Do not combine this with the recomputation correction unless it is the measured
  root cause.

## 23. Correctness invariants that dominate performance

### one semantic authority

- **Requirement:** A snapshot's `SemanticProgram` owns mutable program meaning; source,
  projection, HIR, indexes, and compiled values remain derived or attached.
- **Minimum evidence:** Compare source-free and imported semantic outcomes and ensure no new
  mutable mirror appears.

### source-free construction

- **Requirement:** Selected program creation, edit, query, compile, and run paths invoke source
  loading and parsing zero times.
- **Minimum evidence:** Retain or extend exact counters and assertions.

### honest incomplete state

- **Requirement:** Missing entry points, bodies, and expressions remain explicit blockers or
  holes with unknown facts and no hidden executable subtree.
- **Minimum evidence:** Assert zero complete-HIR, memory, SSA, bytecode, native, and VM work for
  incomplete compile.

### atomic publication

- **Requirement:** A transaction publishes one complete revision or nothing.
- **Minimum evidence:** On failure compare revision, `Arc`, diagnostics, projection, allocator
  state, and deterministic retry.

### stable survivor identity

- **Requirement:** Unchanged semantic entities and nodes retain public identity across private
  relocation where current contracts promise survival.
- **Minimum evidence:** Compare exact public identities before and after representative edits
  and deletions.

### tombstone safety

- **Requirement:** Deleted identities never silently resolve to later same-slot meaning.
- **Minimum evidence:** Delete, query stale identity, recreate later, and assert generation
  separation.

### old snapshot validity

- **Requirement:** Retained immutable snapshots remain queryable and executable according to
  their original state.
- **Minimum evidence:** Hold old `Arc` values across successful edits and verify exact old/new
  outcomes.

### namespace safety

- **Requirement:** Foreign workspace identities fail before mutation or query publication.
- **Minimum evidence:** Use deterministic separate workspaces in focused tests.

### kind safety

- **Requirement:** Wrong-kind entity, node, hole, trait, field, or binding identities fail
  explicitly.
- **Minimum evidence:** Test the changed API boundary, not every kind in unrelated code.

### revision safety

- **Requirement:** Queries, continuations, and transactions remain bound to the exact revision
  and namespace.
- **Minimum evidence:** Use stale continuation and stale base-revision regressions.

### deterministic ordering

- **Requirement:** Entities, edges, query pages, match arms, projections, diffs, blockers, and
  diagnostics use stable documented order.
- **Minimum evidence:** Repeat exact operations and decode or compare complete structured
  results.

### complete pagination

- **Requirement:** Pagination never silently truncates, duplicates, skips, or crosses query
  identity.
- **Minimum evidence:** Collect all pages and compare with the authoritative complete result.

### public semantic types

- **Requirement:** Public types use stable semantic or explicit builtin identities, never
  product names, dense indexes, or binder strings as universal identity.
- **Minimum evidence:** Inspect changed query and projection values.

### generic exactness

- **Requirement:** Type arguments follow stable binder identity and declaration order; witnesses
  and instantiated types are exact.
- **Minimum evidence:** Compare generic signature and call views before and after.

### match exactness

- **Requirement:** Usefulness, exhaustiveness, ordered arms, fields, payload scopes, and result
  types remain canonical.
- **Minimum evidence:** Compare `MatchView`, compilation, and runtime outcome.

### lexical scope

- **Requirement:** Immutable, mutable, parameter, payload, and hidden compiler bindings preserve
  exact visibility and activation rules.
- **Minimum evidence:** Query hole context and reject forward or cross-arm uses.

### ownership legality

- **Requirement:** Move, borrow, mutation, reinitialization, and cleanup follow canonical
  ownership analysis.
- **Minimum evidence:** Use W3 and relevant failed-edit assertions.

### deterministic cleanup

- **Requirement:** Normal, early-return, trap, policy failure, call failure, and teardown paths
  release exactly what they own.
- **Minimum evidence:** Assert owner, loan, backlog, and teardown metrics where exposed.

### exactly-once effects

- **Requirement:** A specialized attempt declines before effects or commits once; there is no VM
  retry after native entry.
- **Minimum evidence:** Retain current execution integration tests when the compile/run path
  changes.

### effect-free check

- **Requirement:** `check` compiles and validates but never executes program effects.
- **Minimum evidence:** Use an observable effect fixture and assert no effect.

### generic route completeness

- **Requirement:** Every supported program retains the validated VM route even when native
  specialization is unavailable.
- **Minimum evidence:** Use an unsupported-native but VM-supported workload when execution
  wiring changes.

### stack safety

- **Requirement:** User-controlled semantic depth does not consume unbounded native stack across
  construction, clone, edit, query, projection, compile, and destruction.
- **Minimum evidence:** Run the relevant retained small-stack fixture after traversal changes.

### no arbitrary validity quota

- **Requirement:** Trusted program validity does not depend on project-selected counts of
  syntax, nodes, fields, locals, functions, files, or IR.
- **Minimum evidence:** Do not introduce count rejection; use generated scale tests for
  algorithm shape.

### checked representation boundary

- **Requirement:** Narrow native, host, and compact indexes use checked conversion and decline
  or fail safely.
- **Minimum evidence:** Exercise the changed boundary with focused large-index or malformed
  input tests.

### failure-atomic allocation

- **Requirement:** Host allocation failure cannot partially publish semantic or artifact state.
- **Minimum evidence:** Preserve fallible allocation paths and existing failure-atomic design.

### truthful diagnostics

- **Requirement:** Structured facts come from the producer; renderers do not parse one another
  or fabricate spans, identities, causes, or suggestions.
- **Minimum evidence:** Decode machine output as a consumer would.

### bounded debug and review

- **Requirement:** Debug and selected projection output do not recursively expand unbounded
  semantic trees or unrelated bytes.
- **Minimum evidence:** Measure and assert bounded output where the changed path touches
  rendering.

### source provenance honesty

- **Requirement:** Source-backed facts retain real source origins; source-free edits retain
  semantic origins without synthetic files or hashes.
- **Minimum evidence:** Compare origin-sensitive facts only where origin is semantically
  relevant.

### package and capability validation

- **Requirement:** Required-package compile validates manifest, lock, target, and grants at the
  real boundary.
- **Minimum evidence:** Do not bypass package checks to improve development-snapshot
  measurements.

### unsafe boundary isolation

- **Requirement:** Executable memory, generated ABI entry, OS calls, SQLite, and FFI remain
  narrow named mechanisms with safe-caller contracts.
- **Minimum evidence:** Run relevant malformed-boundary checks if touched.

### one active path

- **Requirement:** A correction replaces the old path directly; no feature-flagged compatibility
  route, shadow query path, or parallel index authority remains.
- **Minimum evidence:** Search active producers and consumers after the cutover.

## 26. Implementation discipline

- Prefer deletion of unnecessary work before adding retained state.
- Prefer reuse of an existing canonical order before adding a sort cache.
- Prefer one local index for one measured query before a universal index registry.
- Prefer response-local derived facts before snapshot-global caches.
- Prefer a narrow fast path with exact semantic preconditions before a transaction-planning
  framework.
- Prefer full recomputation when its simplicity is adequate.
- Keep the mechanism smaller than the measured problem.
- State the deletion condition for every new retained map, counter, metrics field, script, and
  test.
- Do not expose measurement-only concepts in public language semantics.
- Do not make private timing phases part of a compatibility contract.
- Use mature dependencies only when they remove substantial machinery or risk.
- Do not add a dependency for functionality clearer as local code.
- Organize code by ownership and coherent responsibility, not line counts.
- Split a module only when the split reduces change coupling or establishes a real boundary.
- Merge a boundary only when current consumers and profile evidence show it is conversion-only
  overhead.
- Preserve unrelated APIs and files only when they remain active, not for backward
  compatibility.
- Use one direct cutover and delete the displaced implementation.
- Do not leave disabled code, TODO compatibility, commented alternatives, or a dormant feature
  flag.
- Keep public result models semantic and structured.
- Keep dense IDs private and replaceable.
- Keep every fallible allocation and checked conversion honest.
- Do not use `unwrap`, `expect`, `panic`, `todo`, or `unimplemented` in production code under
  current lint policy.
- Confine unsafe code to the existing named mechanisms if any unsafe boundary must change.
- Do not use `|| true`, broad log filtering, or redirected failures to make verification look
  successful.

## 33. Closing directive

Be willing to conclude that no production optimization is warranted. That conclusion, when
supported by representative evidence and a reusable compact baseline, is better engineering than
an impressive but speculative incremental architecture. Conversely, when one local phase is
demonstrably wrong in complexity or duplicated work, correct it decisively, delete the displaced
path, prove semantic equivalence, and stop. The long-term goal is not maximal machinery. It is a
small, exact, AI-primary language system whose complexity is paid for by current semantics and
measured product value.
