### 4.6 Copy semantics

### 4.7 Purity

### 4.8 One writer and one head

## 10. Expression Model Alternatives

Evaluate at least the following alternatives.

### 10.1 Alternative A: retain explicit-only values

Shape:

- `ValueDraft` remains reference-only;
- every used operation result requires an explicit draft symbol;
- current graph and normalization remain unchanged.

Advantages:

- smallest implementation change;
- current contract is already verified;
- every referenced operation is explicitly named;
- simple error paths;
- no recursive public DTO.

Costs:

- one-use values require names;
- large creation payloads contain repeated symbols;
- agents invent semantically meaningless labels;
- initial authoring remains visually flat and scaffold-heavy;
- interface cost remains measured.

Retain this only if inline alternatives fail dependency closure or do not improve equal-task evidence.

### 10.2 Alternative B: fully recursive expression values

Shape:

- a value input is either an existing value reference or a boxed expression draft;
- inline expressions may recursively contain inline values;
- the normalizer flattens the tree into canonical operations;
- persistent operation nodes remain in the authoritative graph.

Advantages:

- one uniform proposal form;
- captures all one-use expression kinds;
- can reduce labels substantially;
- may align proposal structure with semantic use.

Risks:

- recursive DTO and schema;
- depth and item accounting;
- error-path precision;
- allocation-order ambiguity;
- region-owning expression complexity;
- hole addressability;
- contract size;
- potential duplicate normalization logic;
- possible stack recursion in serde or helper code.

Select only if one iterative algorithm closes every obligation.

### 10.3 Alternative C: regionless complete inline expressions only

Shape:

- a value input may contain an inline expression only when the operation is complete, non-terminating, single-result, and owns no region;
- conditions, loops, matches, holes, yields, and returns remain explicit;
- eligibility derives from executable operation descriptors where practical.

Advantages:

- addresses the bulk of constants, arithmetic, calls, projections, and constructors;
- smaller normalization problem;
- repair targets remain explicit;
- region control remains flat.

Risks:

- a second subset vocabulary;
- descriptor and serde duplication;
- agents must learn two expression categories;
- future expansion pressure;
- may miss enough measured labels to be unhelpful.

Select only if it is materially simpler and the subset definition has one executable authority.

### 10.4 Alternative D: expression-local `let` scopes

Shape:

- introduce a nested expression block with local bindings;
- values refer to scoped local names;
- normalize to canonical operations.

Advantages:

- supports sharing without top-level flat labels;
- familiar structured shape.

Risks:

- effectively creates a proposal mini-language;
- new lexical scope and shadowing rules;
- more names rather than fewer;
- possible duplication of semantic visibility;
- larger schema and diagnostics.

Reject by default.

Retain only if direct recursive values cannot represent a measured common case and a real second consumer exists.

### 10.5 Alternative E: authoritative embedded expressions

Shape:

- some expressions cease being persistent graph nodes;
- their structure is embedded inside a parent semantic operation;
- identity exists only after explicit promotion or sharing.

Advantages:

- fewer persistent nodes and artifacts;
- structural sharing or compact storage may improve scale;
- proposal and authority could align more closely.

Risks:

- major semantic-model change;
- new node-versus-term distinction;
- history and diff complexity;
- repair and maintenance targeting;
- identity promotion semantics;
- compiler and query changes;
- artifact and schema replacement;
- possible second validator;
- very weak current evidence.

Do not select during the mandatory milestone unless measurements prove current persistent expression identity is a material product problem and a complete model replacement is demonstrably simpler.

### 10.6 Alternative F: textual expression import

Shape:

- accept a compact text expression and parse it into the graph.

Advantages:

- compact familiar notation;
- model providers are trained on text.

Risks:

- new parser, grammar, diagnostics, precedence, source spans, and import semantics;
- pressure toward source authority;
- a second authoring language;
- no current evidence that text solves stable identity or repair better.

Reject for this campaign.

### 10.7 Required decision table

For every alternative, score:

- one-authority preservation;
- type precision;
- validator reuse;
- deterministic normalization;
- persistent identity behavior;
- repairability;
- fine-grained maintenance;
- request bytes;
- explicit labels;
- machine-contract bytes;
- error quality;
- depth safety;
- item accounting;
- implementation size;
- test surface;
- documentation burden;
- agent success rate;
- long-term extensibility;
- reversal cost.

Do not select from aesthetics alone.

## 11. Default Inline Contract Hypothesis

Unless the decision table defeats it, implement one recursive value-position expression form with these properties.

A public value input is exactly one of:

- a reference to a function parameter;
- a reference to an operation result;
- a reference to a block argument;
- one inline expression.

An inline expression:

- produces exactly one value;
- appears at exactly one value-use site;
- has no public draft symbol;
- cannot be selected directly in the transaction receipt;
- is normalized into a normal persistent operation node;
- receives a deterministic persistent Node ID;
- is validated by the normal graph validator;
- is visible only through its normalized semantic position;
- may be queried and diffed by Node ID after commit;
- does not persist its proposal nesting;
- does not make symbol spelling affect allocation.

Do not accept an inline expression merely by recursively deserializing the existing `ExpressionDraft`.

Define exact behavior for:

- holes;
- region-owning expressions;
- calls;
- forward function references;
- forward nominal references;
- product field bindings;
- variant payloads;
- match arm bodies;
- loop body values;
- nested structured bodies;
- traps;
- selected returned bindings;
- error paths;
- maximum nesting;
- maximum items;
- canonical order.

The implementation may narrow the eligible set after evidence.

It may not leave two overlapping preferred ways without a reason.

## 12. Hole and Repair Policy

A typed placeholder is incomplete and later repair depends on addressability.

Evaluate these policies.

### 12.1 Forbid anonymous inline holes

Advantages:

- every hole has an explicit draft symbol;
- the receipt can return its Node ID;
- repair context remains straightforward;
- no path-to-identity mechanism is needed.

Costs:

- a hole cannot appear directly inside a parent proposal;
- the author must bind the incomplete value.

Default: prefer this policy for the first retained inline form.

### 12.2 Allow inline holes with mandatory path selection

This would require a stable public path to an implied node.

Risks:

- path becomes quasi-identity;
- proposal shape may affect later repair;
- receipts and idempotency expand;
- canonical-equivalence becomes harder.

Reject unless a measured task needs it.

### 12.3 Allow inline holes with automatic blocker return

Risks:

- receipts become less selected and more implicit;
- multiple holes require ordering;
- output size and contract grow;
- behavior couples transaction creation to repair queries.

Reject by default.

### 12.4 Promote inline hole to explicit identity after commit

Every normalized operation already receives Node ID.

The problem is returning it.

Do not invent a promotion mutation merely to solve proposal addressability.

Prefer an explicit symbol at creation.

## 13. Region-Owning Expression Policy

`if`, `for_i64`, and complete variant handling own nested regions.

Evaluate whether they can be inline in the first retained contract.

### 13.1 Full support

Requirements:

- iterative flattening of nested value and body structures;
- canonical pre-order or post-order allocation;
- exact body ownership;
- exact captures;
- error paths through value and region positions;
- depth and item accounting across both nesting dimensions;
- equivalent explicit and inline graph proof.

### 13.2 Defer region-owning inline expressions

Requirements:

- exact machine description of the eligibility restriction;
- no duplicated hand-maintained operation list;
- a future extension path;
- evidence that regionless values capture most measured labels.

Default: defer if full support materially risks dependency closure.

Do not keep a partially implemented region-owning variant.

### 13.3 Descriptor-derived eligibility

Prefer deriving properties such as:

- result count;
- completeness;
- terminator status;
- region arity;
- refinement eligibility;

from the executable operation descriptors.

Do not create a second manually maintained semantic catalogue solely for inline eligibility.

Serde wire types may still require direct closed variants.

Guard agreement exhaustively.

## 14. Canonical Normalization Requirements

Normalization is the core of the campaign.

It must be specified before implementation.

### 14.1 One algorithm

Use one normalization algorithm for:

- top-level function bodies;
- nested yielding bodies;
- explicit expressions;
- inline value expressions;
- implied regions;
- implied blocks;
- implied block arguments;
- implied terminators;
- normalized product fields;
- normalized match arms.

Do not add one recursive flattener beside the current event-driven expander.

Extend or replace the current explicit worklist coherently.

### 14.2 No user-depth native recursion

Use explicit work items.

The maximum public structured depth may remain small.

That does not justify recursive algorithms in core normalization.

Tests must exercise the maximum accepted shape and first rejected shape.

### 14.3 Deterministic order

Define one exact traversal order.

Candidate rule:

- traverse outer transaction operations in request order;
- within a structured body, preserve explicit operation order;
- for an inline parent operand, normalize child expressions left to right before the parent;
- normalize identity-keyed product fields into declaration order;
- normalize match arms into declaration order;
- allocate explicit and implicit nodes according to the flattened canonical order;
- make draft-symbol spelling irrelevant.

This is a candidate, not an instruction to ignore current ordering.

Choose the order that preserves exact graph equivalence with the retained explicit replay where possible.

### 14.4 Canonical equivalence

Define whether these are equivalent:

- an explicit bound constant followed by an add;
- the same constant inline in the add;
- nested inline arithmetic versus a flat topological expression list;
- product field values in different request orders;
- match arms in different request orders;
- explicit versus inline calls;
- omitted versus explicit unselected bindings.

For equivalent proposals, target:

- same persistent node kinds;
- same owners;
- same child order;
- same direct references;
- same value uses;
- same allocator frontier;
- same Node IDs;
- same snapshot hash;
- same artifact bytes;
- same change list and digest;
- same completeness;
- same run behavior.

Receipt returned bindings may differ only because an inline expression cannot be selected.

If exact equality is not retained, document the precise semantic reason.

### 14.5 Allocation preflight

Count every explicit and implied node before publication behavior can diverge.

Validate all proposal-local references and eligibility before consuming persistent identities.

Rejected and validate-only proposals leave the published frontier unchanged.

Commit and validate-only predict the same IDs and snapshot.

### 14.6 Item accounting

Define exactly what counts as one structured draft item.

Include:

- top-level transaction operations;
- declarations;
- members;
- parameters;
- bodies;
- expression nodes;
- inline expression nodes;
- value-reference wrappers where policy says so;
- call arguments;
- product fields;
- match arms;
- nested bodies;
- selected symbols.

Do not double-count one semantic object through multiple wrappers.

Do not omit recursive inline children.

Use checked arithmetic.

Reject before allocation when the bound is exceeded.

### 14.7 Depth accounting

Define one public nesting metric.

Clarify whether depth includes:

- an inline expression edge;
- an operation-owned body edge;
- a match arm;
- a loop body;
- a product field value;
- a variant payload;
- a call argument;
- a wrapper variant.

The machine contract must state the metric.

Tests must cover mixed nesting, not only a chain of additions.

### 14.8 Error paths

A failure inside an inline expression needs a bounded deterministic path.

The path must identify semantic proposal positions without pretending to be persistent identity.

Include enough detail to locate:

- transaction operation;
- function body;
- explicit expression index;
- operand or argument;
- product field identity or normalized ordinal;
- match variant identity;
- nested body role;
- inline child;
- final invalid target or type.

Do not expose synthetic private symbols.

Do not use unbounded prose paths.

Do not make error text the only machine-readable locator.

### 14.9 Scope and dominance

Inline normalization must preserve current lexical visibility.

A child expression may use:

- visible function parameters;
- visible block arguments;
- prior explicit values;
- earlier normalized inline siblings only if the contract deliberately exposes them;
- nested inline descendants.

A child may not use:

- its parent result;
- a later sibling result;
- a value in another arm;
- a value produced after the parent;
- an unbound anonymous inline result.

The final graph validator remains authoritative.

Early proposal validation should improve errors without becoming a competing scope engine.

### 14.10 Shared values

An inline expression result has one use by construction.

When two parents need the same result:

- require an explicit bound expression;
- refer to its symbol or resulting Node ID;
- do not duplicate it silently;
- do not perform common-subexpression elimination in proposal normalization.

Optimization is derived later.

Proposal spelling must not define semantic sharing accidentally.

### 14.11 Traps and evaluation order

Inline syntax does not authorize eager evaluation.

The normalized graph preserves existing lazy condition and match semantics.

A potentially trapping child in an unselected branch must remain unexecuted.

Do not flatten across region boundaries.

Do not reorder checked arithmetic or calls in a way that changes fuel or trap behavior.

- out-of-range behavior;
- concatenation;
- length conversion to `i64`;
- fuel cost;
- memory cost;
- trap or result behavior;
- deterministic encoding;
- constant persistence;
- query visibility;
- diff behavior.

Do not add operations because they are conventional.
Add only those required by the consumer and coherent future use.

### 23.5 Representation alternatives

Compare:

- inline bytes in value cells;
- a verified side table of immutable byte objects;
- `Arc<[u8]>` or equivalent safe shared backing;
- frame-local arenas;
- interpreter-global immutable object handles;
- copy-on-write;
- content-addressed deduplication;
- external blob store.

Evaluate:

- safe Rust;
- clone cost;
- transfer across calls and blocks;
- frame teardown;
- peak accounting;
- deterministic identity;
- hash cost;
- result projection;
- serialization;
- future native backend;
- future effects;
- future collections;
- artifact size.

Do not introduce content-addressed semantic identity.

Do not introduce global deduplication without measured value.

### 23.6 Memory-safety contract

A valid byte program must not express:

- raw pointers;
- unchecked indexing;
- stale handles;
- use-after-free;
- mutable aliasing;
- unbounded allocation;
- integer-wraparound lengths;
- unbounded native recursion.

Every allocation and copy or share operation has checked bounds.

The runtime distinguishes logical bytes from physical retained bytes.

Peak accounting includes:

- input backing;
- live values;
- shared backing;
- slices;
- concatenation result;
- temporary scratch;
- public flattening;
- returned values.

Do not count the same shared backing as multiple physical allocations unless the policy intentionally charges logical ownership.

State the policy clearly.

### 23.7 Protocol encoding

Compare:

- lowercase hexadecimal;
- canonical base64;
- integer arrays;
- an out-of-band frame;
- a separate blob handle.

Use one canonical representation.

Consider:

- schema simplicity;
- byte overhead;
- dependency cost;
- strict decoding;
- invalid padding;
- output bounds;
- tool compatibility;
- human inspectability;
- cache behavior.

Do not add a second transport for one value without overwhelming evidence.

### 23.8 Core IR and verifier

Define a typed bytes representation in Core IR only if the semantic gate passes.

The verifier must check:

- exact type;
- operation operands and results;
- object-handle domains;
- bounds policy;
- transfer semantics;
- instruction-specific invariants;
- frame or heap footprint metadata.

Do not persist private object handles.

### 23.9 Runtime

Keep the current interpreter as the oracle.

Add no unsafe code.

Test:

- empty bytes;
- maximum accepted bytes;
- first rejected bytes;
- nested calls;
- branch transfer;
- loop transfer;
- result return;
- sharing;
- slices;
- concatenation;
- out-of-range;
- fuel exhaustion;
- memory exhaustion;
- daemon continuation;
- restart where constants are persisted.

### 23.10 Artifact and schema

If bytes constants or semantic types enter the SPG:

- replace semantic schema identity;
- replace artifact format;
- update every reader and writer;
- delete old success readers;
- update history validation;
- update machine schema;
- update examples and docs.

If bytes exist only as runtime input with operations already represented:

- justify why no semantic schema change is needed.

Do not misclassify a semantic type addition as protocol-only.

### 23.11 Go gate

Implement bytes only if:

- the consumer is compelling;
- semantics are narrow and complete;
- representation remains memory-safe in safe Rust;
- resource accounting is exact;
- compiler and verifier changes are coherent;
- protocol encoding is strict;
- artifact changes are dependency-closed;
- retained tests are realistic;
- no universal memory manager is selected prematurely;
- mandatory campaign evidence is already complete.

### 23.12 Stop gate

Stop and defer if:

- the only consumer is a toy echo;
- indexing requires a broad exception system;
- representation forces a runtime rewrite;
- accounting remains ambiguous;
- generic sequence pressure dominates;
- artifact migration cannot close;
- tests or documentation become partial;
- the campaign would end without a green full boundary.

A clean no-go decision is better than half a heap.

## 24. Memory-Safety Review Framework

Apply this framework to every material change.

### 24.1 Language expressiveness

Can a valid program express an invalid address, unchecked access, invalid cast, uninitialized read, data race, use-after-move, or double close?

If yes, redesign.

### 24.2 Semantic validation

Are all operand, result, ownership, visibility, layout, and completeness rules checked before lowering?

Do not trust proposal normalization.

### 24.3 Boundary validation

Are lengths, counts, depths, variants, IDs, numbers, UTF-8, trailing bytes, and allocation sizes checked before use?

### 24.4 Implementation safety

Does safe Rust enforce the intended lifetime and aliasing contract?

Could logic errors still index the wrong object or reuse an invalid handle?

Add verifier and runtime checks.

### 24.5 Resource exhaustion

Name every bounded quantity.

Do not call resource exhaustion memory unsafety.

Do not leave it unbounded because allocation is safe.

### 24.6 Stack safety

Use explicit work structures for user-controlled nesting, recursion, graph traversal, validation, normalization, compilation, and interpretation.

### 24.7 Cleanup

State what happens on:

- normal return;
- semantic rejection;
- runtime trap;
- fuel exhaustion;
- frame exhaustion;
- cancellation;
- timeout;
- client disconnect;
- daemon shutdown;
- process crash.

### 24.8 Concurrency

No current mandatory change needs concurrency.

If an optional adapter introduces tasks or threads, define lifecycle and joins.

Do not let adapter concurrency mutate semantic state outside the daemon.

### 24.9 Authority

Memory safety does not authorize host access.

Keep explicit permission boundaries.

### 24.10 Trusted computing base

List compiler, standard library, Cargo, OS, filesystem, socket implementation, dependencies, build scripts, native code, and generated code.

Update the list when it changes.

## 29. Reversal Conditions

- it requires a second semantic validator;
- normalized graphs differ unpredictably;
- persistent allocation depends on symbol spelling;
- error locations become materially worse;
- depth or item accounting is ambiguous;
- core code uses user-depth recursion;
- machine contract grows disproportionately;
- equal-task labels or failures do not improve;
- maintenance becomes harder;
- region-owning support remains partial;
- old and new paths coexist without need.

Reverse or delete a Codex adapter if:

- it duplicates accepted request types;
- tool order or schema is unstable;
- lifecycle failures exceed CLI failures;
- it adds disproportionate dependencies;
- equal-task evidence shows no material benefit;

Stop optional bytes work if:

- the consumer is artificial;
- memory policy is ambiguous;
- a universal heap rewrite becomes necessary;
- artifact or runtime changes cannot close;
- safe Rust is insufficient without a separately authorized boundary;
- full verification cannot complete.

## 32. Long-Horizon Architecture Review

Complete this review after the mandatory implementation and before final roadmap selection.

For every lens, distinguish current fact, enduring requirement, campaign decision, evidence gate, and reversal condition.

Do not implement every possible future direction.

The purpose is to prevent accidental policy lock-in while keeping this campaign focused.

### 32.1 Product boundary

Current audited baseline:

- The current product boundary is a local service that owns a typed versioned program model while an external coding agent supplies typed proposals.

Enduring requirement:

- Keep human intent and governance outside deterministic acceptance; keep one semantic authority inside the service.

Decision for this campaign:

- Do not add model orchestration. Improve the machine programming surface and prove it with equal tasks.

Evidence required before broader entry:

- A representative agent can author, repair, inspect, and run a program without implementation source.

Stop or reversal condition:

- Reverse any feature that makes model behavior part of language correctness.

### 32.2 Human role

Current audited baseline:

- Humans are first-class at intent, review, explanation, governance, and operation, but not expected to hand-author authority.

Enduring requirement:

- Do not erase human agency in the name of agent optimization.

Decision for this campaign:

- Keep human-facing explanations and review views truthful while optimizing authoring for agents.

Evidence required before broader entry:

- A human can understand what was changed, why it was accepted, and what authority it uses.

Stop or reversal condition:

- Reject opaque automation that cannot produce bounded semantic explanations.

### 32.3 Source independence

Current audited baseline:

- Source text is not program authority; no source frontend currently exists.

Enduring requirement:

- Optional text must import or render the same semantic model and never become coequal truth.

Decision for this campaign:

- No source parser in this campaign. Keep policy open to future views.

Evidence required before broader entry:

- A future frontend can be added without changing identity or execution semantics.

Stop or reversal condition:

- Reject render-and-reparse workflows for normal editing.

### 32.4 Semantic model shape

Current audited baseline:

- The SPG is a closed typed model implemented with direct Rust types, maps, vectors, and explicit relations.

Enduring requirement:

- Closed semantic kinds and one validator remain authoritative; physical storage remains open.

Decision for this campaign:
