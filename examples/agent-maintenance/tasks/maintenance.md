# Sealed maintenance tasks

These tasks define intent and external oracles. They deliberately omit request payloads, packet aliases, durable IDs, and editable-document spelling.

## Reading seal

A controlled agent may read the repository's user-facing README, `lkjscript agent orient`, `lkjscript agent help`, exact schema roots it requests, task-scoped context packets and derived views, typed errors, semantic diffs, and this task statement. It may not read Rust implementation source, private tests, example drivers, prior transcripts, old prompts, git history, or stored answer payloads.

## Task sequence

1. Construct the deployment-policy application with a reachable `i64` placeholder in score calculation. Publish that incomplete revision and show that execution is blocked.
2. Attempt to replace the placeholder with a deployment-decision value. Prove rejection, unchanged head, unchanged next predicted identity, and engine usability.
3. Refine the same placeholder to the legal checked addition. Preserve identity, validate before commit, and obtain the exact accepted/rejected policy matrix.
4. Extend accepted scores by two through a new helper and changed call path. Preserve every rejection result.
5. Refactor that extension into one helper call without changing any result.
6. Rename the resource-memory presentation name while preserving identity and behavior.
7. Publish an entry that deterministically overflows checked `i64` addition. Locate it using only the typed runtime error and a debug context packet, then correct its exact constant producer so the entry returns zero.
8. Replace the immutable `Limits` record with `DeploymentLimits`, adding a rollout flag. Migrate construction, projection, function input, decision output flow, and call sites. A disabled rollout must reject with the exact trust-policy reason.
9. First prove deletion of `Limits` rejects while references survive. Then atomically select the migrated entry and delete the old entry, old decision function, old declaration, and temporary debug function.
10. Reopen the workspace. Re-run the incomplete revision, pre-extension behavior, extended/refactored behavior, historical trap, repaired debug entry, and migrated current entry. Inspect a multi-revision semantic diff.

## Exact oracle

- Before extension, the no-argument main result is `Decision.accept(25)`.
- After extension and refactor, it is `Decision.accept(27)`.
- CPU, memory, unsupported-target, and untrusted-release inputs preserve their exact rejection alternatives.
- The debug revision reports `runtime_trap` at the exact semantic addition operation; its repaired successor returns `i64(0)`.
- The migrated main returns `Decision.accept(27)`; disabled rollout returns `Decision.reject(RejectReason.untrusted_release)`.
- Rejection and validate-only publish no revision and consume no persistent identity.
- Historical revisions remain queryable and runnable after restart.

## Measurements

Record baseline JSON and candidate document action bytes separately, packet/view bytes by purpose, process launches, semantic rejections, correction categories, artifact bytes, reopen results, and elapsed wall time. Provider token, cache, hidden-reasoning, and price telemetry must be reported only when exposed by the harness.
